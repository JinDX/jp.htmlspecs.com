RFC 9126

OAuth 2.0 プッシュ型認可リクエスト

概要

本文書はプッシュ型認可リクエスト (PAR) エンドポイントを定義します。これにより、 クライアントは OAuth 2.0 認可リクエストのペイロードを直接リクエストによって 認可サーバーにプッシュでき、その後の認可エンドポイントへの呼び出しで データへの参照として使用されるリクエスト URI が 提供されます。¶

1. はじめに

本文書は、OAuth [RFC6749] クライアントが 認可リクエストのペイロードを直接 認可サーバーにプッシュできるようにする、プッシュ型認可リクエスト (PAR) エンドポイントを定義します。 その代わりにリクエスト URI 値を受け取ります。これは、その後ユーザーエージェントを介して 認可エンドポイントを呼び出す際に、認可リクエストのペイロードデータへの参照として使用されます。¶

OAuth [RFC6749] では、認可 リクエストパラメーターは通常、ユーザーエージェントでのリダイレクトを介して URI クエリ パラメーターとして送信されます。これは単純ですが、いくつかの課題も生じます:¶

  • 暗号学的な完全性および真正性の保護がありません。 たとえば、攻撃者は要求されたアクセスのスコープを変更したり、スコープ値を変更して 支払いトランザクションのコンテキストをすり替えたりする可能性があります。クライアント またはユーザーがこのような変更の一部を検出できるようにするプロトコル機能は存在しますが、 処理の早い段階で変更を防止する方が、より堅牢な 解決策です。¶
  • リクエスト パラメーターの機密性を確保する仕組みがありません。認可エンドポイントには HTTPS が必要ですが、 リクエストデータはユーザーエージェントを平文で通過し、クエリ文字列のデータが誤って Web サーバーのログ やリファラーを介して他のサイトに漏えいする可能性があります。個人を 特定できる情報やその他の規制対象データが認可リクエストで送信される場合（ID、オープンバンキング、 および類似のシナリオでは十分にあり得ます）、このような漏えいの影響は重大になる可能性があります。¶
  • 認可リクエスト URL は、特に きめ細かな認可データを必要とするシナリオでは非常に大きくなる可能性があり、 リクエスト処理でエラーを引き起こすことがあります。¶

JWT-Secured Authorization Request (JAR) [RFC9101] は、OAuth クライアントが認可リクエスト パラメーターを、署名され、任意で暗号化された JSON Web Token (JWT) [RFC7519] であるリクエストオブジェクトにまとめることを可能にし、セキュリティ上の課題に対する解決策を提供します。 サイズ制限に対処するため、JAR は request_uri パラメーターを導入します。これにより、 クライアントはリクエストオブジェクト自体の代わりに、リクエストオブジェクトへの参照を送信できます。¶

本文書は、認可リクエストのペイロードを 認可サーバーに直接プッシュし、その後の認可リクエストで認可サーバーにおいて使用できる request_uri 値と交換するための相互運用可能な方法を提供することで、JAR を補完します。¶

PAR は、機密性と 完全性が保護された認可リクエストを行うための簡単な手段をクライアントに提供することで、OAuth のセキュリティを促進します。 さらに高いセキュリティレベル、特に暗号学的に確認された否認防止を必要とするクライアントは、 [RFC9101] で定義される JWT ベースのリクエストオブジェクトを PAR と組み合わせて使用できます。¶

PAR により、認可サーバーはユーザーとの 対話が発生する前にクライアントを認証できます。 認可処理中にクライアントの ID に対する確信が高まることで、 認可サーバーは不正なリクエストを処理のより早い段階で拒否でき、 クライアントのなりすましや、認可リクエストの改ざんまたは悪用の試みを防止できます。¶

第3.1節 of [RFC6749] および [OIDC] の第3.1.2.1節で説明されているように、 ユーザーエージェントを介した認可エンドポイントへの HTTP POST リクエストも、 上記のリクエストサイズ制限に対処するために使用できます。しかし、[RFC6749] では任意であるにすぎず、サポートされている場合でも、 従来の Web アプリケーションでは実用的な選択肢ですが、インストール型モバイルアプリケーションで使用することは 極めて困難です。[RFC8252] で説明されているように、 これらのアプリはプラットフォーム固有の API を使用して、システムブラウザーで認可リクエスト URI を開きます。 しかし、モバイルアプリがブラウザーを起動する場合、その結果となる最初のリクエストは GET メソッドの使用に制約されます。認可リクエストに POST を使用するには、アプリがまず、 大きな認可リクエストペイロードを何らかの方法で伝達しながら、アプリが制御する URI を GET で 開くようブラウザーに指示し、その結果のレスポンスに、 認可サーバーに向けたクロスサイトのフォーム POST を開始するためのコンテンツとスクリプトを 含める必要があります。PAR はより簡単に使用でき、上記のような追加のセキュリティ上の利点があります。¶

1.1. 導入例

従来の OAuth 2.0 では、クライアントは通常、 ユーザーエージェントに、認可サーバーの認可エンドポイントに対して次のような HTTP リクエストを 行わせることで認可リクエストを開始します（追加の改行とインデントは 表示上の目的のみです）:¶

 GET /authorize?response_type=code
  &client_id=CLIENT1234&state=duk681S8n00GsJpe7n9boxdzen
  &redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb HTTP/1.1
 Host: as.example.com
¶

代わりに、このようなリクエストは、 次の例に示すように、クライアントが PAR エンドポイントに POST リクエストを送ることで 認可サーバーに直接プッシュできます（追加の改行と空白は表示上の目的のみです）。 リクエストは認可サーバーに直接行われるため、クライアントは認証できます （たとえば、ここに示す JWT クライアントアサーションベースの認証を使用します）。¶

 POST /as/par HTTP/1.1
 Host: as.example.com
 Content-Type: application/x-www-form-urlencoded

 &response_type=code
 &client_id=CLIENT1234&state=duk681S8n00GsJpe7n9boxdzen
 &redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb
 &client_assertion_type=
  urn%3Aietf%3Aparams%3Aoauth%3Aclient-assertion-type%3Ajwt-bearer
 &client_assertion=eyJraWQiOiI0MiIsImFsZyI6IkVTMjU2In0.eyJpc3MiOiJDTE
  lFTlQxMjM0Iiwic3ViIjoiQ0xJRU5UMTIzNCIsImF1ZCI6Imh0dHBzOi8vc2VydmVyL
  mV4YW1wbGUuY29tIiwiZXhwIjoxNjI1ODY4ODc4fQ.Igw8QrpAWRNPDGoWGRmJumLBM
  wbLjeIYwqWUu-ywgvvufl_0sQJftNs3bzjIrP0BV9rRG-3eI1Ksh0kQ1CwvzA
¶

認可サーバーはリクエスト URI で応答します:¶

 HTTP/1.1 201 Created
 Cache-Control: no-cache, no-store
 Content-Type: application/json

 {
   "request_uri": "urn:example:bwc4JK-ESC0w8acc191e-Y1LTC2",
   "expires_in": 90
 }
¶

クライアントはリクエスト URI 値を使用して、 ユーザーエージェントに認可サーバーの 認可エンドポイントへ次のような HTTP リクエストを行わせることで、その後の認可 リクエストを作成します（追加の改行とインデントは表示上の目的のみです）:¶

 GET /authorize?client_id=CLIENT1234
  &request_uri=urn%3Aexample%3Abwc4JK-ESC0w8acc191e-Y1LTC2 HTTP/1.1
 Host: as.example.com
¶

1.2. 規約および 用語

本文書におけるキーワード "MUST"、"MUST NOT"、"REQUIRED"、"SHALL"、"SHALL NOT"、"SHOULD"、"SHOULD NOT"、"RECOMMENDED"、"NOT RECOMMENDED"、 "MAY"、および "OPTIONAL" は、 ここに示すようにすべて大文字で記述されている場合に限り、 BCP 14 [RFC2119] [RFC8174] に 記載されているとおりに解釈されます。¶

本仕様では、「The OAuth 2.0 Authorization Framework」[RFC6749] で定義されている「アクセストークン」、 「認可サーバー」、「認可エンドポイント」、 「認可リクエスト」、「トークンエンドポイント」、 および 「クライアント」という用語を使用します。¶

2. プッシュ型認可リクエストエンドポイント

プッシュ型認可リクエストエンドポイントは、認可サーバーにある HTTP API であり、 application/x-www-form-urlencoded 形式を使用して HTTP リクエストメッセージ本文にパラメーターを含む HTTP POST リクエストを受け付けます。この形式の文字エンコーディングは UTF-8 であり、 付録 B of [RFC6749] で説明されています。PAR エンドポイント URL は "https" スキームを使用しなければ MUST なりません。¶

PAR をサポートする認可サーバーは、第5節で定義される pushed_authorization_request_endpoint パラメーターを使用して、 認可サーバーメタデータ文書 [RFC8414] にプッシュ型認可リクエストエンドポイントの URL を 含めるべきです SHOULD。¶

このエンドポイントは、認可エンドポイント用に [RFC6749] で定義された認可リクエストパラメーター、および 認可エンドポイント用に定義されたすべての適用可能な拡張を受け付けます。そのような拡張の例には、 Proof Key for Code Exchange (PKCE) [RFC7636]、Resource Indicators [RFC8707]、および OpenID Connect (OIDC) [OIDC] があります。このエンドポイントは、 [RFC9101] および本文書の 第3節 に従って、認可リクエストパラメーターの集合をリクエストオブジェクトとして 送信することも MAY サポートできます。¶

トークンエンドポイントリクエストについて [RFC6749] で定義されているクライアント認証の規則は、適用可能な 認証方式を含め、PAR エンドポイントにも適用されます。該当する場合、 token_endpoint_auth_method クライアントメタデータパラメーター [RFC7591] は、PAR エンドポイントへのリクエストを含め、 認可サーバーへ直接リクエストを行う際にクライアントが使用する登録済み認証方式を示します。 同様に、token_endpoint_auth_methods_supported 認可サーバーメタデータ [RFC8414] パラメーターは、PAR エンドポイントへの リクエストを含め、クライアントからの直接リクエストを受け付ける際に認可サーバーがサポートするクライアント認証方式を 列挙します。¶

歴史的な理由により、JWT クライアントアサーションベースの認証 （第2.2節 of [RFC7523] で定義され、[OIDC] の第9節にある private_key_jwt または client_secret_jwt 認証方式名を使用するもの）を採用する場合に使用する適切な audience 値について、曖昧さが生じる可能性があります。この曖昧さに対処するため、 [RFC8414] に従った 認可サーバーの issuer 識別子 URL を audience の値として使用するべきです SHOULD。相互運用性を促進するため、 認可サーバーは、自身を意図された audience として識別する値として、自身の issuer 識別子、 トークンエンドポイント URL、またはプッシュ型認可リクエストエンドポイント URL を受け付けなければ MUST なりません。¶

2.1. リクエスト

クライアントは、認可リクエストを構成するパラメーターを直接 PAR エンドポイントに送信します。一般的なパラメーターセットには、次の例に示すように client_id、response_type、redirect_uri、 scope、state、 code_challenge、および code_challenge_method が含まれることがあります。 ただし、プッシュ型認可リクエストは、[RFC6749] で定義されたもの、および適用可能なすべての拡張を含め、 認可エンドポイントで使用可能な任意のパラメーターから構成できます。 request_uri 認可リクエストパラメーターは例外であり、 提供しては MUST NOT なりません。¶

リクエストには、対象のクライアントに応じて、 クライアント認証に必要な追加パラメーター（たとえば、client_secret または client_assertion と client_assertion_type）も含まれます。このようなパラメーターは、 トークンエンドポイントで使用するために定義および登録されていますが、クライアント 認証にのみ適用されます。プッシュ型認可リクエストに存在する場合、それらは クライアント認証にのみ使用され、認可リクエスト自体には関係しません。クライアント 認証に関係しないトークンエンドポイントパラメーターは、プッシュ型認可リクエストにおいて定義された意味を 持ちません。client_id パラメーターは、認可リクエストと トークンエンドポイントへのリクエストの両方で同じ意味論を持つよう定義されています。必須の 認可リクエストパラメーターであるため、プッシュ型認可リクエストでも同様に必須です。¶

クライアントは、 付録 B of [RFC6749] で説明されているように、 UTF-8 の文字エンコーディングを使用し、x-www-form-urlencoded で整形したパラメーターを含む HTTP POST リクエストのメッセージ本文を構築します。 該当する場合、クライアントはトークンエンドポイントリクエストの場合と同じ規則を使用して、 認証資格情報もリクエストヘッダーまたは リクエスト本文に追加します。¶

 &redirect_uri=https%3A%2F%2Fclient.example.org%2Fcb
 &code_challenge=K2-ltc83acc4h0c9w6ESC_rEMTJ3bww-uCHaoeK1t8U

 &client_assertion_type=

¶

認可サーバーは、リクエストを 次のように処理しなければ MUST なりません:¶

  1. トークンエンドポイントと同じ方法でクライアントを認証する （第 2.3節 of [RFC6749]）。¶
  2. request_uri 認可 リクエストパラメーターが提供されている場合、リクエストを拒否する。¶
  3. プッシュされたリクエストを、認可エンドポイントに送信された 認可リクエストと同じように検証する。たとえば、認可サーバーは、 リダイレクト URI がクライアント用に設定されたリダイレクト URI のいずれかに一致するかどうかを確認し、 また、クライアントがアクセスを要求しているスコープについて認可されているかどうかも確認します。この 検証により、認可サーバーは不正または詐欺的なリクエストを 早期に拒否できます。認可サーバーは、プッシュされたリクエストを処理する際に 実行できない検証手順を MAY 省略できます。ただし、そのような確認は、 認可エンドポイントで認可リクエストを処理する際に MUST 実行しなければなりません。¶

認可サーバーは、認証資格情報を持つクライアントに対し、 プッシュ型認可リクエストごとに認可リクエスト単位のリダイレクト URI を設定することを MAY 許可できます。第2.4節でより詳しく説明されているように、これは、[RFC6749] とは異なり、本仕様が 実際の認可リクエストが行われる前に、認可サーバーがクライアントを認証し、 クライアントのリクエストを検証できるようにするため可能です。¶

2.2. 成功レスポンス

検証に成功した場合、サーバーはリクエスト URI を 生成し、201 HTTP ステータスコードとともにレスポンスで提供しなければ MUST なりません。 次のパラメーターは、[RFC8259] で定義された application/json メディアタイプを使用する HTTP レスポンスのメッセージ本文にトップレベルのメンバーとして含まれます。¶

request_uri
送信された 認可リクエストに対応するリクエスト URI。この URI は、その後の認可リクエストにおいて 対応するリクエストデータへの一度限りの参照です。認可処理が 認可リクエストデータを取得する方法は認可サーバーの裁量に委ねられ、 本仕様の範囲外です。この URI を介して認可リクエストデータを 他の当事者が利用できるようにする必要はありません。¶
expires_in
リクエスト URI の有効期間を 秒単位の正の整数として表す JSON 数値。リクエスト URI の有効期間は 認可サーバーの裁量に委ねられますが、通常は比較的短いものです（たとえば、 5 秒から 600 秒の間）。¶

request_uri 値の形式は 認可サーバーの裁量に委ねられますが、有効な値を予測または推測することが 計算上実行不可能となるよう、暗号学的に強力な疑似乱数アルゴリズムを使用して生成された 一部を含まなければ MUST なりません（詳細については 第 10.10節 of [RFC6749] を参照してください）。 認可サーバーは、対応する認可リクエストデータを参照する URI のランダム部分として <reference-value> を使用し、 urn:ietf:params:oauth:request_uri:<reference-value> の形式で request_uri 値を構築することが MAY できます。¶

request_uri 値は、 認可リクエストを送信したクライアントに結び付けられなければ MUST なりません。¶

次は、そのようなレスポンスの例です:¶

 HTTP/1.1 201 Created
 Content-Type: application/json
 Cache-Control: no-cache, no-store

 {
  "request_uri":
    "urn:ietf:params:oauth:request_uri:6esc_11ACC5bwc014ltc14eY22c",
  "expires_in": 60
 }
¶

2.3. エラーレスポンス

認可サーバーは、第5.2節 of [RFC6749] でトークンエンドポイントからのエラーレスポンスについて 規定されているものと同じ形式で、その節または 第4.1.2.1節 of [RFC6749] にある適切なエラーコードを使用して エラーレスポンスを返します。第 4.1.2.1節 of [RFC6749] が、要求元クライアントへの エラーによる自動リダイレクトを禁止し、そのためエラーコードを定義していない場合 （たとえば、リダイレクト URI の欠落、無効、または不一致によりリクエストが失敗した場合）、 invalid_request エラーコードをデフォルトのエラーコードとして使用できます。 プッシュされた認可リクエストの初期処理にその拡張が関与する場合、 OAuth 拡張で定義されたエラーコードも使用できます。プッシュ型認可リクエストの 初期処理にはリソース所有者との対話が含まれないため、[OIDC] で定義される consent_required など、 ユーザーとの対話に関連するエラーコードは返されません。¶

認可サーバーまたはクライアントポリシーによって、 クライアントに署名済みリクエストオブジェクトの使用が要求される場合（[RFC9101], 第10.5節 を参照）、認可サーバーは 第3節で示された定義に準拠するリクエストのみを MUST 受け付け、その他のリクエストは HTTP ステータスコード 400 および エラーコード invalid_request で MUST 拒否しなければなりません。¶

上記に加えて、PAR エンドポイントは次の HTTP ステータスコードも使用できます:¶

405:
リクエストが POST メソッドを使用していない場合、認可サーバーは HTTP 405 (Method Not Allowed) ステータスコードで応答します。¶
413:
リクエストサイズが認可サーバーの 許容する上限を超えた場合、認可サーバーは HTTP 413 (Payload Too Large) ステータスコードで応答します。¶
429:
特定の期間内にクライアントから送信された リクエスト数が認可サーバーの許容数を超えた場合、 認可サーバーは HTTP 429 (Too Many Requests) ステータスコードで応答します。¶

次は PAR エンドポイントからのエラーレスポンスの例です:¶

 HTTP/1.1 400 Bad Request
 Content-Type: application/json
 Cache-Control: no-cache, no-store

 {
   "error": "invalid_request",
   "error_description":
     "The redirect_uri is not valid for the given client"
 }
¶

2.4. クライアント リダイレクト URI の管理

OAuth 2.0 [RFC6749] は、 特定の状況でクライアントが未登録の redirect_uri 値を使用すること、または 認可サーバーが、認可エンドポイントでクライアントから提示された redirect_uri 値に 独自の一致規則を適用することを許可しています。しかし、OAuth security BCP [OAUTH-SECURITY-TOPICS] および OAuth 2.1 仕様 [OAUTH-V2] は、認可サーバーが redirect_uri パラメーターを、特定のクライアントについて事前に設定された リダイレクト URI の集合と完全一致させることを要求しています。これは、クライアントなりすましの試みを 早期に検出するための手段であり、トークン漏えいおよびオープンリダイレクトを防止します。一方で、 リダイレクト URI は通常、クライアントポリシーの中で最も変動しやすい部分であるため、 クライアント管理がより煩雑になる可能性があります。¶

認可サーバーとの認証資格情報を確立済みのクライアントが PAR を使用する場合、完全一致要件は MAY 緩和できます。 これは、従来の認可リクエストとは異なり、認可サーバーが認可処理開始前に クライアントを認証し、正当なクライアントと対話していることを確認できるため可能です。 認可サーバーは、そのようなクライアントに対し、認可サーバーに事前登録されていない redirect_uri 値を指定することを MAY 許可できます。これによりクライアントの柔軟性が高まり （たとえば、実行時に認可サーバーごとに異なる redirect_uri 値を生成できるようになり）、 クライアント管理を簡素化できます。提供された redirect_uri 値に 制限を適用するかどうかは認可サーバーの裁量に委ねられます。たとえば、認可サーバーは 特定の URI プレフィックスを要求したり、実行時にクエリ パラメーターだけが変更されることを許可したり MAY できます。¶

注: トランザクション固有のリダイレクト URI を設定できることは、 クライアント ID と対応する資格情報およびポリシーが 信頼できる第三者によって管理される状況、たとえばクライアント権限を含むクライアント証明書を介して管理される場合にも 有用です。このように外部で管理されるクライアントは、 追加の登録手順を必要とせず、対応する第三者を信頼する 認可サーバーと対話できます。¶

4. 認可リクエスト

クライアントは、認可サーバーから返された request_uri 値を使用して、 [RFC9101] で定義された認可リクエストを構築します。次の例では、 クライアントがユーザーエージェントに次の HTTP リクエストを行わせます （追加の改行とインデントは表示上の目的のみです）:¶

 GET /authorize?client_id=s6BhdRkqt3&request_uri=urn%3Aietf%3Aparams
  %3Aoauth%3Arequest_uri%3A6esc_11ACC5bwc014ltc14eY22c HTTP/1.1
 Host: as.example.com
¶

認可リクエスト内容の一部、たとえば code_challenge パラメーター値は特定の認可リクエストに固有であるため、クライアントは request_uri 値を一度だけ使用しなければ MUST なりません。認可サーバーは request_uri 値を一度限りの使用として扱うべきですが SHOULD、ユーザーがユーザーエージェントを再読み込み／更新したことによる 重複リクエストを MAY 許可できます。有効期限が切れた request_uri は無効として拒否しなければ MUST なりません。¶

認可サーバーは、プッシュされたリクエストから生じる認可リクエストを、 その他の認可リクエストと同様に検証しなければ MUST なりません。 認可サーバーは、リクエストがプッシュされた際に実行した検証手順を MAY 省略できます。ただし、それがプッシュされたリクエストであること、および リクエストまたは認可サーバーのポリシーが、省略した手順の結果に影響を与える形で 変更されていないことを検証できることが条件です。¶

認可サーバーポリシーは、全体またはクライアント単位で、 クライアントが認可リクエストデータを渡す唯一の手段として PAR を使用するよう定めることが MAY できます。この場合、認可サーバーは PAR エンドポイントから取得した値を持つ request_uri パラメーターがない認可エンドポイントへのリクエストの処理を、 invalid_request エラーコードを使用して拒否します。¶

注: 認可サーバーとクライアントは、望ましい動作を通知するため、 第5節 および 第6節で定義されたメタデータを MAY 使用できます。¶

5. 認可サーバーメタデータ

PAR に関するサーバーの能力およびポリシーを示すため、 次の認可サーバーメタデータパラメーター [RFC8414] が導入されます。¶

pushed_authorization_request_endpoint
クライアントが認可リクエストを送信し、 認可サーバーで使用可能な request_uri 値と交換できる プッシュ型認可リクエストエンドポイントの URL。¶
require_pushed_authorization_requests
認可サーバーが PAR を介してのみ認可リクエストデータを受け付けるかどうかを示すブール値パラメーター。 省略した場合、デフォルト値は false です。¶

pushed_authorization_request_endpoint が存在するだけで、 クライアントが PAR フローを使用できると判断するには十分であることに注意してください。PAR エンドポイントから 取得した request_uri 値は、request_uri_parameter_supported や require_request_uri_registration [OIDC.Disco] などの他の認可サーバーメタデータに関係なく、 認可エンドポイントで使用できます。¶

6. クライアントメタデータ

Dynamic Client Registration Protocol [RFC7591] は、OAuth 2.0 クライアントメタデータを 認可サーバーに動的に登録するための API を定義します。[RFC7591] で定義されたメタデータ、および登録されたその拡張は、 Dynamic Client Registration Protocol を使用しない場合でも、 認可サーバー実装に有用なクライアントの一般的なデータ モデルも暗黙に示しています。このような実装には通常、クライアント設定を 管理するための何らかのユーザーインターフェースがあります。本文書では、 特定のクライアントについてプッシュ型認可リクエストが必要かどうかを示すため、 次のクライアントメタデータパラメーターを導入します。¶

require_pushed_authorization_requests
クライアントが認可リクエストを開始するために 使用を許可される唯一の手段が PAR であるかどうかを示すブール値パラメーター。省略した場合、 デフォルト値は false です。¶

7. セキュリティに関する考慮事項

7.1. リクエスト URI の推測

攻撃者は、有効なリクエスト URI 値を推測してリプレイし、 対応するクライアントになりすまそうとする可能性があります。 認可サーバーは、リクエスト URI のエントロピーについて JAR [RFC9101], 第 10.2節 の (d) 項で示されている考慮事項を考慮しなければ MUST なりません。¶

7.2. オープンリダイレクト

攻撃者は、認可コードを取得したりユーザーに対して他の攻撃を 実行したりするため、自身の制御下にあるサイトを指すリダイレクト URI を登録しようとする可能性があります。 認可サーバーは、認証済みクライアントからのプッシュ型認可リクエストに含まれる 新しいリダイレクト URI のみを受け付けなければ MUST なりません。¶

7.3. リクエストオブジェクトのリプレイ

攻撃者は、正当な 認可リクエストから取得したリクエスト URI をリプレイする可能性があります。このような攻撃に対処するため、 認可サーバーはリクエスト URI を一度限りの使用にするべきです SHOULD。¶

7.4. クライアントポリシーの変更

リクエストオブジェクトの登録と、 特定のリクエストオブジェクトを使用する 認可リクエストとの間に、クライアントポリシーが変更される可能性があります。そのため、 認可リクエストを処理する際、認可サーバーが リクエストパラメーターをクライアントポリシーと照合することが推奨されます。¶

7.5. リクエスト URI のすり替え

攻撃者は、あるリクエストからリクエスト URI を取得し、 それを別の認可リクエストに差し替える可能性があります。たとえば OpenID Connect のコンテキストでは、 攻撃者は、高い認証保証レベルを要求するリクエスト URI を、 より低い保証レベルを要求するものに置き換える可能性があります。クライアントは、 この攻撃を防止するため、プッシュされたリクエストオブジェクト内で PKCE [RFC7636]、一意の state パラメーター [RFC6749]、または OIDC の "nonce" パラメーター [OIDC] を使用するべきです SHOULD。¶

8. プライバシーに関する考慮事項

OAuth 2.0 は、あるエンティティが他の2つの エンティティ間のデータアクセスに対するユーザー認可を仲介するという性質そのものにより、 広範なプライバシー上の影響を持つ複雑で柔軟なフレームワークです。 OAuth 全体のプライバシーに関する考慮事項は、より大きなフレームワーク内の 1つのメッセージシーケンスを開始する代替方法だけを定義する本文書の範囲外です。ただし、 PAR を使用すると、認可リクエストデータを、 ユーザーエージェントを平文で通過する URL のクエリコンポーネントではなく、 HTTP リクエストのメッセージ本文で安全な接続を介してクライアントと認可サーバーの間で直接渡すため、 意図しない情報漏えいの可能性を減らし、プライバシーを向上できる場合があります。¶
