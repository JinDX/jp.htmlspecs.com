概要

広く普及している WOFF 1.0 での経験に基づき、 この仕様は圧縮率を向上させ、 ネットワーク帯域の使用量を減らしつつ、 モバイル機器でも高速に展開できるよう策定された。 これは内容を考慮した前処理と、 改善されたエントロピー符号化を組み合わせることで、 WOFF 1.0 が使用する Flate 圧縮より優れた圧縮を実現する。

1. はじめに

この文書は WOFF2 フォントパッケージ形式を規定する。この形式は、 比較的容易に実装でき、従来の技術より 大幅に優れた圧縮率でフォントデータを圧縮し、 CSS @font-face 規則で使用できるよう設計された。従来の WOFF 1.0 形式 [WOFF1] と比べた圧縮率の向上は、 改善されたエントロピー符号化と、フォントデータの前処理および 最適化により、各種フォントデータ構造に内在する冗長性を減らすことで実現する。 WOFF 2.0 の開発経緯の詳細は WOFF 2.0 評価報告書 [WOFF2ER] にある。

2. 一般要件

WOFF2 形式の主な目的は、CSS の @font-face 規則でウェブ文書にリンクされたフォントを効率よくパッケージ化することである。 リンクされたフォントに WOFF2 形式をサポートするユーザーエージェントは、 CSS3 Fonts 仕様の要件に従わなければならない （[CSS3-Fonts] 4.1 節：@font-face 規則）。特に、 このようなリンクされたフォントは、 それを参照する文書だけで使用でき、 利用者のシステム上の他のアプリケーションや文書で利用可能にしてはならない。

入力フォントファイルは、 [OFF] 仕様の第 5 章に記載された各種のフォントデータテーブルを含み得る。 ファイル内のテーブルの順序は様々であり、テーブルディレクトリーのエントリーは タグの昇順に並べる必要があるが、実際のテーブルはファイル内に 任意の順序で配置できる。

WOFF2 ファイルを展開するとき、デコーダーはテーブルディレクトリーのエントリーを テーブルタグのアルファベット昇順に並べなければならず、ファイル内のテーブル順序を、 [OFF] の推奨事項（8.1 項「最適化されたテーブル順序」）に 従って配置することが望ましい。

3. ファイル全体の構造と基本データ型

WOFF2 ファイルの構造は SFNT や WOFF 1.0 と同様に、 ヘッダー、テーブルディレクトリー、各テーブルの データが順に続く。SFNT 構造は TrueType [TrueType]、OpenType [OpenType]、ISO「Open Font Format」 [OFF] の各仕様で完全に説明される。ただし、 WOFF2 は重要な点で SFNT と異なる。特に、 フォントテーブルのデータは全テーブルを含む単一のデータストリームに圧縮される。 WOFF 1.0 と同様に、省略可能な拡張メタデータとプライベートデータはそれぞれ 独立したデータブロックとなり、連結されて WOFF 2.0 ファイルを構成する。 圧縮フォントデータストリームと拡張メタデータブロックに使う 圧縮アルゴリズムはいずれも Brotli [Brotli] である。

完全な WOFF2 ファイルは複数のデータブロックから成る。48 バイトのヘッダーの直後に、 可変長のテーブルディレクトリー、省略可能なコレクション ディレクトリー（入力がフォントコレクションの場合のみ）、圧縮フォントデータブロック、 省略可能な拡張メタデータブロックとプライベートデータブロックがこの順に続く。 テーブル長またはブロックオフセットの 4 バイト境界への整列が指定された位置で、 最大三つのゼロバイトでパディングする場合を除き、 データブロック間、 WOFF2 ヘッダーとテーブルディレクトリーの間、または最後の ブロックやテーブルの後に、余分なデータがあってはならない。 そのようなデータがあれば、 適合するユーザーエージェントはファイルを無効として拒否しなければならない。また、 いずれかのデータブロックやフォントテーブルのオフセットと長さが、 重なり合うバイト範囲、またはファイルの末尾を 超える範囲を示す場合も、ファイルを無効として拒否しなければならない。

255UInt16 データ型

255UInt16 は、0 から 65535 まで（両端を含む）の 符号なし整数の可変長符号化である。通常は UInt16 で表されるが 比較的小さい値を取る各種フォント値の 中間表現を意図した型である。符号化する値に応じて、 フィールド長は 1～3 バイトとなる。最初のバイトは、 小さい値自体を表すか、追加のバイトの形式を定める コードとして扱われる。255UInt16 形式の読み取り方法を示す C 風の疑似コードを以下に示す：

    Read255UShort( data )
    {
        UInt8 code;
        UInt16 value, value2;

        const oneMoreByteCode1    = 255;
        const oneMoreByteCode2    = 254;
        const wordCode            = 253;
        const lowestUCode         = 253;

        code = data.getNextUInt8();
        if ( code == wordCode ) {
            /* Read two more bytes and concatenate them to form UInt16 value*/
            value = data.getNextUInt8();
            value <<= 8;
            value &= 0xff00;
            value2 = data.getNextUInt8();
            value |= value2 & 0x00ff;
        }
        else if ( code == oneMoreByteCode1 ) {
            value = data.getNextUInt8();
            value = (value + lowestUCode);
        }
        else if ( code == oneMoreByteCode2 ) {
            value = data.getNextUInt8();
            value = (value + lowestUCode*2);
        }
        else {
            value = code;
        }
        return value;
    }

符号化は一意ではない。例えば値 506 は、 [255, 253]、[254, 0]、[253, 1, 250] と符号化できる。エンコーダーはいずれを 生成してもよいが、 デコーダーはすべてを受け入れなければならない。エンコーダーは短い符号化を 選ぶことが望ましく、同じ値には常に同じ符号化を選ばなければならない。 その方が圧縮しやすい傾向があるためである。

UIntBase128 データ型

UIntBase128 は、最大 232-1 までの値に適した、 別の符号なし整数の可変長符号化である。UIntBase128 の数値は、 最後以外の全バイトの最上位ビットを 1、 最後のバイトの最上位ビットを 0 としたバイト列である。値自体は基数 128 で、 各バイトの下位 7 ビットに符号化される。したがって、 デコード手順は次のとおりである。value = 0 から始め、1 バイト読み、value を 以前の value × 128 +（そのバイトと 127 のビット論理積）にする。 そのバイトの最上位ビットが false になるまで繰り返す。

UIntBase128 では、例えば先行するゼロを使って 同じ数値を異なるバイト数で表すような、 最適でない符号化が可能になる。例えば値 63 は 1 バイトの 0x3F、 または 2 バイト以上の [0x80, 0x3f] で表せる。エンコーダーはこれを許してはならず、 可能な限り短い符号化を生成しなければならない。デコーダーは、 先行ゼロのある UintBase128 値 （バイト 0x80 で始まる値）、5 バイトを超える UintBase128 列、 または 232-1 を超える UintBase128 値に遭遇したら、フォントファイルを拒否しなければならない。以下に、 UIntBase128 の読み取り方法を示す C 風の疑似コードを示す：

    bool ReadUIntBase128( data, *result )
    {
        UInt32 accum = 0;

        for (i = 0; i < 5; i++) {
            UInt8 data_byte = data.getNextUInt8();

            // No leading 0's
            if (i == 0 && data_byte == 0x80) return false;

            // If any of top 7 bits are set then << 7 would overflow
            if (accum & 0xFE000000) return false;

            *accum = (accum << 7) | (data_byte & 0x7F);

            // Spin until most significant bit of data byte is false
            if ((data_byte & 0x80) == 0) {
                *result = accum;
                return true;
            }
        }
        // UIntBase128 sequence exceeds 5 bytes
        return false;
    }

3.2. WOFF2 ヘッダー

WOFF 2.0 ヘッダーは識別用シグネチャーを含み、 格納するフォントデータの圧縮後と圧縮前の サイズを提供する。また、WOFF 2.0 ファイルに含む フォントデータの種類とバージョン番号、および ファイル内の追加データブロックへのオフセットを示す。

WOFF2 ヘッダーの解釈は、 [WOFF1] の WOFF ヘッダーと同じだが、 totalCompressedSize フィールドが一つ追加される。 WOFF2 ヘッダーの signature フィールドは、 0x774F4632（'wOF2'）でなければならない。これにより WOFF 1.0 と区別する。このフィールドが この値でなければ、ユーザーエージェントはファイルを無効として拒否しなければならない。 有効な WOFF 2.0 ファイルでは、 予約フィールドをゼロにしなければならないが、デコーダーは、 ヘッダーの予約値がゼロでないことを理由に、 ダウンロードしたフォントを拒否してはならない。ユーザーエージェントは、 正しくデコードされたフォントのサイズが WOFF2 ヘッダー内の totalSfntSize 値と一致しなくても、そのフォントを拒否してはならない。

WOFF2 ヘッダーの「totalSfntSize」は、 参照用に過ぎない。非圧縮の入力フォントのサイズを表す場合もあるが、変換済みの 'glyf' と 'loca' テーブルがある場合、再構築テーブルの非圧縮サイズと 展開後のフォント全体のサイズは、ヘッダーに指定された元の総サイズから 大きく異なる可能性がある。

4. フォントディレクトリー

フォントディレクトリーは、入力ファイル内の一意な各フォントテーブルに 一つのエントリーを持つテーブルディレクトリーから成り、入力がコレクションなら、 省略可能なコレクションディレクトリーテーブルも含み得る。

4.1. テーブルディレクトリーの形式

テーブルディレクトリーは、以下に定義する WOFF2 ディレクトリーエントリーの 配列である。WOFF2 ヘッダーの直後に続くため、 ヘッダーにはこのブロックへの明示的なオフセットはない。 サイズは内容次第なので、デコードでは ランダムアクセスを試みるより、 ストリームとして処理するのが最善である。各エントリーは一つのフォントテーブルの 元のサイズと、追加の変換を施した場合は、 変換後のサイズを指定する。変換済みテーブルは 'flags' フィールドで識別する。 これは既知のタグ（ビット 0～5、「既知のテーブルタグ」参照）と変換の バージョン番号（ビット 6、7、後述）を組み合わせて変換を定める。 タグと変換バージョン番号の組み合わせで、 適用した変換を特定する。現在の変換の詳細は、 この仕様の第 5 章にある。

元の入力フォントのテーブルディレクトリーエントリーが アルファベット昇順なのに対し、 WOFF2 のエントリーは、テーブルを処理して 圧縮ストリームに符号化した物理的な順序を定める。 展開時に再構築したテーブルディレクトリーを ソートして並べ直すのはデコーダーの責任である。

デコードを簡単にするため、エンコーダーは 変換済みテーブルを並べ替え、 関連する 'glyf' と 'loca' が常に対となり、 'loca' が 'glyf' の後に続くようにしなければならない。 変換済み 'loca' のエントリーは、再構築に必要なサイズを示す プレースホルダーであり、ストリーム内のバイトを消費しない点に注意する。 したがって、ディレクトリー内で 'loca' を変換済み 'glyf' の 直後に置く要件により、'loca' 再構築処理を実装しやすくなる。 これは 'glyf' に逆変換（詳細は5.1 項）を 適用するときに行う。テーブル順序の制約の詳細は 5.5 項を参照。

flags の解釈は次のとおり。ビット [0..5] は、フォントに現れやすいタグを 列挙した「既知のタグ」テーブルのインデックスを持つ。タグが そこになければ、このフィールドは 63 となる。ビット 6 と 7 は、 各テーブルに適用した前処理変換のバージョン番号（0～3）を示す。 'glyf' と 'loca' 以外の全テーブルでは、変換バージョン 0 は、 ヌル変換を意味する。元のテーブルデータを Brotli 圧縮器に直接渡し、圧縮ストリームに含める。 'glyf' と 'loca' では、変換バージョン 3 がヌル 変換を意味し、元データを Brotli 圧縮器に直接渡し、 5.1 項と 5.3 項で定義する前処理は適用しない。 変換済みテーブルの形式と対応する変換バージョン番号は、 この仕様の第 5 章で詳述する。

あるテーブルに複数の変換バージョンがあれば、エンコーダーは通常、 変換後のテーブル長を最小にするバージョンを選ぶことが望ましい。 ただし、削減がごくわずかで意味がない場合を除く。

あるタグに複数の変換バージョンがあれば、エンコーダーは、 入力に適用できる定義済み変換のいずれを使ってもよい。デコーダーは、 定義されたどの変換も 受け入れられなければならない。 デコーダーが、 未知の変換バージョン番号を指定するエントリーに遭遇した場合、 フォント全体を拒否しなければならない。正しくデコードできないためである。

既知のタグで符号化するか、4 バイトのタグを明示的に 含めるかに意味上の違いはない。圧縮効率を高めるための 符号化の選択に過ぎない。同様に、ある 4 バイトのタグが 「既知のテーブルタグ」にあるかどうかは、 そのタグをウェブフォントに含めるべきかについての規範的な声明ではない。エンコーダーは、入力テーブルのタグが 「既知のテーブルタグ」にある場合、既知のテーブルフラグを使わなければならない。

既知のタグ一覧にない独自タグ （または将来定義される新しい標準タグ）には、あらかじめ定義した拡張機構がある。 flags バイトのビット [0..5] が 63（0x3f）なら、 その後に任意の 4 バイトタグが続く。それ以外では、 TableDirectoryEntry の tag を省略し、flags のビット [0..5] から、 以下の固定の「既知のテーブルタグ」を用いて導出する。デコーダーは、 独自タグを使って定義されたエントリーを、 後続タグが既知のテーブルタグの一つと 認識されても、受け入れてよい。

変換済みテーブルの再構築は機能の保持を保証するが、 元データとは異なるバイナリー結果を 生成することがある。例えば 'glyf' の輪郭点座標は 1 または 2 バイトで 符号化でき、反復する値は座標ストリームに明示的に 繰り返すことも、省略することもできる（制御点の フラグバイトで示す）。そのため輪郭点には、 同じ描画結果を生む複数の表現があるが、再構築したレコードの バイナリーは元データと大きく異なる場合がある。詳細は、 ISO「Open Font Format」[OFF] 仕様の 5.3.3 項を参照。

このため、変換済みテーブルの origLength は参照用とし、 WOFF2 データのデコード時にメモリー割り当てを 決定する根拠にすべきではない。

4.2. コレクションディレクトリーの形式

コレクションディレクトリーは入力がコレクションの場合、すなわち WOFF2 ヘッダーの flavor が 0x74746366（'ttcf'）の場合だけ存在する。存在する場合はテーブルディレクトリーの 直後に置き、CollectionHeader と一つ以上の CollectionFontEntry から成る。

入力がコレクションなら、テーブルディレクトリーには、 各テーブルが複数のフォントで共有されるかに関係なく、 コレクション内の一意なテーブルごとに一つのエントリーがある。したがって WOFF2 で 圧縮したコレクションのディレクトリーは、ファイル内の 全フォントの全テーブルを含む。

コレクションディレクトリーはヘッダーで始まり、コレクションの フォントエントリー配列が続く。

コレクションのフォントエントリーは、各フォント（個数は CollectionHeader の numFonts で定義）を指定する。各エントリーの形式は次のとおり：

元のコレクションで複数の Offset Table が同じテーブルのオフセットを参照する場合、 そのテーブルは「共有」とみなす。エンコーダーは、 オフセットで定まる一意な各テーブルに一つの TableDirectoryEntry を出力しなければならない。 複数フォントで共有するかどうかは問わない。 すなわち、複数フォントの対応する Table Record が 同じオフセットの共有テーブルを参照する場合、 WOFF2 圧縮ストリーム内でデータを重複させてはならない。

入力が複数の一意な glyf と loca を含むコレクションなら、 変換、すなわち glyf と loca の変換を、 それぞれの対に 適用しなければならない。glyf と loca の共有は 許され、推奨される（コレクションの大きな利点の一つである）。ただし、 共有できない glyf ／loca の対が二つ以上ある場合もある。共有する場合、エンコーダーは、 両方が共有され、関連する対を 構成することを検証しなければならない（glyf ／loca が複数対ある場合）。また、 glyf または loca の一方だけを共有するフォントを 含むコレクションを拒否しなければならない。

コレクションを処理するとき、エンコーダーは 入力コレクションの内部フォントの順序を保持しなければならず、 各フォントの CollectionFontEntry に対応する TableDirectoryEntry のインデックスを記録しなければならない。

デコーダーは、同じ数のフォントと 対応する Offset Table を持つコレクションを復元しなければならない。出力の 各フォントの Offset Table は、 入力と同じ numTables、または元の Offset Table に DSIG があれば 一つ少ない値を持たなければならない。CollectionHeader 内の TTC ヘッダーのバージョンが 2.0 なら、デコーダーは出力 TTC ヘッダーの {ulDsigTag, ulDsigLength, ulDsigOffset} を null にするか、TTC ヘッダーをバージョン 1（0x00010000）に変換しなければならない。

コレクションを処理するとき、デコーダーは 入力と同じ内部フォントの順序を再現しなければならない。各内部フォントの テーブルは並べ替えてよい。複数の 'glyf'/'loca' の対を持つコレクションでは、デコーダーは CollectionFontEntry のインデックスを調べ、参照する両テーブルが互いに対であることを確認し、 対応しなければコレクションを拒否しなければならない。対についての詳細は、 テーブルディレクトリーの説明を参照。 適合ユーザーエージェントは、WOFF2 デコーダーが生成する正しい形式の フォントコレクションを読み込んで使用できなければならない。

5. 圧縮データ形式

WOFF2 の CompressedFontData は各テーブルのデータを、 WOFF2 テーブルディレクトリーのエントリーの 順で連結したものを含む。 展開後のストリームのテーブル間には、 ディレクトリーで定義されない余分なデータがあってはならない。 そのようなデータがあれば、 適合ユーザーエージェントはファイルを無効として拒否しなければならない。 CompressedFontData ストリームは Brotli 圧縮アルゴリズム [Brotli] で圧縮しなければならない。どのような理由でも データブロックの展開に失敗した場合、WOFF2 ファイルは無効であり、 読み込んではならない。

WOFF2 のテーブルデータのデコードは、 CompressedFontData のバイトレベル圧縮を展開して 「テーブルデータブロック」を得た後、以下の 追加デコードを適用する手順として規定できる。実装は手順を統合したり、 一部を逐次的またはストリーミングで処理してもよいが、 結果はここに規定する順次処理と一致しなければならない。

一部のテーブル（タグで識別する glyf、loca、 hmtx など）には追加の変換を 行う。変換しない場合、データはそのまま 圧縮ストリームに現れ、テーブルデータブロックの origLength バイトを 占める。変換の有無とバージョンは flags の最上位 2 ビットで 定義する（4.1 項を参照）。 変換するデータには以下の変換を追加で適用し、 この場合は transformLength バイトを占める。

展開・再構築した テーブルデータは [OFF] 仕様の形式で格納しなければならない。各 再構築エントリーは有効な checkSum を持たなければならず、 デコーダーは各テーブルの checkSum を再計算しなければならない。 また、glyf と loca への 変更を伴う変換により、デコーダーは、 フォント全体の checkSumAdjustment を再計算し、 更新値を head に格納しなければならない。

変換済みテーブルの有無を既知のタグのフラグ値だけで 判断すべきではない。例えば glyf は、 flag = 10 で tag なし、または flag = 63 で 'glyf' タグが続く形で表せる。変換バージョンを 定める flags とタグの組み合わせで適用した変換を判断する。

ディレクトリー内の origLength （非変換テーブル）と transformLength（変換済みテーブル）の 合計は、 [Brotli] で展開したデータブロックのサイズと等しくなければならない。 展開後のサイズが上述のディレクトリーの 長さの合計と一致しなければ、 WOFF2 ファイルを読み込んではならない。

現行 WOFF2 では、次の三種のテーブルに変換を適用できる： 輪郭データの glyf、loca （glyf 内の各字形のオフセット）、および 水平メトリクスの hmtx。フォントに存在する場合に適用する。 オーサリングツールは、 5.3 項と 5.5 項の追加制約を考慮して、適用可能な変換を使える。glyf の変換は 5.1 項、loca の 変換は5.3 項、 hmtx の変換は 5.4 項で規定する。

CFF テーブルの処理とサブルーチン展開。

CFF 輪郭を持つ OpenType の大半は、格納を小さくするため CFF データを サブルーチン化している。WOFF2 の開発と評価の 実験では、エンコード前に CFF のサブルーチンを展開すると、 Brotli が効率よく働き、WOFF2 の圧縮率が 向上して、圧縮サイズが平均 5～10% 小さくなると分かった。 ただし、CFF サブルーチンの展開は同時に、 出力ファイルを約 10% 大きくする。

CFF の前処理／サブルーチン展開は、WOFF2 エンコード前の 外部処理なので、この仕様の対象外である。 フォント製作者は制作工程を最適化し、 出力 CFF が大きくなる代わりに圧縮サイズを減らして ウェブ転送を高速化する（描画性能も向上する）か、 サブルーチン化を保って入出力サイズを最小化するかを選べる。

WOFF 2.0 の変換は、SFNT に内在する冗長性を 減らし、または除去し、フォントデータストリームを再構成して エントロピー符号化を効率化する。再構築データは、 入力フォントの機能を完全に保持するが、 'glyf' の輪郭座標の最適化の程度や、 'loca' のオフセット計算の違いなど、 符号化の差異があり得るため、デコーダーごとの出力が 入力とビット単位で一致するとは限らない。入力のテーブルは、 エンコードの一部として並べ替えられる場合も、 デコーダーによって [OFF] 推奨の順序に並べ替えられる場合もある – その結果、 内容が変わらなくてもオフセットが変わることがある。 エンコード前後のバイナリーデータの差異は、 主に最適化や並べ替えによるわずかなものでも、 既存の DSIG を無効にする。したがって適合エンコーダーは、 入力フォントから DSIG テーブルを 除去しなければならない。変換とエントロピー符号化はその後に行う。

WOFF 2.0 エンコーダーはさらに、 head の flags のビット 11 を設定しなければならない （[OFF] 参照）。これは、 再生成したフォントに可逆的な変更を伴う変換を施したことを示す。

5.1. 変換済み glyf テーブル形式

glyf は WOFF2 内で二つの形式のいずれかを取り、 変換バージョン（ディレクトリーのフラグビットに符号化、 4.1 項参照）で定まる。バージョン 3 は ヌル変換で、glyf の内容を 元の未変更の形式で表す。以下のバージョン 0 は 省略可能で、glyf 内の冗長性を除去するために使える。

この項の glyf 変換バージョン 0 （ディレクトリーのフラグで定義、4.1 項参照）は、 冗長な情報を減らし、 TrueType 字形輪郭を効率的に符号化することを意図する。 この変更した変換は MicroType Express [MTX] の類似変換に基づく。 MTX の参照は参考情報である。変更した変換の詳細は 以下に規定し、この節は規範的である。

glyf の変換は各字形の機能と描画の忠実性を保つが、 元のフォントとバイナリーが一致しない 新しい字形レコードを生成する可能性が高い。 [OFF] 5.3.3 項の規則では、 一つのレコードに複数の有効な再構築があり得る。状況や 再構築した glyf データへの最適化の程度によって、再構築サイズは、 入力の元の glyf より大きく、小さく、または等しくなり得る。 この仕様も [OFF] も、 特定の最適化を義務付けない。したがって WOFF2 デコーダーの 実装は、字形レコードを再構築するとき十分な メモリーを確保する責任がある – 元の glyf サイズを示す、変換済み glyf の origLength は、 参照値としてのみ使用できる。

字形レコードの再構築の実装方法や、 再構築した glyf データの最適化の程度に関係なく、 ユーザーエージェントは、 再構築した glyf のサイズが、 WOFF2 ディレクトリーの glyf エントリーの origLength と一致しないことを理由に、正しくデコードしたフォントを拒否してはならない。

圧縮効率を高めるため、glyf を 複数のサブストリームに分け、同種のデータをまとめる。変換後のテーブルは、 各サブストリームのサイズを示すフィールドと、 順に続くサブストリームから成る。デコードでは逆変換し、 各サブストリームのデータを再結合して、元の glyf の各エントリーの完全なレコードを作る。

この形式は、特に有効・無効なデータの判断を含む デコード過程の説明によって最もよく特徴付けられる。また、 特定のバイト列ではなく意味レベルで結果を規定する点に注意する。

変換済み glyf には、 bboxBitmap があり、各字形の バウンディングボックスが明示的に符号化されるか、 座標から導出するかを示す。エンコーダーとデコーダーの両方が、 その状態を決める計算を行う必要がある。各 単純字形について、 エンコーダーは全輪郭点（曲線上・曲線外の両方）から xMin、yMin、xMax、yMax を計算し、 符号化済みのボックス情報と比較しなければならない。一致すれば、 その情報を省略しなければならない。一致しない場合は、 計算した 値がフォント内の値と異なるため、 対応する bboxBitmap のビットを設定し、 元の値を bboxStream に記録しなければならない。 輪郭数ゼロのレコードでは、 全ボックス値がゼロか確認し、そうでなければ、 入力を無効として拒否しなければならない。空の字形または 輪郭数ゼロの字形では、 対応する bboxBitmap のビットを常にクリアしなければならない。 複合字形では、 対応する bboxBitmap のビットを常に設定し、 元の値を bboxStream に記録しなければならない。

ボックスを導出する場合、デコーダーも同様の 計算を行わなければならない。字形に対応する bboxBitmap のビットが未設定なら、 デコード時に全輪郭点の座標から xMin、yMin、 xMax、yMax を計算しなければならない。bboxBitmap の総バイト数は 4 * floor((numGlyphs + 31) / 32) である。ビットは、 字形 0 が最初のバイトの最上位、 字形 7 が最初のバイトの最下位、 字形 8 が 2 バイト目の最上位となるよう 詰める。ビット値 1 は明示的なボックスを示す。

変換済み glyf を読むと、デコードは 字形ごとに反復する。各字形について、変換済み glyf が参照する各ストリームから 0 バイト以上を読む。 再構築時には、各字形の新しいテーブル内の オフセットも保存する。これらのデータ全体が、 再構築した loca の内容になる （詳細は後述の5.3 項の、 loca 再構築の説明を参照）。

字形レコードの再構築

再構築は、次の手順で符号化された 字形の種類（単純、複合、空）を決めることから始まる：

nContour から Int16 を読み、再構築する TrueType の numberOfContours に格納する。解釈は TrueType と 同じで、ゼロなら空、 正なら単純字形で値は輪郭数、 -1（0xffff）なら複合字形となる。

空字形のデコード

空字形（nContour = 0）の再構築は単純で、 レコード数を増やし、loca に loca[n] = loca[n-1] のエントリーを作る。bboxBitmap が、 ボックス値が bboxStream に明示的にあると示す場合、デコーダーは、 WOFF2 ファイルを無効として 拒否しなければならない。

単純字形のデコード

単純字形（nContour > 0）では、次のように続ける：

  1. nPoints から numberOfContours 個の 255UInt16 を読む。それぞれは 各輪郭の点数である。累積和を計算して 1 を引き、 endPtsOfContours[] に変換する。例えば [2, 4] なら、 endPtsOfContours は [1, 5] となる。また、読み取った値の 総和が字形の全点数 nPoints となる。この例では、 nPoints は 6 である。
  2. flags から nPoints 個の UInt8 を読む。それぞれが再構築する 輪郭の一点に対応する。フラグバイトの 解釈は5.2 項で詳述する。
  3. 各点について（nPoints 回）、glyph から座標 バイトを読む。その数は前の手順のフラグ バイトで決まり、(flag < 0x7f) が 0～83 なら 1 バイト、84～119 なら 2 バイト、 120～123 なら 3 バイト、124～127 なら 4 バイト（いずれも両端を含む）である。 5.2 項に従ってデコードし、 座標の delta-x と delta-y を再構築する。標準 TrueType 字形 符号化を使って再構築した字形に格納する。 [OFF] 5.3.3 項を参照。
  4. glyph から 255UInt16 を一つ読む。これは 命令のバイト数 instructionLength である。
  5. instructionStream から instructionLength バイトを読み、 再構築した字形に命令として格納する。

optionFlags のビット 0 は追加の overlapSimpleBitmap[] の存在を示す。他のビットは予約済みでクリアすべきである。 入力の全単純字形の OVERLAP_SIMPLE が ゼロなら、 エンコーダーは optionFlags のビット 0 をクリアし、 overlapSimpleBitmap[] を省略しなければならない。 少なくとも一つの単純字形で フラグのビット 6 が設定されていれば、 エンコーダーは optionFlags のビット 0 を 1 にし、追加の overlapSimpleBitmap[] を作成しなければならない。 対応する各ビットは、入力の各 単純字形のフラグのビット 6 の値にしなければならない。

デコーダーは、 optionFlags のビット 0 を確認しなければならない。 これにより、追加の overlapSimpleBitmap[] が変換済み glyf に 含まれるかを判断する。存在しなければ、 単純字形のフラグを再構築するとき、 デコーダーはすべての OVERLAP_SIMPLE をゼロにしなければならない。 存在する場合、デコーダーは、 そのビットから OVERLAP_SIMPLE を再構築し、 対応する値を出力の各単純字形の 最初のフラグバイトのビット 6 に設定しなければならない。

複合字形のデコード

複合字形（nContour == -1）では、次の手順で 上記の 1～5 を置き換える：

1a. compositeStream から UInt16 を読み、TrueType 仕様の 構成要素フラグワードとして解釈する。フラグに応じて、 4～14 バイトの追加引数があり、字形インデックス、 arg1、arg2、省略可能なスケールまたはアフィン行列として解釈する。

2a. 手順 1a で定めた数の引数バイトを composite から読み、字形に格納する。1a のフラグで FLAG_MORE_COMPONENTS（ビット 5）が設定されていれば、 1a に戻る。

3a. いずれかのフラグで FLAG_WE_HAVE_INSTRUCTIONS （ビット 8）が設定されていれば、glyph から命令を読み、 上記の手順 4 と 5 と同じ処理で 再構築した字形に格納する。

バウンディングボックスのデコード

単純・複合字形とも、ボックスのビットベクトルの 対応ビットが設定されていれば、bbox から 4 個の Int16 を追加で読み、 それぞれ xMin、yMin、xMax、yMax として、 再構築した字形の対応フィールドに記録する。 単純字形で対応ビットが 未設定なら、輪郭の x、y 座標の最小・ 最大値を計算してボックスを導出し、格納する。

複合字形には明示的なボックスが必要である。 計算が複雑で、 複合字形の命令と各構成要素のスケールを考慮して 構成要素への参照を解決する必要があり、 純粋なストリーミングデコードと相容れないためである。 デコーダーは、 複合字形レコードにボックス情報があるか確認し、 それが欠けるフォントを読み込んではならない。

5.2. 可変長 X・Y 座標のデコード

単純字形の構造は、 字形を構成する全輪郭を、曲線上・曲線外の 座標点列で定義する。座標は差分値として符号化し、 前の点と現在の点の対応する X、Y 座標の増分を表す。各字形の点列の最初の点は (0,0) からの差分である。データ量を最小化するため、 各点を (flag, xCoordinate, yCoordinate) の三つ組で表す。フラグは別ストリームに、 座標は字形データストリーム内に 可変長で符号化し、1 点あたり合計 2～5 バイトを使う。

フラグの最上位ビットは、曲線上か 曲線外かを示す （最上位が 0 なら、 曲線上）。 残り 7 ビットは X、Y の形式を定め、 128 通りのインデックスを指定する。これらは TrueType データの典型的な統計分布を考慮して 割り当てる。座標をニブルで記録する場合 （各座標 4 または 12 ビット）、ビットを詰め、 X の最上位ビットから始め、その後 Y を 最上位から置く。これでデータ量が大きく減り、 同種の値（フラグ、座標）を独立した連続 ストリームにまとめることで、 第二段階のエントロピー符号化も効率化する。

128 個の各インデックス値は、以下の属性を定める。 詳細は次表に示す：

  • バイト数（この座標組の総バイト数。 flag の 1 バイトを含む）。
  • X 座標を表すビット数（X bits）。
  • Y 座標を表すビット数（Y bits）。
  • X bits の値に加える増分（delta X）。
  • Y bits の値に加える増分（delta Y）。
  • X 座標値の符号（X sign）。
  • Y 座標値の符号（Y sign）。

“Byte Count” は三つ組 (flag, xCoordinate, yCoordinate) の総サイズを表し、 別ストリーム内の ‘flag’ も含む点に注意する。

5.3. 変換済み loca テーブル形式

loca は WOFF2 内で二つの形式を取り、 変換バージョン（ディレクトリーのフラグビット、 4.1 項参照）で定まる。バージョン 3 は ヌル変換で、loca を 元の未変更の形式で表す。バージョン 0 は省略可能だが、 loca には、 glyf を変換する場合、 必ず適用しなければならない。つまり、glyf と loca は両方とも変換済み形式にするか、 両方ともヌル変換にしなければならない。

loca の変換バージョン 0 （ディレクトリーのフラグで定義、4.1 項参照）を 以下に規定する。

変換済み loca の transformLength は常にゼロでなければならない。 origLength は適切なサイズでなければならない（numGlyphs+1 に字形ごとのサイズを掛ける。 indexFormat、定義は 5.1 項 変換済み glyf テーブル形式、がゼロなら、 字形ごとのサイズは 2 バイト、それ以外は 4 バイト）。変換済み loca の transformLength がゼロでないか、origLength が上記の計算値と 異なれば、デコーダーは WOFF2 を 無効として拒否しなければならない。

loca は、 glyf のデコード時に再構築しなければならない。 loca の再構築手順は、 5.1 項で、 変換済み glyf のデコードの一部として規定する。 再構築したレコードについて、 デコーダーは各字形のオフセットを、 indexFormat フィールド （変換済み glyf 内）が示す形式で保存しなければならない。

5.4. 変換済み hmtx テーブル形式

hmtx は WOFF2 内で二つの形式のいずれかを取り、 変換バージョン（ディレクトリーのフラグビットに符号化、 4.1 項参照）で定まる。バージョン 0 は ヌル変換で、hmtx の内容を 元の未変更の形式で表す。以下のバージョン 1 は 省略可能で、hmtx 内の冗長性を除去するために使える。

変換バージョン 1 は TrueType 字形の冗長性を利用する。 推奨に従った輪郭では、左サイドベアリングが ボックスの xMin と等しいことが多い。 hmtx の形式は、5.2.4 項で規定する [OFF]。 比例・等幅字形列の左サイドベアリング情報の 二つの配列を持つ。条件を満たせば各配列を入力から除去し、 ボックス情報から再構築できる。

5.5. テーブル順序の制約

有効な WOFF2 に対する以下の制約は、 メモリー効率のよい転送とデコードを支援するためである。

loca は glyf より後に置かなければならない。 単独フォントなら、ディレクトリー内で glyf と loca の 間に他のテーブルを入れてよい。コレクションでは、各 loca は 対応する glyf の直後でなければならない。 例えば 'cmap', 'glyf', 'hhea', 'hmtx', 'loca', 'maxp' ... は単独フォントならよいが、コレクションでは、 glyf / loca を対にする必要がある。 各対が連続したブロックを作る必要はなく、'cmap', 'glyf', 'loca', 'hhea', 'hmtx', 'glyf', 'loca', 'maxp', 'post' ... は許される。 loca の追加制約は5.3 項にある。

6. 拡張メタデータブロック

WOFF2 は拡張メタデータブロックを含んでよい。解釈は [WOFF 1] と完全に同じである。

ただし WOFF 1 は zlib でメタデータを圧縮するが、 WOFF2 では、 存在するメタデータを [Brotli] で圧縮し独立ストリームとして格納しなければならない。 これは実装に必要なバイトレベル圧縮 アルゴリズム数を最小化し、また多くの場合 Brotli が zlib より高い圧縮率を得ると期待されるためである。

メタデータブロックは、 圧縮フォントストリームの直後でなければならない。先頭は、 常に 4 バイト境界に整列しなければならない。 拡張メタデータがある場合、必要なら圧縮ブロック末尾に 最大 3 ゼロバイトを加えて境界に合わせる。 メタデータが最後のブロックなら、 その後に追加のパディングを置くべきではない。

7. プライベートデータブロック

WOFF2 は任意の データブロックを含んでよい。制作者は必要な 情報を格納できる。 この内容は、ユーザーエージェントのフォントの使用や 読み込み動作に影響してはならない。内容を仮定すべきではなく、 ASCII、Unicode、ベンダー独自の バイナリーデータなどがあり、圧縮や暗号化も可能だが、 公開された形式はない。適合ユーザーエージェントは、 構造について何も仮定しない。内容を理解するのは、 そのブロックを担当するフォント開発者またはベンダーだけを想定する。

プライベートデータが あれば最後のブロックとし、圧縮フォントストリームと 拡張メタデータ（存在すれば）の後に置かなければならない。 プライベートデータは、 4 バイト境界で始まらなければならず、必要なら直前のブロックの後に 最大 3 ゼロバイトをパディングとして挿入する。 プライベートデータの末尾は、 WOFF2 の末尾と一致しなければならない。

  • ディレクトリーフラグに変換バージョンを追加し、5.4 項で hmtx 変換を記述した。
  • 変換バージョンに glyf と loca のヌル変換を 追加し、共有 hmtx の変換を明確にした。
  • UIntBase128 の疑似コードと各種編集上の更新を追加した。
  • glyf の空字形再構築を更新し、hmtx に 空字形の左サイドベアリング検査を追加した。軽微な編集も行った。
  • 総フォントサイズや元の glyf サイズが、 WOFF2 ヘッダーまたはディレクトリーの宣言値と 異なる場合をテストする適合要件を追加した。
  • セキュリティーとプライバシーの付録を追加した。
  • IETF が策定中の font/* を参照し、登録付録を WOFF 2.0 のみに絞った。

C. セキュリティーとプライバシーの考慮事項

この付録は参考情報である。

W3C TAG は、仕様編集者が参考情報として回答する自己評価質問票：セキュリティーとプライバシーを策定中である。

検討すべき質問に沿って

  1. この仕様は個人を特定できる情報を扱うか？

    いいえ。

  2. この仕様は高価値データを扱うか？

    いいえ。WOFF2 はクレジットカード情報などを保存しない。

  3. この仕様はオリジンに閲覧セッションをまたいで持続する新しい状態を導入するか？

    いいえ。WOFF2 は参照する 文書だけで利用でき、永続化されないため、 他のアプリケーションや文書では利用できない。

  4. この仕様は持続的なクロスオリジン状態をウェブに公開するか？

    いいえ。

  5. この仕様はオリジンが現在アクセスできない他のデータを公開するか？

    いいえ。

  6. この仕様は新しいスクリプト実行／読み込み機構を可能にするか？

    いいえ。WOFF2 はスクリプトを含まず、リンクもしない。

  7. この仕様はオリジンに利用者の位置へのアクセスを許すか？

    いいえ。

  8. この仕様はオリジンに利用者の機器のセンサーへのアクセスを許すか？

    いいえ。

  9. この仕様はオリジンに利用者のローカル計算環境へのアクセスを許すか？

    いいえ。通常はサーバーで生成・保存し、生成時に利用者環境へアクセスしない。 展開後にも能動的なコードはなく、 利用者環境を調べられない。

  10. この仕様はオリジンに他の機器へのアクセスを許すか？

    いいえ。

  11. この仕様はオリジンにユーザーエージェントのネイティブ UI の制御を許すか？

    いいえ。

  12. この仕様は一時的な識別子をウェブに公開するか？

    いいえ。

  13. この仕様はファーストパーティーとサードパーティーの文脈で動作を区別するか？

    いいえ。

  14. ユーザーエージェントの「シークレット」モードではどう動作すべきか？

    違いはない。

  15. この仕様は利用者のローカル機器にデータを永続保存するか？

    いいえ。

  16. この仕様に「セキュリティーの考慮事項」と「プライバシーの考慮事項」の節はあるか？

    はい。

  17. この仕様は既定のセキュリティー特性を弱めることを許すか？

    いいえ。

font トップレベル型のセキュリティー節 [RFC8081] に、 WOFF2 に関連する追加情報がある。

WOFF2 は Brotli を使う。この付録に加え、Brotli 仕様のセキュリティー節 [Brotli] も参照すべきである。
