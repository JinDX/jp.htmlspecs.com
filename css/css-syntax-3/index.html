1. はじめに

この節は規範的ではない。

このモジュールは、CSS スタイルシートの抽象構文と構文解析 および CSS 構文を使用するその他のもの （HTML の style 属性など）を定義する。

Unicode コードポイントのストリーム （言い換えれば、テキスト）を CSS トークンのストリームへ変換し、 さらにスタイルシート、規則、宣言などの CSS オブジェクトへ変換するためのアルゴリズムを定義する。

1.1. モジュール間の相互作用

このモジュールは、CSS スタイルシートの構文と構文解析を定義する。 CSS 2.1 で定義された字句スキャナーと文法を置き換える。

2. CSS の構文の説明

この節は規範的ではない。

CSS 文書は、一連のスタイル 規則—​文書内の要素にスタイルを適用する修飾規則—​と、CSS 文書の特別な処理 規則や値を定義するat 規則—​から成る。

修飾規則は 前置部から始まり、 次に、宣言のシーケンスを含む {} で囲まれたブロックを持つ。 前置部の意味は、その規則が現れる文脈によって異なる—​スタイル規則の場合、どの 要素に宣言を適用するかを指定するセレクターである。 各宣言は名前を持ち、 その後にコロンと宣言値が続く。 宣言はセミコロンで区切られる。

典型的な規則は、次のようになる:

p > a {
  color: blue;
  text-decoration: underline;
}

上の規則では、"p > a" がセレクターであり、 ソース文書が HTML の場合、 次の任意の a 要素で、 p 要素の子であるものを選択する。

"color: blue" は、 セレクターに一致する要素について、 その color プロパティが値 blue を持つべきことを指定する宣言である。 同様に、その text-decoration プロパティは値 underline を持つべきである。

At 規則はそれぞれ異なるが、 共通する基本構造を持つ。 それらは "@" コードポイントから始まり、その後に CSS キーワードとして名前が続く。 一部の at 規則は単純な文であり、 名前の後にその動作を指定する追加の CSS 値が続き、 最後にセミコロンで終了する。 その他はブロックである。 名前の後に CSS 値を持つことができるが、 修飾規則と同様に、 {} で囲まれたブロックで終了する。 これらのブロックの内容でさえ、指定された at 規則に固有である: 修飾 規則のように宣言のシーケンスを含む場合もあり、 また、追加のブロック、at 規則、あるいはまったく別の構造を含む場合もある。

以下は、含むことのできるさまざまな構文を示すat 規則の いくつかの例である。

@import "my-styles.css";

@import at 規則は単純な文である。 その名前の後には、インポートすべきスタイルシートを示す単一の文字列または url() 関数 を取る。

@page :left {
  margin-left: 4cm;
  margin-right: 3cm;
}

@page at 規則は、任意のページセレクター（:left 疑似クラス）と、 印刷時にページへ適用されるプロパティのブロックから成る。 この点で、通常のスタイル規則と非常によく似ているが、 そのプロパティはどの "要素" にも適用されず、 ページ自体に適用される。

@media print {
  body { font-size: 10pt }
}

@media at 規則は、メディアタイプ と任意のメディアクエリのリストで始まる。 そのブロックには完全な規則が含まれ、 @media の 条件が満たされた場合にのみ適用される。

プロパティ名とat 規則名は常に ident シーケンスであり、 ident-start コードポイント、2 個のハイフン、 またはハイフンの後に ident-start コードポイントが続くものから開始しなければならず、 その後に 0 個以上の ident コードポイントを含むことができる。 任意の コードポイントを、 CSS がその構文で使用するものも含めて、 エスケープすることで含めることができる。

セレクターの構文は Selectors 仕様で定義されている。 同様に、多種多様な CSS 値の構文は Values & Units 仕様で定義されている。 個々のat 規則の特殊な構文は、それらを定義する仕様で確認できる。

2.1. エスケープ

この節は規範的ではない。

任意の Unicode コードポイントは、ident シーケンスまたは引用符付き文字列に、 それをエスケープすることで含めることができる。 CSS エスケープシーケンスはバックスラッシュ (\) で始まり、次が続く:

  • コードポイントのうち、16 進数字でも改行でもない任意の Unicode コードポイント。 エスケープシーケンスは、そのコードポイントに置き換えられる。
  • または、1 個から 6 個の16 進数字の後に 任意の空白が続くもの。 エスケープシーケンスは、 その値が 16 進数字によって与えられる Unicode コードポイント に置き換えられる。 この任意の空白により、16 進エスケープシーケンスの後に "実際の" 16 進数字を続けることができる。

    値が "&B" のident シーケンス は、 \26 B または \000026B と記述できる。

    エスケープシーケンスの後の "実際の" 空白は 2 個重ねなければならない。

2.2. エラー処理

この節は規範的ではない。

CSS でエラーが発生した場合、 パーサーは適切に回復しようとし、 通常どおりの構文解析へ戻る前に 最小限の内容だけを破棄する。 これは、エラーが常に間違いとは限らないためである—​新しい構文は古いパーサーにはエラーに見え、 それを含むスタイルシートが古い UA で完全に壊れることを心配せずに 言語へ新しい構文を追加できることは有用である。

正確なエラー回復動作はパーサー自体で詳述されるが、 十分に単純なので、短い説明でもかなり正確である。

  • スタイルシートの "トップレベル" では、 <at-keyword-token> が at 規則を開始する。 それ以外は修飾規則を開始し、 規則の前置部に含められる。 これにより無効なセレクターが生成される場合があるが、 それは CSS パーサーの関知するところではない—​最悪の場合、セレクターが何にも一致しないことを意味するだけである。
  • at 規則が開始されると、 パーサーの観点からは無効なものは何もなく、 すべて at 規則の前置部の一部となる。 <semicolon-token>に遭遇すると at 規則は直ちに終了し、 一方で左波括弧の <{-token>に遭遇すると at 規則の本体が開始する。 at 規則は、ブロック（()、{}、または [] で囲まれた内容）を対応付けながら先へ進み、 他の何にも対応付けられておらず 別のブロック内にもない右波括弧 <}-token>を見つけるまで進む。 その後、at 規則の内容は at 規則自身の文法に従って解釈される。
  • 修飾規則も同様に動作するが、 セミコロンでは終了しない。 代わりに、それらは単に規則の前置部の一部として取り込まれる。 最初の {} ブロックが見つかると、 内容は常に宣言のリストとして解釈される。
  • 宣言のリストを解釈する際、 任意の時点で未知の構文があると、パーサーは現在 構築中の宣言を破棄し、 セミコロン（またはブロックの終端）が見つかるまで先へ進む。 その後、改めて宣言の構文解析を試みる。
  • 規則、宣言、関数、文字列などのいずれかが開いたままスタイルシートが終了した場合、 すべて自動的に閉じられる。 これによってそれらが無効になるわけではないが、 不完全である可能性があり、 そのため文法に照らして検証される際に破棄されることがある。
    例えば、translateX() 関数の構文は次のとおりである: 
    translateX( <translation-value> )

    ただし、スタイルシートは、次のように関数を閉じないまま終了する場合がある:

    .foo { transform: translate(50px

    CSS パーサーはこれを、1 つの宣言を含むスタイル規則として構文解析し、 その値は "translate" という名前の関数となる。 これは上記の文法に一致する。 終端トークンがトークンストリームに現れなかったとしても、 パーサーが処理を完了する時点では、 終端トークンが存在したかどうかを判定することはもはや不可能であるためである。 分かるのはブロックと関数が存在するという事実だけである。

各構成要素（宣言、スタイル規則、at 規則）が構文解析された後、 ユーザーエージェントは期待される文法に照らしてそれを確認する。 文法に一致しない場合、 それは無効であり、 UA によって無視され、 UA はそれがまったく存在しなかったかのように扱う。

3. CSS のトークン化と構文解析

ユーザーエージェントは、この仕様で説明される構文解析規則を使用して text/css リソースから [CSSOM] ツリーを生成しなければならない。 これらの規則を合わせたものを CSS パーサーと呼ぶ。

この仕様は、CSS 文書が 構文的に正しいかどうかにかかわらず、その構文解析規則を定義する。 構文解析アルゴリズム内の特定の箇所は構文解析エラーと呼ばれる。 構文解析エラーのエラー処理は明確に定義されている: ユーザーエージェントは、そのような問題に遭遇した場合、以下に説明するように動作するか、 以下に説明する規則を適用したくない最初のエラーで 処理を中止しなければならない。

適合性チェッカーは、文書内に 1 つ以上の構文解析エラー条件が存在する場合、 少なくとも 1 つの構文解析エラー条件をユーザーに報告しなければならず、 文書内に存在しない場合は 構文解析エラー条件を報告してはならない。 適合性チェッカーは、文書内に複数の構文解析エラー条件が存在する場合、 複数の構文解析エラー条件を報告してもよい。 適合性チェッカーは構文解析エラーから回復する必要はないが、 回復する場合は、 ユーザーエージェントと同じ方法で回復しなければならない。

3.1. 構文解析モデルの概要

CSS 構文解析処理への入力は Unicode コードポイントのストリームから成り、 これはトークン化段階を通り、その後ツリー構築段階を通る。 出力は CSSStyleSheet オブジェクトである。

注: スクリプトをサポートしない実装は、 実際に CSSOM CSSStyleSheet オブジェクトを作成する必要はないが、 そのような場合でも CSSOM ツリーは仕様の残りのモデルとして使用される。

3.2. 入力バイトストリーム

スタイルシートを構文解析する場合、 トークン化段階への入力を構成する Unicode コードポイントのストリームは、 最初はユーザーエージェントからバイトストリームとして見える場合がある （通常、ネットワークまたはローカルファイルシステムから取得される）。 その場合、ユーザーエージェントは特定の文字エンコーディングに従って これらのバイトをコードポイントへ復号しなければならない。

stylesheet のバイトストリームをコード ポイントのストリームに復号するには:

  1. stylesheet のフォールバックエンコーディングを決定し、 その結果を fallback とする。

  2. stylesheet のバイトストリームを フォールバックエンコーディング fallback を用いて復号し、 その結果を返す。

注: 復号アルゴリズムは、 バイトオーダーマーク（BOM）を優先し、 それが見つからない場合にのみフォールバックを使用する。

stylesheet のフォールバック エンコーディングを決定するには:
  1. HTTP または同等のプロトコルが stylesheet に対して encoding label（例えば Content-Type ヘッダーの charset パラメーター を介して）を提供する場合、 encoding label からエンコーディングを取得する。 それが失敗を返さない場合、 それを返す。
  2. それ以外の場合、stylesheet のバイトストリームを確認する。 ストリームの最初の 1024 バイトが次の 16 進シーケンスで始まる場合、 
    40 63 68 61 72 73 65 74 20 22 XX* 22 3B

    各 XX バイトが 016 以上 2116 以下の値 または 2316 以上 7F16 以下の値である場合、 XX バイトのシーケンスから形成され、 ASCII として解釈される文字列 からエンコーディングを取得する。

    このバイトシーケンスは何を意味するのか?

    上記のバイトシーケンスは、 ASCII として復号すると、 文字列 "@charset "…";" となり、 "…" はエンコーディングのラベルに対応するバイトシーケンスである。

    戻り値が utf-16be または utf-16le だった場合、 utf-8 を返す。 それ以外で失敗でなければ、 それを返す。

    宣言が utf-16 としているのに、なぜ utf-8 を使用するのか?

    エンコーディング宣言のバイトは ASCII で “@charset "…";” を表すが、 UTF-16 は ASCII 互換ではない。 文書内で正しいバイトを得るために完全な意味不明の文字列（䁣桡牳整•utf-16be∻ のようなもの）を入力したか、 そうでなければ、 実際には文書が ASCII 互換エンコーディングであり、 エンコーディング宣言が偽っていることになる。

    いずれにしても、UTF-8 をデフォルトにするのは妥当な答えである。

    さらに、これは HTML の <meta charset> 属性の動作を模倣する。

    注: エンコーディング 宣言の構文は、at 規則である @charset の構文のように見えるが、 実際にはそのような規則は存在せず、 記述方法の規則は通常そのような規則を 認識する場合よりはるかに厳格である。 CSS で実行できることで、（存在すると仮定すれば）有効な @charset 規則を生成するもののうち、 複数の空白、コメント、単一引用符の使用などは、 エンコーディング宣言が認識されない原因となる。 この動作はエンコーディング宣言を可能な限り単純に保ち、 その結果、正しく実装される可能性を最大化する。

  3. それ以外の場合、参照元の文書から環境エンコーディングが提供されていれば、 それを返す。
  4. それ以外の場合、utf-8 を返す。

UTF-8 は Web のデフォルトエンコーディングであり、 多くの新しい Web ベースのファイル形式は UTF-8 エンコーディングを前提または必須としているが、 CSS はどのエンコーディングが主流になるか明らかになる前に作成されたため、 スタイルシートが UTF-8 であると自動的に仮定することはできない。

スタイルシートの作者は、スタイルシートを UTF-8 で作成するべきであり、 HTTP ヘッダー（または同等の方法）がスタイルシートのエンコーディングを UTF-8 として宣言するか、 参照元の文書がそのエンコーディングを UTF-8 として宣言するようにしなければならない。 （HTML では、head に <meta charset=utf-8> 要素を追加することで これを行う。）

これらの選択肢のいずれも利用できない場合、 作者は UTF-8 BOM または次の正確な文字でスタイルシートを開始するべきである

@charset "utf-8";

バイトから復号される CSS スタイルシートを参照する文書言語は、 そのような各スタイルシートに環境 エンコーディングを定義してもよく、 これは他のエンコーディングの手掛かりが利用できない、または使用できない場合のフォールバックとして使用される。

環境エンコーディングという概念は、レガシー コンテンツとの互換性のためだけに存在する。 新しい形式および新しいリンク機構は環境エンコーディングを提供するべきではなく、 より明示的な情報がない場合には、代わりにスタイルシートが UTF-8 をデフォルトとするようにする。

注: [HTML] は、 <link rel=stylesheet> の環境エンコーディングを定義する。

注: [CSSOM] は、<xml-stylesheet?> の 環境エンコーディングを定義する。

注: [CSS-CASCADE-3] は、 @import の環境エンコーディングを定義する。

4. トークン化

コードポイントのストリームを CSS トークンのストリーム input にトークン化するには、 <EOF-token>に到達するまで、input から トークンを消費することを繰り返し、 返された各トークンをストリームへプッシュする。

注: トークンを消費するアルゴリズムの各呼び出しは 単一のトークンを返すため、 必要であれば、構文解析の最中に コードポイントのストリームを "オンデマンド" でトークン化するためにも使用できる。

トークン化段階の出力は、次のトークンの 0 個以上から成るストリームである: <ident-token>, <function-token>, <at-keyword-token>, <hash-token>, <string-token>, <bad-string-token>, <url-token>, <bad-url-token>, <delim-token>, <number-token>, <percentage-token>, <dimension-token>, <unicode-range-token>, <whitespace-token>, <CDO-token>, <CDC-token>, <colon-token>, <semicolon-token>, <comma-token>, <[-token>, <]-token>, <(-token>, <)-token>, <{-token>, および <}-token>。

  • <ident-token>、<function-token>、<at-keyword-token>、<hash-token>、<string-token>、および <url-token> は、0 個以上のコード ポイントから構成される値を持つ。 さらに、hash トークンは "id" または "unrestricted" のいずれかに設定された type フラグを持つ。type フラグは、 他で設定されていない場合、デフォルトで "unrestricted" となる。
  • <delim-token> は、単一のコード ポイントから構成される値を持つ。
  • <number-token>、<percentage-token>、および <dimension-token> は数値を持ち、 また任意の符号文字 が "+" または "-"（または何もなし）のいずれかに設定される。

    <number-token> と <dimension-token> はさらに、 "integer" または "number" のいずれかに設定された type フラグを持つ。type フラグは、他で設定されていない場合、 デフォルトで "integer" となる。 <dimension-token> はさらに、1 個以上のコードポイントから構成される単位を持つ。

  • <unicode-range-token> は開始コード ポイントと終了コードポイントを持つ。 これはコードポイントの包含範囲 （開始と終了の両方を含む）を表す。 終了コードポイントが開始コードポイントより前にある場合、 空の範囲を表す。

注: hash トークンの type フラグは、 Selectors 構文 [SELECT] で使用される。 "id" type の hash トークンのみが有効なID セレクターである。

5.4. パーサーのエントリーポイント

この節で定義されるアルゴリズムは、 CSS トークンのリストから高レベルの CSS オブジェクトを生成する。

ここでのアルゴリズムは、入力としてトークンストリームを扱うが、 利便性のため、 他のいくつかの型の値を指定して呼び出すこともできる。

与えられた input をトークンストリームに正規化するには:

  1. input がすでにトークンストリームである場合、 それを返す。

  2. input が CSS トークンおよび／またはコンポーネント値のリストである場合、 新しいトークンストリームを作成し、 input をそのトークンとし、 それを返す。

  3. input が文字列である場合、 input からコードポイントをフィルターし、 その結果をトークン化し、 トークンのストリームを返す。

  4. 表明: input として渡されるのは、上記の型のみであるべきである。

注: 他の仕様は、 独自の目的のために追加のエントリーポイントを定義できる。

次の注記は、おそらく関連する仕様で規範的な文章に変換し、 この仕様の用語に結び付けるべきである:
  • 「スタイルシートを 構文解析する」は、通常のパーサーエントリーポイントとして、 スタイルシートの構文解析に使用することを意図している。
  • 「スタイルシートの内容を構文解析する」は、 CSSStyleSheet replace() メソッド、 および同様のものによって使用され、 テキストを既存のスタイルシートの 内容へ構文解析することを意図している。
  • 「規則を構文解析する」は、 CSSStyleSheet insertRule() メソッド、 および同様のものによって使用され、 テキストを単一の規則へ構文解析することを意図している。 CSSStyleSheet#insertRule メソッド、 および存在し得る同様の関数で、 テキストを単一の規則へ構文解析する。
  • 「宣言を 構文解析する」は、@supports 条件で使用される。[CSS3-CONDITIONAL]
  • 「ブロックの 内容を構文解析する」は、CSS 内の任意のブロックの内容 （style 属性などを含む）、 およびCSSStyleDeclaration cssText 属性などの API を構文解析することを意図している。
  • 「コンポーネント 値を構文解析する」は、単一の値を消費する必要があるもの、 例えば attr() の構文解析規則のためのものである。
  • 「コンポーネント値のリストを構文解析する」は、 表示属性の内容、 すなわちテキストを単一の宣言の値へ構文解析するもの、 または独立したセレクター [SELECT] や Media Queries のリスト [MEDIAQ] の構文解析、 例えば Selectors API や HTML の media 属性のためのものである。

5.4.1. CSS 文法に従って何かを構文解析する

文字列またはトークンリストを構文解析して、 ある CSS 文法に一致するかどうかを確認し、 一致する場合には、 文法に従ってそれを分解することが望ましい場合がよくある。 この節では、この種の操作のための汎用的なフックを提供する。 次のように呼び出すべきである: 「foo を CSS <color> として構文解析する」、または同様に。

このアルゴリズムは、入力が指定された文法に一致しない場合は 失敗を返し、 それ以外の場合は文法に従って入力を構文解析した結果を返す。 これは指定された文法仕様に対応する未規定の構造である。 戻り値は仕様の文章によってのみ操作されなければならず、 その場合、表現の曖昧さは問題にならない。 仕様言語の外部に公開することを意図する場合、 結果を使用する仕様は、明確に規定された表現へ明示的に変換しなければならない。 例えば、CSS シリアル化アルゴリズムを呼び出すことによって （「CSS <string> 値としてシリアル化する」のように）。

注: このアルゴリズムと、 CSS 文法に従ってカンマ区切りリストを 構文解析するは、 通常、他の仕様が呼び出したい構文解析アルゴリズムのすべてである。 残りの構文解析アルゴリズムは、主として [CSSOM] および関連する「CSS 構造を明示的に構築する」場合を意図している。 他のアルゴリズムのいずれかを使用する必要があると思う場合は、 まず CSSWG に助言を求めること。

input と CSS grammar 生成規則が与えられたとき、 CSS 文法に従って何かを構文解析する （単に構文解析するともいう）には:
  1. input を正規化し、 input をその結果に設定する。
  2. input からコンポーネント値のリストを構文解析し、 戻り値を result とする。
  3. result を grammar と照合する。 成功した場合、 一致した結果を返す。 それ以外の場合、失敗を返す。

5.4.2. CSS 文法に従ってカンマ区切りリストを構文解析する

カンマを含む文法に従って値を構文解析することはもちろん可能だが、 値のいずれかの部分が構文解析に失敗すると、 全体が構文解析されず、 失敗を返す。

それが望ましい場合もある （リスト値の CSS プロパティなど）。 一方で、 値のカンマ区切りの各部分を個別に構文解析し、 正常に構文解析された部分をある方法で処理し、 構文解析に失敗した部分を別の方法で処理する方がよい場合もある （通常はそれらを無視する。 例えば <img sizes>）。

このアルゴリズムは、まさにそれを実現するための簡単なフックを提供する。 「トップレベル」のカンマで分割された値のリストを返し、 各値は失敗 （構文解析に失敗した場合） または構文解析の結果 （構文解析アルゴリズムで説明される 未規定の構造）のいずれかとなる。

input と CSS grammar 生成規則が与えられたとき、 CSS 文法に従ってカンマ区切りリストを構文解析する （別名リストを構文解析する）には:
  1. input を正規化し、 input をその結果に設定する。
  2. input が<whitespace-token>のみを含む場合、 空のリストを返す。
  3. input からコンポーネント値のカンマ区切りリストを 構文解析し、 戻り値を list とする。
  4. list の各 item について反復し、 item を、 grammar を使用して item を構文解析した結果に 置き換える。
  5. list を返す。

宣言と修飾規則は、 許可される構文が通常重複しない。 現在定義されている CSS プロパティでは、その値に {} ブロックを使用できないため、 foo:bar {}; は確実に規則であり、 foo: bar; は確実にプロパティである。 将来の CSS プロパティがその値に {} ブロックを許可するとしても、 許可される構文では {} ブロックが値全体となるよう制限され、 例えば foo: {...}; のようになる。 これは有効な規則にはならないことが保証される。 : の後に ident または関数が続かず、 疑似クラスであることを示さないためである。

これにより、宣言と規則を同じ文脈で混在させることができる: まず何かを宣言として構文解析しようとし、 それが有効な宣言にならなければ、 代わりに規則として再構文解析する。 誤って無効になった宣言は、代わりに規則として構文解析されるが、 それで問題ない: パーサーは宣言の終端セミコロンで停止し、 それを無効な規則と見なす。 （または {} ブロックを含むプロパティの場合、 セミコロンの直前で停止し、 それでも無効な規則と見なし、 次に何かを構文解析しようとすると、 単独のセミコロンが無効として破棄される。） したがって、消費されるトークンの総量はいずれの場合も同じである。

ただし、カスタムプロパティの構文は CSSWG によって 慎重に精査されるものではない。 作者は値に {} ブロックを取るカスタムプロパティを 記述でき、 他のものと組み合わせることさえできる。 そのカスタムプロパティが無効になった場合 （例えば、不正に記述された var() 関数による場合）、 規則として再構文解析されると、 {} ブロックのところで早期に停止する。 その後、カスタムプロパティ値の残りのトークンは 新しい構成要素として構文解析され、 予期しない宣言または規則が 作成される可能性がある。

この（確かに非常に特殊な）コーナーケースを避けるため、 カスタムプロパティの構文を 修飾規則の構文から除外する。 プロパティと規則の混在を許可する文脈にいて、 何らかの理由でカスタムプロパティのように見える 規則を構文解析することになった場合、 何かを誤っており、 代わりにカスタムプロパティ全体を （終端セミコロンまで）消費する必要がある。

（プロパティを許可しない文脈にいる場合、 規則がカスタムプロパティのように見えれば 単にそれを破棄する。 これにより、--foo:hover { color: blue; } が どこでも一貫して無効となり、 存在しない終端セミコロンを探して スタイルシートの大量の部分を消費する可能性を回避する。）

それ以外の場合、input からブロックを 消費し、 その結果を child rules とする。 child rules の最初の項目が宣言のリストである場合、 それを child rules から削除し、 rule の宣言に代入する。 child rules に残っている項目のいずれかが宣言のリストである場合、 それらを、そのリストのみを子として含む ネストされた宣言規則に置き換える。 child rules を rule の子規則に代入する。

6. An+B マイクロ構文

CSS のいくつかのもの、 例えば :nth-child() 疑似クラスでは、 リスト内のインデックスを示す必要がある。 An+B マイクロ構文はこれに有用であり、 作者が単一の要素、 またはリスト内で一定間隔にあるすべての要素を簡単に示せる。

An+B 表記は、整数の ステップ（A）とオフセット（B）を定義し、 n の各正の整数または 0 の値について、 リスト内の An+B 番目の要素を表し、 リストの最初の要素のインデックスは 1（0 ではない）である。

A と B の値が 0 より大きい場合、 これは実質的にリストを A 個の要素のグループに分割し、 （最後のグループは余りを取る）、 各グループの B 番目の要素を選択する。

An+B 表記は、even および odd キーワードも受け入れ、 それぞれ 2n および 2n+1 と同じ意味を持つ。

例: 

2n+0   /* リスト内のすべての偶数番目の要素を表す */
even   /* 同じ */
4n+1   /* リスト内の 1 番目、5 番目、9 番目、13 番目などの要素を表す */

A と B の値は負にもできるが、 n ≥ 0 に対する An+B の正の結果だけが 使用される。

例: 

-1n+6   /* リストの最初の 6 要素を表す */
-4n+10  /* リストの 2 番目、6 番目、10 番目の要素を表す */

A と B が両方とも 0 の場合、 疑似クラスはリスト内のどの要素も表さない。

6.1. 非形式的な構文の説明

この節は非規範的である。

A が 0 の場合、An 部分は省略できる （B 部分がすでに省略されている場合を除く）。 An が含まれておらず、 B が負でない場合、 B の前の+ 記号も（許可されている場合） 省略できる。 この場合、構文は単に B に簡略化される。

例: 

0n+5   /* リスト内の 5 番目の要素を表す */
5      /* 同じ */

A が 1 または -1 の場合、 規則から 1 を省略できる。

例:

したがって、次の表記は同等である: 

1n+0   /* リスト内のすべての要素を表す */
n+0    /* 同じ */
n      /* 同じ */

B が 0 の場合、A 番目ごとの要素が選択される。 この場合、 A 部分がすでに省略されていない限り、 +B（または -B）部分を省略できる。

例: 

2n+0   /* リスト内の偶数番目の各要素を表す */
2n     /* 同じ */

B が負の場合、そのマイナス記号が+ 記号に置き換わる。

有効な例: 

3n-6

無効な例: 

3n + -6

An と B の両方が存在する場合、それらを区切る+ または - の いずれの側にも空白が許可される。

空白を含む有効な例: 

3n + 1
+3n - 2
-n+ 6
+6

空白を含む無効な例: 

3 n
+ 2n
+ 2

7.1. ブロック内容の定義: <block-contents>、<declaration-list>、<qualified-rule-list>、<declaration-rule-list>、および <rule-list> 生成規則

CSS パーサーはブロックの内容を区別しない—​すべて同じ アルゴリズムで構文解析され、 どの構成要素が有効かという点だけで区別される。

規則の文法を記述する際、 <block-contents> は、この区別しない構文解析を表す。 ブロック内の唯一の値としてのみ使用しなければならず、 ブロックが含められるものに暗黙の制限が 課されないことを表す。

付随する文章は、この文脈で何が有効で何が無効かを定義しなければならない。 宣言が有効であり、 かつプロパティ宣言である場合、 カスケードと相互作用するかどうかを定義しなければならない。 相互作用する場合、その詳細度と !important の使用方法を定義しなければならない。

ただし、多くの場合、 ブロックは特定の型のいかなる構成要素も有効には含められない。 これらの場合をより明示的に表すため、 次の生成規則を使用できる

  • <declaration-list>: 宣言のみが 許可され、 at 規則および修飾規則は 自動的に無効となる。

  • <qualified-rule-list>: 修飾 規則のみが許可され、 宣言およびat 規則は自動的に 無効となる。

  • <at-rule-list>: at 規則のみが許可され、 宣言および修飾規則 は自動的に無効となる。

  • <declaration-rule-list>: 宣言およびat 規則が許可され、 修飾規則は 自動的に無効となる。

  • <rule-list>: 修飾規則および at 規則が許可され、 宣言は 自動的に無効となる。

これらはすべて構文解析の点では<block-contents>と完全に同等だが、 付随する文章で有効性を定義する必要があるのは、 自動的に無効とならないカテゴリについてだけである。

各種生成規則の例:

  • トップレベルの @media は、そのブロックに<rule-list>を使用し、 一方、ネストされたもの [CSS-NESTING-1] は<block-contents>を使用する。

  • スタイル規則は<block-contents>を使用する。

  • @font-face は<declaration-list>を使用する。

  • @page は<declaration-rule-list>を使用する。

  • @keyframes は<qualified-rule-list>を使用する

例えば、@font-face の文法は次のように記述できる: 
<@font-face> = @font-face { <declaration-list> }

そして、付随する文章でブロック内で許可される有効な記述子 を定義する。

@keyframes の文法は次のように記述できる:

<@keyframes> = @keyframes { <qualified-rule-list> }
<keyframe-rule> = <keyframe-selector> { <declaration-list> }

そして、付随する文章で<keyframe-rule>のみが @keyframes内で許可されること、 また <keyframe-rule> がすべてのアニメーション可能な CSS プロパティと、 animation-timing-function プロパティを受け入れるが、 カスケードとは相互作用しないことを定義する。

7.2. 任意の内容の定義: <declaration-value> および <any-value> 生成規則

一部の文法では、 文法内で妥当な任意の入力を受け入れ、 内容に対してより具体的なエラー処理を手動で行うことが有用である （文法の不一致で通常行われるように、 単に構成要素全体を無効化するのではなく）。

例えば、カスタム プロパティは妥当な任意の値を許可する。 他の CSS プロパティの任意の断片を含むことができ、 または既存の CSS にまったく含まれないものに使用できるためである。 別の例として、Media Queries の<general-enclosed> 生成規則は、 将来の MQ 構文が許可する範囲を定義し、 「未知」の値を処理するために特別なロジックを使用する。

これを支援するため、2 つの追加の生成規則を定義する:

<declaration-value> 生成規則は、1 個以上のトークンからなる任意のシーケンスに一致する。 ただし、そのシーケンスに <bad-string-token>、 <bad-url-token>、 対応していない<)-token>、<]-token>、または<}-token>、 またはトップレベルの<semicolon-token>トークン、あるいは値が "!" の<delim-token>トークンを含んではならない。 これは、有効な宣言がその値として持てるものすべてを表す。

<any-value> 生成規則は<declaration-value>と同一だが、 トップレベルの<semicolon-token>トークン および値が "!" の<delim-token>トークンも許可する。 これは、任意の文脈で有効な CSS となり得るものすべてを表す。

8. CSS スタイルシート

CSS スタイルシートを 構文解析するには、 まずスタイルシートを 構文解析する。 得られたトップレベルの修飾規則をすべて、以下で定義するスタイル規則として解釈する。

スタイル規則が無効である場合、 または at 規則が認識されないか、その文法または文脈に従って無効である場合、 それは構文解析エラーである。 その規則を破棄する。

8.1. スタイル規則

スタイル規則は修飾規則であり、 セレクターリストを プロパティ宣言のリスト および場合によってはネストされた規則のリストに関連付ける。 これらは、 規則集合とも[CSS2]では呼ばれる。 CSS Cascading and Inheritance [CSS-CASCADE-3]は、スタイル規則内の宣言が カスケードにどのように参加するかを定義する。

修飾規則の前置部は、 構文解析され、 <selector-list>として扱われる。 これが失敗を返した場合、 スタイル規則全体が無効となる。

修飾規則のブロックの内容は<declaration-list>として構文解析される。 このブロック内の修飾規則もスタイル規則である。 他の仕様またはこの仕様の将来のレベルで別途定義されない限り、 そのリスト内の at 規則は無効 であり、無視しなければならない。

注: [CSS-NESTING-1]は、条件付きグループ規則 およびその他の一部のat 規則が、 スタイル規則内で許可されることを定義する。

未知の CSS プロパティの宣言、 または値がそのプロパティで定義された構文に一致しない宣言は無効であり、 無視しなければならない。 スタイル規則の内容の有効性は、スタイル規則自体の有効性には影響しない。 別途指定されない限り、プロパティ名はASCII 大文字・小文字を区別しない。

注: Custom Properties [CSS-VARIABLES]の名前は 大文字と小文字が区別される。

CSS スタイルシートのトップレベルにある修飾規則はスタイル 規則である。 他の文脈にある修飾規則は、スタイル規則である場合もない場合もあり、 それは文脈によって定義される。

例えば、@media 規則 [CSS3-CONDITIONAL]内の修飾規則は スタイル規則だが、 @keyframes 規則 [CSS3-ANIMATIONS]内の修飾規則はそうではない。

8.2. at 規則

at 規則は at-keyword で始まる規則であり、 したがって同じ文脈のスタイル 規則と区別できる。

at 規則は次の目的に使用される:

  • 条件付きグループ規則のように、 スタイル規則やその他の at 規則をグループ化し構造化する

  • 特定の要素に関連付けられていないスタイル情報を宣言する。 例えばカウンタースタイルを定義する

  • インポートや名前空間キーワードマッピングのような 構文構造を管理する

  • また、スタイル規則では果たされないその他の雑多な目的に使用される

at 規則は、具体的な規則とその目的に応じて多くの形式を取るが、 大まかには 2 種類ある: セミコロンで終わる、より単純な構造である 文 at 規則と、 ネストされた修飾規則、at 規則、または宣言を含むことのできる{} ブロックで 終わるブロック at 規則。

ブロック at 規則は通常、 （汎用またはat 規則固有の） at 規則、修飾規則、および／または記述子宣言の集合を含み、 at 規則によって定義された制限に従う。 記述子はプロパティに似ており、 （同じ構文で宣言される） ただしツリー内の要素やボックスではなく、 特定の型のat 規則に関連付けられる。

9. シリアル化

この仕様で説明するトークナイザーは、コメント用のトークンを生成せず、 その他の方法でもコメントを保持しない。 実装は、コメントの内容とトークンストリーム内での位置を保持してもよい。 その場合、この保持された情報は構文解析ステップに影響してはならない。

この仕様は、一般に CSS をどのようにシリアル化するかを定義せず、 その作業を[CSSOM]および個々の機能仕様に委ねる。 特に、コメントと空白のシリアル化は定義されない。

  • ブロックの内容を消費する際、 他の規則に対してどこに現れるかにかかわらず すべての宣言をまとめてグループ化するのではなく、 宣言は周囲の規則に対する相対位置を維持するようになった。 その情報を実際にどう扱うかは個々の規則が決定する。

12.6. CSS 2.1 および Selectors Level 3 からの変更点

注: この仕様の目的は現実に一致させることである。 CSS2.1 からの変更は、ほぼ常に CSS 2.1 が実際のブラウザー の動作と一致しないものを規定していたか、 何かを未規定のまま残していたことによる。 何らかの詳細がブラウザーと一致しない場合、 ほぼ確実に意図したものではないため、 知らせてほしい。

バイトストリームからの復号に関する変更:

  • ASCII 互換のバイトパターンにある@charset 規則だけを検出する。
  • ASCII 非互換のエンコーディングを指定する@charset 規則は無視する。 そうすると規則自体が正しく復号されなくなるためである。
  • 文字エンコーディングについては IANA レジストリではなく、 [ENCODING]を参照する。

トークン化の変更:

  • CSS ソース内の任意の U+0000 NULL コードポイントは U+FFFD REPLACEMENT CHARACTER に置き換えられる。
  • 0 と評価される \0 などの任意の 16 進エスケープシーケンスは、 U+0000 NULL ではなく U+FFFD REPLACEMENT CHARACTER を生成する。
  • 非 ASCII ident コードポイントの定義を変更し、 HTML の有効なカスタム要素名と一致するようにした。
  • トークン化は COMMENT または BAD_COMMENT トークンを出力しなくなった。 BAD_COMMENT は通常のトークンと同じものと見なされるようになった（エラーではない）。 シリアル化が、 分離する必要があるトークン間に必要に応じてコメントを挿入する責任を負う。 例えば、連続する 2 つの<ident-token>。
  • <unicode-range-token>は、 価値が低く、場合によっては積極的に有害だったため削除された。 （例えば u+a { font-weight: bold; } は無効なセレクターだった...）

    代わりに、トークンパターンに基づく<urange> 生成規則を追加した。 技術的には 2.1 が許可していたものより緩い （任意の数の数字と ? 文字）ものだが、 実際の使用に影響するような形ではない。

  • EOF エラー処理規則を トークナイザーに適用し、 EOF 時に BAD_STRING または BAD_URI ではなく、 通常の<string-token>および<url-token> を出力する。
  • BAD_URI トークン（現在の <bad-url-token>）は「自己完結型」である。 言い換えると、トークナイザーが <bad-url-token> ではなく <url-token> にいることを認識すると、 閉じる ) を探して単に先へ進み、 その他すべてを無視する。 この動作は、それを <function-token> のように扱い、 開いているブロックなどに注意を払うよりも単純である。 この動作を示すのは WebKit だけだが、 これによる互換性バグは発生していないようである。
  • <comma-token>が追加された。
  • <number-token>、<percentage-token>、および<dimension-token>を変更し、 前置する +/- 符号をその値の一部として含むようにした （他の仕様でトークンが言及されるたびに手動で処理する必要がある別個の<delim-token>としてではなく）。 これによる唯一の結果は、符号と数値の間にコメントを挿入できなくなったことである。
  • WG 決議に従い、SVG に合わせて数値／パーセンテージ／dimension で科学表記をサポートする。
  • サロゲートの 16 進エスケープは、サロゲートではなく置換文字を出力するようになった。 これにより、実装は内部で UTF-16 を安全に使用できる。

構文解析の変更:

  • 宣言の任意のリストが、WG 決議に従い、@pageのような at 規則も受け入れるようになった。 まだそのような at 規則が定義されていない場合でも、 これはエラー処理に違いを生じさせる: at 規則は、有効かどうかにかかわらず、<semicolon-token>なしで {} ブロックで終了し、 次の宣言を開始できるようにする。
  • 文法内のさまざまな場所に現れる一部の雑多な「特別な」トークン （対応していない<}-token>など） の処理を、少なくとも 1 つのブラウザーが示す妥当な動作として規定した。 以前は、それらの場所にこうしたトークンを含むスタイルシートはスタイルシート文法に まったく一致しなかったため、 処理は完全に未定義だった。 具体的には:
    • [] ブロック、() ブロック、および関数が {} ブロック、<at-keyword-token>、または<semicolon-token>を含められるようになった
    • 修飾規則の前置部がセミコロンを含められるようになった
    • 修飾規則および at 規則の前置部が<at-keyword-token>を含められるようになった

Selectors Level 3 [SELECT]からの An+B の変更:

  • An+B マイクロ構文は、別個のトークナイザーではなく、 CSS トークンの観点から正式に定義されるようになった。 これにより、軽微な違いが生じた:

テスト

この仕様の内容に関連するテストは、 この例のような「テスト」ブロックに記載される場合がある。 このようなブロックはいずれも非規範的である。

    適合性クラス

    この仕様への適合性は、 3 つの適合性クラスについて定義される:

    スタイルシート
    CSS スタイルシート。
    レンダラー
    スタイルシートの意味論を解釈し、それを使用する 文書をレンダリングする UA。
    オーサリングツール
    スタイルシートを作成する UA。

    スタイルシートは、このモジュールで定義された構文を使用するすべての文が、 汎用 CSS 文法およびこのモジュールで定義された各 機能の個別の文法に従って有効である場合、 この仕様に適合する。

    レンダラーは、この仕様に適合するためには、 適切な仕様で定義されているとおりにスタイルシートを解釈することに加えて、 この仕様で定義されるすべての機能を、 正しく構文解析し、 それに応じて文書をレンダリングすることによってサポートしなければならない。ただし、 デバイスの制限により UA が文書を正しくレンダリングできないことによって、 UA が非適合になることはない。（例えば、UA は モノクロモニターで色をレンダリングする必要はない。）

    オーサリングツールは、この仕様に適合するためには、 汎用 CSS 文法およびこのモジュールの各機能の 個別の文法に従って構文的に正しいスタイルシートを作成し、 このモジュールで説明されているスタイルシートのその他すべての適合性要件を 満たさなければならない。

    部分的な実装

    作者が前方互換な構文解析規則を利用して フォールバック値を指定できるようにするため、CSS レンダラーは 必ず 使用可能なレベルのサポートを持たない at 規則、プロパティ、プロパティ値、キーワードを無効として扱い（かつ 適切に 無視し）、 その他の構文構造についても同様に扱わなければならない。特に、ユーザーエージェントは 決して 単一の複数値プロパティ宣言内で、サポートされないコンポーネント値を選択的に 無視し、サポートされる値だけを尊重してはならない。いずれかの値が無効と見なされる場合、 （サポートされない値はそう見なされなければならない）、CSS では宣言全体を 無視することが要求される。

    不安定な機能および独自機能の実装

    将来の安定した CSS 機能との衝突を避けるため、 CSSWG は、CSS の 不安定な機能および 独自拡張の実装について、 ベストプラクティスに従うことを推奨する。

    非実験的な実装

    仕様が候補勧告段階に到達すると、 非実験的な実装が可能になり、実装者は、 仕様に従って正しく実装されていることを実証できる CR レベルの機能について、 接頭辞なしの実装をリリースするべきである。

    実装間で CSS の相互運用性を確立し維持するため、 CSS ワーキンググループは、非実験的な CSS レンダラーに、実装レポート（および必要に応じて、その 実装レポートに使用したテストケース）を W3C に、 CSS 機能の接頭辞なしの実装をリリースする前に提出するよう求めている。テストケースは、 W3C に提出された後、CSS ワーキンググループによるレビューおよび修正の 対象となる。

    テストケースおよび実装レポートの提出に関する詳細情報は、 CSS ワーキンググループの Web サイト https://www.w3.org/Style/CSS/Test/ で確認できる。 質問は、 public-css-testsuite@w3.org メーリングリストに送ること。

    CR 終了基準

    この仕様が提案勧告へ進むためには、 各機能について少なくとも 2 つの独立した相互運用可能な実装が 存在しなければならない。各機能は異なる製品の組み合わせによって実装されてもよく、 すべての機能を単一の製品が実装する必要はない。この基準のため、 次の用語を定義する:

    独立している
    各実装は、 異なる主体によって開発されなければならず、別の適格な実装で使用されるコードを 共有、再利用、または派生してはならない。この仕様の実装に 関係しないコード部分は、 この要件の対象外である。
    相互運用可能
    公式 CSS テストスイート内の 該当するテストケースに合格すること、または実装が Web ブラウザーでない場合は同等のテストに合格すること。相互運用性を主張するためにそのようなユーザー エージェント（UA）を使用する場合、テスト スイート内の関連する各テストについて同等のテストを作成するべきである。さらに、 そのような UA を相互運用性の主張に使用する場合、 相互運用性の目的で、 同じ方法でそれらの同等のテストに合格できる 1 つ以上の追加の UA が 存在しなければならない。同等のテストは、 ピアレビューのために公開されなければならない。
    実装
    次の条件を満たすユーザーエージェント:
    1. 仕様を実装している。
    2. 一般に公開されている。実装は、 出荷製品またはその他の一般公開されたバージョン （例えば、ベータ版、プレビューリリース、または "nightly build"）であってよい。 非出荷製品のリリースは、安定性を 実証するため、その機能を少なくとも 1 か月間 実装していなければならない。
    3. 実験的ではない（すなわち、テストスイートに合格することを目的として特別に設計され、 今後の通常利用を意図していない バージョンではない）。

    この仕様は少なくとも 6 か月間、候補勧告のままとなる。
