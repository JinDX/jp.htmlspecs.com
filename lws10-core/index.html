概要

Linked Web Storage Protocol仕様は、アプリケーションに対し、外部に保存されたデータへの安全で許可に基づく アクセスを相互運用可能な方法で提供することを目的とする。

2. はじめに

本仕様はLinked Web Storage（LWS）プロトコルを定義する。このプロトコルにより、クライアントアプリケーションは エージェントのアイデンティティと権限に基づいて、Webリソースにアクセスし、管理できる。

リンクされたリソースの階層をリソースサーバーが管理し、その階層へのアクセスを提供する方法を標準化することで、この プロトコルは、ユーザーが異なるクライアントアプリケーションを使って同じ格納データを操作できるようにする。これらの リンクされたリソースは、所在を示すコンテナと包含関係、 およびリソース間の関係を記述するメタデータによって定義される。

このプロトコルは、これらのリソースに対する作成、読み取り、更新、削除の標準操作を定義する。各 リソースはURIで識別される。クライアントはルートコンテナからリソース階層をたどり、 サーバー応答で提供されるリンクを通じて、包含リソースとそれらの関係を発見する。

エージェントのアイデンティティを確認するアイデンティティプロバイダーは、Linked Web Storage サーバーの外部にあってもよい。この緩やかな結合により、サーバーは必ずしも資格情報を直接管理せず、代わりに、 署名された認証資格情報をトークンとして受信し、検証できる。そのトークンの発行元は、信頼できるアイデンティティ プロバイダーである。そのため、ユーザーは準拠サーバーに既存のアイデンティティを提示でき、常に そのサーバー専用の新規または既存のアカウントを必要としない。LWSは、たとえば次の OpenID Connect、SAML 2.0、および自己署名された管理下の識別子（CID）の仕様で定義されるユーザー認証を利用する。

認可は、要求元エージェントがリソースへのアクセス、またはそのリソースに対する 操作を実行する権限を持つかどうかを決定する。準拠するLWSサーバーは各リソースにリソース管理者を指定し、その管理者が決定するのは、 リソースが非公開（すなわち、その所有者のみが利用可能）、制限付き（すなわち、定義された ユーザー集合のみが利用可能）、または公開（すなわち、あらゆるユーザーが利用可能）であるかどうかである。サーバーは、 各クライアント要求を処理する際に、リソース管理者によるアクセス判断を適用する。

本仕様は、次の開発者による利用を想定している：

  • クライアントアプリケーションを構築する開発者。そのアプリケーションのアクセス対象はストレージリソース
  • 準拠サーバーを構築する開発者。そのサーバーがアクセスを仲介する対象はストレージリソース

各LWSサーバーインスタンスは、それぞれ独自のリンクされたリソース階層を維持する。エージェントは、 同じ識別情報を使って複数のサーバーを横断的にたどることができ、各サーバーのリソースへのアクセスは、 そのサーバーのリソース管理者が付与する権限によって決定される。すべてのLWSサーバーインスタンスが、 あらゆるエージェント識別子をサポートするとは限らない。個々のLWSサーバーインスタンスは、エージェントに対し、 そのサーバーインスタンスが管理するリソースへのアクセスを得るために、特定のアイデンティティプロバイダーを通じて 自身を識別することを要求する場合がある。

2.1 リソースへのアクセス

LWSプロトコルは、ある当事者がリソースを利用可能にするための標準的なやり取りを定義する。その提供先は、 一部のエージェントである。

  • 提供されるリソース - （利用可能なリソース？公開された リソース？）（未 定義、UCSでは）ネットワーク経由でアクセス可能な実体であり、サービスが公開し、 本書で定義されるプロトコルを使用してやり取り、取得、または操作を行えるもの。
  • 要求元エージェント - （実体、UCSにおける）実体 （例：クライアント、ユーザー、プロセス）であり、提供可能なリソースとやり取りするための要求を開始するもの。

2.2 セキュリティとプライバシー

リソース管理者は、提供されるリソースを 非公開にしても、誰もが利用できるよう公開しても、またはその可視性を限定された集合に制限してもよい。その集合を構成するのは、 要求元エージェントである。

  • 認証 - アイデンティティを検証するプロセス。その対象はエージェントであり、 要求を実行するものである。
  • 認可 - 権限の有無を判断するプロセス。その対象はエージェントであり、 特定のリソースへのアクセス、または一連の操作のいずれかを実行する権限を判断する。
  • リソース 管理者 - （コントローラー、 UCSにおける）エージェントであり、アクセスを制御する権限を持つ。その対象は提供されるリソースである。

3. 用語

「認可サーバー」および「クライアント」という用語は、OAuth 2.0認可フレームワーク[RFC6749]で定義される。

「エンドユーザー」および「発行者」という用語は、OpenID Connect Core 1.0 [OPENID-CONNECT-CORE]で定義される。

本仕様は、以下の用語を定義する：

  • アクセス許可 — データオブジェクトであり、その作成者はストレージコントローラーである。これは、 次の主体の能力を表す：エージェントが特定のアクションを実行する能力であり、対象はストレージリソースで、 一定の 定義された制約に従う。
  • アクセスプロファイル — アクセスプロファイルは、 有効なアクセスポリシーを表現するための要件を記述する。各アクセスプロファイルは、 URIで識別される。サーバーは、1つ以上のアクセスプロファイルをサポートすることを示すために、 サービスオブジェクトのconformsToプロパティでそれらを参照する。このサービスオブジェクトは、 ストレージ記述リソース内にある。
  • アクセス要求 — データオブジェクトであり、その提出者はエージェントである。これは、 特定のアクションを実行する要求を表す。その対象はストレージリソースであり、含まれるのは、 希望するスコープ および制約である。
  • エージェント — URIで識別される人、社会的実体、またはソフトウェア。
  • 認証資格情報 — セキュリティ トークンであり、次の主体についての主張を表明する：エージェントまたはエンドユーザー。このトークンは暗号学的証明によって保護される。 認証資格情報の例には、OpenID Connect IDトークンなどのアイデンティティの表明、 SAMLに基づく表明、および ZCAPなどの能力の表明がある。
  • 認証スイート — 定義された検証 機構であり、具体的にシリアライズされた認証資格情報に対するもの。
  • 補助リソース — ストレージリソースであり、 特定の役割を果たす。その関連先はストレージリソースであり、その主 リソースと呼ばれ、 補助リソースの存続期間は主リソースに結び付けられる。 本仕様は、リンクセットリソースおよびメタデータリソースを、 補助リソースの型として定義するが、 LWS サーバーは、その他の種類の補助リソース（例：アクセス制御 リソース、通知受信箱）も自由に管理できる。 補助リソースは、特定の型のWebリンク[RFC8288]を使用して発見される（次の節を参照：9.1 リソースのメタデータ）。 実装によっては、一部の補助リソースがその主リソースと同一である場合がある。
  • ストレージ リソース — HTTPのリソースであり、定義元はHTTPの 意味論である。これは、Linked Web Storageで定義される読み取り操作をサポートする。 プロトコルによる操作である。 次の仕様に従い、HTTPの 意味論、本仕様は「リソースの性質を制限せず、単に リソースとのやり取りに使用できるインターフェースを定義する」。[RFC9110] このクラスは、IRI https://www.w3.org/ns/lws#StorageResourceで識別される。
  • コンテナ — ストレージリソースであり、列挙できるものは、 次のリソースのコレクションである：ストレージリソース。これは、次に記述される規約に準拠する： 第8節 コンテナ。コンテナ内に新しいリソースを作成する機能、 または既存のコンテナを削除する機能は、次に概説される要件に従う：第9節 操作。
  • データリソース — データを保持するストレージリソースであり、 文書、画像、構造化情報などが該当する。その更新操作および削除操作のサポートは、 次に概説される要件に従う：第9節 操作。
  • 包含 — 次のものの間の関係：コンテナと、ストレージリソース。 そのライフサイクルを、コンテナが管理する。
  • リンクセット リソース — 補助リソースの一種であり、その 表現は次に準拠する：リンクセット：メディア型とリンク関係型 — リンク集合用。リンクセットリソースの更新操作は、 次に概説される要件に従う：第9節 操作。
  • メタデータ リソース — 補助リソースであり、管理するものはストレージである。これは、ストレージリソースを記述し、次に記述される規約に準拠する： 未定。メタデータリソースのライフサイクルは、次のリソースに結び付けられる：ストレージリソース。これは、そのメタデータリソースが記述するものである。
  • リソース — リソースとは、 次に記述されるとおり、[WebArch]および[RFC3986]、「何であれ URIで識別できるもの」である。本質的な特性をメッセージで伝えられるリソース（たとえば、 Webページ、画像、構造化データオブジェクトなど）は、次のように呼ばれる：情報 リソース [WebArch]。
  • ストレージ — 集合であり、 階層的に構成されたHTTPリソースからなる。そのライフサイクルは、 Linked Web Storageプロトコルに記述される規約により管理される。ストレージを記述するのは、ストレージ 記述リソースであり、これはサービスのコレクションを参照する。そのサービスがアフォーダンスを提供する対象は、 それらのリソースである。
  • ストレージコントローラー — エージェントであり、すべてのリソースを制御する。そのリソースが属するのは、ストレージである。
  • ストレージ記述 — ストレージリソースであり、次の文書の要件に準拠する： W3C管理下の識別子文書[CID-1.0]。これは、ストレージを、その サービスおよび機能とともに記述する。
  • ストレージルート — コンテナであり、次の階層のルートにある：包含階層。この階層が属するのは、 ストレージである。ストレージルートは、唯一のストレージリソースであり、LWSの包含階層に親を持たず、また主リソースも持たない。
  • 通知 — 発生したイベントを記述するメッセージ。その発生先は、 リソースである。
  • サブスクリプション — 受信への関心を表明する登録であり、 特定のリソースまたはリソース集合に関する通知を対象とする。
  • サブスクライバー — エージェントであり、作成するものはサブスクリプションで、 その結果として生じる通知を受信する。
  • 通知スイート — 定義された配信機構であり、 具体的なチャネルを対象とする。そのチャネルを通じて通知が送信される相手は、サブスクライバーである。
（削除される可能性のある機能）課題: この節は削除される可能性がある

本仕様は、操作を定義する。その対象は提供される リソースであり、さらに、その結果として生じる状態変化と、応答も定義する。この応答が情報を伝える相手は、要求元エージェントであり、要求された情報を与えるか、または 結果を知らせる。その結果をもたらすのは、操作である。 操作とは、以下のアクションのいずれかであり、実行対象は、 提供されるリソースである：

  • リソースの作成 -
  • リソースの読み取り -
  • 更新： リソース -
  • リソースの削除 -

次の節では、意味論および応答について、 これらの操作ごとに記述する。ただし、以下の基本応答は、あらゆる操作に適用される：

  • 成功 - 操作が完了したとみなされる。これには、リソース表現が伴う場合がある。その表現が内容を伝える対象は、提供されるリソースである。成功応答は、 次の操作については定義されない：リソースの作成操作。代わりに、作成済みを参照。
  • 不 許可
  • 不明な 要求元
  • 不明な エラー - 想定されていないエラー状態の発生に備えて予約されている。その想定の範囲は、 本仕様である

4. 認証

本節は、次の主体を識別する仕組みを定義する：エージェントおよびエンドユーザー。これらがやり取りする相手は、 Linked Web Storageサーバーである。本仕様は、特定の 形式を義務付けない。その対象は、認証資格情報である。ただし、次のものの使用方法は記述する： 既存のアイデンティティシステム。 これらはLinked Web Storage認可フレームワークと組み合わせて使用できる。

4.1 認証 資格情報のデータモデル

本節で記述するデータモデルは、あらゆる 具体的なシリアライズに対する要件を概説する。その対象は、認証資格情報である。

認証資格情報は、MUST 主体についての改ざんを検知できる主張を含めなければならず、その内容は次のとおりである：

  • 主体 REQUIRED — エンドユーザーの識別子。これは、MUST URIでなければならない。
  • 発行者 REQUIRED — 次のものを発行した実体の識別子：認証資格情報。これは、MUST URIでなければならない。
  • クライアント REQUIRED — クライアントアプリケーションの識別子。これは、 SHOULD URIであるべきである。
  • オーディエンス 制限 RECOMMENDED — 値のリストであり、 SHOULD 認可サーバーの識別子を含めるべきである。

4.2 認証 資格情報の検証

検証の対象となるのは、認証資格情報であり、それには信頼が必要である。 その関係は、 資格情報の検証者と発行者の間にある。この信頼関係は、MAY 確立してもよい。 その手段は帯域外の仕組みである。信頼を確立するための追加の仕組みについては、 検証者と発行者の間で用いるものが、個々の認証スイートで概説される。

認証資格情報は、MUST 署名されなければならない。RECOMMENDED：署名には、 非対称暗号を使用することが推奨される。

4.3 認証 資格情報の型識別子

各認証スイートは、MUST トークン型URIに関連付けられなければならない。認証スイートは、SHOULD IANAの「OAuth URI」レジストリで定義されたURIを使用するべきである。

5. 認可

Linked Web Storage は、Web 上で保護対象データを永続化し、管理するための仕組みを記述する。 認可は、そのための仕組みであり、 それにより エージェントはアクセストークンを要求して提示し、この 保護対象データにアクセスする。

本節は、OAuth 2.0 に基づく認可フレームワークを定義する [RFC6749]。これは、基本機構として 取得および提示を行うためのものであり、その対象は アクセストークンである。サーバーは MAY、追加の認可機構をサポートしてもよく、その範囲はこの 基本機構に限られない。

5.1 役割

LWS 認可における役割は、OAuth 2.0 第1.1節で定義されるものと同じである [RFC6749]： リソース所有者、 リソースサーバー、 クライアント（本仕様では 認可クライアントと呼び、 曖昧さを避ける）、および 認可サーバー。 ストレージサーバーは、LWS ストレージ仕様にも準拠するリソースサーバーの一種である。

5.2 プロトコルフロー

本仕様は、クライアントと認可サーバーの間のやり取り、および クライアントと準拠するストレージサーバーの間のやり取りを記述する。

認可サーバーとストレージサーバーの間のやり取りは、この 仕様の対象範囲外である。 認可サーバーは、ストレージサーバーと同じサーバーでも、別の実体でもよい。

5.2.1 認可サーバーの 発見

ストレージサーバーが管理するすべての保護対象リソースには、有効なアクセストークンが必要であり、その生成元は、 信頼できる 認可サーバーである。クライアントは、信頼できる認可サーバーの場所を発見するために、 次の 未認可の HTTP 要求を保護対象リソースに送信できる。

401 (Unauthorized) 応答を生成するストレージサーバーは MUST、 WWW-Authenticate ヘッダーフィールドを送信しなければならず、 少なくとも1つの準拠するチャレンジを含めなければならない。準拠するチャレンジは MUST、 次のパラメーターを含めなければならない： resource_metadata。これは、次の第5.1節で定義される [RFC9728]。その値は、次の文書の URL である： 対象となるのは、 保護対象リソースメタデータ文書であり、 要求されたリソースに対応するものである。

応答は MUST、識別用の Link ヘッダーも含めなければならない。その識別先は、 ストレージであり、そこに含まれるのは、 要求されたリソースである。これは、6.1.2 発見とバインディングに記述される。クライアントは、この URI を resource パラメーターとして、アクセストークンの要求時に指定する。これについては、 5.2.5.1 要求に記述する。

その他のヘッダーおよびパラメーターを MAY 含めてもよい。

以下に、401 応答の例を示す。

例 1 
HTTP/2 401 Unauthorized
Link: <https://storage.example/storage_1>; rel="https://www.w3.org/ns/lws#storage"
WWW-Authenticate: Bearer resource_metadata="https://storage.example/.well-known/oauth-protected-resource/storage_1/photos/img.jpg",
                error="invalid_token"

5.2.2 保護対象リソースの メタデータ

（削除される可能性のある機能）課題

作業部会は、保護対象リソースメタデータの サポートについて、実装者からのフィードバックを積極的に求めている。 十分な実装経験が集まらない場合、この機能は削除または変更される可能性がある。

保護対象リソースメタデータ文書は、クライアントが取得する方法を記述する。 取得対象は、アクセストークンであり、 リソースに対応するものである。この文書は MUST OAuth 2.0保護対象リソースメタデータに準拠しなければならない [RFC9728]。

本仕様は、[RFC9728]を次のように拡張する： authorization_servers パラメーターは REQUIRED であり、 保護対象リソースメタデータ文書に必須となる。また、その値は MUST、 少なくとも1つの発行者識別子を含めなければならず、その発行者は、 認可サーバーである。

注記

保護対象リソースメタデータ文書内の resource 値が識別するのは、 要求されたリソースであり、 ストレージ、すなわちそのリソースを含むものではない。一方、 トークン要求の resource パラメーターは、 ストレージを識別し、そのストレージがアクセストークンのオーディエンスとなる。

以下に、保護対象リソースメタデータ文書の例を示す。

例 2 
{

    "authorization_servers": ["https://authorization.example"]
}

5.2.3 発見結果の検証 — クライアントによる

クライアントがアクセストークンの取得に使用する値は、ストレージサーバーから 401 (Unauthorized) 応答で提供される。アクセストークンを要求する前に、クライアントは MUST、 以下の検査を行わなければならない。各検査では、 発見した値と、401 応答の原因となった要求先 URI とを比較する。いずれかの検査に失敗した場合、 クライアントは MUST NOT、 発見した値を使用してアクセストークンを要求してはならない。

  • resource_metadata URL は MUST、スキームおよび オーソリティが要求先 URI と同じでなければならない。
  • resource 値を持つのは、保護対象リソースメタデータ文書である。この値は MUST、次と同一でなければならない： 要求先 URI。これは、次の第3.3節で要求される [RFC9728]。
  • クライアントは MUST、ストレージ記述を取得しなければならない。その記述対象は、ストレージであり、Link ヘッダーによって識別される。また、その StorageRoot サービスの serviceEndpoint は MUST、スキーム およびオーソリティが要求先 URI と同じでなければならない。
注記

これらの検査は、保護対象リソースメタデータとストレージの両方が、 要求の送信先サーバーを 記述していることを保証する。これにより、第7.3節に記述される TLS サーバー認証、 [RFC9728]の認証が、 メタデータに適用される。これらの検査がないと、悪意あるサーバーが、クライアントにアクセストークンを取得させ、 その対象を別の ストレージにしてから、そのトークンをリプレイできる。クライアントは、ストレージ記述をキャッシュすることで、 毎回の トークン要求の前にそれを取得せずに済む。16.3 リソースの発見を参照。

5.2.4 認可サーバーの メタデータ

認可サーバーは MUST、メタデータリソースを提供しなければならない。これにより、クライアントは、 エンドポイントの場所と機能を、次に記述される方法で発見できる： [RFC8414]。このメタデータリソースは、 MUST 次のパスを持つ URL で利用可能でなければならない： /.well-known/lws-configuration。

次に定義されるメタデータに加えて、[RFC8414]、 LWS 認可サーバーメタデータ文書は、 以下のパラメーターを定義する：

  • subject_token_types_supported OPTIONAL。有効な値のリストを含む JSON 配列であり、 subject_token_type の値が 認可サーバーのトークンエンドポイントに指定可能であることを示す。認可サーバーは、 SHOULD この項目を含めることで、サポートするサブジェクトトークンを通知するべきである。 含める場所は、サーバーメタデータ文書である。
  • subject_identifier_types_supported OPTIONAL。主体識別子の型のリストを含む JSON 配列であり、 認可サーバーがサポートする型を示す。 各値は、"https:" などのスキームで始まる URI、または、 分散型識別子の場合には、 "did:" に DID メソッド名を続けたもの（例："did:web"、 "did:key"）である。 認可サーバーは SHOULD、サポートする主体識別子の型を、 サーバーメタデータ文書にこの項目を含めることで通知するべきである。 省略された場合、既定値は ["https"] である。

5.2.5 トークン交換

LWS 認可サーバーは、準拠する OAuth 2.0 認可サーバーであり、発行できるものは、 クライアント向けのアクセストークンで、 ストレージサーバーで使用するものである。アクセストークンが発行されるには、クライアントがまず、 有効なサブジェクトトークンを提示しなければならない。 その例として、認証資格情報があり、提示先は、 認可サーバーである。提示には OAuth 2.0トークン交換を使用する [RFC8693]。

5.2.5.1 要求

認可サーバーのトークンエンドポイントは MUST、次の urn:ietf:params:oauth:grant-type:token-exchange グラント型をサポートしなければならない。これは、OAuth 2.0トークン交換に記述される [RFC8693]。

トークン交換グラント型を実行する際には、以下の追加要件が適用される：

  • resource パラメーターは REQUIRED である。この パラメーターの値は MUST URI でなければならず、 生成されるアクセストークンの aud（オーディエンス）クレームの設定に使用される。 指定値は MUST、次のものの URI でなければならない：ストレージ。これは、要求されたリソースを含み、その URI が提供されるのは、 Link ヘッダー内で、 未認可応答に含まれる。認可サーバーは MUST、次のすべての要求を拒否しなければならない： resource パラメーターが、 不明または信頼されていない ストレージを識別する要求。
  • subject_token パラメーターは REQUIRED である。 このパラメーターの値は MUST、有効なサブジェクトトークンを含めなければならず、 たとえば、認証 資格情報が該当する。
  • クライアントにアクセストークンを返す前に、認可サーバーは MUST、提示されたすべてのトークンの検証に成功しなければならない。

トークン要求の非規範的な例を示す（subject_token パラメーターは、 途中で省略されている）。

例 4 
POST /token HTTP/1.1
Host: authorization.example
Content-Type: application/x-www-form-urlencoded

grant_type=urn%3Aietf%3Aparams%3Aoauth%3Agrant-type%3Atoken-exchange
&resource=https%3A%2F%2Fstorage.example%2Fstorage_1
&subject_token=eyJ0eXAiOiJhcytqd3QiLCJhbGciO...fiK51VwhsxJ-siBMR-YFiA
&subject_token_type=urn%3Aietf%3Aparams%3Aoauth%3Atoken-type%3Aid_token
5.2.5.2 応答

トークン要求が有効であり、クライアントがその要求を行うことを認可されている場合、 認可サーバーの応答は MUST、 OAuth 2.0認可フレームワークの第5.1節に準拠しなければならない [RFC6749]。生成されるアクセス トークンは MUST、準拠しなければならず、 その準拠先は、OAuth 2.0アクセストークン用の JSON Web Token プロファイルである [RFC9068]。

さらに、アクセストークンは以下の要件を満たさなければならない：

  • sub（主体）— REQUIRED。このクレームは、 MUST、識別用の URI でなければならない。その識別対象は、エージェントであり、 操作を実行するものである
  • iss（発行者）— REQUIRED。このクレームは、 MUST 認可サーバーの URI でなければならない
  • client_id（クライアント ID）— REQUIRED。 このクレームは MUST、クライアントを識別する URI でなければならない。
  • aud（オーディエンス）— REQUIRED。このクレームは、 MUST、クライアントが指定した URI を含めなければならない。 指定先は resource パラメーターであり、この URI が識別するのは、ストレージである。この 値は、制限のために使用され、 アクセストークンが有効となる実体を限定する。
  • exp（有効期限）— REQUIRED。 認可サーバーは SHOULD、存続期間の短いトークンを発行するべきである （RECOMMENDED：300秒以下）。これにより、トークンの 盗難によるリスクを抑える。
  • iat（発行時刻）— REQUIRED。
  • jti（JWT ID）— REQUIRED。

5.2.6 トークンの検証 — ストレージサーバーによる

クライアントはアクセストークンを取得すると、そのトークンをストレージサーバーに提示する。 ストレージサーバーは、操作を実行する前に、このトークンを検証する責任を負う。

5.2.6.1 提示

クライアントは MUST、ストレージサーバーにアクセストークンを提示しなければならず、その際に使用するのは、 Authorization ヘッダーである。 認証スキームは、次に定義されるものを使用する [RFC6750]。

例 8 
Authorization: Bearer eyJ0eXAiOiJhcytqd3QiLCJhbGciOiJFUzI1NiIs...DeWt4QuZXso
5.2.6.2 検証

ストレージサーバーは MUST、アクセストークンを検証しなければならない。そのために行うのは、 以下の検査であり、いずれかに失敗した場合は要求を拒否する：

  • JWT 署名の検証：認可サーバーの公開 鍵を使用して JWT 署名を検証する。この鍵は、 認可サーバーメタデータで指定された jwks_uri から取得する。ストレージサーバーは SHOULD、これらの鍵をキャッシュするべきであり、 MUST 鍵のローテーションをサポートしなければならない。
  • 発行者の検証：iss クレームが、想定する認可 サーバーの識別子と一致することを検証する。
  • オーディエンスの検証：aud クレームに、次のものの URI が含まれることを検証する：ストレージ。そこに含まれるのは、 対象リソースである。
  • 時刻の検証。システム間で許容される時計のずれを考慮する。
    • 現在時刻が exp（有効期限）クレームより前であることを検証する。
    • 現在時刻が nbf（有効開始時刻）クレームより前ではないことを検証する。このクレームが、 存在する場合に行う。
    • iat（発行時刻）クレームが未来の時刻ではないことを検証する。

検証に失敗した場合、ストレージサーバーは MUST、401 Unauthorized を返さなければならず、 WWW-Authenticate ヘッダーを付け、 resource_metadata パラメーターおよび適切なエラーパラメーターを含める。 その例は、 invalid_token、invalid_request、または insufficient_scope である。

それ以外の点ではトークンが有効であっても、認可ポリシーが要求された 操作を許可しない場合、 ストレージサーバーは MUST、要求を拒否しなければならない。

6. 発見

6.1 ストレージ記述リソース

ストレージ記述リソースが提供するのは、 クライアントが利用できる情報であり、 やり取りの対象となるのは、ストレージである。この情報には、機能の記述および サービスエンドポイントの記述が含まれる。

6.1.1 データモデル

ストレージ記述リソースは、 W3C管理下の識別子を特殊化した 文書である [CID-1.0]。 これは、次に定義されるデータモデルに準拠し、[CID-1.0]、そのモデルを LWS 固有のプロパティで拡張する。

  • id - id プロパティは REQUIRED である。その値は MUST、正規 URI でなければならず、 その識別対象は、ストレージである。 次に従い、[CID-1.0]、この URI は、正規の 管理下の識別子文書 URL でもある。
  • type - type プロパティは REQUIRED である。その値は MUST、文字列でなければならず、 その等値対象は、 Storage である。または、Storage と等しい項目を含む文字列の集合でなければならない （大文字と小文字を区別する）。
  • capability - capability プロパティは OPTIONAL である。その値は MUST、集合でなければならず、その要素は、 機能である。各機能は、以下のプロパティを含むマップで記述される。 追加のプロパティが MAY 存在してもよい。
    • id - id プロパティは OPTIONAL である。存在する場合、その値は MUST、 URI でなければならない。
    • type - type プロパティは REQUIRED である。その値は MUST、文字列 または文字列の集合でなければならない。
  • service - service プロパティは REQUIRED である。その値は MUST、サービスの集合でなければならず、 各サービスは、以下のプロパティを含むマップで記述される。追加の プロパティが MAY 存在してもよい。 この集合は MUST、サービスを含めなければならず、その type の値は、 StorageRoot である。
    • id - id プロパティは OPTIONAL である。存在する場合、その値は MUST、 URI でなければならない。
    • type - type プロパティは REQUIRED である。その値は MUST、文字列 または文字列の集合でなければならない。
    • serviceEndpoint - serviceEndpoint プロパティは REQUIRED である。その値は MUST、 URI でなければならない。
例 9: 最小限のストレージ記述リソース 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [{
    "type": "StorageRoot",
    "serviceEndpoint": "https://storage.example/root/"
  }]
}

6.1.2 発見とバインディング

GET および HEAD 要求の対象となるのが、ストレージリソースである場合、すべての応答は MUST、次を含めなければならない： Link ヘッダー。その対象は、ストレージの正規 URI であり、関係 パラメーターも （rel）含め、その値を https://www.w3.org/ns/lws#storage と等しくする。

要求先となる ストレージ URI は MUST、文書を返さなければならず、 その文書は、 ストレージ記述リソースのデータモデルに準拠し、 メディア型を application/lws+cid とする。 ただし、コンテンツネゴシエーションによって別の形式が要求される場合は、この限りではない。

6.1.3 ストレージの機能

ストレージ記述は、記述を含んでもよく、 その記述対象は、ストレージがサポートする追加の機能である。

ストレージが、クライアントによる up リンクの変更を許可し、 そのリンクが属するのが、ストレージリソースで、 それにより、リソースを移動できる場合、その移動先となるのは、コンテナである。この移動については、 9.6 コンテナ間でのリソースの 移動に記述する。このストレージは MUST、機能を記述しなければならず、その type の 値は、 MoveResource である。クライアントは MUST NOT、up リンクを変更できると仮定してはならない。 この機能が存在しない場合が該当する。以下のプロパティを定義する。その対象は、 MoveResource 機能である：

  • appliesTo - appliesTo プロパティは OPTIONAL である。存在する場合、その値は MUST、 型名を表す文字列の集合でなければならない。その型の対象は、ストレージリソースであり、 この機能が適用されるものを示す。たとえば、 DataResource または Container である。プロパティが存在しない場合、この機能は、 適用される対象を、 データリソースのみに限定する。
  • preservesIdentifier - preservesIdentifier プロパティは OPTIONAL である。 存在する場合、その値は MUST、真偽値でなければならず、次のものが識別子を保持するかどうかを示す：ストレージが保持する識別子は、 移動したリソースのものである。プロパティが存在しない場合、クライアントは MUST NOT、 識別子が 保持されると仮定してはならず、MUST、更新への応答に基づいて判断しなければならない。その判断対象は、 識別子であり、 リソースに対応するものである。
例 10: ストレージ記述リソースが、クライアントによる移動を許可することを通知する。 コンテナ間でのリソースの移動が対象となる 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "capability": [{
    "type": "MoveResource",
    "appliesTo": ["DataResource", "Container"],
    "preservesIdentifier": true
  }],
  "service": [{
    "type": "StorageRoot",
    "serviceEndpoint": "https://storage.example/root/"
  }]
}

6.1.4 ストレージサービス

ストレージ記述リソースは MUST、StorageRoot サービスを含めなければならず、その serviceEndpoint は、ストレージルートコンテナの URI である。 追加のサービスが接続される先となるのは、ストレージであり、これらのサービスも MAY 存在してよい。 これらの追加サービスの API 定義は、本仕様の対象範囲外である。

7. リソースの論理的な構成

7.1 コンテナモデル

Linked Web Storage は、リソースを コンテナにまとめる。コンテナは、 メンバーと呼ばれる他のリソースへの参照を保持する特殊なリソースである。コンテナは、 ディレクトリやコレクションに似た構成単位として機能し、クライアントによるリソースのグループ化、発見、 および探索を可能にする。コンテナは、そのメンバーであるリソースへの参照を保持し、 これには、コンテナ以外のリソースと追加のコンテナリソースの両方を含めることができるため、 階層構造を形成できる。通常、コンテナ自体が保持する内容は、 メタデータやそのメンバーの列挙以外にはほとんどなく、その主な役割は、 下位リソースを集約して構造化することである。ストレージシステムのルートは、コンテナとして指定され、 上位の親を持たない最上位の構成単位として機能する。コンテナ表現の構造は、8.1 コンテナの 表現で定義され、そのメディア型とページ分割の要件は、12. LWS メディア型で定義される。 ストレージは MAY ルートコンテナとして機能し、直接の書き込みを可能にしてもよい。

すべての LWS ストレージには、ストレージ ルートがあり、最上位の構成単位として機能する。ストレージルートは親を持たず、 ストレージ 階層へのエントリーポイントとして機能する。

LWS のリソースは、次のいずれかに分類される：

  • コンテナ — 他のリソースを含む リソース。
  • データリソース — データを保持するリソース （文書、画像、構造化データファイルなど）。

7.2 包含

包含関係は、リソースと、その親となる コンテナとの間にあり、rel="up" リンク 関係によって表される。サーバーは MUST Link ヘッダーを、 rel="up" が親コンテナを指す形で、任意のルート以外のリソースへの GET および HEAD 要求に対する 応答に含めなければならない。 

Link: </alice/notes/>; rel="up"

コンテナのメンバーは、その表現内で、 items プロパティを使用して列挙される。このリストはサーバーが管理し、クライアントは直接変更できない。メンバーシップの 変更は、リソースの作成および削除の副作用として発生し、リソースの up リンクの変更を許可するサーバーでは、コンテナ間でのリソースの移動によっても発生する。これについては、9.6 コンテナ間でのリソースの移動に記述する。

7.3 包含関係の整合性

サーバーは MUST 常に 包含関係の整合性を維持しなければならない：

  • 作成: 新しいリソースが コンテナ内に作成された場合、 サーバーは MUST 不可分にそのリソースを コンテナの items リストに追加しなければならない。
  • 削除: リソースが削除された場合、サーバーは MUST、 不可分にそのリソースを親 コンテナの items リストから削除しなければならない。 コンテナを削除するには、その コンテナが、 空である必要がある。ただし、再帰的な削除が明示的に要求された場合は、この限りではない。
  • 移動: リソースの up リンクが変更された場合、サーバーは MUST 不可分にそのリソースを items リストから削除しなければならず、そのリストが属するのは、 以前の親 コンテナである。同時に、items リストへの追加も行わなければならず、そのリストが属するのは、 移動先 コンテナである。up リンクの変更のサポートは、 OPTIONAL であり、それに伴う要件は、9.6 コンテナ間でのリソースの 移動で定義される。
  • 孤立リソースの禁止: すべてのルート以外のリソースは MUST、 ストレージルートから 包含 階層を通じて到達可能でなければならない。
  • 循環の禁止: コンテナは MUST NOT、直接的にも 間接的にも自身を含んではならない。

7.4 リソースの識別

リソースは URI によって識別される。リソースの URI は、包含階層内の位置から独立している。サーバーは、リソースの 作成時に URI を割り当て、MAY クライアントからのヒントを取り入れてもよいが、クライアントは SHOULD NOT、URI 構造が包含関係を反映していると仮定するべきではない。

包含関係は、メタデータ （rel="up" リンクおよび items プロパティを使用する コンテナ 表現）によって表され、URI パス構造によっては表されない。この分離により、サーバーは URI の 割り当てを柔軟に行いつつ、明確に定義された構成モデルを維持できる。

7.5 コンテナのメンバーシップ と認可

クライアントが コンテナへの読み取りアクセス権を持つ場合、その コンテナ 表現は MUST、含まれるリソースの識別子をすべて含めなければならず、 そのリソースは、当該 コンテナ内にあり、クライアントがアクセス権を持つものである。また、MAY、リソースの識別子を含めてもよく、そのリソースが含まれるのは、当該 コンテナであり、クライアントがアクセス権を持たないものである。

クライアントが コンテナの一覧を読み取れることは、含まれる リソース自体へのアクセス権があることを意味せず、その逆も同様である。

8. コンテナ

8.1 コンテナの表現

LWS の コンテナ表現が記述するのは、コンテナとその内容である。本節は、その必須および 任意のプロパティを、application/lws+json として提供される場合について定義する。その他の RDF メディア 型による表現は、コンテンツネゴシエーションを通じて要求できる。

8.1.1 コンテナのプロパティ

コンテナ表現は MUST、以下のプロパティを含めなければならない：

  • id: URI が識別するのは、コンテナである。
  • type: 値は "Container" である。
  • totalItems: リソースの総数を示す整数であり、 含まれる先は、コンテナで、クライアントに開示できるものを数える。この 数は SHOULD 正確であるべきだが、MAY 概算であってもよい。
  • items: 包含リソース記述の配列（下記参照）。もし、 当該 コンテナが空なら、この値は MUST、 空の配列でなければならない。コンテナの一覧が ページ分割されている場合、items は現在のページのリソースのみを含む。詳細は、ページ分割を参照。

8.1.2 包含リソースの 記述

items 配列の各項目は、次に含まれるリソースを記述する：コンテナ。包含リソース記述は MUST、以下を含めなければならない：

  • id: 包含リソースの URI。
  • type: リソースの型。MUST、 "DataResource" または "Container"、あるいは、これらのうち少なくとも1つを含む配列でなければならない。 対象となるのは、この2つの文字列である。サーバーは MAY、追加のユーザー定義型を、 URI として含めてもよい（例：["DataResource", "http://example.org/customType"]）。

包含リソース記述は SHOULD、以下を含めるべきである：

  • format: リソースのメディア型（例： "text/plain"、"image/jpeg"）。MUST 存在しなければならず、 DataResources に適用される。
  • size: 整数で表される、バイト単位のリソースのサイズ。
  • modified: リソースが最後に変更された日時であり、 ISO 8601 の日時文字列として表す。

9. 操作

本節は、Linked Web Storage（LWS）サーバーが行う4つの基本操作を定義する。このサーバーは MUST、それらをサポートしなければならない。これらの操作は、リソースとコンテナを トランスポートに依存しない方法で操作し、実装の詳細よりも意味論に焦点を当てる。各操作は、 入力、期待される動作、および取り得る応答を規定する。応答には、成功を示す情報、リソースの 表現（該当する場合）、およびエラー状態が含まれる。実装は MUST、 これらの操作を不可分かつ一貫した形で処理しなければならない。すなわち、各操作は完全に成功するか、 部分的な副作用を残さずに失敗する。エラーの場合、応答は SHOULD、 十分な詳細を提供するべきであり、エージェントが機密情報の漏えいなしに問題を理解できるようにする。

各基本操作（作成、読み取り、更新、削除）について、使用する HTTP メソッド、必須の ヘッダーまたはその他の特別な考慮事項（コンテンツネゴシエーション、コンテナ一覧のページ分割、 条件付き要求を含む）、およびサーバーが行い、返すべき内容を記述する。結果を示すために標準の HTTP ステータスコードを使用し、 クォータ超過などの状況には、追加の対応付けを行う。 該当するのは、507 Insufficient Storage や、事前条件の不成立を示す 412 Precondition Failed である。この バインディングは、HTTP/1.1 および関連する RFC に従うことを目指す（たとえば、[RFC7231] は HTTP 意味論、[RFC7233] は範囲 要求、[RFC5789] は PATCH、[RFC8288] は Web リンク、 および [RFC9264] はリンク 集合）。これにより、Web 標準と自然に統合される。発見可能性を重視し、そのための仕組みには、 Link ヘッダーや、401 応答の WWW-Authenticate ヘッダーなどがあり、 URI の場所をハードコードすることを避ける。すべての操作でメタデータとの統合が要求され、不可分性、 およびサーバー管理プロパティとユーザー管理プロパティのためのリンク集合の使用を保証する。

注記：本仕様のすべての例と同様に、本節の例（HTTP 要求 および応答の断片）は 非規範的 であり、典型的な使用法を示すためのものである。実際の 要件は、説明文および表で規定する。また、このバインディングは HTTP を扱うが（最初の 対象プロトコルとして）、LWS 操作は、原理上、将来ほかのプロトコルにも結び付けられる。 メディア型の要件が適用される コンテナ表現については、12. LWS メディア型で定義する。

9.1 リソースのメタデータ

9.1.1 メタデータ

本節は、メタデータを関連付けるモデルを定義する。その関連先は、ストレージ リソースである。LWS メタデータシステムは、Web リンクの原則に基づく [RFC8288]。これにより、サーバーは関係を記述できる。 その関係は、型付きリンクを使用してリソース間に表される。メタデータは発見可能性を高め、自己記述的な API をサポートし、リソース操作、および コンテナ階層と整合する。

メタデータモデル LWS のすべてのメタデータは、リソースを起点とする型付きリンクの集合として表される（そのリソースはリンク コンテキストとなる）。各リンクは、以下から構成される：

  • リンクターゲット：関連するリソースを識別する URI。
  • 関係型：関係の性質を定義する文字列。
  • 任意のターゲット属性：リンクまたは ターゲットリソースをさらに記述する、追加のキーと値の組。

メタデータは、リソースとその表現を区別する。複数のメディア型を使用できるのは、 適用可能な場合である。データリソースでは、メタデータに表現が含まれ、それぞれに、 format および任意の sizeInBytes がある。コンテナおよび データリソースについては、親となる コンテナリソースへのリンクを、当該 リソースのメタデータの一部とみなす。

リンクセットリソース ストレージ内の各リソースについて、サーバーは MUST、メタデータの リンクを独立したリソースとして利用可能にしなければならない。その準拠先は、[RFC9264]である。

  • 発見：リソースのリンクセットは、次の関係を持つ Link ヘッダーを通じて発見できる： rel="linkset"。
  • メディア型：リンクセットリソースは MUST、 application/linkset+json として利用可能でなければならない。
  • 整合性：'linkset' リンクは MUST、サーバー管理のリソースを指さなければならない。 リンクセットの更新は MUST、関連するリソースの 操作と不可分に行い、一貫性を維持しなければならない。

メタデータの発見 クライアントは主に、GET または HEAD 要求への応答に含まれる Link ヘッダーを通じてメタデータを発見する。

  • ストレージ：サーバーは MUST、次を指定した Link ヘッダーを、 rel="https://www.w3.org/ns/lws#storage"、関連する応答に含めなければならない。
  • 包含：サーバーは MUST、 ルート以外のすべてのリソースについて、rel="up" を持つ Link ヘッダーを含め、その参照先を親の コンテナとしなければならない。
  • プリファレンス：クライアントは MAY、Prefer ヘッダーを使用してもよい [RFC7240]。その際の URI は、 https://www.w3.org/ns/lws#PreferLinkRelations とし、特定の 関係を含めるか、省略する。

メタデータの型

分類 説明
システム管理 サーバーが維持する。読み取り専用。含まれるものは、linkset、type、 format、size、modified。
コアメタデータ クライアントが管理する（サーバーの制限に従う）。含まれるものは、up、 items、title、creator。
ユーザー定義 ユーザーが作成したカスタム語彙および索引。

変更可能性に関する考慮事項 コアメタデータは MAY、クライアントが変更してもよい。相互運用性を保証するため、 サーバーは MUST、標準の HTTP ヘッダーを使用して、その機能を通知しなければならない：

  1. メソッドの発見：サーバーは MUST、GET および PATCH 操作のサポートを、リンクセットリソースについて、Allow ヘッダーで通知しなければならない。

  2. パッチ形式の発見：サーバーは MUST、JSON Patch のサポートを通知しなければならない [RFC6902]。その通知には、 Accept-Patch ヘッダーを使用する：Accept-Patch: application/json-patch+json。

  3. 任意のメソッド：サーバーは MAY、PUT または代替のパッチ 形式をサポートしてもよい。サポートする場合、これらは MUST、それぞれ Allow および Accept-Patch ヘッダーに含めなければならない。

[!IMPORTANT] クライアントは SHOULD NOT、PUT または特定のパッチ 形式のサポートを、リソースのヘッダーで通知されない限り仮定するべきではなく、MUST、 405 Method Not Allowed または 415 Unsupported Media Type 応答を適切に処理しなければならない。

メタデータの管理 メタデータは、リソースに関連付けられた リンクセット リソースの URI とやり取りすることで管理する。サーバーは MUST、ETag ヘッダーを含めなければならない。 これは、次に定義されるものであり、[RFC9110]、GET および HEAD 要求への応答に含める。

  • 部分更新（PATCH）：これは、メタデータ管理の主要な仕組みである。サーバーは MUST、application/json-patch+json を使用する PATCH をサポートしなければならない。

  • 置換（PUT）：Allow ヘッダーで通知されている場合、クライアントは MAY、 リンクセット全体を置き換えてもよい。サーバーが PUT をサポートしない場合は、MUST、405 Method Not Allowed で要求を拒否しなければならない。

  • 制限：サーバーは MAY、特定のリンクへの変更を制限してもよい。 対象は、up や items などであり、システムの整合性を維持するためである。サーバーは MUST、クライアントによる変更が許可されていないリンクを、 パッチの適用時に保持しなければならない。クライアントによる up リンクの変更を許可するサーバーは、それによって、 リソースの移動を、コンテナ間で許可する。そのようなサーバーは MUST、MoveResource 機能を、ストレージ記述に記述しなければならない。これについては、 6.1.3 ストレージの機能に記述する。それに伴う要件は、9.6 リソースの移動 — コンテナ間で定義する。

  • ライフサイクル：メタデータのライフサイクルは、記述対象のリソースに結び付けられる。リソースの削除は MUST、関連するものの自動削除を伴わなければならず、その対象は、リンクセットリソースのメタデータである。

9.2 リソースの作成

リソースの作成操作は、新しい 提供されるリソースを、既存の コンテナに追加する。この 操作は、データリソースとサブコンテナの両方の作成を扱う。

入力：

  • 対象コンテナ：識別子が指すのは、コンテナであり、その中に、 新しいリソースが作成される。
  • 識別子のヒント：新しいリソースの識別子に対する、任意の提案。サーバーは、 このヒントを使用してもよいが、その必要はない。
  • 内容：新しいリソースの初期内容および型。

動作：

  • 識別子の生成：サーバーは、新しい リソースの最終的な識別子（URI）を決定する。識別子のヒントが指定されている場合、サーバーはそれを取り入れようとし、 一意性と妥当性を、コンテナ内で保証する。ヒントが指定されていない場合、 サーバーは一意の識別子を生成する。
  • コンテナのメンバーシップの更新：サーバーは、新しいリソースを不可分に、 対象の コンテナのメンバー一覧に追加する。
  • メタデータの初期化：サーバーは、新しい リソースのシステムメタデータを初期化する。リソースに関連する メタデータリソースがあれば、それも、 初期化される。

取り得る応答：

  • 作成済み：操作に成功した。サーバーは、 新しく作成されたリソースの最終的な識別子を返す。
  • 対象が見つからない：指定された対象の コンテナが、 存在しない。
  • 不許可：クライアントのアイデンティティは既知だが、リソースを作成する権限がなく、 その作成先は、この コンテナである。
  • 不明な要求元：サーバーはクライアントのアイデンティティを認識せず、 認証を要求する。
  • 競合：生成された識別子を持つリソースがすでに存在するか、 ほかの状態の競合がある。
  • 不明なエラー：予期しない内部エラーが発生した。

新しいリソースは、対象の コンテナ URI に POST することで作成し、サーバーが、 最終的な識別子を割り当てる。クライアントは MAY、新しいリソースの初期ユーザー管理メタデータを、 POST 要求に1つ以上の Link ヘッダーを含めることで指定してもよい。その際の構文は、 次の Web リンクに従う [RFC8288]。サーバー管理メタデータは MUST、 作成時にサーバーが自動生成しなければならず、MUST NOT、 クライアントが指定したリンクによって上書きされてはならない。

成功した場合、サーバーは MUST、新しい URI を次に含め、201 ステータスコードを返さなければならない： Location ヘッダー。サーバーは MUST、Link ヘッダーを含めなければならず、 主要なサーバー管理メタデータを示すものとして、親の コンテナへのリンク （rel="up"）、および作成されたリソース専用の リンクセットリソースへのリンク （rel="linkset"; type="application/linkset+json"）を含める。追加のリンクは SHOULD、rel="type" を含めるべきである（これが示すのは、 https://www.w3.org/ns/lws#Container または https://www.w3.org/ns/lws#DataResource）。本文は MAY、空であっても、 リソースの最小限の表現を含めてもよい。すべてのメタデータの作成およびリンク付けは MUST、一貫性を維持するため、リソースの作成と不可分に行わなければならない。

POST（コンテナ URI に対して） – サーバーが割り当てる名前で作成する： POST を使用し、新しいリソースを、既存の コンテナ内に追加する。サーバーは、識別子を、 そのリソースに割り当てる。クライアントは、作成するリソースの型を次のように示す：

  • 作成対象が コンテナの場合、クライアントは MUST、rel="type" を指定した Link ヘッダーを含め、 その参照先を Container 型としなければならない： Link: <https://www.w3.org/ns/lws#Container>; rel="type"。
  • 作成対象が データリソースの場合、クライアントは、 リソースの内容を要求本文に含め、適切な Content-Type ヘッダーを指定する。

例（POST による新しいデータリソースの作成）：

POST /alice/notes/ HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: text/plain
Content-Length: 47

この例では、クライアントは、コンテナ /alice/notes/ に POST している。 text/plain の内容（食料品の買い物リスト）を指定する。/alice/notes/ が存在し、 クライアントが認可されていれば、サーバーは、新しい データリソースを作成し、それを コンテナのメンバーシップに追加する。

例（POST への応答 — データリソース）：

HTTP/1.1 201 Created
Location: /alice/notes/shoppinglist.txt
Content-Type: text/plain; charset=UTF-8
Link: </alice/notes/shoppinglist.txt.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/notes/>; rel="up"
Link: <https://www.w3.org/ns/lws#DataResource>; rel="type"
Content-Length: 0

成功した場合、Location ヘッダーに新しい URI を含め、201 Created を返す。本文は、 空でも、最小限の表現でもよい。 対象の コンテナ /alice/notes/ が存在しない場合、サーバーは、 MUST、別のステータスコードのほうが適切でない限り、404 エラーステータスを返さなければならない。

作成対象が コンテナの場合：新しい コンテナを作成するには、クライアントは、既存の親 コンテナに対して POST を使用し、Link ヘッダーで、 Container 型を示す。たとえば、次のとおりである： 

POST /alice/ HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Length: 0
Link: <https://www.w3.org/ns/lws#Container>; rel="type"

例（POST への応答 — コンテナ）：

HTTP/1.1 201 Created
Location: /alice/notes/
Link: </alice/notes/.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/>; rel="up"
Link: <https://www.w3.org/ns/lws#Container>; rel="type"
Content-Length: 0

これにより、新しい コンテナが /alice/notes/ に作成され、サーバーが生成した メタデータには、rel="type" として https://www.w3.org/ns/lws#Container が含まれる。

作成に関する追加の注記（HTTP バインディング）：

  • POST は冪等ではない。繰り返すと重複が作成される可能性がある。クライアントは SHOULD、 意図しない再試行を避けるか、一意の識別子や検査を使用してこれを防ぐべきである。
  • メタデータの更新は不可分である。サーバーは MUST、リンクセットリソースが作成され、必須の サーバー管理フィールドが設定されてから、成功を返すことを保証しなければならない。
  • 発見可能性のため、サーバーは SHOULD、Link ヘッダーを含め、 rel="https://www.w3.org/ns/lws#storage" を 401 応答に指定し、クライアントを、 ハードコードされた URI なしで案内するべきである。

メタデータの管理および取得（作成に関連するもの）： メタデータは主に読み取り操作で取得するが、作成時に生成される。クライアントは、 作成直後に、新しいリソース URI への GET または HEAD によって取得できる。クライアントは、 Prefer ヘッダーを使用し、特定のメタデータリンク（関係型を通じて）および 属性を含めるよう要求できる。

9.3 リソースの読み取り

既存のリソースの表現、または次の一覧を取得する：コンテナ。

  • 入力: 対象識別子および任意のパラメーター。
  • 動作:
    • コンテナ以外のリソースの場合、サーバーはリソースの内容を返す。
    • コンテナの場合、サーバーはメンバーである リソースの一覧を返し、MAY、これを次に基づいて絞り込んでもよい：認可。一覧には、 各メンバーのコアメタデータを含めなければならない。
  • 結果: 要求された表現、または失敗の通知。

リソースの読み取り操作は、HTTP GET 要求でリソース表現を要求する（ヘッダーのみの 要求には HEAD を使用する）。動作は、対象 URL が コンテナか、コンテナ以外のリソース（データリソース）かによって異なる。サーバーは MUST、 メタデータを通じてリソースの型を区別しなければならない。すべての応答は MUST、 第8.1節で定義されるメタデータと統合し、主要な関係を示す Link ヘッダーを含めなければならない。その例は、 rel="linkset"、rel="up"、および rel="type" である。サーバーは MUST、読み取り中のリソースの状態とそのメタデータとの間で不可分性を保証しなければならない。

GET（コンテナ以外のリソース） – リソースの内容を取得する： 内容全体を取得するには、リソース URI に GET を送信する（認可されている場合）。200 OK で応答し、本文に データを含め、Content-Type を格納されているメディア型と一致させる。サーバーは MUST、 次に従って範囲要求をサポートしなければならない [RFC7233]。これは部分 取得のためである。応答は MUST、次に定義される ETag ヘッダーを含めなければならない： [RFC9110]。

例（ファイルを GET する）：

GET /alice/notes/shoppinglist.txt HTTP/1.1
Authorization: Bearer <token>
Accept: text/plain

GET（コンテナリソース） – 一覧の取得：コンテナの内容： 対象 URI が コンテナに対応する場合（メタデータの型によって判断する）、GET 要求は、 次のメンバー一覧を返す：コンテナ。応答の Content-Type: application/lws+json は、コンテナ 表現であり、定義先は コンテナの 表現の節である。この表現では、一覧に各メンバーのメタデータを含める： リソース識別子（MUST）、型（MUST）、メディア型 （DataResources では MUST）、サイズ（SHOULD）、および 更新タイムスタンプ（SHOULD）。

      "type": "DataResource",
      "id": "/alice/notes/shoppinglist.txt",
      "format": "text/plain",
      "size": 47,
      "modified": "2025-11-24T12:00:00Z"
    },
    {
      "type": ["DataResource", "http://example.org/customType"],
      "id": "/alice/notes/todo.json",
      "format": "application/json",
      "size": 2048,
      "modified": "2025-11-24T13:00:00Z"
    }
  ]
}

要求：

GET /alice/notes/ HTTP/1.1
Authorization: Bearer <token>
Accept: text/turtle; profile="https://www.w3.org/ns/lws/v1"

応答ヘッダー：

HTTP/1.1 200 OK
Content-Type: text/turtle; profile="https://www.w3.org/ns/lws/v1"
ETag: "container-etag-789"
Link: </alice/notes/.meta>; rel="linkset"; type="application/linkset+json"
Link: </alice/>; rel="up"
Link: <https://www.w3.org/ns/lws#Container>; rel="type"

応答本文：

@prefix lws: <https://www.w3.org/ns/lws#> .
@prefix dcterms: <http://purl.org/dc/terms/> .
@prefix schema: <http://schema.org/> .
@prefix xsd: <http://www.w3.org/2001/XMLSchema#> .

<> a lws:Container ;
  lws:totalItems 2 ;
  lws:items <shoppinglist.txt>, <todo.json> .

<shoppinglist.txt> a lws:DataResource ;
  dcterms:format "text/plain" ;
  schema:size "47"^^xsd:long ;
  dcterms:modified "2025-11-24T12:00:00Z"^^xsd:dateTime .

<todo.json> a lws:DataResource, <http://example.org/customType> ;
  dcterms:format "application/json" ;
  schema:size "2048"^^xsd:long ;
  dcterms:modified "2025-11-24T13:00:00Z"^^xsd:dateTime .

この例では、/alice/notes/ は コンテナである。応答は、LWS コンテキストを持つ JSON-LD を 使用し、必須のメタデータとともにメンバーを列挙する。各項目には、type、 id、format、size、および modified タイムスタンプが、フラットな プロパティとして含まれる。

いずれの場合も、サーバーは MUST、以下のメタデータを応答 ヘッダーに含めなければならない：次に定義される ETag ヘッダー [RFC9110]、および Link ヘッダー。 これには rel="linkset"、rel="up"、および rel="type" を指定し、それが、 コンテナであることを示す。

HEAD（任意のリソースまたは コンテナ） – ヘッダー／メタデータのみ： LWS サーバーは MUST、HEAD をサポートしなければならない [RFC9110]。これは、 コンテナとそれ以外の両方に適用され、GET と同じヘッダーを返す （Content-Type およびメタデータ用の Link を含む）が、本文は返さない。これにより、 内容を転送せずにメタデータを取得できる。

キャッシュと条件付き要求： LWS は HTTP のキャッシュ意味論を利用する。サーバーは SHOULD、次に定義される条件付き要求をサポートするべきである [RFC9110]。 これには、エンティティタグ（ETags）や日付に基づく検証子（たとえば、 If-Modified-Since ヘッダー）などの仕組みが含まれる。リソースまたは コンテナの一覧が、 変更されていない場合、304 Not Modified で応答し、不要な再転送を避ける。

発見可能性と認可： 発見可能性を高めるため、 401 Unauthorized 応答は、WWW-Authenticate ヘッダーを含み、 resource_metadata パラメーターを指定する。これは、認可サーバーの発見に記述されるとおりであり、クライアントは、 URI をハードコードせずに認可サーバーを見つけられる。

9.4 リソースの更新

全体の置換または部分的なパッチにより、既存の[提供されるリソース]の状態を変更する。

  • 入力: 対象識別子、新しい内容、および任意の並行性制約。
  • 動作: サーバーは、変更を不可分に適用する。並行性制約が 指定されている場合、リソースが、最後に読み取られた後で変更されていれば更新を拒否する。読み取りを行ったのは、 要求元である。
  • 結果: 更新の確認、または競合の通知。

リソースの更新は、 既存の 提供される リソースの内容を、PUT 要求（リソース全体を置換する）または PATCH 要求（部分的な 変更を適用する）によって変更する。クライアントには、リソースの URL への書き込みアクセス権が必要であり、その実行対象は、 これらの操作である。 注記：本節は、リソースの主たる内容の更新を記述する。そのメタデータの更新については、次の節を参照： 9.3.2。 LWS サーバーは MUST、リソース URI に対する PUT および PATCH 要求を、 リソースの内容のみの変更として扱わなければならず、既定では、関連する リンクセットリソースに影響を与えない。内容と メタデータを単一の不可分な操作で更新することを選ぶ場合、クライアントは MAY、Link ヘッダーをリソース URI への PUT/PATCH 要求に含め、プリファレンス 'Prefer: set-linkset' を指定してもよい（定義元は [RFC7240]）。この場合、 サーバーは MUST、指定された Link ヘッダーを、リンクセットの置換 （PUT の場合）または部分更新（PATCH の場合）として解釈し、内容の変更とあわせて適用しなければならない。 この動作は、サーバーにとって OPTIONAL だが、サポートする場合は、MUST、Prefer ヘッダーによって明示的に呼び出されなければならない。これにより、 意図しないメタデータの上書きを防ぐ。内容とメタデータの同時更新をサポートしないサーバーは MUST、このプリファレンスを無視するか、501 Not Implemented で応答しなければならない。

PUT（リソース全体の置換） – 新しい内容全体を含めて、リソース URI に PUT を送信する。その内容を含めるのは、 本文であり、一致する Content-Type（通常は既存の型と整合するもの）も指定する。PUT は冪等であり、 既存のリソースに対して適用される。クライアントは SHOULD、次に定義される条件付き要求を使用するべきである： [RFC9110]。これにより、並行して行われた変更の上書きを避ける。

例（PUT によるリソースの更新）：

PUT /alice/personalinfo.json HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
If-Match: "abc123456"
{
"name": "Alice",
"age": 30,
"city": "New London",
"state": "Connecticut"
}

この例では、クライアントは、既存の JSON リソースを更新している。その場所は、 /alice/personalinfo.json である。If-Match ヘッダーには、エンティティタグ （ETag）を含める。これは、以前の GET または HEAD 要求で受け取ったものである。サーバーは、それを、 現在のエンティティタグ（ETag）と比較し、一致すれば、内容を、 指定された JSON に置き換える。一致しなければ、サーバーは更新を拒否する（その間にリソースが、 他の誰かによって変更されたためである）。 成功応答：更新に成功した場合、サーバーは 200 OK で応答でき、 更新後の表現や確認用の情報（新しい内容やその一部など）を含めることもできる。 または、サーバーは 204 No Content で応答し、本文なしで成功を示してもよい。 特に、追加の情報を伝える必要がない場合によく用いられる。たとえば、次のとおりである： 

HTTP/1.1 204 No Content
  • エラー応答：If-Match 事前条件が一致しない場合 （並行した変更）、サーバーは 412 Precondition Failed で応答する。 リソースが存在しない場合、更新を意図した PUT の結果は 404 Not Found となる。 クライアントが認可されていない場合は 403 Forbidden（または 401 Unauthorized。有効な 資格情報が指定されていない場合）。要求ペイロードが有効でない場合は 400 Bad Request。

PATCH（部分更新） – HTTP PATCH メソッド [RFC5789] は、 クライアントがリソースへの部分的な変更を指定できるようにする。新しい 内容全体を送信する必要はない。これは、内容全体の送信が非効率となる大きなリソースで、 わずかな部分だけが変更された場合や、特定の変更を適用したい並行編集に有用である。LWS サーバーは MUST、少なくとも JSON Patch をサポートしなければならない。 対象は、次に定義される application/json-patch+json である [RFC6902]。

リソースメタデータの更新（リンクセットに対する HTTP PUT / PATCH） リソースのメタデータは、対応する リンクセットリソースの変更によって更新する。 これは、rel="linkset" を指定した Link ヘッダーを通じて発見される。 全体の置換（PUT）：リンクセットリソース URI への PUT 要求は、完全な リンクセット文書を本文に含め、リソースのすべてのメタデータを置き換える。 部分更新（PATCH）：リンクセットリソース URI への PATCH 要求は、特定のリンクを追加、削除、または 変更する。

メタデータに対する条件付き要求 リソースのメタデータは複数の主体が変更できるため、並行した上書きを防ぐことが、 重要である。サーバーとクライアントは SHOULD、次に定義される条件付き要求を使用するべきである： [RFC9110]。これは、次に対する PUT および PATCH 操作に適用する：リンクセットリソース。サーバーが条件付き 要求を受信し、その事前条件が満たされない場合、MUST、要求を拒否し、その際の ステータスコードを 412 Precondition Failed としなければならない。 例（PUT によるリンクセットの置換）： クライアントは、まずリンクセットを取得する。 

GET /alice/personalinfo.json.meta HTTP/1.1
Authorization: Bearer <token>
Accept: application/linkset+json
HTTP/1.1 200 OK
Content-Type: application/linkset+json
{
  "linkset": [
    {
      "anchor": "/alice/personalinfo.json",
      "describedby": [ { "href": "/schemas/personal-info.json" } ]
    }
  ]
}

ここで、クライアントはライセンスを追加したいと考える。新しい完全なリンクセット文書を構築し、PUT 要求を送信する。

PUT /alice/personalinfo.json.meta HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/linkset+json
{
  "linkset": [
    {
      "anchor": "/alice/personalinfo.json",
      "describedby": [ { "href": "/schemas/personal-info.json" } ],
      "license": [ { "href": "https://creativecommons.org/licenses/by/4.0/" } ]
    }
  ]
}

成功した場合、サーバーは成功応答を返す。

HTTP/1.1 204 No Content

更新規則の概要 リソースの内容のみを変更する場合 → リソース自体に PUT/PATCH を行う。 リソースのリンク（メタデータ）のみを変更する場合 → リソースに関連付けられた リンクセットリソースに PUT/PATCH を行う。 内容とリンクの両方を変更する場合 → リソース自体に PUT/PATCH を行い、適切な Link ヘッダーと 'Prefer: set-linkset' の両方を含める。両方を設定する動作は、既定では無効である。

9.5 リソースの削除

リソースおよび関連するメタデータを永続的に削除する。

  • 入力: 対象識別子、任意の再帰フラグ（コンテナ用）、および任意の並行性制約。
  • 動作:
    • コンテナ以外のリソースの場合、サーバーは内容とメタデータを削除し、 親 コンテナのメンバーシップを更新する。
    • コンテナの場合、サーバーは通常、その コンテナが空であることを要求する。ただし、再帰的な削除が、 明示的に要求され、かつサポートされている場合は、この限りではない。
  • 結果: 削除の確認、または失敗の通知。

リソースの削除操作は、HTTP DELETE メソッドを使用して実装する。これは、上記の抽象 操作で定義されるとおりである。本節は、入力、動作、および応答に対する HTTP バインディングを規定する。

DELETE 要求は、削除するリソースまたは コンテナの URI を対象とする。クライアントは MAY、ETag を指定した If-Match ヘッダーを、並行性の 検査のために含めてもよい。

削除と 包含： リソースが削除された場合、サーバーは MUST、そのリソースを不可分に、 親 コンテナの items リストから削除しなければならない。親コンテナの totalItems の数値は SHOULD、これに応じて更新するべきである。

コンテナ以外のリソースの場合、サーバーは、リソースの内容、関連するメタデータ（リンクセットリソース）、および 包含参照を削除する。 その参照があるのは、親 コンテナである。

コンテナリソースの場合、サーバーは既定で非再帰的な 削除を行う。コンテナが空でなく、再帰が要求されていない場合、サーバーは、 MUST 409 Conflict で要求を拒否しなければならない。サーバーは MAY、 内包されるすべてのリソースの再帰的な削除をサポートしてもよい。その内包先は、コンテナであり、削除の 対象となる。クライアントは MUST、Depth: infinity ヘッダーを使用して、 再帰的な削除を要求しなければならない。これは、次に定義されるとおりである [RFC4918]。

成功した場合、サーバーは MUST、204 No Content で応答しなければならない。サーバーは SHOULD、次に定義される条件付き要求をサポートするべきである [RFC9110]。

クライアントが認可されていない場合、サーバーは MUST、403 Forbidden（ クライアントのアイデンティティは既知だが権限が不十分な場合）、または 401 Unauthorized（有効な 認証が提供されていない場合）を返さなければならない。リソースの存在を明らかにすることがセキュリティリスクとなる場合、 サーバーは MAY、代わりに 404 Not Found を返してもよい。

例（コンテナ以外のリソースを DELETE する）：

DELETE /alice/notes/shoppinglist.txt HTTP/1.1
Authorization: Bearer <token>
If-Match: "abc123456"

ETag が一致し、クライアントが認可されていると仮定すると、サーバーはリソースとそのメタデータを削除し、 親コンテナ /alice/notes/ からそのリソースを削除する。これらを不可分に行う：

HTTP/1.1 204 No Content

例（空でないコンテナを再帰なしで DELETE する）：

DELETE /alice/notes/ HTTP/1.1
Authorization: Bearer <token>

/alice/notes/ にリソースが含まれると仮定すると、サーバーは削除を拒否する：

HTTP/1.1 409 Conflict
Content-Type: text/plain

削除できません：コンテナ /alice/notes/ - コンテナが空ではありません。

例（サポートされている場合、コンテナを再帰的に DELETE する）：

DELETE /alice/notes/ HTTP/1.1
Authorization: Bearer <token>
Depth: infinity

サーバーが再帰をサポートし、クライアントがすべての内容に対する権限を持つと仮定すると、サーバーは、 コンテナとその子孫を不可分に削除する：

HTTP/1.1 204 No Content

9.6 コンテナ間でのリソースの 移動

本仕様は、移動のための専用の HTTP メソッドを定義しない。その対象は、提供されるリソースであり、その移動元は、 ある コンテナで、移動先は別のコンテナである。この点は、MOVE メソッドを、 定義する WebDAV と異なる [RFC4918]。 代わりに、移動は、リソースの 包含メタデータの更新として表される。すなわち、 クライアントは、リソースの up リンクを、その リンクセットリソース内で変更し、 移動先の コンテナを指すようにするために、リソースの 更新操作を使用する。サーバーは、その変更から実際の移動を導き出す。

注記
移動は、リソースの作成操作に続いて、 リソースの削除操作を行うことには置き換えられない。リソース識別子はサーバーが割り当てるため、 クライアントが別の コンテナに内容を再作成しても、必ずしも、 元のリソースの識別子を保持できず、その識別子を指すすべてのリンクが壊れる 可能性がある。また、この2つの要求は不可分ではなく、観測者からは、リソースが両方の コンテナに存在するか、どちらにも存在しないように見える可能性がある。移動を、 包含メタデータの変更として表すことで、これら両方の問題を回避できる。これは、 変更によってリソースの同一性とその内容が影響を受けないためである。

サーバーのサポート： up リンクはサーバーが管理し、サーバーは、クライアントによる、 変更を許可することを要求されない。これは、9.1 リソースの メタデータに記述される。リソースの up リンクをクライアントが変更することを許可し、 それによってリソースを コンテナ間で移動できるようにするサーバーは、MUST、 MoveResource 機能を、その ストレージ 記述に記述しなければならない。これは、6.1.3 ストレージの機能に記述される。また、MUST、 本節の要件を実装しなければならない。これを許可しないサーバーは、MUST 要求を、 409 Conflict などの適切な 4xx ステータスコードで拒否しなければならず、MUST NOT MoveResource 機能を記述してはならない。

移動の要求： クライアントは、リソースの移動のため、その リンクセットリソースに部分更新を適用し、 up リンクのターゲットを、移動先の コンテナの識別子に置き換える。9.1 リソースのメタデータで要求されるとおり、サーバーは MUST、application/json-patch+json をサポートしなければならない [RFC6902]。この更新に適用される。あらゆる、 変更の対象となる リンクセットリソースと同様に、クライアントは SHOULD、 現在の値を保持する If-Match ヘッダーフィールドを含め、要求を条件付きにするべきである。その値は、 ETag であり、リンクセットリソースのものである。これは、9.4 リソースの更新に記述される。サーバーは、 MAY 条件付き要求を要求し、条件なしの要求を 428 Precondition Required で拒否してもよい。

移動先は MUST、既存の コンテナでなければならない。サーバーは MUST、up リンクのターゲットを、 既存の コンテナ以外に設定するパッチを、409 Conflict などの適切な 4xx ステータスコードで拒否しなければならない。サーバーは MUST、同様に、リソースから、 up リンクを失わせるパッチを拒否しなければならない。これは、すべてのルート以外のリソースが、ストレージルートから到達可能であるためである。

本仕様は、移動先を、ストレージのうち、移動されるリソースを保持するものに限定しない。 ただし、サーバーは、リソースを、コンテナへ移動することをサポートするよう要求されず、その所在が、別の、 ストレージである場合、 MAY、そのようなパッチを 409 Conflict などの適切な 4xx ステータスコードで拒否してもよい。そのようなパッチを受け入れるサーバーには、本節の他の要件も引き続き適用され、 これには、変更を不可分に適用する要件も含まれる。

注記
JSON Patch は、変更する値を JSON Pointer で識別する [RFC6901]。その中では、配列のメンバーが、 位置によって指定される。したがって、up リンクのターゲットを置き換えるパッチは、リソースのリンクコンテキストの位置に依存する。その所在は、linkset 配列であり、さらに、up 配列内でのターゲットオブジェクトの位置にも依存する。クライアントは、これらの、 位置を、リンクセットリソースを読み取ることで把握する。条件付き要求は、 パッチの適用時にもそれらの位置が有効であることを保証する。クライアントはさらに、 test 操作を、たとえばリンクコンテキストの anchor や、 up リンクの現在のターゲットに対して使用し、変更を保護できる。リンクセットリソース全体の置き換えとは異なり、このようなパッチは他のすべてのリンクに、 影響を与えないため、クライアントは、変更しないリンクを改めて記述する必要がない。

影響の対象となる 包含： 更新が成功すると、サーバーは MUST、不可分にそのリソースを、 items リストのうち、以前の親 コンテナのものから削除し、 items リストのうち、移動先の コンテナのものに追加しなければならない。totalItems の数は、 両方の コンテナについて、SHOULD 更新するべきである。 それぞれに応じて更新し、両方の コンテナの ETag は MUST、 変更を反映するように更新しなければならない。

移動されるリソースの内容と、そのユーザー定義メタデータは、移動による影響を受けない。サーバーは MUST、リンクセットリソース内のリンクのうち、 クライアントによる変更が許可されていないものを保持しなければならず、これには linkset および type などのサーバー管理リンクも含まれる。補助リソースのうち、その存続期間が移動される、 リソースに結び付いているものは、移動後もそのリソースに結び付いたままとなる。

サーバーは MUST、更新が 包含関係の整合性に関する、 要件に違反する場合、その更新を拒否しなければならない。その要件は、7. リソースの論理的な構成にあり、応答には 409 Conflict などの適切な 4xx ステータスコードを使用する。 特に、コンテナは MUST NOT、それ自体の内部、 または自身の子孫のいずれかの内部に移動してはならない。これは、包含階層に循環が生じるためである。

移動されるリソースの同一性： リソースの URI は、包含階層内の位置から独立しており、 これは、7. リソースの論理的な構成に記述される。したがって、サーバーは SHOULD、 移動されるリソースの識別子を保持し、そのリソースへの既存のリンクが引き続き有効となるようにするべきであり、SHOULD そうするかどうかを、preservesIdentifier プロパティを MoveResource 機能に使用して宣言するべきである。そのプロパティがない場合、クライアントは MUST NOT、識別子が保持されると仮定してはならない。

移動されるリソースの識別子を保持しないサーバーは MUST、応答に、 200 OK と、更新された リンクセットリソースの表現を使用し、その、 anchor をリソースの新しい識別子としなければならず、MUST、次も含めなければならない： Content-Location ヘッダーフィールド。その値は、リンクセットリソース自体の新しい識別子である。そのようなサーバーは SHOULD、以前の識別子に対する後続の要求に応答するべきであり、その対象は、 リソースおよびその 補助リソースである。応答には 301 Moved Permanently を使用し、 新しい識別子を指す Location ヘッダーフィールドを含める。

移動対象が コンテナの場合： サーバーは MAY、up リンクの変更を、コンテナについてサポートしてもよい。また、MUST、そのサポートを、 Container を appliesTo プロパティに含めて、 MoveResource 機能で示さなければならない。コンテナが移動される場合、その子孫も、 一緒に移動し、それらの識別子には、移動される コンテナの識別子と同じ要件が適用される。データリソースの移動をサポートするが、コンテナの移動はサポートしないサーバーは、MUST、そのような要求を 409 Conflict などの適切な 4xx ステータスコードで拒否しなければならず、MUST NOT、Container を、 appliesTo プロパティに含めてはならない。

認可： サーバーは MUST NOT、up リンクへの変更を適用してはならない。ただし、 要求元の エージェントが、次の両方を認可されている場合を除く：リソースの削除操作を移動されるリソースに対して実行すること、および、 リソースの作成操作を、移動先の コンテナ内で実行すること。

コンテナが移動される場合、その コンテナだけが、 親を変更されるリソースとなる。その子孫は互いの相対的な位置を保持し、 サーバーが識別子を保持する場合は、それぞれの識別子も保持する。したがって、エージェントは、 移動先で各子孫を再作成することについて認可される必要はない。それでも、適用されるポリシーが、 それらの子孫について変わる可能性はある。これは、アクセスが、位置に基づいて制御されることが多いためであり、 その位置が属するのは、包含階層である。このため、必要となる認可は、 移動対象となる コンテナについて、それを削除するための認可であり、 再帰的な削除に適用される。これは、9.5 リソースの削除に記述され、これに加えて、移動先の コンテナで作成するための認可が必要となる。サーバーは MUST、その、 認可をサブツリー全体について変更の適用前に評価しなければならず、MUST NOT、 変更を部分的に適用してはならない。

注記
リソースへのアクセスは、ポリシーによって制御されることが多い。そのポリシーが基準とするのは、 リソースの位置であり、その所在は、包含階層である。したがって、リソースを移動すると、 ポリシーを編集しなくても、誰がアクセスできるかが、許可する方向にも拒否する方向にも変わる可能性がある。実装が、 この結果をどのように可視化するか、その提示先となる ストレージ コントローラーおよび エージェントについての方法は、本仕様の対象範囲外である。16.6 リソースの移動 — コンテナ間および 17.3 コンテナ間でのリソースの移動を参照。

例（データリソースを別のコンテナに移動する）： この例では、ストレージは、不透明な識別子を割り当て、その識別子が反映しないのは、包含関係である。 移動されるリソースは https://storage.example/f8c3de3d で、その リンクセットリソースは、 https://storage.example/9b1e07a4 で、移動元と移動先の コンテナは、 https://storage.example/1d4f8a02 と https://storage.example/c2a71f60 で、 それぞれ識別される。クライアントは、 読み取り済みであり、その対象は、リンクセットリソースで、その中で up リンクは、 最初のリンクコンテキストの最初のターゲットオブジェクトである。 

PATCH /9b1e07a4 HTTP/1.1
Host: storage.example
Authorization: Bearer <token>
Content-Type: application/json-patch+json
If-Match: "meta-v3"

[
  { "op": "replace", "path": "/linkset/0/up/0/href", "value": "https://storage.example/c2a71f60" }
]

クライアントが認可されており、移動先の コンテナが存在すると仮定すると、サーバーは、 リソースを https://storage.example/1d4f8a02 の items リストから削除し、 https://storage.example/c2a71f60 の items リストに追加し、リンクセットリソースを更新する。これらは不可分に行われる： 

HTTP/1.1 204 No Content
ETag: "meta-v4"
Link: <https://storage.example/c2a71f60>; rel="up"

リソースは引き続き https://storage.example/f8c3de3d で利用可能であり、現在は、 https://storage.example/c2a71f60 のメンバーである。リソースの識別子は、その、 位置を、 階層内で符号化していなかったため、移動は、包含メタデータでのみ観測できる。

例（サーバーが新しい識別子を割り当てる移動）：

PATCH /alice/notes/shoppinglist.txt.meta HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: application/json-patch+json
If-Match: "meta-v3"

[
  { "op": "replace", "path": "/linkset/0/up/0/href", "value": "/alice/archive/" }
]

識別子を 包含階層から導出し、そのために、 "preservesIdentifier": false を通知するサーバーは、識別子を保持できない。そのサーバーは、 結果として生じる識別子を、更新された リンクセットリソースで報告する： 

HTTP/1.1 200 OK
Content-Type: application/linkset+json
Content-Location: /alice/archive/shoppinglist.txt.meta
ETag: "meta-v4"

{
  "linkset": [{
    "anchor": "/alice/archive/shoppinglist.txt",
    "up": [{ "href": "/alice/archive/" }],
    "linkset": [{ "href": "/alice/archive/shoppinglist.txt.meta",
                  "type": "application/linkset+json" }]
  }]
}

例（コンテナを自身の子孫のいずれかの内部に移動する）：

PATCH /alice/notes/.meta HTTP/1.1
Host: example.com
Authorization: Bearer <token>
Content-Type: application/json-patch+json
If-Match: "meta-v7"

[
  { "op": "replace", "path": "/linkset/0/up/0/href", "value": "/alice/notes/2026/" }
]

サーバーは、その更新によって、包含階層に循環が生じるため、更新を拒否する： 

HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "title": "コンテナを自身の子孫のいずれかの内部に移動することはできません",
  "status": 409,
  "detail": "/alice/notes/2026/ は /alice/notes/ の子孫です"
}

通知： リソースの移動のサポートを通知し、通知を発行するサーバーは SHOULD、成功した移動を単一の Move アクティビティで記述するべきである。これは、 10.2.3 アクティビティの 型に記述されるとおりであり、個別の Delete および Create アクティビティを使用する代わりとなる。

9.7 HTTP ステータスの対応関係の 概要

この表は、汎用的な LWS 応答（ 第8節）を、一貫性のために HTTP ステータスコードとペイロードに対応付け、具体的な状況として、 ページ分割、条件付き要求、クォータ制約、メタデータとの統合を組み込んでいる：

LWS 応答 HTTP ステータスコード HTTP ペイロード
成功（読み取りまたは更新で、返すものが、 データである場合） 200 OK リソース 表現を応答本文に含める（GET の場合、または PUT/PATCH が内容を返す場合）。あわせて、 関連ヘッダー（Content-Type、および Link。後者は、次のようなメタデータ用： rel="linkset" や rel="up"）も含める。コンテナの一覧には、 規範的なコンテキストとメンバーのメタデータ（ID、型、サイズ、タイムスタンプなど）を持つ JSON-LD を含める。
作成済み（新しいリソース） 201 Created 通常は応答本文を含めない（または新しいリソースの最小限の表現を含める）。 Location ヘッダーは、新しいリソースの URI に設定する。Link ヘッダーは、 サーバー管理メタデータ用である。
削除済み（返す内容なし） 204 No Content 応答本文を含めない。リソースが削除されたか、要求が成功し、 他に伝えることがないことを示す。サーバーは MAY、410 Gone を、 恒久的な削除に使用してもよい。
不正な要求（無効な入力または制約） 400 Bad Request 何が問題であったかを説明するエラーの詳細。サーバーは SHOULD、次に、 定義される標準形式を使用するべきである [RFC9457]。これは、 構造化されたエラー応答に適用され、たとえば、"type"、 "title"、"status"、"detail"、および、 "instance" などのフィールドを持つ JSON オブジェクトが該当する。

10. 通知

本節では、リンクトウェブストレージサーバーが管理するリソースの変更について、 クライアントが適時に更新を受け取る仕組みを定義する。本仕様では、共通の 通知データモデルとサブスクリプションの仕組みを定義する。具体的な配信チャネルは、 個別の通知スイート仕様で説明する。

10.1 通知の発見

ストレージは MAY 通知をサポートしてもよい。通知をサポートするストレージは MUST サービスオブジェクトを service 配列（自身の ストレージ記述 リソース内）で公開し、その type を NotificationService としなければならない。

サービスオブジェクトは MUST serviceEndpoint プロパティを含めなければならず、 その値は サブスクリプションエンドポイントの URI でなければならない。また、サービスオブジェクトは MUST subscriptionType プロパティを含めなければならず、その値は、サポートされる各 サブスクリプションの型を識別する文字列の配列でなければならない。

サービスオブジェクトには、追加のプロパティが MAY 存在してもよい。

例 12: 通知サービスを含むストレージ 記述 
{
  "@context": ["https://www.w3.org/ns/lws/v1"],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [{
    "type": "NotificationService",
    "serviceEndpoint": "https://notification.example/subscriptions",
    "subscriptionType": [
      "WebhookSubscription"
    ]
  }]
}
注記

サーバーは、すべてのサブスクリプションの型をサポートする必要はない。 subscriptionType 配列は、利用可能な型を正確に示す。

10.2 通知データモデル

通知は、型が Notification の JSON-LD 文書として表現される。エンベロープは、配信の コンテキストに関するメタデータを保持し、Activity Streams 2.0 [ACTIVITYSTREAMS-CORE] [ACTIVITYSTREAMS-VOCABULARY] の、イベントを記述するアクティビティを包む。

10.2.1 エンベロープのプロパティ

通知エンベロープには、以下のプロパティがある：

  • type — REQUIRED。値は MUST 文字列 Notification でなければならない。
  • storage — REQUIRED。通知が関連付けられている LWS ストレージを識別する URI。
  • activity — REQUIRED。JSON オブジェクトまたは JSON オブジェクトの配列。 各オブジェクトは Activity Streams 2.0 データモデルに準拠し、発生した1つまたは 複数のイベントを記述する。10.2.2 アクティビティのプロパティを参照。
例 13: 通知エンベロープ 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1",
    "https://www.w3.org/ns/activitystreams"
  ],
  "type": "Notification",
  "storage": "https://storage.example/",
  "activity": {
    "id": "ec4dcc48-6581-4232-81c9-584525a98693",
    "type": ["Delete"],
    "object": {
      "id": "https://storage.example/alice/notes/shopping.txt",
      "type": ["DataResource"]
    },
    "origin": "https://storage.example/alice/notes/",
    "published": "2026-03-26T10:30:00Z"
  }
}

10.2.2 アクティビティのプロパティ

activity プロパティ内の各アクティビティオブジェクトは MUST 次に示す Activity Streams 2.0 データモデルに準拠し、MUST 以下のプロパティを含めなければならない：

  • id — REQUIRED。アクティビティを一意に識別する文字列。
  • type — REQUIRED。少なくとも 1つの Activity Streams 2.0 のアクティビティの型を含む文字列の配列。
  • object — REQUIRED。通知の対象となるリソースを識別する JSON オブジェクト。object は MUST 以下に示す プロパティを含めなければならない：
    • id — REQUIRED。リソースの URI。
    • type — REQUIRED。少なくとも 1つの リソースの型を含む文字列の配列。本仕様で定義される値には、 Container および DataResource がある。追加の型の値を MAY 含めてもよい。
  • published — REQUIRED。次の仕様に準拠する日時の値： [RFC3339]。この値は、 アクティビティが発生した日時を示す。

以下のプロパティは OPTIONAL である：

  • actor — アクションを実行したエージェントを識別する URI。
  • target — リソースの追加先となった コンテナを識別する URI。Create および Move アクティビティで使用する。
  • origin — リソースが削除された元の コンテナを識別する URI。Delete および Move アクティビティで使用する。

10.2.3 アクティビティの型

サーバーは MUST 以下の Activity Streams 2.0 のアクティビティの型をサポートし、 それらによって ストレージリソースの変更を示さなければならない：

  • Create — コンテナ内に新しいリソースが作成された。 target フィールドは、リソースが追加されたコンテナを示す。
  • Update — 既存のリソースのコンテンツまたはメタデータが変更された。
  • Delete — リソースが削除された。origin フィールドは、 リソースが削除された元のコンテナを示す。

次の節で説明するように、クライアントがリソースをコンテナ間で移動することを許可するサーバーは、 9.6 コンテナ間でのリソースの 移動に従い、MUST 以下のアクティビティの型をサポートしなければならない：

  • Move — リソースがあるコンテナから別のコンテナへ移動された。 origin フィールドは、リソースが削除された元のコンテナを示し、 target フィールドは、リソースが追加された先のコンテナを示す。 object フィールドは、移動後のリソースの状態を記述する。

他のアクティビティの型も MAY サポートしてもよい。

10.2.4 通知の一括処理

サーバーは MAY 複数のアクティビティを1つの通知エンベロープに まとめてもよい。そのためには、 アクティビティオブジェクトの配列を activity プロパティの値として指定する。

例 14: 一括通知 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1",
    "https://www.w3.org/ns/activitystreams"
  ],
  "type": "Notification",
  "storage": "https://storage.example/",
  "activity": [
    {
      "id": "a1b2c3d4-5678-9abc-def0-1234567890ab",
      "type": ["Create"],
      "object": {
        "id": "https://storage.example/alice/notes/meeting.txt",
        "type": ["DataResource"]
      },
      "target": "https://storage.example/alice/notes/",
      "published": "2026-03-26T10:30:00Z"
    },
    {
      "id": "b2c3d4e5-6789-abcd-ef01-234567890abc",
      "type": ["Update"],
      "object": {
        "id": "https://storage.example/alice/profile",
        "type": ["DataResource"]
      },
      "published": "2026-03-26T10:30:01Z"
    }
  ]
}

10.3 サブスクリプション

通知を受信するために、サブスクライバーは サブスクリプションを作成する。 これは、 認証済みの POST 要求を serviceEndpoint（ NotificationService のプロパティ）に送信することで行う。要求本文は MUST application/lws+json メディア型に準拠しなければならない。

10.3.1 サブスクリプション要求

サブスクリプション要求は MUST 以下のフィールドを含めなければならない：

  • type — REQUIRED。サブスクリプションの 型を識別する文字列。 値は MUST 対応する型のいずれかでなければならない。対応する型は subscriptionType 配列（NotificationService 内）に列挙される。
  • topic — REQUIRED。サブスクリプションに含まれる リソースを 識別する URI の配列。

サブスクリプション要求は MAY 特定の サブスクリプションの型で 必要とされる追加のフィールドを含めてもよい。

例 15: サブスクリプション要求 
POST /subscriptions HTTP/2
Host: notification.example
Authorization: Bearer <access-token>
Content-Type: application/lws+json

{
  "@context": ["https://www.w3.org/ns/lws/v1"],
  "type": "WebhookSubscription",
  "topic": [
    "https://storage.example/alice/notes/",
    "https://storage.example/alice/profile"
  ],
  "inbox": "https://receiver.example/hooks/lws"
}

10.3.2 サブスクリプションの範囲

コンテナへの サブスクリプションは再帰的である。サブスクライバーは、 コンテナ自体、およびそのコンテナに推移的に含まれるすべてのリソースについて 通知を受け取る。データリソースへの サブスクリプションは、その 個別のリソースだけに適用される。

10.3.3 サブスクリプションの 認可

サーバーは MUST サブスクリプションの作成時にリソースの認可を適用しなければならない。 サブスクライバーが、すべての対象リソースに対する読み取りアクセス相当の権限を 持っていない場合、 その対象が topic 配列に列挙されていれば、サーバーは MUST その サブスクリプションの 要求を拒否しなければならない。

認可は MUST 通知の配信時にも適用しなければならない。サーバーは MUST NOT 通知を、 サブスクライバーが イベント発生時に読み取りを認可されていないリソースについて配信してはならない。この規則は、 サブスクリプションの範囲内の全リソースに適用され、サブコンテナ内のリソースも含まれる。

サブスクライバーのリソースまたはコンテナへのアクセス（ 対象は サブスクリプションの範囲内）が、当該 サブスクリプションの作成後に失効した場合、サーバーは MUST 影響を受けるリソースの通知の配信を停止しなければならない。サーバーは SHOULD NOT サブスクリプション全体を終了するべきではない。 ただし、サブスクライバーが topic 配列内のすべてのリソースへのアクセスを失った場合を除く。

注記

サブスクリプション作成時の認可は、サブスクライバーが通知を受信する正当な 根拠を持つことを検証する。配信時の認可は、 通知が サブスクライバーの現在の権限と整合することを保証し、 サブスクリプションの 作成後に生じる可能性のある認可の変更を考慮する。

10.3.4 サブスクリプション応答

サブスクリプション作成要求が成功した際の応答は MUST メディア型 application/lws+json に準拠し、MUST 以下の フィールドを含めなければならない：

  • type — REQUIRED。要求で指定された サブスクリプションの 型と等しい文字列。
  • subscription — REQUIRED。その サブスクリプションを表す URL。

10.3.5 サブスクリプションの型の 識別子

各 通知スイートは MUST サブスクリプションの型を示す文字列に関連付けられていなければならない。 サブスクリプションの型を示す文字列は、subscriptionType 配列（ NotificationService 内）、およびサブスクリプション要求の type フィールドで使用される。

11. アクセス要求とアクセス許可

アクセス要求とアクセス許可は、エージェントがリソースへのアクセスを要求し、 ストレージコントローラーが定められた制約付きでアクセスを許可するための仕組みを提供する。 アクセスを要求および許可するためのエンドポイントは、一種の専用受信箱として機能する。

エージェントは、 アクセス許可を認可トークンとしてサーバーに提示しない。 むしろ、アクセス許可は、何が誰に認可されたか、 またどのような制約下で認可されたかを記録する役割を果たす。アクセス許可が作成または取り消し（削除）された場合、 基盤となるアクセスポリシーを調整して、 その変更を反映する責任はサーバーにある。アクセス許可エンドポイントと特定のポリシー 適用層とのやり取りは、本仕様の範囲外である。

本節で定義される アクセスプロファイルは、アクション、制約、 および被許諾者などの、 Open Digital Rights Language（ODRL）の概念に基づいている。 他のプロファイルでは、異なる概念的枠組みを使用できる。

11.1 発見

ストレージは MAY アクセス要求および アクセス許可のサポートを、 その ストレージ記述リソースで表明してもよい。そのようなサポートが 表明される場合、 アクセス要求用のエンドポイントを記述するサービスオブジェクトは MUST type を文字列 AccessRequestService と等しくしなければならず、 アクセス許可用のエンドポイントを記述するサービスオブジェクトは MUST プロパティ type を文字列 AccessGrantService と等しくしなければならない。サービス オブジェクトは SHOULD conformsTo プロパティを含めるべきであり、その値は コレクションとし、 そのエンドポイントでサポートされる アクセスプロファイルを識別する1つ以上の URI を 含めるべきである。追加のプロパティを MAY 含めてもよい：

例 16: アクセス要求およびアクセス許可のサービスを含むストレージ 記述 
{
  "@context": [
    "https://www.w3.org/ns/cid/v1",
    "https://www.w3.org/ns/lws/v1"
  ],
  "id": "https://storage.example/",
  "type": "Storage",
  "service": [
    {
      "type": "StorageRoot",
      "serviceEndpoint": "https://storage.example/root/"
    },
    {
      "type": "AccessRequestService",
      "serviceEndpoint": "https://access.example/request/",
      "conformsTo": ["https://www.w3.org/ns/lws#AccessProfile"]
    },
    {
      "type": "AccessGrantService",
      "serviceEndpoint": "https://access.example/grant/",
      "conformsTo": ["https://www.w3.org/ns/lws#AccessProfile"]
    }
  ]
}

11.2 データモデル

アクセス要求または アクセス許可は、データ オブジェクトであり、識別とルーティングのためのプロパティに加え、 要求または許可された操作を記述する access オブジェクトを 表現する。アクセス要求を ODRL の概念を使用して記述するプロファイルについては、11.3 アクセスプロファイルで説明する。

次の例は、アクセス要求を示す。この例は、 11.4.1 JSON-LD シリアライズで定義される JSON-LD シリアライズを使用して示している。

例 17: アクセス要求 
{

    "https://www.w3.org/ns/lws/v1"
  ],
  "type": ["AccessRequest"],
  "inbox": "https://id.example/agent/inbox/",
  "storage": "https://storage.example/",
  "access": [{
    "type": ["AccessPolicy"],

    "assignee": "https://id.example/agent",

      "type": "StorageResource",
      "value": ["https://storage.example/root/projects/"]
    },
    "constraint": [
      {
        "leftOperand": "purpose",

      },
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      }
    ]
  }]
}

次の例は、アクセス許可を示す。この例は、 11.4.1 JSON-LD シリアライズで定義される JSON-LD シリアライズを使用して示している。

例 18: アクセス許可 
{
  "@context": [

他のプロパティは MAY アクセス要求および アクセス許可に存在してもよい。

11.2.1 型

type プロパティは、文書の型を表す。

type プロパティの値は MUST 1つ以上の 用語および 絶対 URL 文字列でなければならない。 アクセス要求では、値は MUST 用語 AccessRequest を含めなければならない。 アクセス許可では、値は MUST 用語として AccessGrant を含めなければならない。追加の型の値を MAY 含めてもよい。

このプロパティは REQUIRED である。

本文書は、次の型の値を アクセス要求 および アクセス許可について定義する：

  • AccessRequest — エージェントによるリソースへのアクセス要求。
  • AccessGrant — ストレージ コントローラーによる、 リソースへのアクセスを許可する認可。
例 19: type プロパティ 
{
  "type": ["AccessGrant"]
}

11.2.2 ストレージ

storage プロパティは、 アクセス要求または アクセス許可の 適用範囲となる LWS ストレージを識別する。

storage プロパティの値は MUST URI でなければならない。

このプロパティは REQUIRED である。

例 20: storage プロパティ 
{
  "storage": "https://storage.example/"
}

11.2.3 受信箱

inbox プロパティは、 アクセス要求または アクセス許可に関連する通知を受信するための URI を指定する （11.6 通知を参照）。

inbox プロパティの値は MUST URI でなければならない。

このプロパティは OPTIONAL である。

例 21: inbox プロパティ 
{
  "inbox": "https://id.example/agent/inbox/"
}

11.2.4 アクセス

access プロパティは、1つ以上の アクセスプロファイルの特性を、 サーバーがサポートするプロファイルに基づいて記述する。 プロファイルのうち、 ODRL 情報モデルに基づくものについては、 11.3 アクセスプロファイルで説明する。

access プロパティの値は MUST 1つ 以上の オブジェクトのコレクションでなければならない。

このプロパティは REQUIRED である。

11.3 アクセスプロファイル

本仕様は、次に示す ODRL 情報モデルおよび ODRL 語彙に基づくアクセスプロファイルを定義する。 このプロファイルは、URL https://www.w3.org/ns/lws#AccessProfile で識別される。

11.3.1 型

type プロパティは、アクセスポリシーの型を表す。

type プロパティの値は MUST 1つ以上の 用語および 絶対 URL 文字列でなければならず、MUST 用語 AccessPolicy を含めなければならない。追加の型の値を MAY 含めてもよい。

このプロパティは REQUIRED である。

例 22: アクセスポリシーの型 
{
  "access": [{
    "type": ["AccessPolicy"]
  }]
}

11.3.2 アクション

action プロパティが記述する 操作は、エージェントが 実行を希望するもの（要求の場合）、または実行を認可されているもの（許可の場合）である。

action プロパティの値は MUST 1つ 以上の 文字列のコレクションでなければならない。各値は MUST サーバーが認識する操作に 対応しなければならない。 以下の値を MUST サポートしなければならない：read、modify、 create、および delete。read、 modify、および delete の各値は、 ODRL 語彙で定義される。 create の値は、本 仕様で定義される。

これらのアクション値は、LWS 操作に次のように対応する：

  • read — リソースまたはそのメタデータを取得する（HTTP GET、HEAD）
  • modify — 既存のリソースを変更する（HTTP PUT、PATCH）
  • create — コンテナ内に新しいリソースを作成する（HTTP POST）
  • delete — 既存のリソースを削除する（HTTP DELETE）

このプロパティは REQUIRED である。

例 23: action プロパティ 
{
  "access": [{
    "action": ["read", "create"]
  }]
}

11.3.3 被許諾者

assignee プロパティは、アクセスを要求する当事者（ 要求の場合）、またはアクセスを許可される当事者（許可の場合）を識別する。

assignee プロパティの値は MUST URI でなければならない。公開 アクセスは MAY Agent クラスを使用して付与してもよい。このクラスは、FOAF 語彙に含まれ、URI http://xmlns.com/foaf/0.1/Agent で識別される。

このプロパティは REQUIRED である。

例 24: assignee プロパティ 
{
  "access": [{
    "assignee": "https://id.example/agent"
  }]
}

11.3.4 対象

target プロパティは、リソースを識別し、そのリソースに対して、 アクセス要求または アクセス許可が 適用される。

target プロパティは MUST 以下の プロパティを含むオブジェクトでなければならない：

  • type — 用語または 絶対 URL 文字列。 対象マッチャーの 型を識別する。
  • value — 対象リソースの識別に使用される、 1つ以上の文字列のコレクション。

本仕様は、対象オブジェクトで使用する以下の type 値を 定義する：

  • https://www.w3.org/ns/lws#DataResource — 型が lws:DataResource のリソースに一致する。
  • https://www.w3.org/ns/lws#Container — 型が lws:Container のリソースに一致する。
  • https://www.w3.org/ns/lws#StorageResource — 任意の ストレージリソースに一致する。

サーバーは MAY 追加の型の値をサポートしてもよい。

このプロパティは OPTIONAL である。

例 25: StorageResource 型を持つ target プロパティ 
{
  "access": [{
    "target": {
      "type": "StorageResource",
      "value": [
        "https://storage.example/root/2025",
        "https://storage.example/root/2026"
      ]
    }
  }]
}

11.3.5 制約

constraint プロパティは、要求または許可されるアクセスを制限したり、 条件付けたりする条件を定義する。このプロパティは、ODRL の 制約モデルを使用する。

constraint プロパティが存在する場合、その値は MUST 制約オブジェクトのコレクション でなければならない。各制約オブジェクトは MUST 以下の プロパティを含めなければならない：

  • leftOperand — 制約対象のオペランドを識別する文字列。
  • operator — 比較演算子を識別する文字列。
  • rightOperand — 比較対象の値。その型は leftOperand に依存する。

複数の制約オブジェクトが存在する場合、そのすべてを MUST 満たさなければならない。

このプロファイルのサポートを表明するサーバーは MUST 以下の leftOperand の値をサポートしなければならない：

  • client — HTTP 要求のクライアント識別子を表す
  • format — 対象となる HTTP リソースのメディア型を 表す
  • type — リソースのリンクヘッダーで表明される型の URL を 表す
  • purpose — 要求または許可されるアクセスの利用目的を 表す
  • dateTime — 現在の日時を表す

このプロパティは OPTIONAL である。

以下の例は、これらの制約の使用方法を示す：

11.3.5.1 目的の制約

以下の例では、leftOperand の値に purpose を使用して、要求または許可されるアクセスの 利用目的を記述する。eq 演算子を 使用する場合、rightOperand の値は目的を識別する URI である。 isAnyOf 演算子を使用する場合、rightOperand の値は目的の URI の配列であり、指定された目的が 列挙された値のいずれかに一致すれば、その制約は満たされる：

例 26: 目的の制約 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "purpose",
        "operator": "isAnyOf",
        "rightOperand": [
          "https://purpose.example/collaboration",
          "https://purpose.example/research"
        ]
      }
    ]
  }]
}
11.3.5.2 クライアントの制約

以下の例では、leftOperand の値に client を使用して、アクセスを 特定のクライアントアプリケーションに制限する。eq 演算子を使用する場合、 rightOperand の値はクライアントを識別する URI である：

例 27: クライアントの制約 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "client",
        "operator": "eq",
        "rightOperand": "https://app.example/client-id"
      }
    ]
  }]
}
11.3.5.3 形式の制約

以下の例では、leftOperand の値に format を使用して、 アクセスを特定のメディア型を持つリソースに制限する。eq 演算子を 使用する場合、rightOperand の値は、 IANA メディア型を識別する文字列である。 isAnyOf 演算子を使用する場合、rightOperand の値は メディア型を示す文字列の配列であり、リソースの メディア型が列挙された値のいずれかに一致すれば、アクセスが許可される：

例 28: 形式の制約 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "format",
        "operator": "isAnyOf",
        "rightOperand": ["image/jpeg", "image/png"]
      }
    ]
  }]
}
11.3.5.4 リソースの型の 制約

すべての ストレージリソースは、型の値を示すリンクヘッダーを 含む：

例 29: 型の値を持つリンクヘッダー 
Link: <https://www.w3.org/ns/lws#DataResource>; rel="type"
Link: <https://type.example/Playlist>; rel="type"

以下の例では、leftOperand の値に type を使用して、表明されたリソースの型に基づきアクセスを制限する。 リソースの型は HTTP Link ヘッダーで表明される。 eq 演算子を使用する場合、rightOperand の値は リソースの型を識別する URI である。isAnyOf 演算子を 使用する場合、rightOperand の値は型の URI の配列であり、 リソースの型が列挙された値のいずれかに一致すれば、アクセスが許可される：

例 30: リソースの型の制約 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "type",
        "operator": "isAnyOf",
        "rightOperand": [
          "https://type.example/Playlist",
          "https://type.example/Song"
        ]
      }
    ]
  }]
}
11.3.5.5 時間の制約

以下の例では、leftOperand の値に dateTime を使用して、アクセスを 特定の時間範囲に制限する。gteq 演算子はその範囲の開始を 定義し、lteq 演算子は終了を定義する。 時間の制約における rightOperand の値は、 XML スキーマの dateTime 文字列である：

例 31: 時間の制約 
{
  "access": [{
    "constraint": [
      {
        "leftOperand": "dateTime",
        "operator": "gteq",
        "rightOperand": "2026-03-09T12:00:00Z"
      },
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      }
    ]
  }]
}
11.3.5.6 制約の組み合わせ

複数の制約オブジェクトが存在する場合、そのすべてを MUST 満たさなければ、 アクセスは許可されない。以下の例では、アクセスを、特定の日付より前における特定のクライアント アプリケーションに制限する：

例 32: 組み合わせた制約 
{
  "access": [{
    "action": ["read"],
    "assignee": "https://id.example/agent",
    "target": {
      "type": "StorageResource",
      "value": ["https://storage.example/root/projects/"]
    },
    "constraint": [
      {
        "leftOperand": "dateTime",
        "operator": "lteq",
        "rightOperand": "2026-06-09T10:00:00Z"
      },
      {
        "leftOperand": "client",
        "operator": "eq",
        "rightOperand": "https://app.example/client-id"
      }
    ]
  }]
}

11.4 シリアライズ

本節で定義するデータモデルは、特定の シリアライズに依存しない。

11.4.1 JSON-LD シリアライズ

本仕様は、アクセス要求 および アクセス許可の JSON-LD シリアライズを定義する。このシリアライズを使用する文書は MUST @context プロパティを含めなければならず、その値は、 https://www.w3.org/ns/lws/v1 を含む順序付き集合でなければならない。追加のコンテキスト項目を MAY 拡張用語の定義のために 含めてもよい。

このシリアライズに関連付けられるメディア型は application/lws+json である。

例 33: JSON-LD @context 
{
  "@context": [
    "https://www.w3.org/ns/lws/v1"
  ]
}

11.5 プロトコル

アクセス要求および アクセス許可のエンドポイントは LWS コンテナであり、MUST 本仕様で定義される規則に準拠しなければならない。

これらのエンドポイントは、少なくとも GET および POST 操作のサポートを必要とする。DELETE 操作は RECOMMENDED である。その他の操作を MAY サポートしてもよい。

これらのエンドポイントは MUST 要求と応答の両方のペイロードについて、 11.4.1 JSON-LD シリアライズで定義される JSON-LD シリアライズをサポートしなければならない。サーバーは MAY 追加のシリアライズをサポートしてもよい。

エージェントが アクセス要求を作成するには、POST 要求を その アクセス要求エンドポイントに送信する。ストレージ コントローラーが アクセス許可を作成するには、 POST 要求を アクセス許可エンドポイントに送信する。

成功した POST 操作は MUST Location ヘッダーを付けて応答し、 その値を 新しいリソースの URL に設定しなければならない。

11.5.1 アクセス要求エンドポイント

  • POST / — アクセス要求を作成する。
  • GET / — アクセス要求の一覧を取得する。
  • GET /:id — 特定のアクセス要求を取得する。
  • DELETE /:id — アクセス要求を取り消す。

11.5.2 アクセス許可エンドポイント

  • POST / — アクセス許可を作成する。
  • GET / — アクセス許可の一覧を取得する。
  • GET /:id — 特定のアクセス許可を取得する。
  • DELETE /:id — アクセス許可を失効させる。

課題 103: LWS 通知機能 work-item

本節は、まだ定義されていない LWS の通知に関する節との整合が必要である。

通知は、エージェントおよび ストレージ コントローラーに対し、 アクセス要求および アクセス許可の変更を知らせる仕組みを提供する。 inbox プロパティが アクセス要求または アクセス許可に存在する場合、 サーバーは SHOULD そのエンドポイントに 通知を配信し、 被許諾者にイベントを知らせるべきである。

通知のシリアライズは MUST LWS 通知データモデルの要件に準拠しなければならない。

inbox エンドポイントに配信される通知は MUST 通知の配信について LWS プロトコルで定義される要件に準拠しなければならない。

注記

本節で記述する通知機構は、 リンクトデータ通知のパターンに相当する。このパターンでは、 通知の発見に inbox プロパティを使用し、POST 要求をその受信箱に送信することで配信する。

11.6.1 通知イベント

サーバーは SHOULD 以下のイベントに応じて通知を送信するべきである：

  • アクセス要求の作成: 新しい アクセス 要求が 提出された場合、ストレージコントローラーは SHOULD 通知を受けるべきである。
  • アクセス許可の作成: 新しい アクセス許可が 作成された場合、 要求元の エージェントには SHOULD inbox で通知するべきである。この宛先は、 関連する アクセス要求で指定される。

サーバーは MAY その他のイベントに応じて通知を送信してもよい。

12. LWS メディア型

12.1 LWS メディア型

LWS の ストレージ記述は MUST メディア型 application/lws+cid でシリアライズ可能でなければならない。 application/lws+cid メディア型が識別する文書は、 W3C 管理下の識別子文書 [CID-1.0] を LWS 語彙で拡張し、特殊化したものである。

LWS の コンテナ表現は MUST メディア型 application/lws+json をサポートしなければならない。

LWS のコンテナ表現は JSON-LD の規約を使用するが、LWS の制約および要件は、 専用のメディア型を使用する根拠となる。

12.1.1 LWS プロファイル

URI https://www.w3.org/ns/lws/v1 は LWS プロファイルを識別する [RFC6906]。コンテナの表現が LWS プロファイルに準拠するのは、 その RDF が、application/lws+json で表された同じ コンテナの状態およびページの RDF と同型である場合である。すなわち、符号化された RDF が、 RDF データセットの 比較 [RDF12-CONCEPTS] で定義される同型性に従い、 application/lws+json 表現を JSON-LD として解釈したときの RDF と同型である場合をいう [JSON-LD11]。application/lws+json 表現は常に LWS プロファイルに準拠する。

12.1.2 コンテンツネゴシエーション

サーバーは MUST application/lws+json を要求された場合、コンテナについてはそれに応じなければならず、MUST Content-Type 応答ヘッダーを、選択した表現のメディア型に設定しなければならない。

クライアントが LWS プロファイルの表現を要求するには、LWS プロファイルの URI を RDF メディア型の profile パラメーターに含める。 このパラメーターを定義する RDF メディア型には、application/ld+json [JSON-LD11]、text/turtle [RDF12-TURTLE]、application/trig [RDF12-TRIG]、application/n-triples [RDF12-N-TRIPLES]、および application/n-quads [RDF12-N-QUADS] がある。サーバーがそのようなメディア型を選択した場合、 応答は MUST LWS プロファイルに準拠しなければならない。すなわち、 MUST application/lws+json 表現と RDF 同型でなければならず、その Content-Type は MUST 同じ profile パラメーターを含めなければならない。サーバーは MUST NOT LWS プロファイルに準拠する表現を生成できないメディア型を選択してはならない。

選択される表現が要求の Accept ヘッダーに依存する場合、応答は SHOULD Vary: Accept ヘッダーを含めるべきである [RFC9110]。

12.1.3 ページ分割

一部の複合リソース、たとえば コンテナは、多数のリソースを保持する場合がある。 クライアントが一覧を段階的に取得できるように、サーバーは SHOULD ページ分割を、コンテナのメンバー数がサーバーの定める しきい値を超える場合にサポートするべきである。

12.1.3.1 ページ分割モデル

ページ分割はリンクに基づく。サーバーは、ページ分割 URI を HTTP Link ヘッダーで提供する [RFC8288]。 これにより、クライアントは数値のオフセットに依存せず、一覧全体をたどることができる。

一覧がページ分割されている場合、応答本文は現在のページの項目のみを含む。 複合リソースの id、type、および totalItems プロパティは、 メンバーシップ全体を反映する。一方、items は、 現在のページのリソースのみを含む。

12.1.3.2 ページ分割のリンク 関係

ページ分割 URI は、Link ヘッダーで、以下の標準リンク 関係を使用して伝達される：

  • rel="first": 結果の最初のページの URI。MUST ページ分割された応答に存在しなければならない。
  • rel="last": 結果の最後のページの URI。MAY ページ分割された応答に存在してもよい。
  • rel="next": 結果の次のページの URI。後続のページがある場合は、MUST 存在しなければならない。最後の ページでは MUST 省略しなければならない。
  • rel="prev": 結果の前のページの URI。先行するページがある場合は、MAY 存在してもよい。最初の ページでは MUST 省略しなければならない。

すべてのページ分割 URI は、クライアントにとって不透明である。クライアントは SHOULD NOT ページ分割の URI を構築または変更するべきではなく、SHOULD サーバーが提供する URI を使用するべきである。

12.1.3.3 ページの要求

クライアントは、複合リソースの URI を要求して最初のページを取得する。応答には、後続のページを取得するための ページ分割用の Link ヘッダーが含まれ、クライアントはそれをたどる。サーバーは MAY 以前の走査で取得したページ分割 URI を通じて、 特定のページへの直接アクセスもサポートしてよい。

ページ分割された応答を返す場合、サーバーは MUST 200 OK で応答しなければならない。応答本文の totalItems プロパティは SHOULD 現在のページだけではなく、 すべてのページにわたる項目の総数を反映するべきである。

13. JSON-LD コンテキスト

LWS の JSON-LD コンテキストは、URL https://www.w3.org/ns/lws/v1 で識別される。 その URL から解決される文書の SHA2-256 ダイジェストを、以下の表に示す：

コンテキストの URL およびハッシュ
URL: https://www.w3.org/ns/lws/v1
SHA2-256 ダイジェスト： TODO: コンテキスト文書が確定したら、 JSON-LD コンテキストのダイジェストを含める

ダイジェストは、次のようなコマンドで検証できる： curl -sL -H "Accept: application/ld+json" https://www.w3.org/ns/lws/v1 | openssl dgst -sha256

注記
本番システムでは、実行時にリモートの JSON-LD コンテキスト文書を取得しないことが推奨される。 コンテキストをローカルに同梱またはキャッシュすると、外部 インフラストラクチャへの実行時の依存をなくし、遅延を減らし、コンテキスト改ざん攻撃を防止できる。

16. セキュリティに関する考慮事項

この節は非規範的である。

脅威モデル、セキュリティ要件、および安全な LWS 配備のための実装指針を扱う、 正式なセキュリティに関する考慮事項の節。

OAuth 2.0 セキュリティに関する現行最良慣行 [RFC9700] に記述される推奨事項は、本 仕様に適用される。

16.1 トランスポートのセキュリティ

この節は非規範的である。

トランスポート層セキュリティ（TLS）は、改ざん、なりすまし、および情報漏えいを防ぐための 重要な仕組みである。TLS で保護された通信は、次に従って検証できる [RFC6125]。 実装のセキュリティに関する考慮事項は、「トランスポート層セキュリティ（TLS）および データグラムトランスポート層セキュリティ（DTLS）の安全な使用のための推奨事項」にある [RFC9325]。

16.2 トークンのセキュリティ

この節は非規範的である。

Bearer トークンおよびデジタル資格情報は、盗難とリプレイに対して脆弱である。緩和策には、適度に短い存続期間の使用、 特定のオーディエンスへのトークンの結び付け、およびトークンの安全な格納がある。

  • 短い存続期間：認可サーバーは、アクセストークンに300秒（5分）以下の存続期間を割り当てることで、 流出した資格情報による潜在的なリスクを抑えられる。
  • オーディエンスへのバインディング：アクセストークンを特定の宛先サーバーに結び付ける際には、 aud クレームなどを使用する。これにより、異なるサーバーへのトークンのリプレイを防げる。アクセストークンの オーディエンスに 複数のサーバーが含まれる場合、そのいずれのサーバーも、他のサーバーにトークンをリプレイできる。認可 サーバーはこれを避けるため、 単一のストレージ URI をオーディエンスとするトークンを発行する。オーディエンスが無制限の資格情報を 扱うアプリケーションは、 これらの資格情報を他の実体に送信する際に注意する必要がある。 特に、信頼できない 認可サーバーに注意が必要である。資格情報の発行者がトークンのオーディエンスを制限できない場合、クライアントは、 次のような仕組みを使用できる： OAuth 2.0 トークン交換 [RFC8693]。これにより、 オーディエンスが制約された資格情報を作成してから、 異なるセキュリティドメインの認可サーバーとやり取りできる。
  • 送信者制約付きトークン：Bearer トークンは、取得したどの当事者でも使用できる。オーディエンスを 制限しても、 流出したトークンが本来のストレージサーバーにリプレイされることは防げない。 オーディエンスは ストレージであるため、盗まれたトークンは、そのストレージ内でエージェントが アクセスを認可されているすべてのリソースに使用できる。 OAuth 2.0 所有の証明の提示 （DPoP） [RFC9449] などを使用して、アクセストークンをクライアントの鍵に結び付けることで、 盗まれたトークンの使用者を、その鍵の所持者に限定できる。保護対象リソースメタデータ文書は、 ストレージサーバーがサポートする DPoP 証明アルゴリズム、および DPoP に結び付けられたアクセストークンを 要求するかどうかを、dpop_signing_alg_values_supported および dpop_bound_access_tokens_required パラメーターで通知できる。これらは次に定義される [RFC9728]。
  • 安全な格納：資格情報を永続化するアプリケーションは、これらのオブジェクトが安全に格納されることを 保証する必要がある。暗号化されていないトークンをブラウザーの localStorage、URL、 またはログに格納すると、そのトークンは流出攻撃を受けやすくなる。

16.3 リソースの発見

この節は非規範的である。

クライアントは、ストレージサーバーが送信する応答から認可サーバーの場所を知る。 そのストレージサーバーをクライアントが 信頼していない場合もある。この発見プロセスには、以下の考慮事項が適用される。

  • 信頼されていないメタデータ：悪意あるストレージサーバーは、クライアントが 信頼していない認可サーバーに クライアントを誘導できる。クライアントが 認証資格情報をその 認可サーバーに提示すると、 資格情報が漏えいする。クライアントは、どの認可サーバーを 信頼するかについて独自のポリシーを 適用し、このリスクを減らせる。5.2.3 クライアントによる発見結果の検証の検査は、 保護対象リソースメタデータが 同じサーバー上の要求されたリソースを記述することを要求し、サーバーが 別のリソースサーバーに属する メタデータを提示することを防ぐ。また、漏えいの影響は、クライアントが 送信先の認可サーバーにオーディエンスを限定した 認証資格情報を 使用する場合にも軽減される。
  • ストレージへのバインディング：クライアントは、ストレージサーバーからの応答内にある Link ヘッダーから ストレージ URI を 取得する。悪意あるサーバーは、別のストレージの URI を指定して、クライアントに そのストレージ向けのアクセストークンを 取得させ、悪意あるサーバーに提示させられる。そのサーバーは、それをリプレイできる。このため、 クライアントには、 アクセストークンの要求前に、ストレージ記述を使用し、 要求された URI が同じオリジンから提供されることを、 ストレージルートと比較して確認することが要求される。 これは、 5.2.3 クライアントによる発見結果の検証に記述される。
  • サーバーサイドリクエストフォージェリ：チャレンジ内の resource_metadata URL、および ストレージ URI を含む Link ヘッダー、ならびに保護対象リソースメタデータ文書内の発行者識別子は、 ストレージサーバーが 選択し、クライアントはそれらが識別する文書を取得する。この取得を 他の当事者に代わって 行うクライアント、たとえばサーバー側アプリケーションは、サーバーサイドリクエストフォージェリにさらされる。 これは、 次の第7.7節に記述される [RFC9728]。予防策には、 取得を https スキームに制限すること、および 内部 IP アドレス範囲への要求を遮断することがある。

16.4 アクセス要求とアクセス許可

この節は非規範的である。

  • サーバーには、認可規則を、 アクセス要求および アクセス許可 エンドポイントの両方に適用することが強く推奨される。特に、 アクセス許可エンドポイントへの書き込みアクセスは、 認可された ストレージコントローラーおよび特定のクライアントに制限するべきである。
  • エージェントが アクセス要求を作成する際、サーバーには、 要求内の assignee 値が要求元エージェントの 認証済みアイデンティティと関連付けられていることの検証が推奨される。
  • アクセス要求エンドポイントは、外部の エージェントからの内容を受け入れるため、 サーバーには、不正利用を防止する対策の実装が推奨される。これには、レート制限、 ペイロードサイズの制限、または送信を受け入れる前に認証を要求することがある。 そのような保護がなければ、エンドポイントは、スパム、リソース枯渇、 またはその他の望ましくない内容に対して脆弱となる可能性がある。

16.5 通知

この節は非規範的である。

  • 情報漏えい: 通知は、リソースの存在または 変更パターンを明らかにする可能性がある。サブスクリプションおよび 個々の通知配信に対するアクセス制御は MUST その基盤となるリソースに対するアクセス制御と 整合しなければならない。
  • サブスクリプションの不正利用: サブスクリプション機構の不正利用を防ぐため、 レート制限およびエンドポイントの検証が推奨される。

16.6 コンテナ間でのリソースの 移動

この節は非規範的である。

  • 適用されるポリシーの変更: リソースへのアクセスは、多くの場合、 リソースの 包含 階層内の位置に基づくポリシーで制御される。したがって、リソースの up リンクを変更すると、 アクセスできる エージェントの集合が、ポリシーを編集することも、 リソースの内容を 変更することもなく、拡大または縮小する可能性がある。この結果を、 ストレージコントローラーおよび エージェントのうち、 移動を要求するものに可視化することは、 有用な緩和策である。ただし、実装がどのように行うかは、 本仕様の対象範囲外である。
  • 権限の組み合わせ: リソースの移動は、削除による効果を 移動元の コンテナで生じさせ、作成による効果を移動先の コンテナで生じさせる。サーバーは MUST 両方の認可を評価しなければならない。これは、9.6 コンテナ間でのリソースの 移動で要求されるとおりである。 リソースのメタデータを更新する認可だけを評価すると、 エージェントが、 リソースを、書き込めない コンテナに配置したり、 削除が許可されていない コンテナからリソースを削除したりできてしまう。
  • コンテナの移動: コンテナを移動すると、その子孫も移動される。そこには、 要求元の エージェントが把握していないリソースが含まれる可能性がある。 それらの子孫の親は変わらないが、適用されるポリシーは変わる可能性があるため、 移動をサポートするサーバーは、コンテナについて、MUST 移動対象サブツリーを再帰的に削除するために 必要な認可を評価しなければならない。これは、9.6 コンテナ間でのリソースの移動で要求される。また、MUST NOT サブツリーの一部で認可に失敗した移動を、部分的に適用してはならない。
  • サーバー管理メタデータの制限緩和: MoveResource 機能を記述すると、通常はサーバー自身が維持する up リンクを、 クライアントが書き込めるようになる。サーバーは SHOULD その配備において 必要となる場合にだけ この機能を記述するべきであり、SHOULD その appliesTo プロパティを、 サポートする必要がある リソースの型に限定するべきである。また、MUST クライアントによる 変更が許可されていないリンクを 引き続き保持しなければならない。

17. プライバシーに関する考慮事項

この節は非規範的である。

データ最小化、ユーザーの同意、およびプライバシーを保護する実装パターンを含む、 LWS プロトコルのプライバシーへの影響。

資格情報は、ユーザーおよび エージェントについての情報を保持する。デジタル署名は改ざんを防げるが、 クライアントや第三者は、暗号化されていない資格情報内の値を読み取ることができる。

このため、資格情報の発行者には、認証または認可に 必要な情報だけを含む トークンを作成し、必要がない限り機密性の高い属性を含めないことが推奨される。

一般に、暗号化されていない資格情報データをログに書き込むことはアンチパターンである。これが 必要な場合、 実装は、資格情報を切り詰めるかハッシュ化して、資格情報の主体のプライバシーを保護できる。

JWT で仮名の識別子を使用していても、ストレージサーバーは、 同じ エージェントからの要求を、 時間をまたいで関連付けられる場合がある。 この場合にユーザーのプライバシーを保護するため、クライアントアプリケーションは JWT の一括発行を要求し、 各 JWT を1回だけ使用できる。 これによっても、ストレージサーバーが、JWT の内容の類似性や 送信元の IP アドレスなどの情報を使用して 要求を関連付けることは防げない。仮名の識別子を使用する場合、認可サーバーは、 同じ識別子を複数回発行しないよう注意する必要がある。

17.1 アクセス要求とアクセス許可

この節は非規範的である。

  • アクセス要求または アクセス許可は、 関係するリソース、エージェント、および目的についての 機密性の高い情報を明らかにする可能性がある。サーバーには、 これらのリソースの可視性を、ストレージコントローラーや 文書内で識別される被許諾者などの認可された当事者に限定することが推奨される。たとえば、ストレージコントローラーは、 すべてのリソースを読み取り、削除する能力を持ち、他のエージェントは、 自身が被許諾者となるリソースにだけアクセスできるようにする場合がある。
  • アクセス許可にクライアントの制約が含まれる場合、 サーバーには、 他のクライアントによる要求への応答から、その許可を除外することが推奨される。 たとえば、エージェントが特定のクライアントを使用する場合にだけリソースへのアクセスを許可されていれば、 別のクライアントを使用したときには、その許可を表示しない。

17.2 通知

この節は非規範的である。

  • 活動の追跡: 通知は、その性質上、リソースが変更された時点を 明らかにする。サブスクライバーは SHOULD 自身にアクセスが認可されているリソースについてだけ 通知を受信するべきである。
  • 実行者の開示: actor プロパティを 通知に含めると、誰が変更したかが明らかになる。状況によっては不適切である。 actor プロパティは SHOULD 既定で省略するべきである。サーバーは MAY これを含めるかどうかを設定可能にしてもよい。
  • タイミング分析: 内容が開示されなくても、通知のタイミングから使用 パターンが明らかになる可能性がある。

17.3 コンテナ間でのリソースの 移動

この節は非規範的である。

  • 意図しない公開: リソースを移動する エージェントは、 移動先の コンテナに適用されるポリシーが、移動元よりも 許容範囲の広いものであることに気付かない場合がある。リソースの up リンクを 変更する前に、適用されるポリシーの違いを示すことは、有用な緩和策である。ただし、クライアントがどのように行うかは、 本仕様の対象範囲外である。
  • 保持される識別子: この考慮事項は、サーバーが 識別子を 包含階層から導出する場合にだけ適用される。そのようなサーバーが 移動されるリソースの識別子を保持すると、その識別子は引き続き、 コンテナのうち、リソースが最初に作成されたものを明らかにする。 本仕様で推奨するとおり、 識別子を不透明なものとして扱うサーバーでは、この開示は生じない。 その識別子は、階層内の位置を符号化していなかったためである。
    課題 207: リソースの識別 （URI の割り当て）に影響する機能の定義 storage-descriptionvocabulary

    この考慮事項の具体例は、作業部会が、 ストレージによる識別子の割り当て方針の記述方法を 決定した後で示すのが最適である。

  • リダイレクト: 以前の識別子に残された 301 Moved Permanently 応答は、 リソースの新しい識別子を、エージェントのうち、そのリソースへの アクセスが認可されていないものにも開示する可能性がある。識別子が 包含 階層から導出される場合、その階層内でのリソースの新しい位置も開示し、 したがって、コンテナのうち、移動先となるものも明らかにする。識別子が不透明である場合は、 新しい識別子だけが 開示される。サーバーは SHOULD 移動されるリソース自体と 同じアクセス制御を そのような応答にも適用するべきであり、MAY 代わりに 404 Not Found で応答してもよい。
