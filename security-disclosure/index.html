概要

この文書は、W3C標準および 仕様（技術報告書）における疑わしいセキュリティ脆弱性を報告する方法を定義し、 問題が適切なW3Cプロセスを通じて トリアージ、確認、解決されるようにします。
これは、ソフトウェア実装またはW3Cの運用インフラストラクチャにおける脆弱性を報告するためのものではありません（範囲外を参照）。

1. はじめに

1.1 概要

W3C の標準および仕様には、ユーザー、実装者、または Web プラットフォームにセキュリティリスクをもたらす設計上の 問題が含まれる場合があります。研究者やより広範なコミュニティからの報告は、W3C がそれらの問題を特定し、それらを評価して対処できる 人々へと引き継ぐのに役立ちます。

1.2 目的

このポリシーでは、W3C が、 W3C の標準および仕様における脆弱性の疑いに関する報告をどのように受領し、トリアージし、振り分け、 調整するかについて説明します。

2. 範囲と適用

W3Cは標準化団体であり、ウェブ技術と仕様を記述した技術報告書を発行する。その中にはW3C勧告、ノート、およびレジストリが含まれる。

このポリシーは、W3C 仕様に記述されている設計上の脆弱性またはセキュリティ上の問題に適用されます。

このポリシーは、以下を対象としません：

  • 実装、ツールまたは設定上の脆弱性で、W3C標準を実装している可能性がある製品、オープンソースプロジェクトまたはサービスに存在するもの。こうした問題は該当するベンダーまたはメンテナーに報告する。
  • w3.org ドメインを支える W3C のインフラストラクチャおよび サービスの脆弱性。これらは W3C Systems の責任であり、独自の 脆弱性開示ポリシーがあります。

3. プロセスとポリシー

W3Cの対応は、問題が見つかった技術報告書の種類、問題の深刻度、対応の複雑さによって異なる。W3Cは確認されたセキュリティ問題を不必要に遅らせることなく解決するよう努める。この方針は[ISO-IEC-29147]と[ISO-IEC-30111]を参考にしている。

W3C は、セキュリティ上の問題が 報告された文書の種類および成熟度に応じて、報告を処理し、 振り分けます。

3.1 W3C標準における 脆弱性の報告

W3C の 文書に脆弱性を発見したと思われる場合は、協調的な 開示のため、vulnerability-disclosure@w3.org までご連絡ください。

このメールアドレスは、W3C チームによる初期トリアージの連絡窓口となります。トリアージ後、W3C チームは、 報告内容および影響を受ける仕様に応じて適切なグループを関与させます。通常、これには チーム連絡担当者、議長、編集者が含まれ、意見が必要な場合には他の人々も含まれることがあります。

このアドレスに送られた報告は公開アーカイブには保存されません。W3C が報告先のメールアドレス用に PGP 公開鍵を公開している場合は、その鍵で報告を暗号化することをお勧めします。

手続きを円滑に進めるため、アドバイザリには[ISO-IEC-29147]と[NIST-SP-800-216]が推奨するような情報を記載すること。

  • 脆弱性が存在する具体的な文書（例：そのタイトル、 安定した URL、および 公開日）。
  • 脆弱性の種類についての簡潔な説明（例：安全でない 暗号 アルゴリズムの使用）。
  • 脆弱性を再現する手順。理想的には、無害で破壊的でない概念実証。
  • この脆弱性を悪用した場合の影響と、攻撃 シナリオにおいてどのように利用され得るか。
  • 提案する是正措置または緩和措置（ある場合）。
  • 連絡先（任意。受領確認や進捗の連絡に使える返信経路は必要だが、報告者は身元を明かす必要はない）。

以下の点にご注意ください：

  • 「バグ報奨金」はありません： W3C は、報告された 脆弱性に対して「バグ報奨金」を支払いません。
  • 機密保持：非公開の脆弱性情報はアクセスが制限された経路で取り扱い、報告の評価や調整に必要な範囲でのみ共有する。非公開での調整が続く間、報告者には合意した制限付きの経路の使用を求める。適切な公開手続きに移行できる時点は、調整担当者が関係者に知らせる。
  • 研究者の保護：W3Cは、この方針に従って誠実に報告したという理由だけで報告者に法的措置を取る意図はない。この方針は、第三者が管理するシステム、サービスまたは製品のテストや、適用される法令に反する行為を許可するものではない。

3.2 セキュリティ課題の受領 および確認応答（VD）

W3Cは、3営業日以内にセキュリティ問題の受領を確認し、報告者との連絡経路を確立することを目指す。W3Cチームはその報告の調整担当者を指名する。

3.3 セキュリティ 課題の検証（VH）

受領確認後、セキュリティ上の問題について、その有効性、技術的な 深刻度、 関連性、および潜在的な影響を判断するための評価が行われます。

W3Cは、15営業日以内に報告者へ初期評価を伝えることを目指す。その時点で評価が完了していない場合、W3Cは代わりに進捗と次回の確認日を知らせる。追加情報が必要なら、W3Cは報告者に詳細を求める。

W3C チームは、これらの対応 目標を追跡し、さらに多くの時間、 調整、または権限が必要な場合に報告をエスカレーションする責任を負います。

3.4 確認後の対応の流れと報告者への進捗連絡（VH/VD）

問題が確認された後、調整担当者は、適切な制限付き調整経路または追跡手段を使い、現在の段階、次回の確認時点、現在対応を担当するW3Cグループまたはその他の関係者を、W3Cの調整対象で影響が確認された各文書について記録する。リポジトリのセキュリティアドバイザリを使う場合は、記録と非公開の協議を兼ねることができ、別の記録は不要である。

固定の状態モデルは必要ない。記録には、対応計画や作業、複数の関係者間の調整、調整の上での開示、フォローアップ、または案件の終了を記載してよい。これらは必ず順に進む段階ではなく、複数が当てはまることもある。

利用可能な返信経路がある場合、調整担当者は、現在の段階、対応を現在調整している担当者、追加情報の要否、次回の確認日または案件に適した更新頻度を報告者に知らせる。W3Cが案件の調整を続ける間は、その時点ごとに合意した経路で進捗を知らせる。確認の時期は、深刻度、複雑さ、関係者の数に応じて案件ごとに決める。既存のリポジトリのセキュリティアドバイザリを通じて連絡する場合も含め、「変更なし」と短く知らせれば十分で、機密性の高い実装の詳細を明かす必要はない。

案件を終了する前に、調整担当者はW3Cの調整対象で影響が確認された各文書の結果を記録する。結果には、文書の更新、アドバイザリや緩和策、他の担当手続きや調整担当者への移管、理由を示した変更なしでの終了が含まれ得る。W3Cの調整対象で影響が確認された別の文書に結果が記録されていなければ、最初に報告された文書への対応が済んでも案件は終了しない。これらの要件は、すべての案件に共通する修正期限ではなく、確認と更新の時点を定めるものである。

3.5 対応および 解決策の開発（VH）

次に調整担当者は、影響を受ける文書を担当するグループと協力し、利用できる返信経路がある場合には報告者とも協力する。多くの場合、解決策の中心は関連文書の更新となる。

非公開での調整中、調整担当者は適切な制限付きの経路を使用する。開示後のフォローアップは、担当グループや他の関係者が通常使用する公開イシューやメーリングリストに移行してよい。

3.5.1 W3C勧告 - 公開済み

これらは、完了し、コミュニティによるレビューを受けた標準です。

  • その勧告を作成したワーキンググループがまだ活動している場合は、最も適切な処理方法を決めるため、そのワーキンググループに報告を回す。脆弱性には次のように対応できる。

    • 正誤表を出す（軽微な問題、または規範的内容を変更しない訂正の場合）。W3Cワーキンググループは、勧告について報告された誤りの公開記録を保持しなければならない。誤りの報告は少なくとも四半期ごとに取りまとめることが望ましい。
    • 勧告を改訂し、更新された勧告仕様書を発行する。
    • 問題に対応するための新しい文書を作成する。

  • ワーキンググループが活動を終了している場合は、グループなしでの保守の仕組みなど、W3Cプロセスで定められた方法を利用できる。どの対応を取れるかは問題の深刻度によって異なる。

    • 軽微な問題には正誤表で対応できる（グループが設置されていなければ、W3Cチームが保守してもよい）。
    • より大きな更新については、W3Cチームが別の対応を検討することがある。

W3Cプロセスに基づくクラス3または4の変更は、 より広範なレビューおよび特許ポリシー上の影響を引き起こす可能性があります。

3.5.2 勧告候補（CR）および作業草案（WD） - 開発中

これらはW3C作業部会に採用された文書ですが、 まだ最終化されていません。

  • W3Cワーキンググループは、技術報告書に関する実質的なレビューコメントに適時かつ正式に対応することが望ましい。

3.5.3 編集者草案 - 初期段階/個人による貢献

これらは W3C において正式に採択された文書ではありません。 W3C 仕様として公開されていない Editor's Draft には、公式な位置付けはありません。

  • この問題は、文書の編集者によって処理および議論されるべきです。

3.5.4 中止、廃止、または撤回された文書

  • 廃止、旧式、または撤回済みとされた W3C 技術報告については、セキュリティ上の問題の報告を受けても、対応が 行われる可能性は低いです。それでも、チームは 文書のステータス（SOTD）にそれらを記載することを検討するべきです。

3.5.5 コミュニティグループ報告書

これらはW3Cにおいて正式に採用された文書ではなく、 コミュニティおよびビジネスグループ プロセスがそれらを 規定しています。

  • 見つかった課題は、その文書の編集者と処理および議論されるべきです。

3.5.6 会員による提出

これらはW3Cにおいて正式に採用された文書ではありません。 会員提出は、検討のために会員によって提案されるものです。

  • 見つかった課題は、その文書の編集者と処理および議論されるべきです。

課題は会員のポリシーに従って処理されます。

3.6 公開と周知（VD）

調整担当者は報告者および影響を受ける関係者と協力して、開示計画を記録する。公開を予定する場合は、十分な情報がそろった段階で、問題の深刻度、利用可能な緩和策、影響を受ける文書の成熟度、複数の関係者間での調整を考慮して公開目標日を計画に含める。早期開示でリスクが大きく増す場合は、上記の確認時点で計画を見直してよい。公開にあたり、関連する文書や実装の更新がすべて完了している必要はない。

公開する情報には、脆弱性の説明、影響を受ける標準を特定できる情報、影響と深刻度、実装者や利用者による緩和や修正に役立つ情報を含めてよい。W3Cがアドバイザリを公開する場合、報告者が公開での謝辞を希望すれば、通常それに応じる。

公開されたリポジトリのセキュリティアドバイザリは、W3Cグループのリポジトリ向け公開セキュリティアドバイザリ索引に掲載される。
