1. はじめに

この節は規範的ではありません。

本仕様は、スクリプトが制限付き API を呼び出す能力を、信頼する別の閲覧コンテキストへ委譲できる仕組みを定義します。ここでは、委譲する能力を対象の閲覧コンテキストに時間制限付きで公開する、動的な委譲の仕組みに焦点を当てます。

1.1. 能力の委譲とは何か？

Web の多くの能力は、JS から制限付きで利用できます。例えば：

  • ほとんどのブラウザーは、ユーザーが最近ページを操作した場合、またはそのページのオリジンからのポップアップを許可した場合に限り、Window.open() によるポップアップを許可します。

  • サンドボックス化された iframe は、特定のサンドボックス属性またはフレーム内でのユーザー操作がなければ、requestFullscreen() によって自身を全画面にできません。

能力の委譲とは、フレームが制限付き API を呼び出す能力を動的に手放し、信頼できる別の（子）フレームへ移せるようにすることです。ここで「動的」とは、委譲の効果が、その能力で定められた限られた時間だけ続くことを意味します。これは、閲覧コンテキストに対し iframe の allow 属性を通じて能力を静的に（読み込み時に）公開することとは異なります。後者では子フレームへの公開に時間制限がありません。

1.2. 委譲の開始と能力の使用

能力の委譲が有効になるには、二つの異なる段階が必要です。最初は「開始」で、一つの閲覧コンテキストが別の閲覧コンテキストへ、特定の能力を委譲することを通知します。その後、後者（受信側）の閲覧コンテキストが委譲された能力を「使用」します。通常、これはその能力で定義されたメソッドの呼び出しです。本仕様は第二段階で使用する API インターフェイスを定義しませんが、その API の内部動作を再定義します。

このため、本仕様は二つの部分からなります。開始段階の API を定義し、次にそれを「利用する」特定の API の委譲時の動作を定義します。後者では支払いリクエスト APIに必要な動作の変更を扱い、将来能力の委譲を利用する他の API に同様の変更を加える際の指針とします。

1.3. 一時的な利用可能性

上述の両段階には、いずれも時間制限があります。

  1. 開始段階は活性化を消費するため、直近にユーザー活性化があった場合にのみ許可されます。また、この消費により、ユーザー活性化ごとに委譲の仕組みを一度しか利用できなくなります。これにより、複数のフレームへの委譲を繰り返して対象 API のユーザー活性化制限を実質的に回避する、といった悪用を防ぎます。

  2. 開始段階が正常に完了すると、委譲された API は対象の閲覧コンテキストで数秒間だけ利用できます。正確な制限時間は、その API の仕様が委譲時の動作をどう定義するかによります。独自の制限時間を定義しない API では、既定値はユーザー活性化の有効期限と同じです。

2. 例

サイトがマウスクリック後に子フレームへ次の API を呼び出す能力を委譲する場合：[payment-request] show()、その子フレームにメッセージを送信し、委譲する能力を指定する追加のオプションを付けます。 
window.onclick = () => {
  targetWindow.postMessage('a_message', {delegate: "payment"});
};

メッセージを受信すると、子フレームはユーザー活性化を受けていなくても show() を使用できます。

window.onmessage = () => {
  const payRequest = new PaymentRequest(...);
  const payResponse = await payRequest.show();
  ...
}

3. 能力の委譲の開始

ある閲覧コンテキストが別の閲覧コンテキストへ能力を委譲する場合、後者の閲覧コンテキストへメッセージを送信し、追加の WindowPostMessageOptions として、能力を指定する delegate を付けます。このオプションの値は機能識別子でなければなりません。値がユーザーエージェントの対応する機能のいずれにも一致しなければ、このオプションを無視しなければなりません。

利用可能な機能識別子の値の一覧はこちらにあります.

3.1. HTML 仕様への暫定的な修正

WindowPostMessageOptions の IDL 定義に、次のフィールドを追加します。

DOMString? delegate;

ウィンドウのメッセージ送信アルゴリズムの次の手順：

  1. transfer を options["transfer"] とします。

の後に、次の二つの手順を追加します。

  1. delegate を options["delegate"] とします。

  2. delegate が null でなければ：

    1. ユーザーエージェントが delegate の示す機能の委譲に対応していなければ、"NotSupportedError" DOMException を投げます。

    2. targetWindow の関連付けられた Documentが使用を許可されていない機能を delegate が示す場合、"NotAllowedError" DOMException を投げます。

    3. targetOrigin が単一の U+002A ASTERISK 文字（*）であれば、"NotAllowedError" DOMException を投げます。

      オプション targetOrigin の既定値は "/" であり、メッセージの宛先を同一オリジンに制限します。さらに "*" 以外の文字列を使う必要があるため、クロスオリジンのメッセージでは、意図する宛先の具体的なオリジンを指定しなければなりません。

    4. source を incumbentSettings のグローバルオブジェクトとします。

    5. source に一時的な活性化がなければ、"NotAllowedError" DOMException を投げます。

    6. ユーザー活性化を消費します。対象は source です。

4. 委譲された能力の追跡

閲覧コンテキストに委譲された能力は、Window.DELEGATED_CAPABILITY_TIMESTAMPS というマップで追跡します。能力が Window に委譲されるたびに、DELEGATED_CAPABILITY_TIMESTAMPS にエントリーを追加します。キーはその能力を表す機能識別子、値は現在の DOMHighResTimeStamp です。同じキーのエントリーが既にあれば、その値を現在の DOMHighResTimeStamp に更新します。

4.1. HTML 仕様への暫定的な修正

ウィンドウのメッセージ送信アルゴリズムの直前に、次の段落を挿入します。

閲覧コンテキストに委譲された能力を追跡するため、各 Window はマップを持ちます。名前は DELEGATED_CAPABILITY_TIMESTAMPS で、機能識別子から DOMHighResTimeStamp へのマップです。空のマップで初期化します。

ウィンドウのメッセージ送信アルゴリズムの現行の手順 8 に、二つの副手順を追加します。一つ目は次の副手順の後に挿入します。

  1. グローバルタスクをキューに入れます…

    1. origin を incumbentSettings のオリジンを直列化したものとします。

次のようにします。

  1. グローバルタスクをキューに入れます… （変更なし）

    1. delegate を options["delegate"] とします。

二つ目の追加副手順は、次の副手順の後に挿入します。

  1. グローバルタスクをキューに入れます…

    1. newPorts を、…からなる新しい凍結配列とします。

次のようにします。

  1. グローバルタスクをキューに入れます… （変更なし）

    1. newPorts を、…からなる新しい凍結配列とします。（番号以外は変更なし）

    2. delegate が null ではなく、かつユーザーエージェントが delegate の委譲に対応していれば、DELEGATED_CAPABILITY_TIMESTAMPS[delegate] を現在の高分解能時刻に設定します。

5. 委譲された能力の動作の定義

委譲時の動作を定義する能力は、その能力に適した方法で Window.DELEGATED_CAPABILITY_TIMESTAMPS の対応するエントリーを使用します。以下に、特定の能力に必要な仕様変更を示します。

5.1. 支払いリクエスト仕様への暫定的な修正

show() のアルゴリズムで、委譲時の動作を実現するために次の手順を置き換えます。

次の二つの手順：

  1. request の関連グローバルオブジェクトに一時的な活性化がなければ：

    1. "SecurityError" DOMException で拒否された promise を返します。

  2. 関連グローバルオブジェクトのユーザー活性化を消費します。

を、次の三つの手順に置き換えます。

  1. request の関連グローバルオブジェクトに一時的な活性化がなく、かつそのオブジェクトのタイムスタンプ DELEGATED_CAPABILITY_TIMESTAMPS["payment"] が undefined または期限切れであれば：

    1. "SecurityError" DOMException で拒否された promise を返します。

  2. request の関連グローバルオブジェクトに一時的な活性化がなければ、マップのエントリー DELEGATED_CAPABILITY_TIMESTAMPS["payment"] を消去します。

  3. そうでなければ、ユーザー活性化を消費します。対象は関連グローバルオブジェクトです。

5.2. 全画面仕様への暫定的な修正

requestFullscreen() のアルゴリズムで、委譲時の動作を実現するために次の変更を行います。

手順 5 の最後の条件：

  1. 次の条件のいずれかが false であれば、error を true に設定します：…

    • this の関連グローバルオブジェクトに一時的な活性化がある、またはユーザーによる向きの変更でアルゴリズムが起動されている。

を、次のように置き換えます。

  1. 次の条件のいずれかが false であれば、error を true に設定します：… （変更なし）

    • this の関連グローバルオブジェクトに一時的な活性化がある、またはそのオブジェクトのタイムスタンプ DELEGATED_CAPABILITY_TIMESTAMPS["fullscreen"] が undefined でも期限切れでもない、またはユーザーによる向きの変更でアルゴリズムが起動されている。

手順 10 の直前：

  1. fullscreenElements を、初期状態で this のみを含む順序付き集合とします。

に、次の新しい手順を挿入します。

  1. this の関連グローバルオブジェクトに一時的な活性化がなければ、そのオブジェクトのマップのエントリー DELEGATED_CAPABILITY_TIMESTAMPS["fullscreen"] を消去します。

  2. fullscreenElements を、初期状態で this のみを含む順序付き集合とします。（番号以外は変更なし）

5.3. 暫定的な修正：[SCREEN-CAPTURE] 仕様

getDisplayMedia() のアルゴリズムで、委譲時の動作を実現するために次の変更を行います。

手順 3 の条件：

  1. this の関連グローバルオブジェクトに一時的な活性化がなければ、name 属性の値が InvalidStateError の DOMException オブジェクトで拒否された promise を返します。

を、次のように置き換えます。

  1. this の関連グローバルオブジェクトに一時的な活性化がなく、かつタイムスタンプ DELEGATED_CAPABILITY_TIMESTAMPS["display-capture"] が this の関連グローバルオブジェクトで undefined または期限切れであれば、拒否された promise を返します。拒否理由は DOMException オブジェクトで、その name 属性の値は InvalidStateError です。
