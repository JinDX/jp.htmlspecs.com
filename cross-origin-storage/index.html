概要

オリジン間ストレージ（COS）は、Web アプリケーションが AI モデル、WebAssembly モジュール、非常に普及している JavaScript ライブラリなどの 大容量ファイルを異なるオリジン間で保存および取得できる、コンテンツアドレス可能なキャッシュです。ファイルは URL ではなく暗号学的ハッシュによって識別されるため、あるオリジンによって一度取得された バイト単位で同一のリソースは、ユーザーエージェントが許可する他の任意のオリジンによって、再度ダウンロードすることなく再利用できます。キャッシュ内の存在を、ユーザーがどのサイトを訪問したかの推測に利用できないようにするため、 ファイルのオリジン間開示は、k-匿名性方式の人気度基準を満たすハッシュに限定されます。

1. はじめに

この節は非規範的である。

ストレージは通常、ユーザーのセキュリティとプライバシーを保護するためにオリジンごとに分割される。これは適切な 既定の動作だが、非常に大きく、広く普及し、公開配布されている一部の リソース（AI モデル、WebAssembly モジュール、JavaScript ライブラリー、ゲームエンジン、大容量の Web フォント）には適さない。 これらは、どのサイトが要求しても、バイト単位で同一のファイルである。互いに無関係な 2 つのオリジンが同じ 8 GB のモデルに依存する場合、オリジンごとに分割されたストレージでは、 ユーザーはそのモデルを 2 回ダウンロードして保持しなければならず、ユーザーの帯域幅、ストレージ、 バッテリー、そしてネットワーク全体にとって無駄となる。

クロスオリジンストレージ（COS）は、内容アドレス方式のキャッシュであり、URL ではなく暗号学的ハッシュを キーとして使用する。これにより、ユーザーエージェントは、その利用を選択したオリジン間で、 このようなリソースの保存済みコピーを 1 つ共有できる。COS へのリソースの保存は、常に保存元の オリジンによる明示的なオプトイン操作であり、ユーザーエージェントは、本来そのリソースの読み取りを 許可されるオリジンに対しても、その存在の確認を差し控えてよい。§ 8 プライバシー とセキュリティに関する考慮事項を参照。

この仕様へのエントリーポイントは、requestFileHandle() メソッドであり、crossOriginStorage を通じて公開される： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // ファイルを使って何らかの処理を行う。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // クロスオリジンストレージに（開示可能な形では）存在しないため、代わりにネットワークから取得する。
  }
}

この仕様は、FileSystemFileHandle、 FileSystemWritableFileStream、 および関連する 基盤を、ファイルシステム標準 [FS] から再利用する。その適用範囲は、オリジン間で共有され、 各オリジンの非公開またはユーザーに見えるファイルシステムとは別の、専用のファイルシステムに限定される。

この仕様は、命令型の JavaScript API と、ホスト統合の基盤となる共有の 保存ステップを定義する。関連する提案は、同じ基盤キャッシュを他のホスト 仕様に統合する。これには、HTML の crossoriginstorage 属性を link および script に設けること、 さらに、 crossOriginStorage JavaScript インポート属性、CSS の cross-origin-storage() <request-url-modifier>、および crossOriginStorage RequestInit オプションを fetch() に設けることが含まれる。それぞれは、 対応するホスト仕様で定義される。§ 9 他の仕様との 統合を参照。

2. 概念

2.1. ハッシュ

COS ハッシュは、構造体であり、 次の 項目を持つ：

algorithm

文字列であり、 ハッシュアルゴリズムの名前を指定する。そのアルゴリズムは [WEBCRYPTO] で認識されるものとし、例えば "SHA-256" である。

value

文字列であり、小文字の 16 進数で符号化されたダイジェストを表す。このダイジェストは、 algorithm によって生成される。 "SHA-256" の場合、その長さは 64 文字である。

algorithm 辞書メンバーの型は、単純な DOMString である。その値域は、[WEBCRYPTO] の ハッシュアルゴリズムが受け入れる名前の集合と厳密に一致するにもかかわらず、この型を用いる。HashAlgorithmIdentifier は (object or DOMString) であり、その object 分岐は、 正規化によって [WEBCRYPTO] により Algorithm 形式の 辞書に変換され、呼び出し元が追加の パラメーターを必要とするアルゴリズムに渡せるようにする（例えば、{name: "HMAC", hash: "SHA-256"}）。ハッシュ アルゴリズムはそのようなパラメーターを取らず、 algorithm の保存、 比較、および往復変換は、内容アドレス方式の キーの一部として行われる。また、この仕様の 例では、常に単純な文字列を使用している。ここで任意のオブジェクトを許容しても機能は増えず、 等価性と直列化を 不必要に複雑にするだけである。したがって、DOMString は、このフィールドにとって より限定的で、より適切な型である。

2 つの COS ハッシュ値が 等しいのは、それらの algorithm 値が ASCII 大文字・小文字を区別しない比較で一致し、それらの value 値が厳密に 等しい場合である。

注： value は、すでに規範的に小文字であると定められている（上記を参照）ため、その比較は 単純な 文字列比較となる。algorithm には、大文字・小文字に関する規範的な指定がない。そのため、 ASCII 大文字・小文字を区別せずに比較する。

内容アドレス方式の ストアでは、エントリーのキーの 等価性を COS ハッシュに基づいて判定する。バイト列が 同一で、同じハッシュアルゴリズムを使用する 2 つのファイルは、それらを保存したオリジンの数や、 取得元の URL の数にかかわらず、同じエントリーとなる。

2.2. COS エントリー

各ユーザーエージェントは、単一の COS レジストリーを持つ。これは、マップであり、COS ハッシュ値を COS エントリー 構造体に対応付け、 クロスオリジンストレージを使用するすべてのオリジン間で共有される。 COS エントリーは、次の 項目を持つ：

hash

COS ハッシュ。

bytes

バイト列であり、hash の algorithm によるそのダイジェストが、hash の value に等しい。

注： エントリーが COS レジストリーに追加されるのは、 書き込み元がこれらのバイトを提供し、 ユーザーエージェントがそれらを検証した後に限られる。検証して保存するを参照。要求されたものの 完了していない書き込みは、レジストリー内にまったく表現されない。このため、読み取り側では、進行中の 書き込みと存在しない書き込みとを区別できない。§ 8.3 進行中の書き込みを参照。

origins

リストであり、オリジンのうち、明示的なクロスオリジン読み取りアクセスを付与されたものを含む。 この付与は、 公開ハッシュ リストとは独立している。初期状態では空であり、以後は増加するのみである。これは、 エントリーを読み取れる主体を決める、互いに独立した加算的な 3 つの権限付与のうちの 1 つである。 残りの 2 つは、そのエントリーの 保存元オリジン（常に読み取り可能であり、それらの オリジンと 同一サイトのオリジンも同様）と、グローバルに 開示可能である。

注： 書き込みにおいて、origins が明示的な空の リスト （origins: []）である場合に付与される権限は、 origins を省略した書き込みの場合と厳密に同じである。すなわち、エントリーの 保存元オリジンと、それらと 同一サイトのオリジンに付与され、これはすべてのエントリーに 備わる基本の権限である（COS の開示を決定するを参照）。上限を 適用すると、 空の リストは null になるため、どちらの書き込みも、 作成要求を完了するの残りの処理に同じ状態で到達する。 明示的な リストは、受け取り手を追加するだけであり、 書き込み元自身のサイトに対してエントリーへのアクセスを差し控えることは決してない。

グローバルに開示可能

真偽値であり、初期値は false である。これは、エントリーが、 グローバルな利用可能性 （"*"）を要求して書き込まれたかどうかを記録する。true の場合、そのエントリーは、要求が § 8.4 利用可能性のゲーティングを通過する任意のオリジンから読み取れる。すなわち、hash が PHL に掲載されており、かつ GREASE の適用によって抑制されない場合である。一度設定されると、true のままとなる。

注： これは、独立した 項目であり、origins とは分けられている。これにより、 後から グローバルな利用可能性を要求したとき、"*" の権限付与が既存の明示的な origins リストに加えて行われる。 この 2 つを 1 つのフィールドにまとめると、バイトを提供した 書き込み元が、リストを範囲とするエントリーを "*" を範囲とするエントリーに変えられてしまう。§ 8.4 利用可能性のゲーティングは、 "*" の権限付与にのみ適用されるため、それまで リストに基づいてエントリーを読み取れたオリジンが、 以後は "NotFoundError" を受け取るようになる。その条件は、hash が 次に該当しないことである： PHL に掲載されている。権限付与を 独立させておくことで、可視性の変更はすべて厳密に加算的なものとなる。 これは、引き上げは可能だが、引き下げは決してできないという 要件を満たすために必要である。

保存元オリジン

集合であり、オリジンのうち、それぞれが、このエントリーのバイトの 書き込みを 少なくとも 1 回正常に完了したものを含む。ページの読み込みをまたいで永続化され、 増加するのは時間の経過とともにであり、§ 5.2 追い出しで説明する場合を除き、減少することはない。 保存元オリジンに含まれるオリジンは、常に、そのエントリーの ハンドルを requestFileHandle() を通じて取得してよい。 これは、origins や、 エントリーの hash が 公開ハッシュリスト （PHL）に掲載されているかどうかに依存しない。 § 3.5.1 元の保存者によるアクセスを参照。

ユーザーエージェントには、関連付けられた クロスオリジンストレージキューがある。これは、 新しい並列キューを開始することによって得られる。COS レジストリーに対するすべての操作は、 キューに入れる際に、このキューに追加されるものとする。これにより、 キューに 入れられた順序で実行され、互いに入り交じることがなくなる。

2.3. 公開ハッシュリスト

クロスオリジンストレージにハッシュが存在することを確認する行為自体が、ユーザーの 閲覧履歴に関する情報を漏らす可能性がある（§ 8.2 クロスサイトの探査を参照）。これは、 特にグローバルな 権限付与に伴うリスクである。エントリーの明示的な origins リストと、すべてのエントリーに備わる同一サイトへの 基本の権限付与では、 開示範囲がすでに保存元オリジンの明示的な選択によって制限されている。一方、 エントリーを グローバルに開示可能にすると、Web 上の任意の オリジンに公開される可能性がある。この 特有のリスクを抑えるため、グローバルに開示可能なリソースを、その 権限付与によって、 そのリソースの 保存元オリジン以外のオリジンに開示できるのは、ハッシュが追加の 独立した条件を満たす場合に限られる。その条件は、公開ハッシュリスト （PHL）への掲載である。これは、ベンダー中立かつ 実装定義の許可リストであり、COS ハッシュ 値を含む。ハッシュが公開ハッシュリストに掲載されるのは、k-匿名性に似た 普及度の基準（例えば、一定数以上の独立したオリジンに、バイト単位で同一のものが 存在すること）を満たした後に限られる。これにより、共有キャッシュ内にそのハッシュが存在することを確認しても、 個々のユーザーについての情報が得られないようにする。

COS ハッシュ hash が 公開ハッシュ リストに掲載されているとは、hash と 等しいエントリーが、ユーザー エージェントの現在の 公開ハッシュリストのスナップショットに含まれることをいう。

公開ハッシュリストの取得プロトコル、 更新頻度、データ形式、普及度のしきい値、およびガバナンスは、 この仕様に付随する成果物として詳細に設計されている。これは、公開接尾辞リストが [URL] 標準に付随するデータファイルであるという考え方に倣ったものである。このリポジトリーの 公開ハッシュリストの解説を参照。その設計では、 公開接尾辞リストのベンダー横断的なローリングリリースの先例をモデルとして、WHATWG によるガバナンスと、 独立して裏付けられた広範な普及を基準とする掲載条件を提案している。 これは、上記の k-匿名性に似た基準の具体例であり、ハッシュの掲載手続きの一環として、 オフラインで一度だけ適用されるため、ユーザーエージェントがクエリーごとに繰り返すことはない。これらは、 まだこの提案の外では確立されていない。リスト自体の初期の非規範的なコードプロトタイプは、 現在、このリポジトリー内の public-hash-list/implementation/ に置かれている。専用の ベンダー横断的なリポジトリーを設けることが、PHL の解説に記されたガバナンス上の目標である。この 仕様が依存するのは、ハッシュが PHL に掲載されているかどうかだけである。したがって、 リストの取得機構、ガバナンスモデル、または設計のその他の部分がどのように進化しても、この仕様の正しさは保たれる。

3. CrossOriginStorageManager インターフェース

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

各 Navigator および WorkerNavigator オブジェクトには、関連付けられた CrossOriginStorageManager オブジェクトがある。crossOriginStorage の取得子の 手順は、 次を返すことである：this に関連付けられた CrossOriginStorageManager。

各 CrossOriginStorageManager オブジェクトには、関連付けられた オリジンがある。これは、 this の 関連する設定群オブジェクトの オリジンに、オブジェクトの 作成時に設定される。

注： オリジンを 関連する設定群オブジェクトから取得し、スクリプト自体の情報には依存しない ことには、ワーカーについて明確にしておくべき帰結がある。 blob: URL から作成されたワーカーは、それを作成したコンテキストの オリジンを持つため、そのオリジンのクロスオリジンストレージの ビューを完全に共有する。つまり、そのワーカーが書き込んだものは作成元のページが読み取れ、 ページが保存したものはワーカーが読み取れる。blob: URL 自体が独自のオリジンを持つわけではなく、 それを取り消しても、ワーカーがそのビューから切り離されることはない。data: URL から作成されたワーカーは、 不透明なオリジンを持つ。この仕様は、現時点では、 requestFileHandle() が、呼び出し元のオリジンが不透明である場合にどう動作するかを定義していない。 不透明なオリジンに関する規則が COS 要求を検証するで扱うのは、 呼び出し元が 指定するオリジンだけである。不透明なオリジンには、 保存元 オリジンのキーや 同一 サイトの比較の基準にできる安定した識別性がないため、 それに対して意味のある権限を付与することはできない。

3.1. requestFileHandle() メソッド

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

hash で識別されるファイルがクロスオリジンストレージ内に存在し、かつ呼び出し元のオリジンに 開示可能である場合、そのファイルのハンドルを返す。それ以外の場合は、 "NotFoundError" DOMException で拒否される。 "NotFoundError" は、ファイルがクロスオリジンストレージに 物理的に存在しないことを証明するものではない。§ 8.4 利用可能性のゲーティングを参照。呼び出し元は、 これを「代わりにネットワークから取得する」と解釈できる。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

hash で識別されるファイルを クロスオリジン ストレージに書き込むためのハンドルを返す。エントリーがまだ存在しない場合は、新しく作成し、既定では同一サイトのオリジンに制限する。 呼び出し元は、ハンドルの createWritable() メソッドを通じて、エントリーがすでに存在していたかどうかにかかわらず、 ファイルの内容全体を書き込む必要がある。その時点でユーザーエージェントは、書き込まれたバイトのハッシュが hash と一致することを検証し、 一致しなければ "DataError" DOMException で拒否する。この要件により、 オリジンが作成要求を使って hash の既存の有無を判別することを防ぐ。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

上記と同様だが、さらに、書き込みが完了すると、 hash に対する要求が § 8.4 利用可能性のゲーティングを通過する任意のオリジンに、エントリーを開示可能にする。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

上記と同様だが、開示先を、列挙されたオリジンに厳密に制限する（呼び出し元の オリジン、およびすでに 保存元オリジンに含まれるすべてのオリジンに加えて）。

requestFileHandle(hash, options) メソッドの 手順は、次のとおりである：

  1. result を、新しい プロミスとする。

  2. realm を、this の 関連する Realmとする。

  3. global を、this の 関連するグローバルオブジェクトとする。

  4. origin を、this に関連付けられた オリジンとする。

  5. クロスオリジンストレージの権限を確認するを global を指定して実行した結果が false である場合：

    1. グローバルタスクをキューに入れる。その際、DOM 操作タスクソースと global を指定し、タスク内で行う 拒否の対象を result、理由を "NotAllowedError" DOMException とする。

    2. result を返す。

  6. validationFailure を、COS 要求を 検証するを hash および options を指定して実行した結果とする。

  7. validationFailure が null でない場合：

    1. グローバルタスクをキューに入れる。その際、DOM 操作タスクソースと global を指定し、タスク内で行う 拒否の対象を result、理由を validationFailure とする。

    2. result を返す。

  8. 以下の手順をキューに入れる。追加先は、 クロスオリジンストレージキューとする：

    1. options["create"] が true である場合：

      1. 作成要求を完了するを、 result、hash、options、global、および realm を指定して実行する。

    2. それ以外の場合：

      1. 読み取り要求を完了するを、 result、hash、origin、global、および realm を指定して実行する。

  9. result を返す。

COS 要求を 検証するには、CrossOriginStorageRequestFileHandleHash hash および CrossOriginStorageRequestFileHandleOptions options を受け取り、null または TypeError を返す：

  1. hash["algorithm"] がハッシュアルゴリズムの 名前として [WEBCRYPTO] で認識されない場合、新しい TypeError を返す。

  2. hash["value"] が正規 表現 /^[0-9a-f]{64}$/ に一致せず、かつ hash["algorithm"] が ASCII 大文字・小文字を区別しない 比較で "SHA-256" と一致する場合、新しい TypeError を返す。

    注： 将来のハッシュアルゴリズムでは、 期待されるダイジェスト長が異なるものとして定義される可能性がある。この 仕様が規範的に制約するのは "SHA-256" だけであり、これは、 すべての 例での使用と一致している。

  3. options["origins"] が 存在し、かつ "*" でない場合：

    1. candidates を、options["origins"] とする。 単一の 文字列は、項目が 1 つの リストとして扱う。

    2. candidates の サイズが、 ユーザーエージェントの オリジンリストの最大長を超える場合、 新しい TypeError を返す。

    3. 各 candidate について、 candidates 内を反復する：

      1. 基本 URL パーサーを candidate に対して実行した結果が失敗であるか、または 解析された URL の オリジンが 不透明なオリジンである場合、新しい TypeError を返す。

  4. null を返す。

3.2. ファイルの読み取り

読み取り要求を 完了するには、プロミス result、COS ハッシュ hash、 オリジン origin、グローバルオブジェクト global、および Realm realm を指定して、次の手順を実行する：

  1. entry を、COS エントリーのうち、COS レジストリー内にあり、その hash が 等しい hash 値を持つものがあればそれとし、なければ null とする。

    注： 別の書き込み元が 要求したものの、まだ完了していない書き込みは、 COS レジストリーに含まれない。そのため、 そのようなハッシュでは entry は null となり、このアルゴリズムは、 どのオリジンも一度も書き込んだことのないハッシュとまったく同様に進む。この仕様で許可されるすべての開示は、 以下の 利用可能性のゲーティングを適用するによって決定される。それよりも 前に応答を返せる 分岐は存在しない。§ 8.3 進行中の書き込みを参照。

  2. disclosableEntry を、利用可能性の ゲーティングを適用するを、entry および origin を指定して実行した結果とする。

  3. disclosableEntry が null である場合：

    1. グローバルタスクをキューに入れる。その際、DOM 操作タスクソースと global を指定し、タスク内で行う 拒否の対象を result、理由を "NotFoundError" DOMException とする。

    2. 戻る。

  4. handle を、新しい FileSystemFileHandle を作成する [FS] ことによって得られる結果とする。その ロケーターは、disclosableEntry の hash を クロスオリジンストレージファイルシステム内で指し、作成先の Realm は、 realm とする。

  5. handle の COS ハッシュを、disclosableEntry の hash に設定する。

  6. handle の COS オリジンを、origin に設定する。

  7. handle の 読み取り可能を true に設定する。

    注： このハンドルは、すでに 利用可能性のゲーティングを適用するを通過しているため、呼び出し元のオリジンには、 そのエントリーのバイトを 取得する権限がある。

  8. グローバルタスクをキューに入れる。その際、DOM 操作タスクソースと global を指定し、タスク内で行う 解決の対象を result、解決値を handle とする。

COS の 開示を決定するには、COS エントリー または null である entry と、 オリジン origin を受け取り、COS エントリーまたは null を返す：

  1. entry が null である場合、null を返す。

    注： COS レジストリー内のエントリーは、 必ず書き込みと検証が完了しているため、このアルゴリズムが考慮すべき 書き込み途中の状態は存在しない。唯一の書き込みがまだ進行中であるハッシュは、 レジストリーに存在せず、どのオリジンも一度も書き込んだことのないハッシュと同様に、null として このアルゴリズムに渡される。§ 8.3 進行中の書き込みを参照。

  2. origin が entry の 保存元 オリジンに含まれる場合、entry を返す。

    注： 元の保存者、および 自らそのエントリーの書き込みを正常に完了したすべてのオリジンは、 常にそれを読み返せる。§ 3.5.1 元の保存者による アクセスを参照。

  3. origin が 同一サイトである相手として、entry の 保存元オリジン内に該当する項目がある場合、 entry を返す。

    注： すべてのエントリーに備わる同一サイトへの 基本の権限付与（ origins オプションのない書き込みが要求する権限付与）は、常に維持される。 これは、origins リストや グローバルに開示可能という権限付与が 後から追加されても変わらない。この確認は、以下の 公開ハッシュリストによる判定よりも 前に行われるため、同一サイトの オリジンは、エントリーの hash が PHL に掲載されているかどうかにかかわらず、そのエントリーを読み取れる。ここでは、同一サイトを 1 つの信頼単位として扱うため、この開示がサイト境界を越えることはなく、 § 8.2 クロスサイトの探査で保護する境界も越えない。

  4. origin の 直列化が、 entry の origins の項目である場合、 entry を返す。

    注： 明示的な origins リスト に含まれるオリジンは、そのエントリーが PHL に 掲載されている必要なしに読み取れる。保存元オリジンは、そのオリジンを指定することで、 範囲を限定した開示を決定している（§ 3.5 リソースの可視性の引き上げおよび § 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照）。 その上で、さらに グローバルな普及を別途要求すると、通常の限定的な共有が、多くの場合は専有的なリソースについての、 それとは無関係な公開の選定作業に依存することになる。この確認を グローバルに開示可能の判定より前に行うことで、 後のグローバルな利用可能性を求める書き込みが、 リスト内のオリジンのアクセス権を取り消すことを防ぐ。§ 8.2 クロスサイトの 探査を参照。

  5. entry の グローバルに開示可能が true である場合：

    1. entry の hash が PHL に掲載されているのでなければ、null を返す。

      注： 公開ハッシュリストによる判定が 適用されるのは、グローバルな権限付与だけである。これは、その判定がなければ、 Web 上の任意のオリジンに開示が及び得る唯一の場合である。エントリーが グローバルに開示可能であっても、その hash が PHL に 掲載されているのでなければ、 この権限付与だけに基づいて資格を得るオリジンには開示されない。一方、 同時に 保存元オリジン、それらと同一サイトのオリジンの集合、または 明示的な origins リストに含まれるオリジンについては、 すでに上記で結果を返している。

    2. ユーザーエージェントが、この要求に GREASE を適用することを選択した場合、 null を返す。

      注： GREASE の適用も、 グローバルな権限付与だけを対象とする。上記で確認した権限付与では、 この手順に到達することは決してない。保存元オリジンとそれらと同一サイトのオリジンは 1 つの信頼単位であり、 明示的な origins リスト内のオリジンは、 書き込み元によって意図的に指定されており、その書き込み元の Cross-Origin-Storage-Allow-Origin ヘッダーによって許可されている。

    3. entry を返す。

  6. null を返す。

利用可能性の ゲーティングを適用するには、COS エントリーまたは null である entry と、 オリジン origin を受け取り、COS エントリーまたは null を返す：

  1. COS の開示を決定するを entry および origin を指定して実行した結果を返す。

3.3. ファイルの作成と書き込み

FileSystemFileHandle が 作成要求を完了するによって作成された場合、関連付けられた 要求されたオリジンを持つ。これは、検証して保存するが、 引き上げの対象とするエントリーの origins に適用しようとする値であり、その適用は、 ハンドルを通じた書き込みが成功した後に試みられる。

すべての FileSystemFileHandle のうち、クロスオリジンストレージファイルシステムを指すものには、さらに、 関連付けられた COS ハッシュ（そのハンドルが指す COS ハッシュ）と、 関連付けられた COS オリジン（そのハンドルを取得した オリジン）と、 関連付けられた 読み取り可能という真偽値がある。この真偽値は、 getFile() が、その特定のハンドルを通じて、指し示すエントリーのバイトを開示してよいかどうかを 制御する。読み取り要求を完了するから返されたハンドルでは、すでに 利用可能性のゲーティングを通過しているため true となる。一方、 作成要求を 完了するから返されたハンドルでは、検証して保存するがその同じハンドルについて成功するまで false となる。

注： ハンドルが指すのは COS ハッシュであり、COS エントリーではない。作成要求を完了するは、 対応するエントリーが COS レジストリーに存在せず、今後も作成されない可能性があるハッシュに対してもハンドルを返す。そのため、 検証して保存するがエントリーを作成するまでは、ハンドルが参照できるエントリーは存在しない。

注： これは意図的に、個々のハンドルのプロパティとしている。 作成要求は、 そのハッシュのエントリーがすでに存在するかどうかにかかわらず、ハンドルを返す（ 作成要求を 完了するを参照）。そのため、エントリー単位の規則では、任意のオリジンが requestFileHandle() を、 create: true を指定して呼び出し、自ら書き込んだことのないエントリーを 直ちに読み取れてしまう。つまり、origins、 PHL への掲載、または GREASE の適用による条件を満たさずに、その内容を知ることができる。この 仕様のすべての開示制御は読み取り経路に適用されるため、エントリー単位で制限すると、作成要求が それらをすべて回避できてしまう。呼び出し元に、まず正しいバイトを提供するよう要求することで、 作成要求から得たハンドルを通じた読み取りが成功しても、呼び出し元がすでに持っていたもの以外は何も開示されない。

作成要求を 完了するには、プロミス result、 COS ハッシュ hash、CrossOriginStorageRequestFileHandleOptions options、グローバルオブジェクト global、および Realm realm を指定して、次の手順を実行する：

  1. requestedOrigins を、要求された オリジンを正規化するを、 options["origins"] を指定して実行した結果とする。

  2. requestedOrigins が リストである場合、 requestedOrigins を、 COS スコープ上限を適用するに、 requestedOrigins と、 COS スコープ上限を取得するを global を指定して実行した結果を渡し、実行した結果に設定する。

  3. handle を、新しい FileSystemFileHandle を作成する [FS]ことによって得られる結果とする。その ロケーターは、hash を クロスオリジンストレージファイルシステム内で指し、作成先の Realm は、 realm とする。

  4. handle の COS ハッシュを、hash に設定する。

  5. handle の COS オリジンを、global の 関連する設定群オブジェクトの オリジンに設定する。

  6. handle の 要求されたオリジンを、 requestedOrigins に設定する。

  7. handle の 読み取り可能を false に設定する。

    注： このアルゴリズムは、COS レジストリーを参照せず、 変更もしない。そうすることはできない。 その結果は、hash がすでに保存されているかどうかに依存してはならず、そうでなければ、作成 要求 自体が以前からの存在を開示してしまうためである（§ 8.2 クロスサイトの探査を参照）。 したがって、handle は、 エントリーが存在する場合、一度も書き込まれていない場合、現在ほかの書き込み元によって書き込まれている場合のいずれでも、 まったく同じ条件で返され、この呼び出し元がバイトを提供するまでは読み取り権限を持たない。

    注： ここでは何も登録されないため、 呼び出し元がハンドルを要求した後に放棄し、 createWritable() を一度も呼び出さなかったり、得られたストリームを閉じなかったりしても、 レジストリーは要求前とまったく同じ状態に保たれる。ほかのオリジンは、その要求が 行われたことを観測できず、後の読み取りを妨げる仮の状態にハッシュが固定されることもない。 § 8.3 進行中の書き込みを参照。

    注： requestedOrigins が適用されるのは、 検証して 保存するが、 リソースの可視性を引き上げるを通じて適用する場合だけであり、これはバイトの 書き込みと検証が完了した後に行われる。これにより、 作成要求が可視性を広げるには、先にバイト全体を提供しなければならなくなる。 § 3.5 リソースの可視性の引き上げを参照。

  8. グローバルタスクをキューに入れる。その際、DOM 操作タスクソースと global を指定し、タスク内で行う 解決の対象を result、解決値を handle とする。

要求された オリジンを正規化するには、(DOMString or sequence<DOMString>) または undefined である origins を受け取り、"*"、リスト（オリジンを項目とするもの）、または null を返す：

  1. origins が 存在しない場合、 null を返す。

  2. origins が "*" である場合、"*" を返す。

  3. list を « » とする。

  4. 各 candidate について、origins 内を反復する（単一の 文字列は、項目が 1 つの リストとして 扱う）：

    1. candidateOrigin を、オリジンのうち、基本 URL パーサーを candidate に対して実行して得られたものとする。

      注： COS 要求を 検証するは、各 candidate が 不透明でないオリジンに解析されることをすでに確認している。

    2. list が 含む項目に candidateOrigin がなければ、追加する：candidateOrigin を list に。

  5. list を返す。

注： 後で既存のエントリーに 併合するよりも前の、 この段階で重複を除去することで、origins は、エントリーが最初に 作成された時点から重複のない状態に保たれる。そのため、その後のすべての 複製も、重複のない状態に保たれる。

FileSystemWritableFileStream のうち、 createWritable() の呼び出しによって取得され、呼び出し先のハンドルの ロケーター が クロスオリジンストレージファイルシステムを指すものが閉じられたとき [FS]、ユーザーエージェントは、 以下の 検証して保存する手順を、 そのハンドルを指定して、閉じる操作のプロミスが履行される 前に実行しなければならない。

注： これは、閉じる操作がどのように開始されたかに かかわらず適用される。明示的な close() 呼び出しでも、pipeTo() 呼び出しがソースの 終端に達した場合でも同様である。後者も既定では転送先を閉じる。[STREAMS] は、ストリームが閉じられる時点では この 2 つを区別せず、このアルゴリズムも区別しない。

検証して保存する 手順は、FileSystemFileHandle handle（そのストリームが 閉じられたもの）、書き込まれた完全な バイト列 bytes、および閉じる操作の 関連する設定群オブジェクトの オリジン origin を指定して、次のとおり実行する：

  1. hash を、handle の COS ハッシュとする。

  2. computedValue を、bytes の小文字の 16 進数によるダイジェストとする。その計算には、 次の アルゴリズムを用いる：hash の algorithm で指定されるアルゴリズム。計算は [WEBCRYPTO] に従う。

  3. computedValue が hash の value と厳密に等しくない場合：

    1. 拒否する：閉じる操作のプロミスを、"DataError" DOMException で。

    2. これらの手順を中止する。

    注： 書き込みが失敗しても、後始末が必要なものは 存在しない。作成要求を完了するはエントリーを登録していないため、 検証済みのバイトを生成しなかった書き込みは、COS レジストリーを変更せず、後で同じハッシュに対して requestFileHandle() を呼び出すと、 "NotFoundError" が、書き込みが一度も試みられなかった場合と同様に返される。いずれかのオリジンが すでに書き込んだエントリーも、同様に影響を受けない。このアルゴリズムが行うのは、バイトと権限付与の追加だけである。

  4. 以下の手順をキューに入れる。追加先は、 クロスオリジンストレージキューとする：

    1. entry を、COS エントリーのうち、COS レジストリー内に存在し、その hash と 等しい値が hash であるものがあればそれとし、なければ null とする。

    2. entry が null である場合：

      1. entry に、新しい COS エントリーを設定する。その hash は hash、 bytes は bytes、origins は空の リスト、 グローバルに開示可能は false、そして 保存元オリジンは空の 集合とする。

      2. 次のように設定する：COS レジストリー[hash] を entry に。

      注： この仕様で、 エントリーを COS レジストリーに追加する手順はこれだけであり、bytes が hash に照らして検証された後にのみ実行される。 2 つの書き込み元が、どちらもハッシュが存在しないと判断して同時に書き込んだ場合、それぞれがここに到達する。 そのうち、 後からキューに入れられた方は、先の書き込み元が作成したエントリーを見つけ、以下で自身のオリジンと 権限付与を追加するだけである。両者のバイトは同じ値にハッシュされるため、一度保存すれば十分である。

    3. 追加する：origin を、entry の 保存元オリジンに。ただし、まだ 含まれていない場合に限る。

    4. リソースの可視性を引き上げるを、 entry および handle の 要求されたオリジンを指定して実行する。

    5. handle の 読み取り可能を true に設定する。

      注： 読み取り可能になるのは、このハンドル だけである。同じハッシュに対する別のハンドルが、 まだ書き込みに使用されていない別の作成要求から得られたものである場合、それは読み取り不可能なままである。

createWritable() の呼び出し先が FileSystemFileHandle であり、それが クロスオリジンストレージファイルシステムを指す場合、生成される FileSystemWritableFileStream の内容は、 最初は空でなければならない。これは、keepExistingData の値にも、 指し示す COS ハッシュに対応するエントリーが COS レジストリーに存在するかどうかにも依存しない。

注： [FS] では、本来、keepExistingData を、既存のファイルの内容で ストリームを初期化するものと定義している。ここでその動作に従うと、呼び出し元は、一度も所有したことのない バイトの保存元オリジンになれてしまう。作成要求は、エントリーがすでに存在するかどうかにかかわらずハンドルを返すため、 呼び出し元は、別のオリジンが保存したハッシュに対する書き込み可能なストリームを開き、何も書き込まずに 閉じることで、引き継がれたバイトを要求された値にハッシュさせることができる。そうすると、 読み取り権限が付与される際に、origins、公開ハッシュリスト、 GREASE の適用が一切参照されない。これは、利用可能性の ゲーティングの回避を、 個別には許可された 2 つの操作を組み合わせて実現することになる。同じ理由により、 検証して保存するは、 すべての作成要求で内容全体を要求する。

注： したがって、何も書き込まずに閉じられた書き込み可能なストリームは、 空のバイト列を保持する。そのハッシュは、 呼び出し元が求めるいずれのエントリーについても要求された値とは一致しないため、検証して保存するは、 "DataError" DOMException で、ほかの不一致の場合と同様に拒否する。この場合に、 代わりにストレージや I/O の失敗を報告する実装は、検証結果を無関係な エラーで覆い隠している。

ファイルシステム標準 [FS] は、それに依存する 仕様が、 書き込みごとの追加の検証を FileSystemWritableFileStream の 閉じる手順に組み込むための拡張点を、まだ定義していない。そのようなフックが用意されるまでは、この節で必要な動作を直接記述する。 将来の改訂では、[FS] と正式に統合されることが期待される。

3.4. 取得したリソースの保存

§ 9 他の仕様との 統合に列挙されたホスト統合は、 取得したリソースを、FileSystemFileHandle を経由せずに保存する。 それらのホスト仕様は、 取得したバイトが、その統合で要求される完全性の検査に合格した後に、 以下のアルゴリズムを実行することが期待される。

取得したリソースをクロスオリジン ストレージに保存するには、レスポンス response、バイト列 bytes、COS ハッシュ hash、"*"、リスト（文字列を項目とするもの）、 または null である origins、および 環境設定群オブジェクト settings を指定して、次の手順を実行する：

  1. クロスオリジンストレージの 権限を確認するを、settings の グローバルオブジェクトを指定して実行した結果が false である場合、戻る。

  2. options を、«[ "origins" → origins ]» とする。ただし、これは origins が null でない場合とし、それ以外の場合は «[ ]» とする。

  3. COS 要求を検証するを hash および options を指定して実行した結果が null でない場合、 戻る。

  4. computedValue を、bytes の小文字の 16 進数によるダイジェストとする。その計算には、 次の アルゴリズムを用いる：hash の algorithm で指定されるアルゴリズム。計算は [WEBCRYPTO] に従う。

  5. computedValue が hash の value と厳密に等しくない場合、戻る。

    注： 統合自体の完全性 メタデータには、複数のダイジェストを列挙でき、そのいずれか 1 つと一致すれば検査に合格する。この手順は、まさにこれらのバイトが生成するハッシュを エントリーのキーとして使用することを保証する。

  6. requestedOrigins を、要求された オリジンを正規化するを、 options["origins"] を指定して実行した結果とする。

  7. requestedOrigins が リストである場合：

    1. internalResponse を、response の 内部レスポンスとする。ただし、これは response が フィルターされたレスポンスである場合とし、それ以外の場合は response とする。

    2. requestedOrigins を、COS スコープ上限を適用するに、 requestedOrigins と、COS スコープ 上限を解析するを、 internalResponse の ヘッダーリストを指定して実行した結果を渡し、実行した結果に設定する。

    注： 上限は、取得した リソース自体の レスポンスから取得されるため、バイトを 提供するサーバーが、それを開示できるオリジンを決定する。読み込み元の Document の COS スコープ上限は関与しない。その運営者は リソースを制御しておらず、 受け取り手を許可できるようにすると、任意のサイトが、別のサイトのアセットを、 自ら選んだオリジンと共有可能だと宣言できてしまうためである。ユーザーエージェントは、内部 レスポンスからヘッダーを読み取るため、不透明な フィルターされたレスポンスでも機能し、そのヘッダーが ページに公開されることは決してない。

  8. origin を、settings の オリジンとする。

  9. 以下の手順をキューに入れる。追加先は、 クロスオリジンストレージキューとする：

    1. entry を、COS エントリーのうち、COS レジストリー内に存在し、その hash と 等しい値が hash であるものがあればそれとし、なければ null とする。

    2. entry が null である場合：

      1. entry に、新しい COS エントリーを設定する。その hash は hash、 bytes は bytes、origins は空の リスト、 グローバルに開示可能は false、そして 保存元オリジンは空の 集合とする。

      2. 次のように設定する：COS レジストリー[hash] を entry に。

      注： 検証して保存すると同様に、 エントリーが作成されるのは、bytes が hash に照らして検証された後に限られ、その検証は、統合の integrity 検査によってすでに行われている。 requestFileHandle() を使った、同じハッシュへの書き込みがまだ 進行中であっても、影響は受けない。その書き込みはレジストリー内に状態を持たず、自身の 検証して保存する は、 このエントリーを見つけて自身のオリジンと権限付与を追加し、通常どおり完了する。

    3. 追加する：origin を、entry の 保存元オリジンに。ただし、まだ 含まれていない場合に限る。

    4. リソースの可視性を引き上げるを、 entry および requestedOrigins を指定して実行する。

注： 検証して保存すると同様に、保存には常に バイト全体が必要であり、エントリーが すでに "written" である場合も同様である。そのため、以前から存在していたかどうかは何も明らかにならない。統合が ネットワークから取得する前に行う 検索は読み取りであり、利用可能性のゲーティングと、 § 8.2 クロスサイトの探査の探査に関する考慮事項の対象となる。

3.5. リソースの可視性の引き上げ

COS エントリーの可視性は、 引き上げることはできるが、引き下げることは決してできない。

リソースの 可視性を引き上げるには、COS エントリー entry と、"*"、リスト（ オリジンを項目とするもの）、または null である requestedOrigins を指定して、次の手順を実行する：

  1. requestedOrigins が null である場合、戻る。

    注： origins の省略は、同一サイトでの 利用可能性のみを要求する。これは、すべてのエントリーがすでに備えている（COS の 開示を決定するを参照）ため、 追加するものはない。

  2. requestedOrigins が "*" である場合：

    1. entry の グローバルに開示可能を true に設定する。

    2. 戻る。

    注： これはグローバルな権限付与を追加するものであり、 entry の origins は変更しない。すでに 明示的な origins リストを持っていたエントリーは、それを保持する。そのため、 その リスト内のすべてのオリジンは、PHL に依存しないアクセス権を、エントリーが グローバルに開示可能になった後も保持する。これこそが、 2 つの権限付与を 別々に保存する理由の核心である。グローバルに開示可能を参照。

  3. 各 candidateOrigin について、 requestedOrigins 内を反復する：

    1. entry の origins が 含む項目に candidateOrigin がある場合、 継続する。

    2. entry の origins の サイズ が、ユーザーエージェントの オリジンリストの最大長と等しい場合、 反復を抜ける。

      注： 残りの candidateOrigin 値は、この引き上げから通知なく除外される。 書き込み自体はすでに成功しているためであり、ユーザーエージェントは、エントリーのオリジンリストが 上限に達したことを示す警告をコンソールに記録することが期待される。

    3. 追加する：candidateOrigin を、 entry の origins に。

注： 引き上げが行うのは、origins への追加、または グローバルに開示可能 を true に設定することだけである。リストを要求する書き込み元は、すでに グローバルに開示可能なエントリーについても、そうでないエントリーと同様に 開示範囲を広げる。2 つの権限付与は 独立しているためであり、新たにリストへ追加されたオリジンは、PHL に依存しないアクセス権を、 "*" の権限付与が引き続き有効である間にも取得する。

注： 元の保存者以外も含め、任意のサイトは、エントリーの 開示先である origins を広げることができる。ただし、 同時に、エントリーの hash にハッシュされるバイトを提供しなければならない。これは意図したものである。 あるハッシュに対応する正しいバイトをすでに所有しているサイトは、その仕組み上、そのハッシュが何を表すかについて、 元の保存者と同じだけの権威を持つためである。

3.5.1. 元の保存者によるアクセス

オリジンが、書き込みを、ある COS エントリーについて正常に完了した場合（ すなわち、その オリジンが、エントリーの 保存元オリジンに含まれる場合）、 その後は常に、 そのエントリーのハンドルを requestFileHandle() を通じて取得できる。 これは、エントリーの origins の値にも、 その hash が PHL に掲載されているかどうかにも依存しない。 これは、オリジンが自ら保存したものに常にアクセスできるという、Cache API のモデルに倣っている。

4. クロスオリジンストレージファイルシステム

クロスオリジンストレージファイルシステムは、ファイルシステムルートであり、いずれの オリジンの バケットファイルシステムやローカルファイルシステムへのアクセスルートとも異なる。その エントリーは、COS レジストリーの COS エントリー項目と一対一で対応する。

クロスオリジンストレージファイルシステムは、[FS] の通常の呼び出しごとの 権限確認 モデルを使用しない。そこから取得されるすべての FileSystemFileHandle は、スクリプトに返される前に、 § 3.2 ファイルの読み取りまたは § 3.3 ファイルの作成と 書き込みによって、すでに完全に許可されている。そのため、 getFile() または createWritable() をそのようなハンドル上で呼び出しても、 追加の権限プロンプトが表示されることは決してない。

したがって、そのようなハンドル上の queryPermission() と requestPermission() は、 決して "prompt" を報告してはならない。プロンプトが表示されることはないためである。書き込みモードについては、 ハンドルが 作成要求によって取得されたものでない場合に "denied" を報告し、それ以外の場合には、 "granted" を報告しなければならない。

注： 書き込みは、ハンドルが実際に欠いている可能性のある 能力である。書き込みに使用できるハンドルを生成するのは、 作成要求だけである。そのため、それ以外のハンドルの書き込みモードについて "granted" を報告すると、 createWritable() が拒否する能力を持っていると主張することになる。読み取りは、 "granted" のままとなる。読み取り可能なハンドルを持つ呼び出し元は、それを通じて読み取れるためである。権限を要求しても、 いずれの応答も 変えられない。表示するプロンプトも、権限付与を記録できる状態も存在しないためである。

getFile() を呼び出す対象が FileSystemFileHandle であり、それが クロスオリジンストレージファイルシステムを指し、その 読み取り可能が false である場合、 "NotAllowedError" DOMException で拒否しなければならない。 これには、異なる 2 つの場合が含まれる：

  • 作成要求から得られたハンドルであり、まだ それを通じた 書き込みが行われておらず、指し示すハッシュに対応するエントリーが COS レジストリーに存在しない場合。返せる検証済みのバイトは 存在せず、呼び出し元が自身の未完了の書き込みを、あたかもファイルの 実際の内容であるかのように観測できてはならない。

  • 別のオリジンがすでに書き込んだハッシュに対する作成要求から得られたハンドルである場合。 検証済みの バイトは存在するが、この呼び出し元はそれらを提供しておらず、 利用可能性のゲーティングも通過していない。そのため、エントリーについては何も知ることができてはならず、 その存在の 有無さえ知ることができてはならない。

注： どちらの場合も拒否は同一であるため、 何も開示しない。このため、 "NotAllowedError" は、読み取り経路では意図的に避けられているにもかかわらず、ここでは安全である。このハンドルは、 呼び出し元自身の作成要求によって取得されたものであり、ほかの オリジンでは逆直列化できない（§ 4.1 ハンドルの転送を参照）。したがって、その応答は、 オリジンの境界を越えることが決してなく、 レジストリーの内容によらず一定である。§ 8.3 進行中の書き込みとは対照的であり、そこでは、 読み取り経路上の異なるエラーが、その境界を越えることになる。

ハンドルの 読み取り可能が true になると、getFile() をそのハンドル上で呼び出したときに返されるのは、File であり、その内容は、指し示すエントリーの bytes である。これは、 [FS] がすでに定義している動作とまったく同じである。その対象は、ファイル エントリーであって、その バイナリーデータがそれらのバイトであるものである。

FileSystemFileHandle が クロスオリジンストレージファイルシステムを指す場合、その ファイルシステムロケーターの パスは、リストであり、 単一の 文字列、すなわち、その COS ハッシュの value を含む。また、その ルート は、クロスオリジンストレージファイルシステムである。

注： [FS] は、name を、ハンドルのロケーターの パスの最後のパス成分として定義している。そのため、これによって name も決まる。 その値は、 ハッシュである。エントリー自体に名前はなく、ハッシュが唯一の識別情報であるため、 それを報告することで、空文字列では捨てられてしまう情報を伝えられる。

エントリーには名前も、それを格納するディレクトリーもないため、[FS] の構造に関する機能の大半には、 操作対象がない。同一性は例外であり、内容アドレス方式のエントリーが 常に答えられる問いである。COS レジストリーが保持する COS エントリーは、COS ハッシュごとに最大 1 つであるため、2 つの ハンドルが同じエントリーを指すのは、それらのハッシュが等しい場合に限られる。

isSameEntry() を呼び出す対象が FileSystemFileHandle であり、そのハンドルが クロスオリジンストレージファイルシステムを指し、引数も 同じファイルシステムを指していて、かつ、 同じ オリジンによって取得されている場合、2 つのハンドルの COS ハッシュ項目が 等しいなら true、それ以外なら false を返さなければならない。

注： これを拒否すると、ユーザーエージェントが すでに保持している情報を捨てることになる。

isSameEntry() の呼び出しに渡された引数が、呼び出し元の オリジンによって取得されたものでない場合、 または、クロスオリジン ストレージファイルシステム以外のファイルシステムを指す場合、拒否しなければならない。

注： その場合に false を返すと、 2 つのハンドルが異なるエントリーを指すと断言することになる。 これは、呼び出し元のオリジンが調べる権限を持たないハンドルについての主張である。拒否が示すのは、 比較できなかったということだけである。

move() と remove() の呼び出し先が、 FileSystemFileHandle であり、それが クロスオリジンストレージファイルシステムを指す場合、 "NotAllowedError" DOMException で拒否しなければならず、 指し示すエントリーがあれば、それを変更せずに保たなければならない。

注： エントリーは、その 保存元 オリジン内のすべてのオリジンで共有される。そのため、 削除を認めると、あるサイトが、ほかのサイトが依存するデータを破壊できてしまう。削除は、 追い出しと、ユーザー自身によるストレージ制御が担う。名前の変更や親の変更には、 操作対象がない。エントリーは、その COS ハッシュによって識別され、それを格納するディレクトリーがないためである。

注： 執筆時点では、どちらのメソッドも [FS] や File System Access API では定義されていない （WICG/file-system-access#214）。 そのため、エラー名は、removeEntry() に倣っている。 これは、[FS] が エントリーを削除するために定義している操作であり、読み書きアクセスが許可されていない場合、 アクセス結果のエラー名で拒否する。ここでは拒否するのが正確な動作である。操作には意味があり、 その操作が拒否されているためである。

createSyncAccessHandle() については、ここで規則を設ける必要はない。その手順は、 "InvalidStateError" DOMException で、ハンドルが バケットファイルシステム内にない場合に拒否する。 また、クロスオリジンストレージファイルシステムは、ファイルシステムルートとして、いずれのオリジンのものとも異なる。 そのため、[FS] がすでに、 拒否されることと、そのエラー名の両方を定めている。

注： これは、この仕様が独自に定めるとしても 望む結果である。 FileSystemSyncAccessHandle は、書き込み可能なファイル記述子を呼び出し元に渡すため、 エントリーの bytes を、 その保存に使用される COS ハッシュとの対応を 崩す形で変更できてしまう。 しかも、そのエントリーを開示できるほかのすべてのオリジンも、同じバイトを読み取る。

4.1. ハンドルの転送

FileSystemFileHandle は、直列化可能なオブジェクトである [FS]。そのため、 COS エントリーを指すものを、別の 環境設定群オブジェクトに渡すことができる。例えば、 postMessage(message, options) を使用する。 これは、 requestFileHandle() に加えて、そのようなハンドルを取得する第 2 の方法であるため、ここでも制約を設ける。

直列化手順は、対象となる FileSystemFileHandle が、 クロスオリジンストレージファイルシステムを指す場合、 value と serialized を指定して、追加で次を行う：

  1. serialized.[[COSHash]] を、value の COS ハッシュに設定する。

  2. serialized.[[COSOrigin]] を、value の COS オリジンに設定する。

  3. serialized.[[COSMayRead]] を、value の 読み取り可能に設定する。

逆直列化手順は、serialized、 value、および realm を指定して、追加で次を行う：

  1. serialized.[[COSOrigin]] と 同一オリジンであるかどうかを、realm の 環境設定群オブジェクトの オリジンについて判定し、同一オリジンでない場合、 "DataCloneError" DOMException を投げる。

  2. value の COS ハッシュを、serialized.[[COSHash]] に設定する。

  3. value の COS オリジンを、 serialized.[[COSOrigin]] に設定する。

  4. value の 読み取り可能を、 serialized.[[COSMayRead]] に設定する。

注： 同一 オリジンの確認がなければ、転送によって、この仕様のすべての開示制御が 一度に無効になってしまう。読み取り可能が true であるハンドルは、 すでに、 利用可能性のゲーティングを適用するを、そのハンドルを要求した オリジンについて通過している。それを別の オリジンに送信すると、そのオリジンに対して origins、 PHL への掲載、または GREASE の適用を一切評価せずに、エントリーのバイトを渡すことになる。これは、 ファイルシステム標準における既存のハンドルの扱いとも一致している。そこでも、ハンドルを利用できるのは、 同一オリジンの受け取り手だけである。

注： 読み取り可能は、 ハンドルとともに引き継がれる。そのため、まだ書き込みに使用されていない作成要求のハンドルは、転送後も読み取り 不可能なままであり、 読み取り要求のハンドルは、ゲーティングを再適用されることなく読み取り可能なままとなる。到着時にゲーティングを再適用すると、 呼び出し元は、同じハンドルを転送することで、 利用可能性を繰り返し探査できてしまう。

5. ストレージの管理

5.1. ストレージの制限

ユーザーエージェントは、オリジンが COS レジストリーに 成功した書き込みを通じて追加できる総バイト数に、上限を設けなければならない。 これは、単一のオリジンが、 ほかのオリジンのエントリーを追い出そうとして、キャッシュを大量のデータで埋め尽くすことを防ぐためである。具体的な上限は、 実装定義である。オリジンによる書き込みが、その 上限を超える場合、ユーザーエージェントは、 拒否を、その 書き込みに対して、"QuotaExceededError" DOMException を理由として行わなければならず、警告を コンソールに記録すべきである。

注： エントリーは 内容アドレス方式であるため、オリジンが 同じハッシュの下で同じ バイトを繰り返し書き込んでも、最初の成功した書き込みを超えて追加のクォータを消費することはない。 § 2.2 COS エントリーを参照。

ユーザーエージェントには、実装定義の オリジンリストの最大長もある。これは、 正の整数であり、オリジンの数について、単一の origins リストが 含められる上限を定める。この制限は、リストが最初に指定されたとき（COS 要求を検証するを参照）と、 後で既存のエントリーに併合されるとき（ リソースの可視性を引き上げるを参照）の両方で適用される。そのため、単一の呼び出しでも、 時間の経過とともに行われる多数の呼び出しの累積効果でも、エントリーの origins を 無制限に増やすことはできない。これは、メモリー使用量を制限するだけでなく、オリジンの リストが、 明示されないまま "*" の代わりとして使用されることも防ぐ。§ 8.2 クロスサイトの探査を参照。

この上限を超えた場合の扱いは、それら 2 か所で異なる。2 つの呼び出しが、 操作の中で大きく異なる時点に行われるためである：

  • COS 要求を検証するでは、ファイルの 取得、ハッシュ計算、または 書き込みが行われる前に上限を確認する。上限を超えた呼び出し元には、直ちに "TypeError" が返され、それ以外は何も起こらない。 これは、ほかの不正な origins 値と同じ扱いである。

  • リソースの可視性を引き上げるでは、上限に達するのは、 個別の独立した書き込み呼び出しで要求された オリジンの累積効果による場合だけである。それらの呼び出しは、無関係なオリジンによって長期間にわたり 行われる場合もあり、この呼び出しのバイトについて、ハッシュ計算、 検証、および永続的な保存がすでに完了した後にのみ上限が確認される。その時点で書き込みを拒否すると、 成功して検証も済んでいる、場合によっては非常に大きな書き込みを、無関係な管理上の上限のために破棄することになり、 しかも、その原因を単一の呼び出し元の誤りに帰することさえできない。そのため、書き込みは成功させたままとし、 上限を超えるオリジンだけを origins への追加から除外し、 コンソールに警告を記録する。これは、 許容範囲の広い状態から、より制限された状態への要求に対する既存の扱いに倣っている。オリジンに関する要求を 完全には受け入れられない場合、通知なく上限が適用されるが、その要求を伴う書き込み自体は、 引き続き成功する。この仕様のほかの箇所における § 8.4 利用可能性のゲーティングと 同様に、 呼び出し元には、要求した オリジンが 実際に追加されたかどうかを事後に確実に確認する方法はない。その後の requestFileHandle() 呼び出しを、その オリジンとして行っても、オリジンが追加されていたにもかかわらず失敗する可能性がある（例えば、エントリーが 追い出された場合や、ユーザーエージェントが要求を抑制した場合）。そのため、その結果を、追加されたことの確認にも、 追加されなかったことの確認にも用いてはならない。

5.2. 追い出し

この節は非規範的である。

ストレージの空き容量が逼迫した場合、ユーザーエージェントは、エントリーを COS レジストリーから追い出してよい。 例えば、最も長く利用されていないものから追い出す方針を、保存元オリジンのうち、 各エントリーに最後にアクセスしたものを対象として用いる。ユーザーエージェントは、ユーザーが、 保存されているファイル、各ファイルにアクセスしたオリジンを確認し、エントリーを手動で 削除したり、すべてのクロスオリジンストレージデータを消去したりできる設定 UI を提供することが期待される。

ユーザーがオリジンのサイトデータを消去したとき、ユーザーエージェントは、そのオリジンが含まれるすべての 保存元 オリジン集合から、そのオリジンを除去すべきである。その除去後に、COS エントリーの 保存元 オリジンが空になった場合、ユーザーエージェントは、そのエントリーを削除対象として検討してよい。

5.3. 手動で追加されたエントリー

この節は非規範的である。

上記の設定 UI は、ユーザーがディスク上にすでに持っているファイルを、 クロスオリジンストレージに直接追加できるようにしてよい（例えば、Web サイトとは独立にダウンロードした AI モデル）。 この場合、スクリプトが requestFileHandle() を呼び出すことはない。 そのようなエントリーには、 書き込みの帰属先となる要求元の オリジンがない。そのため、命令型 API だけでは答えられない 2 つの問いが生じる：

  • 元の保存者は、 § 3.5.1 元の保存者によるアクセスにおいて誰に該当するか。誰にも該当しない。エントリーの 保存元オリジンは、初期状態では空である。 したがって、どのオリジンも、 通常の 利用可能性のゲーティングと origins の確認から 免除されない。これらは、本来、すべての要求元オリジンに適用されるものである。実際にバイトを 書き込んだオリジンはないため、これは正しい結果である。

  • そのようなエントリーは、通常の書き込みで origins を省略した場合と同様に、同一サイトのみに制限すべきか。そうではない。「同一サイト」は、 要求元のオリジンとの関係でのみ意味を持つが、手動での追加には要求元オリジンがない。そのため、「同一サイト」の 基準となるサイトが存在しない。ユーザーエージェントは、そのようなエントリーを グローバルに 開示可能にし、 明示的な origins リストを空のままにすることが期待される。ファイルを手動で あらかじめ保存することが、 その目的（まだ訪問していないサイトで、ユーザーがディスク上にすでに持っているファイルを再利用できるようにすること）を果たすには、 ほかのオリジンが実際にそのファイルを発見できなければならないためである。ユーザーエージェントの設定 UI は、 追加で、ユーザーがより狭い範囲を選択できるようにしてもよい。

このように追加されたエントリーは、それ以外の点では、 Web サイトが requestFileHandle() を通じて書き込んだものと区別できない。 同じ 利用可能性のゲーティングと 可視性の 引き上げの規則が、同じ権限付与を持つほかのエントリーとまったく同様に適用される。 これには、PHL に掲載されているかどうかの確認も含まれる。 エントリーが最終的に グローバルに開示可能となる場合には、この確認が行われる。これは、手動での追加における既定の状態である。

5.4. 来歴メタデータ

この節は非規範的である。

COS エントリーは、意図的に、 そのバイトの取得元について何も記録しない。識別情報は、 hash だけである。同じバイトは、 それを保存したオリジンの数や、 取得元の URL の数にかかわらず、同じエントリーとなる（§ 2.2 COS エントリーを参照）。URL は、 ある書き込み元による 取得の属性である。そのため、複数のオリジンが書き込んだエントリーに対して、 恣意的でない方法で 1 つの URL を選ぶことはできない。また、URL はバイトと同じようには検証できない（§ 8.1 リソースの完全性を参照）。 さらに、URL は、粗い粒度の オリジン値が 保存元 オリジンに保持する情報よりも、はるかに多くのユーザーの閲覧情報を含む。パスやクエリー文字列が、特定の文書、 アカウント、またはセッションを示す可能性があるためである。したがって、URL をエントリーに記録すると、高エントロピーの信号を、 開示制限の外へ迂回させることになる。その制限は、origins と § 8.4 利用可能性の ゲーティングによって課すために設けられている。

それでも、その情報を求める動機は確かにある。§ 5.2 追い出しで説明する設定 UI で、 数 GB のファイルを見ているユーザーと、 requestFileHandle() の呼び出しでファイルが見つからなかった理由を調べている開発者は、どちらも、そのファイルが どこから来たのかを知りたいだろう。ユーザーエージェントは、エントリーに付随して実装内部専用の来歴記録を保持することで、 その需要に応えてよい（例えば、各 保存元オリジンが、 バイトを どの URL からいつ取得したか）。ただし、その記録は、エントリーの外に保持されるユーザーエージェントの状態として 扱わなければならない：

  • スクリプトには決して公開しない。この仕様には、それを開示するものはなく、後から追加されるものも、 開示すべきではない。requestFileHandle() も、それが返す FileSystemFileHandle も、その記録の内容はもちろん、存在するかどうかさえ、 明らかにすべきではない。特に、要求元の オリジンが、 自ら生成していない記録を観測できてはならない。

  • 公開するのは、信頼できる Web 以外のインターフェースに限る。すなわち、ユーザーエージェント自身の設定およびストレージ 検査 UI、開発者ツール、ならびに（ユーザーエージェントに拡張機能プラットフォームがある場合には） ユーザーによる明示的な権限付与を必要とする拡張機能 API である。これは、閲覧履歴を公開するほかの API と同じ扱いである。 ブラウザー拡張機能との統合点の解説を、 この リポジトリーで参照すると、検討中の拡張機能向けインターフェースを確認できる。

  • 記録は未検証であり、そのように表示する。そこに含まれる URL は、バイトを書き込んだ オリジンによる主張である。内容を保証するのは、hash だけである（§ 8.1 リソースの完全性を参照）。2 つのオリジンが、同じエントリーについて異なる URL を 記録することもあり、どちらも、 不正確であったり、意図的に誤解を招くものであったりする可能性がある。

  • 記録の存続期間は、エントリーおよびその記録の帰属先のオリジンと共有する。エントリーが 追い出されたり削除されたりするときには記録を破棄し、あるオリジンに帰属する部分は、 そのオリジンが 保存元オリジンから除去されるときに破棄する。これには、ユーザーが その オリジンのサイトデータを消去する場合も含まれる（§ 5.2 追い出しを参照）。

そのような記録はコンテンツからは見えないため、ユーザーエージェントが記録を保持するかどうか、またどの程度の情報を 保持するかは、完全に実装に委ねられる。この仕様には、その記録に依存するものはなく、 サイトはその有無を検出できない。

6. 権限ポリシーとの統合

本仕様が定義する ポリシーで制御される機能 [permissions-policy] は、 文字列 "cross-origin-storage" で識別される。その既定の許可リストは self である。

[permissions-policy] は、使用を許可されているかどうかを Document について定義している。 しかし、 CrossOriginStorageManager は WorkerGlobalScope にも公開されており、 これは自身の Document を持たない。このため、確認処理は呼び出し元の グローバルオブジェクトを対象として記述される。 ワーカーのグローバルオブジェクトについては、それを推移的に所有する Document 群を 特定し、そのすべてが この機能を許可していなければならない。

クロスオリジンストレージの権限を確認するには、グローバルオブジェクト global を受け取り、 真偽値を返す次の手順を実行する：

  1. global が Window オブジェクトであるなら：

    1. document を、global に 関連付けられた Document とする。

    2. document が null なら、false を返す。

    3. document が 使用を許可されている対象に、 "cross-origin-storage" ポリシーで制御される機能が含まれないなら、 false を返す。

    4. true を返す。

  2. global が WorkerGlobalScope オブジェクトであるなら：

    1. owners を、global の 所有者集合とする。

    2. owners が 空で あるなら、false を返す。

    3. 各 owner（owners の要素）について：

      1. owner が Document であり、かつ owner が 使用を許可されている対象に、 "cross-origin-storage" ポリシーで制御される機能が含まれないなら、 false を返す。

      2. owner が WorkerGlobalScope オブジェクトであり、かつ クロスオリジンストレージの 権限を確認する手順を owner に対して実行した結果が false なら、false を返す。

    4. true を返す。

  3. false を返す。

このアルゴリズムが false を返す グローバルオブジェクトでは、そこから行われるすべての requestFileHandle() 呼び出しが、 "NotAllowedError" DOMException で拒否される。これは、ハッシュの検証、レジストリーの検索、または書き込みが 行われる前に起こる。

注： 所有者集合を通じて所有関係をたどることで、 オプトアウトが名ばかりになるのを防ぐ。blob: URL から作成されたワーカーは、作成元ページの オリジンで実行され、そのページとまったく同じクロスオリジンストレージのビューを共有する（ § 3 CrossOriginStorageManager インターフェイスを参照）。したがって、 グローバルオブジェクト自身の Document だけを参照する確認処理は、すべてのワーカーで空虚に満たされることになり、呼び出しを new Worker(URL.createObjectURL(&hellip;)) 内へ移すだけで、 cross-origin-storage=() ポリシーを ほかに何も変えずに回避できてしまう。

注： ServiceWorkerGlobalScope の 所有者集合は空なので、この アルゴリズムはそこで false を返す。これは、所有者集合の性質によるものである。すなわち、 ワーカーの作成時に構成され、そのワーカーがまだ実際に必要とされているかを判断するために 参照される、生存性を表す関係である。サービスワーカーは、どの Document とも、意図的にそのような関係を持たない。 その登録は永続化され、ユーザーエージェントはイベントに応じてグローバルオブジェクトを起動し、 サービスワーカークライアントがまったくなくても実行できる。したがって、 register() を呼び出したクライアントは登録時には特定できるものの、 グローバルオブジェクトの実行時にはすでに存在しないことが多い。また、実行中の一つのサービスワーカーは、 ポリシーが一致するとは限らない多数のクライアントに対応する。

注： サービスワーカーを対象に含めるには、ポリシーを取り込んで保持する必要があり、 その作業は [permissions-policy] および [service-workers] の範囲に属する。 本仕様が望ましいと考える形は、サービスワーカー自身のスクリプト応答にある Permissions-Policy ヘッダーから、そのサービスワーカーのポリシーを導出することである。これは、そのポリシーコンテナーが すでにその応答の CSP を保持しているのと同じ方式であり、オリジンの制御下にとどまり、 更新確認のたびに再評価される。登録元クライアントのポリシーのスナップショットを取る方式では、オプトアウトが 古い状態のままになる。ヘッダーから機能を 削除しても、登録がたまたま更新されるまで反映されないためである。このような モデルが存在するまでは、拒否する側に倒すことが、オプトアウトの回避に利用できない唯一の対応である。

注： SharedWorkerGlobalScope の 所有者集合には、異なるポリシーを持つ複数の Document が含まれることがあり、ワーカーの存続期間中に所有者が追加されたり失われたりする。 すべての所有者にこの機能の許可を要求すると、一つでも許可しない所有者があれば、 共有ワーカー全体でクロスオリジンストレージが無効になる。また、二つの requestFileHandle() 呼び出しの間で、判定結果が変わることもある。これに対して、 一つの所有者が許可すればよいとすると、この機能を許可する任意の文書が、 許可しない文書に代わって機能を再び有効にできてしまう。

7. Cross-Origin-Storage-Allow-Origin ヘッダー

COS エントリーの origins リストが 空でない場合、そのエントリーは書き込み元オリジンが 制御していないオリジンにも開示可能である。しかし、その リストは、スクリプト（ origins を通じて） またはマークアップによって宣言される。スクリプトまたはマークアップの注入に 成功した攻撃者は、いずれも設定できる。この宣言を、バイト列が開示されるオリジンの運用者と、 注入されたコンテンツには偽造できない形式で結び付けるため、本 仕様では、このような宣言で指定してよいオリジンを制限する応答ヘッダーを定義する。

Cross-Origin-Storage-Allow-Origin 応答ヘッダーは、 COS スコープ上限を保持する。この上限は、 集合 であり、オリジンのうち、書き込みが同一サイトではない origins リストで指定してよいものからなる。 バイト列を提供する側がこのヘッダーを送信するので、開示されるバイト列の元となる 応答から読み取る：

  • requestFileHandle() による書き込みでは、バイト列がスクリプトで生成され、 それ自身の元となる 応答を持たない場合がある。この場合に用いるのは、応答のうち、 呼び出し元の グローバルオブジェクトの Document を作成するために使用されたもの、 または、ワーカーについては、それを所有する Document 群の 作成に使用されたものである（COS スコープ上限を取得するを参照）。

  • ホスト側の統合では、応答として、保存するバイト列を持つ、フェッチされたリソースのものを用いる （フェッチされたリソースを クロスオリジンストレージに保存するを参照）。これはリソースのサーバーからの応答であり、 そのサーバーは、 Document がそのリソースを読み込む際の、その文書のサーバーと同じである必要はない。

宣言された リストについては、 共通部分を上限との間で求める（ COS スコープ上限を 適用するを参照）。したがって、上限は宣言の範囲を狭めることしかできない。

注： このヘッダーは、バイト列を 提供する側による認可である。ヘッダーで指定されるオリジン、すなわち最終的な読み取り元には、 問い合わせは行われず、それらから何かが送信されることもない。列挙されたオリジンが関与するのは後になってからであり、 requestFileHandle() を COS ハッシュに対して呼び出すことで、ほかの読み取り元と 同様に関与する。これは、Access-Control-Allow-Origin [FETCH] とは 逆方向に作用する。そちらでは、リソースを保持するサーバーが、指定されたオリジンによる読み取りを許可する。ここでは、バイト列の提供元が、 後でクロスオリジンストレージからそれを読み取れる主体の範囲を制限する。書き込みを行うページに注入されたコンテンツは、 提供元の応答ヘッダーを設定できないため、その範囲を拡張できない。

注： このヘッダーは リスト形式にのみ適用される。 既定の同一サイトの形式では、クロスオリジンの 受信先を指定しないので認可は不要である。また、"*" 形式は、読み取り処理で 利用可能性のゲーティングを 公開ハッシュリストに照らして行うことで制御される。 ユーザーごとの秘密情報はこのゲーティングを決して通過できないので、この形式にも書き込み時の上限は不要である。 "*" にヘッダーを要求しても、公開ハッシュリストですでに防いでいるもの以上は防げず、 設定不要のグローバル共有を壊すことにもなる。

COS スコープ上限を 解析するには、ヘッダー リスト headers を受け取り、集合を返す。その要素は オリジンであり、次の手順を実行する：

  1. value を、取得、復号、分割を "Cross-Origin-Storage-Allow-Origin" に対して headers から行った結果とする。

  2. value が null なら、空の 集合を返す。

  3. ceiling を、空の 集合とする。

  4. 各 token（value の要素）について：

    1. 先頭と末尾の ASCII 空白を除去する処理を token に対して行う。

    2. token が空文字列なら、次の反復へ進む。

    3. origin は、オリジンを表すものとし、基本 URL パーサーを token に対して実行した結果から得る。

    4. origin が失敗、または 不透明なオリジンであるなら、空の 集合を返す。

      注： これには、 token が "*" の場合も含まれる。これはオリジンとして解析されない。 Cross-Origin-Storage-Allow-Origin ヘッダーで列挙できるのは、具体的な オリジンの 有限集合だけである。"*" は許可される値ではない。上限を「任意のオリジン」とすると、 注入されたコンテンツが 好きな受信先を宣言できるようになり、ヘッダーの目的そのものが 損なわれるためである。 範囲を制限しない 開示は、"*" という origins 形式でのみ実現される。この形式では、 ゲーティングが 公開ハッシュリストによって行われ、この ヘッダーは一切参照されない。不正な形式のヘッダーや "*" を含むヘッダーは、 ヘッダーが存在しない場合とまったく同様に何も認可しない。失敗時には拒否する側に倒す。

    5. 追加する：origin を ceiling に。

  5. ceiling を返す。

注： 取得、復号、分割では U+002C (,) で分割するため、 ヘッダー値に含まれる オリジンはコンマで区切られる。これは Timing-Allow-Origin [RESOURCE-TIMING] および リストを値とする HTTP 応答ヘッダーの一般的な慣例に合わせたものである。一方、対応する crossoriginstorage HTML コンテンツ 属性は、ホスト言語の構文に合わせて空白で区切られる。いずれも同じ オリジンの 集合に解決される。

グローバルオブジェクト globalを与えて COS スコープ上限を取得するには、オリジンの集合を返します：

  1. globalが Window オブジェクトの場合：

    1. documentを globalの関連付けられた Documentとします。

    2. documentが null の場合、空の集合を返します。

    3. documentのCOS スコープ上限を返します。

  2. globalが WorkerGlobalScope オブジェクトの場合：

    1. ownersを globalの所有者集合とします。

    2. ownersが空 である場合、空の集合を返します。

    3. ceilingを null とします。

    4. ownersの各 ownerについて反復します：

      1. ownerCeilingを空の集合とします。

      2. ownerが Document の場合、ownerCeilingを ownerの COS スコープ上限に設定します。

      3. それ以外で、ownerが WorkerGlobalScope オブジェクトの場合、ownerCeilingを ownerを与えてCOS スコープ上限を取得する処理を 実行した結果に設定します。

      4. ceilingが null の場合は ceilingを ownerCeilingに設定し、 それ以外の場合は ceilingを ceilingと ownerCeilingの積集合に設定します。

    5. ceilingを返します。

  3. 空の集合を返します。

リスト状のオリジン requestedOriginsと、 集合状の オリジン ceilingを与えて COS スコープ上限を適用するには、リスト状のオリジンまたは null を返します：

  1. ceilingが含まない各オリジンを requestedOriginsから削除します。

    注: COS スコープ 上限に存在しない受信者は削除されますが、書き込みは引き続き 成功します。これはリソース可視性をアップグレードする処理で 長さ超過分を削除する方法と一致します。ユーザーエージェントは、 削除された各オリジンを示すコンソール警告を記録することが想定されています。

  2. requestedOriginsが空 である場合、null を返します。

    注: メンバーがすべて削除されたリストでは、 書き込みに認可済みの クロスオリジン受信者が残らないため、同一サイトのデフォルトにフォールバックします。バイト列は引き続き 保存され、認可されていない開示だけが差し控えられます。

  3. requestedOriginsを返します。

すべてのDocument にはCOS スコープ上限があります。これはオリジンの集合であり、 document の作成時に、それを作成するために使用されたresponseの ヘッダーリストを与えてCOS スコープ上限を解析する 処理を実行した結果に設定されます。

注: worker の所有者集合全体で積集合を取ることは、 Cross-Origin Storage 権限を確認する処理を反映しています。 オリジンが worker の上限に含まれるのは、推移的にすべての所有元 Document がそれを認可した場合だけです。blob: worker は作成元ページの オリジンと Cross-Origin Storage ビューを完全に共有するため （§ 3 CrossOriginStorageManager インターフェイスを参照）、 worker 自身だけを参照する上限は すべての worker で空になり、リストスコープの書き込みを new Worker(URL.createObjectURL(&hellip;))に移動すると、ページが認可した受信者が削除されてしまいます。 所有者の上限の積集合を取ることで、いずれか 1 つの 所有者に拡張を許すことなく、その認可を維持できます。

Documentの COS スコープ上限をそのresponseから 設定するには、 [HTML]の document 作成ステップにフックが必要です。これは、[permissions-policy]および[CSP]が response 処理時に設定される方法と同様です。そのフックが存在するまでは、この節で必要な 動作を直接説明します。将来の改訂では、§ 3.3 ファイルの作成と書き込みで言及した[FS]フックとともに 正式に統合される予定です。ホスト統合にはそのような フックは不要です。取得したresponseを取得したリソースを Cross-Origin Storage に保存する処理に渡し、 その処理が response から上限を読み取ります。

8. プライバシーとセキュリティに関する考慮事項

この節は、RFC 2119 キーワードを使用する箇所を除き、非規範的である。リポジトリー内の セキュリティとプライバシーに関する質問票も 参照のこと。

8.1. リソースの完全性

すべての COS エントリーは暗号学的ハッシュをキーとし、その バイト列はそのハッシュに照らして検証される（ § 3.3 ファイルの作成と書き込みを参照）。したがって、サイトは、 次の方法で取得したファイルについて、 requestFileHandle() を通じて得たバイト列が、 hash 自体をフェッチして得られるものと完全に同じであると確信できる。開発者は、クロスオリジンストレージの内容を列挙することも、 ハッシュをあらかじめ知らずにファイルへアクセスすることもできない。

COS ハッシュは秘密情報ではない。これは コンテンツ識別子であり、すでにファイルを持っている者なら誰でも 簡単に計算できる。本仕様が対象とする、広く配布される種類の リソースでは、ハッシュは一般に公開情報であり、モデルやライブラリーの リリースに合わせて公開されることも多い。したがって、ハッシュを知っていればエントリーを検索するには十分だが、それ自体でアクセスが許可される わけではない。検索が成功するかどうかは、全面的に origins と § 8.4 利用可能性のゲーティングによって決まる。開発者は、未公開のハッシュを アクセス制御の仕組みとして扱ってはならない。 特定のファイルを狙う攻撃者は、そのハッシュを推測する必要はなく、ファイル 自体を入手するだけでよい（§ 8.2 クロスサイトの探査を参照）。

8.2. クロスサイトの探査

あるリソースが限られたサイト群でしか使用されていない場合、攻撃者は、そのリソースが クロスオリジンストレージに存在すると知ることで、ユーザーがそれらのサイトのいずれかを訪問した可能性が高いと推測できる。 requestFileHandle() は存在を知るための仕組みなので、それぞれの呼び出しは 実質的に探査である。本仕様の二つの独立した仕組みが、探査によって 知り得る情報を制限する：

  • origins（ § 3.5 リソースの可視性の引き上げを参照）により、保存元 オリジンは、 選択したオリジンの集合に開示先を制限できる。そのため、独自のリソースや利用者の少ないリソースを グローバルに探査可能にする必要はまったくない。

  • § 8.4 利用可能性のゲーティングはさらに、 "*" をスコープとするリソースについて、 その 保存元オリジンに含まれない要求元オリジンへの開示を、ハッシュが PHL に登録されている場合に限る。 したがって、origins: "*" で保存されたリソースが、 自動的にウェブ上のすべてのオリジンから探査可能になるわけではない。このゲーティングは、 "*" をスコープとする エントリーにのみ適用される。リストまたは同一サイトをスコープとするエントリーでは、最初の箇条書き項目の制限が唯一の ゲーティングとなる。これらについては、保存元オリジンがすでに開示範囲を明示的に制限しているためである。

最初の箇条書き項目が成り立つのは、「選択したオリジンの集合」がウェブ全体よりも実質的に小さい範囲にとどまる場合だけである。 origins の形式そのものには、呼び出し元が 非常に多数のオリジンを列挙すること（たとえば、公開された 人気サイトランキングから作成したリスト）を防ぐものはない。そのようなリストは、実質的にグローバルな開示に近い働きをしながら、 "*" だけが要求する、意図的かつ明示的なオプトインを回避することになる。オリジンリストの 最大長（ § 5.1 ストレージの制限を参照）は、これを制限する。実際に必要となる 複数サイトの利用例 （共通の管理下にある少数の関連オリジン）を収める程度に小さく、しかも 「すべてのオリジン」に実質的に近づくには遠く及ばない上限を設けることで、オリジンを制限する形式の origins が、 "*" の未宣言の代替手段として使われるのを防ぐ。

ユーザーエージェントはさらに、単一のオリジンから繰り返される requestFileHandle() 呼び出しにレート制限やその他の抑制を適用すべきである。また、 デバイス上のヒューリスティック（たとえば、ユーザーごとに生成されているように見えるハッシュへの 要求パターンの検出）を適用し、探査の試みを識別して阻止してよい。これは、探査対象の ハッシュが PHL に登録されているかどうかとは無関係である。

§ 9 他の仕様との統合にあるホスト側の統合のいずれかによって行われる検索も、 ページにエラーを示さないとしても、同様に探査である。サイトは、 自身のサーバーがフォールバック要求を受信したかどうかを観測でき、それによって、ここでの「見つからない」という 結果と同じ 1 ビットの情報を得られる。このような検索が、本仕様のゲーティングでは開示されない情報を開示することはなく、 同じゲーティングがそのまま適用される。ただし、レート制限が有効に働くのは、これらの 経路からの検索が、requestFileHandle() 呼び出しと合わせて数えられる場合に限られる。 スクリプトから操作できる統合でも、ループ内で同じように容易に検索を発行できるためである。

8.3. 進行中の書き込み

要求されたがまだ完了していない書き込みは、どのオリジンからも、一度も書き込まれたことのない ハッシュと区別できてはならない。本仕様は、これを構造的に実現する。 COS エントリーが COS レジストリーに追加されるのは、検証して保存する手順、または フェッチされたリソースをクロスオリジンストレージに 保存する手順による場合だけであり、いずれの場合も、バイト列全体が ハッシュに照らして検証された後に限られる。作成要求を完了する手順は、 レジストリーの読み取りも書き込みも行わない。 したがって、読み取りで観測できるプレースホルダー状態はなく、読み取り処理には、 応答を 利用可能性のゲーティングを適用する手順より先に返せる分岐もない。

これに対して、作成要求時にプレースホルダーを登録し、それに対する同時の 読み取りを区別可能なエラーで拒否すると、呼び出し元は、何らかのオリジンが 指定されたハッシュを書き込んでいる最中であると知ることができる。この 1 ビットは些細に思えるが、そうではない。この情報は次のように取得可能になる：

  • そのエントリーについて何の許可も持たないオリジンを含め、任意のオリジンから取得できる。プレースホルダーには 許可が付与されておらず、読み取りへの応答が COS の 開示を決定する手順の実行前に返されるためである。

  • 任意のハッシュについて取得できる。PHL に登録されているものではなく、今後も登録され得ないハッシュも含まれるので、攻撃者は ユーザーごとの値から導出したハッシュを使用できる。これは、まさに § 8.6 フィンガープリンティングが 検出しようとしているパターンである。

  • GREASE の適用なしに取得できる。これは、ゲーティングの ステップに到達した開示にのみ適用されるため、 このビットにはノイズが加わらない。

  • バイト列を一切提供せずに取得できるので、オリジンごとのストレージ上限 も、 § 5.2 追い出しも、一つのオリジンがこのようなビットをいくつ作成できるかを制限しない。

したがって、二つのサイトに埋め込まれたトラッカーは、最初のサイトで任意のビット幅の識別子を生成し、 二つ目のサイトでそれを読み取ることができる。ストレージのコストはかからず、origins、 公開ハッシュ リスト、GREASE の適用をまとめて回避する。プレースホルダーは、サービス拒否 攻撃の手段にもなる。実際に広く利用されているリソースのハッシュを占有すると、プレースホルダーが存在する間、 ほかのすべてのオリジンによるそのリソースの読み取りを阻止できる。

注： この方式の代償として、ある呼び出し元が、 別の呼び出し元による大きなファイルのダウンロードがすでに進行中であると知り、 重複するダウンロードの開始を避けることはできなくなる。これは実際のコストであり、 本仕様の以前の草案が、ここで区別可能なエラーを使用していた理由でもある。ただし、 最も重要な単一オリジン内では、この機能を回復できる。 Web Locks、BroadcastChannel、 または共有ワーカーを使用すればよく、 これらはいずれも、 オリジンの境界を越えて情報を開示しない。オリジン間での節約は、大部分が理論上のものにとどまる。無関係な二つの オリジンが、同じハッシュについて同じ瞬間に競合する必要があり、どちらもまだ書き込んでいない エントリーは、いずれにせよ PHL に登録されている状態になるまで、他方に開示できないためである。

注： "NotAllowedError" は、引き続き getFile() を、 作成によって取得した、まだ書き込みを行っていないハンドルに対して呼び出した場合の応答となる（§ 4 クロスオリジンストレージファイルシステムを参照）。この応答は、 レジストリーの状態によらず一定であり、要求を行ったオリジンにしか届かない。 ハンドルはクロスオリジンで逆シリアル化できないためである（§ 4.1 ハンドルの 転送を参照）。したがって、これは情報伝達経路にはならない。

8.4. 利用可能性のゲーティング

requestFileHandle() による読み取りが、 保存元 オリジンに含まれないオリジンから行われる場合、その成否は常に、要求元オリジンがエントリーの読み取りを 許可されているかどうかに依存し、この許可は origins によって決まる。"*" をスコープとするエントリーには、二つ目の 独立した条件も適用される。それは、ユーザーエージェントがエントリーがそもそも 存在することを開示する意思があるかどうかであり、PHL に 登録されていることと GREASE の適用によって決まる。このようなエントリーでは、 両方の条件を満たさなければならない。リストまたは同一サイトをスコープとするエントリーには、最初の条件だけが適用される。 規範的なアルゴリズムについては、§ 3.2 ファイルの読み取りを参照。したがって、"NotFoundError" は、 リソースが存在しない証拠ではない。リソースが存在しないこと、要求元の オリジンがスコープ外であること、"*" をスコープとするリソースのハッシュが（まだ、または今後も）PHL に登録されていないこと、あるいは GREASE の適用によって真陽性が抑制されたことを意味する場合がある。開発者は、"NotFoundError" を、 「ネットワークにフォールバックする」以上に具体的な意味を持つものとして扱ってはならない。

注： サードパーティー Cookie をサポートするユーザーエージェントでは、 "*" による許可があっても、トラッカーが サイトをまたぐユーザーの訪問を関連付ける能力は、サードパーティー Cookie ですでに可能な範囲を超えない。PHL だけでは、 これを制限できない。攻撃者は、個々には PHL への登録条件を満たすリソースから、どの部分集合を書き込むかを選ぶことで、クロスサイトの識別子を構成できる。サードパーティー Cookie をブロックするユーザーエージェントでも、クロスサイトの開示を制限すれば、"*" による許可を提供できる。たとえば、 トップレベルサイトをキーとし、ページ内のすべてのフレームで共有される、クロスサイト検索の 小さな許容回数を設け、一定の時間枠内では再読み込み後も回数を保持し、書き込まれたエントリーの共有を ユーザー操作後に限る方法がある。README の プライバシーに関する考慮事項では、これらの緩和策を説明している。

8.5. GREASE の適用

ユーザーエージェントは、GREASE の適用（ランダムな拡張を生成し、 拡張性を維持する）を行ってよい。これは、 開示可能なエントリーについて、§ 8.4 利用可能性のゲーティングによれば 本来は 開示が許可される場合でも、ときどき存在しないかのように応答することである。これによりノイズが加わり、サイトは、実際の不在と プライバシー保護を目的とした偽陰性とを区別しにくくなる。これは、 UA クライアント ヒントで適用されている手法に似ている。

GREASE の適用対象は、グローバルに 開示可能 という許可だけによって条件を満たすオリジンに限られる。これは、公開ハッシュリストがゲーティングする場合と同じである（COS の開示を決定するを参照）。 ユーザーエージェントは、これを 保存元オリジン、それらと 同一 サイトのオリジン、 または明示的な origins リストに含まれるオリジンに適用してはならない。

GREASE を適用するユーザーエージェントは、対象となるエントリーのサイズに 見合った判断に基づいて行わなければならない。ネットワークからのフェッチへのフォールバックが低コストで済む小さなエントリーでは、ときどき生じる 偽陰性は、プライバシーとの合理的なトレードオフとなる。ユーザーエージェントは、不要な再ダウンロードの負担が、得られるプライバシー上の利益に対して 明らかに不釣り合いになるサイズのエントリー （たとえば、ギガバイト規模の AI モデルの重み）に GREASE を適用してはならない。その場合の偽陰性は、全体の 再ダウンロードを強いることになり、それは観測可能で、コストも高いためである。

8.6. フィンガープリンティング

攻撃者がクロスオリジンストレージを探査して抽出できる情報は、探査対象の リソースがどれほど広く利用されているかによって制限される。一般的な AI モデルや 広く使用される JavaScript ライブラリーなど、非常に広く利用されているリソースをユーザーが持っていると知っても、そのリソースを使用する （場合によっては非常に多数の）サイトのいずれかを訪問したことしか分からない。珍しい、または一意のリソースを持っていると知ることは、はるかに多くの情報をもたらす。 ユーザーエージェントには、デバイス上のヒューリスティックを適用し、ハッシュがユーザーごとに意図的に 一意にされているように見えるリソース（たとえば、一つのサイトからしか書き込まれたことのない ハッシュや、異常な頻度で要求されるハッシュ）を検出し、そのようなパターンを探査の試みとして扱うことが期待される。 これは、形式上の PHL 登録状況とは無関係である。

9. 他の仕様との統合

この節は非規範的である。

ここで定義する COS レジストリーには、 四つのホスト側の統合からも、 requestFileHandle() を直接経由せずにアクセスできる。それぞれの 統合は、対応するホスト仕様で定義される。本仕様は、共通の 基礎概念（COS ハッシュ、COS エントリー、利用可能性のゲーティング、 公開ハッシュ リスト）と、フェッチされたリソースをクロスオリジンストレージに 保存するステップを 定義する。これらの統合は、これらを基礎として構築されることが想定されている。

  • HTML：crossoriginstorage 属性を、 link および script 要素のうち、すでに integrity [SRI] を持つものに追加する。WHATWG への提案は、 whatwg/html#12770 にある。

  • JavaScript：ホスト定義の crossOriginStorage インポート属性。 これは、 integrity と併用でき、インポート属性 提案に基づく。WHATWG への提案は、 whatwg/html#12771 にある。

  • CSS：cross-origin-storage() という <request-url-modifier>。 integrity() と併用できる。 CSS ワーキンググループへの提案は、 w3c/csswg-drafts#14056 にある。

  • Fetch：crossOriginStorage という RequestInit オプションであり、 integrity [FETCH] と併用できる。 WHATWG への提案は、 whatwg/fetch#1954 にある。 これにはホスト定義の宛先がないため、 Response が COS レジストリーから提供される場合、その MIME 型、ステータス、その他のメタデータをどのように 報告するかは、その仕様での未解決の課題である。COS エントリーが保存するのは bytes だけである。

説明のためだけの例として、同じグローバルに共有されるリソースについて、四つの形式それぞれで クロスオリジンストレージの利用を明示的に選択する方法を示す：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

これらのコード片は説明のための例にすぎない。これらの構文はいずれも、本仕様では定義しない。 制限されたオリジンのリストの記述方法を含め、各形式の正式な文法は、 それぞれのホスト仕様に属する。記述形式は意図的に 異なる。RequestInit メンバーは sequence<DOMString> を受け取ることができ、これは origins と完全に一致する。一方、属性値、 インポート属性値、CSS 修飾子の引数には、テキストしか指定できない。

四つの形式はすべて、まず COS レジストリーを参照して、一致する開示可能なエントリーを探し、 その後にネットワークからのフェッチへフォールバックする処理モデルと、 フェッチに成功し、完全性が検証されたリソースを COS レジストリーに保存して、ほかのオリジンによる 再利用を可能にする処理モデルを共有することが想定されている。これは、requestFileHandle() とまったく同じである。保存ステップは、 フェッチされたリソースをクロスオリジンストレージに 保存する手順であり、それぞれの統合が、 フェッチされた 応答を用いて実行する。したがって、制限されたオリジンを指定する値は、 そのリソースの応答にある Cross-Origin-Storage-Allow-Origin ヘッダーによって制限される。このヘッダーは、 バイト列を提供するサーバーが送信する（§ 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照）。これらの統合に関する 議論は、それを取り込むホスト仕様の課題トラッカーで行うものであり、 このリポジトリーの課題トラッカーで行うものではない。
