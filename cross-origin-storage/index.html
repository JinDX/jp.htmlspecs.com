概要

オリジン間ストレージ（COS）は、Web アプリケーションが AI モデル、WebAssembly モジュール、非常に普及している JavaScript ライブラリなどの 大容量ファイルを異なるオリジン間で保存および取得できる、コンテンツアドレス可能なキャッシュです。ファイルは URL ではなく暗号学的ハッシュによって識別されるため、あるオリジンによって一度取得された バイト単位で同一のリソースは、ユーザーエージェントが許可する他の任意のオリジンによって、再度ダウンロードすることなく再利用できます。キャッシュ内の存在を、ユーザーがどのサイトを訪問したかの推測に利用できないようにするため、 ファイルのオリジン間開示は、k-匿名性方式の人気度基準を満たすハッシュに限定されます。

1. はじめに

この節は非規範的である。

ストレージは通常、ユーザーのセキュリティとプライバシーを保護するため、オリジンごとに分割される。これは適切な 既定の動作だが、非常に大きく、広く普及し、公開配布される限られた種類の リソース（AI モデル、WebAssembly モジュール、JavaScript ライブラリー、ゲームエンジン、大きなウェブフォント）には適さない。 これらは、どのサイトが要求したかにかかわらず、バイト単位で同じファイルである。2 つの 無関係なオリジンがそれぞれ同じ 8 GB のモデルに依存する場合、オリジンごとに分割されたストレージでは、 ユーザーはそのモデルを 2 回ダウンロードして保持する必要があり、ユーザーの帯域幅、ストレージ、 バッテリー、およびネットワーク全体にとって無駄となる。

クロスオリジンストレージ (COS) は コンテンツアドレス可能 なキャッシュであり、暗号学的ハッシュをキーとして使用する。 URL をキーとする代わりに、ユーザーエージェントがそのようなリソースの単一の保存済みコピーを、 使用を選択したオリジン間で共有できる。COS へのリソースの保存は、常に明示的なオプトインによる行為として 保存元オリジンが行い、ユーザーエージェントは、リソースの存在の確認を、オリジンに対して差し控えてもよい。 そのオリジンに読み取りが許可されるはずの場合でも同様である。§ 8 プライバシー およびセキュリティに関する考慮事項を参照。

この仕様のエントリーポイントは、次の getFileHandle() メソッドであり、次を通して公開される crossOriginStorage: 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.getFileHandle(hash);
  const file = await handle.getFile();
  // ファイルを使って何らかの処理を行う。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // クロスオリジンストレージに（開示可能な形では）存在しないため、代わりにネットワークから取得する。
  }
}

この仕様は、次の FileSystemFileHandle, FileSystemWritableFileStream, および関連する 基盤を、ファイルシステム標準 [FS] から再利用し、その適用範囲を専用のファイルシステムに限定する。 このファイルシステムはオリジン間で共有され、各オリジンの非公開またはユーザーに見えるファイルシステムとは分離される。

この仕様は、命令的な JavaScript API に加え、ホスト側の 統合が基礎とする共有の保存手順を定義する。関連する提案では、同じ基盤となるキャッシュを他のホスト 仕様に統合する。すなわち、HTML の crossoriginstorage 属性を link および scriptに、 また、 crossOriginStorage JavaScript インポート属性、CSS の cross-origin-storage() <request-url-modifier>、および crossOriginStorage RequestInit オプションを fetch() に導入する。それぞれは 個別のホスト仕様で定義される。§ 9 統合： 他の仕様との統合を参照。

2. 概念

2.1. ハッシュ

COS ハッシュ は 構造体 であり、 次の 項目を持つ。

アルゴリズム

文字列 であり、[WEBCRYPTO] が認識する "SHA-1" 以外のハッシュアルゴリズムを指定する。たとえば "SHA-256" である。

値

文字列 であり、次によって生成されたダイジェストの小文字の 16 進符号化である。 アルゴリズム。 "SHA-256" の場合、長さは 64 文字である。

この algorithm 辞書メンバーの型は単純な DOMString であるが、その値空間は、次が受け入れる名前の集合と厳密に一致する [WEBCRYPTO] の ハッシュアルゴリズム。HashAlgorithmIdentifier は (object or DOMString) であり、その object 分岐は、 次によって正規化される [WEBCRYPTO]。その結果は Algorithm 形式の 辞書となり、呼び出し元は追加の パラメーターを必要とするアルゴリズムに渡せる（たとえば {name: "HMAC", hash: "SHA-256"}）。ハッシュ アルゴリズムはそのようなパラメーターを取らず、 アルゴリズム は保存され、 比較され、往復処理される。その一部となるのは コンテンツアドレス可能 なキーであり、この仕様の 例では常に単純な文字列として使用される。ここで任意のオブジェクトを許可しても機能は増えず、 等価性 と直列化を 不必要に複雑にする。したがって DOMString が、 このフィールドにはより限定的で正確な型である。

2 つの COS ハッシュ 値が 等しい のは、それぞれの アルゴリズム の値が ASCII 大文字小文字を区別せず 一致し、それぞれの 値 が厳密に 等しい場合である。

注: 値 はすでに規範的に小文字と定められているため（上記参照）、その比較は 単純な 文字列比較となる。アルゴリズム には規範的な大文字小文字の指定がないため、比較は ASCII 大文字小文字を区別せず行う。

コンテンツアドレス可能 なストアとは、エントリーのキーが、 等価性 によって決まるものである。その対象は COS ハッシュであり、2 つのファイルの バイト列とハッシュアルゴリズムが同じなら、いくつのオリジンが 保存したか、いくつの URL から取得されたかにかかわらず、同じエントリーとなる。

2.3. 公開ハッシュリスト

ハッシュがクロスオリジンストレージに存在することを確認する行為自体が、 ユーザーの閲覧履歴に関する情報を漏らす可能性がある（§ 8.2 クロスサイトの探索を参照）。これは グローバルな 許可に固有のリスクである。エントリーの明示的な オリジン群 の リスト と、各エントリーが持つ同一サイトの基本的な 許可では、 保存元オリジンの明示的な選択によって、開示の範囲がすでに限定されている。一方、 エントリーを グローバルに開示可能 にすると、任意の ウェブ上のオリジンに公開される可能性がある。この 固有のリスクを制限するため、グローバルに開示可能 なリソースを開示できるのは、 その 許可を通じて、次に含まれないオリジンに対しての場合である 保存元オリジン。ただし、そのハッシュは追加の、 独立した条件を満たす必要がある。それは、次のリストに含まれることである 公開ハッシュリスト (PHL)。これはベンダーに中立で、実装定義 の許可リストであり、COS ハッシュ 値を格納する。ハッシュが公開ハッシュリストに登録されるのは、k-匿名性に似た 普及度の基準を満たした後に限られる（たとえば、ある最小数以上の独立した オリジンに、バイト単位で同じものが存在すること）。これにより、共有キャッシュに存在することを確認しても、 個々のユーザーについての情報を得られないようにする。

COS ハッシュ hash が 公開 ハッシュリストに含まれる のは、hash が 等しい 場合である。その比較対象は、ユーザー エージェントの現在のスナップショット内のエントリーであり、そのスナップショットの対象は 公開ハッシュリストである。

取得プロトコル、 更新頻度、データ形式、普及度の閾値、および管理体制については、 公開ハッシュリストをこの仕様に付随する成果物として詳細に設計している。 これは、公開接尾辞リストが付随データファイルとして [URL] 標準に付属することに倣ったものである。この 公開ハッシュリストの解説を本リポジトリーで参照されたい。この設計は、 WHATWG による管理を提案しており、公開接尾辞リストのベンダー横断的な、 ローリングリリースの先例を模範とし、独立に裏付けられた広範な普及を登録基準とする。 これは、上記の k-匿名性に似た基準を具体化したものであり、オフラインで一度だけ適用する。 その適用はハッシュの登録手続きの一部であり、ユーザーエージェントが問い合わせごとに繰り返すことはない。これらはいずれも、 この提案の外ではまだ確立されていない。リスト自体の初期の非規範的なコード試作は、 現在のところ本リポジトリー内の次の場所にある。 public-hash-list/implementation/。専用の、 ベンダー横断的なリポジトリーは、PHL の解説に記述する管理体制上の目標のままである。この 仕様が依存するのは、ハッシュが PHL に含まれる かどうかだけであるため、 リストの取得機構、管理モデル、その他の設計がどのように発展しても、その正しさは保たれる。

3. この CrossOriginStorageManager インターフェース

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> getFileHandle(
      CrossOriginStorageGetFileHandleHash hash,
      optional CrossOriginStorageGetFileHandleOptions options = {});
};

dictionary CrossOriginStorageGetFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageGetFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

各 Navigator および WorkerNavigator オブジェクトは、関連付けられた CrossOriginStorageManager オブジェクトを持つ。crossOriginStorage の取得子の 手順は、 次を返すことである。this に関連付けられた CrossOriginStorageManager。

各 CrossOriginStorageManager オブジェクトは、関連付けられた オリジン を持ち、その設定値は、 this の 関連する設定群オブジェクトの オリジンであり、オブジェクトが 作成された時点で設定される。

注: オリジンを次から取得することには、関連する設定群オブジェクトを、スクリプト自体のあらゆる情報とは独立に使うため、 ワーカーについて明記すべき帰結がある。 blob: URL から作成されたワーカーは、次の オリジン を持つ。それは、ワーカーを作成したコンテキストのものである。そのため、そのオリジンの クロスオリジンストレージの見え方を完全に共有する。そのようなワーカーが書き込んだものは作成元のページが読み取れ、 ページが保存したものはワーカーが読み取れる。blob: URL 自体は独立したオリジンではなく、 その取り消しによってワーカーがその見え方から切り離されることはない。data: URL から作成されたワーカーは、 次の 不透明なオリジンを持つ。この仕様は、現在のところ、次の動作を定義していない。 getFileHandle() の、呼び出し元のオリジンが不透明である場合の動作である。 次にあるオリジンの規則は、COS 要求を検証するにおいて、 呼び出し元が指定するオリジンのみを対象とする。不透明なオリジンには、キーとして使用する安定した識別情報がない。 保存元 オリジンのキー、または 同一 サイトの比較に使用できないため、意味のある 許可を与えることができない。

3.1. この getFileHandle() メソッド

handle = await navigator . crossOriginStorage . getFileHandle(hash)

      注: 公開ハッシュリストによる制御が 適用されるのは、グローバルな許可だけである。これは、 その制御がなければ開示がウェブ上の任意のオリジンに及び得る唯一の場合である。エントリーが グローバルに開示可能 であっても、その ハッシュ が 次の PHL に含まれるものでなければ、 この許可だけによって資格を得るオリジンには開示されない。そのオリジンが、さらに 次にも含まれる 場合、保存元オリジン、明示的な オリジン群 の リスト、または そのいずれかと同一サイトの集合に含まれるなら、上記ですでに返されている。

    2. ユーザーエージェントがこの要求への GREASE の適用 を選択する場合、 null を返す。

      注: GREASE の適用も、 グローバルな許可だけを対象とする。上記で検査された許可は、決して この手順に到達しない。保存元オリジンとそれらの同一サイトのオリジンは 1 つの信頼単位であり、 明示的な オリジン群 の リストにあるオリジンは、 書き込み元が意図的に指定したものであり、その書き込み元の Cross-Origin-Storage-Allow-Origin ヘッダーがそれを許可している。その許可は、 同一サイトのオリジンにも 及ぶ。

  6. null を返す。

適用する： 可用性の制御 には、COS エントリー または null である entry、および オリジン origin を与え、COS エントリーまたは null を返す。

  1. 次を実行した結果を返す。COS の開示を決定するに、entry および originを与える。

3.3. ファイルの作成と書き込み

FileSystemFileHandle が、次によって作成された場合、作成要求を完了するによるそのハンドルには、関連付けられた 要求されたオリジン群がある。これは、検証して保存するが、 エントリーの対象範囲を 拡大 しようとする際の値であり、その対象は オリジン群である。適用は、 ハンドルを通じた書き込みが正常に完了した後に行われる。

すべての FileSystemFileHandle で、次を指すもの、クロスオリジンストレージのファイルシステムを指すものは、さらに 関連付けられた COS ハッシュを持つ。これは、COS ハッシュであり、そのハンドルが指すものである。また、 関連付けられた COS オリジンも持つ。これは、オリジンであり、そのハンドルを取得したものである。さらに、 関連付けられた 読み取り可能という真偽値を持ち、これは次を制御する。 getFile() が、指し示すエントリーのバイト列を、その特定の ハンドルを通して開示してよいかどうかである。これは、次が返したハンドルでは true となる 読み取り要求を完了する。このハンドルは、すでに 可用性の制御を通過している。一方、次が返したハンドルでは false となる。 作成 要求を完了する。その状態は、検証して保存するが、まさにそのハンドルについて成功するまで続く。

3.5. リソースの可視性の拡大

COS エントリー の可視性は、 拡大できるが、縮小することはできない。

拡大する： リソースの可視性 には、COS エントリー entry および、"*"、リストで、その要素が オリジンであるもの、または null である requestedOriginsを与え、次を行う。

  1. requestedOrigins が null の場合、戻る。

    注: 次を省略すると、origins 要求するのは同一サイトでの 可用性だけとなる。すべてのエントリーはすでにそれを持つため（次を参照 COS の 開示を決定する）、 追加するものはない。

  2. requestedOrigins が "*" の場合、次を行う。

    1. entry の グローバルに開示可能 を true に設定する。

    2. 戻る。

    注: これはグローバルな許可を追加する。 entry の オリジン群は変更しない。エントリーが、 すでに明示的な オリジン群 の リストを持っていた場合は保持されるため、すべての オリジンで、 その リストに含まれるものは、PHLに依存しないアクセスを保持する。エントリーが、 グローバルに開示可能となった後でも同様である。これが、 2 つの許可を 別々に保存する核心的な理由である。グローバルに開示可能を参照。

  3. 各 candidateOrigin について、対象を requestedOriginsとして、次を行う。

    1. entry の オリジン群 が、含む場合、その対象が candidateOrigin なら、 継続する。

    2. entry の オリジン群の サイズ が、ユーザーエージェントの オリジンリストの最大長と等しい場合、 反復を抜ける。

      注: 残りのすべての candidateOrigin 値は、この拡大処理から通知なく除外される。 書き込み自体はすでに成功しているためであり、ユーザーエージェントは、コンソールに エントリーのオリジンリストが上限に達しているという警告を記録することが期待される。

    3. 追加する。candidateOrigin を、 entry の オリジン群に追加する。

注: 拡大処理では、次への追加のみを行う オリジン群。または、次を設定する グローバルに開示可能。 その設定値は true である。書き込み元が リスト を要求すると、すでに グローバルに開示可能 なエントリーについても、そうでないエントリーと同様に、 許可を拡大する。2 つの許可は 独立しているためである。新たに列挙されたオリジンは、PHLに依存しないアクセスを取得する。その間も、 "*" の許可は有効なままである。

注: 元の保存元以外を含む、任意のサイトが、 エントリーの対象範囲を拡大できる。 オリジン群を拡大するには、 そのサイトも、ハッシュがエントリーの ハッシュとなるバイト列を供給する必要がある。これは意図的な動作である。 あるハッシュに対する正しいバイト列をすでに持つサイトは、設計上、そのハッシュが何を指すかについて、 元の保存元と同等の権威を持つためである。

オリジン が、正常に完了した場合、書き込みを COS エントリーに対して完了した場合（すなわち、 任意の オリジン で、エントリーの 保存元オリジンに属するもの）は、 その後、常に取得できる。 そのエントリーのハンドルを、次によって取得できる getFileHandle()。 これは、エントリーの オリジン群 の値とは独立しており、 また、その ハッシュ が PHL に含まれるかどうかにもよらない。 これは Cache API のモデルに倣っており、オリジンは自身が保存したものに常にアクセスできる。

4. クロスオリジンストレージのファイルシステム

クロスオリジンストレージのファイルシステム は ファイルシステムルート であり、各 オリジンの バケットファイルシステム またはローカルファイルシステムへのアクセスルートとは異なる。その エントリー は、次のものと一対一に対応する COS レジストリーの COS エントリー項目である。

クロスオリジンストレージのファイルシステム は、次を使用しない [FS] の通常の呼び出しごとの 権限検査 モデルである。すべての FileSystemFileHandle で、そこから取得したものは、すでに完全に許可されている。 § 3.2 ファイルの読み取り または § 3.3 ファイルの作成と 書き込みにより、スクリプトに返される前に許可される。そのため、 getFile() または createWritable() を、そのようなハンドルに対して呼び出しても、 追加の権限確認が表示されることはない。

したがって、そのようなハンドルに対する queryPermission() および requestPermission() は、決して 報告してはならない。 "prompt" を報告してはならず、確認を表示できないためである。書き込みモードに対しては "denied" を報告しなければならない。 そのハンドルが、 作成要求 によって取得されたものでない場合にそうし、それ以外の場合は、 "granted" を報告しなければならない。

createWritable() が、次の FileSystemFileHandle に対して呼び出され、それが指す先が、 クロスオリジンストレージのファイルシステムであり、それが 次によって取得されたものでない場合、 作成要求によるものでなければ、"NotAllowedError" DOMExceptionで拒否しなければならず、 次を作成してはならない FileSystemWritableFileStream。

注: 書き込みは、ハンドルが実際に 持たないことがある機能である。作成要求だけが、 書き込みに使用できるハンドルを生成するため、他のハンドルの書き込みモードについて "granted" を報告すると、 機能があると主張してしまう。createWritable() が拒否する機能である。読み取りは、 "granted" のままであり、読み取り可能なハンドルを持つ呼び出し元は、それを通して読み取れる。要求しても、 変更できない。 いずれの応答も変更できず、表示する確認も、許可を記録できる状態も存在しないためである。

次を呼び出す場合、getFile() その対象が FileSystemFileHandle であり、指す先が、 クロスオリジンストレージのファイルシステムで、その 読み取り可能が false である場合、拒否しなければならない。 その理由は、"NotAllowedError" DOMExceptionとする。 これは、次の 2 つの異なる場合を含む。

  • 作成要求 によるハンドルで、まだ書き込みに 使用されて おらず、指し示すハッシュに対応するエントリーが、次に存在しない場合 COS レジストリー。検証済みのバイト列がないため、 返すものはなく、呼び出し元が、自身の未完了の書き込みを、 ファイルの実際の内容であるかのように観測できてはならない。

  • 別の他のオリジンがすでに書き込んだハッシュに対する、作成要求によるハンドルの場合。 検証済みの バイト列は存在するが、この呼び出し元はそれを供給しておらず、 可用性の制御を通過していないため、エントリーについて何も知ることができてはならない。 その対象には、 存在するかどうかも含まれる。

注: どちらの場合も拒否は同一であるため、 何も開示しない。このため、 "NotAllowedError" は、読み取り経路では意図的に回避しているにもかかわらず、ここでは安全である。このハンドルは、 呼び出し元自身の作成要求によって取得した自身のものであり、ハンドルは、いかなる 他のオリジンでも逆直列化できない（§ 4.1 ハンドルの転送を参照）。したがって、この応答は、 オリジンの境界を越えることがなく、 レジストリーの内容に対して一定である。これに対して、§ 8.3 進行中の書き込みでは、 読み取り経路における異なるエラーが、その境界を越えることになる。

ハンドルの 読み取り可能 が true になると、getFile() をそのハンドルに対して呼び出した結果は、File であり、その内容は、指し示すエントリーの バイト列となる。これは、 まさに [FS] が、 すでに定義する動作である。その対象は、ファイル エントリーであり、その バイナリーデータが、それらのバイト列である場合である。

FileSystemFileHandle が、次を指す場合、クロスオリジンストレージのファイルシステムを指す場合、そのハンドルは、 ファイルシステムロケーターを持つ。その パス は、リストであり、含むのは、 単一の 文字列、すなわち、その COS ハッシュの 値である。また、その ルート は、次である クロスオリジンストレージのファイルシステム。

注: [FS] は、次を定義している name。 その値は、ハンドルの ロケーターのパスの最後の構成要素であるため、これによって次も決まる name: それは、 ハッシュである。エントリーには固有の名前がなく、ハッシュだけがその識別情報であるため、 それを報告することで、空文字列では失われる情報を伝える。

エントリーには名前がなく、それを格納するディレクトリーもないため、[FS] の構造に関する機能の大部分には、 操作する対象がない。同一性は例外であり、コンテンツアドレスによるエントリーが、 常に答えられる問いである。COS レジストリー が保持するのは、最大 1 つの COS エントリーであり、各 COS ハッシュについてそうなる。したがって、2 つの ハンドルが同じエントリーを指すのは、そのハッシュが等しい場合に限る。

注: この場合に false を返すと、 2 つのハンドルが異なるエントリーを指すと主張することになる。 これは、呼び出し元オリジンに検査する権限がないハンドルについての主張である。拒否が示すのは、 比較を行えなかったことだけである。

注: エントリーは、その 保存元 オリジンにあるすべてのオリジンによって共有されるため、 削除を認めると、あるサイトが他のサイトの依存するデータを破壊できてしまう。削除は、 追い出しおよびユーザー自身のストレージ制御が担う。名前の変更や親の変更には、 操作する対象がない。エントリーは、その COS ハッシュで識別され、それを格納するディレクトリーがないためである。

5. ストレージの管理

5.1. ストレージの制限

ユーザーエージェントは、総バイト数に制限を設けなければならない。その対象は、オリジン が、次へ追加できる量である。 COS レジストリー に、成功した書き込みを通して追加できる量を制限し、 単一のオリジンが、 他のオリジンのエントリーを追い出す目的で、キャッシュを大量のデータで埋め尽くすことを防ぐ。具体的な制限は、 実装定義である。オリジンの書き込みが、その 上限を超える場合、ユーザーエージェントは、 拒否 しなければならない。 その書き込みを、"QuotaExceededError" DOMException で拒否し、警告を記録すべきである。 その記録先は、コンソールとする。

注: エントリーは、コンテンツアドレス可能 であるため、オリジンが、 同じものを繰り返し書き込んでも、 同じハッシュの下で同じバイト列を書き込む場合、最初の成功した書き込みを超える追加の割り当て量は消費しない。 § 2.2 COS エントリーを参照。

ユーザーエージェントは、さらに 実装定義 の オリジンリストの最大長を持つ。これは、 正の整数であり、いくつの オリジン を、単一の オリジン群 の リスト が、 含められるかを制限する。この制限は、リスト が最初に供給されるとき（次を参照 COS 要求を検証する）、 および、後で既存のエントリーにマージされるときの両方で適用される（次を参照 リソースの可視性を拡大する）。これにより、単一の呼び出しも、 長期間にわたる多数の呼び出しの累積効果も、エントリーの オリジン群 を、 無制限に拡大できない。メモリー使用量の制限に加え、これは、リストにあるオリジン群が、 次のものとして "*" の暗黙の代用品として使われることも防ぐ。§ 8.2 クロスサイトの探索を参照。

この上限を超えた場合の扱いは、この 2 か所で異なる。2 つの呼び出しは、 操作の中で大きく異なる時点に行われるためである。

  • 次では、COS 要求を検証するでは、いかなる ファイルの取得、ハッシュ計算、または 書き込みよりも前に上限を検査する。上限を超える呼び出し元は、直ちに "TypeError" を受け取り、それ以外には何も起こらない。 これは、他の不正な origins 値と同じ扱いである。

  • 次では、リソースの可視性を拡大するでは、上限に達するのは、 累積効果による場合だけである。 別々の独立した書き込み呼び出しで要求されたオリジンが累積し、場合によっては無関係なオリジンが、 長期間にわたって追加する。そして検査が行われるのは、この呼び出しのバイト列のハッシュ計算、 検証、および永続的な保存がすでに完了した後だけである。その時点で書き込みを拒否すると、成功し、 検証済みであり、場合によっては非常に大きな書き込みを、無関係な管理上の制限のために破棄することになり、 しかも、単一の呼び出し元の誤りに帰することすらできない。そのため、書き込みは、 成功したままとし、上限を超えたオリジンだけを、オリジン群から除外し、 コンソールに警告を出す。これは、既存の次の要求の扱いに倣う。 許容的な範囲からより限定的な範囲への要求である。オリジンの要求を、 完全には満たせない場合、通知なく上限を適用し、その要求を伴う書き込み自体は、 成功する。この仕様の他の箇所にある § 8.4 可用性の制御 と同様に、 この場合も、 呼び出し元には、要求した オリジン が、 実際に追加されたかどうかを、事後に確実に確認する方法がない。後続の getFileHandle() 呼び出しを、その オリジンとして行っても、オリジンが追加されていても失敗し得る（たとえば、エントリーが、 追い出された場合、またはユーザーエージェントが要求を制限した場合）。したがって、その結果を確認と解釈してはならない。 いずれの結果についても同様である。

5.2. 追い出し

この節は非規範的である。

ストレージが逼迫した場合、ユーザーエージェントは、エントリー を、次から追い出してもよい COS レジストリー。 たとえば、最近使用されていないものを優先する方針を、次にまたがって適用する 保存元オリジンであり、 各エントリーに最後にアクセスしたものである。ユーザーエージェントは、設定 UI を提供することが期待される。その UI を通して、 ユーザーは、保存されているファイル、各ファイルにアクセスしたオリジンを確認し、手動で、 エントリーを削除したり、クロスオリジンストレージのすべてのデータを消去したりできる。

ユーザーがオリジンのサイトデータを消去した場合、ユーザーエージェントは、そのオリジンを、 保存元 オリジンの、含まれているすべての集合から除去すべきである。その除去後、COS エントリーの、 保存元 オリジンが空になった場合、ユーザーエージェントは、そのエントリーを削除対象として検討してもよい。

5.3. 手動で追加されたエントリー

この節は非規範的である。

上記の設定 UI では、ユーザーがディスク上にすでに持つファイルを、直接追加できるようにしてもよい。 クロスオリジンストレージに追加するものであり（たとえば、ウェブサイトとは独立にダウンロードした AI モデル）、 いかなるスクリプトも、次を呼び出すことなく行える getFileHandle()。 そのようなエントリーには、 要求元の オリジン がなく、書き込みをそのオリジンに帰属させられないため、2 つの疑問が生じる。これらは、 命令的な API だけでは答えられないものである。

  • 元の保存元は誰か。その目的は、 § 3.5.1 元の保存元によるアクセスにある。誰もいない。エントリーの 保存元オリジンは、最初は空である。 したがって、いかなるオリジンも免除されない。 通常の 可用性の制御 および オリジン群 の検査であり、 それ以外のすべての要求元オリジンが従うものと同じである。これは正しい結果であり、どのオリジンも、 実際にバイト列を書き込んでいないためである。

  • そのようなエントリーを、通常の書き込みが次を省略する場合と同様に、同一サイトだけに限定すべきか。 origins を省略する場合である。そうではない。「同一サイト」が意味を持つのは、 要求元オリジンとの関係においてだけであり、手動の追加にはそれがないため、「同一サイト」が指すサイトは、 存在しない。ユーザーエージェントは、そのようなエントリーを、グローバルに 開示可能にすることが期待される。 その明示的な オリジン群 の リストは空のままとする。手動で、 ファイルをあらかじめ追加することが、 その目的（ユーザーがまだ訪れていないサイトに、ユーザーがすでに、 ディスク上に持つファイルを再利用させること）を果たすのは、他のオリジンが実際に発見できる場合だけだからである。ユーザーエージェントの設定 UI は、 さらに、ユーザーがより狭い範囲を選択できるようにしてもよい。

このように追加されたエントリーは、他の点では区別できない。 ウェブサイトが、次を通じて書き込んだものと区別できない getFileHandle(): 同じ 可用性の制御 および 可視性の 拡大の規則が適用され、同じ許可を持つ他のエントリーと完全に同じ扱いとなる。 これには、PHL に含まれる ことの検査も含まれる。 それは、エントリーが最終的に、 グローバルに開示可能となる場合に適用され、これは手動の追加の既定である。

5.4. 来歴メタデータ

この節は非規範的である。

COS エントリー は、意図的に、 バイト列の取得元について何も記録しない。識別情報は、 ハッシュだけであり、同じバイト列は、 いくつのオリジンが保存したかによらず、同じエントリーとなる。 いくつの URL から取得したかにもよらない（§ 2.2 COS エントリーを参照）。URL は、 ある 1 つの 書き込み元による取得の性質であるため、エントリーについて 1 つ選ぶ恣意的でない方法はない。 複数のオリジンが書き込んだエントリーではそうなる。また、バイト列のように検証できるものでもなく（§ 8.1 リソースの完全性を参照）、 さらに、ユーザーの閲覧について、粗い粒度の オリジン の値よりも、はるかに多くの情報を伝える。 保存元 オリジンにある値より多くなるのは、パスやクエリー文字列が、特定の文書、 アカウント、またはセッションを指定できるためである。したがって、エントリーに記録すると、高エントロピーの信号が、 開示制限を迂回する経路を得る。その制限を課すために存在するのが、オリジン群 および § 8.4 可用性の 制御である。

それでも、その情報を求める動機は現実に存在する。複数 GB のファイルを、 § 5.2 追い出しに記述する設定 UI で見るユーザーも、次の失敗の理由をデバッグする開発者も、 getFileHandle() の呼び出しがヒットしなかった理由を調べる際、どちらも、ファイルが、 どこから来たかを知りたいと考える。ユーザーエージェントは、実装内部の非公開の来歴記録を、 エントリーに付随して保持することで、この要求に応えてもよい（たとえば、各 保存元オリジン が取得した URL、 その バイト列の取得元と取得時刻）。ただし、記録を、エントリーの外部で保持するユーザーエージェントの状態として扱うことを条件とする。 その条件は、次のとおりである。

  • スクリプトには決して公開しない。この仕様のどの機能も開示せず、後で追加する機能も、 開示すべきではない。getFileHandle() も、 次の FileSystemFileHandle という戻り値も、そのような記録が存在するかどうかを明らかにすべきではなく、その 内容はなおさらである。特に、要求元の オリジン は、自身が 生成していない記録を観測できてはならない。

  • 信頼された、ウェブ以外の経路を通してのみ表示する。その経路は、ユーザーエージェント自身の設定およびストレージ 検査 UI、開発者ツール、および（ユーザーエージェントに拡張機能プラットフォームがある場合） 明示的にユーザーが与えた権限によって制御される拡張機能 API とし、他の、 閲覧履歴を公開する API と同じ扱いとする。次を参照されたい。 ブラウザー拡張機能との統合点の解説が、 この リポジトリーにあり、検討中の拡張機能向けの機能を記述している。

  • 未検証であり、その旨を示して提示する。記録内の URL は、バイト列を書き込んだオリジンによる、 主張である。ハッシュ だけが内容を保証する（§ 8.1 リソースの完全性を参照）。2 つのオリジンが、異なる URL を、 同じエントリーについて記録してもよく、そのいずれも、 不正確、または意図的に誤解を招くものである可能性がある。

  • エントリー、および帰属先のオリジンと存続期間を共有する。記録は、次の場合に破棄する。 エントリーが追い出されたか削除された場合であり、オリジンに帰属する部分は、次の場合に破棄する。 そのオリジンが、保存元オリジンから除去された場合である。ユーザーが、 その オリジンのサイトデータを消去した場合も含む（§ 5.2 追い出しを参照）。

そのような記録はコンテンツから見えないため、ユーザーエージェントが保持するかどうか、およびどの程度、 保持するかは、完全に実装に委ねられる。この仕様のいずれの部分も、それに依存せず、その、 有無をサイトが検出することはできない。

6. 権限ポリシーとの統合

この仕様は、ポリシーによって制御される機能 を定義する [permissions-policy]。その識別子は、 文字列 "cross-origin-storage" である。その既定の許可リストは、 self である。

[permissions-policy] は、使用を許可されている を、Documentについて定義する。 しかし、 CrossOriginStorageManager は、次においても公開される WorkerGlobalScope。 これは、自身の Document を持たない。そのため、検査は、呼び出し元の グローバルオブジェクトについて記述する。 ワーカーのグローバルオブジェクトでは、次をたどる Document群であり、 そのワーカーを推移的に所有するものとなる。それらのすべてが、 この機能を許可しなければならない。

クロスオリジンストレージの権限を検査する には、グローバルオブジェクト global を与え、 真偽値を返す。

  1. global が Window オブジェクトである場合、次を行う。

    1. document を、global の 関連付けられた Documentとする。

    2. document が null の場合、false を返す。

    3. document が、次について 使用を許可されているものでない場合、その対象が、 "cross-origin-storage" ポリシーによって制御される機能であるなら、 false を返す。

    4. true を返す。

  2. global が WorkerGlobalScope オブジェクトである場合、次を行う。

    1. owners を、global の 所有者集合とする。

    2. owners が 次の状態、 空である場合、false を返す。

8.1. リソースの完全性

すべての COS エントリー は、そのキー、および、 バイト列の検証対象として、暗号学的ハッシュを使用する（次を参照 § 3.3 ファイルの作成と書き込み）。したがって、サイトは確信できる。 ファイルを、次を通じて取得した場合、 getFileHandle() そのファイルのバイト列は、取得したはずのものと厳密に同じである。 自身で hash を取得した場合と同じになる。開発者は、クロスオリジンストレージの内容を列挙したり、 ハッシュをあらかじめ知らずにファイルにアクセスしたりすることはできない。

COS ハッシュ は秘密ではない。それは、 コンテンツの識別子であり、誰でも容易に計算できる。 そのファイルをすでに持つ者なら計算でき、この仕様が対象とするような、広く配布された、 リソースでは、通常、公知の情報である。モデルやライブラリーの、 リリースに合わせて公開されることも多い。したがって、ハッシュを知っていれば、エントリーを検索するには十分だが、 それ自体ではアクセスは許可されない。検索が成功するかどうかは、完全に、オリジン群 および、 § 8.4 可用性の制御によって決定される。開発者は、未公開のハッシュを、 アクセス制御の仕組みとして扱ってはならない。 特定のファイルに関心のある攻撃者は、そのハッシュを推測する必要はなく、ファイル、 自体を取得するだけでよい（§ 8.2 クロスサイトの探索を参照）。

8.2. クロスサイトの探索

リソースが限られたサイト群だけで使用される場合、攻撃者が、そのリソースが、 クロスオリジンストレージに存在すると知ることができれば、ユーザーがそのいずれかのサイトを訪れた可能性が高いと推測できる。 getFileHandle() は、存在を知るための仕組みであるため、各呼び出しは、 実質的に探索となる。この仕様の 2 つの独立した仕組みが、探索によって、 知り得るものを制限する。

  • オリジン群 （次を参照 § 3.5 リソースの可視性の拡大）により、保存元の、 オリジンは制限できる。 開示先を、選択したオリジンの集合と、それらと 同一サイト にあるオリジンに限定する。したがって、独自のリソースや普及度の低いリソースを、 必ずしも、 グローバルに探索可能にする必要はない。

  • § 8.4 可用性の制御 は、さらに、次のリソースの開示を差し控える。 "*" を範囲とするリソースについて、 要求元のオリジンが、その 保存元オリジンの外にある場合、ハッシュが PHL に含まれる場合を除き、開示しない。 これにより、次を指定して保存したリソースが、origins: "*" であっても、 ウェブ上のすべてのオリジンから、自動的に探索可能にはならない。この制御が適用されるのは、 "*" を範囲とする、 エントリーだけである。リストまたは同一サイトを範囲とするエントリーには、最初の箇条書きの制限だけが、 適用される。これらについては、保存元オリジンが、すでに開示範囲を明示的に制限しているためである。

最初の箇条書きが成り立つのは、「選択したオリジンの集合」が、ウェブ全体よりも意味のある程度に小さいままである場合だけである。 次の形式には、origins 呼び出し元を妨げるものはなく、 非常に多数のオリジンを列挙できる（たとえば、公開の、 人気サイトランキングから作成したリスト）。そうすると、機能上はグローバルな開示に近づきながら、 "*" だけが要求する、意図的かつ明示的なオプトインを回避できてしまう。オリジンリストの最大 長 （次を参照 § 5.1 ストレージの制限）が、これを制限する。実際の、 複数サイトを運営する利用事例に適した、 上限（共通の管理下にある少数の関連するオリジン）でありながら、意味のある近似としての、 「すべてのオリジン」には遠く及ばない制限により、オリジンを限定する形式の オリジン群 が、次のものとして使用されることを防ぐ。 "*" の暗黙の代用品である。

ユーザーエージェントは、さらに、繰り返される次のものにレート制限、または他の抑制を適用すべきである。 getFileHandle() の、単一のオリジンからの呼び出しである。また、適用してもよい。 端末上のヒューリスティック（たとえば、次のように見えるハッシュへの要求パターンを検出するもの、 ユーザーごとに生成されたもの）を使用して、探索の試みを識別し、阻止してもよい。これは、探索対象の、 ハッシュが PHL に含まれるかどうかとは独立して行う。

ホスト側の統合のいずれかによって行われる検索も、§ 9 他の仕様との統合にあるとおり、 同じように探索である。ページにエラーを表示しなくても、サイトは、自身の、 サーバーがフォールバック要求を受け取ったかどうかを観測できる。それは、「見つからない」という、 結果がここで伝えるものと同じ 1 ビットを伝える。そのような検索は、この仕様の制御が許す範囲を超える開示をせず、 それらの制御は、変更することなく適用される。ただし、レート制限が有効となるのは、それらの、 経路からの検索を、次と合わせて数える場合だけである getFileHandle() の呼び出しと合わせて数える必要がある。 スクリプトから操作できる統合でも、同じように容易に、ループ内で検索を発行できるためである。

8.3. 進行中の書き込み

要求されたものの完了していない書き込みは、すべてのオリジンにとって、次と区別できてはならない。 一度も書き込まれていないハッシュである。この仕様は、構造によってそれを実現する。 COS エントリー が追加される先は、COS レジストリーであり、その追加を行うのは、検証して保存する、または、 取得したリソースをクロスオリジン ストレージに保存するだけである。どちらも、完全なバイト列が、 ハッシュに対して検証された後だけに行われる。作成要求を完了するは、読み取りも書き込みも行わない。 レジストリーに対して行わない。したがって、 読み取りで観測できる仮の状態はなく、読み取り経路に、先に、 応答できる分岐もない。可用性の制御を適用するより前に応答することはない。

別の方法として、作成要求が行われたときに仮のエントリーを登録し、同時の、 読み取りを区別可能なエラーで拒否すると、呼び出し元は、何らかのオリジンが、 指定したハッシュを今まさに書き込んでいると知ることができてしまう。その 1 ビットは些細に見えるが、そうではない。次の条件で取得できてしまう。

  • 任意のオリジンが取得でき、エントリーに対して一切の許可を持たないものも含む。仮のエントリーは、 許可を持たず、読み取りには、次より前に応答されるためである COS の 開示を決定するが実行される前である。

  • 任意のハッシュについて取得でき、次に該当しないものも含む PHL に含まれるものではなく、今後も含まれ得ないハッシュも対象となるため、攻撃者は、 ユーザーごとの値から導出したハッシュを使える。これは、まさに、§ 8.6 フィンガープリンティング が検出しようとしているパターンである。

  • GREASE の適用 なしで取得できる。これは、制御の、 手順に到達する開示だけに適用されるため、 そのビットにはノイズが含まれない。

  • バイト列を何も供給せずに取得できるため、オリジンごとのストレージ上限 も、 また、 § 5.2 追い出しも、オリジンが作成できる、そのようなビットの数を制限しない。

したがって、2 つのサイトに埋め込まれた追跡者は、最初のサイトで任意のビット幅の識別子を作成し、 2 番目のサイトで読み取れる。ストレージのコストを負わず、次を迂回できる オリジン群、 公開ハッシュ リスト、および GREASE の適用を、すべて同時に迂回する。仮のエントリーは、サービス拒否の、 攻撃経路にもなる。実際に広く普及しているリソースのハッシュを固定すると、他のすべてのオリジンによる読み取りを、 その仮のエントリーが存続する間、抑制できてしまう。

注: この方式の代償は、ある呼び出し元が、 別の呼び出し元がすでにダウンロード中であると知る能力を失うことである。 大きなファイルについて、重複するダウンロードの開始を避けられなくなる。これは現実のコストであり、 この仕様の以前の草案が、ここで区別可能なエラーを使用していた理由でもある。この能力は、 最も重要な範囲である、単一のオリジン内では回復できる。使用するのは、 Web Locks、BroadcastChannel、 または共有ワーカーであり、 これらはいずれも、 オリジンの境界を越えて何も開示しない。オリジン間での節約は、大部分が理論上のものにすぎない。2 つの無関係な、 オリジンが、同じハッシュについて同じ瞬間に競合する必要があり、どちらもまだ、 書き込んでいないエントリーは、いずれにせよ、次の条件を満たすまで相手には開示できない PHL に含まれることである。

注: "NotAllowedError" は、引き続き次に対する応答となる getFile()。 その対象は、 作成によって取得し、まだ書き込みに使用していないハンドルである（§ 4 クロスオリジンストレージのファイルシステムを参照）。その応答は、 レジストリーに対して一定であり、要求したオリジンだけに届く。 ハンドルは、クロスオリジンでは逆直列化できないためである（§ 4.1 転送： ハンドルを参照）。したがって、情報伝達の経路にはならない。

8.4. 可用性の制御

次による getFileHandle() 読み取りが、次の外にあるオリジンから行われた場合、 保存元 オリジンの外からの読み取りが成功するかどうかは、常に、要求元オリジンが、 エントリーを読み取ることを許可されるかどうかに依存し、これは、オリジン群によって決まる。"*" を範囲とするエントリーでは、第 2 の、 独立した問いも適用される。ユーザーエージェントが、エントリーが、 そもそも存在することを開示する意思があるかどうかであり、これは、PHL への 所属および GREASE の適用によって決まる。両方が、 そのようなエントリーでは成立しなければならない。リストまたは同一サイトを範囲とするエントリーでは、最初の問いだけが適用される。 規範的なアルゴリズムは、§ 3.2 ファイルの読み取りを参照。したがって、"NotFoundError" は、 リソースが存在しないことの証明ではない。リソースが存在しない、要求元の、 オリジンが対象範囲外である、"*" を範囲とするリソースのハッシュが（まだ、または今後も）PHL に含まれない、または、 GREASE の適用が真陽性を抑制した、という意味かもしれない。開発者は、"NotFoundError" を、 「ネットワークにフォールバックする」よりも具体的な意味として扱ってはならない。

注: サードパーティークッキーをサポートするユーザーエージェントでは、 "*" の許可により、追跡者が関連付けられる、 ユーザーのサイト間の訪問は、サードパーティークッキーがすでに可能にしている範囲を超えない。PHL だけでは、 これを制限できない。攻撃者は、個々には、 PHL の条件を満たすリソースから、書き込む部分集合を選ぶことで、クロスサイトの識別子を構成できる。サードパーティー、 クッキーを遮断するユーザーエージェントでも、クロスサイトの開示を制限すれば、"*" の許可を提供できる。たとえば、 トップレベルサイトをキーとし、ページ内のすべてのフレームで共有する、クロスサイト検索の少量の予算を設け、 その回数を一定時間、再読み込みをまたいで保持し、書き込まれたエントリーが、 "*" の許可を通じて利用可能になるのを、ユーザー操作の後だけに限定する。README の、 プライバシーに関する考慮事項に、これらの緩和策を記述している。 GREASE の適用と同様に、これらが適用されるのは、次のものを通じて資格を得るオリジンだけである。 グローバルに開示可能という許可だけを通じる場合である。保存元 オリジン、および、次のものにあるオリジン、 明示的な オリジン群 の リストにあるもの、および、 いずれかと 同一サイト にあるオリジンは、エントリーを読み取れる。 その時点は、COS の開示を決定するが返すと同時であり、ユーザー操作も、 検索予算も必要ない。

8.5. GREASE の適用

ユーザーエージェントは、次を適用してもよい GREASE の適用 （ランダムな拡張を生成し、維持する： 拡張可能性）。これは、ときどき、次のように応答することである。 開示可能なエントリーが存在しないかのように応答する。§ 8.4 可用性の制御が、 それ以外の点では、 開示を許可する場合でも同様である。これによりノイズが加わり、サイトが、実際の不在と、 プライバシーを目的とした偽陰性を区別しにくくなる。この手法は、次で適用されるものに似ている。 UA クライアント ヒントである。

GREASE の適用が対象とするのは、次を通じて資格を得るオリジンだけである グローバルに 開示可能という、 許可だけを通じる場合であり、これは、公開ハッシュリストによって制御される場合と同じである（COS の開示を決定するを参照）。 ユーザーエージェントは、次には適用してはならない 保存元オリジン、明示的な、 オリジン群 の リストにあるオリジン、または、 そのいずれかと 同一サイト にあるオリジンである。

GREASE を適用するユーザーエージェントは、エントリーのサイズに、 見合った判断で行わなければならない。小さなエントリーでは、ネットワーク取得へのフォールバックが安価であるため、ときどき発生する、 偽陰性は、プライバシーとの妥当なトレードオフとなる。ユーザーエージェントは、次のエントリーに GREASE を適用してはならない。 そのサイズのため、不要な再ダウンロードが、得られるプライバシー上の利点に明らかに釣り合わないもの、 （たとえば、GB 規模の AI モデルの重み）である。この場合の偽陰性は、完全な、 観測可能で、コストの大きい再ダウンロードを強いるためである。

8.6. フィンガープリンティング

攻撃者がクロスオリジンストレージの探索から抽出できる情報は、普及度によって制限される。 その普及度は、探索対象リソースのものである。ユーザーが、一般的な AI モデルのように非常に普及したリソース、 または広く使用される JavaScript ライブラリーを持つと知っても、明らかになるのは、ユーザーが、そのリソースを使う（場合によっては非常に、 多数の）サイトのいずれかを訪れたということだけである。珍しいリソースや固有のリソースを持つと知ることは、はるかに多くの情報をもたらす。 ユーザーエージェントは、端末上のヒューリスティックを適用して、ハッシュが次のように見えるリソースを検出することが期待される。 意図的にユーザーごとに固有となっているもの（たとえば、単一の、 サイトによってしか書き込まれたことがないハッシュ、または異常な頻度で要求されるハッシュ）を検出し、そのようなパターンを探索の試みとして扱う。 これは、名目上の PHL の状態とは独立して行う。

9. 他の仕様との統合

この節は非規範的である。

ここで定義する COS レジストリー には、 4 つのホスト側の統合からもアクセスできる。その際、 次を経由する必要はない getFileHandle()。 直接呼び出す必要はない。それぞれの、 統合は、個別のホスト仕様で定義する。この仕様は、共有される、 基盤となる概念（COS ハッシュ、COS エントリー、可用性の制御、および、 公開ハッシュ リスト）と、取得したリソースをクロスオリジン ストレージに保存するという手順を定義する。 それらの統合は、この手順を基礎とすることが期待される。

  • HTML: crossoriginstorage 属性を、次に導入する。 link および、 script 要素で、すでに、 integrity を持つものが対象となる [SRI]。WHATWG への提案は、次にある。 whatwg/html#12770。

  • JavaScript: ホスト定義の crossOriginStorage インポート属性であり、使用できる。 次と併用できる。 integrity と併用し、基礎とするのは、インポート属性 提案である。WHATWG への提案は、次にある。 whatwg/html#12771。

  • CSS: cross-origin-storage() <request-url-modifier>であり、 integrity() と併用できる。 CSS 作業部会への提案は、次にある。 w3c/csswg-drafts#14056。

  • Fetch: crossOriginStorage RequestInit オプションであり、次と併用できる。 integrity [FETCH]。提案先は、 WHATWG であり、その提案は、次にある。 whatwg/fetch#1954。 この形式には、ホスト定義の宛先がなく、COS エントリー が保存するのは、バイト列だけである。 そのため、その仕様が次を定義する Response。 その提供元は、COS レジストリーである。期待される、 形式は成功レスポンスであり、ステータスは 200、ステータスメッセージは OK、そして、 本文は、次のもののストリームである バイト列。Content-Type ヘッダーは、MIME 型であり、 その値は、 呼び出し元が宣言する。他のヘッダーは持たず、ネットワーク取得が行われていないためである。

説明のためだけに、同じグローバルに共有されるリソースを、クロスオリジンストレージに明示的に参加させる例を、 4 つの各形式で示す。

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

これらのコード片は説明のためだけのものである。この仕様は、これらの構文を一切定義しない。 各形式の正式な文法は、オリジンを限定するリストの表記方法も含め、 それぞれのホスト仕様に属する。表記は意図的に 異なる。RequestInit メンバーは sequence<DOMString> を受け取ることができ、対応するのは origins そのものである。一方、属性値、 インポート属性の値、および CSS 修飾子の引数は、テキストしか保持できない。

4 つの形式はすべて、まず次を参照する処理モデルを共有することが期待される COS レジストリーから、一致する開示可能なエントリーを探し、 その後にネットワーク取得へフォールバックし、さらに、 取得に成功し、完全性が検証されたリソースの保存先を COS レジストリーとし、再利用できるようにする。 他のオリジンによる再利用であり、まさに getFileHandle() と同じである。保存の手順 は 取得したリソースをクロスオリジン ストレージに保存するであり、各統合がその実行時に与えるのは、 取得した レスポンスである。したがって、オリジンを限定する値は、次によって制限される。 Cross-Origin-Storage-Allow-Origin ヘッダーがそのリソースのレスポンスにあり、それを送信するのは、 バイト列を供給するサーバーである（§ 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照）。議論の対象が、 これらの統合である場合、それらを取り込むホスト仕様のトラッカーで扱い、 このリポジトリーの課題トラッカーでは扱わない。
