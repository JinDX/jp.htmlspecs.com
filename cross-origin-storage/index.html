概要

オリジン間ストレージ（COS）は、Web アプリケーションが AI モデル、WebAssembly モジュール、非常に普及している JavaScript ライブラリなどの 大容量ファイルを異なるオリジン間で保存および取得できる、コンテンツアドレス可能なキャッシュです。ファイルは URL ではなく暗号学的ハッシュによって識別されるため、あるオリジンによって一度取得された バイト単位で同一のリソースは、ユーザーエージェントが許可する他の任意のオリジンによって、再度ダウンロードすることなく再利用できます。キャッシュ内の存在を、ユーザーがどのサイトを訪問したかの推測に利用できないようにするため、 ファイルのオリジン間開示は、k-匿名性方式の人気度基準を満たすハッシュに限定されます。

1. はじめに

この節は非規範的です。

Storage は通常、ユーザーのセキュリティとプライバシーを保護するためにオリジンによって分割されています。これは適切なデフォルトですが、どのサイトから要求されたかにかかわらずバイト単位で同一のファイルとなる、非常に大規模で非常に人気があり、公開分散されるリソース（AI モデル、WebAssembly モジュール、JavaScript ライブラリ、ゲームエンジン、大規模な Web フォント）という限定的な種類には適していません。互いに無関係な 2 つのオリジンがそれぞれ同じ 8 GB のモデルに依存している場合、オリジン分割ストレージはユーザーにそのモデルを 2 回ダウンロードして保持させることになり、ユーザーの帯域幅、ストレージ、バッテリー、そしてネットワーク全体にとって無駄になります。

Cross-Origin Storage (COS) は、URL ではなく暗号学的ハッシュをキーとする コンテンツアドレス指定可能キャッシュであり、ユーザーエージェントが、そのようなリソースの保存済みコピー 1 つを、 その使用を選択した複数のオリジン間で共有できるようにします。COS にリソースを保存することは、常に保存元 オリジンによる明示的なオプトイン操作であり、ユーザーエージェントは、本来なら読み取りを許可される オリジンに対してさえ、リソースの存在確認を差し控えることができます。§ 8 プライバシー およびセキュリティ上の考慮事項を参照してください。

この仕様のエントリーポイントは、requestFileHandle() メソッドであり、crossOriginStorage を介して公開されます: 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // ファイルを使って何らかの処理を行う。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // Cross-Origin Storage に（開示可能な形で）存在しないため、代わりにネットワークから取得する。
  }
}

この仕様は、File System Standard [FS] から、FileSystemFileHandle、 FileSystemWritableFileStream、 および関連する基盤を再利用します。これは、オリジン間で共有され、いずれかのオリジンのプライベートなものまたはユーザーに表示されるものとは分離された専用ファイルシステムを対象とします。

この仕様は、命令型 JavaScript API に加えて、ホスト統合が基盤として利用する共有ストア手順を定義します。関連する提案では、同じ基盤となるキャッシュを他のホスト仕様にも統合します。HTML の crossoriginstorage 属性を link および script に追加するもの、 crossOriginStorage JavaScript import 属性、 CSS の cross-origin-storage() <request-url-modifier>、 および fetch() のための crossOriginStorage RequestInit オプションです。それぞれは独自のホスト仕様で定義されています。詳しくは § 9 他の仕様との統合 を参照してください。

2. 概念

2.1. ハッシュ

A COS hash は、 以下の struct である。 items を持つ:

algorithm

[WEBCRYPTO] によって認識されるハッシュアルゴリズムの名前を示す 文字列です。 例として "SHA-256" があります。

value

文字列であり、 algorithm によって生成されたダイジェストの小文字 16 進数エンコードです。 "SHA-256" の場合、これは 64 文字の長さになります。

algorithm 辞書メンバーは単純な DOMString として型付けされていますが、その値域は正確には [WEBCRYPTO] の ハッシュアルゴリズムが受け入れる名前の集合です。 HashAlgorithmIdentifier は (object or DOMString) であり、その object 分岐は、 [WEBCRYPTO] によって Algorithm 形式の辞書へ正規化されることで、 追加パラメーターを必要とするアルゴリズム（例: {name: "HMAC", hash: "SHA-256"}）に対して、 呼び出し元が追加のパラメーターを渡せるようにします。 ハッシュアルゴリズムはそのようなパラメーターを取りません。 algorithm は コンテンツアドレス可能 キーの一部として保存、比較、往復処理され、この仕様の例で使用されるすべてのものは単純な文字列です。 ここで任意のオブジェクトを許可しても機能は追加されず、 等価性とシリアル化を 不必要に複雑化させます。そのため、このフィールドには DOMString がより狭く、より正確な型です。

2 つの COS hash 値は、 それらの algorithm 値が ASCII 大文字小文字を区別しない一致であり、 それらの value 値が 完全に等しい場合に 等しいとされます。

注: value はすでに規範上小文字になっています（上記参照）。そのため比較は単純な 文字列比較になります。 algorithm には規範上の大文字小文字の指定がないため、 ASCII 大文字小文字を区別せず比較されます。

コンテンツアドレス可能 ストアとは、エントリーが 等価性によってキー付けされる COS hash のストアです。 同一のバイト列と同じハッシュアルゴリズムを持つ 2 つのファイルは、 それを保存したオリジンの数や取得元となった URL の数に関係なく、同じエントリーになります。

2.2. COS エントリー

各ユーザーエージェントは、単一の COS レジストリを持ちます。これは COS ハッシュ値から COS エントリー 構造体への マップであり、 Cross-Origin Storage を使用するすべてのオリジンによって共有されます。 COS エントリーは、次の 項目を持ちます:

hash

COS hashです。

bytes

Null、または バイト列であり、そのダイジェストが hash の algorithm に基づいて生成され、hash の value と等しいものです。 writer が 検証と保存 を完了するまで Null です。

state

"pending" または "written" のいずれかです。 エントリーは最初 "pending" で開始し、 bytes が最初に設定された時点で一度だけ "written" になります。

pending writer count

最初は 0 である非負整数で、未完了の writer の数を数えます。つまり、 create request の完了によって返された FileSystemFileHandle ハンドルであり、その closing write がまだ確定していないものです。 これは verify and store において、 失敗した書き込みを安全にクリーンアップできるかどうかを判断するためだけに使用されます。 詳細は § 3.3 Creating and writing files を参照してください。

origins

origin の listであり、 Public Hash List とは独立して、明示的なクロスオリジン読み取りアクセスを許可されたものです。 初期状態では空であり、増加することのみが可能です。 これは、エントリーを読み取れる対象を決定する 3 つの独立した加算的な許可の 1 つです。 他の 2 つは、その storing origins （常に読み取り可能であり、それらと same site の origins も含む） と globally disclosable です。

globally disclosable

booleanであり、初期値は false です。 エントリーがグローバル（"*"）利用可能性の要求を伴って書き込まれたかどうかを記録します。 true の場合、要求が § 8.3 Availability gating を通過する任意の origin によってエントリーを読み取ることができます。 つまり、その hash が on the PHL であり、 GREASE によって抑制されない場合です。 一度 設定されると、true のままになります。

注: これは item として origins とは別に存在します。 これにより、後からグローバル利用可能性の要求が行われた場合、 既存の明示的な origins list に "*" の許可を追加できます。 2 つを 1 つのフィールドに統合した場合、bytes を提供した writer が、 list の範囲に限定されたエントリーを "*" の範囲に変更できてしまいます。 § 8.3 Availability gating は "*" の許可にのみ適用されるため、 以前は list からエントリーを読み取れた origin は、 hash が on the PHL ではない場合、 常に NotFoundError を受け取るようになります。 許可を独立させることで、すべての可視性変更は厳密に加算的になり、 アップグレード可能であるがダウングレード不可能 という要件を満たします。

storing origins

このエントリーの bytes の writing を少なくとも一度正常に完了した origins の set です。 ページ読み込みをまたいで保持され、時間の経過とともに 増加します。 § 5.2 Eviction に記載された場合を除き、減少することはありません。 storing origins 内の origin は、origins や、エントリーの hash が Public Hash List (PHL) に存在するかどうかに関係なく、 常に requestFileHandle() を通じてエントリーのハンドルを取得できます。 § 3.5.1 Original storer access を参照してください。

ユーザーエージェントには、関連付けられた Cross-Origin Storage キューがあり、これは 新しい並列キューを開始することの結果です。COS レジストリに対するすべての操作は、このキューに エンキューされるため、 エンキューされた 順序で実行され、互いに割り込むことはありません。

2.3. 公開ハッシュリスト

Cross-Origin Storage にハッシュが存在すること自体を確認できることは、ユーザーの閲覧履歴に関する情報を漏えいさせる可能性があります（§ 8.2 Cross-site probing を参照）。これは特にグローバルな許可に関するリスクです。エントリーの明示的な origins list と、すべてのエントリーが持つ same-site の基本的な範囲については、保存元 origin による明示的な選択によって、すでに開示範囲が制限されています。一方で、エントリーを globally disclosable にすると、Web 上の任意の origin に公開される可能性があります。この特定のリスクを制限するため、 globally disclosable リソースは、その許可を通じて、その storing origins の外部にある origin に対しては、ハッシュが追加の独立したゲートを通過した場合にのみ開示できます。そのゲートとは、 Public Hash List (PHL) への登録です。これは、ベンダー中立で、 implementation-defined な COS hash 値の許可リストです。ハッシュは、k-匿名性に類似した人気基準（例えば、独立した複数の origin 間でバイト単位で同一のものとして出現すること）を満たした場合にのみ Public Hash List に登録されます。これにより、共有キャッシュ内でその存在を確認しても、特定の個人ユーザーについて有益な情報にならないようにします。

COS hash hash は、hash がユーザーエージェントの現在のスナップショットである Public Hash List のエントリーと 等しい 場合に、 Public Hash List に存在する とされます。

Public Hash List の取得プロトコル、更新頻度、データ形式、人気基準、およびガバナンスは、この仕様の補足成果物として詳細に設計されています。これは [URL] Standard の補足データファイルである public suffix list の考え方に沿ったものです。 詳細については、このリポジトリの Public Hash List explainer を参照してください。 この設計では、Public Suffix List のベンダー横断的なローリングリリースの前例をモデルとして、 WHATWG によるガバナンスと、独立して確認された普遍性に基づく登録基準を提案しています。 これは、上記で説明した k-匿名性に類似した基準を具体的に適用したものであり、ハッシュが登録される際にオフラインで一度だけ適用されるため、ユーザーエージェントはクエリごとにそれを繰り返す必要がありません。 これらはすべて、この提案の外部ではまだ確立されていません。 現時点では、このリポジトリ内にリスト自体の初期段階の非規範的なコードプロトタイプが public-hash-list/implementation/ に存在します。 専用のベンダー横断リポジトリは、PHL explainer で説明されているガバナンス目標として残されています。 この仕様は、ハッシュが on the PHL であるかどうかだけに依存するため、 リストの取得メカニズム、ガバナンスモデル、またはその他の設計がどのように発展しても正しく機能し続けます。

3. CrossOriginStorageManager インターフェイス

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

各 Navigator および WorkerNavigator オブジェクトには、関連付けられた CrossOriginStorageManager オブジェクトがあります。crossOriginStorage ゲッターの 手順は、 this に関連付けられた CrossOriginStorageManager を返すことです。

各 CrossOriginStorageManager オブジェクトには関連付けられた オリジンがあり、オブジェクトが 作成されるときに、this の 関連設定オブジェクトの オリジンに設定されます。

注: relevant settings object から origin を取得することは、 スクリプト自体に関するあらゆる情報とは独立しており、ワーカーについて明記する価値のある結果をもたらします。 blob: URL から作成されたワーカーは、それを作成したコンテキストの origin を持つため、その origin の Cross-Origin Storage ビューを完全に共有します。 つまり、そのようなワーカーが書き込んだものは作成元のページが読み戻すことができ、 ページが保存したものはワーカーが読み取ることができます。 blob: URL は独自の origin ではなく、それを取り消してもワーカーがそのビューから切り離されることはありません。 data: URL から作成されたワーカーは opaque origin を持ちます。 この仕様では現在、calling origin が opaque である場合に requestFileHandle() がどのように動作するかを定義していません。 opaque origin の規則は、 validate a COS request において、呼び出し元が 指定する origin のみに適用されます。 opaque origin には、 storing origins や same site 比較のキーとして使用できる安定した識別子が存在しないため、 それに対して付与できる意味のある許可はありません。

3.1. requestFileHandle() メソッド

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

hash で識別されるファイルが Cross-Origin Storage に存在し、かつ呼び出し元オリジンに 開示可能である場合、そのファイルのハンドルを返します。それ以外の場合、これは "NotFoundError" DOMException で拒否されます。 "NotFoundError" は、ファイルが Cross-Origin Storage に 物理的に存在しないことを証明するものではありません。§ 8.3 可用性ゲーティングを参照してください。呼び出し元は、 これを「代わりにネットワークから取得する」と扱うことができます。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

hash で識別されるファイルを Cross-Origin Storage に書き込むために使用できるハンドルを返し、エントリーがまだ存在しない場合は新しいエントリーを作成します。デフォルトでは同一サイトのオリジンに制限されます。 呼び出し元は、エントリーがすでに 存在していたかどうかにかかわらず、ハンドルの createWritable() メソッドを介して完全なファイル内容を書き込む必要があります。その時点でユーザーエージェントは、書き込まれたバイトのハッシュが hash になることを検証し、 そうでない場合は "DataError" DOMException で拒否します。この要件は、 オリジンが作成要求を、hash がすでに存在していたかどうかを判定するオラクルとして使用することを防ぎます。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

上記と同様ですが、さらに、書き込み後に hash に対する要求が § 8.3 可用性ゲーティングを通過する任意のオリジンに エントリーを開示可能にします。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

上記と同様ですが、開示を指定されたオリジンのみに制限します（呼び出し元 オリジン、およびすでに 保存元オリジンに含まれるオリジンに加えて）。

requestFileHandle(hash, options) メソッドの 手順は次のとおりです:

  1. result を 新しい promise とします。

  2. realm を this の 関連 Realm とします。

  3. global を this の 関連グローバルオブジェクト とします。

  4. origin を this に関連付けられた オリジン とします。

  5. global を与えて Cross-Origin Storage 権限を確認するを 実行した結果が false の場合、次を行います:

    1. global を与えて、DOM 操作タスクソース上で グローバルタスクをキューに入れ、 result を "NotAllowedError" DOMException で 拒否します。

    2. result を返します。

  6. validationFailure を、hash と options を与えて COS 要求を検証するを実行した結果とします。

  7. validationFailure が null でない場合:

    1. global を与えて、DOM 操作タスクソース上で グローバルタスクをキューに入れ、 result を validationFailure で 拒否します。

    2. result を返します。

  8. 次の手順を Cross-Origin Storage キューに エンキューします:

    1. options["create"] が true の場合:

      1. result、hash、options、global、および realm を与えて 作成要求を完了するを実行します。

    2. それ以外の場合:

      1. result、hash、origin、global、および realm を与えて 読み取り要求を完了するを実行します。

  9. result を返します。

CrossOriginStorageRequestFileHandleHash hash および CrossOriginStorageRequestFileHandleOptions options が与えられたときに、null または TypeError を返すように COS 要求を検証するには:

  1. hash["algorithm"] が [WEBCRYPTO] によって認識されるハッシュアルゴリズム 名でない場合、新しい TypeError を返します。

  2. hash["value"] が正規 表現 /^[0-9a-f]{64}$/ に一致せず、かつ hash["algorithm"] が "SHA-256" と ASCII 大文字小文字不区別で 一致する場合、新しい TypeError を返します。

    注: 将来のハッシュアルゴリズムでは、 異なる期待ダイジェスト長を定義できます。この 仕様は、例全体での使用に合わせて、"SHA-256" のみを規範的に制約します。

3.3. ファイルの作成と書き込み

作成要求を完了するによって作成された FileSystemFileHandle には、関連付けられた 要求されたオリジンがあり、これはハンドルへの書き込みが正常に完了した後、 検証して保存するが エントリーの オリジンを アップグレードしようとする値です。

COS エントリーを指すすべての FileSystemFileHandle には、さらに関連付けられた COS オリジン、すなわちそれを取得した オリジンと、 関連付けられた 読み取り可能真偽値もあります。これは、 getFile() がその特定のハンドルを介してエントリーのバイトを開示できるかどうかを制御します。 これは、すでに 可用性ゲーティングを通過した 読み取り要求を完了するによって返されたハンドルでは true であり、 作成 要求を完了するによって返されたハンドルでは、同じハンドルについて 検証して保存するが成功するまで false です。

注: これは意図的に各ハンドルのプロパティです。create request は、エントリーがすでに存在して "written" になっているかどうかにかかわらず、ハンドルを返します（complete a create request を参照）。 そのため、エントリー単位の規則では、任意の origin が requestFileHandle() を create: true で呼び出し、 自身が一度も書き込んでいないエントリーを直ちに読み取ることが可能になります。 これにより、 origins、 PHL membership、 または GREASE’ing を満たすことなく、その内容を知ることができます。 この仕様におけるすべての開示制御は読み取り経路で適用されるため、エントリー単位でゲートを設けると、create request がそれらすべてを回避できてしまいます。 呼び出し元にまず正しい bytes を提供することを要求することで、create によって取得されたハンドルを通じた正常な読み取りは、呼び出し元がすでに保持していなかった情報を何も開示しません。

create request を完了する 手順は、promise result、 COS hash hash、 CrossOriginStorageRequestFileHandleOptions options、global object global、 および Realm realm を与えられた場合、次の手順を実行します:

  1. requestedOrigins を、 options["origins"] を与えて normalize requested origins を実行した結果とします。

  2. requestedOrigins が list の場合、 requestedOrigins を、 requestedOrigins と global に対して obtain the COS scope ceiling を実行した結果を使用して apply a COS scope ceiling を実行した結果に設定します。

  3. entry を、COS registry 内で、 hash が equals hash である COS entry が存在する場合はそれとし、 存在しない場合は null とします。

  4. entry が null の場合:

    1. entry を新しい COS entry に設定します。 その hash は hash、 bytes は null、 state は "pending"、 origins は空の list、 globally disclosable は false、 そして storing origins は空の set です。

    2. Set COS registry[hash] を entry に設定します。

    注: 新しいエントリーは明示的な origins 許可なしで開始され、 globally disclosable ではありません。 requestedOrigins は、下記で verify and store によって upgrade resource visibility を通じて適用されます。 これは bytes が書き込まれて検証された後に行われ、既存のエントリーを見つけるリクエストの場合とまったく同じです。 これにより、create request は可視性を拡大する前に完全な bytes を提供する必要があります （§ 3.5 Resource visibility upgrades を参照）。

  5. entry の pending writer count を 1 増加させます。

    注: これは、呼び出し元が createWritable() を呼び出さない場合、または生成されたストリームを閉じない場合でも、 handle を未完了の writer として追跡します。 このような放棄された handle は永続的に entry に数えられます。 これは、この仕組みが存在する前に放棄された処理中の書き込みが entry を永続的に "pending" にしていた場合と同じです。 verify and store を参照してください。

  6. handle を、 creating a new FileSystemFileHandle の結果とします。 その locator は realm 内の Cross-Origin Storage file system 内にある entry を指します。

  7. handle の COS origin を global の relevant settings object の origin に設定します。

  8. handle の requested origins を requestedOrigins に設定します。

  9. handle の may read を false に設定します。

    注: handle は、entry がすでに存在するかどうか、 またすでに "written" であるかどうかにかかわらず返されます。 呼び出し元は、以前の存在を検出するために書き込みを利用できないようにするため、 handle を通じて完全なファイル bytes を提供する必要があります。 また、より広い origins 値の要求が承認される前に検証できるようにします。 § 3.5 Resource visibility upgrades を参照してください。

  10. Queue a global task を DOM manipulation task source 上に、global を指定して実行し、 resolve result を handle で完了します。

要求された origin を正規化する 手順は、(DOMString または sequence<DOMString>) または undefined である origins を与えられた場合、"*"、 origins の list、または null を返します:

  2. origins が "*" の場合、"*" を返します。

  3. list を « » とします。

  4. 各 candidate について origins 内で繰り返します。 （単一の string は 1 つの要素を持つ list として扱います）。

    1. candidateOrigin を、 candidate に対して basic URL parser を実行した結果得られる origin とします。

      注: validate a COS request は、各 candidate が opaque ではない origin に解析されることをすでに確認しています。

    2. list が candidateOrigin を contain していない場合、 append candidateOrigin を list に追加します。

注: 後で既存のエントリーへ merge する前にここで重複を除去することで、 origins はエントリーが最初に作成された時点から重複なしになります。 そのため、その後の clone もすべて重複なしの状態になります。

FileSystemWritableFileStream を、 createWritable() を呼び出して取得したハンドル上で使用し、その locator が COS entry を指している場合、そのストリームが閉じられると、ユーザーエージェントは verify and store 手順を、閉じる操作の promise が履行される前に実行しなければなりません。

注: これは閉じる処理がどのように発生したかに関係なく適用されます。 明示的な close() 呼び出しの場合も、 pipeTo() 呼び出しがソースの終端に到達した場合も同様です。 後者はデフォルトで宛先も閉じます。 [STREAMS] はストリームが閉じた時点ではこの 2 つを区別せず、このアルゴリズムも区別しません。

verify and store 手順は、閉じられたストリームのハンドルが指す COS entry entry、 完全に書き込まれた byte sequence bytes、 および閉じる操作の relevant settings object の origin origin を与えられた場合、次の手順を実行します:

  1. computedValue を、bytes の小文字 16 進数ダイジェストとします。 これは、 algorithm によって指定されたアルゴリズムを使用し、 [WEBCRYPTO] に従って計算されます。

  2. computedValue が entry の value と完全に等しくない場合:

    1. 閉じる操作の promise を、 "DataError" DOMException で reject します。

    2. 以下の手順を Cross-Origin Storage queue に enqueue します:

      1. entry の pending writer count を 1 減らします。

      2. entry の state が "pending" であり、かつ entry の pending writer count が 0 の場合、 entry の hash を COS registry から remove します。

        注: これにより、失敗した書き込みが自身をクリーンアップできます。 同じ hash に対する後続の requestFileHandle() 呼び出しは、他の writer が未完了でなくなった後にはエントリーをまったく見つけず、 通常の "NotFoundError" を取得します。 このカウントは、同じ hash に対して同時に処理中の別の writer （例えば、両方のタブが hash の不在を確認し、それぞれ独立して書き込みを開始した場合） がまだ正常に write できる可能性があるエントリーを削除しないよう保護します。 その writer がまだ未完了である場合、またはすでに成功している場合は、 カウントがまだ 0 に達していないか、 entry の state がすでに "pending" ではないため、この手順は何もしません。 すでに "written" になったエントリーは、 後続の writer がいくつ要求され失敗したとしても、この方法で削除されることはありません。 対象となるのは、一度も正常に書き込まれたことがないエントリーだけです。

    3. これらの手順を中止します。

  3. 以下の手順を Cross-Origin Storage queue に enqueue します:

    1. entry の bytes を bytes に設定します。

    2. entry の state を "written" に設定します。

    3. origin を、まだ存在しない場合は entry の storing origins に Append します。

    4. entry の pending writer count を 1 減らします。

    5. entry と handle の requested origins を指定して、 upgrade resource visibility を実行します。

    6. handle の may read を true に設定します。

      注: 読み取り可能になるのはこの handle のみです。 同じエントリーに対する別の create request から取得され、書き込みが行われていない別の handle は、読み取り不可のままです。

createWritable() は、COS entry を指す FileSystemFileHandle 上で呼び出された場合、 FileSystemWritableFileStream を生成しなければなりません。 その内容は、 keepExistingData の値に関係なく、 また指し示されたエントリーの state に関係なく、空の状態から開始します。

注: [FS] では、通常 keepExistingData は既存ファイルの内容でストリームを初期化するものとして定義されています。 ここでそれを適用すると、呼び出し元は自身が一度も保持していなかった bytes に対して storing origin になることが可能になります。 create request はエントリーがすでに存在するかどうかにかかわらず handle を返すため、 呼び出し元は別の origin が保存した hash に対して writable を開き、 何も書き込まずに閉じ、 引き継がれた bytes が要求された値の hash になる可能性があります。 これにより、origins、 Public Hash List、 および GREASE’ing が一切確認されることなく、読み取りアクセスが付与されます。 これは、個別には許可されている 2 つの操作から構成された availability gating の回避です。 すべての create request で完全な内容を要求する verify and store の理由も同じです。

注: したがって、何も書き込まずに閉じられた writable は空のバイト列を保持します。 これは呼び出し元が必要とする任意のエントリーの要求値には hash が一致しないため、 verify and store は、他の不一致の場合と同様に、 "DataError" DOMException で拒否します。 その場合に、実装が代わりにストレージまたは I/O の失敗を報告すると、 検証結果が無関係なエラーの背後に隠されることになります。

File System Standard [FS] では、依存する仕様が FileSystemWritableFileStream の終了手順に追加の書き込みごとの検証を組み込むための拡張ポイントを、まだ定義していません。 そのようなフックが存在するまで、この節では必要な動作を直接記述します。 将来の改訂では、 [FS] との正式な統合が予定されています。

3.5. リソース可視性のアップグレード

COS エントリ の可視性は アップグレードできるが、ダウングレードすることは決してできない。

  2. requestedOriginsが"*"の場合:

    1. entryのグローバルに開示可能を true に設定する。

    2. return する。

    注: これはグローバルな許可を追加するものであり、entryのオリジンには触れない。すでに明示的なオリジンのリストを持つエントリはそれを保持するため、そのリスト上のすべてのオリジンは、エントリがグローバルに開示可能になった後も、 PHLに依存しないアクセスを維持する。これが、2つの許可が別々に格納される理由の核心である。グローバルに開示可能を参照。

  3. 各candidateOriginについて、requestedOrigins内で:

    1. entryのオリジンがcandidateOriginを含む場合、継続する。

    2. entryのオリジンのサイズが、ユーザーエージェントの 最大オリジンリスト長と等しい場合、break する。

      注: 残りのcandidateOrigin値は、このアップグレードから暗黙に除外される。書き込み自体はすでに成功しており、ユーザーエージェントは、エントリのオリジンリストが上限に達したことを示すコンソール警告を記録することが期待されるためである。

    3. candidateOriginをentryのオリジンに追加する。

注: アップグレードは常に origins に追加するか、 グローバル開示可能 を true に設定するだけである。リストを要求する writer は、すでに グローバル開示可能なエントリを、そうでないものと同じように 拡張する。これは 2 つの許可が独立しているためである。新しく一覧に追加されたオリジンは、 「*」許可が有効なままでも PHL に依存しないアクセスを得る。

注: 元の保存者以外のサイトを含む任意のサイトは、 エントリの origins を拡張できる。ただし、そのサイトもエントリの hash に対応するバイト列を提供する必要がある。これは意図的なものである。 hash に対する正しいバイト列をすでに所有するサイトは、構造上、その hash が示すものについて 元の保存者と同等に権威を持つためである。

3.5.1. 元の保存者のアクセス

origin が 書き込み を正常に完了した COS エントリ（つまり、エントリの storing origins 内の任意の origin）は、その後常に requestFileHandle() を介してハンドルを取得できる。 これはエントリの origins の値や、その hash が PHL 上 にあるかどうかに依存しない。 これは Cache API のモデルと同じであり、origin は常に自身が保存したものへアクセスできる。

4. Cross-Origin Storage ファイルシステム

Cross-Origin Storage ファイルシステム は、いずれの オリジンの ファイルシステムルートとも異なる バケットファイルシステムまたはローカルファイルシステムアクセスルートであり、 その エントリは、COS レジストリのCOS エントリ項目と一対一で対応する。

Cross-Origin Storage ファイルシステムは、[FS]の通常の呼び出しごとの 権限チェック モデルを使用しない。そこから取得されるすべてのFileSystemFileHandleは、 スクリプトに返される前に、§ 3.2 ファイルの読み取りまたは§ 3.3 ファイルの作成と 書き込みによってすでに完全に承認されているため、このようなハンドルに対して getFile() またはcreateWritable() を呼び出しても、 追加の権限プロンプトが発生することはない。

したがって、このようなハンドルに対するqueryPermission()およびrequestPermission()は、 プロンプトを表示できないため、決して "prompt"を報告してはならない。作成リクエストによって取得されなかったハンドルに対する書き込みモードでは "denied"を報告し、それ以外の場合は "granted" を報告しなければならない。

注: 書き込みは、ハンドルが 実際に欠く可能性のある唯一の機能である。作成リクエストだけが、そこを通じて書き込み可能な ハンドルを生成するため、それ以外のハンドルで書き込みモードに対して"granted"を報告することは、 createWritable() が拒否する機能を持つと主張することになる。読み取りは "granted"のままである。読み取り可能なハンドルを保持する呼び出し元は、それを通じて読み取れるためである。リクエストによって どちらの回答も変更することはできない。表示すべきプロンプトがなく、許可を記録できる状態も存在しないためである。

getFile() を、FileSystemFileHandleのうち、 COS エントリを指し、そのmay readが false であるものに対して呼び出すと、 "NotAllowedError" DOMExceptionで 拒否しなければならない。 これには、異なる2つのケースが含まれる。

  • エントリがまだ"pending"である作成リクエストからのハンドル。この理由は、同じハッシュに対する並行した requestFileHandle() 呼び出しが拒否される理由と同じである（§ 3.2 ファイルの読み取りを参照）。呼び出し元が、まだ検証されていないプレースホルダーを ファイルの実際の内容であるかのように観察できてはならないためである。

  • ある別のオリジンがすでに書き込みを行ったエントリに対する作成リクエストからのハンドル。その エントリの状態は "written"であるが、この呼び出し元はバイト列を提供しておらず、 可用性ゲーティングも通過していないため、エントリについて何も知ってはならない。 存在するかどうかさえ知ってはならない。

ハンドルのmay readが true になると、そのハンドルに対して呼び出されたgetFile()は、 指定されたエントリのバイト列を内容とするFileを返す。これは、 それらのバイト列をファイル エントリのバイナリデータとする場合に、[FS] がすでに定義している動作とまったく同じである。

FileSystemFileHandleは、 COS エントリを指す場合、その ファイルシステムロケーターの パスが、 エントリのCOS ハッシュの値である単一の文字列を含むリストであり、 そのルートは Cross-Origin Storage ファイルシステムである。

注: [FS]は、nameを、ハンドルの ロケーターのパスにおける最後のパスコンポーネントとして定義しているため、これにより nameも定まる。 それは ハッシュである。エントリ自体には名前がなく、ハッシュが持つ唯一の識別情報であるため、それを報告することには意味があるが、空文字列ではその情報が失われる。

エントリには名前も含まれるディレクトリもないため、[FS]の構造に関する機能の大部分は作用する対象がない。例外は識別情報であり、コンテンツアドレス指定されたエントリが常に答えられる唯一の問いである。 COS レジストリは、COS ハッシュごとに最大1つのCOS エントリを保持するため、2つのハンドルが同じエントリを指すのは、それらのハッシュが等しい場合に限られる。

isSameEntry()を、 COS エントリを指すFileSystemFileHandleに対して呼び出し、 同じくCOS エントリを指し、同じオリジンによって取得された引数を渡した場合、2つのハンドルのCOS ハッシュ項目が等しければ true を返し、それ以外の場合は false を返さなければならない。

注: これを拒否すると、ユーザーエージェントがすでに保持している情報を破棄することになる。

isSameEntry()を、 呼び出し元のオリジンが取得していない引数、または Cross-Origin Storage ファイルシステム以外のファイルシステムを指す引数とともに呼び出した場合、拒否しなければならない。

注: その場合に false を返すと、2つのハンドルが異なるエントリを指していると断定することになり、 これは呼び出し元のオリジンが検査する権利を持たないハンドルについての主張となる。拒否することが示すのは、比較を実行できなかったということだけである。

move()およびremove()を、FileSystemFileHandleのうち COS エントリを指すものに対して呼び出すと、"NotAllowedError" DOMExceptionで 拒否しなければならず、エントリを変更してはならない。

注: エントリは、その格納 オリジンに属するすべてのオリジンによって共有されるため、削除を認めると、あるサイトが他のサイトの依存するデータを破壊できてしまう。削除は 排除およびユーザー自身のストレージ制御に委ねられる。エントリはCOS ハッシュによって名前が付けられ、含まれるディレクトリを持たないため、名前変更や親の変更には作用する対象がない。

注: いずれのメソッドも、執筆時点では[FS]または File System Access API によって定義されていない (WICG/file-system-access#214)。 そのため、エラー名は、エントリを削除するために[FS]が定義している操作であるremoveEntry()に従う。これは、読み書きアクセスが許可されていない場合、アクセス結果のエラー名で拒否する。ここでの正確な動作は拒否することである。操作には意味があるが、許可されていないためである。

createSyncAccessHandle()については、 ここで規則を定める必要はない。その手順は、ハンドルがバケットファイルシステムに属していない場合、常に "InvalidStateError" DOMExceptionで 拒否する。また、Cross-Origin Storage ファイルシステムは、いずれのオリジンのものとも異なる ファイルシステムルートであるため、[FS]がその拒否と名前の両方をすでに定めている。

注: これは、この仕様が独立して望む結果でもある。FileSystemSyncAccessHandleは、呼び出し元に書き込み可能なファイルディスクリプターを渡すため、 それによって、格納先となっているCOS ハッシュに対応するエントリのバイト列を、 そのエントリが開示可能な他のすべてのオリジンが同じバイト列を読み取っている最中に変更できてしまう。

4.1. ハンドルの転送

FileSystemFileHandleは、 シリアライズ可能なオブジェクトである[FS]ため、COS エントリを指すものを、別の環境設定オブジェクトに、例えば postMessage(message, options)を使用して渡すことができる。 これは、このようなハンドルを取得する2つ目の方法であり、 requestFileHandle()と並ぶものであるため、ここでも制約される。

シリアライズ手順は、COS エントリを指すFileSystemFileHandleについて、 valueおよびserializedが与えられた場合、さらに次のようになる。

  1. serialized.[[COSOrigin]]を、valueのCOS オリジンに設定する。

  2. serialized.[[COSMayRead]]を、valueのmay readに設定する。

デシリアライズ手順は、serialized、 valueおよびrealmが与えられた場合、さらに次のようになる。

  1. serialized.[[COSOrigin]]が、realmの 環境設定オブジェクトのオリジンと同一オリジンでない場合、"DataCloneError" DOMExceptionをスローする。

  2. valueのCOS オリジンを serialized.[[COSOrigin]]に設定する。

  3. valueのmay readを serialized.[[COSMayRead]]に設定する。

注: 同一 オリジンチェックがなければ、転送によってこの仕様におけるすべての開示制御が一度に無効になる。 may readが true のハンドルは、すでに 可用性ゲーティングを適用することをそれをリクエストしたオリジンについて完了している。これを別の オリジンに投稿すると、そのオリジンに対して、オリジン、 PHL メンバーシップまたはGREASEが評価されることなく、エントリのバイト列を渡すことになる。この動作は、ハンドルが同様に 同一オリジンの受信者に対してのみ有用であるという、File System Standardの既存の扱いと一致する。

注: may readはハンドルとともに移動する。そのため、まだ書き込みが行われていない作成リクエストのハンドルは、転送後も読み取り不能のままであり、 読み取りリクエストのハンドルは再ゲーティングされることなく読み取り可能なままである。到着時に再ゲーティングすると、同じ ハンドルを転送することで、呼び出し元が可用性を繰り返し探索できてしまう。

5. ストレージ管理

5.1. ストレージ制限

ユーザーエージェントは、成功した書き込みを通じてオリジンがCOS レジストリに 寄与できるバイト数の合計に上限を課さなければならない。これは、単一のオリジンが、他のオリジンのエントリを排除しようとしてキャッシュを 氾濫させることを防ぐためである。具体的な上限は 実装依存である。あるオリジンの書き込みがその上限を超える場合、ユーザーエージェントは "QuotaExceededError" DOMExceptionで その書き込みを拒否しなければならず、 コンソールに警告を記録すべきである。

注: エントリはコンテンツアドレス指定可能であるため、同じハッシュのもとで同じ バイト列を繰り返し書き込むオリジンは、最初の成功した書き込みを超える追加のクォータを消費しない。§ 2.2 COS エントリを参照。

ユーザーエージェントはまた、実装依存の最大オリジンリスト長を持つ。これは、単一のオリジンリストが含むことのできる オリジンの数を制限する正の整数である。これは、リストが最初に提供されたとき(COS リクエストの検証を参照)と、 後で既存のエントリにマージされたとき(リソース可視性のアップグレードを参照)の両方で強制される。これにより、単一の呼び出しでも、時間をかけた多数の呼び出しの累積的な効果でも、エントリのオリジンを無制限に 増大させることができない。メモリ使用量を抑えることに加えて、これにより、オリジンのリストが "*"の未宣言の代替として使われることも防ぐ。§ 8.2 クロスサイトプロービングを参照。

この上限を超えた場合の扱いは、これら2つの箇所でそれぞれ異なる。なぜなら、2つの呼び出しは操作の中で 非常に異なる時点で発生するためである。

  • COS リクエストの検証では、この上限はファイルが取得、ハッシュ化、または 書き込みされる前にチェックされる。これを超える呼び出し元は、即座に"TypeError" を受け取り、それ以外には何も起こらない。これは、他の不正なorigins 値と同じ扱いである。

  • リソース可視性のアップグレードでは、この上限は、無関係な複数のオリジンによって、 長期間にわたって行われる可能性がある、独立した個別の書き込み呼び出しにわたってリクエストされたオリジンの累積的な効果によってのみ 到達し得る。また、この上限は、今回の呼び出しのバイト列がすでにハッシュ化され、検証され、永続的に格納された後にのみチェックされる。 その時点で書き込みを拒否すると、成功済みですでに検証されている、場合によっては非常に大きな書き込みを、無関係な 帳簿上の上限のために破棄することになり、しかもそれは単一の呼び出し元の過失に帰することさえできない。したがって、書き込みは 成功したままにされ、容量を超えるオリジンのみがオリジンから 除外され、コンソール警告が表示される。これは、 より制限的な方向へのリクエストの既存の扱いを反映している。完全に尊重できないオリジンリクエストは、暗黙のうちに上限が課され、それを伴う書き込みは 依然として成功する。この仕様の他の箇所である§ 8.3 可用性ゲーティングと整合して、 呼び出し元には、リクエストしたオリジンが実際に追加されたかどうかを事後に確認する信頼できる方法がない。そのオリジンとして 後続のrequestFileHandle() 呼び出しは、オリジンが追加されていたとしても失敗する可能性がある(例えば、エントリが 排除された場合や、ユーザーエージェントがリクエストをスロットリングした場合など)ため、その結果はどちらの意味でも確認とみなしてはならない。

5.2. 退去

この節は非規範的です。

ストレージの圧迫下では、ユーザーエージェントはCOS レジストリからエントリを排除してもよい。 例えば、各エントリに最近アクセスした格納オリジンにわたる、最も最近使用されていないものから排除するポリシーを用いることができる。ユーザーエージェントは、ユーザーが どのファイルが保存されているか、どのオリジンが各ファイルにアクセスしたかを確認し、手動で エントリを削除したり、Cross-Origin Storage のすべてのデータを消去したりできる設定UIを提供することが期待される。

ユーザーがあるオリジンのサイトデータを消去した場合、ユーザーエージェントは、そのオリジンが現れるすべての 格納 オリジン集合からそのオリジンを削除すべきである。その削除の結果、COS エントリの 格納 オリジンが空になった場合、ユーザーエージェントはそのエントリを削除の対象として検討してよい。

5.3. 手動で追加されたエントリー

この節は非規範的です。

上記で説明した設定UIは、ユーザーがすでにディスク上に持っているファイルを、スクリプトが一度もrequestFileHandle()を呼び出すことなく、 Cross-Origin Storageに直接追加できるようにしてもよい (例えば、ウェブサイトとは無関係にユーザーがダウンロードしたAIモデルなど)。 このようなエントリには、書き込みの帰属先となるリクエスト元のオリジンがないため、命令型APIだけでは答えられない次の2つの疑問が生じる。

  • § 3.5.1 元の格納者のアクセスの目的における 元の格納者は誰か。誰もいない。エントリの格納オリジンは空の状態で始まる。 したがって、いかなるオリジンも、すべてのリクエスト元オリジンが通常従う 可用性ゲーティングおよびオリジンチェックから 免除されない。実際にバイト列を書き込んだオリジンは存在しないため、これが正しい結果である。

  • そのようなエントリは、originsを省略した通常の書き込みと同様に、同一サイトのみの利用に制限すべきか。いいえ。「同一サイト」はリクエスト元オリジンとの相対でのみ意味を持つが、手動追加にはリクエスト元オリジンがないため、「同一サイト」が意味するサイトも存在しない。ユーザーエージェントは、このようなエントリをグローバルに 開示可能にし、その明示的なオリジンのリストを空のままにすることが期待される。ファイルを手動でシードすることの目的(ユーザーがまだ訪問していないサイトでも、ユーザーがすでにディスク上に持っているファイルを再利用できるようにすること)は、他のオリジンが実際にそれを発見できる場合にのみ果たされるためである。ユーザーエージェントの設定UIは、ユーザーがより狭い範囲を選択できるようにしてもよい。

この方法で追加されると、stateが"written"であるエントリは、ウェブサイトがrequestFileHandle()を通じて書き込んだエントリと、それ以外の点では区別できない。 同じ 可用性ゲーティングおよび可視性の アップグレード規則が、他の同じ許可を持つエントリの場合とまったく同様に適用される。 これには、エントリがグローバルに開示可能になった場合のPHL上チェックも含まれる。これは手動追加のデフォルトである。

5.4. 来歴メタデータ

この節は非規範的です。

COS エントリは、そのバイト列がどこから来たものかを意図的に何も記録しない。識別情報は ハッシュだけである。同じバイト列は、どれだけ多くのオリジンが それを格納したか、またはどれだけ多くのURLから取得されたかにかかわらず、同じエントリである(§ 2.2 COS エントリを参照)。URLは ある1つの書き込み元による取得の属性であるため、複数のオリジンが書き込んだエントリについて1つを選ぶ、恣意的でない方法は存在しない。また、バイト列のように検証することもできない(§ 8.1 リソースの完全性を参照)。 さらに、URLはオリジンの大まかな値よりも、ユーザーの閲覧についてかなり多くの情報を含む。格納 オリジンにおけるオリジン値は、パスやクエリ文字列が特定のドキュメント、アカウント、またはセッションを示すことができるためである。したがって、エントリにURLを記録すると、オリジンおよび§ 8.3 可用性 ゲーティングが課すために存在する開示制限を回避して、高エントロピーなシグナルを伝達することになる。

それでも、これを知りたいという動機は現実に存在する。§ 5.2 排除で説明した設定UIで数ギガバイトのファイルを見ているユーザーも、 requestFileHandle() の呼び出しが失敗した理由をデバッグしている開発者も、ファイルがどこから来たのかを知りたいと考えるだろう。ユーザーエージェントは、エントリとともに実装内部の来歴記録を保持することでこれに対応してもよい (例えば、各格納オリジンがバイト列をどのURLから取得したか、およびその時刻)。ただし、その記録はエントリの外部に保持されるユーザーエージェントの状態として扱われなければならない。

  • これはスクリプトに決して公開されない。この仕様のどの部分もこれを開示せず、後から追加されるものも開示すべきではない。requestFileHandle()も、 それが返す FileSystemFileHandleも、そのような記録が存在するかどうかはもちろん、その内容を明らかにしてはならない。特に、リクエスト元のオリジンは、それ自体が生成していない記録を観測できてはならない。

  • これは、信頼された非ウェブのサーフェスを通じてのみ表示される。すなわち、ユーザーエージェント自身の設定およびストレージ検査UI、開発者ツール、そして(ユーザーエージェントが拡張機能プラットフォームを備えている場合は)明示的にユーザーが許可した権限の下にある拡張機能APIである。これは、閲覧履歴を公開する他のAPIと同じ扱いである。検討対象となっている拡張機能向けサーフェスについては、このリポジトリのブラウザ拡張機能統合ポイントの解説を参照。

  • これは検証されておらず、そのように提示される。そこに含まれるURLは、バイト列を書き込んだオリジンによる主張である。内容を保証するのはハッシュだけである(§ 8.1 リソースの完全性を参照)。2つのオリジンが同じエントリについて異なるURLを記録する可能性があり、どちらか一方が不正確であったり、意図的に誤解を招くものであったりする可能性がある。

  • これはエントリおよび帰属先のオリジンと同じ存続期間を持つ。エントリが排除または削除されると破棄され、オリジンに帰属する部分は、そのオリジンが格納オリジンから削除されると破棄される。これには、ユーザーがそのオリジンのサイトデータを消去した場合も含まれる(§ 5.2 排除を参照)。

このような記録はコンテンツから見えないため、ユーザーエージェントが記録を保持するかどうか、またどの程度保持するかは、完全に実装に委ねられる。この仕様のいかなる部分もそれに依存せず、その存在または不在がサイトによって検出されることもない。

6. Permissions Policy との統合

この仕様は、文字列"cross-origin-storage"によって識別されるポリシー制御機能[permissions-policy]を定義する。そのデフォルトの許可リストは selfである。

[permissions-policy]は、Documentに対する使用許可を定義しているが、 CrossOriginStorageManagerは WorkerGlobalScopeにも公開される。 こちらには 独自のDocumentがない。そのため、チェックは呼び出し元のグローバルオブジェクトに対して記述される。ワーカーのグローバルは、それを所有する Documentを 推移的に解決し、それらすべてが機能を許可しなければならない。

Cross-Origin Storage の権限をチェックするには、グローバルオブジェクト globalが与えられた場合、ブール値を返す。

  1. globalがWindow オブジェクトである場合:

    1. documentを、globalの関連付けられた Documentとする。

    2. documentが null の場合、false を返す。

    3. documentが "cross-origin-storage" ポリシー制御機能の使用を許可されていない場合、false を返す。

    4. true を返す。

  2. globalがWorkerGlobalScope オブジェクトである場合:

    1. ownersを、globalの所有者集合とする。

    2. ownersが空の場合、false を返す。

    3. 各ownerについて、owners内で:

      1. ownerがDocumentであり、かつownerが "cross-origin-storage" ポリシー制御機能の 使用を許可されていない場合、false を返す。

      2. ownerがWorkerGlobalScope オブジェクトであり、ownerを与えて Cross-Origin Storage の権限をチェックするを実行した結果が false である場合、false を返す。

    4. true を返す。

  3. false を返す。

このアルゴリズムが false を返すグローバルオブジェクトでは、そこから行われるすべての requestFileHandle()呼び出しが、 ハッシュの検証、レジストリ検索、または書き込みが行われる前に、 "NotAllowedError" DOMExceptionで 拒否される。

注: 所有者集合を通じて解決することで、この機能が名前だけのオプトアウトになることを防いでいる。blob: URLから作成されたワーカーは、作成元ページのオリジンで実行され、そのページとまったく同じ Cross-Origin Storage ビューを共有する(§ 3 CrossOriginStorageManager インターフェースを参照)。したがって、グローバル自身の Documentのみを参照するチェックでは、すべてのワーカーで自明に満たされてしまい、 new Worker(URL.createObjectURL(&hellip;))に呼び出しを移すだけで、他の点を何も変更せずに cross-origin-storage=()ポリシーを回避できてしまう。

注: ServiceWorkerGlobalScopeの 所有者集合は空であるため、このアルゴリズムはそこで false を返す。これは、所有者集合が何であるかに由来する。これは、ワーカーの作成時に設定され、そのワーカーが 依然としてアクティブに必要とされているかどうかの判断に参照される、生存性の関係である。サービスワーカーには、いかなるDocumentとのそのような関係も意図的に存在しない。 その登録は永続化され、ユーザーエージェントはイベントに応答してグローバルを開始し、サービスワーカーは サービスワーカークライアントなしでも実行できる。したがって、register()を 呼び出したクライアントは登録時には把握できるが、グローバルが実行される頃には通常すでに存在せず、1つの実行中のサービスワーカーが、ポリシーの一致しない多数のクライアントに対応する。

注: サービスワーカーを対象にするには、捕捉されたポリシーが必要であり、その作業は[permissions-policy]および[service-workers]に属する。この仕様が望ましいと考える形は、サービスワーカーのポリシーを、その独自のスクリプト応答におけるPermissions-Policyヘッダーから導出することである。これは、そのポリシーコンテナがすでに応答のCSPを保持している方法と同様である。この方法なら、ポリシーはオリジンの管理下にあり、更新チェックごとに再評価される。登録元クライアントのポリシーをスナップショット化すると、オプトアウトが古くなってしまう。ヘッダーから機能を削除しても、登録がたまたま更新されるまで反映されないためである。このようなモデルが存在するまでは、オプトアウトを回避するために使用できない唯一の答えは、失敗時に閉じることである。

注: SharedWorkerGlobalScopeの 所有者集合には、異なるポリシーを持つ複数の Documentを 保持でき、ワーカーの存続期間中に所有者が追加および削除される。 すべての所有者にこの機能の許可を要求すると、これを許可しない1つの所有者によって、共有ワーカー全体で Cross-Origin Storageが無効になり、その結果は2つの requestFileHandle() 呼び出しの間で変化し得る。反対に、1つの許可する所有者だけを要求すると、この機能を許可する任意のドキュメントが、許可しないドキュメントに代わって再び有効化できてしまう。

7. Cross-Origin-Storage-Allow-Origin ヘッダー

COS エントリは、そのオリジンのリストが空でない場合、 書き込み元オリジンが管理していないオリジンに開示可能である。しかし、そのリストは、スクリプト(originsを通じて)またはマークアップによって宣言される。攻撃者は、スクリプトまたはマークアップの注入に成功すれば、いずれも設定できる。この宣言を、開示されるバイト列のオリジンの運用者に、注入されたコンテンツが偽造できない形で結び付けるため、この仕様は、そのような宣言が指定できるオリジンを制限するレスポンスヘッダーを定義する。

Cross-Origin-Storage-Allow-Origin レスポンスヘッダーは、COS スコープ上限を持つ。これは、同一サイトではない オリジンのリストで書き込みが指定できる オリジンの集合である。バイト列を提供する者がヘッダーを送信するため、これは開示されるバイト列の背後にあるレスポンスから読み取られる。

  • requestFileHandle() による書き込みでは、バイト列がスクリプト内で生成され、それ自体の起点となるレスポンスを持たない場合がある。その場合、これは呼び出し元のグローバルオブジェクトのDocumentを作成するために使用されたレスポンスであり、ワーカーの場合は、それを所有する Documentのものとなる(COS スコープ上限を取得するを参照)。

  • ホスト統合では、格納されるバイト列を持つ取得されたリソースのレスポンスである(取得したリソースを Cross-Origin Storage に格納するを参照)。これはリソースのサーバーであり、それを読み込む Documentのサーバーである必要はない。

宣言されたリストは上限と共通部分を取られる(COS スコープ上限を適用するを参照)ため、上限によって宣言が狭められることはあっても、広げられることはない。

注: このヘッダーは、バイト列を提供する側による承認である。そこに指定されるオリジン、つまり最終的な読み取り元には照会も送信も求められない。指定されたオリジンは、他の読み取り元と同様に、後からrequestFileHandle()を COS ハッシュに対して呼び出すことによってのみ関与する。これは、Access-Control-Allow-Origin[FETCH]とは逆方向に動作する。そこでは、リソースを保持するサーバーが、指定されたオリジンによる読み取りを許可する。ここでは、バイト列の提供者が、後から Cross-Origin Storage から読み取れる者を制限する。書き込みページに注入されたコンテンツは、提供者のレスポンスヘッダーを設定できないため、その制限を拡張できない。

注: このヘッダーはリスト形式にのみ適用される。同一サイトのデフォルトはクロスオリジンの受信者を指定しないため、承認を必要としない。また、"*"形式は、読み取り経路で可用性ゲーティングによって公開ハッシュリストに対して制御される。ユーザーごとの秘密情報によってこのリストを通過させることは決してできないため、書き込み時の上限も必要ない。"*"にヘッダーを要求すると、公開ハッシュリストがすでに防いでいるものを何も追加で防ぐことなく、設定不要のグローバル共有のケースも壊してしまう。

COS スコープ上限を解析するには、ヘッダー リスト headersが与えられた場合、オリジンの集合を返す。

  1. headersから"Cross-Origin-Storage-Allow-Origin"を取得、デコード、および分割した結果をvalueとする。

  2. valueが null の場合、空の集合を返す。

  3. 空の集合をceilingとする。

  4. valueの各tokenについて:

    1. tokenから先頭および末尾のASCII空白を取り除く。

    2. tokenが空文字列の場合、継続する。

    3. tokenに対して基本URLパーサーを実行した結果のオリジンをoriginとする。

    4. originが失敗であるか、不透明オリジンである場合、空の集合を返す。

      注: これには、オリジンに解析されない"*"のtokenも含まれる。Cross-Origin-Storage-Allow-Originヘッダーは、有限個の具体的なオリジンのみを列挙できる。"*"は許可される値ではない。なぜなら、"任意のオリジン"という上限にすると、注入されたコンテンツが任意の受信者を宣言でき、ヘッダーの目的全体が無効になるためである。 無制限の開示は、オリジンの"*"形式を通じてのみ発生する。この形式は公開ハッシュリストによってゲーティングされ、このヘッダーを参照することはない。不正なヘッダー、または"*"を含むヘッダーは、ヘッダーが存在しない場合とまったく同様に、何も承認しない。失敗時には閉じられる。

    5. originをceilingに追加する。

  5. ceilingを返す。

注: 取得、デコード、および分割は U+002C (,) で分割する。そのため、ヘッダー値内のオリジンはカンマで区切られる。これは、Timing-Allow-Origin[RESOURCE-TIMING]およびリスト値を持つHTTPレスポンスヘッダーの一般的な慣例に一致する。一方、兄弟要素であるcrossoriginstorage HTMLコンテンツ属性は、ホスト構文に合わせて空白で区切られる。どちらも同じオリジンの集合に解決される。

COS スコープ上限を取得するには、グローバルオブジェクト globalが与えられた場合、オリジンの集合を返す。

  1. globalがWindow オブジェクトである場合:

    1. documentを、globalの関連付けられた Documentとする。

    2. documentが null の場合、空の集合を返す。

    3. documentのCOS スコープ上限を返す。

  2. globalがWorkerGlobalScope オブジェクトである場合:

    1. ownersを、globalの所有者集合とする。

    2. ownersが空の場合、空の集合を返す。

    3. ceilingを null とする。

    4. ownersの各ownerについて:

      1. 空の集合をownerCeilingとする。

      2. ownerがDocumentの場合、ownerCeilingをownerの COS スコープ上限に設定する。

      3. それ以外で、ownerがWorkerGlobalScope オブジェクトの場合、ownerを与えてCOS スコープ上限を取得するを実行した結果にownerCeilingを設定する。

      4. ceilingが null の場合、ceilingをownerCeilingに設定する。それ以外の場合、ceilingと ownerCeilingの共通部分にceilingを設定する。

    5. ceilingを返す。

  3. 空の集合を返す。

COS スコープ上限を適用するには、オリジンのリスト requestedOriginsと、オリジンの集合 ceilingが与えられた場合、オリジンのリストまたは null を返す。

  1. ceilingが含まない各オリジンを、requestedOriginsから削除する。

    注: COS スコープ上限にない受信者は削除され、書き込みは引き続き成功する。これは、リソース可視性をアップグレードする際に、長すぎるアップグレードの余分な部分を削除する方法と一致する。ユーザーエージェントは、削除された各オリジンを示すコンソール警告を記録することが期待される。

  2. requestedOriginsが空の場合、null を返す。

    注: すべての要素が削除されたリストでは、承認されたクロスオリジンの受信者が存在しない書き込みになるため、同一サイトのデフォルトに戻る。バイト列は引き続き格納され、承認されていない開示のみが抑制される。

  3. requestedOriginsを返す。

すべてのDocumentは、COS スコープ上限を持つ。これはオリジンの集合であり、ドキュメントの作成時に、それを作成するために使用されたレスポンスのヘッダーリストを与えてCOS スコープ上限を解析するを実行した結果に設定される。

注: ワーカーの所有者集合全体で共通部分を取ることは、Cross-Origin Storage の権限をチェックすることを反映している。オリジンがワーカーの上限に含まれるのは、推移的に見て、所有するすべての Documentがそのオリジンを承認した場合だけである。blob:ワーカーは、作成元ページのオリジンおよびCross-Origin Storageビューを完全に共有するため(§ 3 CrossOriginStorageManager インターフェースを参照)、ワーカー自身だけを参照する上限はすべてのワーカーで空になってしまう。また、リスト形式の書き込みをnew Worker(URL.createObjectURL(&hellip;))に移すと、ページが承認した受信者が除去されてしまう。所有者の上限の共通部分を取ることで、いずれか1つの所有者が上限を広げることなく、その承認が保たれる。

DocumentのCOS スコープ上限を、そのレスポンスから設定するには、[HTML]のドキュメント作成手順にフックが必要である。これは、[permissions-policy]および[CSP]がレスポンス処理時に設定される方法と同じである。そのフックが存在するまでは、このセクションで必要な動作を直接説明する。将来の改訂では、[FS]のフックとともに、正式に統合されることが期待される。このフックについては§ 3.3 ファイルの作成と書き込みで説明している。ホスト統合にはこのようなフックは必要ない。取得したレスポンスを取得したリソースを Cross-Origin Storage に格納するに渡せばよく、そこから上限が読み取られる。

8. プライバシーおよびセキュリティ上の考慮事項

この節は RFC 2119 キーワードを使用している箇所を除き非規範的です。リポジトリ内の セキュリティおよびプライバシー質問票も参照してください。

8.1. リソースの完全性

すべてのCOS エントリは、暗号学的ハッシュをキーとし、そのバイト列はそのハッシュに対して検証される(§ 3.3 ファイルの作成と書き込みを参照)。したがって、サイトは requestFileHandle()を通じて取得したファイルが、hashを自ら取得した場合に得られるものと 完全に同じバイト列を持つことを確認できる。開発者は、Cross-Origin Storageの内容を列挙したり、ハッシュをすでに知っていることなくファイルにアクセスしたりすることはできない。

COS ハッシュは秘密ではない。これはコンテンツ識別子であり、すでにファイルを持っている者なら誰でも容易に計算できる。また、この仕様が対象とする広く配布される種類のリソースでは、通常は公開情報であり、モデルやライブラリのリリース時に、そのリリースと併せて公開されることも多い。したがって、ハッシュを知っていればエントリを検索するには十分であるが、それ自体がアクセスを許可するわけではない。検索が成功するかどうかは、完全にオリジンおよび§ 8.3 可用性ゲーティングによって決まる。開発者は、未公開のハッシュをアクセス制御メカニズムとして扱ってはならない。特定のファイルに関心を持つ攻撃者は、そのハッシュを推測する必要はなく、ファイル自体を取得すればよい(§ 8.2 クロスサイトプロービングを参照)。

8.2. クロスサイトプロービング

あるリソースが限られたサイトの集合でのみ使用されている場合、そのリソースがCross-Origin Storageに存在することを知り得た攻撃者は、ユーザーがそれらのサイトのいずれかを訪問した可能性が高いと推測できる。 requestFileHandle()は存在を知るための手段であるため、 各呼び出しは実質的にプローブとなる。この仕様には、プローブが知り得る情報を制限する2つの独立した仕組みがある。

  • オリジン(§ 3.5 リソース可視性のアップグレードを参照)により、格納オリジンは 選択したオリジンの集合に開示を制限できる。そのため、専有的または低人気のリソースは、そもそもグローバルにプローブ可能である必要がない。

  • § 8.3 可用性ゲーティングはさらに、ハッシュがPHL上にない限り、"*"スコープのリソースの開示を、その格納オリジン以外のリクエスト元オリジンから差し止める。これにより、origins: "*"で格納されたリソースが、ウェブ上のすべてのオリジンから自動的にプローブ可能になることはない。この関門は "*"スコープのエントリにのみ適用される。リストおよび同一サイトスコープのエントリについては、格納オリジンがすでに明示的に開示を制限しているため、最初の項目の制限が唯一の関門となる。

最初の項目は、「選択したオリジンの集合」がウェブ全体よりも意味のある程度に小さいままである場合にのみ成立する。originsの形状には、 呼び出し元が非常に多数のオリジンを列挙すること(例えば、公開されている人気サイトランキングから組み立てられたリスト)を阻む要素は何もない。これは、"*"のみが必要とする意図的で明示的なオプトインを回避しつつ、実質的にグローバルな開示を近似することになる。最大オリジンリスト長(§ 5.1 ストレージの制限を参照)はこれを制限する。すなわち、真の複数プロパティのユースケース (共通の管理下にある少数の関連オリジン)には十分収まるが、「あらゆるオリジン」の意味のある近似にはほど遠い小さな上限とすることで、オリジンの制限付きオリジン形式が、 "*"の未宣言の代替として使われることを防ぐ。

ユーザーエージェントはさらに、単一のオリジンからの繰り返しの requestFileHandle() 呼び出しをレート制限またはその他の方法でスロットリングすべきであり、また、プローブされたハッシュが PHL上にあるかどうかにかかわらず、プロービングの試みを識別してブロックするために (例えば、ユーザーごとに生成されたように見えるハッシュへのリクエストのパターンを検出するなど)デバイス上のヒューリスティクスを適用してもよい。

§ 9 他の仕様との統合にあるホスト統合の1つによって行われる検索も、ページにエラーを表示しないものの、同様にプローブである。サイトは、自身のサーバーがフォールバックリクエストを受信したかどうかを観測できる。これは、ここでの「見つからない」という結果が伝えるのと同じ単一ビットの情報を伝える。そのような検索は、この仕様の関門が防いでいる以上の情報を開示することはなく、それらの関門は変更なくそれに適用される。ただし、レート制限が効果的であるためには、これらのサーフェスからの検索が、 requestFileHandle()呼び出しと合わせてカウントされる必要がある。なぜなら、スクリプト可能な統合であれば、同様に容易にループでそれらを発行できるためである。

8.3. 可用性ゲーティング

オリジンが格納 オリジンの外部にある場合に、requestFileHandle()による読み取りが成功するかどうかは、常に、リクエスト元のオリジンがエントリを読み取ることを 許可されているかどうかに依存する。これはオリジンによって決まる。"*"スコープのエントリには、これとは独立した2つ目の問いも適用される。それは、ユーザーエージェントがエントリが存在すること自体を開示する意思があるかどうかであり、PHL メンバーシップおよびGREASEによって決まる。こうしたエントリについては、両方が成立しなければならない。リストスコープまたは同一サイトスコープのエントリについては、最初の問いのみが適用される。 規範的なアルゴリズムについては§ 3.2 ファイルの読み取りを参照。したがって、"NotFoundError"は リソースが存在しないことの証明ではない。リソース自体が存在しない、リクエスト元のオリジンがスコープ外である、"*"スコープのリソースのハッシュがまだ(または永久に)PHL上にない、あるいは GREASEによって真の陽性結果が抑制された、という意味である可能性がある。開発者は、"NotFoundError"を 「ネットワークにフォールバックする」以上に具体的なものとして扱ってはならない。

注: サードパーティ Cookie をサポートするユーザーエージェントでは、 "*" grant により、トラッカーはサードパーティ Cookie がすでに可能であるもの以上に、 サイト間でのユーザーの訪問を関連付けることはできません。PHL だけでは これを制限するものにはなりません。攻撃者は、書き込むサブセットを選択することにより、 個々には PHL の対象となるリソースからサイト間識別子を構築できます。サードパーティ Cookie をブロックするユーザーエージェントでも、サイト間の開示を制限する場合は "*" grant を提供できます。例えば、トップレベルサイトをキーとしてページ上の すべてのフレームで共有される少量のサイト間ルックアップ予算、一定の時間枠内でリロード後も 継続するカウント、およびユーザー操作後にのみ書き込まれたエントリを共有することなどが 例として挙げられます。README の プライバシーに関する考慮事項では、これらの緩和策について説明しています。

8.4. GREASE 化

ユーザーエージェントは、GREASE 化（Generate Random Extensions And Sustain Extensibility）を適用できます。これは、§ 8.3 Availability gating が 本来であれば開示を許可する場合であっても、開示可能なエントリが存在しないかのように 時折応答することです。これによりノイズが追加され、サイトが真の不在とプライバシー保護を 目的とした偽陰性を区別することが困難になります。これは、 UA Client Hints で適用されている手法と同様です。

GREASEは、グローバルに開示可能 な許可のみによって適格となるオリジン、すなわち公開ハッシュリストがゲーティングするのと同じケースにのみ適用される(COS 開示を決定するを参照)。ユーザーエージェントは、格納オリジン、それらと同一 サイトのオリジン、または明示的なオリジンリスト上のオリジンに対して、これを適用してはならない。

GREASEを適用するユーザーエージェントは、対象となるエントリのサイズに見合った判断でこれを行わなければならない。小さなエントリについては、ネットワーク取得へのフォールバックのコストが低いため、時折の偽陰性は妥当なプライバシー上のトレードオフである。ユーザーエージェントは、不当な再ダウンロードが結果として得られるプライバシー上の利益に対して明らかに不釣り合いになるほど大きいエントリ(例えば、ギガバイト規模のAIモデルの重みなど)に対しては、GREASEを適用してはならない。なぜなら、そこでの偽陰性は、完全で、観測可能で、コストの高い再ダウンロードを強制することになるためである。

8.5. フィンガープリンティング

攻撃者が Cross-Origin Storage のプロービングから抽出できる情報は、プローブ対象リソースがどれほど 人気であるかによって制限されます。一般的な AI モデルや広く使われている JavaScript ライブラリなど、 非常に人気のあるリソースをユーザーが持っていると分かっても、そのユーザーがそれを使用する（おそらく非常に 多数の）サイトのいずれかを訪問したことしか分かりません。ユーザーが希少または固有のリソースを持つことを知る方が はるかに多くの情報を与えます。ユーザーエージェントは、名目上の PHL 状態にかかわらず、 ハッシュが意図的にユーザーごとに固有になるよう作られているように見えるリソース（例えば、単一の サイトからしか書き込まれたことがないハッシュ、または異常な頻度で要求されるハッシュ）を検出するオンデバイス ヒューリスティックを適用し、そのようなパターンをプロービングの試みとして扱うことが期待されます。

9. 他の仕様との統合

この節は非規範的です。

ここで定義されるCOS レジストリには、requestFileHandle()を 直接経由することなく、4つのホスト統合からも到達できる。各統合は、それぞれ独自のホスト仕様で定義される。この仕様は、共有される基礎概念(COS ハッシュ、COS エントリ、可用性ゲーティング、および公開ハッシュ リスト)と、それらの統合が基礎とすることを期待される取得したリソースを Cross-Origin Storage に格納する手順を定義する。

  • HTML: すでにintegrity[SRI]を持つ linkおよび script要素に対する crossoriginstorage属性。whatwg/html#12770でWHATWGに提案されている。

  • JavaScript: integrityと併用可能な、ホスト定義のcrossOriginStorageインポート属性。 Import Attributes提案を基礎とし、whatwg/html#12771でWHATWGに提案されている。

  • CSS: integrity()と併用可能なcross-origin-storage() <request-url-modifier>。w3c/csswg-drafts#14056でCSSワーキンググループに提案されている。

  • Fetch: RequestInitの crossOriginStorageオプション。integrity[FETCH]と併用可能であり、whatwg/fetch#1954でWHATWGに提案されている。 これはホスト定義の宛先を持たないため、COS レジストリから提供されたResponseがそのMIMEタイプ、ステータス、およびその他のメタデータをどのように報告するかは、その仕様における未解決の問題である。COS エントリはバイト列のみを格納する。

説明のためだけに、同じグローバル共有リソースを4つの形式それぞれでCross-Origin Storageにオプトインする例を以下に示す。

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

これらの断片は説明のためだけのものである。これらの構文のいずれも、この仕様では定義されない。各形式の正式な文法は、制限付きオリジンリストをどのように記述するかも含めて、それぞれのホスト仕様に属する。表記が意図的に異なるのは、RequestInitのメンバーがsequence<DOMString>を受け取ることができ、originsと完全に一致する一方で、属性値、インポート属性値、およびCSS修飾子の引数はテキストしか保持できないためである。

4つの形式はいずれも、ネットワーク取得にフォールバックする前に、まず一致する開示可能なエントリをCOS レジストリで検索し、正常に取得され完全性が検証されたリソースをCOS レジストリに格納して他のオリジンが再利用できるようにする処理モデルを共有すると期待される。これは、requestFileHandle()が行うものとまったく同じである。格納手順は取得したリソースを Cross-Origin Storage に格納するであり、各統合は取得したレスポンスとともにこれを実行する。したがって、制限付きオリジン値は、そのバイト列を提供するサーバーが送信する、そのリソースのレスポンスに含まれる Cross-Origin-Storage-Allow-Originヘッダーによって制限される(§ 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照)。これらの統合に関する議論は、このリポジトリのイシュートラッカーではなく、それらを実装するホスト仕様のトラッカーで行うべきである。

Public Hash List の取得プロトコル、更新頻度、データ形式、普及度のしきい値、およびガバナンスは、 この仕様書の付属成果物として詳細に設計されている。これは、[URL] Standard の付属データファイルである public suffix list の考え方に沿ったものである。詳細については、このリポジトリの Public Hash List explainer を参照。 この設計では、Public Suffix List のベンダー横断的なローリングリリースの前例をモデルとして、 WHATWG によるガバナンスと、独立して裏付けられた広範な利用状況を基準とする登録条件を提案している。 これは、上記で説明した k-匿名性スタイルの基準を具体的に適用したものであり、 hash が登録される方法の一部としてオフラインで一度だけ適用されるため、 ユーザーエージェントがクエリごとにそれを繰り返すことはない。 これらはすべて、この提案以外ではまだ確立されていない。 このリスト自体の初期の非規範的なコードプロトタイプは、現在このリポジトリの public-hash-list/implementation/ に存在する。 専用のベンダー横断的リポジトリは、PHL explainer で説明されているガバナンス目標として残っている。 この仕様書が依存するのは、hash が PHL 上にあるかどうかだけであり、 したがって、そのリストの取得メカニズム、ガバナンスモデル、またはその他の設計部分がどのように発展しても 正しくあり続ける。 ↵

Document の COS scope ceiling を、その response から設定するには、[HTML] の document 作成ステップにフックが必要である。 これは、[permissions-policy] および [CSP] が response 処理時に設定される方法と同じである。 そのフックが存在するまでは、この節で必要な動作を直接説明する。 将来の改訂では、[FS] のフックとともに正式に統合されることが期待される。 これは § 3.3 Creating and writing files で記載されたものである。 ホスト統合にはそのようなフックは必要ない。 ホスト統合はフェッチされた response を store a fetched resource in Cross-Origin Storage に渡し、そこで ceiling を読み取る。 ↵
