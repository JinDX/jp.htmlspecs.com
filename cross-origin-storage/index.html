概要

オリジン間ストレージ（COS）は、Web アプリケーションが AI モデル、WebAssembly モジュール、非常に普及している JavaScript ライブラリなどの 大容量ファイルを異なるオリジン間で保存および取得できる、コンテンツアドレス可能なキャッシュです。ファイルは URL ではなく暗号学的ハッシュによって識別されるため、あるオリジンによって一度取得された バイト単位で同一のリソースは、ユーザーエージェントが許可する他の任意のオリジンによって、再度ダウンロードすることなく再利用できます。キャッシュ内の存在を、ユーザーがどのサイトを訪問したかの推測に利用できないようにするため、 ファイルのオリジン間開示は、k-匿名性方式の人気度基準を満たすハッシュに限定されます。

1. はじめに

この節は非規範的である。

ストレージは通常、ユーザーのセキュリティとプライバシーを保護するため、オリジンごとに分割される。これは適切な デフォルトだが、非常に大きく、非常に広く利用され、公に配布される一部のリソース （AI モデル、WebAssembly モジュール、JavaScript ライブラリ、ゲームエンジン、大規模な Web フォント） には適していない。これらは、どのサイトが要求してもバイト単位でまったく同じファイルである。2 つの 無関係なオリジンがそれぞれ同じ 8 GB のモデルに依存する場合、オリジン分割ストレージでは ユーザーはそのモデルを 2 回ダウンロードして保持する必要があり、ユーザーの帯域幅、ストレージ、 バッテリー、さらにはネットワーク全体にとって無駄となる。

クロスオリジンストレージ（COS）は、URL ではなく暗号学的ハッシュをキーとする コンテンツアドレス可能なキャッシュであり、 ユーザーエージェントが、その使用を選択した複数のオリジン間で、そのようなリソースの保存済みコピー 1 つを 共有できるようにする。COS へのリソース保存は常に保存元オリジンによる明示的なオプトイン操作であり、 ユーザーエージェントは、本来読み取りを許可されるオリジンに対してさえ、リソースの存在確認を拒否してもよい。 § 8 プライバシーとセキュリティに関する考慮事項を参照。

この仕様のエントリポイントは getFileHandle() メソッドであり、crossOriginStorage を介して公開される。 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.getFileHandle(hash);
  const file = await handle.getFile();
  // ファイルを使用して何かを行う。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // クロスオリジンストレージに（開示可能な状態で）存在しないため、代わりにネットワークから取得する。
  }
}

この仕様は FileSystemFileHandle、 FileSystemWritableFileStream、 および関連する ファイルシステム標準 [FS] の基盤を再利用し、任意のオリジンのプライベートまたはユーザー可視のファイルシステムとは 別個で、オリジン間で共有される専用ファイルシステムに適用する。

この仕様は命令型 JavaScript API と、ホスト統合が基礎として使用する共有保存ステップを定義する。 関連する提案では、同じ基盤キャッシュを他のホスト仕様へ統合する。HTML の link および script 上の crossoriginstorage 属性、crossOriginStorage JavaScript import 属性、CSS の cross-origin-storage() <request-url-modifier>、および crossOriginStorage RequestInit の fetch() 用オプションである。それぞれは 各自のホスト仕様で定義される。§ 9 他の仕様との統合を 参照。

2. 概念

2.1. ハッシュ

COS ハッシュは、次の 構造体であり、 以下の 項目を持つ。

アルゴリズム

文字列であり、 [WEBCRYPTO] が認識するハッシュアルゴリズムを指定する。たとえば「SHA-256」。

値

文字列であり、アルゴリズムによって生成されたダイジェストを小文字の 16 進数で符号化したものである。 「SHA-256」の場合、長さは 64 文字である。

algorithm 辞書メンバーは単純な DOMString として型指定されるが、その値空間は [WEBCRYPTO] が 受け入れるハッシュアルゴリズム名の集合と正確に一致する。HashAlgorithmIdentifier は (object or DOMString) であり、その object 分岐は [WEBCRYPTO] により Algorithm 形状の 辞書へ正規化されるため、呼び出し元は必要なアルゴリズムへ追加 パラメーターを渡せる（たとえば {name: "HMAC", hash: "SHA-256"}）。ハッシュ アルゴリズムはそのようなパラメーターを取らず、 アルゴリズムは コンテンツアドレス可能な キーの一部として保存、比較、ラウンドトリップされ、この仕様の すべての例では単純な文字列が使用される。ここで任意のオブジェクトを許可しても機能は増えず、 等価性とシリアル化を 不必要に複雑にするだけである。そのため DOMString が、このフィールドには より限定的で適切な型である。

2 つの COS ハッシュ値は、等しいといいます。それらの アルゴリズム 値が ASCII 大文字小文字を区別しない一致であり、それらの 値の値が厳密に 等しい場合です。

注: 値はすでに規範的に小文字である（上記参照）ため、その比較は単純な 文字列比較である。アルゴリズムには規範的な大小文字指定がないため、 ASCII 大文字小文字不区別で比較される。

コンテンツアドレス可能な ストアとは、そのエントリが 等価性を持つ COS ハッシュをキーとするものである。すなわち、 同一のバイト列と同じハッシュアルゴリズムを持つ 2 つのファイルは、何個のオリジンが 保存したか、また何個の URL から取得されたかにかかわらず、同じエントリである。

2.2. COS エントリ

各ユーザーエージェントは単一の COS レジストリを持つ。これは マップであり、COS ハッシュ値から COS エントリの 構造体へ対応し、 クロスオリジンストレージを使用するすべてのオリジン間で共有される。 COS エントリは以下の 項目を持つ。

ハッシュ

COS ハッシュ。

バイト

バイト列であり、その ハッシュの アルゴリズム によるダイジェストが ハッシュの 値と等しい。

注: エントリが COS レジストリへ追加されるのは、書き込み側がこれらのバイトを 提供し、ユーザーエージェントがそれらを検証した後に限られる。検証して保存を参照。要求済みだが 完了していない書き込みはレジストリ上に一切表現されず、これにより読み取り経路では進行中の 書き込みと存在しないものとを区別できない。§ 8.3 進行中の書き込みを参照。

オリジン

リストであり、オリジンに対し、公開ハッシュ リストとは独立して、明示的なクロスオリジン読み取りアクセスを許可する。この許可は、 同一サイトにあるすべてのオリジンへ拡張されるため、 https://a.example を列挙すると https://www.a.example も許可される。初期状態では 空であり、以後は増加するだけである。これは誰がエントリを読み取れるかを決める 3 つの独立した加算的な許可のうち 1 つであり、 残る 2 つはその 保存元オリジン（それらと 同一サイトのオリジンを含め常に読み取り可能）と グローバルに 開示可能である。

注: origins が明示的に空の リスト （origins: []）である書き込みは、 origins を省略した書き込みとまったく同じ許可を与える。すなわちエントリの 保存元オリジンと、それらと 同一サイトのオリジンであり、これは各エントリが 持つ基準である（COS 開示を決定を参照）。上限を 適用することで、 空の リストは null となるため、どちらの書き込みも 作成要求を完了の残りへ同じ状態で到達する。明示的な リストは受信者を追加するだけであり、 書き込み元自身のサイトからエントリを隠すことはない。

グローバルに開示可能

真偽値であり、初期値は false で、エントリが グローバル（「*」）な利用可能性を要求して書き込まれたかどうかを記録する。true の場合、そのエントリは § 8.4 利用可能性ゲーティングを通過する任意のオリジン、すなわち ハッシュが PHL 上にあり、かつ GREASE 処理によって抑制されないオリジンから読み取り可能である。一度設定されると true のままとなる。

注: これは 項目として オリジンとは別であり、 後続の グローバル利用可能性要求が、既存の明示的な オリジン リストに 「*」許可を追加できるようにする。 2 つを 1 つのフィールドへ統合すると、バイトを提供した書き込み元が リストスコープのエントリを「*」スコープへ変えられる。§ 8.4 利用可能性ゲーティングは 「*」許可にのみ適用されるため、それまで リストによってエントリを読み取れたオリジンが NotFoundError を ハッシュが PHL 上にないたびに受け取るように なってしまう。許可を独立させておけば、可視性の変更はすべて厳密に加算的となり、 アップグレード可能だがダウングレード不可という 要件を満たす。

保存元オリジン

集合であり、各々がこのエントリのバイトの オリジンとして少なくとも一度 書き込みを正常に完了しているものを含む。 ページ読み込みをまたいで永続化され、 増加し続ける。§ 5.2 退避で説明する場合を除き縮小しない。 保存元オリジン内のオリジンは、 getFileHandle() を介して常にエントリのハンドルを取得でき、オリジンや エントリの ハッシュが 公開ハッシュリスト （PHL）上にあるかどうかには依存しない。 § 3.5.1 元の保存者によるアクセスを参照。

ユーザーエージェントには関連付けられた クロスオリジンストレージキューがあり、これは 新しい並列キューを開始した結果である。COS レジストリに対するすべての操作はこのキューに エンキューされ、 エンキューされた 順序で実行され、相互に入り交じらない。

2.3. 公開ハッシュリスト

あるハッシュがクロスオリジンストレージに存在することを確認する行為自体が、 ユーザーの閲覧履歴に関する情報を漏洩させる可能性がある（§ 8.2 クロスサイト プロービングを参照）。これは特にグローバル 許可に対するリスクである。エントリの明示的な オリジン リストと、各エントリが持つ同一サイト基準は、 保存元オリジンによる明示的な選択によってすでに開示範囲が限定されている。一方、 エントリを グローバルに開示可能にすると、Web 上の任意の オリジンへ公開される可能性がある。その 特定のリスクを制限するため、グローバルに開示可能なリソースは、その 許可を通じて 保存元オリジン外のオリジンへ、そのハッシュが追加の 独立したゲート、すなわち 公開ハッシュリスト （PHL）に含まれる場合にのみ開示可能である。これはベンダー中立で、 実装定義の COS ハッシュ 値の許可リストである。ハッシュが公開ハッシュリストへ登録されるのは、k-匿名性風の 普及度基準（たとえば、バイト単位で同一のものが独立した一定数以上の オリジンに出現すること）を満たした場合だけであり、共有キャッシュ内に存在することを確認しても 個々のユーザーについて有益な情報にならないようにする。

COS ハッシュ hash が 公開 ハッシュリスト上にあるとは、hash が ユーザーエージェントの現在の 公開ハッシュリストのスナップショット内のエントリと 等しい場合である。

公開ハッシュリストの取得プロトコル、 更新頻度、データ形式、普及度しきい値、ガバナンスは、この仕様に付随する成果物として詳細に設計され、 公開サフィックスリスト、すなわち [URL] 標準に付随するデータファイルと同様の位置付けである。詳細はこのリポジトリの 公開ハッシュリストの解説を参照。その設計は Public Suffix List のベンダー横断的なローリングリリースの先例をモデルとして、WHATWG によるガバナンスと、 独立して裏付けられた普遍性に基づく登録基準を提案する。 これは前述の k-匿名性風の基準を、ハッシュ登録時の一度だけオフラインで適用する 具体例であるため、ユーザーエージェントがクエリごとに繰り返すことはない。このいずれも 現時点ではこの提案の外部で確立されていない。リスト自体の初期的で非規範的なコードプロトタイプは、 当面このリポジトリの public-hash-list/implementation/ に置かれている。専用の ベンダー横断リポジトリは、PHL 解説で説明されるガバナンス上の目標のままである。この 仕様が依存するのは、ハッシュが PHL 上にあるかどうかだけであるため、 リストの取得機構、ガバナンスモデル、その他の設計がどのように進化しても仕様は正しいままである。

3. CrossOriginStorageManager インターフェイス

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> getFileHandle(
      CrossOriginStorageGetFileHandleHash hash,
      optional CrossOriginStorageGetFileHandleOptions options = {});
};

dictionary CrossOriginStorageGetFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageGetFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

各 Navigator および WorkerNavigator オブジェクトには、関連付けられた CrossOriginStorageManager オブジェクトがある。crossOriginStorage getter の手順は this に関連付けられた CrossOriginStorageManager を返すことである。

各 CrossOriginStorageManager オブジェクトには、関連付けられた オリジンがあり、オブジェクトが 作成されたときに this の 関連設定オブジェクトの オリジンに設定される。

注: スクリプト自体に関する情報とは無関係に、 関連設定オブジェクトからオリジンを取得することには、ワーカーについて明記すべき重要な帰結がある。 blob: URL から作成されたワーカーは、それを作成したコンテキストの オリジンを持つため、そのオリジンの クロスオリジンストレージビューを完全に共有する。つまり、そのようなワーカーが書き込んだものを作成元ページが読み戻せ、 ページが保存したものをワーカーが読み取れる。blob: URL 自体は独自のオリジンではなく、 それを取り消してもワーカーはそのビューから切り離されない。data: URL から作成されたワーカーは 不透明オリジンを持つ。この仕様は現在、 getFileHandle() が呼び出し元オリジンが不透明である場合に何をするかを定義していない。 不透明オリジンに関する COS 要求を検証の規則が適用されるのは、 呼び出し元が指定するオリジンだけである。不透明オリジンには、 保存元 オリジンのキーや 同一 サイト比較に使用できる安定した識別情報がないため、 付与できる意味のある許可も存在しない。

3.1. getFileHandle() メソッド

handle = await navigator . crossOriginStorage . getFileHandle(hash)

hash で識別されるファイルがクロスオリジンストレージに存在し、呼び出し元オリジンに 開示可能である場合、そのファイルのハンドルを返す。それ以外の場合は 「NotFoundError」 DOMException で拒否する。 「NotFoundError」は、ファイルが クロスオリジンストレージに物理的に存在しないことを証明するものではない。§ 8.4 利用可能性ゲーティングを参照。呼び出し元は これを「代わりにネットワークから取得する」と扱える。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true })

hash で識別されるファイルをクロスオリジン ストレージへ書き込むために使用できるハンドルを返し、まだ存在しない場合は新しいエントリを作成する。デフォルトでは同一サイトのオリジンに制限される。 呼び出し元は、そのエントリがすでに存在していたかどうかにかかわらず、ハンドルの createWritable() メソッドを介してファイル内容全体を書き込む必要がある。ユーザーエージェントはその時点で、書き込まれたバイトが hash にハッシュされることを検証し、そうでなければ「DataError」 DOMException で拒否する。この要件は、 オリジンが作成要求を、hash がすでに存在したかどうかを調べるオラクルとして利用することを防ぐ。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: "*" })

上記と同じだが、書き込み完了後は、hash に対する要求が § 8.4 利用可能性ゲーティングを通過する任意のオリジンにもエントリを開示可能にする。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

上記と同じだが、開示を列挙したオリジンおよび、それぞれと 同一サイトのオリジンに制限する （呼び出し元オリジン、すでに 保存元オリジンに含まれる任意のオリジン、およびそれらと 同一サイトのオリジンに加えて）。

getFileHandle(hash, options) メソッドの 手順は次のとおり。

  1. result を 新しい promise とする。

  2. realm を this の 関連 Realm とする。

  3. global を this の 関連グローバルオブジェクトとする。

  4. origin を this に関連付けられた オリジンとする。

  5. global を与えて クロスオリジンストレージ権限を確認を実行した結果が false の場合、次を行う。

    1. global を与えて グローバルタスクをキューに入れ、DOM 操作タスクソース上で result を 「NotAllowedError」 DOMException によって 拒否する。

    2. result を返す。

  6. validationFailure を、hash と options を与えて COS 要求を検証を実行した結果とする。

  7. validationFailure が null でない場合:

    2. ユーザーエージェントがこの要求に GREASE 処理を適用することを選択した場合、 null を返す。

      注: GREASE 処理も グローバル許可にのみ適用される。上で確認された許可はこのステップへ 到達しない。保存元オリジンとその同一サイトオリジンは 1 つの信頼単位であり、 明示的な オリジン リスト内のオリジンは、 Cross-Origin-Storage-Allow-Origin ヘッダーによって許可された書き込み元により 意図的に指定されており、その同一サイトオリジンも 含まれる。

    3. entry を返す。

  6. null を返す。

3.3. ファイルの作成と書き込み

作成要求を完了によって作成された FileSystemFileHandle には、関連付けられた 要求されたオリジンがある。これは、 ハンドルへの書き込みが正常に完了した後で 検証して保存がエントリの オリジンを アップグレードしようとする値である。

クロスオリジンストレージファイルシステムを指すすべての FileSystemFileHandle には、関連付けられた COS ハッシュ、すなわちそれが指す COS ハッシュと、 関連付けられた COS オリジン、すなわちそれを取得した オリジンと、 関連付けられた 読み取り可能真偽値があり、これは getFile() がその特定のハンドルを介して対象エントリのバイトを開示できるかを制御する。 読み取り要求を完了によって返されるハンドルでは true であり、これはすでに 利用可能性ゲーティングを通過している。一方、 作成 要求を完了によって返されるハンドルでは、その同じハンドルについて 検証して保存が成功するまで false である。

注: ハンドルが指すのは COS ハッシュであり、COS エントリではない。作成要求を完了は、 COS レジストリ内にエントリがなく、今後も取得されない可能性のあるハッシュについて ハンドルを返すため、検証して保存がエントリを作成するまでは参照先となる エントリが存在しない。

注: これは意図的に各ハンドルの性質である。 作成要求は、ハッシュのエントリがすでに存在するかどうかにかかわらず ハンドルを返す（作成 要求を完了を参照）ため、エントリ単位の規則では任意のオリジンが getFileHandle() を create: true で呼び出し、すぐに自身が一度も書き込んでいないエントリを読み取れてしまい、 オリジン、 PHL メンバーシップ、または GREASE 処理を満たさずに内容を知ることができる。この 仕様のすべての開示制御は読み取り経路で適用されるため、エントリ単位でゲーティングすると作成要求が それらすべてを回避できる。まず呼び出し元に正しいバイト全体を提供させることで、 作成によって取得したハンドルを介した読み取り成功は、呼び出し元がすでに持っていない情報を何も開示しない。

promise result、COS ハッシュ hash、 CrossOriginStorageGetFileHandleOptions options、グローバルオブジェクト global、および Realm realm を与えて 作成 要求を完了するには:

  1. requestedOrigins を、options["origins"] を与えて 要求された オリジンを正規化を実行した結果とする。

  2. requestedOrigins が リストである場合、 requestedOrigins を、 global を与えて COS スコープ上限を取得を実行した結果と requestedOrigins を与えて COS スコープ上限を適用を実行した結果に設定する。

  3. handle を 新しい FileSystemFileHandle を作成した結果とする [FS]。その ロケーターは、realm 内の クロスオリジンストレージファイルシステムにおける hash を指す。

  4. handle の COS ハッシュを hash に設定する。

  5. handle の COS オリジンを global の 関連設定オブジェクトの オリジンに設定する。

  6. handle の 要求されたオリジンを requestedOrigins に設定する。

  7. handle の 読み取り可能を false に設定する。

    注: このアルゴリズムは COS レジストリを参照せず、 変更もしない。それは不可能である。 結果は hash がすでに保存されているかどうかに依存してはならず、そうでなければ作成 要求自体が過去の存在を開示することになる（§ 8.2 クロスサイトプロービングを参照）。 したがって handle は、エントリが存在する場合、一度も書き込まれていない場合、または他者が 現在書き込み中の場合のいずれでもまったく同じ条件で返され、この呼び出し元がバイトを提供するまで読み取りアクセスを持たない。

    注: ここでは何も登録されないため、 ハンドルを要求した後で放棄し、 createWritable() を呼び出さない、または得られたストリームを閉じない呼び出し元は、 レジストリを要求前と完全に同じ状態に残す。他のオリジンはその要求が 発生したことを観測できず、後続の読み取りを抑制するプレースホルダー状態にハッシュを固定することもできない。 § 8.3 進行中の書き込みを参照。

    注: requestedOrigins は、 バイトの書き込みと検証が完了した後にのみ、 リソースの可視性をアップグレードを通して 検証して 保存によって適用される。これにより、 作成要求は可視性を広げる前にバイト全体を提供する必要がある。§ 3.5 リソースの可視性のアップグレードを参照。

  8. global を与えて グローバルタスクをキューに入れ、 DOM 操作タスクソース上で result を handle によって 解決する。

(DOMString or sequence<DOMString>) または undefined の origins を与えて 要求された オリジンを正規化するには、「*」、リストの オリジン、または null を返す。

  1. origins が 存在しない場合、 null を返す。

  2. origins が「*」の場合、「*」を返す。

  3. list を « » とする。

  4. origins の各 candidate について それぞれ処理する（単一の 文字列は、1 要素の リストとして 扱う）。

    1. candidateOrigin を、candidate に対して 基本 URL パーサーを実行して得られた オリジンとする。

      注: COS 要求を検証により、各 candidate が 不透明でないオリジンへ解析されることはすでに確認されている。

クロスオリジンストレージファイルシステムを指すハンドルに対して createWritable() を呼び出して取得した FileSystemWritableFileStream が閉じられるとき [FS]、 ユーザーエージェントは、その閉じる操作の promise が fulfillment される前に、そのハンドルを与えて下記の 検証して保存手順を実行しなければならない。

注: これは閉じる処理がどのように 引き起こされたかに関係なく適用される。明示的な close() 呼び出し、またはその ソースの末尾に到達し、デフォルトで宛先も閉じる pipeTo() 呼び出しのどちらでもよい。[STREAMS]はストリームが閉じた時点で この 2 つを区別せず、このアルゴリズムも区別しない。

ストリームが閉じられた FileSystemFileHandle handle、完全に書き込まれた バイト列 bytes、および閉じる操作の 関連設定オブジェクトの オリジン origin を与えたときの 検証して保存手順は次のとおり。

  1. hash を handle の COS ハッシュとする。

  2. computedValue を、hash の アルゴリズムで指定された アルゴリズムを使用し、[WEBCRYPTO] に従って計算した、 bytes の小文字 16 進ダイジェストとする。

  3. computedValue が hash の 値と完全に等しくない場合:

    1. 閉じる操作の promise を「DataError」 DOMException によって 拒否する。

    2. これらの手順を中止する。

    注: 失敗した書き込みにはクリーンアップすべきものがない。 作成要求を完了はエントリを登録していないため、 検証済みバイトを生成しなかった書き込みは COS レジストリを変更せず、同じハッシュに対する後続の getFileHandle() 呼び出しは、その書き込みが一度も試みられなかった場合と同じ 「NotFoundError」 を得る。すでに別のオリジンが書き込んだエントリも同様に影響を受けない。このアルゴリズムは バイトと許可を追加することしかない。

      1. entry を新しい COS エントリに設定し、その ハッシュを hash、 バイトを bytes、オリジンを空の リスト、 グローバルに開示可能を false、保存元オリジンを空の 集合とする。

      2. 設定して COS レジストリ[hash] を entry とする。

      注: これはこの 仕様で COS レジストリへエントリを追加する唯一のステップであり、 bytes が hash に対して検証された後にのみ実行される。2 つの 書き込み元がどちらもハッシュが存在しないことを確認し、同時に書き込んだ場合、それぞれがここへ到達する。 後から エンキューされた側は先に作成されたエントリを見つけ、下で自身のオリジンと許可を追加するだけである。 両者のバイトは同じ値へハッシュされるため、一度だけ保存すれば十分である。

    3. origin がまだ存在しない場合、entry の 保存元オリジンへ 追加する。

    4. entry と handle の 要求されたオリジンを与えて リソースの可視性をアップグレードを実行する。

    5. handle の 読み取り可能を true に設定する。

      注: このハンドルだけが 読み取り可能になる。同じハッシュに対する別のハンドルで、 まだ書き込みが完了していない別の作成要求から取得されたものは、読み取り不可のままである。

クロスオリジンストレージファイルシステムを指す FileSystemFileHandle 上で呼び出された createWritable() は、 keepExistingData の値や、 対象の COS ハッシュが COS レジストリ内にエントリを持つかどうかにかかわらず、 内容が空から始まる FileSystemWritableFileStream を生成しなければならない。

注: [FS]は通常 keepExistingData を、既存ファイルの内容でストリームを 初期化するものとして定義する。ここでそれを尊重すると、呼び出し元が一度も保有していないバイトについて保存元 オリジンになれてしまう。作成要求はエントリがすでに存在するかどうかにかかわらずハンドルを返すため、 呼び出し元は別のオリジンが保存したハッシュの writable を開き、何も書かずに閉じても、 引き継がれたバイトが要求した値へハッシュされ得る。それにより オリジン、公開ハッシュリスト、および GREASE 処理を一度も確認せずに読み取りアクセスを取得できる。これは 2 つの個別には許可された操作を組み合わせた 利用可能性 ゲーティング回避である。 同じ理由により、検証して保存は すべての作成要求で完全な内容を要求する。

注: したがって何も書き込まずに閉じられた writable は 空のバイト列を保持するが、これは 呼び出し元が必要とするどのエントリについても要求された値へハッシュされないため、検証して保存は 他の不一致と同様に「DataError」 DOMException で拒否する。その場合に ストレージまたは I/O 障害を代わりに報告する実装は、検証結果を無関係なエラーの背後に隠すことになる。

ファイルシステム標準 [FS] はまだ、依存する 仕様が FileSystemWritableFileStream の 閉じる手順に追加の書き込み単位検証をフックするための拡張点を定義していない。そのようなフックが存在するまで、この節では必要な動作を直接説明する。 将来の改訂では [FS] との正式な統合が期待される。

3.4. 取得したリソースの保存

§ 9 他の仕様との統合に列挙されたホスト統合は、 取得したリソースを FileSystemFileHandleを経由せずに保存する。 それらのホスト仕様は、取得したバイト列がその 統合で要求される完全性チェックに合格した後、次のアルゴリズムを実行することが期待される。

取得したリソースを Cross-Origin Storage に保存するには、レスポンス response、バイト列 bytes、COS ハッシュ hash、"*"、リストである文字列、 または null である origins、および環境設定オブジェクト settingsを与え、次を行う：

  1. settingsの グローバルオブジェクトを与えてCross-Origin Storage 権限を確認するを実行した結果が false なら、返る。

  2. originsが null でない場合、 optionsを «[ "origins" → origins ]» とし、 それ以外の場合は «[ ]» とする。

  3. hashと optionsを与えてCOS リクエストを検証するを実行した結果が null でないなら、 返る。

  4. computedValueを、bytesについて、hashのalgorithmが指定する アルゴリズムを用い、[WEBCRYPTO]に従って計算した小文字16進数のダイジェストとする。

  5. computedValueが hashのvalueと厳密に等しくない場合、返る。

    注: 統合自体の完全性 メタデータには複数のダイジェストを列挙でき、その いずれか1つとの一致で条件を満たす。この手順により、エントリがこれらの 正確なバイト列から生成されるハッシュをキーとして持つことを保証する。

  6. requestedOriginsを、 options["origins"]を与えて要求された オリジンを正規化するを実行した結果とする。

  7. requestedOriginsがリストである場合：

    1. responseがフィルターレスポンスなら、 internalResponseを responseの内部レスポンスとし、それ以外の場合は response とする。

    2. requestedOriginsを、 requestedOriginsと、internalResponseのヘッダーリストを与えてCOS スコープ上限を解析するを実行した結果を与えてCOS スコープ上限を適用するを実行した結果に設定する。

    注: 上限は取得した リソース自身のレスポンスから得られるため、その バイト列を供給するサーバーが、どのオリジンに開示できるかを決定する。読み込み側の Documentの COS スコープ上限は関与しない。その運営者は リソースを制御しておらず、受信者を認可できるようにすると、任意のサイトが別サイトのアセットを 自ら選んだオリジンと共有可能だと宣言できてしまう。ユーザーエージェントは内部 レスポンスからヘッダーを読み取るため、不透明なフィルターレスポンスでも機能し、ヘッダーが ページに公開されることはない。

  8. originを settingsのオリジンとする。

  9. 次の手順を Cross-Origin Storage キューにエンキューする：

    1. entryを、COS レジストリ内に存在する場合は、そのhashが hashと等しい COS エントリとし、存在しない場合は null とする。

    2. entryが null の場合：

      1. entryを新しいCOS エントリに設定し、そのhashを hash、 bytesを bytes、originsを空のリスト、 グローバルに開示可能を false、保存元オリジンを空の 集合とする。

      2. 設定することにより、COS レジストリ[hash]を entryにする。

      注: 検証して保存すると同様に、 エントリは bytesが hashに対して検証された後にのみ作成され、 その検証は統合の integrity チェックによってすでに行われている。同じハッシュに対する getFileHandle() の書き込みがまだ 進行中であっても影響を受けない。それはレジストリ状態を保持せず、それ自身の検証して保存するは 通常どおり完了し、このエントリを見つけて自身のオリジンと許可を追加する。

    3. originがまだ存在しない場合、entryの保存元オリジンに originを追加する。

    4. entryと requestedOriginsを与えてリソースの可視性をアップグレードするを実行する。

注: 検証して保存すると同様に、保存では エントリがすでに "written" である場合を含め、 常に完全なバイト列が必要となるため、以前から存在していたかどうかについて何も明らかにしない。統合が ネットワーク取得前に行う検索は読み取りであり、可用性ゲーティングおよび § 8.2 クロスサイトプロービングのプロービングに関する考慮事項の対象となる。

3.5. リソースの可視性のアップグレード

COS エントリの可視性は アップグレードできるが、ダウングレードすることはできない。

リソースの 可視性をアップグレードするには、COS エントリ entryと、"*"、リストである オリジン、または null である requestedOriginsを与え、次を行う：

  1. requestedOriginsが null なら、返る。

    注: originsを省略すると、 すべてのエントリがすでに持つ同一サイトの 可用性のみを要求する（COS 開示を決定するを参照）ため、 追加するものはない。

  2. requestedOriginsが "*" の場合：

    1. entryのグローバルに開示可能を true に設定する。

    2. 返る。

    注: これはグローバル許可を追加するだけで、 entryのoriginsには触れない。明示的なorigins リストをすでに持っていたエントリは それを保持するため、その リスト上のすべてのオリジンは、エントリが グローバルに開示可能になった後も PHLに依存しないアクセスを維持する。これこそ、 2つの許可を別々に保存する核心的な理由である。グローバルに開示可能を参照。

  3. requestedOriginsの各 candidateOriginについて反復する：

    1. entryのoriginsが candidateOriginを含む場合、 続行する。

    2. entryのoriginsのサイズが ユーザーエージェントの 最大オリジンリスト長に等しい場合、 中断する。

      注: 残りの candidateOrigin値は、このアップグレードから黙って除外される。なぜなら 書き込み自体はすでに成功しており、ユーザーエージェントはエントリの origins リストが上限に達したことを コンソール警告として記録することが期待されるためである。

    3. candidateOriginを entryのoriginsに追加する。

注: アップグレードはoriginsに追加するか、グローバルに開示可能を true に設定することしかない。リストを要求する書き込み元は、 すでにグローバルに開示可能なエントリも、 そうでないエントリと同様に拡張する。これは2つの許可が 独立しているためであり、新しく列挙されたオリジンは、"*" 許可が有効なままでも PHLに依存しないアクセスを得る。

注: 元の 保存元以外のサイトを含む任意のサイトは、そのハッシュに対応する正しいバイト列を提供する限り、 エントリのoriginsを拡張できる。 これは意図的である。ハッシュに対応する正しいバイト列をすでに所持しているサイトは、そのhashが何を表すかについて、構造上 元の保存元と同等の権威を持つためである。

3.5.1. 元の保存元によるアクセス

オリジンが書き込みを正常に完了したCOS エントリ（つまり、 エントリの保存元オリジンに含まれる任意のオリジン）は、その後いつでも getFileHandle()を介して そのハンドルを取得できる。これはエントリの origins値にも、 そのhashがPHL 上にあるかどうかにも依存しない。 これは、オリジンが自ら保存したものには常にアクセスできる Cache API のモデルを反映する。

4. Cross-Origin Storage ファイルシステム

Cross-Origin Storage ファイルシステムは、 任意のオリジンのバケットファイルシステムまたはローカルファイルシステムアクセスのルートとは異なるファイルシステムルートであり、その エントリは、COS レジストリのCOS エントリ項目と1対1で対応する。

Cross-Origin Storage ファイルシステムは、[FS]の通常の呼び出しごとの 権限確認 モデルを使用しない。このファイルシステムから得られるすべての FileSystemFileHandleは、 スクリプトに返される前に § 3.2 ファイルの読み取りまたは§ 3.3 ファイルの作成と 書き込みによってすでに完全に認可されているため、そのようなハンドルで getFile() または createWritable()を呼び出しても、 追加の権限プロンプトが発生することはない。

したがって、そのようなハンドルに対する queryPermission() および requestPermission() は プロンプトが表示され得ないため、"prompt" を報告してはならない。 作成リクエストによって取得されていないハンドルの書き込みモードについては "denied"を報告し、 それ以外では "granted" を報告しなければならない。

注: 書き込みは、ハンドルが 実際に欠いている可能性がある唯一の能力である。作成リクエストだけが 書き込み可能なハンドルを生成するため、他のハンドルの書き込みモードで "granted" を報告すると、 createWritable()が拒否する能力を 持つと主張することになる。読み取りは、 読み取り可能なハンドルを持つ呼び出し元がそれを介して読み取れるため、"granted" のままである。要求しても どちらの答えも変更できない。表示するプロンプトも、許可を記録できる状態も存在しないためである。

読み取り可能が false である Cross-Origin Storage ファイルシステムを参照する FileSystemFileHandleに対して getFile()を呼び出した場合、 "NotAllowedError" DOMExceptionで拒否しなければならない。 これは2つの異なる場合を扱う：

  • まだ書き込みが行われていない 作成リクエストからのハンドルであり、 その参照先ハッシュにCOS レジストリ内のエントリがまだない場合。返すべき検証済みバイト列は 存在せず、呼び出し元は自身の未完了の書き込みを ファイルの実際の内容であるかのように観測できてはならない。

  • 別の他のオリジンがすでに書き込んだハッシュに対する作成リクエストからのハンドル。 検証済み バイト列は存在するが、この呼び出し元はそれらを提供しておらず、 可用性ゲーティングにも合格していないため、エントリについて何も知ってはならず、 その 存在すら知ってはならない。

注: 拒否は両方の場合で同一なので、 何も開示しない。読み取りパスでは意図的に避けているにもかかわらず、ここで "NotAllowedError" が安全なのはそのためである。このハンドルは 呼び出し元自身が自身の作成リクエストによって取得したものであり、ハンドルは他の オリジンでデシリアライズできない（§ 4.1 ハンドルの転送を参照）。したがって答えが オリジン境界を越えることはなく、 レジストリの内容に対して一定である。これに対して§ 8.3 進行中の書き込みでは、読み取りパス上の 異なるエラーはその境界を越えることになる。

ハンドルの読み取り可能が true になると、それに対して呼び出された getFile()は、 参照先エントリのbytesを内容とする Fileを返す。これは [FS]が、 ファイル エントリの バイナリデータがそのバイト列である場合についてすでに定義している動作そのものである。

Cross-Origin Storage ファイルシステムを参照する FileSystemFileHandleは、 ファイルシステムロケーターを持ち、そのパスは、 そのCOS ハッシュのvalueである単一の 文字列を含むリストであり、その ルートは Cross-Origin Storage ファイルシステムである。

注: [FS]は nameを、 ハンドルのロケーターのパスの最後の構成要素として定義しているため、これによって nameも決まる。 それは ハッシュである。エントリ自体には名前がなく、ハッシュが唯一の識別子であるため、 それを報告することには、空文字列では失われる情報が含まれる。

エントリには名前も包含ディレクトリもないため、[FS]の構造的な機能のほとんどには 操作対象がない。識別性は例外であり、コンテンツアドレス指定されたエントリが 常に答えられる唯一の問いである。COS レジストリには、COS ハッシュごとに 最大1つのCOS エントリしか存在しないため、2つの ハンドルが同じエントリを参照するのは、そのハッシュが等しい場合に限る。

Cross-Origin Storage ファイルシステムを参照する FileSystemFileHandle上で isSameEntry()を、 同じファイルシステムを参照し、 同じオリジンによって取得された引数とともに呼び出した場合、2つのハンドルの COS ハッシュ項目が等しいなら true を、そうでなければ false を返さなければならない。

注: これを拒否すると、ユーザー エージェントがすでに保持している情報を捨てることになる。

isSameEntry()を、 呼び出し側のオリジンが取得していない引数、 またはCross-Origin Storage ファイルシステム以外のファイルシステムを参照する引数で呼び出した場合、拒否しなければならない。

注: その場合に false を返すと、 2つのハンドルが異なるエントリを参照していると断定することになり、 これは呼び出し側オリジンが検査する権利を持たないハンドルについての主張である。拒否は、 比較を実行できなかったということだけを表す。

Cross-Origin Storage ファイルシステムを参照する FileSystemFileHandleに対して呼び出された move() および remove() は、 "NotAllowedError" DOMExceptionで拒否し、 参照先のエントリを変更してはならない。

注: エントリは、その保存元 オリジンに含まれるすべてのオリジンで共有されるため、 削除を認めると1つのサイトが他のサイトが依存するデータを破壊できてしまう。削除は 退避およびユーザー自身のストレージ制御に属する。名前変更や親変更には、 エントリがCOS ハッシュによって名付けられ、包含ディレクトリを持たないため、 操作対象がない。

注: 執筆時点では、どちらのメソッドも[FS]にも File System Access API にも定義されていない （WICG/file-system-access#214）ため、 エラー名は removeEntry()に従う。これは [FS]がエントリ削除用に 定義している操作であり、readwrite アクセスが 許可されていない場合にはアクセス結果のエラー名で拒否する。ここでも拒否が正確な動作である。 操作自体には意味があるが、許可されないためである。

createSyncAccessHandle()には ここで規則を設ける必要はない。その手順は、ハンドルがバケットファイルシステム内にない場合、 "InvalidStateError" DOMExceptionで拒否する。 Cross-Origin Storage ファイルシステムは任意のオリジンのものとは異なるファイルシステムルートなので、 [FS]がすでに 拒否することと、その名前の両方を決定している。

注: これは、この仕様が独立に考えても 望む結果である。FileSystemSyncAccessHandleは 呼び出し元に書き込み可能なファイル記述子を渡すため、 エントリのbytesを、 それが保存されているCOS ハッシュとの対応を 崩す形で変更できてしまい、 エントリを開示可能な他のすべてのオリジンもその同じバイト列を読むことになる。

4.1. ハンドルの転送

FileSystemFileHandleは シリアライズ可能オブジェクトである[FS]ため、COS エントリを参照するものは 別の環境設定オブジェクトへ、たとえば postMessage(message, options)を使って渡すことができる。 これは getFileHandle()と並ぶ、 そのようなハンドルを得る第2の方法であるため、 ここでも制約される。

シリアライズ手順は、valueと serializedを与え、 Cross-Origin Storage ファイルシステムを参照する FileSystemFileHandleについて、 追加で次を行う：

  1. serialized.[[COSHash]]を valueのCOS ハッシュに設定する。

  2. serialized.[[COSOrigin]]を valueのCOS オリジンに設定する。

  3. serialized.[[COSMayRead]]を valueの読み取り可能に設定する。

デシリアライズ手順は、serialized、 valueおよび realmを与え、追加で次を行う：

  1. serialized.[[COSOrigin]]が realmの 環境設定オブジェクトのオリジンと同一オリジンでない場合、 "DataCloneError" DOMExceptionをスローする。

  2. valueのCOS ハッシュを serialized.[[COSHash]]に設定する。

  3. valueのCOS オリジンを serialized.[[COSOrigin]]に設定する。

  4. valueの読み取り可能を serialized.[[COSMayRead]]に設定する。

注: 同一 オリジンチェックがなければ、転送は この仕様のあらゆる開示制御を一度に無効化してしまう。読み取り可能が true のハンドルは、 すでにそのハンドルを要求したオリジンについて 可用性ゲーティングを適用するを通過している。それを別の オリジンへ post すると、そのオリジンに対してorigins、 PHL メンバーシップ、またはGREASE 処理を一度も評価せずに、エントリのバイト列を渡してしまう。これは File System Standard の既存のハンドルの扱いと一致しており、そこでもハンドルは 同一オリジンの受信者にしか有用でない。

注: 読み取り可能は ハンドルとともに移動する。そのため、まだ書き込みが行われていない作成リクエストのハンドルは転送後も 読み取り不能のままであり、 読み取りリクエストのハンドルは再度ゲーティングされることなく読み取り可能なままである。到着時に再ゲーティングすると、 呼び出し元が同じ ハンドルを繰り返し転送することで可用性をプローブできてしまう。

5. ストレージ管理

5.1. ストレージ制限

ユーザーエージェントは、単一のオリジンが 他のオリジンのエントリを追い出そうとしてキャッシュを埋め尽くすことを防ぐため、 オリジンが正常な書き込みを通じて COS レジストリに寄与できる総バイト数に 制限を設けなければならない。具体的な制限は 実装定義である。オリジンの書き込みがその 制限を超える場合、ユーザーエージェントは 書き込みを "QuotaExceededError" DOMExceptionで拒否し、 コンソールに警告を 記録すべきである。

注: エントリはコンテンツアドレス可能なので、同じ バイト列を同じハッシュで繰り返し書き込むオリジンは、最初の正常な書き込みを超えて追加のクォータを消費しない。§ 2.2 COS エントリを参照。

ユーザーエージェントには、単一のorigins リストが 含められるオリジン数を制限する正の整数である、実装定義の 最大オリジンリスト長もある。 これはリストが最初に提供された時点（COS リクエストを検証するを参照）と、 後で既存のエントリにマージされる時点（ リソースの可視性をアップグレードするを参照）の両方で適用されるため、 1回の呼び出しでも時間をまたぐ多数の呼び出しの累積効果でも、エントリのoriginsを 無制限に増やすことはできない。メモリ使用量を制限することに加え、これはオリジンのリストが、 "*" の宣言されていない代替として使われることも防ぐ。§ 8.2 クロスサイトプロービングを参照。

この制限を超えた場合の扱いは、2つの場所で異なる。なぜなら2つの呼び出しは 操作のまったく異なる時点で行われるためである。

  • COS リクエストを検証するでは、ファイルが 取得、ハッシュ化、または 書き込まれる前に制限が確認される。それを超えた呼び出し元には即座に "TypeError" が返され、 それ以上何も起こらない。これは不正な他の origins 値と同じ扱いである。

  • リソースの可視性をアップグレードするでは、制限に達するのは 別々の独立した書き込み呼び出しで要求されたオリジンの累積効果による場合だけであり、 長期間にわたり無関係なオリジンによる可能性もある。また、この呼び出しのバイト列がすでにハッシュ化、 検証され、永続的に保存された後にしか確認できない。その時点で書き込みを拒否すると、 正常に完了し、すでに検証され、しかも非常に大きい可能性がある書き込みを無関係な管理上の制限のために破棄することになり、 単一の呼び出し元の誤りに帰することさえできない。したがって書き込み自体は 成功させ、容量を超えるオリジンだけをoriginsから除外し、 コンソール警告を出す。これは既存の 許容的なものからより制限されたものへのリクエストの扱いを反映する。完全には実現できないオリジンの要求は 黙って上限に抑えられ、それを伴う書き込みはなお 成功する。この仕様の他の§ 8.4 可用性ゲーティングと同様に、 呼び出し元には、要求したオリジンが 実際に追加されたかどうかを後から確実に確認する方法はない。その オリジンとしての後続の getFileHandle() 呼び出しも、オリジンが追加されていたとしても失敗する可能性がある（たとえばエントリが 退避された、またはユーザーエージェントがリクエストを制限した場合）ため、その結果をどちらかの確認として 解釈してはならない。

5.2. 退避

この節は非規範的である。

ストレージ圧迫時、ユーザーエージェントはCOS レジストリからエントリを退避してよい。 たとえば、各エントリに最近アクセスした保存元オリジン全体で 最終使用時刻が最も古いものから削除するポリシーを使用できる。ユーザーエージェントは、 保存されているファイル、各ファイルにアクセスしたオリジンをユーザーが確認し、手動で エントリを削除したり Cross-Origin Storage データをすべて消去したりできる設定 UI を提供することが期待される。

ユーザーがオリジンのサイトデータを消去した場合、ユーザーエージェントは、そのオリジンが含まれるすべての 保存元 オリジン集合からそのオリジンを削除すべきである。その削除後にCOS エントリの 保存元 オリジンが空になった場合、ユーザーエージェントはそのエントリを削除対象として考慮してよい。

5.3. 手動で追加されたエントリ

この節は非規範的である。

前述の設定 UI は、ユーザーがディスク上にすでに持っているファイルを Cross-Origin Storage に直接追加できるようにしてよい（たとえば、どのウェブサイトとも無関係にダウンロードした AI モデル）。 その場合、スクリプトが一度も getFileHandle()を呼び出す必要はない。 そのようなエントリには、 書き込みを帰属させる要求元オリジンがないため、命令的 API だけでは答えられない2つの疑問が生じる：

  • § 3.5.1 元の保存元によるアクセスにおける 元の保存元は誰か？ 誰もいない。エントリの保存元オリジンは空で開始する。 したがって、どのオリジンも通常の 可用性ゲーティングおよびoriginsチェックを免除されず、 他のすべての要求元オリジンと同様にその対象となる。これは正しい結果である。実際にはどのオリジンも バイト列を書き込んでいないためである。

  • そのようなエントリは、originsを省略する通常の書き込みと同様に、 同一サイトのみに制限すべきか？ いいえ。"same-site" は要求元オリジンを基準にして初めて意味を持ち、 手動追加にはそれがないため、"same-site" が指すサイトも存在しない。 ユーザーエージェントは、そのようなエントリをグローバルに 開示可能にし、 明示的なorigins リストは空のままにすることが期待される。 ファイルを手動で事前投入することは、 ユーザーがまだ訪問していないサイトに、ユーザーがディスク上にすでに持っているファイルを再利用させるという 目的を、他のオリジンが実際にそれを発見できる場合にしか果たせないからである。ユーザーエージェントの設定 UI は さらに、ユーザーがより狭い範囲を選択できるようにしてよい。

この方法で追加されたエントリは、それ以外の点では ウェブサイトが getFileHandle()を介して書き込んだものと区別できない。 同じ 可用性ゲーティングと可視性 アップグレード規則が、同じ許可を持つ他のエントリとまったく同様に適用される。 これには、エントリが最終的に グローバルに開示可能になる場合、つまり手動追加の既定である場合の、 PHL 上にあるチェックも含まれる。

5.4. 来歴メタデータ

この節は非規範的である。

COS エントリは、そのバイト列が どこから来たかについて意図的に何も記録しない。識別子は hashだけであり、同じバイト列は いくつのオリジンが保存したか、 いくつの URL から取得されたかに関係なく同じエントリである（§ 2.2 COS エントリを参照）。 URL は1つの 書き込み元による取得の属性であるため、複数のオリジンが書き込んだエントリに対して 非恣意的に1つを選ぶ方法はない。またバイト列のように検証可能でもない（§ 8.1 リソースの完全性を参照）。 さらに、パスやクエリ文字列は特定の文書、 アカウント、またはセッションを特定し得るため、オリジンという粗い値を 保存元 オリジンに保持するより、ユーザーの閲覧に関するはるかに多くの情報を含む。 したがってそれをエントリに記録すると、高エントロピーのシグナルを originsおよび§ 8.4 可用性 ゲーティングが課すために存在する開示制限の外側へ迂回させることになる。

それを求める動機自体は現実的である。§ 5.2 退避で説明した設定 UI にある 数 GB のファイルを見ているユーザーも、getFileHandle() 呼び出しが失敗した理由をデバッグしている開発者も、 ファイルがどこから来たかを知りたい。ユーザーエージェントは、エントリと並べて実装非公開の来歴記録 （たとえば、その各保存元オリジンが バイト列を取得した URL とその時刻）を保持することでそれを提供してよい。ただし、その記録は エントリの外側に保持されるユーザーエージェント状態として扱わなければならない：

  • それはスクリプトに公開されない。この仕様のいかなるものもそれを開示せず、今後追加されるものも 開示すべきではない。getFileHandle()も、 それが返す FileSystemFileHandleも、 そのような記録の存在すら、ましてその 内容を明らかにしてはならない。特に、要求元オリジンは、自身が 生成していない記録を観測できてはならない。

  • それは信頼された非ウェブのサーフェス、すなわちユーザーエージェント自身の設定とストレージ 検査 UI、その開発者ツール、そして（ユーザーエージェントが拡張機能プラットフォームを持つ場合） 明示的にユーザーが付与した権限で保護された拡張機能 API を通じてのみ提示される。これは、閲覧履歴を 公開する他の API と同等の扱いである。検討中の拡張機能サーフェスについては、この リポジトリの ブラウザー拡張機能統合ポイントの explainerを参照。

  • それは検証されておらず、そのように提示される。そこにある URL は、その バイト列を書き込んだオリジンによる主張である。内容を保証するのはhashだけである（§ 8.1 リソースの完全性を参照）。2つのオリジンが同じエントリについて異なる URL を 記録してもよく、どちらかが 不正確または意図的に誤解を招くものである可能性もある。

  • それは、エントリおよび帰属先オリジンと寿命を共有する。エントリが 退避または削除されたときに破棄され、オリジンに帰属する部分は、そのオリジンが 保存元オリジンから削除されたとき、ユーザーがその オリジンのサイトデータを消去した場合も含めて破棄される（§ 5.2 退避を参照）。

そのような記録はコンテンツから不可視であるため、ユーザーエージェントがそれを保持するかどうか、およびどの程度 保持するかは完全に実装に委ねられる。この仕様のいかなるものもそれに依存せず、その 存在または不在をサイトが検出することはできない。

6. Permissions Policy との統合

この仕様は、文字列 "cross-origin-storage" で識別される ポリシー制御機能 [permissions-policy]を定義する。その既定の許可リスト は self である。

[permissions-policy]は Documentについて使用を許可されているを定義するが、 CrossOriginStorageManagerは 自身の Documentを持たない WorkerGlobalScopeにも公開される。 したがって確認は、呼び出し側のグローバルオブジェクトを基準に記述される。ワーカーのグローバルは、それを所有する Documentへ 推移的に解決され、そのすべてが この機能を許可しなければならない。

グローバルオブジェクト globalを与えて Cross-Origin Storage 権限を確認するには、 真偽値を返すものとして次を行う：

  1. globalが Window オブジェクトである場合：

    1. documentを globalの関連付けられた Documentとする。

    2. documentが null なら false を返す。

    3. documentが "cross-origin-storage" ポリシー制御機能の使用を許可されていない場合、 false を返す。

    4. true を返す。

  2. globalが WorkerGlobalScope オブジェクトである場合：

    1. ownersを globalの所有者集合とする。

    2. ownersが空なら false を返す。

    3. ownersの各 ownerについて反復する：

      1. ownerが Document であり、かつ ownerが "cross-origin-storage" ポリシー制御機能の使用を許可されていない場合、 false を返す。

      2. ownerが WorkerGlobalScope オブジェクトであり、ownerを与えて Cross-Origin Storage 権限を確認するを実行した結果が false なら、false を返す。

    4. true を返す。

  3. false を返す。

このアルゴリズムが false を返すグローバルオブジェクトから行われるすべての getFileHandle() 呼び出しは、 ハッシュ検証、レジストリ検索、または書き込みが 行われる前に "NotAllowedError" DOMExceptionで拒否される。

注: 所有者集合を介して解決することで、この機能が 名目上だけのオプトアウトになるのを防いでいる。blob: URL から作成されたワーカーは、その作成元ページの オリジンで実行され、そのページの Cross-Origin Storage ビューを正確に共有する（ § 3 CrossOriginStorageManager インターフェイスを参照）。そのため、 グローバル自身の Documentだけを参照するチェックは、 すべてのワーカーで自明に満たされてしまい、呼び出しを new Worker(URL.createObjectURL(&hellip;))へ移すだけで、 それ以外を何も変えずに cross-origin-storage=()ポリシーを回避できてしまう。

注: ServiceWorkerGlobalScopeの 所有者集合は空なので、この アルゴリズムはそこで false を返す。これは所有者集合の意味に従うものである。つまり、 ワーカー作成時に設定され、そのワーカーがまだ能動的に必要かどうかを判断するために参照される 生存関係である。サービスワーカーは意図的に、どの Documentともそのような関係を持たない。 登録は永続化され、ユーザーエージェントはイベントに応じてグローバルを起動し、 サービスワーカークライアントが1つもない状態でも実行できる。register()を呼び出したクライアントは 登録時には分かるが、グローバルが実行される頃には 通常すでに存在せず、1つの実行中サービスワーカーが、ポリシーの一致しない可能性のある 多数のクライアントにサービスを提供する。

注: サービスワーカーを対象にするには、取得時に保存されたポリシーが必要であり、 その作業は [permissions-policy]および[service-workers]に属する。この仕様が 望ましいと考える形は、サービスワーカー自身のスクリプトレスポンスの Permissions-Policyヘッダーからそのポリシーを導出することである。これはポリシーコンテナが そのレスポンスの CSP をすでに保持する方法と同様であり、オリジンの制御下に保たれ、 更新確認のたびに再評価される。登録元クライアントのポリシーをスナップショットするとオプトアウトが 古くなり、ヘッダーから機能を削除しても 登録がたまたま更新されるまで有効にならない。そのような モデルが存在するまでは、fail closed がオプトアウトの回避に使用できない唯一の答えである。

注: SharedWorkerGlobalScopeの 所有者集合には、異なるポリシーを持つ複数の Documentが含まれ得て、 ワーカーの生存期間中に所有者が増減する。 すべての所有者が機能を許可することを要求するということは、1つの所有者がそれを禁止すると 共有ワーカー全体で Cross-Origin Storage が無効になり、2つの getFileHandle() 呼び出しの間で答えが変わる可能性もあることを意味する。代わりに、許容的な所有者を1つだけ要求すると、 機能を許可する任意の文書が、禁止する 文書に代わって機能を再有効化できてしまう。

7. Cross-Origin-Storage-Allow-Origin ヘッダー

COS エントリのorigins リストが 空でない場合、そのエントリは書き込み元オリジンが 制御していないオリジンにも開示できる。しかし、そのリストはスクリプト（ originsを介して） またはマークアップによって宣言され、スクリプトやマークアップの注入に成功した攻撃者は どちらも設定できる。その宣言を、開示されるバイト列を持つオリジンの運営者に 結び付け、注入されたコンテンツが偽造できない形にするため、この 仕様は、その宣言が指定できるオリジンを制限するレスポンスヘッダーを定義する。

Cross-Origin-Storage-Allow-Origin レスポンスヘッダーは、 COS スコープ上限、 すなわち、書き込みが同一サイトではない origins リストで指定できるオリジンの集合を保持する。 バイト列を供給する側がヘッダーを送るため、それは 開示されるバイト列の背後にあるレスポンスから読み取られる：

  • getFileHandle() の書き込みでは、バイト列は スクリプトで生成され、元となるレスポンスを持たないことがある。その場合は、呼び出し側グローバルオブジェクトの Documentを 作成するために使われたレスポンス、またはワーカーの場合は、 それを所有する Document群のレスポンスである （COS スコープ上限を取得するを参照）。

  • ホスト統合では、保存されるバイト列を持つ取得済みリソースのレスポンスである （取得したリソースを Cross-Origin Storage に保存するを参照）。これはリソースのサーバーであり、 それを読み込む Documentの サーバーとは限らない。

宣言されたリストは 上限との積集合を取られる（ COS スコープ上限を適用するを参照）ため、上限は宣言を狭めることしかできない。

注: このヘッダーは、バイト列を 供給する側による認可である。そこに指定されたオリジン、 つまり最終的な読み取り側は相談されず、何も送信しない。列挙されたオリジンが関与するのは後になってからであり、 他の読み取り側と同様に getFileHandle()を COS ハッシュに対して呼び出す。 これは Access-Control-Allow-Origin [FETCH]とは逆方向に働く。 そちらではリソースを持つサーバーが特定のオリジンによる読み取りをオプトインする。ここではバイト列の供給者が、 後で Cross-Origin Storage から誰が読み取れるかを制限し、書き込み ページに注入されたコンテンツはその制限を拡張できない。供給者のレスポンスヘッダーを設定できないためである。

注: このヘッダーはリスト形式にのみ適用される。 同一サイトの既定値はクロスオリジンの 受信者を指定しないため認可を必要とせず、"*" 形式は読み取りパスで、 公開ハッシュリストに対する 可用性ゲーティングによって制御される。ユーザーごとの秘密はこれを決して通過できないため、 書き込み時の上限も不要である。"*" にヘッダーを要求すると、 公開ハッシュリストがすでに防いでいないものを新たに防ぐことなく、設定不要のグローバル共有ケースを 壊してしまう。

ヘッダー リスト headersを与えてCOS スコープ上限を解析するには、 オリジンの集合を返すものとして、次を行う：

  1. valueを、headersから "Cross-Origin-Storage-Allow-Origin" を取得し、デコードし、分割する結果とする。

  2. valueが null なら、空の集合を返す。

  3. ceilingを空の集合とする。

  4. valueの各 tokenについて反復する：

    1. tokenから先頭および末尾の ASCII 空白を除去する。

    2. tokenが空文字列なら、続行する。

    3. originを、tokenに対して基本 URL パーサーを実行した結果のオリジンとする。

    4. originが failure または不透明オリジンなら、空の集合を返す。

      注: これには "*" である tokenも含まれる。これはオリジンとして解析されない。 Cross-Origin-Storage-Allow-Originヘッダーが列挙できるのは有限個の 具体的な オリジンだけである。"*" は許可された値ではない。"任意のオリジン"という上限を認めると、 注入されたコンテンツが好きな受信者を宣言でき、 ヘッダーの目的全体を無効化してしまうためである。 無制限の 開示は "*" のorigins形式を通じてのみ実現され、 これは 公開ハッシュリストによってゲーティングされ、この ヘッダーを参照することはない。不正な、または "*" を含むヘッダーは 欠落したヘッダーとまったく同様に何も認可しない。失敗時は閉じる。

    5. originを ceilingに追加する。

  5. ceilingを返す。

注: 取得し、デコードし、分割するは U+002C (,) で分割するため、 ヘッダー 値内のオリジンはコンマ区切りとなり、Timing-Allow-Origin [RESOURCE-TIMING]および リスト値を持つ HTTP レスポンスヘッダーの一般的な 慣例と一致する。一方、兄弟である crossoriginstorage HTML コンテンツ 属性は、ホスト構文に合わせて空白区切りである。どちらも同じ オリジンの集合に解決される。

グローバルオブジェクト globalを与えてCOS スコープ上限を取得するには、 オリジンの集合を返すものとして、次を行う：

  1. globalが Window オブジェクトである場合：

    1. documentを globalの関連付けられた Documentとする。

    2. documentが null なら、空の集合を返す。

    3. documentのCOS スコープ上限を返す。

  2. globalが WorkerGlobalScope オブジェクトである場合：

    1. ownersを globalの所有者集合とする。

    2. ownersが空なら、空の集合を返す。

    3. ceilingを null とする。

    4. ownersの各 ownerについて反復する：

      1. ownerCeilingを空の集合とする。

      2. ownerが Documentなら、 ownerCeilingを ownerの COS スコープ上限に設定する。

      3. それ以外で、ownerが WorkerGlobalScope オブジェクトなら、ownerCeilingを ownerを与えてCOS スコープ上限を取得するを 実行した結果に設定する。

      4. ceilingが null なら ceilingを ownerCeilingに設定し、 それ以外では ceilingを ceilingと ownerCeilingの積集合に設定する。

    5. ceilingを返す。

  3. 空の集合を返す。

リストであるオリジン requestedOriginsと、 集合であるオリジン ceilingを与えてCOS スコープ上限を適用するには、リストであるオリジンまたは null を返すものとして、次を行う：

  1. ceilingが 含まない各オリジンを requestedOriginsから削除する。

    注: COS スコープ 上限にない受信者は除外されても、書き込みは 成功する。これは、長さ上限を超えたアップグレードが余分なものを リソースの可視性をアップグレードするで除外する方法と一致する。ユーザーエージェントは 除外された各オリジンを示すコンソール警告を 記録することが期待される。

  2. requestedOriginsが空なら、null を返す。

    注: すべての メンバーが除外されたリストでは、 書き込みに認可されたクロスオリジン受信者が1つも残らないため、同一サイトの既定値にフォールバックする。 バイト列は保存される。認可されていない開示だけが行われない。

  3. requestedOriginsを返す。

すべての Documentは、 集合であるオリジンのCOS スコープ上限を持ち、 文書作成時に、その文書を作成するために使用されたレスポンスの ヘッダーリストを与えて COS スコープ上限を解析するを 実行した結果に設定される。

注: ワーカーの所有者集合全体で積集合を取ることは、 Cross-Origin Storage 権限を確認するを反映する。 オリジンがワーカーの上限内にあるのは、推移的にすべての所有 Documentが そのオリジンを認可した場合だけである。blob: ワーカーは作成元ページの オリジンと Cross-Origin Storage ビューを正確に共有するため（ § 3 CrossOriginStorageManager インターフェイスを参照）、 ワーカー自身だけを参照する上限は すべてのワーカーで空になり、リスト範囲の書き込みを new Worker(URL.createObjectURL(&hellip;))へ移すと、ページが認可した受信者が失われてしまう。 所有者の上限の積集合を取ることで、単一の 所有者がそれを拡張できるようにせず、その認可を維持できる。

Documentの COS スコープ上限をそのレスポンスから設定するには、 [HTML]の文書 作成手順にフックが必要である。これは[permissions-policy]および[CSP]が レスポンス処理時に設定される方法と同じである。そのフックが存在するまでは、この節で 必要な動作を直接記述する。将来の改訂では、[FS]のフックと並べて正式に統合することが期待される（§ 3.3 ファイルの作成と書き込みを参照）。ホスト統合にはそのような フックは不要である。それらは取得済みレスポンスを取得したリソースを Cross-Origin Storage に保存するへ渡し、そこから 上限を読み取る。

8. プライバシーとセキュリティに関する考慮事項

この節は RFC 2119 キーワードを使用する箇所を除いて非規範的である。リポジトリ内の セキュリティとプライバシーに関する質問票も 参照。

8.1. リソースの完全性

すべてのCOS エントリは暗号学的ハッシュを キーとし、そのバイト列もそのハッシュに対して検証される（ § 3.3 ファイルの作成と書き込みを参照）。したがってサイトは、 getFileHandle()を通じて得られたファイルが、 hashを自身で取得した場合とまったく同じバイト列を持つことを確信できる。 開発者は Cross-Origin Storage の内容を列挙できず、そのハッシュをすでに知らない限り ファイルにアクセスすることもできない。

COS ハッシュは秘密ではない。 それはコンテンツ識別子であり、 ファイルをすでに持つ誰でも簡単に計算できる。またこの仕様が対象とする広く配布される種類の リソースについては通常公開情報であり、モデルやライブラリの リリースとともに公開されることが多い。したがってハッシュを知っていればエントリを検索するには十分だが、 それ自体がアクセスを与えるわけではない。検索が成功するかどうかは、originsと § 8.4 可用性ゲーティングによって完全に決定される。開発者は未公開のハッシュを アクセス制御の仕組みとして扱ってはならない。 特定のファイルに関心を持つ攻撃者はそのハッシュを推測する必要はなく、ファイル 自体を取得すればよい（§ 8.2 クロスサイトプロービングを参照）。

8.2. クロスサイトプロービング

リソースが限られた一群のサイトでのみ使用されている場合、そのリソースが Cross-Origin Storage に 存在することを知ることができる攻撃者は、ユーザーがそれらのサイトのいずれかを訪問した可能性が高いと推測できます。 getFileHandle() が存在を知るための仕組みであるため、各呼び出しは 実質的にプローブです。この仕様にある 2 つの独立した仕組みが、プローブから得られる情報を 制限します:

  • origins（ § 3.5 リソース可視性のアップグレードを参照）により、保存元 オリジンは 開示を選択した一群のオリジンと、それらと同一サイトのオリジンに制限できるため、独自仕様または人気の低いリソースを グローバルにプローブ可能にする必要は ありません。

  • § 8.4 可用性ゲーティングはさらに、 "*" スコープのリソースについて、そのハッシュが保存元オリジン外の要求元オリジンに対する開示を、ハッシュがPHL 上にある場合を除き差し控えます。 これにより、origins: "*" で保存されたリソースが Web 上のすべてのオリジンから自動的にプローブ可能になることはありません。このゲートは "*" スコープの エントリにのみ適用されます。リストスコープおよび同一サイトスコープのエントリでは、保存元オリジンがすでにそれらの開示範囲を明示的に制限しているため、 最初の箇条書きの制限が唯一のゲートです。

最初の箇条書きが成り立つのは、「選択した一群のオリジン」が Web 全体より意味のある程度に小さい場合だけです。 origins の形式自体は、呼び出し元が 非常に多数のオリジン（たとえば、公開されている 上位サイトランキングから作成したリスト）を列挙することを妨げません。これは、"*" だけが要求する 意図的かつ明示的なオプトインを迂回しながら、機能上グローバルな開示に近づくことになります。オリジンリストの最大 長（ § 5.1 ストレージ制限を参照）がこれを制限します。正当な 複数プロパティのユースケース （共通の管理下にある少数の関連オリジン）には十分である一方、 「すべてのオリジン」に意味のある形で近づくにははるかに足りない上限にすることで、origins の制限オリジン形式を "*" の未宣言の代替として使用できないようにします。

ユーザーエージェントはさらに、単一オリジンから繰り返される getFileHandle() 呼び出しをレート制限するか、その他の方法で抑制すべきであり、 プローブ対象のハッシュがPHL 上にあるかどうかに関係なく、 端末上のヒューリスティック（たとえば、ユーザーごとに生成されているように見えるハッシュへの要求パターンを検出すること）を適用して プロービングの試行を識別してブロックしてもかまいません。

§ 9 他の仕様との統合にあるホスト統合のいずれかによって行われる検索も、 ページにエラーが現れないとしても同様にプローブです。サイトは、自身の サーバーがフォールバック要求を受信したかどうかを観察でき、これはここでの「見つからない」 結果と同じ 1 ビットの情報を伝えます。このような検索は、この仕様のゲートが開示しないものを何も開示せず、 それらのゲートはそのまま適用されます。ただし、レート制限が有効なのは、それらの サーフェスからの検索も getFileHandle() 呼び出しと合わせて数える場合だけです。スクリプト可能な統合は 同じように容易にループ内でそれらを発行できるためです。

8.3. 進行中の書き込み

要求されたものの完了していない書き込みは、すべてのオリジンにとって、 まったく書き込まれたことのないハッシュと区別できてはなりません。この仕様は構造的にそれを実現します。COS エントリがCOS レジストリに追加されるのは、検証して保存または 取得したリソースを Cross-Origin Storage に保存によってのみであり、どちらの場合も完全なバイト列が ハッシュに対して検証された後に限られます。作成要求を完了はレジストリの読み取りも書き込みもしません。 したがって、読み取りが観察できるプレースホルダー状態は存在せず、読み取り経路上には 可用性ゲーティングを適用する前に応答できる分岐もありません。

別の方法として、作成要求が行われた時点でプレースホルダーを登録し、それに対する同時 読み取りを識別可能なエラーで拒否すると、呼び出し元は何らかのオリジンが今まさに 指定したハッシュを書き込んでいることを知ることができます。その 1 ビットは些細に聞こえますが、そうではありません。これは次の場合にも利用可能になります:

  • エントリに対して一切の許可を持たないものを含む任意のオリジンに対して。プレースホルダーは 許可を持たず、読み取りはCOS 開示を決定が実行される前に 応答されるためです。

  • PHL 上にない、また今後もなり得ないハッシュを含む任意のハッシュについて。したがって攻撃者は ユーザーごとの値から導出したハッシュを使用でき、これはまさに§ 8.6 フィンガープリンティング が検出するために存在するパターンです。

  • GREASE 処理なしで。これはゲーティング 手順まで到達した開示にのみ適用されるため、 そのビットにはノイズがありません。

  • バイト列を一切提供せずに。したがってオリジンごとのストレージ制限も § 5.2 退避も、そのようなビットをオリジンがいくつ作成できるかを制限しません。

したがって、2 つのサイトに埋め込まれたトラッカーは、最初のサイトで任意の幅の識別子を生成し、 2 番目のサイトでストレージコストなしに読み戻すことができ、origins、 公開ハッシュ リスト、および GREASE 処理をまとめて迂回できます。プレースホルダーはサービス拒否の ベクトルにもなります。真に人気のあるリソースのハッシュを固定すると、そのプレースホルダーが存続する限り、 他のすべてのオリジンによる読み取りを抑止できるためです。

注: その代償は、ある呼び出し元が 別の呼び出し元がすでに大きなファイルをダウンロードしていることを検出し、 重複するダウンロードの開始を避ける能力です。これは実際の代償であり、 この仕様の以前のドラフトがここで識別可能なエラーを使用していた理由です。この能力は、 最も重要な単一オリジン内では Web Locks、BroadcastChannel、 または shared worker を使用して回復できます。 これらはいずれもオリジン境界をまたいで何も開示しません。オリジンをまたいだ場合、その節約はほぼ理論上のものです。無関係な 2 つの オリジンが同じ瞬間に同じハッシュで競合する必要があり、どちらもまだ書き込んでいないエントリは、いずれにしても PHL 上にあるまでは相手に開示できないためです。

注: "NotAllowedError" は、まだ書き込みが行われていない 作成によって取得したハンドル上の getFile() に対する応答のままです（§ 4 Cross-Origin Storage ファイルシステムを参照）。その応答は レジストリの内容に関係なく一定であり、ハンドルはオリジンをまたいでデシリアライズできないため（§ 4.1 ハンドルの 転送を参照）、 要求を行ったオリジンにしか届きません。したがってこれはチャネルではありません。

8.4. 可用性ゲーティング

保存元 オリジン外のオリジンからの getFileHandle() 読み取りが成功するかどうかは常に、 要求元オリジンがエントリを読み取ることを許可されているかどうかに依存し、これはoriginsによって管理されます。"*" スコープのエントリでは、2 つ目の 独立した問いも適用されます。すなわち、ユーザーエージェントがエントリが そもそも存在することを開示する意思があるかどうかで、これはPHL メンバーシップとGREASE 処理によって管理されます。このようなエントリでは両方が 成立しなければなりません。リストスコープまたは同一サイトスコープのエントリでは、最初の問いだけが適用されます。 規範的アルゴリズムについては§ 3.2 ファイルの読み取りを参照してください。したがって、"NotFoundError" は リソースが存在しないことの証明ではありません。リソースが存在しないこと、要求元 オリジンがスコープ外であること、"*" スコープのリソースのハッシュが PHL 上に（まだ、または永遠に）ないこと、あるいは GREASE 処理が真陽性を抑止したことを意味する場合があります。開発者は "NotFoundError" を 「ネットワークにフォールバックする」以上に具体的な意味として扱ってはなりません。

注: サードパーティ Cookie をサポートするユーザーエージェントでは、 "*" の許可によってトラッカーが サイト間のユーザー訪問を関連付けられる程度は、サードパーティ Cookie で既に可能な程度を超えません。PHL だけでは これを制限できません。攻撃者は、個別には PHL の対象となるリソースのうちどの部分集合を書き込むかを選ぶことでクロスサイト識別子を構築できます。サードパーティ Cookie をブロックするユーザーエージェントでも、クロスサイト開示を制限するなら "*" の許可を提供できます。たとえば、 トップレベルサイトをキーとし、ページ上のすべてのフレームで共有される少量のクロスサイト検索予算、 一定期間リロードをまたいで持続するカウント、およびユーザージェスチャー後にのみ書き込み済みエントリを共有する仕組みなどです。README の プライバシーに関する考慮事項では、これらの緩和策について説明しています。

8.5. GREASE 処理

ユーザーエージェントは GREASE 処理（ランダムな拡張を生成し拡張可能性を維持する）を適用してもよく、これは § 8.4 可用性ゲーティングが通常なら 開示を許可する場合でも、開示可能なエントリが存在しないかのように時折応答することです。 これによりノイズが追加され、サイトが実際の不在と プライバシー上の理由による偽陰性とを区別しにくくなります。これは UA Client Hintsで適用されている手法と似ています。

GREASE 処理は、グローバルに 開示可能という 許可だけによって条件を満たすオリジンにのみ適用されます。これは公開ハッシュリストがゲートするのと同じ場合です（COS 開示を決定を参照）。ユーザーエージェントは、 保存元オリジン、明示的な origins リスト上のオリジン、または それらのいずれかと同一サイトのオリジンに適用してはなりません。

GREASE 処理を適用するユーザーエージェントは、対象となるエントリのサイズに見合った判断をしなければなりません。 小さなエントリでは、ネットワーク取得へのフォールバックが安価であるため、時折の 偽陰性は妥当なプライバシー上のトレードオフです。ユーザーエージェントは、誤った再ダウンロードのコストが得られるプライバシー上の利益に対して 明らかに不釣り合いとなるサイズのエントリ （たとえば、ギガバイト規模の AI モデルの重み）に GREASE 処理を適用してはなりません。そこで偽陰性が発生すると、 完全な、観察可能で高コストな再ダウンロードが強制されるためです。

8.6. フィンガープリンティング

攻撃者が Cross-Origin Storage のプロービングから抽出できる情報は、プローブ対象のリソースがどれほど人気かによって制限されます。 一般的な AI モデル や広く使用されている JavaScript ライブラリのような非常に人気のあるリソースをユーザーが持っていると分かっても、 ユーザーがそれを使用する（場合によっては非常に 多数の）サイトのいずれかを訪問したことしか明らかになりません。ユーザーが希少または一意なリソースを持つと分かる方がはるかに多くの情報をもたらします。 ユーザーエージェントは、ユーザーごとに意図的に一意に見えるハッシュを持つリソース （たとえば、単一の サイトによってしか書き込まれたことのないハッシュや、異常な頻度で要求されるハッシュ）を検出する端末上のヒューリスティックを適用し、 名目上の PHL 状態とは無関係に、そのようなパターンをプロービングの試行として扱うことが期待されます。

9. 他の仕様との統合

この節は非規範的です。

ここで定義されるCOS レジストリには、 getFileHandle() を直接経由せずに、4 つのホスト統合からもアクセスできます。それぞれの 統合は各自のホスト仕様で定義されます。この仕様は、共有される 基礎概念（COS ハッシュ、COS エントリ、可用性ゲーティング、および 公開ハッシュ リスト）と、それらの統合が基礎として使用することが期待される取得したリソースを Cross-Origin Storage に保存手順を定義します。

  • HTML: すでに link および script 要素上で integrity [SRI] とともに使用される crossoriginstorage 属性。WHATWG に whatwg/html#12770 で提案されています。

  • JavaScript: integrity と 併用可能なホスト定義の crossOriginStorage import 属性で、 Import Attributes 提案を基礎とし、WHATWG に whatwg/html#12771 で提案されています。

  • CSS: integrity() と併用可能な cross-origin-storage() <request-url-modifier> で、 CSS Working Group に w3c/csswg-drafts#14056 で提案されています。

  • Fetch: integrity [FETCH] と併用可能な crossOriginStorage RequestInit オプションで、WHATWG に whatwg/fetch#1954 で提案されています。 これにはホスト定義の送信先がないため、 Response がCOS レジストリから提供された場合に MIME タイプ、ステータス、その他のメタデータをどう報告するかは その仕様における未解決の問題です。COS エントリはバイト列だけを保存します。

説明のみを目的として、同じグローバル共有リソースを 4 つの各形式で Cross-Origin Storage に オプトインする例を以下に示します:

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

これらの断片は説明用にすぎません。この構文はいずれもこの仕様では定義されていません。 制限されたオリジンリストをどう記述するかを含む各形式の正式な文法は、 それぞれのホスト仕様に属します。表記は意図的に 異なります。RequestInit メンバーは sequence<DOMString> を受け取ることができ、 origins と完全に一致しますが、属性値、 import 属性値、および CSS 修飾子引数はテキストしか持てません。

4 つの形式はいずれも、まずCOS レジストリを参照して、一致し開示可能なエントリを探し、 見つからなければネットワーク取得にフォールバックし、 正常に取得され完全性検証されたリソースをCOS レジストリに保存して 他のオリジンが再利用できるようにする、という処理モデルを共有することが期待されます。これは getFileHandle() とまったく同じです。保存手順は 取得したリソースを Cross-Origin Storage に保存であり、各統合は取得した responseを使ってこれを実行します。したがって、制限された origins 値は、そのリソースの response にある Cross-Origin-Storage-Allow-Origin ヘッダー、すなわちバイト列を 提供するサーバーが送信したものによって制限されます（§ 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照）。これらの統合についての議論は、 このリポジトリの issue tracker ではなく、それらを担うホスト仕様の tracker に属します。
