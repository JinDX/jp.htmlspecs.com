概要

オリジン間ストレージ（COS）は、Web アプリケーションが AI モデル、WebAssembly モジュール、非常に普及している JavaScript ライブラリなどの 大容量ファイルを異なるオリジン間で保存および取得できる、コンテンツアドレス可能なキャッシュです。ファイルは URL ではなく暗号学的ハッシュによって識別されるため、あるオリジンによって一度取得された バイト単位で同一のリソースは、ユーザーエージェントが許可する他の任意のオリジンによって、再度ダウンロードすることなく再利用できます。キャッシュ内の存在を、ユーザーがどのサイトを訪問したかの推測に利用できないようにするため、 ファイルのオリジン間開示は、k-匿名性方式の人気度基準を満たすハッシュに限定されます。

1. はじめに

この節は非規範的です。

ストレージは通常、ユーザーのセキュリティとプライバシーを保護するためにオリジンごとに分割されます。これは適切な デフォルトですが、非常に大きく、非常に人気があり、一般に配布される限られた種類の リソース — AI モデル、WebAssembly モジュール、JavaScript ライブラリ、ゲームエンジン、大容量 Web フォント — には適していません。これらは、どのサイトが要求しても、バイト単位でまったく同じファイルです。2 つの 無関係なオリジンがそれぞれ同じ 8 GB のモデルに依存している場合、オリジン分割ストレージでは ユーザーがそのモデルを 2 回ダウンロードして保持することになり、ユーザーの帯域幅、ストレージ、 バッテリー、そしてネットワーク全体にとって無駄になります。

Cross-Origin Storage (COS) は、URL ではなく暗号学的ハッシュをキーとする コンテンツアドレス指定可能キャッシュであり、ユーザーエージェントが、そのようなリソースの保存済みコピー 1 つを、 その使用を選択した複数のオリジン間で共有できるようにします。COS にリソースを保存することは、常に保存元 オリジンによる明示的なオプトイン操作であり、ユーザーエージェントは、本来なら読み取りを許可される オリジンに対してさえ、リソースの存在確認を差し控えることができます。§ 8 プライバシー およびセキュリティ上の考慮事項を参照してください。

この仕様のエントリーポイントは、requestFileHandle() メソッドであり、crossOriginStorage を介して公開されます: 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // ファイルを使って何らかの処理を行う。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // Cross-Origin Storage に（開示可能な形で）存在しないため、代わりにネットワークから取得する。
  }
}

この仕様では、FileSystemFileHandle、 FileSystemWritableFileStream、 および関連する File System Standard [FS] の基盤を再利用し、単一オリジンのプライベートまたはユーザー可視の ファイルシステムではなく、専用のクロスオリジン共有 ファイルシステムにスコープを限定します。

この仕様は命令型 JavaScript API のみを定義します。関連する提案では、 同じ基盤キャッシュを他のホスト仕様に統合します — HTML の crossoriginstorage 属性を link および script に追加するもの、 crossOriginStorage JavaScript import 属性、CSS の cross-origin-storage() <request-url-modifier>、および fetch() 用の crossOriginStorage RequestInit オプション — それぞれが独自のホスト仕様で定義されます。§ 9 他の仕様との統合を参照してください。

2. 概念

2.1. ハッシュ

COS ハッシュは、次の 構造体であり、 次の 項目を持ちます:

アルゴリズム

[WEBCRYPTO] が認識するハッシュアルゴリズムの名前を表す 文字列。 例えば "SHA-256" です。

値

文字列であり、アルゴリズムによって生成されたダイジェストを小文字の 16 進数で符号化したものです。 "SHA-256" の場合、これは 64 文字です。

algorithm 辞書メンバーは、単純な DOMString として型付けされ、HashAlgorithmIdentifier としては型付けされません。その値空間は、 [WEBCRYPTO] のハッシュアルゴリズムが受け付ける名前の集合とまったく同じです。HashAlgorithmIdentifier は (object or DOMString) です — さらに object も許容し、[WEBCRYPTO] によって Algorithm 形状の 辞書へ正規化されるため、呼び出し元は必要とするアルゴリズムに追加パラメーターを渡すことができます （例えば、{name: "HMAC", hash: "SHA-256"}）。ハッシュアルゴリズムはそのようなパラメーターを取らず、 アルゴリズムは、単一の操作で一度だけ消費されるのではなく、 コンテンツアドレス指定可能 キーの一部として保存、比較、往復変換され、この仕様の 例におけるすべての使用箇所は単純な文字列です。ここで任意のオブジェクトを許容しても機能は増えず、 等価性とシリアル化を 不必要に複雑にするだけです。したがって、DOMString がこのフィールドには より狭く、より適切な型です。

2 つの COS ハッシュ値が等しいとは、それらの アルゴリズム 値が ASCII 大文字小文字不区別で一致し、それらの 値の値が完全に 等しい場合です。

注: 大文字小文字が規範的に 制約されていない アルゴリズムとは異なり、 値はすでに規範的に 小文字です（上記参照）。したがって、その比較は ASCII 大文字小文字不区別の比較ではなく、単純な 文字列比較です。

コンテンツアドレス指定可能な ストアとは、そのエントリーが URL や 名前ではなく、COS ハッシュの 等価性をキーとするものです。つまり、 同一のバイト列と同じハッシュアルゴリズムを持つ 2 つのファイルは、いくつのオリジンが それらを保存したか、またはいくつの URL から取得されたかにかかわらず、同じエントリーです。

2.2. COS エントリー

各ユーザーエージェントは、単一の COS レジストリを持ちます。これは COS ハッシュ値から COS エントリー 構造体への マップであり、 Cross-Origin Storage を使用するすべてのオリジンによって共有されます。 COS エントリーは、次の 項目を持ちます:

ハッシュ

COS ハッシュ。

バイト

Null、または バイト列であり、ハッシュの アルゴリズムによるそのダイジェストが ハッシュの 値と等しいものです。書き込み側が 検証と 保存を完了するまでは Null です。

状態

"pending" または "written" のいずれかです。エントリーは "pending" で開始し、バイトが初めて設定されたときに、ちょうど一度だけ "written" に なります。

保留中の書き込み側の数

非負の整数で、初期値は 0 です。未完了の書き込み側 — 作成要求を完了するによって返された FileSystemFileHandle ハンドルのうち、その 終了時の書き込みが まだ確定していないもの — を数えます。検証して保存するにおいて、失敗した書き込みを安全に クリーンアップできるかを判断するためだけに使用されます。§ 3.3 ファイルの作成と書き込みを参照してください。

オリジン

オリジンの リストであり、 公開ハッシュ リストとは独立して、明示的なクロスオリジン読み取りアクセスが許可されています。初期状態では空です。増加することだけがあり、 減少することはありません。これは、誰がエントリーを読み取れるかを決定する、独立して加算される 3 つの許可の 1 つであり、 残りの 2 つは、その 保存元オリジン（それらと 同一サイトのオリジンとともに常に読み取り可能）と、グローバルに 開示可能であることです。

グローバルに開示可能

真偽値で、初期値は false です。エントリーがグローバル （"*"）可用性を要求して書き込まれたかどうかを記録します。true の場合、そのエントリーは、要求が § 8.3 可用性ゲーティングを通過する任意のオリジン — すなわち、その ハッシュが PHL 上にあり、 GREASE 化によって抑制されていないオリジン — から読み取り可能です。設定されることだけがあり、 解除されることはありません。

注: これは 項目であり、オリジン内のセンチネル 値ではありません。これにより、後からのグローバル可用性要求は、既存の明示的な オリジン リストを置き換えるのではなく、その上に "*" の許可を 追加します。2 つを 1 つのフィールドに統合した場合、バイトを提供した書き込み側が、リストにスコープされたエントリーを "*" にスコープされたものへ変更できてしまい、さらに — § 8.3 可用性 ゲーティングは "*" の許可には適用される一方、 明示的な オリジン リストには適用されないため — 以前は リストによりエントリーを読み取れたオリジンが、 ハッシュが PHL 上にない場合には常に "NotFoundError" を受け取るようになります。許可を独立させておくことで、可視性の変更はすべて厳密に加算的になり、 これは アップグレード可能だがダウングレード不可という要件に 合致します。

保存元オリジン

それぞれが少なくとも一度、この エントリーのバイトの 書き込みを正常に完了した オリジンの 集合です。ページの読み込みをまたいで永続化され、 時間の経過とともに 増加します。§ 5.2 退去で説明される場合を除き、減少することはありません。 保存元オリジンに含まれるオリジンは、 requestFileHandle()を介して、常にそのエントリーのハンドルを取得できます。 これは オリジンや、 エントリーの ハッシュが公開ハッシュリスト (PHL) 上にあるかどうかとは無関係です。 § 3.4.1 元の保存者によるアクセスを参照してください。

ユーザーエージェントには、関連付けられた Cross-Origin Storage キューがあり、これは 新しい並列キューを開始することの結果です。COS レジストリに対するすべての操作は、このキューに エンキューされるため、 エンキューされた 順序で実行され、互いに割り込むことはありません。

2.3. 公開ハッシュリスト

あるハッシュが Cross-Origin Storage に存在することを確認すること自体が、 ユーザーの閲覧履歴に関する情報を漏洩させる可能性があります（§ 8.2 クロスサイトプロービングを参照）。これは特に グローバルな許可に関するリスクです — エントリーの明示的な オリジン リストと、 すべてのエントリーが持つ同一サイトのベースラインは、すでに 保存元オリジンによる明示的な選択によって開示範囲が制限されていますが、エントリーを グローバルに開示可能にすると、Web 上の任意の オリジンに公開される可能性があります。この 特定のリスクを制限するため、グローバルに開示可能なリソースは、その 許可を通じて、保存元オリジン外のオリジンに対し、そのハッシュが追加の 独立したゲートを通過した場合にのみ開示可能です。そのゲートとは、ベンダー中立で 実装定義の COS ハッシュ 値の許可リストである 公開ハッシュリスト （PHL）への登録です。ハッシュは、k-匿名性形式の 人気度基準 — 例えば、ある最小数の独立した オリジンにおいてバイト単位で同一のものが現れること — を満たした場合にのみ公開ハッシュリストへ登録されるため、 共有キャッシュ内にそのハッシュが存在することを確認しても、特定の ユーザーに関する情報にはなりません。

COS ハッシュ hashが公開 ハッシュリスト上にあるとは、hashが ユーザーエージェントの現在の 公開ハッシュリストのスナップショット内のエントリーと 等しい場合です。

公開ハッシュリストの取得プロトコル、 更新頻度、データ形式、人気度しきい値、およびガバナンスは、 この仕様の付随成果物として詳細に設計されており、[URL] Standard の public suffix list が規範的な文章ではなく付随するデータファイルであることにならっています — このリポジトリの 公開ハッシュリスト解説を参照してください。その設計では、 Public Suffix List のクロスベンダーかつ ローリングリリースという先例をモデルとして、WHATWG によるガバナンスを提案し、独立して裏付けられた遍在性に基づく登録基準 —​上で説明した k-匿名性形式の基準を具体化し、 ハッシュを登録する過程の一部としてオフラインで一度だけ適用し、 ユーザーエージェントがクエリごとに繰り返す検査とはしないもの — を提案しています。これらはいずれも、まだ この提案の外部では確立されていません。リスト自体の初期の非規範的なコードプロトタイプは このリポジトリの public-hash-list/implementation/ で管理されています — 実用的な 暫定的な置き場所です。専用のクロスベンダーリポジトリは、引き続き PHL 解説で説明されているガバナンス上の目標です。 この仕様は、あるハッシュが PHL 上にあるかどうかだけに依存し、特定の 取得メカニズムやガバナンスモデルには依存しないため、その設計がどのように 発展しても、この仕様の正しさは維持されます。

3. CrossOriginStorageManager インターフェイス

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

各 Navigator および WorkerNavigator オブジェクトには、関連付けられた CrossOriginStorageManager オブジェクトがあります。crossOriginStorage ゲッターの 手順は、 this に関連付けられた CrossOriginStorageManager を返すことです。

各 CrossOriginStorageManager オブジェクトには関連付けられた オリジンがあり、オブジェクトが 作成されるときに、this の 関連設定オブジェクトの オリジンに設定されます。

注: スクリプト自体に関する何らかの情報からではなく、関連設定オブジェクトからオリジンを取得することには、ワーカーについて明示する価値のある結果があります。blob: URL から作成された ワーカーは、それを作成したコンテキストの オリジンを持つため、そのオリジンの Cross-Origin Storage ビューを完全に共有します。つまり、そのようなワーカーが書き込んだものは、作成元ページが読み戻すことができ、 ページが保存したものは、ワーカーが読み取ることができます。blob: URL はそれ自体のオリジンではなく、 それを取り消してもワーカーがそのビューから切り離されることはありません。一方、data: URL から作成されたワーカーは、 不透明なオリジンを持ちます。この仕様では現在、 呼び出し元オリジンが不透明な場合に requestFileHandle() が何を行うかを定義していません。 不透明なオリジンに関する COS 要求を検証する内の規則は、呼び出し元が 指定するオリジンを制御するものであり、呼び出し元自身のオリジンを制御するものではありません。不透明なオリジンには、 保存元 オリジンや 同一 サイト比較のキーとするための安定した識別子がないため、それに 付与できる意味のあるものはありません。

3.1. requestFileHandle() メソッド

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

hash で識別されるファイルが Cross-Origin Storage に存在し、かつ呼び出し元オリジンに 開示可能である場合、そのファイルのハンドルを返します。それ以外の場合、これは "NotFoundError" DOMException で拒否されます。 "NotFoundError" は、ファイルが Cross-Origin Storage に 物理的に存在しないことを証明するものではありません。§ 8.3 可用性ゲーティングを参照してください。呼び出し元は、 これを「代わりにネットワークから取得する」と扱うことができます。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

hash で識別されるファイルを Cross-Origin Storage に書き込むために使用できるハンドルを返し、エントリーがまだ存在しない場合は新しいエントリーを作成します。デフォルトでは同一サイトのオリジンに制限されます。 呼び出し元は、エントリーがすでに 存在していたかどうかにかかわらず、ハンドルの createWritable() メソッドを介して完全なファイル内容を書き込む必要があります。その時点でユーザーエージェントは、書き込まれたバイトのハッシュが hash になることを検証し、 そうでない場合は "DataError" DOMException で拒否します。この要件は、 オリジンが作成要求を、hash がすでに存在していたかどうかを判定するオラクルとして使用することを防ぎます。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

上記と同様ですが、さらに、書き込み後に hash に対する要求が § 8.3 可用性ゲーティングを通過する任意のオリジンに エントリーを開示可能にします。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

上記と同様ですが、開示を指定されたオリジンのみに制限します（呼び出し元 オリジン、およびすでに 保存元オリジンに含まれるオリジンに加えて）。

requestFileHandle(hash, options) メソッドの 手順は次のとおりです:

  1. result を 新しい promise とします。

  2. realm を this の 関連 Realm とします。

  3. global を this の 関連グローバルオブジェクト とします。

  4. origin を this に関連付けられた オリジン とします。

  5. global を与えて Cross-Origin Storage 権限を確認するを 実行した結果が false の場合、次を行います:

    1. global を与えて、DOM 操作タスクソース上で グローバルタスクをキューに入れ、 result を "NotAllowedError" DOMException で 拒否します。

    2. result を返します。

  6. validationFailure を、hash と options を与えて COS 要求を検証するを実行した結果とします。

  7. validationFailure が null でない場合:

    1. global を与えて、DOM 操作タスクソース上で グローバルタスクをキューに入れ、 result を validationFailure で 拒否します。

    2. result を返します。

  8. 次の手順を Cross-Origin Storage キューに エンキューします:

    1. options["create"] が true の場合:

      1. result、hash、options、global、および realm を与えて 作成要求を完了するを実行します。

    2. それ以外の場合:

      1. result、hash、origin、global、および realm を与えて 読み取り要求を完了するを実行します。

  9. result を返します。

CrossOriginStorageRequestFileHandleHash hash および CrossOriginStorageRequestFileHandleOptions options が与えられたときに、null または TypeError を返すように COS 要求を検証するには:

  1. hash["algorithm"] が [WEBCRYPTO] によって認識されるハッシュアルゴリズム 名でない場合、新しい TypeError を返します。

  2. hash["value"] が正規 表現 /^[0-9a-f]{64}$/ に一致せず、かつ hash["algorithm"] が "SHA-256" と ASCII 大文字小文字不区別で 一致する場合、新しい TypeError を返します。

    注: 将来のハッシュアルゴリズムでは、 異なる期待ダイジェスト長を定義できます。この 仕様は、例全体での使用に合わせて、"SHA-256" のみを規範的に制約します。

  3. options["origins"] が 存在し、かつ "*" でない場合:

    1. candidates を options["origins"] とし、 単一の 文字列は 1 要素の リストとして扱います。

    2. candidates の サイズが ユーザーエージェントの 最大オリジンリスト長より大きい場合、新しい TypeError を返します。

    3. candidates の各 candidate について 反復します:

      1. candidate に対して 基本 URL パーサーを実行した結果が失敗であるか、または 解析された URL の オリジンが 不透明なオリジンである場合、新しい TypeError を返します。

  4. null を返します。

3.2. ファイルの読み取り

promise result、COS ハッシュ hash、 オリジン origin、グローバルオブジェクト global、および Realm realm が与えられたときに、読み取り 要求を完了するには:

  1. entry を、COS レジストリ内の COS エントリーのうち、その ハッシュが hash と 等しいものがあればそれとし、なければ null とします。

  2. entry が null でなく、かつ entry の 状態が "pending" の場合:

    1. global を与えて、DOM 操作タスクソース上で グローバルタスクをキューに入れ、 result を "NotAllowedError" DOMException で 拒否します。

    2. 返ります。

    注: 書き込み進行中のハッシュは、意図的に 存在しないハッシュと同じようには動作しません。これにより、呼び出し元が進行中の書き込みを真のキャッシュミスと誤認し、 非常に大きなファイルを、それを書き込むことだけを目的として冗長に並行ダウンロードし始めることを 防ぎます。§ 3.3 ファイルの作成と書き込みを参照してください。

  3. disclosableEntry を、entry および origin を与えて 可用性 ゲーティングを適用するを実行した結果とします。

  4. disclosableEntry が null の場合:

    1. global を与えて、DOM 操作タスクソース上で グローバルタスクをキューに入れ、 result を "NotFoundError" DOMException で 拒否します。

    2. 返ります。

  5. handle を、realm 内で、 Cross-Origin Storage ファイルシステム内の disclosableEntry を指す ロケーターを持つ 新しい FileSystemFileHandle を作成する [FS]ことの結果とします。

  6. handle の COS オリジンを origin に設定します。

  7. handle の 読み取り可能を true に設定します。

    注: このハンドルはすでに 可用性ゲーティングを適用するを通過しているため、呼び出し元オリジンには エントリーのバイトを取得する権利があります。

  8. global を与えて、DOM 操作タスクソース上で グローバルタスクをキューに入れ、 result を handle で 解決します。

COS エントリー または null の entry、および オリジン origin が与えられたときに、COS エントリーまたは null を返すように COS 開示を決定するには:

  1. entry が null の場合、null を返します。

  2. 表明: entry の 状態は "written" です。

  3. origin が entry の 保存元 オリジンに含まれる場合、entry を返します。

    注: 元の保存者、および自身でエントリーを正常に書き込んだ任意のオリジンは、 常にそれを読み戻すことができます。§ 3.4.1 元の保存者による アクセスを参照してください。

  4. origin が entry の 保存元オリジンのいずれかの項目と 同一サイトである場合、 entry を返します。

    注: すべてのエントリーが持つ同一サイトのベースライン — origins オプションなしの書き込みが要求する許可 — は、 後から追加された オリジン リストまたは グローバルに開示可能な許可に 関係なく、常に有効です。これは下の 公開ハッシュリストのゲートより前に確認されるため、同一サイトの オリジンは、その ハッシュが PHL 上にあるかどうかにかかわらず、エントリーを読み取ります。ここでは同一サイトが 1 つの信頼単位であるため、§ 8.2 クロスサイトプロービングが保護する サイト境界を越えて何かを開示することはありません。

  5. origin の シリアル化が entry の オリジンの項目である場合、 entry を返します。

    注: 明示的な オリジン リスト上のオリジンは、エントリーが PHL 上にある必要なしに エントリーを読み取ります。保存元オリジンは、それを指定することで範囲を限定した開示判断を行っています （§ 3.4 リソースの可視性のアップグレードおよび § 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照）。その上で別途 グローバルな遍在性を要求すると、通常の制限付き共有が、しばしば独占的なリソースについての無関係な 公開キュレーションに依存することになります。これを グローバルに開示可能なゲートより前に確認することによって、後からのグローバル可用性の書き込みが リスト内オリジンのアクセスを取り消さないようにします。§ 8.2 クロスサイト プロービングを参照してください。

  6. entry の グローバルに開示可能が true の場合:

    1. entry の ハッシュが PHL 上にない場合、null を返します。

      注: 公開ハッシュリストのゲートは、 グローバルな許可にのみ適用されます — これは、開示がそうでなければ Web 上の任意のオリジンに到達し得る唯一の場合です。 グローバルに開示可能であるものの、その ハッシュが PHL 上にないエントリーは、 この許可のみを通じて資格を得るオリジンには 開示されません。保存元オリジン、それらの同一サイト集合、または明示的な オリジン リストにも含まれるオリジンは、すでに 上で返されています。

    2. entry を返します。

  7. null を返します。

COS エントリーまたは null の entry、および オリジン origin が与えられたときに、COS エントリーまたは null を返すように 可用性 ゲーティングを適用するには:

  1. disclosable を、entry および origin を与えて COS 開示を決定するを実行した結果とします。

  2. disclosable が null の場合、null を返します。

  3. origin が disclosable の 保存元 オリジンに含まれる場合、disclosable を返します。

  4. ユーザーエージェントがこの要求に GREASE 化を適用することを選択した場合、 null を返します。

  5. disclosable を返します。

3.3. ファイルの作成と書き込み

作成要求を完了するによって作成された FileSystemFileHandle には、関連付けられた 要求されたオリジンがあり、これはハンドルへの書き込みが正常に完了した後、 検証して保存するが エントリーの オリジンを アップグレードしようとする値です。

COS エントリーを指すすべての FileSystemFileHandle には、さらに関連付けられた COS オリジン、すなわちそれを取得した オリジンと、 関連付けられた 読み取り可能真偽値もあります。これは、 getFile() がその特定のハンドルを介してエントリーのバイトを開示できるかどうかを制御します。 これは、すでに 可用性ゲーティングを通過した 読み取り要求を完了するによって返されたハンドルでは true であり、 作成 要求を完了するによって返されたハンドルでは、同じハンドルについて 検証して保存するが成功するまで false です。

注: これは意図的にエントリーではなくハンドルのプロパティです。 作成要求は、エントリーがすでに存在し、かつすでに "written" であるかどうかにかかわらずハンドルを返すため（ 作成 要求を完了するを参照）、エントリー単位の規則では、任意のオリジンが requestFileHandle() を create: true で呼び出して、自身が 一度も書き込んでいないエントリーを即座に読み取り、その内容を オリジン、 PHL 登録、または GREASE 化を満たすことなく知ることができてしまいます。この 仕様のすべての開示制御は読み取りパス上で適用されるため、エントリー単位のゲーティングでは作成要求によって それらすべてを迂回できてしまいます。呼び出し元にまず正しいバイトを提供させることにより、作成で取得したハンドルを介した 成功した読み取りが、呼び出し元がすでに持っていなかったものを開示しないようにします。

promise result、 COS ハッシュ hash、CrossOriginStorageRequestFileHandleOptions options、グローバルオブジェクト global、および Realm realm が与えられたときに、作成 要求を完了するには:

  1. requestedOrigins を、options["origins"] を与えて 要求された オリジンを正規化するを実行した結果とします。

  2. requestedOrigins が リストの場合:

    1. ceiling を、global を与えて COS スコープ上限を取得するを実行した結果とします。

    2. ceiling が 含まない各 オリジンを requestedOrigins から 削除します。

      注: これは § 7 Cross-Origin-Storage-Allow-Origin ヘッダーで説明される COS スコープ上限との 積集合です。開示元オリジンの Cross-Origin-Storage-Allow-Origin ヘッダーが許可しなかった受信者は、書き込みを失敗させるのではなく 除外されます。これは リソースの可視性をアップグレードするで、長さ超過のアップグレードが余分な項目を除外する方法と一致します。ユーザー エージェントは、除外された各 オリジンを示すコンソール警告を記録することが期待されます。

    3. requestedOrigins が 空である場合、requestedOrigins を null に設定します。

      注: すべてのメンバーが除外された リストは、書き込みに許可された クロスオリジン受信者を残さないため、厳密により狭い空の リスト（これは 同一サイトの読者さえ除外します）ではなく、同一サイトのデフォルトにフォールバックします。バイトは 引き続き保存されます。許可されていない開示だけが差し控えられます。

  3. entry を、COS レジストリ内の COS エントリーのうち、その ハッシュが hash と 等しいものがあればそれとし、なければ null とします。

  4. entry が null の場合:

    1. entry を新しい COS エントリーに設定します。その ハッシュは hash、 バイト は null、状態は "pending"、オリジンは 空の リスト、グローバルに開示可能は false、そして 保存元オリジンは空の 集合です。

    2. 設定: COS レジストリ[hash] を entry に設定します。

    注: 新しいエントリーは明示的な オリジン の許可なしで開始し、 グローバルに開示可能でもありません。 requestedOrigins は、バイトが書き込まれて 検証された後、既存のエントリーを見つけた要求の場合とまったく同様に、検証して 保存するによって リソースの可視性をアップグレードすることを通じて下で適用されます。これにより、作成 要求は可視性を広げる前に完全なバイトを提供することになります（§ 3.4 リソースの可視性のアップグレードを参照）。

  5. entry の 保留中の書き込み側の数を 1 増やします。

    注: これは、呼び出し元が createWritable() を呼び出さない場合や、結果のストリームを閉じない場合でも、handle を 未完了の書き込み側として追跡します。このように放棄されたハンドルは、entry に対して恒久的にカウントされます。これは、この仕組みが存在する前から 放棄された進行中の書き込みによって entry が恒久的に "pending" のままになっていたことと同じです。 検証して 保存するを参照してください。

  6. handle を、realm 内で、 Cross-Origin Storage ファイルシステム内の entry を指す ロケーターを持つ 新しい FileSystemFileHandle を作成する [FS]ことの結果とします。

  7. handle の COS オリジンを、global の 関連設定オブジェクトの オリジンに設定します。

  8. handle の 要求されたオリジンを requestedOrigins に設定します。

  9. handle の 読み取り可能を false に設定します。

    注: handle は entry がすでに存在していたかどうか、および すでに "written" であるかどうかにかかわらず返されます。呼び出し元は依然として handle を介して完全なファイルバイトを提供する必要があります。これにより、書き込みを以前の存在の検出に使用できなくし（ § 8.2 クロスサイトプロービングを参照）、またより寛容な オリジン 値の要求が受け入れられる前に検証されるようにします。 § 3.4 リソースの可視性のアップグレードを参照してください。

  10. global を与えて、DOM 操作タスクソース上で グローバルタスクをキューに入れ、 result を handle で 解決します。

(DOMString or sequence<DOMString>) または undefined の origins が与えられたときに、"*"、リストの オリジン、または null を返すように、 要求された オリジンを正規化するには:

  1. origins が 存在しない場合、 null を返します。

  2. origins が "*" の場合、"*" を返します。

  3. list を « » とします。

  4. origins の各 candidate について 反復します（単一の 文字列は 1 要素の リストとして 扱います）:

    1. candidateOrigin を、candidate に対して 基本 URL パーサーを実行した結果の オリジンとします。

      注: COS 要求を検証するによって、各 candidate が 不透明でないオリジンへ解析されることはすでに確認されています。

    2. list が candidateOrigin を 含まない場合、candidateOrigin を list に 付加します。

  5. list を返します。

注: 後で既存のエントリーへ マージするときだけでなく、ここで重複を除去することで、 エントリーが最初に作成された時点から オリジンに重複がない状態を保ち、その後のすべての 複製も重複なしのままになります。

COS エントリーを指す ロケーターを持つハンドルで createWritable() を呼び出して取得した FileSystemWritableFileStream が閉じられたとき [FS]、ユーザーエージェントは その閉じる操作の promise が履行される前に、以下の 検証して保存する 手順を実行しなければなりません。

注: これは閉じる処理がどのように トリガーされたかにかかわらず適用されます — 明示的な close() 呼び出し、またはソースの末尾に到達し、デフォルトで宛先も閉じる pipeTo() 呼び出しです。[STREAMS] は、ストリームが閉じられる時点でこの 2 つを 区別せず、このアルゴリズムも区別しません。

閉じられた ストリームのハンドルによって指される COS エントリー entry、完全に書き込まれた バイト列 bytes、および閉じる操作の 関連設定オブジェクトの オリジン origin が与えられたときの、 検証して保存する 手順は次のとおりです:

  1. computedValue を、entry の アルゴリズムで指定されたアルゴリズムを使用し、 [WEBCRYPTO] に従って計算した、bytes の 小文字 16 進数ダイジェストとします。

  2. computedValue が entry の 値と完全に等しくない場合:

    1. 閉じる操作の promise を "DataError" DOMException で 拒否します。

    2. 次の手順を Cross-Origin Storage キューに エンキューします:

      1. entry の 保留中の書き込み側の数を 1 減らします。

      2. entry の 状態が "pending" で、かつ entry の 保留中の書き込み側の数が 0 の場合、entry の ハッシュを COS レジストリから 削除します。

        注: これにより、 失敗した書き込みが、恒久的に到達不能な "pending" エントリーを残すのではなく、自身をクリーンアップします。同じハッシュに対する後の requestFileHandle() 呼び出しは、他に未完了の 書き込み側がなくなると、エントリーをまったく見つけず、無期限の "NotAllowedError" ではなく通常の "NotFoundError" を受け取ります。 このカウントは、同じハッシュについて並行して進行中の別の書き込み側（ 例えば、2 つのタブがどちらもハッシュが存在しないことを検出し、それぞれ独立して 書き込みを開始した場合）が存在するエントリーを削除しないようにします。その書き込み側がまだ未完了であるか、 すでに成功している場合、カウントがまだ 0 に達していないか、または entry の 状態がもはや "pending" ではないため、 この手順は何もしません。その書き込み側はまだ 正常に書き込む可能性があります。 すでに "written" のエントリーは、その後いくつの 書き込み側がそれを要求して失敗したとしても、この方法で削除されることはありません。一度も正常に 書き込まれていないエントリーだけが対象です。

    3. これらの手順を中止します。

  3. 次の手順を Cross-Origin Storage キューに エンキューします:

    1. entry の バイトを bytes に設定します。

    2. entry の 状態を "written" に設定します。

    3. origin がまだ存在しない場合、entry の 保存元オリジンに 付加します。

    4. entry の 保留中の書き込み側の数を 1 減らします。

    5. entry とハンドルの 要求されたオリジンを与えて、 リソースの可視性をアップグレードするを実行します。

    6. ハンドルの 読み取り可能を true に設定します。

      注: このハンドルだけが 読み取り可能になります。同じエントリーに対する別のハンドルで、まだ書き込みが完了していない 別の作成要求から取得されたものは、読み取り不可のままです。

COS エントリーを指す FileSystemFileHandle 上で呼び出された createWritable() は、 keepExistingData の値、および 指されているエントリーの 状態にかかわらず、 内容が空から始まる FileSystemWritableFileStream を生成しなければなりません。

注: [FS] は通常、keepExistingData を、既存ファイルの内容で ストリームを初期化するものとして定義しています。ここでそれを認めると、呼び出し元が一度も所有していなかったバイトの保存元 オリジンになれてしまいます。作成要求は、エントリーがすでに存在するかどうかにかかわらずハンドルを返すため、 呼び出し元は別のオリジンが保存したハッシュについて書き込み可能ストリームを開き、何も書き込まずに閉じ、 引き継がれたバイトを要求された値にハッシュさせることができます。それにより、 オリジン、公開ハッシュリスト、および GREASE 化が一度も参照されることなく読み取りアクセスが付与されます — これは、個別には許可された 2 つの操作から組み立てられた 可用性 ゲーティングの迂回です。 これは、検証して保存するが すべての作成要求で完全な内容を要求するのと同じ理由です。

注: したがって、何も書き込まずに閉じられた書き込み可能ストリームは 空のバイト列を保持し、呼び出し元が求めるどのエントリーについても要求された値には ハッシュされないため、検証して保存するは、他の不一致の場合と同様に "DataError" DOMException で拒否します。その場合に 代わりにストレージまたは I/O 障害を報告する実装は、検証結果を 無関係なエラーの背後に隠すことになります。

File System Standard [FS] は、依存する 仕様が FileSystemWritableFileStream の 閉じる手順に追加の書き込みごとの検証を組み込むための拡張ポイントをまだ定義していません。そのようなフックが存在するまでは、この節で必要な動作を直接説明します。将来の 改訂では、[FS] と正式に統合することが期待されます。

3.4. リソースの可視性のアップグレード

COS エントリーの可視性は アップグレードできますが、ダウングレードすることはできません。

COS エントリー entry および "*"、リストの オリジン、または null の requestedOrigins が与えられたときに、 リソースの 可視性をアップグレードするには:

  1. requestedOrigins が null の場合、返ります。

    注: origins を省略すると、同一サイトの 可用性のみが要求されます。これはすべてのエントリーがすでに持っています（COS 開示を決定するを参照）。したがって、 追加するものはありません。

  2. requestedOrigins が "*" の場合:

    1. entry の グローバルに開示可能を true に設定します。

    2. 返ります。

    注: これはグローバルな許可を追加しますが、 entry の オリジンには影響しません。すでに明示的な オリジン リストを持つエントリーは、それを維持するため、 その リスト上のすべてのオリジンは、エントリーが グローバルに開示可能になった後も、 PHL に依存しないアクセスを維持します。これこそが、 2 つの許可を別々に保存する理由の核心です。グローバルに開示可能を参照してください。

  3. requestedOrigins の各 candidateOrigin について 反復します:

    1. entry の オリジンが candidateOrigin を 含む場合、 継続します。

    2. entry の オリジンの サイズが ユーザーエージェントの 最大オリジンリスト長と等しい場合、 中断します。

      注: 残りの candidateOrigin 値は、このアップグレードを失敗させるのではなく、暗黙に破棄されます — 書き込み自体はすでに成功しています — ただし、ユーザーエージェントは エントリーのオリジンリストが上限に達したことを示すコンソール警告を記録することが期待されます。

    3. candidateOrigin を entry の オリジンに 付加します。

注: アップグレードは オリジンに追加するか、グローバルに開示可能 を true に設定することしかありません。どちらの許可も削除されたり狭められたりすることはありません。リストを要求する書き込み側は、 まだグローバルに開示可能でないエントリーを広げる場合と同じように、すでに グローバルに開示可能なエントリーも広げます — 新たにリストされたオリジンは、"*" の許可が引き続き 有効であっても、PHL に依存しないアクセスを得ます — これは 2 つの許可が順序付けられているのではなく、独立しているためです。

注: 元の保存者だけでなく、新しいサイトも、 エントリーの オリジンを広げることができます。ただし、 エントリーの ハッシュになるバイトも提供する必要があります。これは意図的です。 ハッシュに対応する正しいバイトをすでに所有するサイトは、構造上、そのハッシュが何を表すかについて 元の保存者と同じ程度に権威があります。

3.4.1. 元の保存者によるアクセス

オリジンが COS エントリーの 書き込みを正常に完了した場合 — つまり、 エントリーの 保存元オリジンに含まれる任意の オリジン — は、その後いつでも requestFileHandle() を介してそのハンドルを取得できます。これは、エントリーの オリジン値や、 その ハッシュが PHL 上にあるかどうかには依存しません。 これは、オリジンが自身の保存したものへ常にアクセスできる Cache API のモデルを反映しています。

4. Cross-Origin Storage ファイルシステム

Cross-Origin Storage ファイルシステムは、任意の オリジンの バケットファイルシステムまたはローカルファイルシステムアクセスルートとは異なる ファイルシステムルートであり、その エントリーは、COS レジストリの COS エントリー項目と一対一で対応します。

Cross-Origin Storage ファイルシステムは [FS]の通常の呼び出しごとの 権限確認 モデルを使用しません。そこから取得されたすべての FileSystemFileHandle は、スクリプトに返される前に、すでに § 3.2 ファイルの読み取りまたは § 3.3 ファイルの作成と 書き込みによって完全に認可されているため、そのようなハンドルで getFile() または createWritable() を呼び出しても、 追加の権限プロンプトが発生することはありません。

したがって、そのようなハンドルでの queryPermission() および requestPermission() は、 プロンプトが表示され得ないため、 "prompt" を報告してはなりません。作成要求によって取得されなかったハンドルの 書き込みモードでは "denied" を報告し、それ以外の場合は "granted" を報告しなければなりません。

注: 書き込みは、ハンドルが 実際に欠いている可能性がある唯一の能力です。作成要求だけが書き込み可能な ハンドルを生成するため、その他のハンドルの書き込みモードについて "granted" と報告すると、 createWritable() が拒否する能力を持つと主張することになります。読み取りは "granted" のままです。読み取り可能なハンドルを保持する呼び出し元は、それを介して読み取ることができるためです。要求しても、 表示するプロンプトも許可を記録できる状態もないため、 どちらの回答も変更できません。

COS エントリーを指し、その 読み取り可能が false である FileSystemFileHandle で getFile() を呼び出した場合、 "NotAllowedError" DOMException で拒否しなければなりません。 これは 2 つの異なる場合を対象とします:

  • エントリーがまだ "pending" である 作成要求からのハンドル。同じハッシュに対する並行した requestFileHandle() 呼び出しが拒否されるのと同じ理由です（ § 3.2 ファイルの読み取りを参照）。呼び出し元が まだ検証されていないプレースホルダーを、あたかも ファイルの実際の内容であるかのように観測できてはなりません。

  • 別の他のオリジンがすでに書き込んだエントリーに対する作成要求からのハンドル。 エントリーの 状態は "written" ですが、この呼び出し元はバイトを提供しておらず、 可用性ゲーティングも通過していないため、 エントリーについて何も知ることができてはなりません — その存在の有無も含みます。

ハンドルの 読み取り可能が true になると、そのハンドルで呼び出された getFile() は、指されているエントリーの バイトを内容とする File を返します。これは、[FS]が、 そのバイトを バイナリデータとして持つ ファイル エントリーについて すでに定義している動作そのものです。

COS エントリーを指す FileSystemFileHandle は ファイルシステムロケーターを持ち、その パス は単一の 文字列、すなわちエントリーの COS ハッシュの 値を含む リスト であり、その ルートは Cross-Origin Storage ファイルシステムです。

注: [FS] は name をハンドルの ロケーターのパスの最後の構成要素として定義しているため、これは name を未指定のままにせず、その値を確定します。つまり、 ハッシュです。エントリー自体には名前がなく、ハッシュがその唯一の識別子であるため、 それを報告することで、空文字列なら失われる情報を保持できます。

エントリーには名前も包含ディレクトリもないため、[FS]の構造的な機能の大部分には 操作対象がありません。識別性は例外であり、コンテンツアドレス指定されたエントリーが 常に答えられる唯一の問いです。COS レジストリは 1 つの COS ハッシュにつき最大 1 つの COS エントリーを保持するため、2 つの ハンドルは、そのハッシュが等しい場合に限り、同じエントリーを指します。

COS エントリーを指す FileSystemFileHandle で isSameEntry() が呼び出され、引数も COS エントリーを指し、 同じ オリジンによって取得された場合、2 つのハンドルの COS ハッシュ項目が等しければ true を返し、それ以外の場合は false を返さなければなりません。

注: これを拒否すると、ユーザー エージェントがすでに保持している情報を捨てることになります。

isSameEntry() が、呼び出し元の オリジンが取得していない引数、 または Cross-Origin Storage ファイルシステム以外のファイルシステムを指す引数で呼び出された場合、拒否しなければなりません。

注: この場合に false を返すと、 2 つのハンドルが異なるエントリーを指すと断言することになりますが、 これは呼び出し元オリジンが検査する権利を持たないハンドルについての主張です。拒否することは、 比較できなかったということだけを示します。

COS エントリーを指す FileSystemFileHandle で呼び出された move() および remove() は、 "NotAllowedError" DOMException で拒否しなければならず、 エントリーを変更してはなりません。

注: エントリーは、その 保存元 オリジンに含まれるすべてのオリジンで共有されるため、 削除を認めると、あるサイトが他のサイトの依存するデータを破壊できてしまいます。削除は 退去とユーザー自身のストレージ制御に属します。エントリーはその COS ハッシュによって名付けられ、包含ディレクトリを持たないため、 名前変更や親変更には操作対象がありません。

注: 執筆時点では、どちらのメソッドも [FS]または File System Access API によって定義されていません （WICG/file-system-access#214）。 したがって、エラー名は removeEntry() に従います。これは、エントリーを削除するために [FS]が 定義している操作であり、読み書きアクセスが 許可されていない場合、アクセス結果のエラー名で拒否します。ここでは「存在しない」ではなく「拒否された」と解釈するのが正確です — 操作自体には意味があり、拒否されているためです。

createSyncAccessHandle() についてはここで規則を定める必要はありません。その手順は、ハンドルが バケットファイルシステム内にない場合は常に、 "InvalidStateError" DOMException で拒否し、 Cross-Origin Storage ファイルシステムは、任意のオリジンのものとは異なる ファイルシステムルートであるため、 [FS]がすでに 拒否することとその名前の両方を決定しています。

注: これは、この仕様が 独立に望む結果でもあります。FileSystemSyncAccessHandle は呼び出し元に書き込み可能なファイル記述子を渡し、それによって エントリーが格納されている COS ハッシュと 対応しないように、エントリーの バイトを 変更できてしまいます。そして、そのエントリーを開示可能な他のすべてのオリジンも同じバイトを読み取ります。

4.1. ハンドルの転送

FileSystemFileHandle は シリアル化可能なオブジェクト [FS]であるため、 COS エントリーを指すものは、例えば postMessage(message, options) を使用して、別の 環境設定オブジェクトに渡すことができます。 これは requestFileHandle() と並ぶ、そのようなハンドルを取得する第 2 の方法であるため、 ここでも制約されます。

シリアル化手順は、COS エントリーを指す FileSystemFileHandle について、value と serialized が与えられたとき、さらに次を行います:

  1. serialized.[[COSOrigin]] を value の COS オリジンに設定します。

  2. serialized.[[COSMayRead]] を value の 読み取り可能に設定します。

逆シリアル化手順は、serialized、 value および realm が与えられたとき、さらに次を行います:

  1. serialized.[[COSOrigin]] が realm の 環境設定オブジェクトの オリジンと 同一オリジンでない場合、 "DataCloneError" DOMException をスローします。

  2. value の COS オリジンを serialized.[[COSOrigin]] に設定します。

  3. value の 読み取り可能を serialized.[[COSMayRead]] に設定します。

注: 同一 オリジン確認がなければ、転送によってこの仕様のすべての開示制御を一度に 無効化できてしまいます。読み取り可能が true のハンドルは、すでに それを要求したオリジンについて 可用性ゲーティングを適用するを 通過しています。これを別の オリジンに送信すると、そのオリジンについて オリジン、 PHL 登録、または GREASE 化を評価することなく、エントリーのバイトを渡すことになります。これは、 File System Standard における既存のハンドルの扱いとも一致します。ハンドルも同様に 同一オリジンの受信者に対してのみ有用です。

注: 読み取り可能は、 再計算されるのではなくハンドルとともに移動するため、 まだ書き込まれていない作成要求のハンドルは転送後も読み取り不可のままであり、 読み取り要求のハンドルは再度ゲーティングされることなく読み取り可能なままです。到着時に再ゲーティングするのは 改善ではなく悪化です。同じハンドルを繰り返し転送することで、呼び出し元が可用性を何度も探査できてしまうためです。

5. ストレージ管理

5.1. ストレージ制限

ユーザーエージェントは、単一のオリジンが他のオリジンのエントリーを退去させる目的で キャッシュを埋め尽くすことを防ぐため、オリジンが 成功した書き込みを通じて COS レジストリに寄与できる 総バイト数に制限を課さなければなりません。具体的な制限は 実装定義です。オリジンの書き込みがその 制限を超える場合、ユーザーエージェントはその書き込みを "QuotaExceededError" DOMException で 拒否し、 コンソールに警告を記録するべきです。

注: エントリーは コンテンツアドレス指定可能であるため、 オリジンが同じハッシュの下に同じ バイトを繰り返し書き込んでも、最初の成功した書き込みを超えて追加のクォータを消費することはありません。§ 2.2 COS エントリーを参照してください。

ユーザーエージェントはさらに、実装定義の 最大オリジンリスト長を持ちます。これは、 単一の オリジン リストが 含めることのできる オリジンの数を制限する正の整数です。これは、リストが最初に指定されるとき（COS 要求を検証するを参照）と、 後で既存のエントリーにマージされるとき（ リソースの可視性をアップグレードするを参照）の両方で適用されるため、 1 回の呼び出しでも、時間をかけた多数の呼び出しの累積効果でも、エントリーの オリジンを 無制限に増やすことはできません。メモリ使用量を制限するだけでなく、これはオリジンの リストが "*" の未宣言の代替として使用されることも防ぎます。§ 8.2 クロスサイトプロービングを参照してください。

この制限を超えた場合は、この 2 か所で異なる方法で処理されます。これは、2 つの呼び出しが 操作の非常に異なる時点で行われるためです:

  • COS 要求を検証するでは、ファイルが取得、ハッシュ、または 書き込みされる前に制限を確認します。これを超えた呼び出し元は即座に "TypeError" を受け取り、それ以外は何も起こりません —​ その他の不正な origins 値と同じ扱いです。

  • リソースの可視性をアップグレードするでは、この制限は、 別々の独立した書き込み呼び出しにわたって要求されたオリジンの累積効果によってのみ 到達し得ます。場合によっては、長期間にわたり無関係なオリジンによって到達します。そして、この呼び出しのバイトがすでにハッシュされ、 検証され、永続的に保存された後でしか確認されません。その時点で書き込みを拒否すると、無関係な管理上の制限のために、 成功し、すでに検証済みの — しかも非常に大きい可能性のある — 書き込みを破棄することになり、 単一の呼び出し元の誤りに帰することさえできません。したがって、書き込み自体は 成功したままとし、容量を超えるオリジンだけを オリジンから破棄し、 コンソール警告を出します。これは、既存の より寛容なものからより制限されたものへの要求の扱いを反映しています。完全には満たせない オリジン要求は、それを運んだ書き込みを失敗させるのではなく、 暗黙に上限で制限されます。この仕様の他の箇所にある § 8.3 可用性ゲーティングと一貫して、 呼び出し元は、要求した オリジンが 実際に追加されたかどうかを後から確実に確認する方法を持ちません。その オリジンとして後続の requestFileHandle() 呼び出しを行っても、そのオリジンが追加されていても失敗する可能性があります — 例えば GREASE 化のためです — したがって、その結果をどちらかの確認として解釈してはなりません。

5.2. 退去

この節は非規範的です。

ストレージ圧迫時には、ユーザーエージェントは COS レジストリから エントリーを退去させることができます。例えば、各エントリーに最近アクセスした 保存元オリジン全体で 最終使用時刻が最も古いものから削除するポリシーを使用できます。ユーザーエージェントは、どのファイルが保存されているか、 各ファイルにどのオリジンがアクセスしたかをユーザーが確認でき、エントリーを手動で 削除したり、すべての Cross-Origin Storage データを消去したりできる設定 UI を提供することが期待されます。

ユーザーがオリジンのサイトデータを消去するとき、ユーザーエージェントは、そのオリジンが含まれるすべての 保存元 オリジン集合からそのオリジンを削除するべきです。その削除後に COS エントリーの 保存元 オリジンが空になった場合、ユーザーエージェントはそのエントリーを削除候補として扱うことができます。

5.3. 手動で追加されたエントリー

この節は非規範的です。

上記の設定 UI では、ユーザーがすでにディスク上に持っているファイルを直接 Cross-Origin Storage に追加できる場合があります — 例えば、Web サイトとは無関係にダウンロードした AI モデルです —​ スクリプトが requestFileHandle() を一度も呼び出すことなく追加できます。 そのようなエントリーには、書き込みを帰属させる要求元 オリジンがないため、命令型 API だけでは答えられない 2 つの問題が生じます:

  • § 3.4.1 元の保存者によるアクセスの目的における 元の保存者は誰でしょうか。誰もいません。エントリーの 保存元オリジンは、書き込みを行ったオリジンを含むのではなく、 空で開始します。したがって、どのオリジンも通常の 可用性ゲーティングおよび オリジン確認から 免除されません。これは、実際にバイトを書き込んだオリジンが存在しないため、正しい結果です。

  • そのようなエントリーは、origins を省略した通常の書き込みのように、同一サイトだけに制限するべきでしょうか。いいえ。「同一サイト」は要求元 オリジンとの関係でのみ意味を持ちますが、手動追加には要求元オリジンがないため、「同一サイト」が意味するサイトがありません。 したがって、ユーザーエージェントはそのようなエントリーを代わりに グローバルに 開示可能にし、その明示的な オリジン リストは空のままにすることが期待されます。手動でファイルを シードする目的 — ユーザーがまだ訪問していないサイトに、すでにディスク上にあるファイルを再利用させること — は、 他のオリジンが実際にそれを発見できる場合にのみ達成できるためです。ユーザーエージェントの設定 UI では、 ユーザーがより狭いスコープを選択できるようにしてもかまいません。

この方法で追加された後、状態が "written" のエントリーは、それ以外の点では Web サイトが requestFileHandle() を介して書き込んだものと区別されません。同じ 可用性ゲーティングおよび 可視性の アップグレード規則が適用され、同じ許可を持つ他のエントリーとまったく同様に扱われます —​ エントリーが最終的に グローバルに開示可能になった場合の PHL 上にある確認も含みます。 これは手動追加のデフォルトですが、唯一の可能な結果ではありません。

5.4. 来歴メタデータ

この節は非規範的です。

COS エントリーは、そのバイトが どこから来たかについて意図的に何も記録しません。識別子は ハッシュだけです。同じバイトは、 いくつのオリジンがそれを保存したか、 またはいくつの URL から取得されたかにかかわらず同じエントリーです（§ 2.2 COS エントリーを参照）。URL は エントリー自体ではなく、ある 書き込み側による取得のプロパティであるため、複数のオリジンが書き込んだエントリーについて 1 つを選ぶ非恣意的な方法はありません。また、バイトのように検証することもできません（§ 8.1 リソースの完全性を参照）。 さらに、パスやクエリ文字列は特定の文書、 アカウント、またはセッションを示すことができるため、URL は オリジンの粗い値よりも、ユーザーの閲覧についてはるかに多くの情報を持ちます。 これをエントリーに記録すると、オリジンと § 8.3 可用性 ゲーティングが課すために存在する開示制限を、高エントロピーな信号が迂回することになります。

それでも、それを求める動機は現実にあります。§ 5.2 退去で説明される設定 UI で 数 GB のファイルを見ているユーザーも、 requestFileHandle() 呼び出しが失敗した理由をデバッグしている開発者も、ファイルが どこから来たのかを知りたいでしょう。ユーザーエージェントは、エントリーと並行して実装内部の来歴レコードを 保持することでこれに対応できます — 例えば、それぞれの 保存元オリジンが バイトを取得した URL とその時刻などです — ただし、そのレコードはエントリーの一部ではなくユーザーエージェントの状態として扱われる必要があります:

  • スクリプトには決して公開されません。この仕様にはそれを開示するものはなく、後で追加されるものも 開示するべきではありません。requestFileHandle() も、それが返す FileSystemFileHandle も、そのようなレコードが存在するかどうか、ましてやその 内容を明らかにするべきではありません。特に、要求元 オリジンは、自身が 生成していないレコードを観測できてはなりません。

  • これは信頼された非 Web サーフェスを通じてのみ表示されます。ユーザーエージェント自身の設定およびストレージ 検査 UI、開発者ツール、および — ユーザーエージェントが拡張機能プラットフォームを持つ場合 —​ 閲覧履歴を公開する他の API と同様に、明示的なユーザー付与権限によって保護された拡張機能 API です。検討されている拡張機能サーフェスについては、この リポジトリの ブラウザー拡張機能の統合ポイント解説を参照してください。

  • これは未検証であり、そのようなものとして提示されます。そこに含まれる URL は、バイトを書き込んだ オリジンによる主張であり、それらについての証明ではありません — 内容を保証するのは ハッシュだけです（ § 8.1 リソースの完全性を参照）。2 つのオリジンが同じエントリーについて異なる URL を 記録する可能性があり、どちらかが 不正確または意図的に誤解を招くものである可能性があります。

  • これはエントリー、および帰属先オリジンと同じ存続期間を持ちます。エントリーが退去または削除されると 破棄され、あるオリジンに帰属する部分は、そのオリジンが 保存元オリジンから削除されたときに破棄されます。これには、ユーザーが その オリジンのサイトデータを消去した場合も含まれます（§ 5.2 退去を参照）。

このようなレコードはコンテンツから見えないため、ユーザーエージェントがそれを保持するかどうか、およびどの程度 保持するかは、完全に実装に委ねられます。この仕様のいかなる部分もそれに依存せず、その 有無をサイトが検出することはできません。

6. Permissions Policy との統合

この仕様は、文字列 "cross-origin-storage" によって識別される ポリシー制御機能 [permissions-policy] を定義します。 そのデフォルト許可リスト は self です。

[permissions-policy] は Document に対する 使用を許可されているを定義しますが、 CrossOriginStorageManager は、それ自身の Document を持たない WorkerGlobalScope にも公開されます。したがって、確認は呼び出し元の グローバルオブジェクトに対して記述されます。 ワーカーグローバルは、それを所有する Document 群へ 推移的に解決され、それらすべてが この機能を許可しなければなりません。

グローバルオブジェクト global が与えられたときに 真偽値を返すように、 Cross-Origin Storage 権限を確認するには:

  1. global が Window オブジェクトである場合:

    1. document を global の 関連付けられた Document とします。

    2. document が null の場合、false を返します。

    3. document が "cross-origin-storage" ポリシー制御機能の 使用を許可されていない場合、 false を返します。

    4. true を返します。

  2. global が WorkerGlobalScope オブジェクトである場合:

    1. owners を global の 所有者集合とします。

    2. owners が 空である場合、false を返します。

    3. owners の各 owner について 反復します:

      1. owner が Document であり、かつ owner が "cross-origin-storage" ポリシー制御機能の 使用を許可されていない場合、 false を返します。

      2. owner が WorkerGlobalScope オブジェクトであり、owner を与えて Cross-Origin Storage 権限を確認するを実行した結果が false の場合、false を返します。

    4. true を返します。

  3. false を返します。

このアルゴリズムが false を返す グローバルオブジェクトから行われるすべての requestFileHandle() 呼び出しは、ハッシュ検証、レジストリ検索、または書き込みが 行われる前に "NotAllowedError" DOMException で拒否されます。

注: 所有者集合を通じて解決することにより、この機能が 名目上だけのオプトアウトになることを防ぎます。blob: URL から作成されたワーカーは、その作成元ページの オリジンで実行され、そのページの Cross-Origin Storage ビューを完全に共有します（ § 3 CrossOriginStorageManager インターフェイスを参照）。したがって、 グローバル自身の Document だけを参照する確認では、すべてのワーカーで自明に満たされてしまい、呼び出しを new Worker(URL.createObjectURL(&hellip;)) に移すだけで、それ以外を何も変えることなく cross-origin-storage=() ポリシーを 回避できてしまいます。

注: ServiceWorkerGlobalScope の 所有者集合は空であるため、この アルゴリズムはそこで false を返します。これは [HTML] の欠落ではなく、構造上のものです。 所有者集合は、ワーカーが作成されたときに設定され、 そのワーカーがまだ実際に必要とされているかどうかを判断するために 参照される生存関係ですが、サービスワーカーは意図的に、いかなる Document ともそのような関係を持ちません。 その登録は永続化され、ユーザー エージェントはページが起動するのではなくイベントに応答してグローバルを起動し、まったく サービスワーカークライアントがない状態でも実行できます。 register() を呼び出したクライアントは登録時には分かりますが、 グローバルが実行される頃には通常すでに存在せず、1 つの実行中のサービスワーカーは ポリシーが一致するとは限らない多数のクライアントを処理します。

注: サービスワーカーを対象にするには、所有者をたどるのではなく キャプチャされたポリシーが必要であり、これは この仕様ではなく [permissions-policy] および [service-workers] 側の作業です。この仕様が 適切と考える形は、サービスワーカー自身のスクリプト応答の Permissions-Policy ヘッダーからポリシーを導出することです。これは、そのポリシーコンテナーが すでにその応答の CSP を保持しているのと同じ方法です。これによりポリシーはオリジンの制御下に留まり、 登録時に固定されるのではなく、更新確認のたびに 再評価されます。代わりに登録元クライアントのポリシーをスナップショットすると、ヘッダーから機能を 削除しても登録がたまたま更新されるまで反映されず、オプトアウトが古くなってしまいます。そのような モデルが存在するまでは、フェイルクローズすることが、オプトアウトの回避に利用できない唯一の回答です。

注: SharedWorkerGlobalScope の 所有者集合は、異なるポリシーを持つ複数の Document を保持でき、ワーカーの存続期間中に所有者が追加・削除されます。 すべての所有者が機能を許可することを要求すると、1 つの所有者がそれを許可しないだけで 共有ワーカー全体の Cross-Origin Storage が無効になり、その結果は 2 回の requestFileHandle() 呼び出しの間で変わる可能性があります。これに対して、許可する所有者を 1 つだけ 要求する方式では、機能を許可する任意の文書が、それを許可しない 文書に代わって機能を再び有効にできてしまいます。

7. Cross-Origin-Storage-Allow-Origin ヘッダー

COS エントリーの オリジン リストが 空でない場合、そのエントリーは書き込み元オリジンが制御していないオリジンにも開示可能ですが、 その リストはスクリプト（ origins を介して） またはマークアップによって宣言され、そのどちらもスクリプトまたはマークアップの インジェクションに成功した攻撃者が設定できます。その宣言を、注入されたコンテンツではなく 開示されるバイトを持つオリジンの運用者に帰属できるようにするため、この 仕様は、そのような宣言が指定できるオリジンを制限する応答ヘッダーを定義します。

Cross-Origin-Storage-Allow-Origin 応答ヘッダーは COS スコープ上限を保持します。これは、 開示元環境からの requestFileHandle() 書き込み、または開示元環境へ読み込むホスト統合が、同一サイトではない オリジン リストで指定できる オリジンの 集合です。 宣言された リストは そのまま受け入れられず、上限との 積集合が取られます （作成要求を完了するを参照）。したがって、上限は宣言を 狭めることしかできず、広げたり新たに作成したりすることはできません。

注: このヘッダーは リスト形式にのみ適用されます。 同一サイトのデフォルトはクロスオリジンの 受信者を指定しないため認可を必要とせず、"*" 形式は読み取りパスで 可用性ゲーティングにより 公開ハッシュリストに照らして制御されます。 ユーザーごとの秘密はこれを通過できないため、書き込み時の上限も必要ありません。 "*" にヘッダーを要求すると、公開ハッシュリストがすでに防いでいるもの以外を 新たに防ぐことなく、ゼロ設定のグローバル共有も壊してしまいます。

ヘッダー リスト headers が与えられたときに、オリジンの 集合を返すように、 COS スコープ上限を解析するには:

  1. value を、headers から "Cross-Origin-Storage-Allow-Origin" を 取得し、デコードし、分割する結果とします。

  2. value が null の場合、空の 集合を返します。

  3. ceiling を空の 集合とします。

  4. value の各 token について 反復します:

    1. token から 先頭と末尾の ASCII 空白を除去します。

    2. token が空文字列の場合、継続します。

    3. origin を、token に対して 基本 URL パーサーを実行した結果の オリジンとします。

    4. origin が失敗であるか、不透明なオリジンである場合、空の 集合を返します。

      注: これには、オリジンとして解析されない "*" の token も含まれます。 Cross-Origin-Storage-Allow-Origin ヘッダーは、有限個の具体的な オリジンだけを列挙できます。"*" は許可された値ではありません。「任意のオリジン」という上限を許すと、 注入されたコンテンツが好きな受信者を宣言でき、 ヘッダーの目的全体を無効にしてしまうためです。 無制限の 開示は、"*" の オリジン形式を通じてのみ実現され、 これは 公開ハッシュリストによってゲートされ、この ヘッダーを参照することはありません。不正な、または "*" を含むヘッダーは、 ヘッダーがない場合とまったく同じく何も認可しません。失敗時は閉じる動作になります。

    5. origin を ceiling に 付加します。

  5. ceiling を返します。

注: 取得し、デコードし、分割するは U+002C (,) で分割するため、 ヘッダー 値内のオリジンはコンマ区切りになります。これは Timing-Allow-Origin [RESOURCE-TIMING] および リスト値を持つ HTTP 応答ヘッダーの一般的な 慣例と一致します。一方、同類の crossoriginstorage HTML コンテンツ 属性は、そのホスト構文に合わせて空白区切りです。どちらも同じ オリジンの 集合に解決されます。

グローバルオブジェクト global が与えられたときに、オリジンの 集合を返すように、 COS スコープ上限を取得するには:

  1. global が Window オブジェクトである場合:

    1. document を global の 関連付けられた Document とします。

    2. document が null の場合、空の 集合を返します。

    3. document の COS スコープ上限を返します。

  2. global が WorkerGlobalScope オブジェクトである場合:

    1. owners を global の 所有者集合とします。

    2. owners が 空である場合、空の 集合を返します。

    3. ceiling を null とします。

    4. owners の各 owner について 反復します:

      1. ownerCeiling を空の 集合とします。

      2. owner が Document である場合、ownerCeiling を owner の COS スコープ上限に設定します。

      3. それ以外で、owner が WorkerGlobalScope オブジェクトである場合、ownerCeiling を owner を与えて COS スコープ上限を取得するを 実行した結果に設定します。

      4. ceiling が null の場合、ceiling を ownerCeiling に設定し、 それ以外の場合は ceiling を ceiling と ownerCeiling の 積集合に設定します。

    5. ceiling を返します。

  3. 空の 集合を返します。

すべての Document は COS スコープ上限を持ちます。これは オリジンの 集合であり、 文書が作成されるときに、その作成に使用された 応答の ヘッダーリストを与えて COS スコープ上限を解析するを 実行した結果に設定されます。

注: ワーカーの 所有者集合全体で積集合を取ることは、 Cross-Origin Storage 権限を確認するを反映しています。 あるオリジンがワーカーの上限に含まれるのは、推移的に、所有するすべての Document がそれを認可した場合だけです。blob: ワーカーは、その作成元ページの オリジンと Cross-Origin Storage ビューを完全に共有するため（ § 3 CrossOriginStorageManager インターフェイスを参照）、 ワーカー自身だけを参照する上限では すべてのワーカーについて空になり、リストにスコープされた書き込みを new Worker(URL.createObjectURL(&hellip;)) に移すと、ページの認可を維持するのではなく 受信者が取り除かれてしまいます。所有者の上限の積集合を取ることで、どの単一の 所有者にもそれを広げさせずに、ページの認可を維持できます。

Document の COS スコープ上限をその 応答から設定し、 各ホスト統合について、保存されるバイトを持つ 応答から同等の上限を 確立するには、ホスト仕様内のフックが必要です。これは [permissions-policy] および [CSP] が応答処理時に設定されるのと同じです。そのような フックが 存在するまでは、この節で必要な動作を直接説明します。将来の改訂では、 § 3.3 ファイルの作成と 書き込みで言及した [FS] フックとともに正式に統合されることが期待されます。

8. プライバシーおよびセキュリティ上の考慮事項

この節は RFC 2119 キーワードを使用している箇所を除き非規範的です。リポジトリ内の セキュリティおよびプライバシー質問票も参照してください。

8.1. リソースの完全性

すべての COS エントリーは暗号学的ハッシュをキーとし、 そのバイトはそのハッシュに対して検証されます（ § 3.3 ファイルの作成と書き込みを参照）。したがってサイトは、 requestFileHandle() を通じて取得したファイルが、 hash を自身で取得した場合に得られるものとまったく同じバイトであることを確信できます。 開発者は Cross-Origin Storage の内容を列挙したり、そのハッシュをすでに知っていないファイルへ アクセスしたりすることはできません。

COS ハッシュは秘密ではありません。それは コンテンツ識別子であり、すでにファイルを持つ誰でも容易に計算でき、 この仕様が対象とする広く配布される種類のリソースについては通常、公知です。例えば、 モデルやライブラリのリリースとともに公開されます。したがって、ハッシュを知っていればエントリーを検索できますが、 ケイパビリティ URL やベアラートークンとは異なり、それ自体ではアクセス権を与えません。検索が成功するかどうかは、 ハッシュがたまたま非公開のままだったかどうかではなく、完全に オリジンと § 8.3 可用性ゲーティングによって制御されます。開発者は、非公開のハッシュを アクセス制御メカニズムとして扱ってはなりません。特定のファイルに関心を持つ攻撃者は、そのハッシュを 推測する必要はなく、ファイル自体を取得するだけでよいためです（§ 8.2 クロスサイトプロービングを参照）。

8.2. クロスサイトプロービング

あるリソースが限られた一部のサイトでしか使用されていない場合、そのリソースが Cross-Origin Storage に存在することを知ることのできる攻撃者は、ユーザーがそれらのサイトのいずれかを 訪問した可能性が高いと推測できます。 requestFileHandle() は存在を知るためのメカニズムであるため、各呼び出しは 実質的にプローブです。この仕様にある 2 つの独立したメカニズムが、プローブから得られる情報を 制限します:

  • オリジン（ § 3.4 リソースの可視性のアップグレードを参照）により、保存元 オリジンは選択したオリジン集合に 開示を制限できるため、独占的または人気の低いリソースをグローバルにプローブ可能にする必要は まったくありません。

  • § 8.3 可用性ゲーティングはさらに、 ハッシュが PHL 上にある場合を除き、 "*" にスコープされたリソースを、その 保存元オリジン外の要求元オリジンに 開示しないようにします。これにより、origins: "*" で保存されたリソースが、 Web 上のすべてのオリジンから自動的にプローブ可能になることを防ぎます。このゲートは "*" にスコープされた エントリーにのみ適用されます。リストおよび同一サイトにスコープされたエントリーでは、 保存元オリジンがすでにそれらについて開示範囲を明示的に限定しているため、最初の項目の制限が唯一の ゲートです。

最初の項目が成立するのは、「選択されたオリジン集合」が Web 全体より意味のある程度に小さいままである場合だけです。 origins の形自体は、呼び出し元が 非常に多数のオリジンを列挙することを妨げません。例えば公開された 人気サイトランキングから組み立てたリストであれば、"*" だけが要求する意図的で明示的なオプトインを 回避しながら、機能的にはグローバル開示に近づけられます。最大オリジンリスト 長（ § 5.1 ストレージ制限を参照）がこれを制限します。実際の 複数プロパティ用途（共通の管理下にある少数の関連オリジン）を収容するには十分小さい一方で、 「すべてのオリジン」に意味のある形で近似するには到底足りない制限により、制限付きオリジン形式の オリジンを "*" の未宣言の代替として使用できないようにします。

ユーザーエージェントはさらに、単一オリジンから繰り返される requestFileHandle() 呼び出しをレート制限するか、その他の方法で抑制するべきであり、 プローブされるハッシュが PHL 上にあるかどうかにかかわらず、 オンデバイスのヒューリスティック（例えば、ユーザーごとに生成されたように見えるハッシュに対する要求パターンの検出）を 適用して、プロービングの試みを識別しブロックしてもかまいません。

§ 9 他の仕様との統合にあるホスト統合の 1 つによって行われる検索も、 ページにエラーを提示しない場合でも同様にプローブです。サイトは、自身のサーバーがフォールバック要求を 受信したかどうかを観測でき、それはここでの「見つからない」結果が持つのと同じ 1 ビットを伝えます。 そのような検索が開示するのは、この仕様のゲートが開示しないものではなく、 これらのゲートは変更なく適用されます。ただし、レート制限は、それらの サーフェスからの検索も requestFileHandle() 呼び出しとともに数える場合にのみ有効です。スクリプト可能な統合は、 同じように容易にループ内で検索を発行できるためです。

8.3. 可用性ゲーティング

保存元 オリジン外のオリジンからの requestFileHandle() 読み取りが成功するかどうかは、常に要求元オリジンがエントリーの読み取りを 許可されているかどうかに依存し、これは オリジンによって制御されます。"*" にスコープされたエントリーでは、2 番目の 独立した問いも適用されます。すなわち、ユーザーエージェントがエントリーがそもそも存在することを開示する意思があるかであり、 これは PHL 登録と GREASE 化によって制御されます。そのようなエントリーでは両方が 満たされなければなりません。リストまたは同一サイトにスコープされたエントリーでは最初の問いだけが適用されますが、 GREASE 化は オリジンが本来 許可する開示を依然として抑制する可能性があります。規範的アルゴリズムについては § 3.2 ファイルの読み取りを参照してください。 したがって、"NotFoundError" はリソースが存在しない 証明ではありません。リソースが存在しない、要求元 オリジンがスコープ外である、"*" にスコープされたリソースのハッシュが PHL 上に（まだ、あるいは永久に）ない、または GREASE 化が真陽性を抑制した、という意味である可能性があります。開発者は "NotFoundError" を 「ネットワークへフォールバックする」より具体的な意味として扱ってはなりません。

注: "*" にスコープされたエントリーの開示は、 現在のコンテキストでサードパーティ Cookie を設定または読み取ることのできる要求元 オリジンにさらに制限されます。そのような エントリーは、PHL 登録にかかわらず、 サードパーティ Cookie を利用できないオリジンには開示されません。これは PHL 登録だけでは防げない抜け穴を塞ぎます。攻撃者は、本来は通常で個別には PHL の対象となるリソースから、 書き込むサブセットを選択することでクロスサイト識別子を構築でき、結果として得られる プローブが通常のトラッキング Cookie より有益かどうかを決める要因は、サードパーティ Cookie の可用性だからです。

8.4. GREASE 化

ユーザーエージェントは GREASE 化（ランダムな 拡張を生成し、拡張可能性を 維持する）を適用してもかまいません。つまり、 § 8.3 可用性ゲーティングが本来 開示を許可する場合でも、ときどき開示可能なエントリーが存在しないかのように応答します。これは、 真の不在とプライバシー目的の偽陰性をサイトが区別しにくくするノイズを加えます。これは UA クライアント ヒントで適用される技法に似ています。

GREASE 化を適用するユーザーエージェントは、対象エントリーのサイズに比例した判断をしなければなりません。 小さなエントリーでは、ネットワーク取得へフォールバックするコストが低いため、時折の 偽陰性は妥当なプライバシー上のトレードオフです。ユーザーエージェントは、 偽の再ダウンロードが得られるプライバシー上の利益に対して明らかに不釣り合いになるサイズのエントリーに GREASE 化を適用してはなりません —​例えば、 ギガバイト規模の AI モデル重みです — その場合の偽陰性は、安価な再取得ではなく、完全で、 観測可能かつ高コストな再ダウンロードを強制するためです。

8.5. フィンガープリンティング

攻撃者が Cross-Origin Storage のプロービングから抽出できる情報は、プローブ対象リソースがどれほど 人気であるかによって制限されます。一般的な AI モデルや広く使われている JavaScript ライブラリなど、 非常に人気のあるリソースをユーザーが持っていると分かっても、そのユーザーがそれを使用する（おそらく非常に 多数の）サイトのいずれかを訪問したことしか分かりません。ユーザーが希少または固有のリソースを持つことを知る方が はるかに多くの情報を与えます。ユーザーエージェントは、名目上の PHL 状態にかかわらず、 ハッシュが意図的にユーザーごとに固有になるよう作られているように見えるリソース（例えば、単一の サイトからしか書き込まれたことがないハッシュ、または異常な頻度で要求されるハッシュ）を検出するオンデバイス ヒューリスティックを適用し、そのようなパターンをプロービングの試みとして扱うことが期待されます。

9. 他の仕様との統合

この節は非規範的です。

ここで定義される COS レジストリは、 requestFileHandle() を直接経由せずに、4 つのホスト統合からもアクセスできます。各 統合はこの文書ではなく、それぞれのホスト仕様で定義されます。この 仕様は、それらの統合が基礎とすることを想定している共有基盤概念（COS ハッシュ、COS エントリー、 可用性ゲーティング、および 公開ハッシュリスト）のみを定義します。

  • HTML: すでに integrity [SRI] を持つ link および script 要素上の crossoriginstorage 属性であり、WHATWG に whatwg/html#12770 で提案されています。

  • JavaScript: Import Attributes 提案を基礎として、integrity とともに使用できるホスト定義の crossOriginStorage import 属性であり、WHATWG に whatwg/html#12771 で提案されています。

  • CSS: integrity() とともに使用できる cross-origin-storage() <request-url-modifier> であり、 CSS Working Group に w3c/csswg-drafts#14056 で提案されています。

  • Fetch: integrity [FETCH] とともに使用できる crossOriginStorage RequestInit オプションであり、WHATWG に whatwg/fetch#1954 で提案されています。 3 つの宣言的形式とは異なり、これにはホスト定義の宛先がないため、 COS レジストリから提供された Response が MIME タイプ、ステータス、およびその他のメタデータをどのように報告するかは、 その仕様における未解決の問題です。COS エントリーが保存するのは バイトだけです。

説明のためだけに、同じグローバル共有リソースを 4 つの各形式を通じて Cross-Origin Storage に オプトインした例を次に示します:

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

これらのスニペットは説明のみを目的としています。この構文はいずれもこの仕様では定義されておらず、 各形式の正式な文法 — 制限付きで "*" ではない origins 値をどのように 記述するかを含む — は、この文書ではなく、それぞれのホスト仕様に属します。表記は意図的に 異なります。RequestInit メンバーは origins と完全に一致する sequence<DOMString> を取れますが、属性値、 import 属性値、および CSS 修飾子の引数はテキストしか保持できません。

4 つの形式すべては、ネットワーク取得へフォールバックする前に、まず一致して開示可能なエントリーがあるか COS レジストリを参照し、 正常に取得され完全性が検証されたリソースを、他のオリジンによる再利用のために COS レジストリへ保存するという、 requestFileHandle() とまったく同じ処理モデルを共有することが期待されます。これらの統合についての 議論は、このリポジトリの issue tracker ではなく、それらを採用するホスト仕様の tracker に属します。
