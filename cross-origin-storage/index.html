概要

クロスオリジンストレージ (COS) は、ウェブアプリケーションがファイルを保存・取得できるコンテンツアドレス指定型キャッシュであり、 AI モデル、WebAssembly モジュール、広く利用されている JavaScript ライブラリなどの大容量ファイルを、 異なるオリジンをまたいで扱える。ファイルは URL ではなく暗号学的ハッシュで識別されるため、バイト単位で同一の リソースをあるオリジンが一度フェッチすれば、ユーザーエージェントが許可する他のどのオリジンでも再利用でき、 再度ダウンロードする必要はない。既定では、同一サイトのオリジンがファイルを読み取れる。書き込み元は、少数のオリジンを追加で指定するか、 すべてのオリジンと共有できる。後者が有効になるのは、ハッシュの普及度が k-匿名性に準じた しきい値を超える場合に限られる。サイトごとにクロスサイトの照会回数と書き込みに上限を設けることで、各サイトが知り得るのは、 他のサイトが保存した内容の一部に限られる。

1. はじめに

この節は規定ではない。

通常、ストレージは利用者のセキュリティとプライバシーを保護するため、オリジンごとに分割される。これは適切な 既定動作だが、非常に大きく、広く利用され、一般に配布されている一部の リソース（AI モデル、WebAssembly モジュール、JavaScript ライブラリ、ゲームエンジン、大容量のウェブフォント）には適さない。 これらは、どのサイトが要求してもバイト単位で同一のファイルだからである。二つの 互いに無関係なオリジンが同じ 8 GB のモデルに依存する場合、ストレージがオリジンごとに分割されていると、 利用者は同じモデルを二度ダウンロードして二重に保存する必要がある。これは利用者の帯域幅、ストレージ、 バッテリーを浪費し、ネットワーク全体にとっても無駄になる。

クロスオリジンストレージ（COS）は、コンテンツアドレス指定方式のキャッシュであり、キーには暗号学的ハッシュを URL の代わりに用いる。これにより、ユーザーエージェントは、そのようなリソースの保存済みコピー一つを、 利用を明示的に選択したオリジン間で共有できる。COS にリソースを保存するかどうかは、常に 保存元オリジンが明示的に選択する。ユーザーエージェントは、リソースの存在を明かすことを、 本来そのリソースを読み取ることが許されているオリジンに対しても差し控えてよい。§ 8 プライバシーと セキュリティに関する考慮事項を参照。

この仕様のエントリーポイントは、getFileHandle() メソッドであり、crossOriginStorage を介して公開される。 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.getFileHandle(hash);
  const file = await handle.getFile();
  // ファイルを使って何らかの処理を行う。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // クロスオリジンストレージに存在しないか、その存在を開示できないため、ネットワークから取得する。
  }
}

この仕様は、FileSystemFileHandle、 FileSystemWritableFileStream、 およびこれらに関連する 基盤をファイルシステム標準 [FS] から再利用する。その適用範囲は、オリジン間で 共有され、各オリジンの非公開ファイルシステムや利用者に見えるファイルシステムとは別の、専用ファイルシステムである。

この仕様は、命令型の JavaScript API に加え、ホスト側の 統合の基盤となる共通の保存手順を定義する。関連する提案では、同じキャッシュを他のホスト 仕様にも統合する。HTML の crossoriginstorage 属性は、 link および script に用いる。 他にも、 crossOriginStorage という JavaScript のインポート属性、CSS の cross-origin-storage() <request-url-modifier>、および crossOriginStorage という RequestInit オプション（fetch() 用）がある。それぞれ、 対応するホスト仕様で定義される。§ 9 他の仕様との 統合を参照。

2. 概念

2.1. ハッシュ

COS ハッシュは、構造体であり、 次の項目を持つ。

アルゴリズム

ハッシュアルゴリズムの名前を表す文字列。 指定できるのは、[WEBCRYPTO] が認識する "SHA-1" 以外のハッシュアルゴリズムであり、 例えば "SHA-256" がある。

値

ダイジェストを表す文字列。ダイジェストは小文字の十六進数で符号化し、その生成には アルゴリズムを用いる。 "SHA-256" の場合、この文字列の長さは 64 文字である。

algorithm 辞書メンバーの型は単純な DOMString であるが、その値域は [WEBCRYPTO] の ハッシュアルゴリズムが受け付ける名前の集合と正確に一致する。HashAlgorithmIdentifier は (object or DOMString) であり、その object 分岐は、 [WEBCRYPTO] に従って Algorithm の形を持つ 辞書に正規化される。この分岐を使えば、呼び出し元は追加の パラメーターを必要とするアルゴリズムにそれらを渡せる（例：{name: "HMAC", hash: "SHA-256"}）。ハッシュ アルゴリズムはそのようなパラメーターを取らない。 アルゴリズムは、保存、 比較、および往復変換の際に、コンテンツアドレス指定方式の キーの一部として扱われる。また、この仕様の 例では常に単なる文字列を用いる。ここで任意のオブジェクトを受け付けても機能は増えず、 等価性の判定と直列化が 不必要に複雑になる。したがって、DOMString の方が このフィールドの値をより厳密に限定でき、型として適切である。

二つの COS ハッシュの値が等しいのは、それぞれのアルゴリズムの 値が ASCII 大文字・小文字を区別せずに一致し、かつそれぞれの値が完全に 等しい場合である。

注： 値については、すでに小文字を用いることが規定されている（上記参照）。したがって、その比較は 単純な 文字列比較である。アルゴリズムについては大文字・小文字の別が規定されていないため、 ASCII 大文字・小文字を区別せずに比較する。

コンテンツアドレス指定方式の ストアでは、エントリーのキーが同じかどうかを、 等価性に基づいて判定する。比較するのは COS ハッシュである。二つのファイルの バイト列とハッシュアルゴリズムが同一であれば、それらは同じエントリーである。保存したオリジンの数や 取得元の URL の数は問わない。

2.2. COS エントリー

COS パーティションは、 環境設定群オブジェクト settings に対して、 次の操作の結果として定まる。 サイトを取得する操作を settings のトップレベルオリジンに適用する。settings が ファーストパーティ COS コンテキストであるのは、サイトを取得する操作を settings のオリジンに適用した結果が同一 サイトとなる場合である。比較対象はその COS パーティションである。

COS 共有レコード は、構造体であり、 次の項目を持つ。 オリジンは、あるオリジンである。パーティションは、書き込み時の COS パーティションであり、ここでいう書き込みとは レコードを追加した書き込みを指す。ファーストパーティは、 真偽値であり、 その書き込みがファーストパーティ COS コンテキストで行われたかどうかを記録する。レコードは、読み取りの COS パーティションが同一サイトとなる場合に、その読み取りに適用される。比較対象はレコードのパーティションである。 COS の開示を 判定するを参照。

各ユーザーエージェントは一つの COS レジストリーを持つ。これはマップであり、COS ハッシュの値を COS エントリーという構造体に対応付ける。 このマップは、クロスオリジンストレージを利用するすべてのオリジンが共有する。 COS エントリーは次の項目を持つ。

ハッシュ

COS ハッシュ。

バイト列

このバイト列のダイジェストは、ハッシュのアルゴリズムで求めると、 ハッシュの値に等しい。

注： エントリーが COS レジストリーに追加されるのは、 書き込み元がこのバイト列を提供し、 ユーザーエージェントがそれを検証した後に限られる。検証して保存するを参照。書き込みが要求されても、 完了するまでは、レジストリーにはそれを表すものが一切ない。そのため、読み取り側からは進行中の 書き込みと、書き込みがない場合とを区別できない。§ 8.3 進行中の書き込みを参照。

オリジン群

このリストの各 COS 共有 レコードは、クロスオリジンの読み取りアクセスを明示的に許可する。この許可は 公開ハッシュ リストとは独立している。各レコードは、同一サイトのすべてのオリジンに及ぶ。比較対象はレコードの オリジンである。したがって、https://a.example を列挙すると、 https://www.a.example も許可される。また、レコードのファーストパーティが真であれば、そのレコードは、 ファーストパーティ COS コンテキストにある読み取り元にも、トップレベルサイトを問わず適用される。 リストは初期状態では空で、その後は 増える一方である。これは、 エントリーを読み取れる主体を決める、互いに独立し加算的に適用される三つの範囲の一つである。 残りの二つは、エントリーの保存元オリジン群（常に読み取り可能であり、他の オリジンも、これらと 同一サイトであれば同様である）と、グローバルに 開示可能かどうかである。

注： したがって、あるオリジンを指定することは、その サイト全体を信頼することを意味する。書き込み元が指定したオリジンの サイトが、書き込み元の信頼しないコンテンツをホストしている場合、例えば公開サフィックスリストに載っていない ホスティング用ドメインの場合には、それらすべてのコンテンツにエントリーが開示される。

注： 書き込み時に origins として明示的に空の リスト （origins: []）を指定しても、origins を省略した場合と許可範囲はまったく同じである。対象はエントリーの 保存元オリジン群と、それらと同一サイトのオリジンであり、これはすべてのエントリーに 共通する基本範囲である（COS の開示を判定するを参照）。範囲の上限を 適用すると、 空のリストは null になる。したがって、いずれの書き込みも、 作成要求を完了するための残りの手順に同じ状態で進む。 明示的なリストは開示先を追加するだけであり、 書き込み元自身のサイトへのエントリーの開示を妨げることはない。

グローバルに開示可能

この真偽値は初期状態では偽であり、エントリーの書き込み時に 次の要求が行われ、それが認められたかどうかを記録する。すなわち、 グローバル（"*"）に利用可能にする要求が行われ、その要求が COS ユーザー活性化 ゲートを通過したかどうかである。この値が 真であれば、要求が § 8.4 可用性の制御を通過したどのオリジンも、エントリーを読み取れる。すなわち、 要求したハッシュが PHL に載っていること、クロスサイト検索予算が要求を許容すること、 および GREASE 処理が要求を抑止しないことが条件である。いったん 設定されると、この値は真のままとなる。

注： これは、別個の項目としてオリジン群から独立している。そのため、 後から グローバルに利用可能にする要求があれば、グローバルな範囲が既存の明示的な オリジン群のリストに加わる。 仮にこの二つを一つのフィールドにまとめると、バイト列を提供した書き込み元は、 リストに限定されていたエントリーの範囲を "*" に変更できてしまう。§ 8.4 可用性の制御が 適用されるのはグローバルな範囲だけなので、それまではリストに基づいて エントリーを読み取れたオリジンにも、以後は "NotFoundError" が返ることになる。 これは、エントリーのハッシュについて、 次の条件が成立しない場合に必ず起こる。すなわち、 PHL に載っているという条件である。二つの 範囲を独立させれば、可視範囲の変更はすべて拡大に限られる。これは、 拡大は可能だが縮小はできないという 要件を満たす。

保存元オリジン群

この集合は COS 共有レコードからなり、各オリジンと COS パーティションの組に対して、そのパーティションの下でその オリジンがこのエントリーのバイト列の書き込みを少なくとも一度正常に完了していれば、一つのレコードを持つ。 各レコードのファーストパーティは考慮しない。この集合はページを 読み込み直しても保持され、時間とともに 増える。減少するのは § 5.2 追い出しに記述された場合に限られる。レコードのオリジンは常に、 エントリーのハンドルを取得できる。その際には getFileHandle() をレコードのパーティションの下で使用する。 このアクセスは、オリジン群にも、エントリーのハッシュが 公開ハッシュリスト（PHL）に載っているかどうかにも依存しない。§ 3.5.2 元の保存者によるアクセスを参照。

注： 共有レコードをトップレベル サイトでキー付けすると、埋め込みフレームから見える クロスオリジンストレージの範囲は、ストレージの分割によって他のストレージに適用される範囲と同じになる。このキーがなければ、 複数のサイトに埋め込まれたフレームは、あるサイトで小さなファイルを書き込み、別のサイトで 保存元オリジンとしてそれらを読み戻すことができ、公開ハッシュリスト、GREASE 処理、 および クロスサイト検索予算を迂回できてしまう。これは実質的に サードパーティ Cookie と同じである。トップレベルでの書き込みにもキーを用いるため、 トラッカーがトップレベルでの訪問時に一度書き込んだ情報を、あらゆるサイトの自分のフレームから読み戻すことはできない。 オリジン群のレコードが ファーストパーティ COS コンテキストに由来する場合、読み取り元もファーストパーティであれば、 どのトップレベルサイトの下でもそのレコードが適用されるため、トップレベルサイト間の制限付き共有は引き続き機能する。 別のトップレベルサイトの下でそのレコードに基づいて検索に応答すると、書き込み元のサイトの下で 保存された内容が開示されるため、クロスサイト検索予算にその検索を計上する（可用性の制御を適用するを参照）。 グローバルに開示可能には、このキーを用いない。すでに公開ハッシュ リスト、GREASE 処理、 およびクロスサイト検索予算によって制御されているからである。

ユーザーエージェントには、クロスオリジンストレージキューが関連付けられる。これは、 新しい並列キューを開始する操作の結果である。COS レジストリーに対するすべての操作は、 キューに追加する際に、このキューを用いる。こうすることで、各操作は キューに 追加された順序で実行され、互いに入り交じることがない。

2.3. 公開ハッシュリスト

あるハッシュがクロスオリジンストレージに存在することを確認するだけで、 利用者の閲覧履歴に関する情報が漏れる可能性がある（§ 8.2 クロスサイトでの探索を参照）。これは グローバルな範囲に特有のリスクである。エントリーの明示的なオリジン群のリストと、すべての エントリーに 共通する同一サイトの基本範囲については、開示先がすでに保存元オリジンの明示的な選択によって制限されている。一方、 エントリーをグローバルに開示可能にすると、ウェブ上のどの オリジンにも開示され得る。この 特有のリスクを抑えるため、グローバルに開示可能なリソースについて、この範囲に基づいて その保存元オリジン群以外のオリジンに開示できるのは、ハッシュが追加の、 独立した条件を満たす場合に限られる。その条件は、公開ハッシュリスト （PHL）に載っていることである。これは、ベンダーに依存しない、実装定義の許可リストであり、COS ハッシュの 値を収録する。公開ハッシュリストにハッシュを収録するのは、k-匿名性に類する 普及度の基準を満たした後に限られる（例えば、一定数以上の独立した オリジンにバイト単位で同一のリソースが現れること）。これにより、共有キャッシュにそのリソースが存在すると確認できても、個々の 利用者について明らかになることはほとんどない。

COS ハッシュ hash が公開ハッシュ リストに載っているのは、hash が 等しいと判定されるエントリーが、ユーザー エージェントが現在保持する公開ハッシュリストのスナップショットに存在する場合である。

取得プロトコル、 更新頻度、データ形式、普及度のしきい値、運営体制といった 公開ハッシュリストの詳細は、この仕様に付随する別の成果物で設計している。その手本は、 公開サフィックスリストである。これは [URL] 標準に付随するデータファイルである。 このリポジトリーの公開ハッシュリストの解説を参照。その設計では、 公開サフィックスリストで複数のベンダーが継続的にリリースしてきた前例にならい、WHATWG による運営を提案している。 また、広く普及していることが独立に裏付けられているかどうかを収録基準としている。 これは前述の k-匿名性に類する基準を具体化したものであり、オフラインで一度だけ、 ハッシュの収録手続きの一環として適用する。したがって、ユーザーエージェントが照会のたびに繰り返すことはない。これらはいずれも、 現時点ではこの提案の外で確立されたものではない。リスト自体の初期の参考用プロトタイプ実装は、 現在のところ、このリポジトリーの public-hash-list/implementation/ にある。専用の リポジトリーを複数のベンダーが共同で運営することが、引き続き PHL の解説に示された目標である。この 仕様が依存するのは、ハッシュが PHL に載っているかどうかだけである。したがって、 リストの取得機構、運営モデル、その他の設計がどのように変化しても、この仕様は引き続き成り立つ。

3. CrossOriginStorageManager インターフェイス

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> getFileHandle(
      CrossOriginStorageGetFileHandleHash hash,
      optional CrossOriginStorageGetFileHandleOptions options = {});
};

dictionary CrossOriginStorageGetFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageGetFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [Exposed=(Window,Worker), SameObject, SecureContext]
  readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

各 Navigator および WorkerNavigator オブジェクトには、一つの CrossOriginStorageManager オブジェクトが関連付けられている。crossOriginStorage の取得子の 手順は、 this に関連付けられた CrossOriginStorageManager を返すことである。

各 CrossOriginStorageManager オブジェクトには、オリジンが関連付けられている。この値には、 this の関連する設定群オブジェクトのオリジンを設定する。また、各オブジェクトには パーティションが関連付けられており、その値には COS パーティションを設定する。これは this の 関連する設定群オブジェクトのものである。これらの値はオブジェクトの作成時に設定する。

注： オリジンは関連する設定群オブジェクトから取得し、 スクリプト自体の性質には依存しない。これがワーカーにどう影響するかを明記しておく。 blob: URL から作成されたワーカーのオリジンは、そのワーカーを作成したコンテキストのオリジンであり、そのオリジンと クロスオリジンストレージで見える範囲が完全に一致する。ワーカーが書き込んだものは作成元のページが読み戻せ、 ページが保存したものはワーカーが読み取れる。blob: URL が独自のオリジンを持つわけではなく、 その URL を失効させても、ワーカーから見える範囲は変わらない。data: URL から作成されたワーカーは、 不透明なオリジンを持つ。この仕様では現在、 getFileHandle() の呼び出し元のオリジンが不透明である場合の動作を定義していない。 COS 要求を検証する手順でのオリジンに関する規則は、 呼び出し元が指定するオリジンにのみ適用される。不透明なオリジンには、 保存元 オリジン群のキーや同一 サイトかどうかの比較に使える安定した識別情報がないため、 そのオリジンに意味のあるアクセス権を付与することはできない。

3.1. getFileHandle() メソッド

handle = await navigator . crossOriginStorage . getFileHandle(hash)

hash で識別されるファイルが存在し、かつそのファイルを クロスオリジンストレージから呼び出し元オリジンに開示できる場合、そのハンドルを返す。それ以外の場合、プロミスは "NotFoundError" DOMException で拒否される。 "NotFoundError" が返っても、そのファイルが クロスオリジンストレージに物理的に存在しないことの証明にはならない。§ 8.4 可用性の制御を参照。呼び出し元はこれを、 「代わりにネットワークから取得する」という意味に受け取ることができる。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true })

hash で識別されるファイルを クロスオリジン ストレージに書き込むためのハンドルを返す。エントリーがまだ存在しなければ新規に作成し、既定では開示先を同一サイトのオリジンに制限する。 呼び出し元は、ファイルの内容全体を、ハンドルの createWritable() メソッドを介して書き込む必要がある。これはエントリーがすでに 存在していたかどうかを問わない。ユーザーエージェントはその時点で、書き込まれたバイト列のハッシュが hash と一致することを検証し、 一致しなければ "DataError" DOMException で拒否する。この要件により、 オリジンが作成要求を利用して hash がすでに存在していたかどうかを判別することを防ぐ。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: "*" })

上記と同様だが、書き込み後は、次の条件を満たすどのオリジンにもエントリーを開示できる。その条件は、 hash に対するそのオリジンの要求が § 8.4 可用性の制御を通過することである。

handle = await navigator . crossOriginStorage . getFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

上記と同様だが、開示先を、列挙されたオリジンと、それらのいずれかと同一サイトである オリジンに制限する（これらに加え、呼び出し元オリジン、すでに 保存元オリジン群に含まれるオリジン、およびそれらと同一サイトであるオリジンにも開示できる）。

getFileHandle(hash, options) メソッドの 手順は次のとおりである。

  1. result を新しい プロミスとする。

  2. realm を this の関連するレルムとする。

  3. global を this の関連するグローバルオブジェクトとする。

  4. origin を this に関連付けられたオリジンとする。

  5. partition を this のパーティションとする。

  6. クロスオリジンストレージの許可を確認する手順を global を与えて実行した結果が 偽である場合は、次の手順を実行する。

    1. グローバルタスクをキューに追加する。タスクソースにはDOM 操作タスクソースを用い、 global を与える。このタスクで 拒否するプロミスは result、拒否理由は "NotAllowedError" DOMException とする。

    2. result を返す。

  7. validationFailure を、COS 要求を 検証する手順に hash および options を与えて実行した結果とする。

  8. validationFailure が null でない場合は、次の手順を実行する。

    1. グローバルタスクをキューに追加する。タスクソースにはDOM 操作タスクソースを用い、 global を与える。このタスクで 拒否するプロミスは result、拒否理由は validationFailure とする。

    2. result を返す。

  9. 次の手順をキューに追加する。追加先は クロスオリジンストレージキューとする。

    1. options["create"] が真である場合は、次の手順を実行する。

      1. 作成要求を完了する手順に result、hash、options、global、および realm を与えて実行する。

    2. それ以外の場合は、次の手順を実行する。

      1. 読み取り要求を完了する手順に result、hash、origin、partition、 global、および realm を与えて実行する。

  10. result を返す。

COS 要求を 検証するには、CrossOriginStorageGetFileHandleHash hash および CrossOriginStorageGetFileHandleOptions options を受け取り、次の手順で null または TypeError を返す。

  1. hash["algorithm"] がハッシュアルゴリズムの 名前として [WEBCRYPTO] に認識されないか、または ASCII 大文字・小文字を区別せずに比較して "SHA-1" と一致する場合、 新しい TypeError を返す。

    注： SHA-1 は衝突耐性を持たない。 COS エントリーのキーには、 その COS ハッシュだけを用いる。そのため、SHA-1 で 衝突が起これば、あるオリジンのバイト列が、別の オリジンが同じダイジェストを持つ別のバイト列を読み取ろうとしたときに返され得る。

  2. hash["value"] が次の正規 表現 /^[0-9a-f]{64}$/ に一致せず、かつ hash["algorithm"] が ASCII 大文字・小文字を区別せずに "SHA-256" と一致する場合、新しい TypeError を返す。

    注： 将来のハッシュアルゴリズムでは、 ダイジェストに期待する長さを別の値に定めることができる。この 仕様で規定として制約を課すのは "SHA-256" だけである。これは、 すべての 例でこのアルゴリズムを使用していることに対応する。

  3. options["origins"] が存在し、かつ "*" でない場合は、次の手順を実行する。

    1. candidates を options["origins"] とする。 ただし、単一の文字列は、要素一つのリストとして扱う。

    2. candidates のサイズが、 ユーザーエージェントの オリジンリストの最大長を超える場合、 新しい TypeError を返す。

      注： この上限は、受け取ったままの candidates に対して、構文解析や 重複排除を行う前に適用する（要求されたオリジン群を正規化するを参照）。したがって、 一度の呼び出しで生じる URL の 構文解析の量も制限される。リストに含まれる同じオリジンの個数が オリジンリストの最大長を一つ超えていれば、 そのリストは拒否される。正規化すれば 一つのオリジンになるとしても同様である。

    3. 各 candidate について、 candidates 内を順に処理する。

      1. url を、基本 URL パーサーを candidate に対して実行した結果とする。

      2. url が失敗である場合、新しい TypeError を返す。

        注： origins を省略するか、 または 空のリストを渡した場合に限り、同一サイトという既定の範囲を要求する。空 文字列は、リストに含まれる唯一の 候補として構文解析に失敗するため、他の無効なオリジンと同様に拒否される。 一方、 宣言的な統合で同一サイトを意味する空の値（ § 9 他の仕様との 統合を参照）は、それらのテキスト構文に固有のものであり、 それぞれのホスト仕様で定義される。

      3. url のスキームが "http" と "https" のいずれでもない場合、または url の オリジンが潜在的に信頼できる オリジンでない場合、新しい TypeError を返す。

        注： オリジンを列挙する意味があるのは、 そのオリジン自体が getFileHandle() を呼び出せる場合だけである。API が公開されるのはセキュアコンテキストに限られるため、ここでは https: オリジンと、ループバックの http: オリジン（例えば http://localhost）を許可する。一方、拒否する対象は、 他のホストの http: オリジン、ws:、wss:、 ftp:、および オリジンが不透明なすべてのスキームであり、chrome-extension: のような拡張機能用スキームも これに含まれる。

  4. null を返す。

3.2. ファイルの読み取り

読み取り要求を 完了するには、プロミス result、COS ハッシュ hash、 オリジン origin、サイト partition、グローバルオブジェクト global、およびレルム realm を受け取り、次の手順を実行する。

  1. entry を、次の条件を満たす COS エントリーとする。すなわち、COS レジストリー内にあり、そのハッシュが 等しいと判定されるものである。比較対象は hash とする。そのようなエントリーがなければ null とする。

    注： 別の書き込み元が 要求したもののまだ完了していない書き込みは、 COS レジストリーに存在しない。したがって、 このようなハッシュでは entry は null となり、このアルゴリズムは、 どのオリジンも一度も書き込んだことのないハッシュとまったく同じように進む。この仕様で許される開示はすべて、 後述の可用性の制御を適用する手順で決まる。この手順より 前の分岐で先に応答を返すことは できない。§ 8.3 進行中の書き込みを参照。

  2. disclosableEntry を、可用性の制御を 適用する手順に entry、 origin、および partition を与えて実行した結果とする。

  3. disclosableEntry が null である場合は、次の手順を実行する。

    1. グローバルタスクをキューに追加する。タスクソースにはDOM 操作タスクソースを用い、 global を与える。このタスクで 拒否するプロミスは result、拒否理由は "NotFoundError" DOMException とする。

    2. リターンする。

  4. handle を、新しい FileSystemFileHandle を作成する手順の結果とする [FS]。その ロケーターは、disclosableEntry のハッシュを クロスオリジンストレージファイルシステム内で指し示す。作成先のレルムは realm とする。

  5. handle の COS ハッシュを disclosableEntry のハッシュに設定する。

  6. handle の COS オリジンを origin に設定する。

  7. handle の読み取り可能を真に設定する。

    注： このハンドルは、すでに可用性の制御を適用する手順を通過しているため、呼び出し元オリジンには この エントリーのバイト列を読み取る権限がある。

  8. グローバルタスクをキューに追加する。タスクソースにはDOM 操作タスクソースを用い、 global を与える。このタスクで 解決するプロミスは result、その値は handle とする。

COS の開示を 判定するには、COS エントリー または null である entry、 オリジン origin、およびサイト partition を受け取り、次の手順で COS エントリーまたは null を返す。

  1. entry が null である場合、null を返す。

    注： COS レジストリー内のエントリーは 常に書き込みと検証が済んでいるため、このアルゴリズムで 書き込み途中の状態を考慮する必要はない。あるハッシュについて唯一の書き込みがまだ進行中であれば、そのハッシュは レジストリーに存在せず、このアルゴリズムには null として渡される。これはどのオリジンも一度も 書き込んだことのないハッシュと同じである。§ 8.3 進行中の書き込みを参照。

  2. firstParty は、サイトを取得する操作を origin に適用した結果が 同一サイトとして partition と一致する場合は真、それ以外の場合は偽とする。

  3. entry の保存元オリジン群が次の条件を満たすレコードを含むかを調べる。 COS 共有 レコードのうち、 オリジンが同一サイトとして origin と一致し、かつパーティションが 同一サイトとして partition と一致するものがあれば、entry を返す。

    注： 元の保存者、および エントリーを自ら正常に書き込んだすべてのオリジンは、 書き込み時と同じトップレベルサイトの下で常にそのエントリーを読み戻せる。 § 3.5.2 元の保存者によるアクセスを参照。

    注： すべてのエントリーに共通する 同一サイトの基本範囲（書き込み時に origins オプションを指定しない場合に要求されるアクセス範囲）は、常に有効である。 これは、オリジン群のリストやグローバルな範囲が 後から追加されても変わらない。この範囲は、後述の公開ハッシュリストによる判定より 先に確認するため、同一サイトの オリジンは、エントリーのハッシュが PHL に載っているかどうかにかかわらず、そのエントリーを読み取れる。ここでは同一サイトを 一つの信頼単位とするため、サイトの境界を越えて情報が開示されることはない。この境界は § 8.2 クロスサイトでの探索が保護するものである。

  4. entry のオリジン群が次の条件を満たすレコードを含むかを調べる。 COS 共有 レコードのうち、 オリジンが同一サイトとして origin と一致し、さらに次のいずれかを満たすものを対象とする。レコードのパーティションが 同一サイトとして partition と一致するか、またはレコードのファーストパーティと firstParty が いずれも 真である。そのようなレコードがあれば、entry を返す。

    注： 明示的なオリジン群の リストに載っているオリジン、 またはそのいずれかと同一サイトのオリジンは、 エントリーを読み取ることができる。エントリーが PHL に載っている必要はない。列挙された各オリジンの範囲を そのサイトに広げるのは、前述の同一サイトの基本範囲と同じ考え方である。同一サイトのオリジンは一つの信頼単位なので、 サイトのオリジンを一つ指定すれば、それらすべてを指定したことになる。保存元オリジンは、開示先のオリジンを 指定する ことで、開示範囲を限定している（§ 3.5 リソースの可視範囲の拡大および § 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照）。そのうえで、 別途 広く普及していることまで要求すると、通常の制限付き共有が、それとは無関係な、 しかも多くの場合は専有リソースを対象とする公開リストの選定に依存してしまう。この条件を グローバルに開示可能かどうかの判定より先に確認することで、 後からグローバルな可用性を要求する書き込みがあっても、 列挙されたオリジンのアクセス権は失われない。§ 8.2 クロスサイトでの 探索を参照。

  5. entry のグローバルに開示可能が真である場合は、次の手順を実行する。

    1. entry のハッシュが PHL に載っているという条件を満たさない場合、null を返す。

      注： 公開ハッシュリストによる判定は、 グローバルな範囲にのみ適用する。この判定がなければ ウェブ上のどのオリジンにも開示され得るのは、この場合だけである。エントリーが グローバルに開示可能であっても、そのハッシュが PHL に 載っているという条件を満たさなければ、 この範囲だけを根拠に対象となるオリジンには開示しない。一方、そのオリジンが以下にも 含まれる場合、すなわち、 保存元オリジン群、明示的なオリジン群のリスト、または それらのいずれかと同一サイトのオリジンの集合に含まれる場合は、上の手順ですでにエントリーが返されている。

    2. ユーザーエージェントがこの要求に GREASE 処理を適用することを選択した場合、 null を返す。

      注： GREASE 処理も、 グローバルな範囲にのみ適用する。上で確認したレコードに基づく読み取りがこの手順に達することはない。保存元オリジンと、 それと同一サイトのオリジンは一つの信頼単位である。また、 明示的なオリジン群のリストに載っているオリジンは、 書き込み元が意図的に指定し、その Cross-Origin-Storage-Allow-Origin ヘッダーで許可したものである。この許可は、 同一サイトのオリジン にも及ぶ。

    3. entry を返す。

  6. null を返す。

可用性の制御を 適用するには、COS エントリーまたは null である entry、 オリジン origin、およびサイト partition を受け取り、次の手順で COS エントリーまたは null を返す。

  1. 計上対象外の検索かどうかを判定する手順を entry、 origin、および partition を与えて実行した結果が 偽であり、かつクロスサイト検索を計上する手順を partition を与えて実行した結果が偽である場合、 null を返す。

    注： 予算超過で拒まれた検索は null を返し、読み取り要求を完了する手順が これを、検索が外れた場合と同じ "NotFoundError" DOMException に、検索が外れた場合と同じ時間で変換する。 計上対象の検索は、エントリーが見つかるかどうかにかかわらず計上する。検索が外れた場合にも、 ヒットした場合と同程度の情報が明らかになるからである。

  2. COS の開示を判定する手順に entry、 origin、および partition を与えて実行した結果を返す。

3.2.1. クロスサイト検索予算

各サイトは、クロスサイト検索予算を持つ。これは構造体であり、次の項目を持つ。 回数は非負の整数で、初期値は 0 である。 期間の開始時刻は時刻または null で、初期値は null である。 この 予算は利用者が訪問しているトップレベルサイトに属するため、ページ内のすべてのフレームと、 それらのフレームが読み込むすべてのオリジンが同じ予算を消費する。

ユーザーエージェントは、実装定義のクロスサイト検索の最大回数を持つ。これは 小さな 正の整数である。また、実装定義の検索期間を持つ。これは時間の長さである。

注： 検索予算を 8 回から 16 回程度とし、 期間を 1 週間程度とすれば、 トラッカーが一期間内に取得できる情報は、クロスサイト識別子に必要な約 32 ビットを大きく下回る。一方で、 サイトが実際に使用する共有ファイルを検索するには十分な回数を確保できる。

ユーザーエージェントは、各サイトのクロスサイト 検索予算を、複数回のページ読み込みにまたがり、かつ 利用者のすべてのトップレベルのトラバーサブルにまたがって保持しなければならない。これにより、ページを再読み込みしたり新しいタブで開いたりしても、 予算はリセットされない。また、サイトの予算については、 利用者がそのサイトの データをユーザーエージェント自身の設定画面またはストレージインターフェイスで消去したときに、初期状態に戻さなければならない。 Clear-Site-Data 応答ヘッダーなど、サイト自体が引き起こせる事象に応じてリセットしてはならない。

検索が計上対象外であるかどうかを判定するには、 COS エントリーまたは null である entry、 オリジン origin、およびサイト partition を受け取り、次の手順を実行する。

  1. entry が null である場合、偽を返す。

  2. entry の保存元オリジン群が次の条件を満たすレコードを含むかを調べる。 COS 共有 レコードのうち、 オリジンが同一サイトとして origin と一致し、かつ パーティションが同一サイトとして partition と一致するものがあれば、真を返す。

  3. entry のオリジン群が次の条件を満たすレコードを含むかを調べる。 COS 共有 レコードのうち、 オリジンが同一サイトとして origin と一致し、かつ パーティションが同一サイトとして partition と一致するものがあれば、真を返す。

  4. 偽を返す。

注： 計上対象外となるのは、共有レコードに基づいて応答する検索のうち、 そのレコードが読み取り元自身の トップレベルサイトの下で書き込まれたものである。こうした検索は、他のサイトが保存した内容を何も開示しない。それ以外の検索はすべて 計上する。これには、検索が外れた場合、グローバルな範囲に基づいて応答した場合、および ファーストパーティのオリジン群のレコードに基づいて応答し、そのレコードが別の トップレベル サイトの下で書き込まれていた場合が含まれる。

クロスサイト検索を 計上するには、サイト partition を受け取り、次の手順で真偽値を返す。

  1. budget を partition のクロスサイト検索 予算とする。

  2. now を、ユーザーエージェントがセッションをまたいで維持する時計の現在時刻とする。

  3. budget の期間の開始時刻が null でなく、 now がその開始時刻から少なくとも 検索期間だけ 経過した時刻である場合、budget の回数を 0 に、その 期間の開始時刻を null に設定する。

  4. budget の回数がユーザーエージェントの クロスサイト検索の最大回数以上である場合、偽を返す。

  5. budget の期間の開始時刻が null である場合、それを now に設定する。

  6. budget の回数を 1 増やす。

  7. 真を返す。

いずれのホスト側の統合を介する検索も、 可用性の制御を 適用する手順に達する。これは getFileHandle() の呼び出しの 場合と同じであり、同じ条件で計上する。これらの検索はすべて同じ予算に計上する。

3.3. ファイルの作成と書き込み

FileSystemFileHandle のうち、 作成要求を完了する手順で作成したものには、 要求されたオリジン群が関連付けられる。これは、検証して保存する手順が、 可視範囲を拡大する際に、エントリーのオリジン群に反映しようとする値である。この処理は、 ハンドルを介した書き込みが成功した後に行う。

各 FileSystemFileHandle のうち、 クロスオリジンストレージファイルシステムを指すものには、 COS ハッシュも関連付けられる。これは、そのハンドルが指す COS ハッシュである。また、 ハンドルに関連付けられた COS オリジンは、そのハンドルを取得したオリジンである。さらに、 ハンドルに関連付けられた 読み取り可能という真偽値は、 getFile() が参照先エントリーのバイト列を、その特定の ハンドルを介して開示してよいかどうかを決める。この値は、読み取り要求を完了する手順で返されたハンドルでは真である。そのハンドルはすでに 可用性の制御を通過しているからである。一方、 作成要求を 完了する手順で返されたハンドルでは、検証して保存する手順がその同じハンドルについて成功するまで偽である。

注： ハンドルが指すのは COS ハッシュであり、COS エントリーではない。作成要求を完了する手順は、 対応するエントリーが COS レジストリーに存在せず、今後も作成されないかもしれないハッシュに対してもハンドルを返す。そのため、 ハンドルが参照できるエントリーは、検証して保存する手順で作成されるまで存在しない。

注： これは意図的にハンドルごとの性質としている。 作成要求は、 そのハッシュのエントリーがすでに存在するかどうかにかかわらずハンドルを返す（ 作成要求を 完了するを参照）。したがって、エントリーごとの規則にすると、どのオリジンも getFileHandle() を create: true で呼び出して、自らは一度も 書き込んでいないエントリーをただちに読み取れる。その結果、オリジン群、 PHL への収録、または GREASE 処理による条件を満たさずに内容を知ることができてしまう。この 仕様の開示制御はすべて読み取り時に適用するため、エントリー単位で制御すると、作成要求によって すべての制御を迂回できてしまう。呼び出し元に正しいバイト列を先に提供させれば、 作成要求で取得したハンドルからの読み取りに成功しても、呼び出し元がまだ持っていなかった情報は何も開示されない。

作成要求を 完了するには、プロミス result、 COS ハッシュ hash、CrossOriginStorageGetFileHandleOptions options、グローバルオブジェクト global、およびレルム realm を受け取り、次の手順を実行する。

  1. requestedOrigins を、要求された オリジン群を正規化する手順に options["origins"] を与えて実行した結果とする。

  2. requestedOrigins がリストである場合、 requestedOrigins に次の手順の結果を設定する。 COS の範囲の上限を適用する手順を実行し、引数として requestedOrigins、および COS の範囲の上限を取得する手順に global を与えて実行した結果を渡す。

  3. handle を、新しい FileSystemFileHandle を作成する手順の結果とする [FS]。その ロケーターは、hash を クロスオリジンストレージファイルシステム内で指し示す。作成先のレルムは realm とする。

  4. handle の COS ハッシュを hash に設定する。

  5. handle の COS オリジンを、global の 関連する設定群オブジェクトのオリジンに設定する。

  6. handle の要求されたオリジン群を requestedOrigins に設定する。

  7. handle の読み取り可能を偽に設定する。

    注： このアルゴリズムは COS レジストリーを参照せず、 変更することもない。どちらも行うことはできない。 結果は hash がすでに保存されているかどうかと独立していなければならず、そうでなければ作成 要求 自体が以前から存在していたことを明かしてしまうからである（§ 8.2 クロスサイトでの探索を参照）。 したがって、handle が返される条件はまったく 同じである。エントリーが存在する場合も、一度も書き込まれていない場合も、他者がまさに 書き込んでいる場合も同様であり、この呼び出し元がバイト列を提供するまでは読み取り権限を持たない。

    注： ここでは何も登録しないため、 呼び出し元がハンドルを要求した後に放棄し、 一度も createWritable() を呼び出さない場合や、得られたストリームを閉じない場合も、 レジストリーは元の状態のままである。他のオリジンは、その要求が 行われたことを観測できず、後続の読み取りを抑止する仮の状態にハッシュを固定することもできない。 § 8.3 進行中の書き込みを参照。

    注： requestedOrigins を適用するのは 検証して 保存する手順だけである。その際に リソースの可視範囲を拡大する手順を用いるのは、バイト列の 書き込みと検証が完了した後である。このため、 作成要求で可視範囲を広げるには、先にバイト列全体を提供する必要がある。 § 3.5 リソースの可視範囲の拡大を参照。

  8. グローバルタスクをキューに追加する。タスクソースにはDOM 操作タスクソースを用い、 global を与える。このタスクで 解決するプロミスは result、その値は handle とする。

要求された オリジン群を正規化するには、(DOMString or sequence<DOMString>) または undefined である origins を受け取り、"*"、リスト（要素はオリジン）、または null を次の手順で返す。

  1. origins が存在しない場合、 null を返す。

  2. origins が "*" である場合、"*" を返す。

  3. list を « » とする。

  4. 各 candidate について、origins 内を順に処理する（単一の 文字列は、リストの 唯一の要素として扱う）。

    1. candidateOrigin を、次のオリジンとする。すなわち、基本 URL パーサーを candidate に対して実行して得られた URL のオリジンである。

      注： COS 要求を 検証する手順で、各 candidate の構文解析結果が http: または https: URL であり、そのオリジンが潜在的に信頼できるオリジンであることは確認済みである。

    2. list が次のオリジンを含むかを調べ、candidateOrigin が含まれていなければ、末尾に追加する。追加する値は candidateOrigin、 追加先は list とする。

注： 後で既存のエントリーに統合する前に、 ここで重複を排除することで、オリジン群にはエントリーを 最初に作成した時点から重複がない。したがって、後で作成する各複製にも重複が生じない。

FileSystemWritableFileStream のうち、 次の呼び出しで取得したものを考える。 createWritable() を呼び出す対象は、ロケーターが クロスオリジンストレージファイルシステムを指すハンドルである。このストリームが閉じられるとき [FS]、ユーザーエージェントは、 次の 検証して保存する手順を、 そのハンドルを与えて、閉じる操作のプロミスが 履行される前に実行しなければならない。

注： これは、ストリームを閉じるきっかけに かかわらず適用される。明示的な close() 呼び出しであっても、pipeTo() 呼び出しが読み取り元の 末尾に達して、既定の動作で書き込み先も閉じた場合であっても同じである。[STREAMS] は、ストリームが閉じた状態になった 時点でこの二つを区別しない。このアルゴリズムでも区別しない。

検証して保存する 手順は、FileSystemFileHandle handle（そのストリームは 閉じられている）、書き込まれた完全なバイト列 bytes、および閉じる操作の 関連する設定群オブジェクト settings を受け取り、次のように実行する。

  1. origin を settings のオリジンとする。

  2. partition を、COS パーティションのうち settings に対応するものとする。

  3. firstParty は、settings がファーストパーティ COS コンテキストである場合は真、それ以外の場合は偽とする。

  4. hash を handle の COS ハッシュとする。

  5. computedValue を、小文字の十六進数で表した bytes のダイジェストとする。計算に 用いるのは、 hash のアルゴリズムで指定されたアルゴリズムであり、[WEBCRYPTO] に従う。

  6. computedValue が hash の値と完全には一致しない場合は、次の手順を実行する。

    1. 拒否する対象は閉じる操作のプロミスとし、その理由は "DataError" DOMException とする。

    2. これらの手順を中止する。

    注： 書き込みが失敗しても、後始末をする 必要はない。作成要求を完了する手順ではエントリーを登録していない。 したがって、検証済みのバイト列が得られなかった書き込みによって COS レジストリーが変化することはない。その後の getFileHandle() 呼び出しで同じハッシュを指定すると、 "NotFoundError" が返る点も、書き込みを試みなかった場合と同じである。いずれかのオリジンが すでに書き込んだエントリーも同様に影響を受けない。このアルゴリズムが行うのは、バイト列と共有 レコードの追加だけである。

  7. 次の手順をキューに追加する。追加先は クロスオリジンストレージキューとする。

    1. entry を、次の条件を満たす COS エントリーとする。すなわち、COS レジストリー内にあり、そのハッシュが 等しいと判定されるものである。比較対象は hash とする。そのようなエントリーがなければ null とする。

    2. COS のストレージ上限を確認する手順に entry、origin、および bytes の長さを与えて実行した結果が偽である場合、またはCOS への書き込みを計上する手順に entry、origin、partition、および bytes の 長さを与えて実行した結果が偽である場合は、次の手順を実行する。

      1. グローバルタスクをキューに追加する。タスクソースにはDOM 操作タスクソースを用い、 settings の グローバルオブジェクトを与える。このタスクで拒否する対象は、閉じる操作の プロミスとし、その理由は "QuotaExceededError" DOMException とする。

      2. これらの手順を中止する。

    3. entry が null である場合は、次の手順を実行する。

      1. entry に新しい COS エントリーを設定する。そのハッシュは hash、 バイト列は bytes、オリジン群は空のリスト、 グローバルに開示可能は 偽、保存元オリジン群は空の 集合とする。

      2. 設定する対象を COS レジストリー[hash] とし、その値を entry とする。

      注： この仕様でエントリーを追加するのは、 この手順だけである。追加先は COS レジストリーであり、この手順を実行するのは bytes を hash と照合して検証した後に限られる。二つの 書き込み元がともにハッシュの不在を確認して並行して書き込む場合、どちらもここに到達する。 このとき、 後からキューに追加された方は、先の書き込み元が作成したエントリーを見つけ、以降の手順で自分のオリジンと レコードを追加するだけである。双方のバイト列のハッシュ値は同じなので、保存は一度で足りる。

    4. 末尾に追加するのは、次の COS 共有レコードである。 そのオリジンは origin、 パーティションは partition、 ファーストパーティは firstParty とする。追加先は entry の保存元オリジン群であり、等しいレコードが すでに存在する場合は追加しない。

    5. リソースの可視範囲を拡大する手順に、 entry、handle の 要求されたオリジン群、 partition、firstParty、および settings の グローバルオブジェクトを与えて実行する。

    6. handle の読み取り可能を真に設定する。

      注： 読み取り可能になるのは、 このハンドルだけである。同じハッシュであっても、別の 作成要求で取得したハンドルは、それを介した書き込みがなければ読み取り不能のままである。

createWritable() を FileSystemFileHandle に対して呼び出す際、その参照先が クロスオリジンストレージファイルシステムである場合、生成する FileSystemWritableFileStream の内容は 初期状態で空でなければならない。これは keepExistingData の値に かかわらず、 また、参照先の COS ハッシュに対応するエントリーが COS レジストリーに存在するかどうかにもかかわらない。

注： [FS] では通常、keepExistingData を指定すると、 ストリームを既存ファイルの内容で初期化すると定めている。ここでもこの指定に従うと、呼び出し元は、 一度も保持していないバイト列の保存元オリジンになり得る。作成要求は、エントリーが すでに存在するかどうかにかかわらずハンドルを返すため、別のオリジンが保存したハッシュに対する書き込み可能なストリームを開き、 何も書き込まずに閉じても、引き継いだバイト列のハッシュが要求した値と一致してしまう。その結果、読み取りが可能になる一方、 開示条件であるオリジン群、 公開ハッシュ リスト、および GREASE 処理は一度も参照されない。こうして、可用性の 制御の迂回が、 個別には許可されている二つの操作の組み合わせによって可能になる。 検証して保存する手順で、 作成要求のたびに完全な内容を要求するのも同じ理由からである。

注： したがって、何も書き込まずに閉じた書き込み可能なストリームが 保持するのは空のバイト列である。そのハッシュは、 呼び出し元が取得したいエントリーの要求値とは一致しないため、検証して保存する手順は、 "DataError" DOMException で拒否する。他の不一致の場合と同じである。この場合に ストレージ障害や I/O 障害を報告する実装では、検証結果が 無関係なエラーに隠されてしまう。

ファイルシステム標準 [FS] は、まだ 拡張点を定義していない。ここで必要なのは、この標準に依存する 仕様が、書き込みごとの追加検証を FileSystemWritableFileStream の 閉じる手順に組み込むための拡張点である。そのような拡張点が設けられるまでは、この節で必要な動作を直接記述する。 将来の改訂では [FS] と正式に統合することを見込んでいる。

3.4. 取得したリソースの保存

§ 9 他の仕様との 統合に挙げたホスト側の統合では、取得したリソースを保存する際に FileSystemFileHandle を介さない。 それぞれのホスト仕様では、 取得したバイト列が、その統合で必要とされる完全性検査に合格した後で、 次のアルゴリズムを実行することが期待される。

取得したリソースをクロスオリジン ストレージに保存するには、応答 response、バイト列 bytes、COS ハッシュ hash、"*"、リスト（要素は文字列）、 または null である origins、および環境設定群オブジェクト settings を受け取り、次の手順を実行する。

  1. クロスオリジンストレージの許可を 確認する手順に settings の グローバルオブジェクトを与えて実行した結果が偽である場合、リターンする。

  2. options の値は «[ "origins" → origins ]» とする。ただし、これは origins が null でない場合であり、それ以外の場合は «[ ]» とする。

  3. COS 要求を検証する手順に hash および options を与えて実行した結果が null でない場合、 リターンする。

  4. computedValue を、小文字の十六進数で表した bytes のダイジェストとする。計算に 用いるのは、 hash のアルゴリズムで指定されたアルゴリズムであり、[WEBCRYPTO] に従う。

  5. computedValue が hash の値と完全には一致しない場合、リターンする。

    注： ホスト側の統合が用いる完全性 メタデータには複数のダイジェストを列挙でき、 そのいずれか一つに一致すれば検査に合格する。この手順により、エントリーのキーとなるハッシュが、 実際にそのバイト列から得られるものであることを保証する。

  6. requestedOrigins を、要求された オリジン群を正規化する手順に options["origins"] を与えて実行した結果とする。

  7. requestedOrigins がリストである場合は、次の手順を実行する。

    1. internalResponse を response の内部応答とするのは、 response がフィルター済み応答である場合である。response 自体を用いるのは、 それ以外の場合である。

    2. requestedOrigins に、COS の 範囲の上限を適用する手順の結果を設定する。引数は requestedOrigins、およびCOS の 範囲の上限を構文解析する手順に internalResponse のヘッダーリストを与えて実行した結果とする。

    注： 上限は、取得した リソース自身の応答から得る。したがって、 バイト列をどのオリジンに開示できるかを決めるのは、そのバイト列を提供するサーバーである。読み込み元の Document の COS の範囲の上限は関与しない。文書の運営者は リソースを管理しておらず、 開示先を許可する権限を与えると、どのサイトでも、別のサイトのリソースを自分の選んだ オリジンと共有できると宣言できてしまう。ユーザーエージェントは内部の 応答からヘッダーを読み取るため、不透明なフィルター済み応答でもこの手順は機能し、ヘッダーが ページに公開されることはない。

  8. origin を settings のオリジンとする。

  9. partition を、COS パーティションのうち settings に対応するものとする。

  10. firstParty は、settings がファーストパーティ COS コンテキストである場合は真、それ以外の場合は偽とする。

  11. 次の手順をキューに追加する。追加先は クロスオリジンストレージキューとする。

    1. entry を、次の条件を満たす COS エントリーとする。すなわち、COS レジストリー内にあり、そのハッシュが 等しいと判定されるものである。比較対象は hash とする。そのようなエントリーがなければ null とする。

    2. COS のストレージ上限を確認する手順に entry、origin、および bytes の長さを与えて実行した結果が偽である場合、またはCOS への書き込みを計上する手順に entry、origin、partition、および bytes の 長さを与えて実行した結果が偽である場合、 これらの手順を中止する。

    3. entry が null である場合は、次の手順を実行する。

      1. entry に新しい COS エントリーを設定する。そのハッシュは hash、 バイト列は bytes、オリジン群は空のリスト、 グローバルに開示可能は 偽、保存元オリジン群は空の 集合とする。

      2. 設定する対象を COS レジストリー[hash] とし、その値を entry とする。

      注： 検証して保存する手順と同様に、 エントリーを作成するのは bytes を hash と照合して検証した後に限られる。この検証は、ホスト側の統合の integrity 検査ですでに行われている。 getFileHandle() を用いる書き込み元が同じハッシュについてまだ書き込みを 行っていても、影響は受けない。その書き込み元はレジストリーに状態を保持しておらず、自身の検証して保存する手順も 正常に 完了する。このエントリーを見つけ、自身のオリジンと共有レコードを追加するからである。

    4. 末尾に追加するのは、次の COS 共有レコードである。 そのオリジンは origin、 パーティションは partition、 ファーストパーティは firstParty とする。追加先は entry の保存元オリジン群であり、等しいレコードが すでに存在する場合は追加しない。

    5. リソースの可視範囲を拡大する手順に entry、requestedOrigins、partition、 firstParty、および settings のグローバルオブジェクトを与えて実行する。

注： 検証して保存する手順と同様に、保存には常に 完全なバイト列が必要である。そのハッシュの エントリーがすでに存在する場合も同じなので、以前から存在していたかどうかは何も明らかにならない。ホスト側の統合が ネットワークから取得する前に行う検索は読み取りであり、可用性の制御と、 § 8.2 クロスサイトでの探索に示す探索に関する考慮事項が適用される。

3.5. リソースの可視範囲の拡大

COS エントリーの可視範囲は 拡大できるが、縮小することはできない。

リソースの 可視範囲を拡大するには、COS エントリー entry、"*"、リスト（要素は オリジン）、または null である requestedOrigins、サイト partition、真偽値 firstParty、 および グローバルオブジェクト global を受け取り、次の手順を実行する。

  1. requestedOrigins が null である場合、リターンする。

    注： origins を省略すると、 同一サイトからのみ 利用可能にすることを要求する。すべてのエントリーはすでにこの範囲で利用できる（COS の開示を 判定するを参照）。したがって、 追加するものはない。

  2. requestedOrigins が "*" である場合は、次の手順を実行する。

    1. entry のハッシュが PHL に載っているという条件を満たさない場合、ユーザーエージェントには 次の内容を コンソールに警告として記録するか、開発者ツールで問題として報告することが期待される。エントリーを 読み取れるのは、同一サイトのオリジンと、エントリーのオリジン群のリストに載っているオリジンだけである。

      注： 書き込み自体は成功するため、 メッセージがなければ、開発者には グローバルな範囲が有効にならなかったことを知る手段がない。§ 8.5 開発者向けの 指針を参照。

    2. entry のグローバルに開示可能が真である場合、 リターンする。

    3. global が COS ユーザー活性化を持つ場合、 entry の グローバルに開示可能を真に設定する。

    4. それ以外の場合、末尾に追加する値を entry、追加先を partition のグローバル開示待ちのエントリー群とする。

    5. リターンする。

    注： この処理はグローバルな範囲を追加するだけで、 entry のオリジン群は変更しない。エントリーが すでに明示的なオリジン群のリストを持っていた場合、そのリストは保持される。そのため、各 オリジンが そのリストに基づいて持つ PHL に依存しないアクセス権は、エントリーが グローバルに開示可能になった後も保持される。これが、 二つの範囲を別々に 保存する主な理由である。グローバルに開示可能を参照。

  3. 各 candidateOrigin について、 requestedOrigins 内を順に処理する。

    1. record を、次の COS 共有レコードとする。そのオリジンは candidateOrigin、 パーティションは partition、 ファーストパーティは firstParty とする。

    2. entry のオリジン群が次のレコードを含む場合、すなわち record と等しいレコードがある場合は、 次の反復に進む。

    3. entry のオリジン群のサイズが ユーザーエージェントの オリジンリストの最大長と等しい場合、 反復を終了する。

      注： 残りの candidateOrigin の値は、この拡大処理ではエラーを返さずに除外する。 書き込み自体はすでに成功しているためである。ユーザーエージェントには、エントリーのオリジンリストが上限に達したことを コンソールに警告として記録することが期待される。

    4. 末尾に追加する値を record、追加先を entry のオリジン群とする。

注： 可視範囲を拡大する際に行うのは、オリジン群に追加すること、またはグローバルに開示可能を 真に設定することだけである。書き込み元がリストを指定すれば、エントリーがすでに グローバルに開示可能であっても、そうでない場合と同じように 可視範囲を拡大できる。二つの範囲は 独立しているため、新しくリストに加えたオリジンには PHL に依存しないアクセス権が与えられ、その間も グローバルな範囲は有効なままである。

注： 元の保存者とは別のサイトも含め、どの サイトでも、エントリーの オリジン群を拡大できる。ただし、 提供するバイト列から計算したハッシュが、エントリーのハッシュと一致することが条件となる。これは意図した動作である。 あるハッシュに対応する正しいバイト列をすでに持つサイトは、その仕組み上、そのハッシュが何を指すかについて、 元の保存者と同じだけの根拠を持つからである。

3.5.1. ユーザー活性化ゲート

COS ユーザー 活性化ゲートは、利用者が 書き込み時のサイトのページを操作するまで、その書き込みのグローバルな範囲を保留する。書き込み元のページは、 自身の保存元オリジン群のレコードに基づいてエントリーをただちに読み取れる。同一サイトのオリジン、および 明示的な オリジン群のリストに載っているオリジンも、 書き込み元がそのリストを Cross-Origin-Storage-Allow-Origin ヘッダーで許可しているため、同様に ただちに読み取れる。

各サイトは、グローバル開示待ちのエントリー群を持つ。これは集合であり、要素は COS エントリー、初期状態では 空である。

ユーザーエージェントは、 活性化 通知を Window window に対して実行するたびに [HTML]、 次の手順をキューに追加する必要がある。追加先はクロスオリジンストレージ キューとする。

  1. partition を、COS パーティションのうち window の関連する設定群オブジェクトに対応するものとする。

  2. 各 entry について、partition のグローバル開示待ちの エントリー群内を順に処理し、entry の グローバルに開示可能を真に設定する。

  3. 空にする対象を、partition のグローバル開示待ちのエントリー群とする。

注： 別のサイトが開いたポップアップ内のページで、そのポップアップが 数秒で閉じられるものや、連鎖的に再読み込みされる ページは、ユーザー活性化を受けない。そのため、そこから書き込んだファイルは他のサイトからは見えない。これらの 書き込みがグローバルに開示可能になるのは、利用者がそのサイトのページを実際に操作したときであり、それは 同じ訪問中でも後の訪問時でもよい。追い出されたエントリーは、すべての グローバル開示待ちの エントリー群の集合からも取り除かれる。

グローバルオブジェクト global が COS ユーザー活性化を持つのは、 global が Window オブジェクトであり、 持続的な活性化を持つ場合、または global が DedicatedWorkerGlobalScope オブジェクトであり、その 所有者のいずれかの関連するグローバルオブジェクトが COS ユーザー活性化を持つ場合である。

注： 専用ワーカーは、それを所有するページのために動作するので、 それらのページの活性化を引き継ぐ。これは、 クロスオリジンストレージの許可を確認する手順でページのポリシーを引き継ぐのと同じである。共有 ワーカーの所有者は入れ 替わるため、共有ワーカーによるグローバルな範囲への書き込みは、同じトップレベル サイトのページで次に活性化が起きるまで待機する。

3.5.2. 元の保存者によるアクセス

オリジンが正常に完了した書き込みの対象である COS エントリーについて、そのオリジン（ すなわち、レコードのオリジンであって、そのレコードがエントリーの保存元オリジン群に含まれているもの）は、 その後いつでも、 エントリーのハンドルを getFileHandle() を介して 書き込み時と 同じトップレベルサイトの下で取得できる。これは、エントリーのオリジン群の値にも、 そのハッシュが PHL に載っているかどうかにも依存しない。これは Cache API のモデルと同じである。このモデルでは、 オリジンは自ら保存したものに常にアクセスでき、ストレージの分割に際して Cache API もトップレベルサイトをキーとする点まで共通している。他のトップレベルサイトの下では、そのオリジンも、他の オリジンと同じ条件でエントリーを読み取る。

4. クロスオリジンストレージファイルシステム

クロスオリジンストレージファイルシステムは、ファイルシステムのルートである。これは、どの オリジンのバケットファイルシステムとも、ローカルファイルシステムへのアクセスに用いるルートとも異なり、その エントリーは、COS レジストリーの各COS エントリーと一対一に対応する。

クロスオリジンストレージファイルシステムでは、[FS] の通常の呼び出しごとの 許可確認 モデルは使用しない。このファイルシステムから得られるすべての FileSystemFileHandle は、スクリプトに返される前に、 § 3.2 ファイルの読み取りまたは§ 3.3 ファイルの作成と 書き込みによってすでに必要な認可をすべて受けている。したがって、 getFile() または createWritable() をこのようなハンドルに対して呼び出しても、 追加の許可プロンプトが表示されることはない。

このため、このようなハンドルの queryPermission() と requestPermission() は、決して 次の値を報告してはならない。 "prompt"。プロンプトが表示されることはないためである。書き込みモードについては、"denied" を報告しなければならないのは、 対象のハンドルが 作成要求で取得されたものでない場合であり、 "granted" を報告しなければならないのは それ以外の場合である。

createWritable() を、次の条件を満たす FileSystemFileHandle に対して呼び出す場合、すなわち、その参照先が クロスオリジンストレージファイルシステムであり、かつ、その 取得元が 作成要求でない場合、"NotAllowedError" DOMException で拒否しなければならず、 FileSystemWritableFileStream を作成してはならない。

注： 書き込みは、ハンドルに実際に備わっていないことがある唯一の 機能である。書き込みに使えるハンドルが得られるのは 作成要求だけなので、それ以外のハンドルの書き込みモードについて "granted" を報告すると、 createWritable() が 拒否する機能を利用可能と示すことになる。読み取りは "granted" のままである。読み取り可能なハンドルを持つ呼び出し元は、そのハンドルを通じて読み取れるためである。許可を要求しても 結果は変わらない。 どちらについても、表示するプロンプトも、許可を記録できる状態もないためである。

getFile() を、次の条件を満たす FileSystemFileHandle に対して呼び出す場合、すなわち、その参照先が クロスオリジンストレージファイルシステムであり、その読み取り可能が false の場合は、拒否しなければならない。 このとき使用するのは "NotAllowedError" DOMException である。 これには、異なる二つの場合がある。

  • 作成要求で取得したハンドルで、これを通じた書き込みが まだ 行われておらず、参照先のハッシュに対応するエントリーが COS レジストリーにない場合。返せる検証済みのバイト列は 存在せず、呼び出し元が自身の未完了の書き込みを、あたかもファイルの 実際の内容であるかのように観測できてはならない。

  • ある別のオリジンがすでに書き込んだハッシュについて、作成要求で取得したハンドルの場合。 検証済みの バイト列は存在するが、この呼び出し元がそれを提供したわけではなく、 可用性の制御も通過していない。したがって、エントリーについて何も知り得てはならず、 そのエントリーが 存在するかどうかさえ知り得てはならない。

注： どちらの場合も拒否の結果は同じであるため、 何も開示しない。このことから、 "NotAllowedError" は、読み取り経路では意図的に避けているものの、ここでは安全である。このハンドルは 呼び出し元が自ら作成要求で取得したものであり、ハンドルを他の オリジンで逆直列化することはできない（§ 4.1 ハンドルの転送を参照）。したがって、応答が オリジン境界を越えることはなく、 レジストリーの内容によって変化することもない。対照的に、§ 8.3 進行中の書き込みでは、 読み取り経路で区別できるエラーを返したなら、その情報は境界を越えることになる。

ハンドルの読み取り可能が true になると、getFile() をそのハンドルに対して呼び出した結果は File となり、 その内容は参照先エントリーのバイト列である。これは、 [FS] がすでに定義している挙動とまったく同じであり、 その定義は、ファイル エントリーの バイナリーデータがそのバイト列である場合に適用される。

FileSystemFileHandle の 参照先がクロスオリジンストレージファイルシステムである場合、その ファイルシステムロケーターのパスはリストであり、その要素は 一つの 文字列、すなわち、そのハンドルの COS ハッシュの値である。また、このロケーターの ルート は、クロスオリジンストレージファイルシステムである。

注： [FS] は、name を、ハンドルのロケーターが持つ パスの最後の構成要素と定義している。したがって、これにより name も決まる。 その値は ハッシュである。エントリーは固有の名前を持たず、ハッシュがその唯一の識別子であるため、 それを返すことで、空文字列なら失われる情報を伝えられる。

エントリーには名前も親ディレクトリーもないため、[FS] が定める構造に関する操作の大半には、 操作対象がない。同一性は例外であり、コンテンツによってアドレス指定されるエントリーが 常に答えられる問いである。COS レジストリーが保持できる COS エントリーは、一つの COS ハッシュにつき最大一つなので、二つの ハンドルが同じエントリーを参照するのは、それらのハッシュが等しい場合に限られる。

isSameEntry() を、ある FileSystemFileHandle に対して呼び出す際に、その参照先が クロスオリジンストレージファイルシステムであり、引数も 同じファイルシステムを参照し、かつ両方を取得したのが 同じオリジンである場合、二つのハンドルの COS ハッシュが等しいなら true を、それ以外なら false を返さなければならない。

注： この比較を拒否すると、ユーザーエージェントが すでに持っている情報を捨てることになる。

isSameEntry() を、ある FileSystemFileHandle に対して呼び出す際に、その参照先が クロスオリジンストレージファイルシステムであり、引数が 呼び出し元のオリジンが取得したものでないか、または その引数の参照するファイルシステムがクロスオリジンストレージファイルシステム以外である場合は、次の例外で拒否しなければならない。 "NotAllowedError" DOMException。 別のファイルシステムを参照するハンドル、たとえば getDirectory() が返すハンドルについては、[FS] が定める挙動が維持される。これは、引数として FileSystemFileHandle を渡し、その参照先がクロスオリジンストレージファイルシステムである場合にも当てはまる。

注： この場合に false を返すと、 二つのハンドルが異なるエントリーを参照すると断定することになる。 これは、呼び出し元のオリジンに調べる権限がないハンドルについての断定である。拒否によって伝わるのは、 比較を行えなかったということだけである。

move() または remove() を、 FileSystemFileHandle に対して呼び出し、その参照先がクロスオリジンストレージファイルシステムである場合、次の例外で拒否しなければならない。 "NotAllowedError" DOMException。 また、参照先のいずれのエントリーも変更してはならない。

注： エントリーは、その保存元 オリジン群に属するすべてのオリジンに共有されるため、 削除要求に応じると、他のサイトが依存するデータを一つのサイトが破壊できてしまう。削除を担うのは 追い出しと、利用者自身が操作するストレージ管理機能である。名前の変更や親の変更には対象が ない。エントリーの名前はその COS ハッシュであり、親ディレクトリーもないためである。

注： 執筆時点では、どちらのメソッドも [FS] にもファイルシステム アクセス API にも定義されていない （WICG/file-system-access#214）。 そのため、エラー名は removeEntry() に従う。 これは [FS] がエントリーの削除について実際に 定義している操作であり、読み書きアクセスが付与されていない場合は、アクセス結果のエラー名で 拒否する。ここでの正確な挙動は拒否である。これらの操作には意味があるものの、 許可されないためである。

createSyncAccessHandle() について、ここで規則を追加する必要はない。その手順は、次の例外で拒否する。 "InvalidStateError" DOMException。 対象となるのは、ハンドルがバケットファイルシステムに属さないすべての場合であり、 クロスオリジンストレージファイルシステムは、ファイルシステムのルートとしてどのオリジンのものとも異なる。 したがって、[FS] によってすでに 拒否することもエラー名も決まっている。

注： この仕様が独自に挙動を決めるとしても、 望ましい結果は同じである。 FileSystemSyncAccessHandle は、書き込み可能なファイル記述子を呼び出し元に渡す。すると、呼び出し元は エントリーのバイト列を、 対応する COS ハッシュに結び付けて 保存したまま変更できてしまう。 しかも、エントリーを開示できる他のすべてのオリジンが、それと同じバイト列を読み取る。

4.1. ハンドルの転送

FileSystemFileHandle は直列化可能なオブジェクトである [FS]。したがって、 COS エントリーを参照するハンドルは、別の環境設定群オブジェクトに渡せる。たとえば、 postMessage(message, options) を使用できる。 これは、このようなハンドルを取得するための、 getFileHandle() に次ぐ二つ目の方法であり、 この方法にも以下の制約が適用される。

直列化手順は、対象の FileSystemFileHandle の参照先が クロスオリジンストレージファイルシステムであり、引数として value と serialized が与えられたとき、追加で次を実行する。

  1. serialized.[[COSHash]] を value の COS ハッシュに設定する。

  2. serialized.[[COSOrigin]] を value の COS オリジンに設定する。

  3. serialized.[[COSMayRead]] を value の読み取り可能に設定する。

逆直列化手順は、serialized、 value、realm が与えられたとき、追加で次を実行する。

  1. serialized.[[COSOrigin]] が次に示すオリジンと同一オリジンでない場合、すなわち realm の 環境設定群オブジェクトのオリジンと同一オリジンでない場合、 "DataCloneError" DOMException を投げる。

  2. value の COS ハッシュを serialized.[[COSHash]] に設定する。

  3. value の COS オリジンを serialized.[[COSOrigin]] に設定する。

  4. value の読み取り可能を serialized.[[COSMayRead]] に設定する。

注： 同一 オリジンの確認がなければ、転送によって、この仕様のすべての開示制御が 一度に無効になってしまう。読み取り可能が true であるハンドルは、 すでに 可用性の制御を適用する手順を、そのハンドルを要求した オリジンについて通過している。これを別の オリジンに送ると、そのオリジンについてオリジン群、 PHL への掲載、GREASE 処理のいずれも評価せずにエントリーのバイト列を渡すことになる。この規則は、 ファイルシステム標準がすでに定めているハンドルの扱いと一致する。そこでも同様に、 同一オリジンの受信側だけがハンドルを利用できる。

注： 読み取り可能はハンドルとともに 転送される。このため、作成要求で取得し、まだ書き込みに使っていないハンドルは、 転送後も読み取り不能のままであり、 読み取り要求で取得したハンドルは、制御を再適用せずに引き続き読み取れる。受信時に再適用すると、 呼び出し元は同じハンドルを転送することで、可用性を繰り返し 探れるようになってしまう。

注： 元のハンドルを通じて書き込む前に複製したハンドルは、 読み取り不能のままである。その保有者は、 getFileHandle() を、 create を指定せずに呼び出すことで、読み取り可能なハンドルを 元の保存者によるアクセスを通じて取得できる。

5. ストレージ管理

5.1. ストレージの上限

ユーザーエージェントは、一つのオリジンが COS レジストリーに成功した書き込みを通じて提供できる合計バイト数に上限を設けなければならない。 これにより、一つのオリジンが、 他のオリジンのエントリーを追い出そうとしてキャッシュを埋め尽くすことを防ぐ。具体的な上限は 実装定義である。

COS のストレージ 上限を確認するには、COS エントリーまたは null である entry、オリジン origin、非負の整数 length を受け取り、次のように真偽値を返す。

  1. entry が null でなく、その保存元オリジン群が含む COS 共有 レコードの中に、そのオリジンが origin であるものがあれば、true を返す。

    注： エントリーはコンテンツアドレス指定方式であるため、 このオリジンがすでに保存したバイト列をもう一度書き込んでも、 保持する量は増えない。

  2. held を、以下に該当するバイト列の長さの合計とする。対象となるのは、バイト列を保持する各 COS エントリーのうち、COS レジストリーにあり、その 保存元オリジン群が含む COS 共有 レコードの中に、そのオリジンが origin であるものがあるエントリーである。

  3. held と length の和が origin のストレージ上限を超える場合は、 コンソールに警告を記録し、 false を返す。

  4. true を返す。

ストレージの上限が制限するのは、一つのオリジンがある時点で保持する量である。したがって、多くのオリジンを持ち込むページには、 その数だけ上限がある。このため、ユーザーエージェントは、COS 書き込み上限も各 サイトについて保持し、そのサイトをCOS パーティションとして行った書き込みを、実行したオリジンや フレームにかかわらず数えなければならない。この上限には、実装定義の最大書き込み回数と最大 バイト数が あり、いずれも実装定義の時間枠ごとに適用される。また、永続化とリセットには、 次と同じ条件が 適用される。すなわち、クロスサイト検索予算の条件である。

COS への書き込みを 計上するには、COS エントリーまたは null である entry、オリジン origin、 サイト partition、非負の整数 length を受け取り、次のように 真偽値を返す。

  1. entry が null でなく、その保存元オリジン群が含む COS 共有 レコードの中に、そのオリジンが origin であり、かつ、その パーティションが partition であるものがあれば、 true を返す。

    注： このオリジンがこのトップレベルサイトの下ですでに 保存したバイト列を書き込んでも、保持する量は増えない。したがって、 オリジンごとのストレージ上限と同じく、これは計上されない。適用の有無はこの オリジン自身が過去に行った書き込みだけで決まり、他のオリジンの保存内容を何も開示しない。

  2. 書き込みがもう 1 回増えるか、バイト数が length 増えると、partition の COS 書き込み 上限を 現在の時間枠で超える場合は、コンソールに警告を記録し、false を返す。

  3. 書き込み 1 回と length バイトを、partition の COS 書き込み 上限に対して計上する。

  4. true を返す。

注： 書き込みはバイト列の検証が済んだ時点で計上する。そのコストは、別の オリジンが、または別のトップレベルサイトの下で同じ オリジンが、そのハッシュをすでに保存しているかどうかによって変わらない。このため、上限からは 他のサイトの保存内容は何も分からない。二つの許容量は利用形態に応じて異なる働きをする。サイトが 一つの 大きな AI モデルを保存する場合、バイト数を消費するが、回数はほとんど消費しない。一方、トラッカーが多数の小さな マーカーファイルに識別子を符号化しようとすると、回数をたちまち使い切る。

ユーザーエージェントは、実装定義のオリジンリストの最大長も持つ。これは、 一つのリストに含められるオリジンの数を制限する正の整数である。対象はオリジン群のリストに 含まれるオリジンである。この上限は、リストが初めて指定されたとき（COS 要求を検証するを参照）と、 後から既存のエントリーにリストをマージするとき（ リソースの可視範囲を拡大するを参照）の両方で適用される。そのため、単一の呼び出しでも、 長期にわたる多数の呼び出しの累積でも、エントリーのオリジン群が際限なく 増えることはない。これはメモリー使用量を制限するとともに、オリジンのリストが、 明示的に宣言することなく "*" の代わりに使用されることも防ぐ。§ 8.2 クロスサイトでの探索を参照。

上限を超えた場合の扱いは、この二つの箇所で異なる。二つの呼び出しが行われるのは、 一つの操作の中でも大きく異なる時点だからである。

  • COS 要求を検証する手順では、上限の確認は、どの ファイルについても取得、ハッシュの計算、または 書き込みを行う前に実施する。上限を超えた呼び出し元には、ただちに "TypeError" が返り、それ以外は何も起こらない。 これは、他の不正な origins 値と同じ扱いである。

  • リソースの可視範囲を拡大する手順で上限に達するのは、 別々の独立した書き込み呼び出しで要求された オリジンが累積した場合に限られる。それらの要求は、互いに無関係なオリジンから 長期間にわたって行われた可能性もある。上限を確認するのは、今回の呼び出しのバイト列について、ハッシュを計算し、 検証を終え、永続的に保存した後である。この段階で書き込みを拒否すると、成功し、 すでに検証を終えた、非常に大きいかもしれない書き込みを、無関係な記録管理上の上限のために捨てることになる。しかも、 単一の呼び出し元の誤りに帰することさえできない。そのため、書き込み自体は 成功させ、容量を超えたオリジンだけをオリジン群から除外し、 コンソールに警告を記録する。これは、 許容範囲を狭める要求の既存の扱いと同じである。すなわち、オリジンの要求を 完全には満たせない場合、その範囲を暗黙に制限し、その要求を伴う書き込みは引き続き 成功する。この仕様の他の箇所にある§ 8.4 可用性の制御と同様に、 要求した オリジンが 実際に追加されたかどうかを、呼び出し元が後から確実に確認する方法はない。その後の getFileHandle() の呼び出しは、その オリジンとして行っても、オリジンが追加されていてなお失敗し得る（たとえば、エントリーが 追い出された場合や、読み取り側のサイトがクロスサイト検索予算を使い切った場合）。したがって、その結果を、 追加の有無を裏付けるものと解釈してはならない。

5.2. 追い出し

この節は参考情報である。

ストレージ容量が逼迫した場合、ユーザーエージェントはエントリーを COS レジストリーから追い出してもよい。 たとえば、それぞれのエントリーに最後にアクセスした保存元オリジン群を横断して、 最も長く使われていないものから追い出す方針を採用できる。ユーザーエージェントには、利用者が 保存されているファイルと、各ファイルにアクセスしたオリジンを確認し、手動で エントリーを削除するか、クロスオリジンストレージのデータをすべて消去できる設定 UI を提供することが期待される。

利用者があるオリジンのサイトデータを消去したとき、ユーザーエージェントは、その オリジンが当該オリジンであるすべての共有レコードを、すべての保存元オリジン群の集合から取り除くべきである。 取り除いた後、ある COS エントリーの 保存元 オリジン群が空なら、ユーザーエージェントは、そのエントリーを削除の候補にしてもよい。

5.3. 派生成果物

ユーザーエージェントは、派生成果物を保持してもよい。これは、 バイト列を一つ以上の COS エントリーから取得して計算し、再利用のために保持するデータである。 例として、コンパイル済みの WebAssembly モジュール、GPU パイプライン、コンパイル済みの機械学習グラフがある。派生成果物は、 次の項目を持つ。

派生元

空でないリスト。各要素は、COS ハッシュ値であり、計算に使ったバイト列を持つエントリーを表す。

ページが選択した入力

結果に影響し、スクリプトが自由に設定できる他のすべての入力。たとえば、コンパイル オプション、それ自体は派生元でないコードやグラフ構造、定数、演算子のオプションがある。 これは空でもよい。

生成元

集合であり、その要素はサイトである。 これらは、COS パーティションとして、 ユーザーエージェントがその下で成果物を計算したものである。

ユーザーエージェントは、派生成果物のキーを、その派生元、 ページが選択した入力、および実装定義のユーザーエージェントと デバイスの特性から導出する。ユーザーエージェントは、スクリプトがキーを選択したり読み取ったりできるようにしてはならず、 派生 成果物の内容をスクリプトに公開してもならない。

派生成果物は、 そのキーのみに依存しなければならない。成果物の計算のきっかけとなったコンテンツを 実行した結果から得たデータを含んではならない。

注： そうでなければ、頻繁に実行されるコードを最適化するコンパイラーが、 生成元のページでどの関数が 実行されたかを記録することになり、再利用によってその実行プロファイルが別のサイトに開示されてしまう。

ユーザーエージェントは、派生成果物を、その生成元以外の COS パーティションで再利用してはならない場合がある。すなわち、その 生成元の外で再利用してはならないのは、あるサイトのコンテンツがキーを 介さずに成果物に影響を及ぼし得る場合である。

注： あるサイトのコンテンツを実行するプロセスでコンパイルしたコードは、その プロセスが侵害されると、当該コンテンツによって改変され得る。それを別のトップレベルサイトの下で再利用すると、 一つのサイトが別のサイトのプロセスでコードを実行できてしまう。

ユーザーエージェントは、派生成果物について、その 派生元のいずれかを COS レジストリーから取り除くとき、その成果物も取り除かなければならない。 利用者がサイトのデータを消去したとき、ユーザー エージェントは、そのサイトをすべての生成元の集合から取り除くべきであり、その結果、成果物の 生成元が空になった場合は、その成果物を削除してもよい。

派生成果物を再利用できるか判定するには、次の引数を受け取る。派生成果物 artifact、サイト partition、およびリスト obtained である。リストの要素は COS ハッシュ値であり、対応するバイト列は、要求元の コンテキストが COS レジストリーから読み取って提供したものである。次のように真偽値を返す。

  1. artifact の生成元が含む サイトの中に、 同一サイトの関係にあるものが partition について存在すれば、true を返す。

    注： これは、ユーザーエージェントがすでに行っている サイトごとのキャッシュである。

  2. obtained が次に示すすべての項目を含むのでなければ、 すなわち、各項目を artifact の 派生元のすべてについて含んでいなければ、false を返す。

    注： 読み取り時には、すでに可用性の制御を適用する手順を経ており、その際に クロスサイト検索予算に計上される。他の 供給元のバイト列を認めると、ページは、いずれの確認も経ずに、 計算にかかった時間からエントリーが存在するかどうかを知ることができてしまう。

  3. artifact のページが選択した入力が空である場合、true を返す。

  4. クロスサイト検索を計上する手順を partition を与えて実行した結果が true なら、 true を返す。

  5. false を返す。

派生成果物を再利用できるか判定する手順が false を返した場合、 ユーザーエージェントは、成果物が存在しなかったかのように 新たに計算し、その後、要求元の COS パーティションを、その成果物の 生成元に追加しなければならない。これにより、 再利用の拒否をキャッシュミスと区別できなくなる。§ 8.7 派生成果物の タイミングを参照。

どの入力が派生元で、どの入力をページが選択したものとするかは、ホスト仕様が定義する。

  • WebAssembly：WebAssembly.compileStreaming() または WebAssembly.instantiateStreaming() を使用して、File をクロスオリジンストレージから読み取ってコンパイルしたモジュールでは、その エントリーが派生元である。既定値以外のコンパイルオプションは、ページが選択した入力である。

  • WebGPU：シェーダーコードのうち、COS エントリーから読み取ったものは派生元である。その他のシェーダーコード、 パイプラインで上書き可能な定数、およびパイプラインレイアウトは、ページが選択した入力である。 gpuweb/gpuweb#11110 を参照。

  • WebNN：定数のうち、COS エントリーから読み取ったものは派生元である。グラフ構造、演算子の オプション、その他の定数は、ページが選択した入力である。 webmachinelearning/webnn#971 を参照。

WebGPU と WebNN には、入力が COS のどこに由来するかをコンパイラーに伝えるホスト統合が必要である。

5.4. 手動で追加されたエントリー

この節は参考情報である。

前述の設定 UI は、利用者がすでにディスク上に持っているファイルを、直接 クロスオリジンストレージに追加できるようにしてもよい（たとえば、どのウェブサイトとも無関係にダウンロードした AI モデル）。 このとき、スクリプトが次のメソッドを呼び出す必要はまったくない。getFileHandle()。 このようなエントリーには、 書き込みの主体となる要求元のオリジンが存在しない。ここから、命令型 API だけでは答えの出ない二つの問いが生じる。

  • 誰が元の保存者に当たるのか。すなわち、 § 3.5.2 元の保存者によるアクセスが適用されるのは誰か。該当者はいない。エントリーの保存元オリジン群は、初めは空である。 したがって、どのオリジンも、 通常の可用性の制御とオリジン群の確認を免れない。これらは どの要求元オリジンにも適用されるものである。これは正しい結果である。どのオリジンも 実際にはバイト列を書き込んでいないためである。

  • このようなエントリーは、通常の書き込みで origins を省略した場合と同様に、同一サイトに限るべきか。答えは否である。「同一サイト」は 要求元オリジンを基準として初めて意味を持つが、手動での追加には要求元オリジンがないため、「同一サイト」が 指すサイトも存在しない。ユーザーエージェントには、このようなエントリーをグローバルに 開示可能とし、 明示的なオリジン群のリストを空のままにすることが期待される。ファイルを手動で あらかじめ配置することが 目的を果たす（利用者がまだ訪問していないサイトでも、ディスク上にあるファイルを再利用できるようにする）のは、 他のオリジンが実際にそのファイルを見つけられる場合に限られるからである。ユーザーエージェントの設定 UI は、 さらに、利用者がより狭い範囲を選べるようにしてもよい。

この方法で追加された後は、他の点で、そのエントリーを ウェブサイトが getFileHandle() を介して書き込んだものと区別することはできない。 同じ 可用性の制御と可視範囲の 拡大の規則が、同じ共有レコードを持つ他のエントリーとまったく同じように適用される。 これには、PHL に載っているかどうかの確認も含まれる。 この確認は、エントリーが最終的に グローバルに開示可能になれば常に行われる。それが手動追加の既定値である。

5.5. 来歴メタデータ

この節は参考情報である。

COS エントリーは、意図的に、 そのバイト列の由来をいっさい記録しない。同一性は、 ハッシュだけで決まる。同じバイト列は、 いくつのオリジンが保存し、いくつの URL から 取得したかにかかわらず、同じエントリーである（§ 2.2 COS エントリーを参照）。URL は一つの 書き込み元が行った フェッチの特性であるため、複数のオリジンが書き込んだエントリーに対して、 恣意性なく一つを選ぶ方法はない。また、URL はバイト列と同じ方法では検証できない（§ 8.1 リソースの完全性を参照）。 さらに、URL は利用者の閲覧について、粒度の粗いオリジン値が 保存元 オリジン群内で伝えるより、はるかに多くの情報を伝える。パスやクエリー文字列から、特定の文書、 アカウント、セッションを特定できるためである。したがって、URL をエントリーに記録すると、エントロピーの高いシグナルが、 開示の制限を迂回して伝わることになる。そうした制限を課すのが、オリジン群と§ 8.4 可用性の 制御の役割である。

それでも、この情報を必要とする理由はある。数ギガバイトのファイルを § 5.2 追い出しで述べた設定 UI で見ている利用者も、 getFileHandle() の呼び出しでエントリーが見つからなかった理由を調べている開発者も、そのファイルがどこから 来たかを知りたい。ユーザーエージェントは、実装内部だけで使用する来歴レコードを エントリーとともに保持することで、これに応えてもよい（たとえば、それぞれの保存元オリジン群の各オリジンが取得に用いた URL、 およびそのバイト列の取得日時）。ただし、レコードはユーザーエージェントの状態として、次のように エントリーの外部で保持する。

  • レコードをスクリプトに公開することは決してない。この仕様にはそれを開示するものがなく、 将来追加するものも開示すべきでない。getFileHandle() も、それが返す FileSystemFileHandle も、そのようなレコードの存在の有無さえ明らかにすべきでなく、 内容についてはなおさらである。特に、要求元のオリジンは、自身が生成していないレコードを 観測できてはならない。

  • レコードを表示するのは、信頼できるウェブ外のインターフェイスだけである。ユーザーエージェント自身の設定とストレージ 検査用 UI、その開発者ツール、または（ユーザーエージェントに拡張機能のプラットフォームがある場合は） 利用者が明示的に付与した許可を要する拡張機能 API に限られる。これは、閲覧履歴を公開する他の API と同じ扱いである。検討中の拡張機能向けインターフェイスについては、 ブラウザー拡張機能との統合箇所の解説を参照。 これは このリポジトリーに収録されている。

  • レコードは未検証であり、そのことが分かるように提示する。そこにある URL は、バイト列を書き込んだオリジンによる 申告である。内容を保証するのはハッシュだけである（§ 8.1 リソースの完全性を参照）。二つのオリジンが異なる URL を 同じエントリーに対して記録する場合があり、そのいずれも 不正確であったり、意図的に誤解を招くものであったりする可能性がある。

  • レコードの存続期間は、エントリーの存続期間と、そのレコードの帰属先オリジンの存続期間に従う。 エントリーが追い出されるか削除されたとき、レコードは破棄される。あるオリジンに帰属する部分は、 そのオリジンの共有レコードが保存元オリジン群から取り除かれたときに破棄される。 これには、利用者がその オリジンのサイトデータを消去した場合も含まれる（§ 5.2 追い出しを参照）。

このようなレコードはコンテンツから見えないため、ユーザーエージェントがレコードを保持するかどうか、またどの程度 保持するかは、全面的に実装に委ねられる。この仕様にはレコードに依存するものはなく、 サイトはその有無を検出できない。

6. 許可ポリシーとの統合

この仕様は、ポリシーで制御される機能 [permissions-policy] を定義する。その識別子は、 文字列 "cross-origin-storage" である。既定の許可リストは self である。ワーカーの許可ポリシー [WORKERS-PERMISSIONS-POLICY] の用語で言えば、この機能は サービスワーカーでは有効にできない。

この節は、 ワーカーの許可ポリシー [WORKERS-PERMISSIONS-POLICY] があたかも すでに [permissions-policy] と [HTML] の一部であるかのように、これに依存している。この提案は解説文書であり、 ワーカーのポリシー、SharedWorker の allow オプション、この節で参照する「サービスワーカーで 有効にできる」という真偽値は、いずれの仕様にも定義されていない。 執筆時点では、Chromium が共有ワーカーに関する部分をフラグ （PermissionsPolicyForSharedWorkers）の下で実装しているが、既定で提供しているエンジンはない。この作業が仕様化されたら、 この節ではフックを記述する代わりに、仕様化されたフックを呼び出すべきである。

[permissions-policy] は、使用を許可されているという判定を Document に対して定義する。 しかし、 CrossOriginStorageManager は WorkerGlobalScope にも公開されており、 それ自身の Document は存在しない。したがって、この確認は、呼び出し元のグローバルオブジェクトに対して定める。 これは [WORKERS-PERMISSIONS-POLICY] に従う。専用 ワーカーは、自身を所有する Document の ポリシーを推移的に継承し、共有ワーカーは独自のポリシーを持ち、サービス ワーカーではこの機能を有効にできない。

クロスオリジンストレージの許可を確認するには、グローバルオブジェクト global を受け取り、次のように 真偽値を返す。

  1. global が Window オブジェクトである場合、次を実行する。

    1. document を global に関連付けられた Document とする。

    2. document が null なら、false を返す。

    3. document について、次の機能の使用が許可されているという条件を満たさない場合、すなわち、 "cross-origin-storage" ポリシーで制御される機能の使用が許可されていなければ、 false を返す。

    4. true を返す。

  2. global が DedicatedWorkerGlobalScope オブジェクトである場合、次を実行する。

    1. owners を global の所有者集合とする。

    2. owners が空で ある場合、false を返す。

    3. 各 owner について、owners 内で次を実行する。

      1. owner が Document であり、owner について、次の機能の使用が許可されているという条件を満たさない場合、すなわち、 "cross-origin-storage" ポリシーで制御される機能の使用が許可されていなければ、 false を返す。

      2. owner が WorkerGlobalScope オブジェクトであり、 クロスオリジンストレージの 許可を確認する手順を owner を与えて実行した結果が false なら、false を返す。

    4. true を返す。

  3. global が SharedWorkerGlobalScope オブジェクトである場合は、 "cross-origin-storage" が global の許可 ポリシー [WORKERS-PERMISSIONS-POLICY] で有効なら true を、 それ以外なら false を返す。

    注： このポリシーに含まれる機能は、 作成元が allow メンバーを通じて委譲したものに限られる。このメンバーは、 SharedWorker コンストラクターのオプションに属する。さらに、ワーカースクリプト自身の Permissions-Policy レスポンスヘッダーで無効になっている機能は除かれる。これらの機能を委譲できない コンテキストは、 たとえば自身のポリシーがクロスオリジンストレージを無効にしている場合、接続に失敗する。 したがって、このポリシーはワーカーの実行中に変化し得ない。

  4. false を返す。

    注： これには ServiceWorkerGlobalScope が含まれる。 そこでは "cross-origin-storage" を有効にできない [WORKERS-PERMISSIONS-POLICY]。

このアルゴリズムが false を返すグローバルオブジェクトでは、そこから行われるすべての getFileHandle() 呼び出しが、次の例外で拒否される。 "NotAllowedError" DOMException。 これは、ハッシュの検証、レジストリーの検索、書き込みのいずれを 行うよりも前である。

注： 所有者集合をたどって判定することで、この機能の無効化が 名目だけのものになるのを防ぐ。blob: URL から作成されたワーカーは、作成元ページの オリジンで動作し、そのページとまったく同じクロスオリジンストレージの内容を見る（ § 3 CrossOriginStorageManager インターフェイスを参照）。このため、 グローバルオブジェクト自身の Document だけを参照する確認では、どのワーカーでも条件が自明に満たされてしまい、 new Worker(URL.createObjectURL(&hellip;)) に移した呼び出しに、 cross-origin-storage=() ポリシーが それ以外の条件が同じでも適用されなくなる。

注： サービスワーカーはクロスオリジンストレージを使用できない。 これは、 "cross-origin-storage" が、サービスワーカーで有効にできる機能には 該当しないためである [WORKERS-PERMISSIONS-POLICY]。これは、 ポリシーで制御されるすべての機能に対する 既定の扱いであり、クロスオリジンストレージでも維持される。サービスワーカーの登録は永続化され、ユーザー エージェントはイベントに応じてそれを起動する。また、一つの実行中のサービスワーカーが複数のクライアントに対応し、それらの ポリシーは一致するとは限らない。このため、単一の Document を選んで、そのポリシーを参照することはできない。 API 自体はそこでも公開されているので、呼び出しは "NotAllowedError" で拒否される。これは、この アルゴリズムが拒否する他の呼び出しと同じである。次も参照。 explainers-by-googlers/workers-permissions-policy#4。

注： SharedWorkerGlobalScope の 所有者集合は、複数の Document を含み得る。 それらのポリシーは異なる場合があり、ワーカーの存続中に所有者は増減する。 ワーカーの作成時に固定されるワーカー自身のポリシーを参照することで、判定は 連続する二度の getFileHandle() 呼び出しの間で変わらない。これを利用して 無効化を免れることもできない。ポリシーでクロスオリジンストレージを無効にした文書は、この機能を委譲できず、 この機能を持つ共有ワーカーを作成することも、そのようなワーカーに接続することもできないからである。

7. Cross-Origin-Storage-Allow-Origin ヘッダー

COS エントリーのオリジン群のリストが 空でなければ、そのエントリーは、書き込み元が管理していないオリジンにも 開示できる。一方、そのリストを宣言するのはスクリプト（ origins を介する） またはマークアップであり、そのどちらも、スクリプトまたはマークアップの 注入に成功した攻撃者が設定できる。開示されるバイト列のオリジンを運営する者に、 注入されたコンテンツが偽造できない形でその宣言を結び付けるため、この 仕様は、そのような宣言で指定できるオリジンを制限するレスポンスヘッダーを定義する。

Cross-Origin-Storage-Allow-Origin レスポンスヘッダーは、 COS の範囲の上限を伝える。これは、 集合であり、 その要素は、オリジンのうち、書き込みが同一サイトに限らない オリジン群のリストで指定できるものである。 ヘッダーを送るのはバイト列の提供者であるため、読み取り元は、 開示対象のバイト列の由来となるレスポンスである。

  • getFileHandle() による書き込みでは、バイト列をスクリプト内で 生成することがあり、バイト列自身の由来となるレスポンスが存在するとは限らない。この場合に使うレスポンスは、 呼び出し元のグローバルオブジェクトの Document の作成に使ったものである。 ワーカーの場合は、そのワーカーを作成した Document のもとになったレスポンスを使う。作成は、直接でも他のワーカーを介してでもよい（ COS の範囲の上限を取得するを参照）。

  • ホスト統合の場合、使うのは、レスポンスのうち、取得され、そのバイト列が保存されるリソースのものである （取得したリソースを クロスオリジンストレージに保存するを参照）。送信元はリソースのサーバーであり、 次の Document 、すなわちリソースを読み込む文書のサーバーと同じである必要はない。

宣言されたリストについては、 共通部分を上限との間で取る（ COS の範囲の 上限を適用するを参照）。したがって、上限によって宣言の範囲が広がることはない。

注： このヘッダーは、バイト列を提供する側による 認可である。指定されたオリジン、すなわち、 後に読み取る側への問い合わせはなく、その側が何かを送ることもない。リストに載ったオリジンが関わるのは、後から getFileHandle() を その COS ハッシュについて、他の読み取り元と同様に 呼び出すときだけである。これは Access-Control-Allow-Origin [FETCH] とは逆向きに働く。そちらでは、 リソースを持つサーバーが、所定のオリジンにそのリソースの読み取りを認める。ここでは、バイト列の提供者が、 後にクロスオリジンストレージから読み取れる相手を制限する。書き込み元ページに注入されたコンテンツは、 提供者のレスポンスヘッダーを設定できないため、その制限を広げることはできない。

注： ヘッダーが適用されるのはリスト形式のみである。 同一サイトという既定値はクロスオリジンの 受信先を指定しないので認可を必要としない。また、"*" 形式は、読み取り経路で、 可用性の制御により公開ハッシュリストに照らして判定される。利用者ごとの 秘密情報がこの判定を通過することはないので、この形式にも書き込み時の上限は必要ない。 "*" にヘッダーを要求すると、設定なしでのグローバルな共有が機能しなくなるうえに、 公開ハッシュリストがすでに防ぐもの以外に、防げるものはない。

COS の範囲の 上限を構文解析するには、ヘッダー リスト headers を受け取り、次のように集合を返す。その要素は オリジンである。

  1. value を、取得し、デコードし、分割する手順を "Cross-Origin-Storage-Allow-Origin" について headers に対して実行した結果とする。

  2. value が null なら、空の集合を返す。

  3. ceiling を空の集合とする。

  4. 各 token について、value 内で次を実行する。

    1. 先頭と末尾の ASCII 空白を取り除く操作を token に対して行う。

    2. token が空文字列なら、次の反復に進む。

    3. url を、基本 URL パーサーを token に対して実行した結果とする。

    4. url が失敗である場合、url のスキームが "http" と "https" のいずれでもない場合、または url のオリジンが潜在的に信頼できるオリジンでない場合、 空の集合を返す。

      注： これには、 token が "*" の場合も含まれる。これはオリジンとして構文解析できない。 Cross-Origin-Storage-Allow-Origin ヘッダーで列挙できるのは、有限個の 具体的な オリジンのみである。"*" は許可される値ではない。上限を「任意のオリジン」とすれば、 注入されたコンテンツが 好きな受信先を宣言できるようになり、ヘッダーの目的そのものが 損なわれるからである。 範囲を限定しない 開示は、"*" というオリジン群の形式を通じてのみ可能であり、 その可否は 公開ハッシュリストによって制御され、この ヘッダーを参照することはない。不正なヘッダーや "*" を含むヘッダーは、 ヘッダーが存在しない場合とまったく同じく、何も認可しない。失敗時には閉じる。

    5. 追加する項目を url のオリジンとし、ceiling に追加する。

  5. ceiling を返す。

注： 取得し、デコードし、分割する手順は U+002C (,) で分割するため、 ヘッダー値に含まれるオリジンは コンマ区切りである。これは Timing-Allow-Origin [RESOURCE-TIMING] にも、 リストを値に取る HTTP レスポンスヘッダー一般の慣例にも合致する。一方、対応する crossoriginstorage HTML コンテンツ 属性は、ホストの構文に合わせて空白区切りである。どちらも同じ オリジンの集合に解決される。

COS の範囲の 上限を取得するには、グローバルオブジェクト global を受け取り、次のように集合を返す。その要素は オリジンである。

  1. global が Window オブジェクトである場合、次を実行する。

    1. document を global に関連付けられた Document とする。

    2. document が null なら、空の集合を返す。

    3. document の COS の範囲の上限を返す。

  2. global が WorkerGlobalScope オブジェクトである場合、global の COS の範囲の上限を返す。

  3. 空の集合を返す。

COS の範囲の 上限を適用するには、次の引数を受け取る。リストで、各要素がオリジンである requestedOrigins と、 集合で、 各要素がオリジンである ceiling である。返す値は、リストで各要素がオリジンであるもの、または null である。

  1. 取り除く対象は、requestedOrigins にある各オリジンのうち、ceiling が 含むもの以外とする。

    注： 受信先が COS の範囲の 上限に含まれなければ、その受信先は除外されるが、書き込みは 成功する。これは、上限長を超えた拡大で超過分を除外する リソースの可視範囲を拡大する手順と同じ扱いである。ユーザーエージェントには、 コンソールに警告を記録し、そこで 除外した各オリジンを明示することが期待される。

  2. requestedOrigins が空で ある場合、null を返す。

    注： リストのすべての 要素が除外されると、その書き込みには認可された クロスオリジンの受信先がないため、同一サイトという既定値にフォールバックする。バイト列は引き続き 保存される。見送られるのは、認可されていない開示だけである。

  3. requestedOrigins を返す。

すべての Document は、COS の範囲の上限を持つ。これは集合であり、その要素はオリジンである。 文書の作成時に、その値は、COS の範囲の上限を構文解析する 手順に次の ヘッダーリストを与えて実行した結果に設定される。それは、レスポンスのうち、当該文書の 作成に使用したもののヘッダーリストである。

すべての WorkerGlobalScope は、COS の範囲の上限を持つ。これは、 集合であり、 その要素はオリジンである。その値は、ワーカーを 実行する手順によるワーカーの作成時に、 COS の範囲の上限を取得する手順を、グローバルオブジェクト として outside settings のものを与えて実行した結果に設定される。この設定群は、ワーカーを 実行する手順に与えられたものである。専用ワーカーの場合、 これは、そのワーカーを構築したグローバルオブジェクトである。共有ワーカーの場合は、 SharedWorker コンストラクターの呼び出しによってワーカーを作成したグローバルオブジェクトである。実行中のワーカーに後から接続する コンテキストが、その上限を変更することはない。

注： ワーカーが受け取るのは作成元の上限であり、自身のスクリプトの レスポンスから上限を取得することはない。 blob: ワーカーは、作成元ページのオリジンを共有し、まったく同じクロスオリジンストレージの内容を見る （§ 3 CrossOriginStorageManager インターフェイスを参照）。 また、そのレスポンスにはヘッダーがない。したがって、 ワーカー自身から読み取ると、どの blob: ワーカーでも上限が空になり、 リストで範囲を指定した書き込みを new Worker(URL.createObjectURL(&hellip;)) に移すだけで、 その ページが認可した受信先が除かれてしまう。作成時に上限を固定するのは、クロスオリジンストレージの 許可を確認する手順と同様である。そこでは共有ワーカーのポリシーに含まれるのは、作成元が 委譲したものだけである。そのため、判定は、 二度の getFileHandle() 呼び出しの間で、コンテキストがどのように 接続または切断しても変化しない。共有ワーカーに接続できるコンテキストはすべて、そのワーカーの オリジンを持つ。したがって、後から接続するコンテキストの上限がより狭い場合でも、その運営者は、 作成元の上限を 認可した運営者と同じである。

Document の COS の範囲の 上限を、そのレスポンス から設定するには、 [HTML] の文書 作成手順にフックが必要である。これは [permissions-policy] や [CSP] が レスポンス処理時に設定されるのと同様である。このフックができるまで、この節で 必要な挙動を直接記述する。将来の改訂では、 [FS] のフック（§ 3.3 ファイルの作成と書き込みを参照）とともに正式に統合することが期待される。WorkerGlobalScope の COS の範囲の上限にも、同じ種類のフックが ワーカーを実行する手順に必要である。ホスト統合には、そのようなフックは必要ない。 取得したレスポンスを取得したリソースをクロスオリジンストレージに 保存する手順に渡すと、この手順が そのレスポンスから上限を読み取るためである。

8. プライバシーとセキュリティに関する考慮事項

この節は、RFC 2119 のキーワードを使用している箇所を除き、参考情報である。 セキュリティとプライバシーに関する質問票も、 リポジトリー内を参照されたい。

リポジトリー内のプライバシー分析では、これらの考慮事項が対象とする攻撃と、 個々の緩和策がどこまで有効かを説明している。

8.1. リソースの完全性

すべての COS エントリーは、暗号学的ハッシュをキーとし、その バイト列は同じハッシュに照らして検証される（ § 3.3 ファイルの作成と書き込みを参照）。したがって、サイトは、 次のメソッドで取得したファイルが、 getFileHandle() を使わずに自ら取得した場合とまったく同じバイト列を持つと確信できる。 ここで取得の対象となるのは hash である。開発者はクロスオリジンストレージの内容を列挙できず、 ファイルのハッシュをあらかじめ知らなければ、そのファイルにアクセスすることもできない。

COS ハッシュは秘密情報ではない。これは コンテンツの識別子であり、すでにファイルを持っている人なら誰でも容易に 計算できる。この仕様が対象とする広く配布されるリソースでは、ハッシュは通常公知であり、 モデルやライブラリーのリリースとともに公開されることも 多い。したがって、ハッシュを知っていればエントリーの検索はできるが、それだけでアクセス権が得られるわけではない。 検索の成否は、もっぱらオリジン群と § 8.4 可用性の制御によって決まる。開発者は、未公開のハッシュを アクセス制御の仕組みとして扱ってはならない。特定のファイルに関心のある 攻撃者は、そのハッシュを推測する必要はなく、ファイルそのものを入手すれば 足りる（§ 8.2 クロスサイトでの探索を参照）。

8.2. クロスサイトでの探索

あるリソースをごく限られたサイトしか使っていない場合、そのリソースが クロスオリジンストレージに存在することを知った攻撃者は、利用者がそれらのサイトのいずれかを訪問した可能性が高いと推測できる。 getFileHandle() が存在を知るための仕組みであるため、その呼び出しは一つひとつが 実質的に探索となる。この仕様では、探索によって知り得ることを三つの仕組みで制限する。

  • オリジン群（ § 3.5 リソースの可視範囲の拡大を参照）により、保存元の オリジンは、 開示先を選択したオリジンの集合と、それらと同一サイトのオリジンに制限できる。したがって、独自のリソースや利用頻度の低いリソースを グローバルに 探索可能にする必要はまったくない。

  • § 8.4 可用性の制御は、さらに、 範囲が "*" のリソースについて、 要求元オリジンがその保存元オリジン群の外にある場合、ハッシュがPHL に載っている場合を除いて開示を見送る。 そのため、リソースの保存時に origins: "*" を指定しても、 ウェブ上のすべてのオリジンから自動的に探索可能になることはない。この制御の対象は、 範囲が "*" の エントリーだけである。リストまたは同一サイトを範囲とするエントリーでは、最初の項目の制限だけが 適用される。保存元オリジンがそれらの開示範囲をすでに明示的に制限しているためである。

  • クロスサイト検索予算は、 トップレベルサイトが一つの 検索時間枠内で行える探索の回数を制限する。そのため、 一つひとつはありふれたファイルであっても、その組み合わせを無制限に調べることはできない。

最初の項目が成り立つのは、「選択したオリジンの集合」が、ウェブ全体に比べて実質的に小さい範囲にとどまる場合だけである。 origins の形式そのものは、呼び出し元が 非常に多数のオリジンを列挙することを妨げない（たとえば、公開されている人気サイトの ランキングから作ったリスト）。そのようなリストは、実質的にグローバルな開示に近づく一方で、 "*" だけが要求する、意図的かつ明示的な選択を伴わない。そこで、オリジンリストの 最大長（ § 5.1 ストレージの上限を参照）がこれを制限する。実際に複数のサイトを運営する場合の 用途 （同一の運営者が管理する少数の関連オリジン）に対応しつつ、「すべてのオリジン」に近いとは到底いえないほど 小さな上限を定めることで、オリジン群の制限付き形式が、 宣言のない "*" の代用品として使われることを防ぐ。

注： § 9 他の仕様との統合のいずれかのホスト統合による検索も、 ページにエラーを見せることはないものの、同じく探索である。サイトは、自身の サーバーがフォールバック要求を受け取ったかどうかを観測できる。これは "NotFoundError" が伝えるのと同じ 1 ビットである。同じ制御が この検索にも適用され、クロスサイト検索予算は、これも getFileHandle() の呼び出しとともに計上する。スクリプトから使える統合なら、 同じように容易にループ内で検索を繰り返せるためである。

8.3. 進行中の書き込み

要求されたが完了していない書き込みは、どのオリジンから見ても、 一度も書き込まれていないハッシュと区別できてはならない。この仕様では、構造によってこれを実現している。 COS エントリーを COS レジストリーに追加するのは、検証して保存する手順または 取得したリソースをクロスオリジンストレージに 保存する手順に限られ、どちらの場合も、バイト列の全体を ハッシュに照らして検証した後にのみ追加する。作成要求を完了する手順は、レジストリーの読み取りも書き込みも 行わない。したがって、 読み取り時に観測できるプレースホルダーの状態はなく、読み取り経路には、 可用性の制御を適用する手順より先に応答できる分岐もない。

これに対して、作成要求を受けた時点でプレースホルダーを登録し、それと並行した 読み取りを区別可能なエラーで拒否すると、いずれかのオリジンが、あるハッシュに対して 今まさに書き込み中であることを呼び出し元が知り得る。この 1 ビットは些細に見えるが、そうではない。次の場合にも取得できてしまう。

  • どのオリジンにも、そのエントリーに対するいかなるアクセス権もないオリジンにさえ取得できる。プレースホルダーは 共有レコードを持たず、読み取りへの応答が、可用性の制御を 適用する手順の実行前に返るためである。

  • どのハッシュについても取得できる。PHL に載っていることがなく、今後も載り得ないものも含まれるため、攻撃者は 利用者ごとの値から導出したハッシュも使用できてしまう（§ 8.8 フィンガープリンティングを参照）。

  • GREASE 処理を経ずに取得できる。この処理は、制御の段階に到達した開示にのみ 適用される ため、このビットにはノイズがない。

  • バイト列を一切提供せずに取得できる。このため、オリジンごとのストレージ上限も、 次の COS 書き込み上限も、 § 5.2 追い出しも、一つのオリジンが作れるそのようなビットの数を制限できない。

そのため、二つのサイトに埋め込まれたトラッカーは、一方で任意の長さの識別子を生成して 他方で読み取ることができてしまう。ストレージを消費することなく、オリジン群、 公開ハッシュ リスト、GREASE 処理のすべてを迂回できる。プレースホルダーはサービス妨害の 要因にもなる。実際に広く使われるリソースのハッシュを占有されると、プレースホルダーが残っている限り、 他のどのオリジンもそのリソースを読み取れなくなる。

注： この設計で失われるのは、ある呼び出し元が、 別の呼び出し元がすでに大きなファイルをダウンロードしていることを知り、 重複するダウンロードの開始を避ける機能である。これは実際の不利益であり、 この仕様の以前の草案がここで区別可能なエラーを用いた理由でもある。最も重要な場合、すなわち、 単一オリジン内であれば、この機能は Web Locks、BroadcastChannel、 または共有ワーカーを使用することで取り戻せる。 これらはいずれも、 オリジン境界を越えて情報を開示しない。オリジン間での節約効果は、ほぼ理論上のものにすぎない。無関係な二つの オリジンがまったく同時に同じハッシュをめぐって競合する必要があるうえ、どちらもまだ書き込んでいない エントリーは、いずれにせよ、そのハッシュがPHL に載っている状態になるまで相手に開示できない。

注： "NotAllowedError" は、引き続き getFile() を、 作成要求で取得し、まだ書き込みに使っていないハンドルで呼び出したときの応答である（§ 4 クロスオリジンストレージファイルシステムを参照）。この応答は、 レジストリーの内容によって変化せず、要求を行ったオリジンにしか届かない。ハンドルは オリジンを越えて逆直列化できないためである（§ 4.1 ハンドルの 転送を参照）。したがって、これは情報伝達経路にはならない。

8.4. 可用性の制御

getFileHandle() による読み取りを、次の集合の外にあるオリジンから行う場合、すなわち、 保存元 オリジン群の外から行う場合、その成否は常に、要求元のオリジンに エントリーを読み取ることが許可されているかどうかに依存する。これを決めるのがオリジン群である。範囲が "*" のエントリーには、これとは独立した 二つ目の条件も適用される。ユーザーエージェントが、そもそもエントリーが存在する ことを開示する用意があるかどうかである。これを決めるのは、PHL への 掲載とGREASE 処理である。このようなエントリーでは両方の条件が 成り立たなければならない。リストまたは同一サイトを範囲とするエントリーには、最初の条件だけが適用される。 規範となるアルゴリズムは§ 3.2 ファイルの読み取りを参照。したがって、"NotFoundError" を受け取っても、 リソースが存在しないことの証明にはならない。リソースが存在しない場合のほか、要求元の オリジンが範囲外の場合、範囲が "*" のリソースのハッシュが PHL にまだ載っていないか今後も載らない場合、 または そのリソースが引き続き COS ユーザー活性化ゲートを待っている場合、要求元のトップレベルサイトが すでに 自身のクロスサイト検索予算を使い切った場合、あるいは GREASE 処理が 真陽性を抑制した場合もある。開発者は、"NotFoundError" に対して、 「ネットワークにフォールバックする」以上に具体的な意味を持たせてはならない。

注： 公開ハッシュリストだけでは、 グローバルな範囲を十分に制限できない。個々には PHL に掲載できるリソースでも、 どの部分集合が書き込まれたかによってクロスサイト識別子になり得るためである。 これを制限するのは、クロスサイト検索予算、COS ユーザー活性化ゲート、 および COS 書き込み上限 である。いずれも、利用者のサードパーティ Cookie の設定には依存しない。

注： クロスサイト検索予算 に検索を計上しないのは、その応答に使用した共有レコードが、 読み取り元自身のトップレベルサイトの下で書き込まれた場合に限られる（ 計上対象外の検索で あるを参照）。該当するのは、保存元オリジン群のレコード、またはオリジン群のレコードのうち、そのパーティションが同一 サイトであるもの、すなわち、 読み取り元の COS パーティションと同一サイトであるものである。 それ以外の検索は、エントリーが見つかるかどうかにかかわらず、すべて計上する。これには、 ファーストパーティのオリジン群のレコードであっても、それが 別のトップレベルサイトの下で書き込まれた場合の検索が含まれる。Cross-Origin-Storage-Allow-Origin ヘッダーは、注入されたコンテンツが このような読み取り元を指定することを防ぐ。一方、書き込み元サイトの運営者は任意のオリジンを指定できる。このため、 計上しなければ、協力関係にある二つのサイトが、一方のマーカーファイルについて、リストで他方を指定することで、 別々の訪問にまたがって、他方で任意の長さの識別子を無制限に読み取れるようになってしまう。 予算超過を理由に拒否された検索は、"NotFoundError" DOMException で拒否される。 これは、検索でエントリーが 見つからなかった場合とまったく同じである。COS ユーザー活性化ゲートは、GREASE 処理と同様に、グローバルな範囲だけを根拠に 条件を満たすオリジンにのみ適用される。保存元オリジン群、明示的なオリジン群のリストに載るオリジン、および いずれかと同一サイトである オリジンは、COS の開示を判定する手順がエントリーを返すとすぐに、それを読み取れる。

8.5. 開発者向けの指針

情報が漏れるサイトに攻撃者がいなくても、生じ得る漏えいがある。サインインした利用者についてだけファイルを保存するサイトや、 利用者ごとにバイト列が異なるファイルを保存するサイトは、そのファイルを検索できるすべてのサイトに利用者の状態を開示してしまう。 しかも、自身の遠隔測定データにはそのことが現れない。ユーザーエージェントには、書き込みによって何が開示されるかを、 書き込みが行われた時点で、コンソールの警告または開発者ツールを通じて開発者に知らせることが期待される。 メッセージを出すに値する場合には、次のものがある。

  • "*" を要求する書き込みで、ハッシュがPHL に載っているという条件を満たさず、範囲が同一サイトのままになる場合（ リソースの可視範囲を拡大するを参照）。

  • オリジン群のリスト が、COS の範囲の 上限によって切り詰められた場合（ COS の範囲の上限を適用するを参照）、またはオリジンリストの最大長に達した場合。

  • オリジンごとのストレージ上限または COS 書き込み上限によって書き込みが拒否された場合。

8.6. GREASE 処理

ユーザーエージェントは、GREASE 処理（ランダムな拡張を生成して拡張可能性を 維持する）を適用してもよい。これは、開示可能なエントリーが 存在しないかのように、ときおり応答することである。§ 8.4 可用性の制御が 通常なら 開示を許す場合でも、そのように応答する。これによってノイズが加わり、サイトにとって、本当に存在しない場合と プライバシーを理由とする偽陰性とを区別することが難しくなる。これは、 ユーザーエージェント・クライアント ヒントで使われる手法と同様である。

GREASE 処理は、グローバルな範囲だけを根拠に条件を満たすオリジンにのみ適用される。これは、公開ハッシュ リストが開示を制御する場合と同じである（COS の開示を判定するを参照）。 ユーザーエージェントは、この処理を、保存元オリジン群、明示的な オリジン群のリストに載るオリジン、または それらのいずれかと同一サイトであるオリジンに適用してはならない。

GREASE 処理を適用するユーザーエージェントは、対象のエントリーのサイズに 見合った判断をしなければならない。ネットワークからのフェッチへのフォールバックが安価な小さいエントリーでは、ときおり生じる 偽陰性は、プライバシーのための妥当な代償である。ユーザーエージェントは、サイズのために、 不要な再ダウンロードの負担が、その結果得られるプライバシー上の利益と明らかに釣り合わないエントリーに、GREASE 処理を適用してはならない （たとえば、ギガバイト規模の AI モデルの重み）。その場合、偽陰性により、全体を 観測可能かつ高いコストで再ダウンロードすることを強いられるからである。クロスサイト検索予算がそれらのエントリーへの検索を 制限し、GREASE 処理の結果を見分けるために検索が繰り返されれば、その都度計上する。

8.7. 派生成果物のタイミング

派生 成果物の再利用は、新たに計算するより速いため、観測可能である。成果物に ページが選択した入力がなければ、開示されるのは、 その成果物の作成に使われた読み取り、すなわち、 派生元を提供した読み取りがすでに開示した情報だけである。 ページが選択した入力は、 識別子を伝え得る。一つのサイトでの演算子オプションの選択が成果物に反映されると、 別のサイトでどの計算が速く終わるかという違いから、協調するスクリプトに識別情報が伝わり得る。 このような再利用を毎回クロスサイト検索予算に計上することで、伝わる情報を、検索によってすでに 開示される範囲に制限する。

8.8. フィンガープリンティング

クロスオリジンストレージを探索して攻撃者が得られる情報の量は、探索対象のリソースがどの程度 普及しているかによって制限される。ある利用者が、一般的な AI モデルや 広く使われている JavaScript ライブラリーのように非常に普及したリソースを持っていると分かっても、それを使う（場合によっては非常に 多数の）サイトのいずれかを訪問したことしか明らかにならない。珍しいリソースや固有のリソースを持っていると分かれば、得られる情報ははるかに多い。

珍しいハッシュや利用者ごとのハッシュがPHL に 載っていることはない。したがって、他のサイトがそのエントリーを読み取れるのは、 オリジン群のリストを 書き込み元の運営者が認可した場合に限られる。また、 クロスサイト 検索予算は、他のトップレベルサイトの下で行われるそのような読み取りを計上する。なお残るリスクは、 PHL に掲載されていても、少数のデバイスしか保持していないハッシュである。たとえば、手動で選定される AI モデルの部門に掲載された用途の限られたモデルがこれに当たる。この場合、一度の検索で一人の利用者を指し示し得るため、 一度しか検索を必要としない攻撃を、予算で制限することはできない。PHL への掲載が認めるのは開示にすぎないため、ユーザーエージェントは、 そのようなエントリーをいつでも自身のスナップショットから除いても、手動で選定された部門全体を省いてもよい。 ユーザーエージェントは、デバイス上のヒューリスティックを用いて探索のパターンを検出し、ブロックしてもよい。

9. 他の仕様との統合

この節は参考情報である。

ここで定義する COS レジストリーには、 四つのホスト統合からもアクセスできる。その際、 getFileHandle() を直接使用する必要はない。各 統合はそれぞれのホスト仕様で定義する。この仕様は、共通の 基礎概念（COS ハッシュ、COS エントリー、可用性の制御、および 公開ハッシュ リスト）と、取得したリソースをクロスオリジンストレージに 保存する手順を定義する。 これらの統合は、そうした概念と手順を基礎にすることが期待される。

  • HTML：crossoriginstorage 属性を、 link および script 要素のうち、すでに integrity [SRI] を持つものに指定する。WHATWG への提案は whatwg/html#12770 にある。

  • JavaScript：ホスト定義の crossOriginStorage インポート属性。 これは、 integrity と併用でき、インポート属性 の提案を基礎とする。WHATWG への提案は whatwg/html#12771 にある。

  • CSS：cross-origin-storage() という <request-url-modifier>。 これは integrity() と併用できる。 CSS ワーキンググループへの提案は w3c/csswg-drafts#14056 にある。

  • Fetch：crossOriginStorage という RequestInit オプション。これは integrity [FETCH] と併用できる。 WHATWG への提案は whatwg/fetch#1954 にある。 この形式にはホスト定義の宛先がなく、COS エントリーが保存するのはバイト列だけである。 したがって、その仕様が、Response を COS レジストリーからどのように返すかを定義する。期待される 形は成功レスポンスである。ステータスは 200、ステータスメッセージは OK、そして 本体はバイト列のストリームである。Content-Type ヘッダーの値は、 その 呼び出し元が宣言する MIME タイプであり、ネットワークからのフェッチは行われていないため、他のヘッダーは持たない。 このオプションには GET メソッドが必要になることが期待される。ヒットしたときは、要求を 送信せずに応答するためである。これが安全なのは、要求に本体がなく、副作用もないメソッドだけである。 したがって、Request コンストラクターは、TypeError を、 それ以外のすべてのメソッドについて投げることになる。

説明のために、同じグローバルに共有されるリソースについて、クロスオリジンストレージの利用を 四つの形式それぞれで指定する例を示す。

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

これらのコード断片は例示にすぎない。この仕様は、ここに示したどの構文も定義しない。 各形式の正式な文法は、範囲を制限するオリジンリストの記法も含め、 それぞれのホスト仕様が定める。記法の違いは 意図的である。RequestInit のメンバーは sequence<DOMString> を取ることができ、これは origins と完全に一致する。一方、属性値、 インポート属性値、および CSS 修飾子の引数で渡せるのはテキストだけである。

四つの形式には、共通の処理モデルが期待される。まず COS レジストリーを調べ、一致する開示可能なエントリーがない場合に ネットワークからのフェッチにフォールバックする。また、 取得に成功して完全性の検証を終えたリソースは、COS レジストリーに保存し、 他のオリジンが再利用できるようにする。これは getFileHandle() が行うこととまったく同じである。保存の手順は、 取得したリソースをクロスオリジンストレージに 保存するであり、各統合はこれを、 取得したレスポンスを与えて実行する。したがって、範囲を制限するオリジンの値は、 そのリソースのレスポンスの Cross-Origin-Storage-Allow-Origin ヘッダーによって制限される。これを送信するのは、 バイト列を提供するサーバーである（§ 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照）。 これらの統合に関する議論は、各統合を取り込むホスト仕様の課題トラッカーで行うものであり、 このリポジトリーの課題トラッカーで扱うものではない。

9.1. リソースタイミング

上記の統合のいずれかが COS レジストリーから提供するリソースは、 リソースタイミング [RESOURCE-TIMING] に、他の取得済みリソースと同様に報告される。レスポンスが このようなヒットによって提供される場合、そのキャッシュ状態には "local" が設定されることが期待される。ネットワークからの フェッチが行われなかったためである。また、そのタイミング許可通過フラグはセットされることが期待される。ここには、 タイミング情報の 保護を必要とするサーバーが関与しないためである。さらに、その本体情報の エンコード済みサイズとデコード済みサイズには、 バイト列の長さが設定されることが期待される。これは Cache API が保存するレスポンスについて行うことと同じである [SERVICE-WORKERS]。 統合は、配信種別として "cross-origin-storage" を リソースタイミングを記録する手順に渡すことが期待される。その結果、エントリーの deliveryType は "cross-origin-storage" となり、その transferSize は 0 となり、その encodedBodySize は保存されたリソースのサイズとなる。

注： ヒットは、タイミングや、 サーバーに要求が届かないことからすでに 観測可能であるため、これによって、§ 8.4 可用性の制御がすでに制御している範囲を超えて 何かが開示されることはない。

deliveryType に、もう一つ値を追加することを提案します。
