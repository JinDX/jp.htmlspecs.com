概要

オリジン間ストレージ（COS）は、Web アプリケーションが AI モデル、WebAssembly モジュール、非常に普及している JavaScript ライブラリなどの 大容量ファイルを異なるオリジン間で保存および取得できる、コンテンツアドレス可能なキャッシュです。ファイルは URL ではなく暗号学的ハッシュによって識別されるため、あるオリジンによって一度取得された バイト単位で同一のリソースは、ユーザーエージェントが許可する他の任意のオリジンによって、再度ダウンロードすることなく再利用できます。キャッシュ内の存在を、ユーザーがどのサイトを訪問したかの推測に利用できないようにするため、 ファイルのオリジン間開示は、k-匿名性方式の人気度基準を満たすハッシュに限定されます。

1. はじめに

この節は非規範的です。

ストレージは通常、ユーザーのセキュリティとプライバシーを保護するためにオリジンごとに分割されます。これは適切な デフォルトですが、非常に大きく、非常に人気があり、公開配布されている限られた種類の リソース（AI モデル、WebAssembly モジュール、JavaScript ライブラリ、ゲームエンジン、大容量の Web フォント） には適していません。これらは、どのサイトが要求しても、バイト単位でまったく同じファイルです。関連のない 2 つの オリジンがそれぞれ同じ 8 GB のモデルに依存する場合、オリジン分割ストレージでは ユーザーはそのモデルを 2 回ダウンロードして保持する必要があり、ユーザーの帯域幅、ストレージ、 バッテリー、およびネットワーク全体にとって無駄になります。

Cross-Origin Storage (COS) は、URL ではなく暗号学的ハッシュをキーとするコンテンツアドレス可能キャッシュであり、ユーザーエージェントが、その利用をオプトインした オリジン間で、このようなリソースの保存済みコピーを 1 つ共有できるようにします。COS へのリソースの保存は常に、保存する オリジンによる明示的なオプトイン操作であり、ユーザーエージェントは、本来なら読み取りが許可されているオリジンに対しても、 リソースが存在することの確認を差し控えることができます。§ 8 プライバシーと セキュリティに関する考慮事項を参照してください。

この仕様のエントリポイントは、requestFileHandle() メソッドであり、crossOriginStorageを介して公開されます： 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // ファイルを使用して何らかの処理を行う。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // Cross-Origin Storage 内に（開示可能な形で）存在しないため、代わりにネットワークから取得する。
  }
}

この仕様は、File System Standard [FS] の FileSystemFileHandle、 FileSystemWritableFileStream、 および関連する 基盤を再利用し、オリジン間で共有され、各オリジンの非公開またはユーザー可視のファイルシステムとは 分離された専用ファイルシステムに適用します。

この仕様は命令型 JavaScript API と、ホスト統合がその上に構築する共有保存ステップを定義します。 関連する提案では、同じ基盤キャッシュを他のホスト仕様にも統合します。HTML の link および script 上の crossoriginstorage 属性、 crossOriginStorage JavaScript import 属性、CSS の cross-origin-storage() <request-url-modifier>、および fetch() 用の crossOriginStorage RequestInit オプションです。それぞれは 独自のホスト仕様で定義されます。§ 9 他の仕様との統合を参照してください。

2. 概念

2.1. ハッシュ

COS ハッシュは、次の構造体項目を持ちます：

algorithm

[WEBCRYPTO] が認識するハッシュアルゴリズムを示す文字列。 たとえば "SHA-256"。

value

文字列であり、algorithmによって生成されたダイジェストを 小文字の 16 進数で符号化したものです。 "SHA-256" の場合、これは 64 文字です。

algorithm dictionary メンバーは単純な DOMString として型指定されていますが、その値空間は [WEBCRYPTO] の ハッシュアルゴリズムが受け入れる名前の集合と正確に一致します。HashAlgorithmIdentifier は (object or DOMString) であり、その object 分岐は、 [WEBCRYPTO] によって Algorithm 形式の dictionary に正規化されるため、呼び出し元は必要とするアルゴリズムに追加の パラメーターを渡せます（たとえば {name: "HMAC", hash: "SHA-256"}）。ハッシュ アルゴリズムにはそのようなパラメーターはなく、 algorithmはコンテンツアドレス可能 キーの一部として保存、比較、ラウンドトリップされ、この仕様の 例ではすべて単純な文字列が使用されています。ここで任意のオブジェクトを許可しても機能は増えず、 等価性とシリアル化を 不必要に複雑にするだけです。したがって、このフィールドには DOMString の方が より限定的で適切な型です。

2 つのCOS ハッシュ値は、そのalgorithm 値がASCII 大文字・小文字不区別で一致し、かつそのvalue値が正確に 等しい場合、等しいものとします。

注: valueはすでに規範的に小文字と定められているため（上記参照）、その比較は 単純な 文字列比較です。algorithmには規範的な大文字・小文字の指定がないため、 ASCII 大文字・小文字不区別で比較されます。

コンテンツアドレス可能な ストアとは、そのエントリが COS ハッシュの等価性によってキー付けされるものです。 同一のバイト列と同一のハッシュアルゴリズムを持つ 2 つのファイルは、それらを保存したオリジンの数や 取得元 URL の数に関係なく、同じエントリです。

2.2. COS エントリ

各ユーザーエージェントは単一のCOS レジストリを持ちます。これはCOS ハッシュ値から COS エントリ構造体へのマップであり、 Cross-Origin Storage を使用するすべてのオリジンで共有されます。 COS エントリには次の項目があります：

hash

COS ハッシュ。

bytes

Null、またはバイト列であり、そのhashのalgorithm によるダイジェストが、hashのvalueと等しいものです。ライターが 検証と 保存を完了するまでは Null です。

state

"pending" または "written" のいずれかです。エントリは "pending" で開始し、bytesが最初に設定された時点で、 正確に一度だけ "written" になります。

保留中ライター数

初期値が 0 の非負整数で、未完了のライター、すなわちcreate リクエストを完了することによって返されたFileSystemFileHandle ハンドルのうち、その終了時の書き込みが まだ確定していないものを数えます。これは検証して保存する際に、失敗した書き込みを安全に クリーンアップできるかを判断するためだけに使用されます。§ 3.3 ファイルの作成と書き込みを参照してください。

origins

オリジンのリストで、 Public Hash Listとは独立に、明示的なクロスオリジン読み取りアクセスを許可されたものです。初期状態では空であり、 増加することしかありません。これは、誰がエントリを読み取れるかを決定する 3 つの独立かつ加算的な許可の 1 つで、他の 2 つは、その保存元オリジン（常に読み取り可能で、それらと 同一サイトのオリジンも含む）と、グローバルに 開示可能であることです。

注: origins が明示的な空の リスト （origins: []）である書き込みは、origins を省略した書き込みと正確に同じものを許可します。すなわち、エントリの 保存元オリジンと、それらと同一サイトのオリジンであり、これはすべてのエントリが持つ 基本許可です（COS 開示を決定するを参照）。上限を 適用すると、 空のリストは null になるため、どちらの書き込みも残りの create リクエストを完了する処理に同じ状態で到達します。明示的なリストは受信者を追加することしかなく、 ライター自身のサイトからエントリを隠すことはありません。

グローバルに開示可能

初期値が false の真偽値であり、エントリが グローバル（"*"）可用性を要求して書き込まれたかどうかを記録します。true の場合、そのエントリは、 § 8.3 可用性ゲーティングを通過する要求を行った任意のオリジン、 すなわちhashがPHL 上にあり、かつ GREASE’ing によって抑制されないオリジンから読み取り可能です。一度設定されると、true のままです。

注: これはoriginsとは別の項目であり、 後からグローバル可用性が要求された場合に、既存の明示的な origins リストの上に "*" の許可を追加できるようにしています。 この 2 つを 1 つのフィールドにまとめると、バイト列を提供したライターが リストスコープのエントリを "*" スコープに変更できてしまいます。§ 8.3 可用性ゲーティングは "*" 許可にのみ適用されるため、それまでリストによってエントリを読み取れていたオリジンが、 hashが PHL 上にない場合に "NotFoundError" を受け取り始めることになります。許可を独立して保持することで、すべての可視性変更が厳密に加算的となり、 アップグレード可能だがダウングレード不可能という要件を満たします。

保存元オリジン

このエントリのバイト列の書き込みを少なくとも一度正常に完了したオリジンの集合です。ページの読み込みをまたいで保持され、時間の経過とともに 増加し、§ 5.2 退避で説明する場合を除いて縮小しません。保存元オリジンに含まれるオリジンは、 originsや、 エントリのhashがPublic Hash List (PHL) 上にあるかどうかに関係なく、 requestFileHandle() によって常にそのエントリのハンドルを取得できます。 § 3.5.1 元の保存者によるアクセスを参照してください。

ユーザーエージェントには、Cross-Origin Storage キューが関連付けられます。これは 新しい並列キューを開始する結果です。COS レジストリに対するすべての操作は このキューにエンキューされなければならず、それによって エンキューされた 順序で実行され、相互に割り込むことがありません。

2.3. Public Hash List

あるハッシュが Cross-Origin Storage に存在することを確認する行為自体が、ユーザーの閲覧履歴に関する情報を 漏えいさせる可能性があります（§ 8.2 クロスサイトプロービングを参照）。これは特にグローバル 許可に関するリスクです。エントリの明示的なorigins リストと、各エントリが持つ同一サイトの基本許可は、 すでに保存元オリジンによる明示的な選択によって開示範囲が制限されています。一方で、エントリをグローバルに開示可能にすると、Web 上の任意の オリジンに公開される可能性があります。この 特定のリスクを制限するため、グローバルに開示可能なリソースは、その許可を通じて、 保存元オリジンの外部にあるオリジンに対して、ハッシュが追加の独立した ゲートを通過した場合にのみ開示可能です。そのゲートとは、Public Hash List （PHL）への登録であり、これはベンダー中立で、 実装定義のCOS ハッシュ 値の許可リストです。ハッシュは、k-匿名性に類似した人気度の基準 （たとえば、ある最小数の独立したオリジンで、バイト単位で同一のものとして出現すること）を満たした場合にのみ Public Hash List に登録されるため、共有キャッシュに存在することを確認しても、特定の ユーザーについて有益な情報にはなりません。

COS ハッシュ hashは、 hashがユーザーエージェントの現在のPublic Hash Listスナップショットのエントリと等しい場合、 Public Hash List 上にあるものとします。

Public Hash List の取得プロトコル、 更新頻度、データ形式、人気度しきい値、およびガバナンスは、この仕様の付随成果物として詳細に設計されます。 これは、[URL] Standard に付随するデータファイルである public suffix list と同様の考え方です。このリポジトリの Public Hash List explainerを参照してください。この設計では、 Public Suffix List のベンダー横断かつローリングリリースの先例をモデルとして WHATWG によるガバナンスを提案し、 独立に裏付けられた普及度に基づく登録基準を設けています。 これは上記の k-匿名性に類似した基準を具体化したもので、ハッシュを登録する際にオフラインで一度だけ適用されるため、 ユーザーエージェントがクエリごとに繰り返すことはありません。これらはいずれも、 この提案の外部ではまだ確立されていません。リスト自体の初期の非規範的なコードプロトタイプは 現時点ではこのリポジトリの public-hash-list/implementation/にあります。専用の ベンダー横断リポジトリは、引き続き PHL explainer で説明されているガバナンス上の目標です。この 仕様が依存するのは、ハッシュがPHL 上にあるかどうかだけなので、 リストの取得機構、ガバナンスモデル、またはその他の設計がどのように発展しても仕様は正しく機能します。

3. CrossOriginStorageManager インターフェイス

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

各 Navigator および WorkerNavigator オブジェクトには、関連付けられた CrossOriginStorageManager オブジェクトがあります。crossOriginStorage getter の ステップは、thisに関連付けられたCrossOriginStorageManager を返すことです。

各 CrossOriginStorageManager オブジェクトには関連付けられたオリジンがあり、オブジェクトの作成時に thisの関連設定オブジェクトのオリジンに設定されます。

注: スクリプト自体に関する情報とは独立に、関連設定オブジェクトからオリジンを取得することには、worker に関して明記すべき結果があります。 blob: URL から作成された worker は、それを作成したコンテキストのオリジンを持つため、そのオリジンの Cross-Origin Storage ビューを完全に共有します。このような worker が書き込んだものは作成元ページが読み戻せ、 ページが保存したものは worker が読み取れます。blob: URL はそれ自体のオリジンではなく、 それを revoke しても worker はそのビューから切り離されません。data: URL から作成された worker は 不透明オリジンを持ちます。この仕様では現在、 呼び出し元オリジンが不透明である場合にrequestFileHandle() が何を行うかを定義していません。 不透明オリジンに関するCOS リクエストを検証する規則は、 呼び出し元が指定するオリジンにのみ適用されます。不透明オリジンには、 保存元 オリジンや同一 サイト比較のキーとして使用できる安定した識別情報がないため、 それに付与できる意味のある権限はありません。

3.1. requestFileHandle() メソッド

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

hashによって識別されるファイルが Cross-Origin Storage に存在し、かつ呼び出し元オリジンに 開示可能である場合、そのファイルのハンドルを返します。それ以外の場合は "NotFoundError" DOMException で拒否します。 "NotFoundError" は、ファイルが Cross-Origin Storage に 物理的に存在しないことを証明するものではありません。§ 8.3 可用性ゲーティングを参照してください。呼び出し元は これを「代わりにネットワークから取得する」として扱えます。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

hashによって識別されるファイルを Cross-Origin Storage に書き込むために使用できるハンドルを返し、まだエントリが存在しない場合は新しいエントリを作成します。 デフォルトでは同一サイトのオリジンに制限されます。 エントリがすでに存在していたかどうかに関係なく、呼び出し元はハンドルの createWritable() メソッドを介して完全なファイル内容を書き込む必要があります。 ユーザーエージェントはその時点で、書き込まれたバイト列のハッシュが hash になることを検証し、 そうでない場合は "DataError" DOMException で拒否します。この要件により、 オリジンが create リクエストを hash がすでに存在するかどうかを調べるオラクルとして使用することを防ぎます。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

上記と同様ですが、さらに書き込み後、hashに対する要求が § 8.3 可用性ゲーティングを通過する任意のオリジンに対して エントリを開示可能にします。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

上記と同様ですが、開示を列挙されたオリジンだけに制限します（呼び出し元 オリジン、およびすでに保存元オリジンに含まれるオリジンに加えて）。

requestFileHandle(hash, options) メソッドの ステップは次のとおりです：

  1. resultを新しい promiseとします。

  2. realmをthisの関連 Realmとします。

  3. globalをthisの関連グローバルオブジェクトとします。

  4. originをthisに関連付けられたオリジンとします。

  5. globalを与えてCross-Origin Storage 権限を確認する処理を実行した結果が false の場合、次を行います：

    1. globalを与え、DOM 操作タスクソース上でグローバルタスクをキューに入れ、 resultを "NotAllowedError" DOMException で拒否します。

    2. resultを返します。

  6. validationFailureを、hashおよび optionsを与えてCOS リクエストを検証する処理を実行した結果とします。

  7. validationFailureが null でない場合：

    1. globalを与え、DOM 操作タスクソース上でグローバルタスクをキューに入れ、 resultを validationFailure で拒否します。

    2. resultを返します。

  8. 次のステップを Cross-Origin Storage キューにエンキューします：

    1. options["create"] が true の場合：

      1. result、hash、options、global、 realmを与えてcreate リクエストを完了する処理を実行します。

    2. それ以外の場合：

      1. result、hash、origin、global、 realmを与えてread リクエストを完了する処理を実行します。

  9. resultを返します。

CrossOriginStorageRequestFileHandleHash hash と CrossOriginStorageRequestFileHandleOptions optionsを与えてCOS リクエストを検証するには、null または TypeErrorを返します：

  1. hash["algorithm"] が [WEBCRYPTO] によって認識されるハッシュアルゴリズム 名でない場合、新しい TypeErrorを返します。

3.3. ファイルの作成と書き込み

create リクエストを完了する処理によって作成されたFileSystemFileHandle には、関連付けられた 要求されたオリジンがあります。これは、 ハンドルへの書き込みが正常に完了した後に検証して保存する処理が、エントリのoriginsをアップグレードしようとする値です。

注: これは意図的に各ハンドルのプロパティです。create リクエストは、エントリがすでに存在し、すでに "written" であるかどうかに関係なくハンドルを返します （create リクエストを完了するを参照）。したがってエントリ単位の規則では、任意のオリジンが requestFileHandle() を create: true として呼び出し、自身が一度も書き込んでいないエントリを即座に読み取ることができ、 origins、 PHL 登録、または GREASE’ingを満たすことなく内容を知ることができてしまいます。この 仕様のすべての開示制御は読み取り経路に適用されるため、エントリ単位でゲーティングすると create リクエストによって それらすべてを回避できてしまいます。呼び出し元にまず正しいバイト列の提供を要求することで、 create によって取得したハンドルを通じた正常な読み取りは、呼び出し元がすでに持っていなかった情報を何も開示しません。

  1. computedValueを、entryのalgorithmで指定された アルゴリズムを用いて [WEBCRYPTO] に従って計算した、 bytesの小文字 16 進ダイジェストとします。

    1. 終了操作の promise を "DataError" DOMException で拒否します。

    2. 次のステップを Cross-Origin Storage キューにエンキューします：

      1. entryの保留中ライター数を 1 減らします。

      2. entryのstateが "pending" で、 entryの 保留中ライター数が 0 の場合、 entryのhashを COS レジストリから削除します。

COS エントリを指す FileSystemFileHandle 上で呼び出されたcreateWritable() は、keepExistingData の値や、 対象エントリのstateに関係なく、内容が空の状態から始まるFileSystemWritableFileStream を生成しなければなりません。

注: [FS]では通常、keepExistingData は既存ファイルの内容で ストリームを初期化するものとして定義されています。ここでそれを認めると、呼び出し元が一度も保持していなかったバイト列の 保存元オリジンになれてしまいます。create リクエストはエントリが すでに存在するかどうかに関係なくハンドルを返すため、呼び出し元は別のオリジンが保存したハッシュに対して writable を開き、 何も書かずに閉じ、引き継がれたバイト列のハッシュが要求値と一致するようにできます。そうすると origins、Public Hash List、および GREASE’ingが一度も確認されないまま読み取りアクセスが与えられます。これは、個別には許可された 2 つの操作を 組み合わせて作られた可用性 ゲーティング回避です。これと同じ理由により、 検証して保存する処理は、 すべての create リクエストで完全な内容を要求します。

注: したがって何も書かずに閉じられた writable は 空のバイト列を保持します。それは呼び出し元が必要とするどのエントリの要求値にも ハッシュされないため、検証して保存する処理は 他の不一致と同様に "DataError" DOMException で拒否します。この場合に 代わりにストレージまたは I/O 障害を報告する実装は、検証結果を無関係なエラーの背後に隠すことになります。

File System Standard [FS]には、依存する 仕様が FileSystemWritableFileStreamの 終了ステップに追加の書き込みごとの検証を差し込むための拡張点がまだ定義されていません。 そのようなフックが存在するまでは、この節で必要な動作を直接説明します。将来の改訂では[FS]と正式に統合される予定です。

      1. entryのbytesを bytesに設定します。

      2. entryのstateを "written" に設定します。

      注: 同じハッシュに対する requestFileHandle() ライターがまだ処理中の場合、ここでエントリが "pending" であることがあります。その保留中ライター数は変更されないため、 そのライター自身の検証して保存する処理は通常どおり完了します。その バイト列は同じ値にハッシュされるため、再度保存しても何も変わりません。

    4. まだ存在しない場合、originを entryの保存元オリジンに追加します。

    5. entryと requestedOriginsを与えてリソース可視性をアップグレードする処理を実行します。

注: 検証して保存する処理と同様に、 エントリがすでに "written" である場合も含め、保存では常に 完全なバイト列が必要であるため、以前からの存在について何も開示しません。ネットワーク取得前に統合側が行う 検索は読み取りであり、可用性ゲーティングと § 8.2 クロスサイトプロービングの考慮事項の対象です。

3.5. リソース可視性のアップグレード

COS エントリの可視性は アップグレードできますが、ダウングレードすることはできません。

COS エントリ entryと、"*"、リスト状の オリジン、または null の requestedOriginsを与えて リソース可視性を アップグレードするには：

  1. requestedOriginsが null の場合、返します。

    注: origins を省略すると同一サイトの 可用性のみを要求します。これはすべてのエントリがすでに持っています（COS 開示を決定するを参照）ので、 追加するものはありません。

  2. requestedOriginsが "*" の場合：

    1. entryのグローバルに開示可能を true に設定します。

    2. 返します。

    注: これはグローバル許可を追加しますが、 entryのoriginsには触れません。すでに明示的なorigins リストを持つエントリは それを維持するため、そのリスト上のすべてのオリジンは、エントリが グローバルに開示可能になった後も、 PHLに依存しないアクセスを維持します。これが 2 つの許可を別々に 保存する理由の核心です。グローバルに開示可能を参照してください。

  3. requestedOriginsの各 candidateOriginについて反復します：

    1. entryのoriginsが candidateOriginを含む場合、 続行します。

    2. entryのoriginsのサイズが ユーザーエージェントの 最大 origins リスト長に等しい場合、 break します。

      注: 残りの candidateOrigin値はこのアップグレードから暗黙に破棄されます。書き込み自体はすでに成功しており、 ユーザーエージェントはエントリの origins リストが上限に達していることを コンソール警告として記録することが想定されています。

    3. candidateOriginを entryのoriginsに追加します。

注: アップグレードはoriginsへの追加、またはグローバルに開示可能を true に設定することしか行いません。リストを要求するライターは、すでに グローバルに開示可能なエントリも、そうでないものと同様に 可視性を広げます。これは 2 つの許可が 独立しているためです。新たに列挙されたオリジンは、"*" 許可が引き続き有効な間も PHLに依存しないアクセスを得ます。

注: 元の保存者以外を含む任意のサイトは、 エントリのoriginsを広げられます。 ただし、そのエントリのhashになるバイト列も提供する必要があります。これは意図的です。 あるハッシュについて正しいバイト列をすでに持つ任意のサイトは、構造上、そのハッシュが何を表すかについて 元の保存者と同程度に権威を持つためです。

3.5.1. 元の保存者によるアクセス

COS エントリの書き込みを正常に完了したオリジン（つまり、エントリの保存元オリジンに含まれる 任意のオリジン）は、その後いつでも requestFileHandle() によってそのハンドルを取得できます。これは、エントリの origins値や、 そのhashがPHL 上にあるかどうかに依存しません。 これは、オリジンが自身で保存したものには常にアクセスできる Cache API のモデルを反映しています。

4. Cross-Origin Storage ファイルシステム

Cross-Origin Storage ファイルシステムは、 各オリジンのバケットファイルシステムまたはローカルファイルシステムアクセスのルートとは異なる ファイルシステムルートであり、その エントリはCOS レジストリのCOS エントリ項目と 1 対 1 で対応します。

Cross-Origin Storage ファイルシステムは [FS]の通常の呼び出しごとの 権限確認モデルを使用しません。そこから取得されるすべてのFileSystemFileHandle はスクリプトに返される前に、すでに § 3.2 ファイルの読み取りまたは§ 3.3 ファイルの作成と 書き込みによって完全に認可されているため、そのようなハンドル上で getFile() または createWritable() を呼び出しても 追加の権限プロンプトは発生しません。

そのため、このようなハンドル上の queryPermission() および requestPermission()は、 プロンプトが表示されることがないため "prompt" を報告してはなりません。create リクエストによって取得されていないハンドルに write モードを指定した場合は "denied" を報告し、それ以外の場合は "granted" を報告しなければなりません。

注: 書き込みは、ハンドルが実際に 持たない可能性のある唯一の機能です。create リクエストだけが 書き込み可能なハンドルを返すため、それ以外のハンドルについて write モードを "granted" と報告すると、 createWritable() が拒否する機能を持っていると主張することになります。読み取りは "granted" のままです。読み取り可能なハンドルを保持する呼び出し元は、それを通じて読み取れるためです。 要求によっていずれの回答も変更することはできません。表示するプロンプトもなく、 許可を記録できる状態もないためです。

COS エントリを指し、 may readが false のFileSystemFileHandle 上でgetFile() を呼び出すと、 "NotAllowedError" DOMException で拒否されなければなりません。 これは 2 つの異なる場合を対象とします：

  • create リクエストから得られたハンドルで、そのエントリがまだ "pending" である場合。同じハッシュに対する並行した requestFileHandle() 呼び出しが拒否されるのと同じ理由です（ § 3.2 ファイルの読み取りを参照）。呼び出し元が、まだ検証されていないプレースホルダーを ファイルの実際の内容であるかのように観察できてはなりません。

  • ある別のオリジンがすでに書き込んだエントリに対する create リクエストから得られたハンドル。 エントリのstateは "written" ですが、この呼び出し元はバイト列を提供しておらず、 可用性ゲーティングも通過していないため、 エントリについて、存在するかどうかさえ含め、何も知ることができてはなりません。

ハンドルのmay readが true になると、そのハンドル上で呼び出されたgetFile() は、その対象エントリのbytesを内容として持つFile を返します。これはまさに、[FS]が そのバイト列をバイナリデータとして持つファイル エントリについてすでに定義している動作です。

COS エントリを指すFileSystemFileHandle はファイルシステムロケーターを持ち、その パスは 単一の文字列、すなわちエントリの COS ハッシュのvalueを含むリストであり、 そのルートは Cross-Origin Storage ファイルシステムです。

注: [FS]は、name をハンドルのロケーターのパスの最後の構成要素として定義しているため、これによってname も決まります。 これはハッシュです。エントリ自体に名前はなく、ハッシュが唯一の識別情報であるため、 空文字列では失われる情報をこれによって報告できます。

エントリには名前も格納ディレクトリもないため、[FS]の構造的な機能の大部分には 対象がありません。例外は同一性であり、それはコンテンツアドレス型エントリが常に答えられる唯一の問いです。 COS レジストリは 1 つのCOS ハッシュにつき 最大 1 つのCOS エントリしか保持しないため、2 つの ハンドルが同じエントリを指すのは、それらのハッシュが等しい場合に限ります。

COS エントリを指すFileSystemFileHandle 上で、同じくCOS エントリを指し、 同じオリジンによって取得された引数を指定して isSameEntry() を呼び出した場合、2 つのハンドルのCOS ハッシュ項目が等しければ true を、 それ以外の場合は false を返さなければなりません。

注: これを拒否すると、ユーザーエージェントがすでに 持っている情報を捨てることになります。

呼び出し元オリジンが取得していない引数、または Cross-Origin Storage ファイルシステム以外のファイルシステムを指す引数を指定して isSameEntry() を呼び出した場合、拒否しなければなりません。

注: この場合に false を返すと、 2 つのハンドルが異なるエントリを指していると主張することになり、 これは呼び出し元オリジンに検査する権利がないハンドルについての主張になります。拒否は単に、 比較を実行できなかったことだけを示します。

COS エントリを指す FileSystemFileHandle 上で move() または remove() を呼び出した場合、 "NotAllowedError" DOMException で拒否し、エントリを変更しないままにしなければなりません。

注: エントリはその保存元 オリジンに含まれるすべてのオリジンで共有されるため、 削除を許可すると、あるサイトが他サイトの依存するデータを破壊できてしまいます。削除は 退避とユーザー自身のストレージ制御に属します。エントリはCOS ハッシュによって名付けられ、格納ディレクトリを持たないため、 名前変更や親の変更にも対象がありません。

注: 執筆時点では、どちらのメソッドも[FS]または File System Access API で定義されていません （WICG/file-system-access#214）。 したがってエラー名は、[FS]が エントリを削除するために定義している操作 removeEntry() に従います。これは readwrite アクセスが 許可されていない場合、アクセス結果のエラー名で拒否します。ここでは拒否することが正しい動作です。 操作自体には意味がありますが、許可されていないためです。

createSyncAccessHandle() についてここで規則を追加する必要はありません。そのステップは、ハンドルがバケットファイルシステムにない場合、 "InvalidStateError" DOMException で拒否します。そしてCross-Origin Storage ファイルシステムは 各オリジンのものとは異なるファイルシステムルートであるため、 [FS]がすでに 拒否とその名前の両方を決定しています。

注: これは、この仕様が独立に望む結果でもあります。 FileSystemSyncAccessHandle は呼び出し元に書き込み可能なファイルディスクリプターを渡すため、 エントリが保存されているCOS ハッシュに対応したbytesを その下から変更できてしまい、 エントリの開示先となる他のすべてのオリジンも同じバイト列を読み取ることになります。

4.1. ハンドルの転送

FileSystemFileHandle はシリアル化可能オブジェクトです [FS]。そのため、COS エントリを指すものは、 たとえば postMessage(message, options) によって別の環境設定オブジェクトに渡せます。 これは、requestFileHandle() に加えて、このようなハンドルを得る 2 つ目の方法であるため、 ここでも制約されます。

シリアル化ステップで、COS エントリを指す FileSystemFileHandle に対し、valueと serializedが与えられた場合、さらに次を行います：

  1. serialized.[[COSOrigin]]を valueのCOS originに設定します。

  2. serialized.[[COSMayRead]]を valueのmay readに設定します。

デシリアル化ステップで、serialized、 valueおよび realmが与えられた場合、さらに次を行います：

  1. serialized.[[COSOrigin]]が realmの 環境設定オブジェクトのオリジンと同一オリジンでない場合、 "DataCloneError" DOMException をスローします。

  2. valueのCOS originを serialized.[[COSOrigin]]に設定します。

  3. valueのmay readを serialized.[[COSMayRead]]に設定します。

注: 同一 オリジン確認がなければ、転送によってこの仕様のすべての開示制御を一度に無効化できてしまいます。 may readが true の ハンドルは、すでにそのハンドルを要求したオリジンについて 可用性ゲーティングを適用する処理を通過しています。これを別の オリジンに投稿すると、そのオリジンについてorigins、 PHL 登録、または GREASE’ingを一度も評価することなく、エントリのバイト列を渡してしまいます。 これは File System Standard の既存のハンドルの扱いと一致します。そこでもハンドルは 同一オリジンの受信者に対してのみ有用です。

注: may readは ハンドルとともに移動するため、まだ書き込みが完了していない create リクエストのハンドルは転送後も読み取り不能のままで、 read リクエストのハンドルは再度ゲーティングされることなく読み取り可能なままです。到着時に再ゲーティングすると、 呼び出し元が同じハンドルを繰り返し転送することによって可用性をプローブできてしまいます。

5. ストレージ管理

5.1. ストレージ制限

ユーザーエージェントは、単一のオリジンが他のオリジンのエントリを退避させようとして キャッシュを埋め尽くすことを防ぐため、オリジンが正常な書き込みを通じて COS レジストリに 提供できる総バイト数に上限を課さなければなりません。具体的な上限は 実装定義です。オリジンの書き込みによってその 上限を超える場合、ユーザーエージェントは "QuotaExceededError" DOMException で書き込みを拒否し、 コンソールに警告を記録するべきです。

注: エントリはコンテンツアドレス可能であるため、 オリジンが同じハッシュの下で同じ バイト列を繰り返し書き込んでも、最初に正常に書き込んだとき以外は追加のクォータを消費しません。 § 2.2 COS エントリを参照してください。

ユーザーエージェントには、実装定義の最大 origins リスト長もあります。 これは単一のorigins リストに含められるオリジンの数を制限する正の整数です。 この上限は、リストが最初に与えられるとき （COS リクエストを検証するを参照）と、 その後既存エントリにマージされるとき （リソース可視性をアップグレードするを参照）の両方で適用されるため、 単一の呼び出しでも、時間をかけた多数の呼び出しの累積効果でも、エントリのoriginsを 無制限に増やせません。メモリ使用量を制限するだけでなく、これはオリジンのリストが "*" の未宣言の代替として使用されることも防ぎます。§ 8.2 クロスサイトプロービングを参照してください。

この上限超過は、2 つの場所で異なる方法で処理されます。2 つの呼び出しが 操作上まったく異なる時点で発生するためです：

  • COS リクエストを検証する処理では、ファイルの取得、ハッシュ計算、または 書き込みが行われる前に上限を確認します。上限を超えた呼び出し元は即座に "TypeError" を受け取り、それ以外は何も行われません。これは他の不正な origins 値と同じ扱いです。

  • リソース可視性をアップグレードする処理では、 この上限に達するのは、別々の独立した書き込み呼び出しで要求されたオリジンの累積効果による場合に限られます。 それは長期間にわたり、互いに無関係なオリジンによって行われる可能性もあり、この呼び出しのバイト列がすでに ハッシュ計算、検証、永続的な保存を完了した後でのみ確認されます。その時点で書き込みを拒否すると、 無関係な管理上の上限のために、正常で、すでに検証され、場合によっては非常に大きい書き込みを捨てることになり、 しかも単一の呼び出し元の誤りに帰属させることもできません。そのため書き込み自体は成功させたままにし、 容量を超えるオリジンだけをoriginsから削除し、 コンソール警告を出します。これは既存の より寛容な範囲からより制限された範囲への要求の扱いを反映しています。 完全に満たせないオリジン要求は暗黙に上限で切られ、 それを伴う書き込み自体は成功します。この仕様の他の箇所の§ 8.3 可用性ゲーティングと 一貫して、呼び出し元には、要求したオリジンが実際に追加されたかどうかを 後から確実に確認する方法はありません。そのオリジンとして後続のrequestFileHandle() 呼び出しを行っても、 そのオリジンが追加されていたとしても失敗する可能性があります （たとえばエントリが退避された場合やユーザーエージェントが要求を制限した場合）。したがって、 その結果もどちらかを確認するものとして解釈してはなりません。

5.2. 退避

この節は非規範的です。

ストレージ容量が逼迫している場合、ユーザーエージェントはCOS レジストリからエントリを退避してもかまいません。 たとえば、各エントリを最後にアクセスした保存元オリジンに基づく LRU ポリシーを使用できます。ユーザーエージェントは、どのファイルが保存されているか、どのオリジンが各ファイルに アクセスしたかをユーザーが確認でき、手動で エントリを削除したり、すべての Cross-Origin Storage データを消去したりできる設定 UI を提供することが想定されています。

ユーザーがオリジンのサイトデータを消去した場合、ユーザーエージェントはそのオリジンが含まれるすべての 保存元 オリジン集合からそのオリジンを削除するべきです。その削除後にCOS エントリの 保存元 オリジンが空になった場合、ユーザーエージェントはそのエントリを削除対象として検討してもかまいません。

5.3. 手動で追加されたエントリ

この節は非規範的です。

上記の設定 UI では、ユーザーがすでにディスク上に持っているファイル （たとえば、Web サイトとは無関係にダウンロードした AI モデル）を、 スクリプトが一度もrequestFileHandle() を呼び出すことなく Cross-Origin Storage に直接追加できるようにしてもかまいません。このようなエントリには、 書き込みを帰属させる要求元オリジンがないため、命令型 API だけでは答えられない 2 つの問題が生じます：

  • § 3.5.1 元の保存者によるアクセスの目的上、 元の保存者は誰でしょうか。誰もいません。エントリの保存元オリジンは空で始まります。 したがって、どのオリジンも 通常の可用性ゲーティングおよびorigins確認を免除されません。 これは、実際にバイト列を書き込んだオリジンがないため、正しい結果です。

  • そのようなエントリは、origins を省略した通常の書き込みと同様に、同一サイトのみに制限されるべきでしょうか。いいえ。 「同一サイト」は要求元オリジンとの関係でのみ意味を持ちますが、手動追加には要求元オリジンがないため、 「同一サイト」が意味するサイトが存在しません。ユーザーエージェントはそのようなエントリを グローバルに 開示可能にし、 明示的なorigins リストは空のままにすることが想定されています。 ファイルを手動でシードする目的 （ユーザーがまだ訪問していないサイトでも、ユーザーがディスク上にすでに持っているファイルを再利用できるようにすること） は、他のオリジンが実際にそのファイルを発見できる場合にのみ達成されるためです。 ユーザーエージェントの設定 UI では、ユーザーがより狭いスコープを選択できるようにしてもかまいません。

この方法で追加された後、stateが "written" のエントリは、それ以外の点では、 Web サイトがrequestFileHandle() を介して書き込んだものと区別されません。同じ 可用性ゲーティングおよび可視性 アップグレード規則が、同じ許可を持つ他のエントリとまったく同様に適用されます。 これには、エントリが グローバルに開示可能になった場合の PHL 上にあるかどうかの確認も含まれます。 これは手動追加のデフォルトです。

5.4. 来歴メタデータ

この節は非規範的です。

COS エントリは、そのバイト列が どこから来たかについて意図的に何も記録しません。同一性は hashだけで決まります。 同じバイト列は、それを保存したオリジンの数や 取得元 URL の数に関係なく同じエントリです（§ 2.2 COS エントリを参照）。 URL はある 1 人の ライターによる取得のプロパティであるため、複数のオリジンによって書き込まれたエントリについて 1 つを選ぶ非恣意的な方法はありません。また、バイト列のように検証できません （§ 8.1 リソース完全性を参照）。 さらに、パスやクエリ文字列は特定の文書、アカウント、セッションを識別できるため、 オリジンの値よりも、ユーザーの閲覧についてはるかに多くの情報を持ちます。 それをエントリに記録すると、originsと§ 8.3 可用性 ゲーティングが課す開示制限を迂回する、高エントロピーのシグナル経路を作ることになります。

それを求める動機自体は現実的です。§ 5.2 退避で説明した設定 UI で 数ギガバイトのファイルを見ているユーザーも、requestFileHandle() 呼び出しがミスした理由をデバッグしている開発者も、ファイルが どこから来たのか知りたいでしょう。ユーザーエージェントは、エントリと並べて 実装非公開の来歴記録 （たとえば、各保存元オリジンが バイト列を取得した URL とその時刻）を保持することでそれを提供してもかまいません。ただし、 その記録はエントリの外部に保持されるユーザーエージェント状態として扱わなければなりません：

  • スクリプトには決して公開されません。この仕様にはそれを開示するものはなく、後から追加されるものも 開示するべきではありません。requestFileHandle() も、それが返す FileSystemFileHandle も、このような記録が存在するかどうか、ましてその内容を明らかにするべきではありません。 特に、要求元オリジンは、自身が生成していない記録を観察できてはなりません。

  • それは、信頼された非 Web サーフェス、すなわちユーザーエージェント自身の設定およびストレージ検査 UI、 開発者ツール、および（ユーザーエージェントに拡張機能プラットフォームがある場合） 明示的にユーザーから付与された権限によって制御される拡張 API を通じてのみ表示されます。 これは閲覧履歴を公開する他の API と同じ扱いです。検討されている拡張サーフェスについては、 このリポジトリの ブラウザー拡張統合ポイントの解説を参照してください。

  • これは未検証であり、そのように提示されます。その中の URL は、バイト列を書き込んだオリジンによる主張です。 内容を保証するのはhashだけです（§ 8.1 リソース完全性を参照）。2 つのオリジンが同じエントリについて異なる URL を 記録することがあり、そのどちらかが不正確または意図的に誤解を招くものである可能性があります。

  • その寿命はエントリ、およびそれが帰属するオリジンと同じです。エントリが退避または削除されたときに 破棄され、オリジンに帰属する部分は、そのオリジンが保存元オリジンから削除されたとき、 ユーザーがその オリジンのサイトデータを消去した場合を含め、破棄されます（§ 5.2 退避を参照）。

このような記録はコンテンツから見えないため、ユーザーエージェントがそれを保持するかどうか、および どの程度保持するかは完全に実装に委ねられます。この仕様のいかなる部分もそれに依存せず、その 存在または不在をサイトが検出することはできません。

6. Permissions Policy との統合

この仕様は、文字列 "cross-origin-storage" で識別される ポリシー制御対象機能 [permissions-policy]を定義します。 そのデフォルト許可リストは self です。

[permissions-policy]は、Documentに対する使用を許可されているを定義しますが、 CrossOriginStorageManager は独自の Document を持たないWorkerGlobalScope にも公開されます。そのため確認は呼び出し元のグローバルオブジェクトについて記述されます。 worker global はそれを所有するDocument へ推移的に解決され、そのすべてがこの機能を許可しなければなりません。

グローバルオブジェクト globalを与えて Cross-Origin Storage 権限を確認するには、 真偽値を返します：

  1. globalが Window オブジェクトの場合：

    1. documentを globalの関連付けられた Documentとします。

    2. documentが null の場合、false を返します。

    3. documentが "cross-origin-storage" ポリシー制御対象機能の使用を許可されていない場合、 false を返します。

    4. true を返します。

  2. globalが WorkerGlobalScope オブジェクトの場合：

    1. ownersを globalの所有者集合とします。

    2. ownersが空 である場合、false を返します。

    3. ownersの各 ownerについて反復します：

      1. ownerが Document であり、かつ "cross-origin-storage" ポリシー制御対象機能の使用を許可されていない場合、 false を返します。

      2. ownerが WorkerGlobalScope オブジェクトであり、ownerを与えて Cross-Origin Storage 権限を確認する処理を実行した結果が false の場合、false を返します。

    4. true を返します。

  3. false を返します。

このアルゴリズムが false を返すグローバルオブジェクトから行われるすべての requestFileHandle() 呼び出しは、ハッシュ検証、レジストリ検索、または書き込みが 行われる前に "NotAllowedError" DOMException で拒否されます。

注: 所有者集合を通じて解決することで、この機能が 名目上だけのオプトアウトになることを防ぎます。blob: URL から作成された worker は作成元ページの オリジンで動作し、そのページの Cross-Origin Storage ビューを完全に共有します （§ 3 CrossOriginStorageManager インターフェイスを参照）。 したがって、グローバル自身の Document だけを参照する確認はすべての worker で自動的に満たされてしまい、呼び出しを new Worker(URL.createObjectURL(&hellip;))に移動するだけで、 他に何も変更せずに cross-origin-storage=()ポリシーから逃れられてしまいます。

注: ServiceWorkerGlobalScopeの 所有者集合は空であるため、この アルゴリズムはそこで false を返します。これは所有者集合の性質から導かれます。それは worker が作成されたときに設定され、その worker がまだ積極的に必要かどうかを判断するために参照される 生存関係です。service worker は意図的にどのDocument ともそのような関係を持ちません。その登録は永続化され、ユーザーエージェントはイベントに応じてグローバルを開始し、 service worker clientがまったくない状態でも実行できます。 そのため、register() を呼び出した client は登録時には分かりますが、 グローバルが実行されるころには通常すでに存在せず、1 つの実行中 service worker は、ポリシーが一致するとは限らない 多数の client にサービスを提供します。

注: service worker を対象にするにはキャプチャされたポリシーが必要であり、 その作業は [permissions-policy]と[service-workers]に属します。 この仕様が望ましいと考える形は、service worker のポリシーを 自身のスクリプト response 上の Permissions-Policyヘッダーから導出することです。 これは、そのポリシーコンテナーがすでにその response の CSP を保持するのと同様です。これにより オリジン側の制御下にとどまり、更新確認ごとに再評価されます。登録した client のポリシーをスナップショット化すると、 ヘッダーから機能を削除しても登録がたまたま更新されるまで反映されないため、 オプトアウトが古い状態のままになります。そのような モデルが存在するまでは、fail closed がオプトアウト回避に使用できない唯一の答えです。

注: SharedWorkerGlobalScopeの 所有者集合には、異なるポリシーを持つ複数の Document が含まれる可能性があり、worker の存続期間中に所有者が増減します。 すべての所有者がこの機能を許可することを要求すると、1 つの所有者が禁止しただけで shared worker 全体の Cross-Origin Storage が無効になり、2 回の requestFileHandle() 呼び出しの間でも結果が変化する可能性があります。代わりに 1 つの 許容的な所有者だけを必要とすると、この機能を許可する任意の document が、 それを禁止している document の代わりに再度有効化できてしまいます。

7. Cross-Origin-Storage-Allow-Origin ヘッダー

COS エントリのorigins リストが 空でない場合、そのエントリは 書き込み元オリジンが制御しないオリジンにも開示可能です。しかし、そのリストはスクリプト（ origins を通じて）またはマークアップで宣言されます。そして、スクリプトまたはマークアップインジェクションに成功した攻撃者は そのどちらも設定できます。その宣言を、開示されるバイト列を持つオリジンの運営者に結びつけ、 注入されたコンテンツが偽造できない形にするため、この 仕様は、そのような宣言が指定できるオリジンを制限する response ヘッダーを定義します。

Cross-Origin-Storage-Allow-Origin response ヘッダーは COS スコープ上限を持ちます。 これは、書き込みが同一サイトでないorigins リストで指定できる オリジンの集合です。 バイト列を提供する側がヘッダーを送信するため、それは 開示されるバイト列の背後にあるresponseから読み取られます：

  • requestFileHandle() による書き込みでは、バイト列は スクリプトによって生成される可能性があり、そのバイト列自身の取得元responseを持たないことがあります。その場合は、 呼び出し元グローバルオブジェクトのDocument を作成するために使用されたresponse、または worker の場合はそれを所有する Document の response です（COS スコープ上限を取得するを参照）。

  • ホスト統合では、それは、バイト列が保存される取得済みリソースのresponseです （取得したリソースを Cross-Origin Storage に保存するを参照）。これはリソース自身のサーバーであり、 それを読み込むDocument のサーバーとは限りません。

宣言されたリストは 上限との積集合を取られるため （COS スコープ上限を適用するを参照）、上限は宣言を狭めることしかできません。

注: このヘッダーは、バイト列を 提供する側による認可です。そこに指定されたオリジン、 つまり最終的な読み取り側は参照されず、何も送信しません。列挙されたオリジンは後になってから、 他の読み取り側と同様にCOS ハッシュについて requestFileHandle() を呼び出すことで参加します。これは Access-Control-Allow-Origin [FETCH]とは反対方向に動作します。 後者では、リソースを保持するサーバーが、指定されたオリジンによる読み取りをオプトインします。ここでは バイト列の供給者が、後で Cross-Origin Storage からそれを読み取れる相手を制限します。書き込みページに 注入されたコンテンツは供給者の response ヘッダーを設定できないため、その制限を拡張できません。

注: このヘッダーはリスト形式にのみ適用されます。 同一サイトのデフォルトはクロスオリジンの 受信者を指定しないため認可を必要とせず、"*" 形式は読み取り経路で Public Hash Listに対する可用性ゲーティングによって制御されます。 ユーザーごとの秘密値はこれを通過できないため、書き込み時の上限も必要ありません。 "*" にヘッダーを要求すると、Public Hash List がすでに防いでいるもの以外を防ぐことなく、 設定不要のグローバル共有のケースも壊してしまいます。

ヘッダー リスト headersを与えてCOS スコープ上限を解析するには、オリジンの集合を返します：

  1. valueを、headersから "Cross-Origin-Storage-Allow-Origin" を取得、デコード、分割した結果とします。

  2. valueが null の場合、空の集合を返します。

  3. ceilingを空の集合とします。

  4. valueの各 tokenについて反復します：

    1. tokenから先頭と末尾の ASCII 空白を除去します。

    2. tokenが空文字列の場合、続行します。

    3. originを、tokenに対して基本 URL パーサーを実行した結果得られるオリジンとします。

    4. originが failure または不透明オリジンの場合、 空の集合を返します。

      注: これには "*" の tokenも含まれます。これはオリジンとして解析されません。 Cross-Origin-Storage-Allow-Originヘッダーが列挙できるのは有限個の具体的な オリジンだけです。"*" は許可された値ではありません。 「任意のオリジン」という上限を許可すると、 注入されたコンテンツが好きな受信者を宣言でき、ヘッダーの目的全体を無効化できるためです。 無制限の 開示は、"*" のorigins形式を通じてのみ行われ、 これは Public Hash Listによってゲーティングされ、 このヘッダーを参照しません。不正な、または "*" を含むヘッダーは 何も認可せず、ヘッダーが存在しない場合とまったく同じです。失敗時は閉じる動作です。

    5. originを ceilingに追加します。

  5. ceilingを返します。

注: 取得、デコード、分割は U+002C (,) で分割するため、 ヘッダー値内のオリジンは カンマ区切りです。これは Timing-Allow-Origin [RESOURCE-TIMING]および リスト値 HTTP response ヘッダーの一般的な 規則と一致します。一方、兄弟である crossoriginstorage HTML content 属性は、ホスト構文に合わせてスペース区切りです。どちらも同じ オリジンの集合に解決されます。

グローバルオブジェクト globalを与えて COS スコープ上限を取得するには、オリジンの集合を返します：

  1. globalが Window オブジェクトの場合：

    1. documentを globalの関連付けられた Documentとします。

    2. documentが null の場合、空の集合を返します。

    3. documentのCOS スコープ上限を返します。

  2. globalが WorkerGlobalScope オブジェクトの場合：

    1. ownersを globalの所有者集合とします。

    2. ownersが空 である場合、空の集合を返します。

    3. ceilingを null とします。

    4. ownersの各 ownerについて反復します：

      1. ownerCeilingを空の集合とします。

      2. ownerが Document の場合、ownerCeilingを ownerの COS スコープ上限に設定します。

      3. それ以外で、ownerが WorkerGlobalScope オブジェクトの場合、ownerCeilingを ownerを与えてCOS スコープ上限を取得する処理を 実行した結果に設定します。

      4. ceilingが null の場合は ceilingを ownerCeilingに設定し、 それ以外の場合は ceilingを ceilingと ownerCeilingの積集合に設定します。

    5. ceilingを返します。

  3. 空の集合を返します。

リスト状のオリジン requestedOriginsと、 集合状の オリジン ceilingを与えて COS スコープ上限を適用するには、リスト状のオリジンまたは null を返します：

  1. ceilingが含まない各オリジンを requestedOriginsから削除します。

    注: COS スコープ 上限に存在しない受信者は削除されますが、書き込みは引き続き 成功します。これはリソース可視性をアップグレードする処理で 長さ超過分を削除する方法と一致します。ユーザーエージェントは、 削除された各オリジンを示すコンソール警告を記録することが想定されています。

  2. requestedOriginsが空 である場合、null を返します。

    注: メンバーがすべて削除されたリストでは、 書き込みに認可済みの クロスオリジン受信者が残らないため、同一サイトのデフォルトにフォールバックします。バイト列は引き続き 保存され、認可されていない開示だけが差し控えられます。

  3. requestedOriginsを返します。

すべてのDocument にはCOS スコープ上限があります。これはオリジンの集合であり、 document の作成時に、それを作成するために使用されたresponseの ヘッダーリストを与えてCOS スコープ上限を解析する 処理を実行した結果に設定されます。

注: worker の所有者集合全体で積集合を取ることは、 Cross-Origin Storage 権限を確認する処理を反映しています。 オリジンが worker の上限に含まれるのは、推移的にすべての所有元 Document がそれを認可した場合だけです。blob: worker は作成元ページの オリジンと Cross-Origin Storage ビューを完全に共有するため （§ 3 CrossOriginStorageManager インターフェイスを参照）、 worker 自身だけを参照する上限は すべての worker で空になり、リストスコープの書き込みを new Worker(URL.createObjectURL(&hellip;))に移動すると、ページが認可した受信者が削除されてしまいます。 所有者の上限の積集合を取ることで、いずれか 1 つの 所有者に拡張を許すことなく、その認可を維持できます。

Documentの COS スコープ上限をそのresponseから 設定するには、 [HTML]の document 作成ステップにフックが必要です。これは、[permissions-policy]および[CSP]が response 処理時に設定される方法と同様です。そのフックが存在するまでは、この節で必要な 動作を直接説明します。将来の改訂では、§ 3.3 ファイルの作成と書き込みで言及した[FS]フックとともに 正式に統合される予定です。ホスト統合にはそのような フックは不要です。取得したresponseを取得したリソースを Cross-Origin Storage に保存する処理に渡し、 その処理が response から上限を読み取ります。

8. プライバシーとセキュリティに関する考慮事項

この節は RFC 2119 キーワードを使用している箇所を除いて非規範的です。このリポジトリの セキュリティとプライバシーに関する質問票も参照してください。

8.1. リソース完全性

すべてのCOS エントリは暗号学的ハッシュを キーとし、そのバイト列はそのハッシュに対して検証されます （§ 3.3 ファイルの作成と書き込みを参照）。したがって、サイトは requestFileHandle() によって取得したファイルが、自身で hashを取得した場合に得られるものと 正確に同じバイト列を持つことを確信できます。開発者は Cross-Origin Storage の内容を列挙できず、 そのハッシュをすでに知らなければファイルにアクセスできません。

COS ハッシュは秘密ではありません。 これはコンテンツ識別子であり、ファイルを すでに持つ者なら誰でも簡単に計算できます。この仕様が対象とする広く配布された リソースについては通常公開情報でもあり、モデルやライブラリのリリースとともに公開されることもよくあります。 したがってハッシュを知っていればエントリを検索するには十分ですが、それ自体はアクセス権を与えません。 検索が成功するかどうかは完全にoriginsと § 8.3 可用性ゲーティングによって決まります。開発者は未公開ハッシュを アクセス制御機構として扱ってはなりません。特定のファイルに関心のある 攻撃者はそのハッシュを推測する必要はなく、ファイル自体を入手すればよいだけです （§ 8.2 クロスサイトプロービングを参照）。

8.2. クロスサイトプロービング

あるリソースが限られた一群のサイトだけで使用されている場合、そのリソースが Cross-Origin Storage に存在すると知ることのできる攻撃者は、ユーザーがそれらのサイトのいずれかを 訪れた可能性が高いと推測できます。requestFileHandle() が存在を知るための仕組みであるため、各呼び出しは 実質的に 1 回のプローブです。この仕様では、プローブが何を知れるかを 2 つの独立した仕組みで 制限します：

  • origins （§ 3.5 リソース可視性のアップグレードを参照）により、保存元 オリジンは開示を選択したオリジン集合に制限できるため、専有的または人気度の低いリソースを まったくグローバルにプローブ可能にしないことができます。

  • § 8.3 可用性ゲーティングはさらに、 "*" スコープのリソースについて、そのハッシュがPHL 上にある場合を除き、 保存元オリジンの外部にある要求元オリジンへの開示を差し控えます。 そのため、origins: "*" として保存されたリソースが、 Web 上のすべてのオリジンから自動的にプローブ可能になるわけではありません。このゲートは "*" スコープの エントリにのみ適用されます。リストスコープおよび同一サイトスコープのエントリでは、保存元オリジンが すでにそれらに対する開示を明示的に制限しているため、最初の箇条書きの制限だけがゲートです。

最初の箇条書きが成り立つのは、「選択したオリジン集合」が Web 全体より意味のある程度に小さい場合だけです。 origins の形自体には、呼び出し元が 非常に多数のオリジンを列挙することを防ぐものがありません（たとえば、公開された 人気サイトランキングから構築したリスト）。これは機能的にはグローバル開示に近似しつつ、 "*" だけが要求する意図的で明示的なオプトインを回避することになります。 最大 origins リスト 長（§ 5.1 ストレージ制限を参照）はこれを制限します。 本物の複数プロパティ用途 （共通管理下にある少数の関連オリジン）を収容できる程度に小さく、しかし 「すべてのオリジン」の意味のある近似には到底足りない上限にすることで、制限付きオリジン形式のoriginsが "*" の未宣言の代替として使用されることを防ぎます。

ユーザーエージェントはさらに、単一オリジンから繰り返される requestFileHandle() 呼び出しをレート制限またはその他の方法で抑制するべきであり、 端末上のヒューリスティック （たとえば、ユーザーごとに生成されたように見えるハッシュへの要求パターンの検出）を適用して、 プローブ対象のハッシュがPHL 上にあるかどうかに関係なく プロービング試行を識別して遮断してもかまいません。

§ 9 他の仕様との統合のホスト統合のいずれかによって行われる検索も、 ページにエラーを公開しない場合でも同様にプローブです。サイトは、自身の サーバーがフォールバック要求を受信したかどうかを観察でき、これはここでの「見つからない」 結果が伝えるものと同じ 1 ビットの情報を持つためです。このような検索は、この仕様のゲートが許す以上のものを 開示せず、それらのゲートは変更なく適用されます。ただしレート制限は、それらの サーフェスからの検索をrequestFileHandle() 呼び出しとともにカウントする場合にのみ有効です。スクリプト可能な統合では、それらも同様に ループ内で容易に発行できるためです。

8.3. 可用性ゲーティング

保存元 オリジンの外部にあるオリジンからのrequestFileHandle() 読み取りが成功するかどうかは、常に要求元オリジンが エントリを読み取ることを許可されているかどうかに依存し、これはoriginsによって制御されます。"*" スコープのエントリでは、 2 つ目の独立した問いも適用されます。すなわち、ユーザーエージェントがエントリが 存在すること自体を開示する意思があるかどうかであり、これはPHL 登録およびGREASE’ingによって制御されます。そのような エントリでは両方が満たされる必要があります。リストスコープまたは同一サイトスコープのエントリでは最初の問いだけが適用されます。 規範的アルゴリズムについては§ 3.2 ファイルの読み取りを参照してください。 したがって "NotFoundError" はリソースが存在しないことの 証明ではありません。リソースが存在しない、要求元 オリジンがスコープ外である、"*" スコープのリソースのハッシュが PHL 上に（まだ、または永遠に） ない、あるいは GREASE’ing が true positive を抑制したことを意味する可能性があります。 開発者は "NotFoundError" を 「ネットワークにフォールバックする」以上に具体的な意味として扱ってはなりません。

注: サードパーティ Cookie をサポートするユーザーエージェントでは、 "*" 許可によるサイト間の ユーザー訪問の関連付け能力は、サードパーティ Cookie がすでに持つ能力を超えません。 PHLだけでは これを制限できません。攻撃者は、PHL の条件を個別には満たすリソースをどの部分集合だけ書き込むか選ぶことで、 クロスサイト識別子を構築できるためです。サードパーティ Cookie をブロックするユーザーエージェントでも、クロスサイト開示を制限するのであれば "*" 許可を提供できます。たとえば、トップレベルサイトをキーとし、ページ上のすべてのフレームで共有する 少数のクロスサイト検索予算、一定期間リロードをまたいで保持されるカウント、 ユーザージェスチャー後にのみ書き込み済みエントリを共有する仕組みなどです。README の プライバシーに関する考慮事項でこれらの緩和策を説明しています。

8.4. GREASE’ing

ユーザーエージェントはGREASE’ing（ランダムな拡張を生成し拡張可能性を維持する）を適用してもかまいません。 つまり、§ 8.3 可用性ゲーティングで本来 開示が許可される場合でも、 開示可能なエントリが存在しないかのように時折応答します。これによりノイズが加わり、サイトが実際の不在と、 プライバシー目的の false negative を区別しにくくなります。これは UA Client Hintsで適用される手法に似ています。

GREASE’ing は、グローバルに 開示可能な 許可だけによって条件を満たすオリジンにのみ適用されます。これはPublic Hash Listがゲートする場合と同じです （COS 開示を決定するを参照）。 ユーザーエージェントは、保存元オリジン、それらと同一 サイトのオリジン、 または明示的なorigins リスト上のオリジンには適用してはなりません。

GREASE’ing を適用するユーザーエージェントは、対象エントリのサイズに比例した判断をしなければなりません。 小さなエントリでは、ネットワーク取得へのフォールバックが安価であるため、時折の false negative は妥当なプライバシー上のトレードオフです。ユーザーエージェントは、誤った再ダウンロードが 得られるプライバシー上の利益に対して明らかに不釣り合いとなるサイズのエントリ （たとえばギガバイト規模の AI モデルの重み）には GREASE’ing を適用してはなりません。 その場合の false negative は完全な、観察可能で、高コストな再ダウンロードを強制するためです。

8.5. フィンガープリンティング

攻撃者が Cross-Origin Storage のプロービングから抽出できる情報は、プローブ対象リソースの人気度によって 制限されます。一般的な AI モデルや広く利用される JavaScript ライブラリのような非常に人気のあるリソースを ユーザーが持っていると知っても、そのユーザーがそれを利用する（場合によっては非常に多数の） サイトのいずれかを訪れたことしか分かりません。ユーザーが希少または一意のリソースを持っていると知ることは、 はるかに多くの情報を明らかにします。 ユーザーエージェントは、ユーザーごとに意図的に一意になるように作られたように見えるハッシュを持つ リソースを検出する端末上のヒューリスティック （たとえば、そのハッシュが 1 つのサイトによってしか書き込まれたことがない、または異常な頻度で要求される場合）を 適用し、そのようなパターンを、名目上の PHL 状態に関係なくプロービング試行として扱うことが想定されています。

9. 他の仕様との統合

この節は非規範的です。

ここで定義されるCOS レジストリは、 requestFileHandle() を直接経由せずに、4 つのホスト統合からも利用できます。それぞれの 統合は独自のホスト仕様で定義されます。この仕様は、共有される基盤概念 （COS ハッシュ、COS エントリ、 可用性ゲーティング、および Public Hash List）と、それらの統合がその上に構築することが想定される取得したリソースを Cross-Origin Storage に保存するステップを定義します。

  • HTML：すでに integrity [SRI]を持つ link および script 要素上の crossoriginstorage 属性。WHATWG に whatwg/html#12770で提案されています。

  • JavaScript：integrityと併用できる、ホスト定義の crossOriginStorage import 属性。 Import Attributes proposal の上に構築され、WHATWG に whatwg/html#12771で提案されています。

  • CSS：integrity()と併用できる cross-origin-storage() <request-url-modifier>。 CSS Working Group に w3c/csswg-drafts#14056で提案されています。

  • Fetch：integrity [FETCH]と併用できる crossOriginStorage RequestInit オプション。WHATWG に whatwg/fetch#1954で提案されています。 これにはホスト定義の destination がないため、COS レジストリから提供される Response が MIME type、status、その他のメタデータをどのように報告するかは、 その仕様における未解決問題です。COS エントリが保存するのはbytesだけです。

説明のためだけに、同じグローバル共有リソースを 4 つの各形式で Cross-Origin Storage にオプトインする例を示します：

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

const response = await fetch("popular-resource.ext", {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
});

これらのスニペットは説明用にすぎません。この構文はいずれもこの仕様では定義されていません。 制限付き origins リストをどのように記述するかを含む各形式の正式な文法は、 それぞれのホスト仕様に属します。表記は意図的に 異なります。RequestInitメンバーは sequence<DOMString>を取ることができ、 origins と正確に一致します。一方、属性値、 import 属性値、および CSS modifier 引数が保持できるのはテキストだけです。

4 つの形式はいずれも、ネットワーク取得にフォールバックする前に 一致し開示可能なエントリについてCOS レジストリをまず参照し、 正常に取得され完全性が検証されたリソースを 他のオリジンで再利用できるようCOS レジストリに保存するという、 requestFileHandle() とまったく同じ処理モデルを共有することが想定されています。保存ステップは 取得したリソースを Cross-Origin Storage に保存するであり、各統合は取得した responseとともにそれを実行します。そのため、制限付き origins 値は、 バイト列を供給するサーバーが送信する、そのリソースの response 上の Cross-Origin-Storage-Allow-Originヘッダーによって制限されます （§ 7 Cross-Origin-Storage-Allow-Origin ヘッダーを参照）。 これらの統合に関する議論は、このリポジトリの issue tracker ではなく、 それらを含むホスト仕様の tracker で行うべきです。

Public Hash List の取得プロトコル、更新頻度、データ形式、普及度のしきい値、およびガバナンスは、 この仕様書の付属成果物として詳細に設計されている。これは、[URL] Standard の付属データファイルである public suffix list の考え方に沿ったものである。詳細については、このリポジトリの Public Hash List explainer を参照。 この設計では、Public Suffix List のベンダー横断的なローリングリリースの前例をモデルとして、 WHATWG によるガバナンスと、独立して裏付けられた広範な利用状況を基準とする登録条件を提案している。 これは、上記で説明した k-匿名性スタイルの基準を具体的に適用したものであり、 hash が登録される方法の一部としてオフラインで一度だけ適用されるため、 ユーザーエージェントがクエリごとにそれを繰り返すことはない。 これらはすべて、この提案以外ではまだ確立されていない。 このリスト自体の初期の非規範的なコードプロトタイプは、現在このリポジトリの public-hash-list/implementation/ に存在する。 専用のベンダー横断的リポジトリは、PHL explainer で説明されているガバナンス目標として残っている。 この仕様書が依存するのは、hash が PHL 上にあるかどうかだけであり、 したがって、そのリストの取得メカニズム、ガバナンスモデル、またはその他の設計部分がどのように発展しても 正しくあり続ける。 ↵

Document の COS scope ceiling を、その response から設定するには、[HTML] の document 作成ステップにフックが必要である。 これは、[permissions-policy] および [CSP] が response 処理時に設定される方法と同じである。 そのフックが存在するまでは、この節で必要な動作を直接説明する。 将来の改訂では、[FS] のフックとともに正式に統合されることが期待される。 これは § 3.3 Creating and writing files で記載されたものである。 ホスト統合にはそのようなフックは必要ない。 ホスト統合はフェッチされた response を store a fetched resource in Cross-Origin Storage に渡し、そこで ceiling を読み取る。 ↵
