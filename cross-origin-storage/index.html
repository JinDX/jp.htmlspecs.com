概要

オリジン間ストレージ（COS）は、Web アプリケーションが AI モデル、WebAssembly モジュール、非常に普及している JavaScript ライブラリなどの 大容量ファイルを異なるオリジン間で保存および取得できる、コンテンツアドレス可能なキャッシュです。ファイルは URL ではなく暗号学的ハッシュによって識別されるため、あるオリジンによって一度取得された バイト単位で同一のリソースは、ユーザーエージェントが許可する他の任意のオリジンによって、再度ダウンロードすることなく再利用できます。キャッシュ内の存在を、ユーザーがどのサイトを訪問したかの推測に利用できないようにするため、 ファイルのオリジン間開示は、k-匿名性方式の人気度基準を満たすハッシュに限定されます。

1. はじめに

この節は非規範的です。

ストレージは通常、ユーザーのセキュリティとプライバシーを保護するためにオリジンごとに分割されます。これは適切な デフォルトですが、非常に大容量で、非常に普及し、一般に配布される限られた種類の リソース — AI モデル、WebAssembly モジュール、JavaScript ライブラリ、ゲームエンジン、大容量 Web フォント — には適していません。これらは、どのサイトが要求してもバイト単位で同一のファイルです。互いに無関係な 2 つのオリジンが 同じ 8 GB のモデルに依存する場合、オリジン分割ストレージではユーザーが そのモデルを 2 回ダウンロードして保持することを強制され、ユーザーの帯域幅、ストレージ、 バッテリー、そしてネットワーク全体を浪費します。

オリジン間ストレージ（COS）は、URL ではなく暗号学的ハッシュをキーとするコンテンツアドレス可能なキャッシュであり、ユーザーエージェントが、その利用をオプトインした オリジン間で、このようなリソースの単一の保存済みコピーを共有できるようにします。COS へのリソースの保存は、保存元オリジンによる 明示的なオプトイン操作であり、ユーザーエージェントは、本来そのリソースの読み取りを許可されるオリジンに対しても、 リソースの存在確認を控えることができます。§ 7 プライバシーおよび セキュリティに関する考慮事項を参照してください。

この仕様のエントリポイントは、requestFileHandle() メソッドであり、crossOriginStorageを介して公開されます。 

const hash = {
  algorithm: 'SHA-256',
  value: '8f434346648f6b96df89dda901c5176b10a6d83961dd3c1ac88b59b2dc327aa4',
};
try {
  const handle = await navigator.crossOriginStorage.requestFileHandle(hash);
  const file = await handle.getFile();
  // ファイルを使用して何らかの処理を行う。
} catch (err) {
  if (err.name === 'NotFoundError') {
    // オリジン間ストレージ内に（開示可能な状態で）存在しないため、代わりにネットワークから取得する。
  }
}

この仕様は、FileSystemFileHandle、 FileSystemWritableFileStream、 およびファイルシステム標準 [FS] の関連インフラストラクチャを再利用しますが、単一オリジンの非公開またはユーザーに可視なファイルシステムではなく、 専用のオリジン間共有ファイルシステムに適用します。

この仕様は、命令型 JavaScript API のみを定義します。関連する提案では、 同じ基盤キャッシュを宣言的マークアップと統合します。具体的には、HTML の crossoriginstorage 属性を link および scriptに追加し、 JavaScript の crossOriginStorage インポート属性、および CSS の cross-origin-storage() <request-url-modifier> を使用します。これらは、それぞれのホスト 言語の仕様で定義されます。§ 8 他の 仕様との統合を参照してください。

2. 概念

2.1. ハッシュ

COS ハッシュは、次の項目を持つ構造体です。

アルゴリズム

[WEBCRYPTO]が認識するハッシュアルゴリズムの名前を表す文字列です。たとえば「SHA-256」です。

値

アルゴリズムによって生成されたダイジェストを小文字の 16 進数で符号化した文字列です。 「SHA-256」の場合、長さは 64 文字です。

algorithm 辞書メンバーは、その値空間が [WEBCRYPTO] のハッシュアルゴリズムが受け付ける名前の集合と完全に一致するにもかかわらず、HashAlgorithmIdentifierではなく、単純な DOMStringとして型付けされています。HashAlgorithmIdentifier は (object or DOMString) であり、追加で object を受け付けます。このオブジェクトは [WEBCRYPTO] によって Algorithm形式の 辞書へ正規化され、呼び出し元は必要なアルゴリズムに追加パラメーターを渡せます （たとえば {name: "HMAC", hash: "SHA-256"}）。ハッシュアルゴリズムはそのようなパラメーターを受け取らず、 アルゴリズムは単一の操作によって一度だけ消費されるのではなく、コンテンツアドレス可能な キーの一部として保存、比較、ラウンドトリップされます。また、この仕様の すべての例では単純な文字列が使用されています。ここで任意のオブジェクトを許可しても機能は増えず、 等価性とシリアル化を 不必要に複雑にするだけです。したがって、DOMString がこのフィールドにとって より限定的で、より適切な型です。

2 つのCOS ハッシュ値は、それらのアルゴリズム 値がASCII 大文字小文字不区別で一致し、かつそれらの値が厳密に 等しい場合に、等しいとします。

注: 大文字小文字が規範的に制約されていないアルゴリズムとは異なり、 値はすでに規範的に 小文字であるため（上記参照）、その比較はASCII 大文字小文字不区別の比較ではなく、単純な 文字列比較です。

コンテンツアドレス可能な ストアとは、そのエントリが URL や名前ではなく、 COS ハッシュの等価性をキーとするものです。バイト列が同一で、同じハッシュアルゴリズムを使用する 2 つのファイルは、 保存したオリジンの数や取得元 URL の数に関係なく、同じエントリです。

2.2. COS エントリ

各ユーザーエージェントには単一のCOS レジストリがあり、これはCOS ハッシュ値から COS エントリの構造体へのマップであり、オリジン間ストレージを使用するすべてのオリジンによって共有されます。 COS エントリは、次の項目を持ちます。

ハッシュ

COS ハッシュです。

バイト列

Null、またはハッシュのアルゴリズムによるダイジェストが、 ハッシュの値に等しいバイト列です。書き込み元が 検証と 保存を完了するまでは Null です。

状態

「pending」または「written」のいずれかです。エントリは「pending」から始まり、 バイト列が初めて設定されたときに一度だけ「written」になります。

オリジン

宣言された共有範囲です。「*」（任意のオリジン）、オリジン文字列のリスト （そのオリジンのみ）、または null（同一サイトのオリジンのみ）のいずれかです。最初の書き込み元によって設定され、 拡張できますが縮小することはできません。

保存元オリジン

それぞれがこのエントリのバイト列の書き込みを少なくとも一度正常に完了したオリジンの集合です。ページの読み込みをまたいで永続化され、時間の経過とともに増加します。§ 5.2 削除で説明されている場合を除き、縮小することはありません。 保存元オリジンに含まれるオリジンは、 オリジンや エントリのハッシュが公開ハッシュリスト （PHL）に含まれているかどうかに関係なく、 requestFileHandle()を介して常にエントリのハンドルを取得できます。 § 3.4.1 元の保存元によるアクセスを参照してください。

ユーザーエージェントには、新しい並列キューを開始した結果である、関連付けられたオリジン間ストレージキューがあります。COS レジストリに対するすべての操作は、 このキューにエンキューされなければならず、それによって操作は エンキューされた 順序で実行され、互いに割り込むことがありません。

2.3. 公開ハッシュリスト

あるハッシュがオリジン間ストレージ内に存在することを確認する行為自体が、 ユーザーの閲覧履歴に関する情報を漏えいさせる可能性があります（§ 7.2 サイト間プロービングを参照）。これは、特にグローバルな 範囲を持つエントリに関するリスクです。オリジンがリストまたは null であるエントリは、 保存元オリジンの明示的な選択によってすでに開示範囲が限定されていますが、「*」は、エントリを Web 上の任意のオリジンに公開する可能性があります。この特定のリスクを限定するため、「*」範囲のリソースは、 その保存元オリジン外のオリジンに対して、ハッシュが追加の独立したゲートを通過した場合にのみ 開示できます。このゲートは、ベンダー中立で実装定義のCOS ハッシュ 値の許可リストである公開ハッシュリスト （PHL）への登録です。ハッシュは、 k-匿名性方式の人気度基準を満たした場合にのみ公開ハッシュリストに登録されます。たとえば、一定数以上の独立した オリジンに、バイト単位で同一のものが存在する場合です。これにより、共有キャッシュ内にそのハッシュが存在することを確認しても、 個々のユーザーに関する情報にはなりません。

COS ハッシュ hashは、 hashがユーザーエージェントの現在の公開ハッシュリストのスナップショット内のエントリと 等しい場合に、公開ハッシュ リストに含まれるものとします。

Public Hash List の取得プロトコル、 更新頻度、データ形式、人気閾値、およびガバナンスは、この仕様の付属成果物として詳細に設計されており、 [URL] Standard のパブリックサフィックスリストが規範的な文ではなく付属データファイルであるのと同じ趣旨で、 このリポジトリの Public Hash List explainer を参照してください。この設計では、 Public Suffix List のベンダー横断的なローリングリリースの前例をモデルとして WHATWG によるガバナンスを提案し、 独立して裏付けられた普遍性を基準とする登録基準を採用しています。これは、上記で説明した k-anonymity スタイルの基準を 具体化したものであり、ユーザーエージェントがクエリごとに繰り返し確認するものではなく、ハッシュが登録される方法の一部として 一度だけオフラインで適用されます。この提案以外では、これらはまだ確立されていません。リスト自体の初期の非規範的なコードプロトタイプは、 このリポジトリの public-hash-list/implementation/ で維持されています — 実用的な 暫定的な配置場所です。専用のベンダー横断的なリポジトリは、PHL explainer で説明されているガバナンス目標として残されています。 この仕様は、特定の取得メカニズムやガバナンスモデルではなく、ハッシュが PHL 上にある かどうかだけに依存するため、その設計が どのように発展しても正しい状態を維持します。

3. CrossOriginStorageManager インターフェイス

[Exposed=(Window,Worker), SecureContext]
interface CrossOriginStorageManager {
  Promise<FileSystemFileHandle> requestFileHandle(
      CrossOriginStorageRequestFileHandleHash hash,
      optional CrossOriginStorageRequestFileHandleOptions options = {});
};

dictionary CrossOriginStorageRequestFileHandleHash {
  required DOMString value;
  required DOMString algorithm;
};

dictionary CrossOriginStorageRequestFileHandleOptions {
  boolean create = false;
  (DOMString or sequence<DOMString>) origins;
};

interface mixin NavigatorCrossOriginStorage {
  [SameObject, SecureContext] readonly attribute CrossOriginStorageManager crossOriginStorage;
};
Navigator includes NavigatorCrossOriginStorage;
WorkerNavigator includes NavigatorCrossOriginStorage;

各Navigator およびWorkerNavigator オブジェクトには、関連付けられたCrossOriginStorageManager オブジェクトがあります。crossOriginStorage ゲッターの 手順は、thisに関連付けられたCrossOriginStorageManagerを返すことです。

各CrossOriginStorageManager オブジェクトには、オブジェクトの作成時に thisの関連設定オブジェクトのオリジンに設定される、関連付けられたオリジンがあります。

3.1. requestFileHandle() メソッド

handle = await navigator . crossOriginStorage . requestFileHandle(hash)

hashで識別されるファイルがオリジン間ストレージに存在し、かつ呼び出し元オリジンに開示可能である場合、 そのファイルのハンドルを返します。それ以外の場合は、「NotFoundError」 DOMExceptionで拒否されます。 「NotFoundError」は、 ファイルがオリジン間ストレージに物理的に存在しないことを証明するものではありません。§ 7.3 可用性ゲーティングを参照してください。呼び出し元は、 これを「代わりにネットワークから取得する」として扱えます。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true })

hashで識別されるファイルをオリジン間ストレージへ書き込むために使用できるハンドルを返し、 まだエントリが存在しない場合は新しいエントリを作成します。デフォルトでは同一サイトのオリジンに制限されます。 エントリがすでに存在するかどうかに関係なく、呼び出し元はハンドルの createWritable() メソッドを介して完全なファイル内容を書き込む必要があります。その時点でユーザーエージェントは、 書き込まれたバイト列のハッシュが hash と一致することを検証し、一致しない場合は「DataError」 DOMExceptionで拒否します。この要件は、 オリジンが作成要求を、hash がすでに存在するかどうかを判定するオラクルとして使用することを防ぎます。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: "*" })

上記と同様ですが、書き込み後、hashに対する要求が § 7.3 可用性ゲーティングを通過した任意のオリジンに対して、 エントリをさらに開示可能にします。

handle = await navigator . crossOriginStorage . requestFileHandle(hash, { create: true, origins: ["https://a.example", "https://b.example"] })

上記と同様ですが、開示を一覧に含まれるオリジンのみに制限します （呼び出し元オリジン、および保存元オリジンにすでに含まれる任意のオリジンを除く）。

requestFileHandle(hash, options) メソッドの 手順は次のとおりです。

  1. resultを新しい Promiseとします。

  2. realmをthisの関連する Realmとします。

  3. globalをthisの関連するグローバルオブジェクトとします。

  4. originをthisに関連付けられたオリジンとします。

  5. globalに関連付けられたDocumentが存在する場合に、その文書が 「cross-origin-storage」 ポリシー制御機能の使用を許可されていない場合は、次の手順を実行します。

    1. globalを指定して、DOM 操作タスクソース上にグローバルタスクをキューに追加し、そのタスクで resultを「NotAllowedError」 DOMExceptionによって拒否します。

    2. resultを返します。

  6. validationFailureを、hashおよび optionsを指定してCOS 要求を検証する手順を実行した結果とします。

  7. validationFailureが null でない場合は、次の手順を実行します。

    1. globalを指定して、DOM 操作タスクソース上にグローバルタスクをキューに追加し、そのタスクで resultをvalidationFailureによって拒否します。

    2. resultを返します。

  8. 次の手順を オリジン間ストレージキューへエンキューします。

    1. options["create"] が true の場合は、次の手順を実行します。

      1. result、hash、options、global、および realmを指定して、作成要求を完了する手順を実行します。

    2. それ以外の場合は、次の手順を実行します。

      1. result、hash、origin、global、および realmを指定して、読み取り要求を完了する手順を実行します。

  9. resultを返します。

CrossOriginStorageRequestFileHandleHash hash およびCrossOriginStorageRequestFileHandleOptions optionsを指定して、COS 要求を検証するには、null またはTypeErrorを返します。

  1. hash["algorithm"] が[WEBCRYPTO]によって認識されるハッシュアルゴリズム名でない場合、新しいTypeErrorを返します。

  2. hash["algorithm"] が「SHA-256」とASCII 大文字小文字不区別で 一致する場合に、hash["value"] が正規表現 /^[0-9a-f]{64}$/に 一致しない場合、新しいTypeErrorを返します。

    注: 将来のハッシュアルゴリズムでは、 異なる想定ダイジェスト長を定義できます。この 仕様は、例全体で使用されている「SHA-256」のみを規範的に制約します。

  3. options["origins"] が存在し、 「*」でない場合は、次の手順を実行します。

    1. candidatesをoptions["origins"]とし、 単一の文字列は 1 項目のリストとして扱います。

    2. candidatesのサイズが ユーザーエージェントのオリジンリストの最大長より大きい場合、新しいTypeErrorを返します。

    3. candidatesの各 candidateについて反復します。

      1. candidateに対して基本 URL パーサーを実行した結果が失敗である場合、または 解析された URL のオリジンが不透明なオリジンである場合、新しいTypeErrorを返します。

  4. null を返します。

3.2. ファイルの読み取り

Promise result、COS ハッシュ hash、 オリジン origin、グローバルオブジェクト global、およびRealm realmを指定して、読み取り 要求を完了するには、次の手順を実行します。

  1. entryを、COS レジストリ内にある、ハッシュが hashと等しいCOS エントリとします。存在しない場合は null とします。

  2. entryが null でなく、entryの状態が「pending」である場合は、 次の手順を実行します。

    1. globalを指定して、DOM 操作タスクソース上にグローバルタスクをキューに追加し、そのタスクで resultを「NotAllowedError」 DOMExceptionによって拒否します。

    2. 返します。

    注: 書き込み処理中のハッシュは、意図的に 存在しないハッシュとは異なる動作をします。これにより呼び出し元が、進行中の書き込みを実際のキャッシュミスと誤認して、 非常に大きなファイルをキャッシュへ書き込むことだけを目的として、重複した同時ダウンロードを開始することを防ぎます。 § 3.3 ファイルの作成と書き込みを参照してください。

  3. disclosableEntryを、entry およびoriginを指定して可用性ゲーティングを 適用する手順を実行した結果とします。

  4. disclosableEntryが null の場合は、次の手順を実行します。

    1. globalを指定して、DOM 操作タスクソース上にグローバルタスクをキューに追加し、そのタスクで resultを「NotFoundError」 DOMExceptionによって拒否します。

    2. 返します。

  5. handleを、realm内で、 オリジン間ストレージファイルシステム内の disclosableEntryを指すロケーターを持つ 新しい FileSystemFileHandleを作成した結果とします [FS]。

  6. globalを指定して、DOM 操作タスクソース上にグローバルタスクをキューに追加し、そのタスクで resultをhandleで解決します。

3.4. リソースの可視性の拡張

COS エントリの可視性は、 拡張できますが、縮小することはできません。

    注: すでにグローバルに利用可能なエントリを、 後の書き込み元が制限することはできません。この注が適用され、requestedOriginsが「*」でない場合、 ユーザーエージェントは要求された制限が適用されなかったことを開発者へ通知するコンソール警告を記録することが想定されます。

  3. requestedOriginsが「*」である場合は、次の手順を実行します。

    1. entryのオリジンを「*」に設定します。

    2. 返します。

  4. entryのオリジンが null の場合は、次の手順を実行します。

    1. entryのオリジンをrequestedOriginsに設定します。

    2. 返します。

  5. mergedを、entryのオリジンの複製とします。

    2. mergedのサイズが ユーザーエージェントのオリジンリストの最大長と等しい場合は、 中断します。

3.4.1. 元の保存元によるアクセス

COS エントリの書き込みを正常に完了したオリジン、すなわち、 エントリの保存元オリジンに含まれる任意のオリジンは、その後いつでも requestFileHandle()を介してハンドルを取得できます。これは、エントリの オリジン値や、 そのハッシュがPHL に含まれるかどうかには依存しません。 これは、オリジンが自身の保存したものへ常にアクセスできる Cache API のモデルを反映しています。

4. オリジン間ストレージファイルシステム

オリジン間ストレージファイルシステムは、 任意のオリジンのバケットファイルシステムまたはローカルファイルシステムアクセスのルートとは異なるファイルシステムルートであり、その エントリは、COS レジストリのCOS エントリ項目と一対一で対応します。

オリジン間ストレージファイルシステムは、[FS]の通常の呼び出しごとの 権限検査モデルを使用しません。このファイルシステムから取得されたすべてのFileSystemFileHandleは、スクリプトへ返される前に、 § 3.2 ファイルの読み取りまたは§ 3.3 ファイルの作成と 書き込みによってすでに完全に認可されています。そのため、そのようなハンドルに対して getFile() またはcreateWritable()を呼び出しても、 追加の権限プロンプトが表示されることはありません。

COS エントリ entryを指すFileSystemFileHandleは、 entryの状態がまだ 「pending」である間にも存在できます。たとえば、 作成要求の直後で、対応する書き込みが完了する前です。 そのようなハンドルに対してgetFile()を呼び出すと、 「NotAllowedError」 DOMExceptionで拒否されなければなりません。 これは同じハッシュに対する同時実行中の requestFileHandle() 呼び出しが拒否されるのと同じ理由です（§ 3.2 ファイルの読み取りを参照）。 ハンドルを要求した呼び出し元であっても、まだ検証されていないプレースホルダーを ファイルの実際の内容であるかのように観測できてはなりません。

entryの状態が「written」になると、そのようなハンドルに対して呼び出されたgetFile()は、 内容がentryのバイト列であるFileを返します。これは、 [FS]が、 ファイル エントリのバイナリデータがentryの バイト列である場合について、すでに定義している動作と完全に同じです。

5. ストレージ管理

5.1. ストレージ制限

単一オリジンが他のオリジンのエントリを削除させる目的でキャッシュをあふれさせることを防ぐため、ユーザーエージェントは、 オリジンが正常な書き込みを通じて COS レジストリへ提供できる総バイト数に上限を設けなければなりません。具体的な上限は 実装定義です。オリジンの書き込みが上限を超える場合、ユーザーエージェントは、 その書き込みを「QuotaExceededError」 DOMExceptionで拒否し、 コンソールへ警告を記録するべきです。

注: エントリはコンテンツアドレス可能であるため、 オリジンが同じハッシュで同じバイト列を繰り返し書き込んでも、最初に正常に書き込んだとき以上のクォータを消費しません。 § 2.2 COS エントリを参照してください。

ユーザーエージェントには、単一のオリジンのリストに含められるオリジン数を制限する、正の整数である実装定義のオリジンリストの最大長もあります。 これは、リストが最初に提供される場合 （COS 要求を検証するを参照）と、 後で既存エントリへマージされる場合 （リソースの可視性を拡張するを参照）の両方で適用されます。これにより、 単一の呼び出しでも、多数の呼び出しの長期的な累積効果でも、エントリのオリジンが無制限に増加することはありません。 メモリ使用量を制限するだけでなく、オリジンのリストが 「*」の宣言されていない代替として使用されることも防ぎます。§ 7.2 サイト間プロービングを参照してください。

この上限を超えた場合、これら 2 つの場所では異なる方法で処理されます。2 つの呼び出しは、 操作のまったく異なる段階で発生するためです。

  • COS 要求を検証するでは、ファイルが取得、ハッシュ化、または 書き込まれる前に上限が検査されます。上限を超えた呼び出し元は、ただちに「TypeError」を受け取り、 それ以外には何も起こりません。これは、その他の不正なorigins 値と同じ扱いです。

  • リソースの可視性を拡張するでは、 上限には、長期間にわたって互いに無関係なオリジンによって行われる可能性のある、別々の独立した書き込み呼び出しを通じて要求された オリジンの累積効果によってのみ到達できます。また、この呼び出しのバイト列がすでにハッシュ化、検証、永続保存された後にのみ検査されます。 その時点で書き込みを拒否すると、無関係な管理上の上限のために、正常に検証された、すでに保存済みの、 そして非常に大きい可能性のある書き込みを破棄することになります。また、それを単一の呼び出し元の誤りに帰することもできません。 したがって書き込みは成功したままとし、上限を超えたオリジンだけがオリジンから削除され、 コンソール警告が記録されます。これは、既存の より許容的な範囲からより制限的な範囲への要求の処理を反映しています。 完全に満たせないオリジン要求は、それを伴う書き込みを失敗させるのではなく、 上限に合わせて警告なしに制限されます。この仕様の他の場所にある§ 7.3 可用性ゲーティングと同様に、 呼び出し元は、自身が要求したオリジンが実際に追加されたかどうかを、後から確実に確認する方法を持ちません。 そのオリジンとして行う後続のrequestFileHandle() 呼び出しは、オリジンが追加されていた場合でも、たとえば GREASE の適用によって失敗する可能性があります。そのため、その結果をどちらの意味の確認としても解釈してはなりません。

5.2. 削除

この節は非規範的です。

ストレージ容量が逼迫した場合、ユーザーエージェントは、 各エントリへ最近アクセスした保存元オリジン全体で 最終使用時刻が最も古いものを削除するポリシーなどを使用して、COS レジストリからエントリを削除できます。ユーザーエージェントは、 どのファイルが保存されているか、どのオリジンが各ファイルへアクセスしたかをユーザーが確認し、 エントリを手動で削除したり、すべてのオリジン間ストレージデータを消去したりできる設定 UI を提供することが想定されます。

ユーザーがオリジンのサイトデータを消去した場合、ユーザーエージェントは、そのオリジンが含まれるすべての 保存元 オリジン集合から、そのオリジンを削除するべきです。その削除後にCOS エントリの 保存元 オリジンが空になった場合、ユーザーエージェントはそのエントリを削除対象と見なせます。

5.3. 手動で追加されたエントリ

この節は非規範的です。

上記の設定 UI では、ユーザーがディスク上にすでに持っているファイルを直接 オリジン間ストレージへ追加できる場合があります。たとえば、Web サイトとは無関係にダウンロードした AI モデルです。この場合、スクリプトは requestFileHandle()を呼び出しません。 そのようなエントリには、書き込みを帰属させる要求元オリジンがなく、命令型 API だけでは答えられない 2 つの問題が生じます。

  • § 3.4.1 元の保存元によるアクセスにおける 元の保存元は誰でしょうか。誰も該当しません。エントリの保存元オリジンは、書き込みを実行したオリジンを含むのではなく、空の状態から始まります。 したがって、通常の可用性ゲーティングおよびオリジン検査から免除されるオリジンはありません。 他のすべての要求元オリジンと同じ制約を受けます。実際にバイト列を書き込んだオリジンが存在しないため、これは正しい結果です。

  • オリジンは、 originsを省略する通常の書き込みと同様に、 同一サイトのみにデフォルト設定するべきでしょうか。いいえ。「同一サイト」は要求元オリジンとの関係によってのみ意味を持ち、 手動追加には要求元オリジンがないため、「同一サイト」の基準となるサイトもありません。その代わり、ユーザーエージェントは、 そのようなエントリのオリジンをデフォルトで「*」に設定することが想定されます。 ファイルを手動で事前登録する目的、すなわち、ユーザーがまだ訪問していないサイトが、ユーザーのディスク上にすでにあるファイルを再利用できるようにする目的は、 他のオリジンがそのファイルを実際に発見できる場合にのみ達成されるためです。ユーザーエージェントの設定 UI では、 ユーザーがより狭い範囲を選択できるようにしてもかまいません。

この方法で追加された後は、状態が「written」のエントリは、 Web サイトがrequestFileHandle()を介して書き込んだエントリと、それ以外の点では区別できません。 同じ可用性ゲーティングおよび可視性の 拡張規則が適用されます。これは、同じオリジン値を持つ他のエントリとまったく同じです。 手動追加ではデフォルトであるものの唯一の結果ではない「*」範囲になった場合には、 PHL に含まれるかどうかの検査も適用されます。

6. 権限ポリシーとの統合

この仕様は、文字列「cross-origin-storage」によって識別されるポリシー制御機能を定義します [permissions-policy]。デフォルトの許可リストは selfです。

この機能の使用を許可されていないDocumentでは、そのDocumentから （または所有元がそのDocumentであるワーカーから）行われるすべての requestFileHandle() 呼び出しが、ハッシュ検証、レジストリ検索、または書き込みが行われる前に、 「NotAllowedError」 DOMExceptionで拒否されます。

7. プライバシーおよびセキュリティに関する考慮事項

この節は、RFC 2119 のキーワードを使用する箇所を除き、非規範的です。リポジトリ内の セキュリティおよびプライバシー質問票も参照してください。

7.1. リソースの完全性

すべてのCOS エントリは暗号学的ハッシュをキーとし、 そのバイト列はそのハッシュに対して検証されます（§ 3.3 ファイルの作成と書き込みを参照）。 したがって、サイトは、requestFileHandle()を通じて取得したファイルが、 hashを自身で取得した場合と厳密に同じバイト列であることを確信できます。開発者は、 オリジン間ストレージの内容を列挙したり、ハッシュを事前に知らずにファイルへアクセスしたりすることはできません。

COS ハッシュは秘密ではありません。 これはコンテンツ識別子であり、ファイルをすでに所有している者なら誰でも簡単に計算できます。また、この仕様が対象とする 広く配布される種類のリソースでは、通常は公開情報です。たとえば、モデルやライブラリの リリースとともに公開されます。したがって、ハッシュを知っていればエントリを検索できますが、ケイパビリティ URL やベアラートークンとは異なり、それ自体ではアクセス権を付与しません。検索が成功するかどうかは、 ハッシュが非公開のままであったかどうかではなく、常にオリジンおよび § 7.3 可用性ゲーティングによって決まります。開発者は、非公開のハッシュをアクセス制御機構として扱ってはなりません。 特定のファイルに関心を持つ攻撃者は、そのハッシュを推測する必要はなく、ファイル自体を入手するだけでよいためです （§ 7.2 サイト間プロービングを参照）。

7.2. サイト間プロービング

リソースが少数のサイトでしか使用されていない場合、そのリソースがオリジン間ストレージに存在することを学習できる攻撃者は、 ユーザーがそれらのサイトのいずれかを訪問した可能性が高いと推測できます。 requestFileHandle() は存在を知るための機構であるため、各呼び出しは実質的にプローブです。この仕様の 2 つの独立した機構が、 プローブによって学習できる内容を制限します。

  • オリジン （§ 3.4 リソースの可視性の拡張を参照）によって、保存元 オリジンは開示を選択したオリジン集合に制限できます。そのため、独占的または人気度の低いリソースを グローバルにプローブ可能にする必要はありません。

  • § 7.3 可用性ゲーティングは、 ハッシュがPHL に含まれない限り、 「*」範囲のリソースを、その保存元オリジン外の要求元オリジンへ開示しないようにします。 そのため、origins: 「*」で保存されたリソースが、 Web 上のすべてのオリジンから自動的にプローブ可能になることはありません。このゲートは、 「*」範囲のエントリにのみ適用されます。リスト範囲および同一サイト範囲のエントリでは、 保存元オリジンがすでに明示的に開示範囲を限定しているため、最初の箇条書きの制限だけがゲートになります。

最初の箇条書きは、「選択したオリジン集合」が Web 全体より十分に小さい場合にのみ成立します。 originsの形状自体は、 呼び出し元が非常に多数のオリジンを列挙することを妨げません。たとえば、公開された上位サイトのランキングから構成したリストです。 これは機能的にはグローバルな開示に近似しながら、「*」だけに要求される意図的で明示的なオプトインを回避します。 オリジンリストの 最大長（§ 5.1 ストレージ制限を参照）がこれを制限します。 正当な複数プロパティのユースケース、すなわち共通管理下にある少数の関連オリジンを収容できる程度には大きいものの、 「すべてのオリジン」への意味のある近似には遠く及ばない上限にすることで、制限されたオリジン形式のオリジンが、「*」の宣言されていない代替として使用されることを防ぎます。

ユーザーエージェントはさらに、単一オリジンから繰り返される requestFileHandle() 呼び出しをレート制限またはその他の方法で抑制するべきです。また、プローブされたハッシュが PHL に含まれるかどうかに関係なく、 端末上のヒューリスティック（たとえば、ユーザーごとに生成されたように見えるハッシュの要求パターンの検出）を適用し、 プロービング試行を識別して遮断してもかまいません。

7.3. 可用性ゲーティング

保存元 オリジン外のオリジンからのrequestFileHandle() 読み取りが成功するかどうかは、常に要求元オリジンがエントリを読み取ることを許可されているかどうかに依存し、 これはオリジンによって管理されます。「*」範囲のエントリには、 さらに独立した第 2 の問題が適用されます。ユーザーエージェントがエントリの存在自体を開示する意思があるかどうかであり、 これはPHL への登録およびGREASE の適用によって管理されます。そのようなエントリでは両方が 成立しなければなりません。リスト範囲または同一サイト範囲のエントリには最初の問題だけが適用されますが、 GREASE の適用により、オリジンが本来許可する開示が抑制される場合があります。 規範的なアルゴリズムについては、§ 3.2 ファイルの読み取りを参照してください。 したがって、「NotFoundError」は リソースが存在しないことの証明ではありません。リソースが存在しない、要求元オリジンが範囲外である、 「*」範囲のリソースのハッシュがまだ、または今後も PHL に含まれない、あるいは GREASE の適用によって 真の肯定結果が抑制された、のいずれかを意味する場合があります。開発者は、「NotFoundError」を 「ネットワークへフォールバックする」以上に具体的な意味として扱ってはなりません。

7.4. GREASE の適用

ユーザーエージェントは、GREASE を適用してもかまいません（ランダムな拡張を生成して 拡張性を維持する）。これは、§ 7.3 可用性ゲーティングが本来開示を 許可する場合でも、開示可能なエントリが存在しないかのように時折応答することです。これによりノイズが加わり、 サイトが実際の不存在と、プライバシーを目的とする偽陰性を区別しにくくなります。これは、 UA クライアント ヒントで適用される手法に似ています。

GREASE を適用するユーザーエージェントは、対象エントリのサイズに応じた適切な判断を行わなければなりません。 小さいエントリでは、ネットワーク取得へのフォールバックが低コストであるため、時折生じる偽陰性は妥当なプライバシー上のトレードオフです。 ユーザーエージェントは、誤った再ダウンロードのコストが得られるプライバシー上の利益に明らかに不釣り合いとなるサイズのエントリに対して、 GREASE を適用してはなりません。たとえば、ギガバイト規模の AI モデルの重みです。この場合、偽陰性によって、 安価な再取得ではなく、完全で観測可能かつ高コストな再ダウンロードが強制されるためです。

7.5. フィンガープリンティング

攻撃者がオリジン間ストレージのプロービングから抽出できる情報は、プローブ対象リソースの人気度によって制限されます。 一般的な AI モデルや広く使用される JavaScript ライブラリなど、非常に人気の高いリソースをユーザーが持っていることを知っても、 ユーザーがそれを使用する多数のサイトのいずれかを訪問したことしか分かりません。一方、まれまたは一意のリソースを持っていることを知ると、 はるかに多くの情報が得られます。ユーザーエージェントは、ハッシュがユーザーごとに意図的に一意になるように見えるリソースを検出するため、 端末上のヒューリスティックを適用することが想定されます。たとえば、単一サイトによってしか書き込まれていないハッシュや、 異常な頻度で要求されるハッシュです。そして、公称上の PHL ステータスに関係なく、そのようなパターンをプロービング試行として扱うことが想定されます。

8. 他の仕様との統合

この節は非規範的です。

ここで定義されるCOS レジストリには、 requestFileHandle()を直接介さずに、 3 つのホスト言語から宣言的にアクセスすることもできます。各統合はこの文書ではなく、それぞれのホスト言語の仕様で定義されます。 この仕様は、それらの統合が基盤とすることを想定した共有概念 （COS ハッシュ、COS エントリ、 可用性ゲーティング、および公開ハッシュリスト）のみを定義します。

  • HTML: すでにintegrityを持つ link および script 要素に追加するcrossoriginstorage属性です [SRI]。WHATWG HTML 標準へ提案される予定です。

  • JavaScript: integrityと併用できる、ホスト定義の crossOriginStorageインポート属性です。インポート属性 提案を基盤とし、WHATWG HTML 標準へ提案される予定です。

  • CSS: integrity()と併用できる cross-origin-storage() <request-url-modifier>です。 w3c/csswg-drafts#14056で CSS ワーキンググループに提案されています。

説明のみを目的として、次に、同じグローバル共有リソースを 3 つの各形式から オリジン間ストレージへオプトインする例を示します。

<script src="popular-library.js" integrity="sha256-abc123..." crossoriginstorage="*"></script>

import data from "popular-resource.ext" with {
  integrity: "sha256-abc123...",
  crossOriginStorage: "*",
};

@font-face {
  font-family: "Popular Font";
  src: url("popular-font.woff2" integrity("sha256-abc123...") cross-origin-storage(*));
}

これらのスニペットは説明のみを目的としています。この構文はいずれもこの仕様では定義されず、 制限付きで「*」でないオリジン値の表記方法を含む、各形式の正式な文法は、 この文書ではなく、それぞれのホスト言語仕様に属します。

3 つの形式はいずれも、ネットワーク取得へフォールバックする前に、 一致する開示可能なエントリがないかCOS レジストリを最初に調べ、 正常に取得され完全性が検証されたリソースを、他のオリジンで再利用できるよう COS レジストリへ保存するという、共通の処理モデルを持つことが想定されます。これは requestFileHandle() とまったく同じです。これらの統合に関する議論は、このリポジトリの課題トラッカーではなく、 それを担うホスト言語仕様のトラッカーで行われるべきです。
