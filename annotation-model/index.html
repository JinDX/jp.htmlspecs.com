概要

アノテーションは通常、リソースに関する情報やリソース間の関連付けを伝達するために使用されます。 単純な例としては、ウェブページや画像へのコメントやタグ、ニュース記事に関するブログ投稿などがあります。

Web Annotation Data Model仕様は、アノテーションが異なるハードウェアやソフトウェアプラットフォーム間で共有・再利用できるよう、構造化されたモデルとフォーマットを記述しています。一般的なユースケースは、シンプルかつ便利な方法でモデル化できる一方で、特定のデータポイントや時間指定のマルチメディアリソースのセグメントへの任意コンテンツのリンク付けなど、より複雑な要件にも対応可能です。

この仕様では、これらのユースケースに対応する概念モデルに基づいたアノテーションの作成と利用を容易にするため、特定のJSON形式およびそれを表現する語彙を提供しています。

1. はじめに

このセクションは規範的でありません。

別々の情報の断片の間に関連付けを作成する「注釈」は、オンラインで多くの形で広く行われている活動です。ウェブ市民は、ホスティングウェブサイトに組み込まれたツール、外部ウェブサービス、または注釈クライアントの機能を使用して、オンラインリソースに関するコメントを行います。共有された写真やビデオに対するコメント、製品レビュー、あるいはウェブリソースへのソーシャルネットワークでの言及も、すべて注釈と見なすことができます。加えて、「付箋」システムや、スタンドアロンのマルチメディア注釈システムなども多く存在します。本仕様は、これらの注釈を表現するための共通のアプローチ等について記述します。

Web Annotation Data Modelは、注釈を表現するための拡張可能で相互運用可能なフレームワークを提供します。これにより、プラットフォーム間で容易に注釈を共有できるだけでなく、複雑な要件にも対応できる表現力を持ちながら、一般的なユースケース（テキスト片を単一ウェブリソースに添付する等）には十分シンプルな設計となっています。

注釈は通常、本体（body）と対象（target）を含む、相互に関連付けられたリソースの集合と考えられ、その本体が対象と関係していることを示します。この関係の正確な内容は注釈の意図によって変わりますが、本体が対象に「関する」ものである場合が多いです。この見方は、下図のような3つの部分からなる基本モデルとなります。完全なモデルは、注釈内へのコンテンツ埋め込み、リソースの任意部分の指定、リソースの適切な表現の選択、クライアントへのスタイルの伝達など追加機能もサポートします。機械による、または機械向けの注釈も可能であり、データウェブが単に人間向けのドキュメントウェブに限定されず考慮されています。

Web Annotation Data Modelは、注釈の作成、管理、取得のための伝送プロトコルを規定しません。かわりに、多様なプロトコルで運用可能な、リソース指向の構造とそのシリアル化方式について記述します。関連する[annotation-protocol]仕様には、推奨されるトランスポート層が記載されていますが、それは別途採用することもできます。

1.1 モデルの目的

Web Annotation Data Modelの主な目的は、注釈のシステム間共有を可能にする標準的な記述モデルおよびフォーマットを提供することです。この相互運用性は、他者との共有や、プライベート注釈をデバイス間またはプラットフォーム間で移行するためにも利用できます。共有された注釈は、既存のコレクションにも統合でき、重要な情報を失うことなく再利用できなければなりません。このモデルはできる限り多くの注釈ユースケースをカバーし、単純な注釈は簡単に扱え、そこから複雑な利用にまで拡張可能であることが求められます。

Web Annotation Data Modelは、すべての関係者が利用できる単一かつ一貫したモデルです。生産者と消費者の双方の実装コストを最小に抑えるよう努められています。ユースケースを満たす方法は一つであることが強く推奨されますが、既存標準への対応や一つの方法に特に重大な制約がある場合を除きます。データモデルはLinked Dataの基本に基づいて構築されていますが、グラフベースでない実装も十分に構築できるよう設計されています。推論やその他のグラフベースのクエリは、モデル設計において最適化の優先事項とはされていません。

1.2 モデルのシリアル化

本文書中の例では、アノテーション語彙の付録Aに示されたContextを用いて[JSON-LD]でシリアル化されています（これは推奨されるシリアル化形式です）。このフォーマットのメディアタイプは、Annotation Protocol[annotation-protocol]3章で application/ld+json;profile="http://www.w3.org/ns/anno.jsonld" と定義されています。

注釈に記録された情報がリソースのIRIだけの場合、そのIRIが関係の値として用いられます（例1）。リソースについてより多くの情報がある場合は、そのIRIがオブジェクトのidプロパティ値となり、そのオブジェクト自体が関係の値となります（例2参照）。

1.3.1 セレクター関連の適合要件

すべてのセレクターがすべてのメディアタイプで適用できるわけではなく、無意味または正式に定義されていない組み合わせもあります。特定の実装で該当メディアタイプを取り扱わない場合、その実装は特定種別のセレクターを無視しても構いません。

A. メディアタイプとセレクターの対応の表は、本仕様で扱う主なメディアタイプとセレクタータイプの関係を示しています。表中各要素の意味と、実装適合性への影響は次のとおりです。

  • 表中に「✔︎」がある場合、そのセレクタータイプが当該メディアタイプで適用されます。適合実装は、当該メディアタイプを扱う場合、その組み合わせを必ず実装しなければなりません。
  • 表中に「✘」がある場合、そのセレクタータイプは当該メディアタイプで適用されません。適合実装はその組み合わせを無視することが推奨されます。
  • 「?」は、その組み合わせが有効かどうか一般的に特定できない場合を示します（例: フラグメント識別子は特定メディアタイプで定義されており、プレーンテキスト以外の特定テキストメディアタイプにも定義される場合はありますが、表中には記載されていません）。また有用性が不明な場合（例：バイナリ画像のData Positionセレクター等）も含みます。適合実装は、その組み合わせを実装してもよいです。

1.4 用語集

IRI
IRI（国際化リソース識別子）は、URI仕様を拡張し、Unicode文字の利用を可能にするものです。URIはASCII文字のサブセットのみで構成されます。IRIと同等のエンコードされたURI形式への変換アルゴリズムが存在します。IRIは[rfc3987]で定義されています。
リソース
興味の対象となる項目であり、IRIによって識別できる場合があります。
ウェブリソース
リソースのうち、IRIで識別されるものです（Web Architecture [webarch]参照）。ウェブリソースはそのIRIを通じて参照可能な場合があります。
外部ウェブリソース
ウェブリソースのうち、注釈の表現に含まれないもので、ウェブページ、画像、ビデオなどが該当します。外部ウェブリソースは、IRI で参照可能です。
プロパティ
リソースの特徴であり、多くの場合特定のデータ型を持ちます。本モデルの章では、「プロパティ」とは関係以外で、リテラル値（文字列、整数、日付等）を持つものを指します。プロパティの有効値は、オブジェクトではない任意のデータ型、または複数が許容される場合はその型の配列です。
関係
本モデルの章では、「関係」とは、他のリソースを参照したり、注釈の表現内にそのリソースの説明を含めたりする特徴を指します。有効値は、IRIを含む文字列、"id"プロパティを持つオブジェクト、またはこれらの配列（複数が許容される場合）です。
クラス
リソースは、概念的に「クラス」と呼ばれるグループに分類できます。クラスのメンバーはインスタンスと呼ばれます。クラスとの関連付けはタイプ付けを通じて行われます。クラスはIRIで識別され、つまりそれ自体もウェブリソースです。
タイプ
特別な関係であり、クラスのインスタンスを、その所属先クラス(クラス)に関連付けます。
インスタンス
特定のクラスによって表されるリソース群の要素です。

2. ウェブ注釈の原則

Web Annotation Data Modelは、以下の基本原則に基づいて定義されます。

  • アノテーションはリソース間の関係を表す根付き有向グラフです。
  • この関係に関与する主要なリソースには、本文と対象の2種類があります。
  • アノテーションは0個以上の本文を持ち得ます。
  • アノテーションは1個以上の対象を持ちます。
  • 本文リソースの内容は、対象リソースの内容に関連し、通常「〜について」です。
  • アノテーション、本文、対象は、それぞれ独自のプロパティや関係（作成や記述情報含む）を持つ場合があります。
  • アノテーション作成や特定の本文・対象を含む意図は重要なプロパティであり、「モチベーション」リソースで表されます。

以下は、対象（Target）および本文（Body）の性質に関する追加原則です。

  • 対象・本文リソースは、そのIRIだけで特定される内容よりも具体的な場合があります。
  • 特に、
    • 対象・本文リソースがリソースの特定セグメントである場合
    • 対象・本文リソースに特定のスタイルが適用されている場合
    • 対象・本文リソースが特定状態である場合
    • 対象・本文リソースがアノテーション内で特定の役割を果たす場合
    • 上記の複数組み合わせである場合
  • こうした制約付きリソースは、アノテーション／本文／対象とは別個のリソースとされ、「SpecificResource」と呼びます。
  • SpecificResourceは、元となるリソースと、それをより具体化する制約とを参照します。
  • SpecificResourceの同一性は、制約記述とは切り離されています。
  • 本文リソースは複数リソース間からの選択になる場合があります。

アノテーション文書内に記載した本文・対象など外部リソースのプロパティは、クライアントへのヒントとして意図されたものであり、正式な情報とは見なされません。例えば、作成時刻、作成主体、変更時刻、権利表明、フォーマット、言語、テキスト方向などが含まれます。

3. ウェブ注釈フレームワーク

3.1 アノテーション

アノテーションはウェブリソースです。典型的には、1つの本文（コメントやそのほかの説明リソース）と、本文が「〜について」いる1つの対象を持ちます。アノテーションはさらに説明的なプロパティを持つことが多いです。

利用例: アリスは、特定のウェブページについてコメントした投稿を書きました。彼女のクライアントは、その投稿をbodyリソース、ウェブページをtargetリソースとしてアノテーションを作成します。

モデル

用語 型 説明
@context プロパティ JSONがアノテーションとして解釈される際の文脈。
アノテーションは、1つ以上の@context値を必ず持ち、http://www.w3.org/ns/anno.jsonldもその一つでなければなりません。値が一つだけの場合、それは文字列で提供されます。
id プロパティ アノテーションの識別子。
アノテーションは、それを識別するIRIをちょうど1つ持ちます。
type 関係 アノテーションの型。
アノテーションは、1つ以上の型を必ず持ち、その中にAnnotationクラスが含まれている必要があります。
Annotation クラス ウェブアノテーション用のクラス。
Annotationクラスはtypeを用いてアノテーションと関連付けられなければなりません。

アノテーションには1つ以上のbody関係があるべきですが、0でも構いません。

{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno1",
  "type": "Annotation",
  "body": "http://example.org/post1",
  "target": "http://example.com/page1"
}

3.2 本文および対象

ウェブは分散されており、異なるシステムが連携してコンテンツへのアクセスを提供しています。アノテーションは、それらのリソースを本文および対象としてリンクするために使用できます。対象リソースは常に外部ウェブリソースですが、本文はアノテーション内部に埋め込むこともできます。外部ウェブリソースは、その状態の表現を取得するために個別に参照できますが、埋め込み本文は、表現がアノテーション内部に含まれているため参照する必要はありません。

3.2.1 外部ウェブリソース

ウェブリソースはIRIで識別され、リソースのコンテンツのフォーマットや言語など様々なプロパティを持ちます。この情報は、たとえリソースの表現をウェブから取得しなければならない場合でも、アノテーションの一部として記録できます。

利用例: ベアトリスは特許についての長い分析を記録し、音声を自身のウェブサイトにmp3として公開します。その後、mp3を本文、特許のPDFを対象とするアノテーションを作成します。

モデル

用語 型 説明
id プロパティ 本文または対象リソースを識別するIRI。
外部ウェブリソースである本文または対象は必ずリソースのIRI値を持つidをただ1つ持ちます。
format プロパティ ウェブリソースのコンテンツのフォーマット。
本文または対象は、そのフォーマットを1つ持つべきですが、0個以上でもよいです。値は[rfc6838]仕様に従ったメディアタイプであるべきです。
language プロパティ ウェブリソースのコンテンツの言語。
本文または対象は、その言語を1つ持つべきですが、特定できない場合や複数言語を含む場合など0個以上持てます。値は[bcp47]仕様に従った言語コードであるべきです。
processingLanguage プロパティ 改行・ハイフネーション・フォント指定等のテキスト処理アルゴリズムのために用いる言語。
各本文・対象は1つだけprocessingLanguageを持てます。値は[bcp47]仕様に従った言語コードであるべきです。このプロパティが存在せずlanguageが1つのみの場合は、クライアントはその言語を処理用に使うべきです。
textDirection 関係 リソース内テキストの大域的な基本方向。
本文または対象は、ちょうど1つのtextDirectionを持てます。値は下記で定義される方向（ltr、rtl、auto）のいずれかでなければなりません。
ltr インスタンス リソースの値が左から右（left-to-right）方向で明示的に分離されるテキストであることを示します。
rtl インスタンス リソースの値が右から左（right-to-left）方向で明示的に分離されるテキストであることを示します。
auto インスタンス リソースの値が明示的に分離されたテキストであり、その方向を値を使ってプログラム的に決定することを示します。
注記
[iana-media-types]ドキュメントはformatプロパティに使用できる公式なメディアタイプのレジストリです。[w3c-language-tags]記事はlanguageプロパティで実装者が遭遇しうる値の良い概要を提供します。テキスト方向およびauto、ltr、rtlの定義はHTML5[html5]のdir属性に由来します。外部リソースによって提供される情報がアノテーション情報と矛盾する場合、外部リソースが権威的であり、アノテーションの情報は無視されるべき点にも注意してください。

例

例 2: 外部ウェブリソース
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno2",
  "type": "Annotation",
  "body": {
    "id": "http://example.org/analysis1.mp3",
    "format": "audio/mpeg",
    "language": "fr"
  },
  "target": {
    "id": "http://example.gov/patent1.pdf",
    "format": "application/pdf",
    "language": ["en", "ar"],
    "textDirection": "ltr",
    "processingLanguage": "en"
  }
}

3.2.2 クラス

クライアントがウェブリソースのおおまかな種別を事前に知っておくことは有益です。クライアントがビデオを再生できない場合、本文がビデオであると分かれば、不必要に大きなコンテンツストリームのダウンロードを回避できます。明確なメディアタイプを持たないリソース、たとえば多くのデータフォーマットについても、クライアントが text/csv というフォーマットのリソースはメディアタイプの最初の部分にかかわらず単なるプレーンテキストとしてレンダリングすべきではないこと、逆に application/pdf はメインタイプが 'application' でもユーザーエージェントで表示可能なことを知っていると便利です。

利用例: Corinaはスマートフォンでウェブサイトについてのコメントを動画として撮影し、アップロードします。彼女は動画を注釈を通じてウェブサイトと関連付け、彼女のクライアントはシステム利用者へのヒントとしてタイプを追加します。

モデル

用語 型 説明
type 関係 本文または対象リソースの型。
本文または対象は1つ以上のtypeを持てます。その場合、値は下記に示すクラス一覧から選ぶべきですが、他のボキャブラリから選んでも構いません。
Dataset クラス 定義された構造でデータをエンコードするリソース用のクラス。
Image クラス 主に視覚的に表示することを目的とした画像リソースのクラス。
Video クラス 音声の有無に関わらず動画リソースのクラス。
Sound クラス 主に聴覚的に再生されることを目的としたリソースのクラス。
Text クラス 主に読まれることを目的としたリソースのクラス。

例

例 3: 本文と対象の型指定
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno3",
  "type": "Annotation",
  "body": {
    "id": "http://example.org/video1",
    "type": "Video"
  },
  "target": {
    "id": "http://example.org/website1",
    "type": "Text"
  }
}

3.2.3 外部リソースのセグメント

多くのアノテーションは、外部ウェブリソース全体ではなく一部分に関わります。Webの中では [webarch]、 リソースのセグメントはフラグメント部を持つIRIを使って識別されます。このフラグメントは、そのリソースから注目する部分を抽出する方法と、抽出された内容自体の識別の両方を示します。単純なアノテーションの場合、フラグメント部付きIRIを本文や対象の識別子として使えることが価値を持ちます。

利用例: Dawnは画像の特定領域について説明したいと考えます。彼女はクライアント上でその領域をハイライトし説明を入力します。クライアントはそれを適切なフラグメント部を付与したIRIとしてtargetに構築します。

モデル

用語 型 説明
id プロパティ 本文や対象リソースを識別するIRI。
外部ウェブリソースの本文や対象は、必ずリソースのIRI値を持つidを1つだけ持ち、そのIRIにはフラグメント部があってもよいです。
注記
リソースの type や format、language など、その他のプロパティに記載されているプロパティも、全体リソースと同様にリソースのセグメントにも適用可能です。

フラグメント部付きIRIを使う場合の影響や実装上の制約を理解しておくことが重要です。

  • フラグメントはメディアタイプごとに定義されます。たとえばHTMLではIRIフラグメント部分の意味について特定のセマンティクスがあります。
  • すべてのメディアタイプがフラグメント仕様を持つわけではありません。たとえば、Officeドキュメントなどはメディアタイプを持ちウェブ上で配布されていても、IRIのフラグメント部に特有のセマンティクスがないこともあります。
  • メディアタイプにフラグメント定義があったとしても、関心セグメントを十分に厳密に記述できるとは限りません。たとえば、HTMLのフラグメントでは任意のテキスト範囲を記述できません。
  • 何を識別しているのかはメディアタイプを知らなければ確定できません。同じフラグメント文字列が異なる仕様で使われている場合もあり得ます。たとえば、同じフラグメント文字列が画像の矩形領域にもHTML文書のセクションにもなり得ます。
  • フラグメント部付きIRIはリソースセグメントのより詳細な記述方法と互換性がありません。例えば、どの表現を取得するかやスタイル情報の付与、リソースに役割を付与する等はIRIではできません。こうした要件を満たす方法についてはフラグメント・セレクターを含む特定リソースの章で説明します。
  • IRIは不透明な文字列とみなされるため、アノテーションシステムがフラグメントなしIRIで検索しても、フラグメント付きIRIによる注釈は見つからない場合があります。たとえば、ターゲット http://example.com/image.jpg#xywh=1,1,1,1 のアノテーションは http://example.com/image.jpg をその一部であっても簡易検索時には検出されません。
フラグメント部付きIRIの詳細利用については、Best Practices for Fragment Identifiers and Media Type Definitions [fragid-best-practices]を参照してください。

例

例 4: フラグメント部付きIRI
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno4",
  "type": "Annotation",
  "body": "http://example.org/description1",
  "target": {
    "id": "http://example.com/image1#xywh=100,100,300,300",
    "type": "Image",
    "format": "image/jpeg"
  }
}

3.2.4 埋め込みテキスト本文

多くの場合、アノテーションの本文はテキスト形式であり、注釈作成時に個別のIRIを持たず同時に作成されます。この場合、複数のシステムとやりとりせず注釈内に本文テキストを含めることができます。本文は、テキストの言語やフォーマットなど外部ウェブリソースの特性も持つ場合があります。

利用例: Emilyは写真共有サイトで画像が気に入ったというコメントを書きます。クライアントはコメントをアノテーション内部に埋め込み、フランス語でHTMLフォーマットであることも付与します。

モデル

テキスト本文の基本的特性は次のとおりです：
用語 型 説明
id プロパティ テキスト本文を識別するIRI。
本文にはそれを識別するIRIが1つだけあっても構いません。
type 関係 テキスト本文リソースの型。
本文にはTextualBodyクラスが推奨されます。また他のクラスもあっても構いません。
TextualBody クラス 注釈内でテキストリソースを埋め込むために本文に付与するクラス。
本文にはTextualBodyクラスが推奨されます。
value プロパティ テキスト本文の内容となる文字列。
TextualBodyにはvalueプロパティが必須で1つだけ関連付けられます。

システムは、たとえ type プロパティに明示的に含まれていなくても、テキスト本文が上記クラスで説明されている Text クラスを持つと想定すべきです。

外部ウェブリソースのlanguageやformat等のプロパティは、埋め込みテキスト本文リソースにも適用されます。

例

例 5: テキスト本文 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno5",
  "type": "Annotation",
  "body": {
    "type" : "TextualBody",
    "value" : "<p>j'adore !</p>",
    "format" : "text/html",
    "language" : "fr"
  },
  "target": "http://example.org/photo1"
}

3.2.5 文字列型本文

最も単純な本文は、追加情報やプロパティを持たないプレーンテキスト文字列です。この本文の型は非常に単純なアノテーション用途でのみ有用であり、外部から本文を参照する可能性がある場合には非推奨です。

利用例 Franceskaは簡易なコマンドラインクライアントで素早くアノテーションを作りたいと考えます。彼女はテキストファイルでJSONシリアル化を書き、アノテーションサーバーに送信します。

モデル

用語 型 説明
bodyValue プロパティ アノテーションの本文の文字列値。
アノテーションにつきbodyValueは1つだけあり、値は下記要件に従う必要があります。bodyValueプロパティが存在する場合、body関係は併用してはなりません。

この形式が使える場合とその解釈についていくつか制約があります。
文字列型本文は:

  • 必ず 単一のxsd:stringであり、データ型はシリアル化で明示してはなりません。
  • 言語を持ってはなりません。
  • 必ず Textual Bodyのvalueプロパティとして値が解釈されます。
  • 必ず Textual Bodyリソースにformatプロパティtext/plainがあるものと解釈されます。
  • Textual Bodyの他のプロパティ値をアノテーションリソースの同様のプロパティから補完してはなりません。

上記のいずれかの解釈が正しくない場合は、TextualBody構成を必ず使用しなければなりません。

注記
システムは、bodyValue形式を維持するのではなく、TextualBody構成を使用するようにアノテーションを書き換えてもよいです。クライアントがアノテーションを処理する際に言語やフォーマット情報が重要であるため、TextualBody構成が推奨されます。

例

例 6: 文字列型本文 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno6",
  "type": "Annotation",
  "bodyValue": "Comment text",
  "target": "http://example.org/target1"
}
これは次と等価です:
例 7: 同等なテキスト本文
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno7",
  "type": "Annotation",
  "body": {
    "type": "TextualBody",
    "value": "Comment text",
    "format": "text/plain"
  },
  "target": "http://example.org/target1"
}

3.2.6 本文および対象の多重度

いくつかのアノテーションには本文がまったく存在しない場合もあります。例えば、テキストを伴わない単純なハイライトやブックマークです。また、アノテーションが複数の本文や対象を持つことも可能です。この場合、各本文はすべての対象の集合ではなく、それぞれ個別の対象と等しく関連しているものとみなされます。

利用例: Gretchenは、自分の電子書籍の特定領域を緑色でハイライトします。その意味が分かっているため、コメントは付けません。クライアントはアノテーションにスタイルシートを関連付け、本文は一切作りません。

利用例: Hannahは、1つのアノテーションでタグと説明を2つの画像に関連付けます。

モデル

アノテーションに本文がない場合、body 関係は記載しません。

アノテーションの body および／または target 関係は、単一オブジェクトではなく配列として指定可能です。値はリソースのIRI文字列またはオブジェクトのいずれかとなります。

例

例 8: 本文なしアノテーション
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno8",
  "type": "Annotation",
  "target": "http://example.org/ebook1"
}
例 9: 複数の本文または対象
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno9",
  "type": "Annotation",
  "body": [
    "http://example.org/description1",
    {
      "type": "TextualBody",
      "value": "tag1"
    }
  ],
  "target": [
    "http://example.org/image1",
    "http://example.org/image2"
  ]
}

3.2.7 本文の選択

Choiceは、アプリケーションが処理または表示するためにひとつだけ選択すべきリソースの順序付きリストを持ちます。順序はアノテーション作成者や発行者が最も望ましいものから順に並べています。

利用例: Irinaはあるウェブサイトについての議論をフランス語と英語の両方でまとめました。2つの投稿は等価なので両方表示する必要なく、フランス語話者にはフランス語を、他の利用者には英語を見せたいと考えます。クライアントは英語のコメントを最初にリストしたChoiceを作成します。

モデル

用語 型 説明
id プロパティ Choiceを識別するIRI。
Choiceはそれを識別するIRIを1つだけ持てます。
type 関係 リソースの型。
Choiceはtypeを必ず1つもち、その値はCHOICEクラスでなければなりません。
Choice クラス 消費者アプリケーションに対して、一覧されたリソースから1つだけ選んでユーザーに表示し、すべてを表示しないよう伝える仕組み。推奨です。
items 関係 選択候補のリソースのリスト。デフォルトの選択肢が最初に配置されます。
注記
クライアントはリソース選択に任意のアルゴリズムを使うことができ、与えられた情報を使って自動で選ぶべきですが、一覧を表示しユーザーの選択を促してもかまいません。

例

例 10: Choice
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno10",
  "type": "Annotation",
  "body": {
    "type": "Choice",
    "items": [
      {
        "id": "http://example.org/note1",
        "language": "en"
      },
      {
        "id": "http://example.org/note2",
        "language": "fr"
      }
    ]
  },
  "target": "http://example.org/website1"
}

3.3 その他の特性

注釈および外部ウェブリソースが作成、変更、利用された文脈に関する情報を持つことはしばしば重要です。特に以下の点が挙げられます、
  • リソースがいつ作成、変更、または生成されたか
  • 注釈や他のリソースのシリアル化された形式を誰が作成、変更、生成したか、またそれが誰を対象としているか
  • なぜそのリソースが注釈に含まれたのか、あるいは注釈が作成されたのか
  • そのリソースが持つ他の識別子は何か
  • 権利やライセンスに従ってそのリソースはどのように利用できるか
注記
本節で説明した機能に加えて、注釈やモデル内の任意のリソースに他のプロパティが追加されることがあり得ます。この方法の詳細については、[annotation-vocab] の拡張(Extension)セクションを参照してください。

3.3.1 ライフサイクル情報

注釈や参照されたリソースに関与した人物、組織、または機械にはその貢献に対してクレジットを与えるべきであり、これらのリソースが作成された時刻は表示順序の決定や古くなった（場合によっては無関係な）コンテンツのフィルタリングに有用です。アノテーションの作成者は、アノテーションの信頼性を判断するうえでも重要です。アノテーションを作成・シリアル化するために使用されたソフトウェアやその活動が行われた時刻は、広告やデバッグのために有用です。

利用例: Jane はオンラインでレストランのレビューを書き、それが彼女のレビューであることを友人が知り信頼できるように関連付けたいと考えます。彼女のクライアントはアカウントの識別情報とクライアント自身の識別情報、そしてリソースが作成された適切なタイムスタンプを注釈に追加します。

モデル

用語 型 説明
creator 関係 リソースの作成に責任を持つエージェント。これは個人、組織、またはソフトウェア・エージェントであり得ます。
AnnotationおよびBodyには正確に1つのcreator関係があるべきですが、リソースの作成者が匿名を望む場合や複数のエージェントが共同で作業した場合には0個または複数でもあり得ます。これらの関係は他のリソースにも関連付けられることがあります。
created プロパティ リソースが作成された時刻。
AnnotationおよびBodyには正確に1つのcreatedプロパティがあるべきで、1つより多くあってはなりません。他のリソースにもこのプロパティを関連付けることができます。日時は必ずUTCタイムゾーンを"Z"で表したxsd:dateTimeである必要があります。
generator 関係 アノテーションのシリアル化を生成したエージェント。
アノテーションごとに0個以上のgenerator関係が存在し得ます
generated プロパティ アノテーションのシリアル化が生成された時刻。
アノテーションごとに正確に1つのgeneratedプロパティが存在し得ますが、1つより多くあってはなりません。日時は必ずUTCタイムゾーンを"Z"で表したxsd:dateTimeである必要があります。
modified プロパティ 作成後にリソースが変更された時刻。
AnnotationおよびBodyには正確に1つのmodifiedプロパティが存在し得ますが、1つより多くあってはなりません。他のリソースにもこのプロパティを関連付けることがあります。日時は必ずUTCタイムゾーンを"Z"で表したxsd:dateTimeである必要があります。

例

Example 11: ライフサイクル情報
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno11",
  "type": "Annotation",
  "creator": "http://example.org/user1",
  "created": "2015-01-28T12:00:00Z",
  "modified": "2015-01-29T09:00:00Z",
  "generator": "http://example.org/client1",
  "generated": "2015-02-04T12:00:00Z",
  "body": {
    "id": "http://example.net/review1",
    "creator": "http://example.net/user2",
    "created": "2014-06-02T17:00:00Z"
  },
  "target": "http://example.com/restaurant1"
}

3.3.2 エージェント

注釈の作成に関与したエージェントについては、通常それらを識別する IRI だけでは不十分で追加情報が求められます。これには個人なのかグループなのかソフトウェアなのか、実名、アカウントのニックネーム、メールアドレスなどのプロパティが含まれます。

利用例: Kelly は彼女の身元を管理しないシステムに注釈を送信したいが、ニックネームを表示させたいと考えています。彼女のクライアントはこの情報を注釈に追加してサービスに送信します。

モデル

用語 型 説明
id プロパティ エージェントを識別する IRI。
エージェントは識別用の IRI を正確に1つ持つことが推奨され、1つより多くあってはなりません。
type 関係 エージェントの型。
エージェントは下記に示すクラスのうち1つ以上を持つことが推奨されます。
Person クラス 人間のエージェントのクラス。

3.3.3 想定利用者

注釈や他のリソースの作成・管理に関連するエージェントに加えて、そのリソースが意図する消費者エージェントのクラス（想定利用者）を知ることも有用です。これにより、教師対学生のような役割や、推奨年齢層のようなクラスの特性を記録できます。

3.3.5 動機と目的

多くの場合、注釈が作成された理由やテキスト本文が注釈に含まれた目的を理解することは、単に時刻や関与したエージェントを知るだけでなく重要です。これらの理由は、アノテーションの作成動機やテキスト本文を注釈に含める目的を宣言することで提供されます。つまり前節で述べた「誰が」「いつ」に対する「なぜ」の情報です。

利用例: Noelle は将来の参照のためにリソースをブックマークする意図で注釈を付け、見つけやすくするために説明とタグを付けます。彼女のクライアントは、この目的を捉えるためにアノテーションとテキスト本文リソースに適切な動機を追加します。

purpose 関係 テキスト本文が注釈に含まれる理由。
各 TextualBody に対して0個以上のpurposeが関連付けられることがあります。

highlighting インスタンス 対象リソースやそのセグメントに注意を引くためにハイライトする意図のある場合の動機。例えば注釈者が異議を唱える選択テキストを強調する場合など。

3.3.6 権利情報

リソースに対してライセンスや権利表明を関連付け、その利用条件を記述することは一般的な慣行です。これにより利用者は適切にリソースを利用でき、いくつかの自動化システムは使用が許可されているかを確認できます。アノテーション、本文、および対象はそれぞれ異なるライセンスや権利で作成され得るため、各々を個別に記述できます。アノテーション自身以外のリソースの権利は、消費クライアントアプリケーションへの参考的なヒントとみなされます。

利用例: Ophelia は商品のレビューを書き、レビューの著者として知られたいが、レビューと商品を結び付ける注釈自体の利用方法については気にしません。彼女はアノテーションと本文それぞれに別個の権利声明を主張します。対象リソースに対する権利を知らないため、対象には何も指定しません。

3.3.7 その他の識別子

ウェブのような大規模に分散したシステムでは、情報が複製されることがよくあります。アノテーションや関連リソースの出所（プロベナンス）を追跡するために、そのリソースを識別する追加の IRI を記録することが可能です。これらは参照可能な「パーマリンク」であったり、クライアントがオフラインで割り当てた識別子であったり、現在の収集システムがリソースを発見した場所の位置であったりします。

利用例: Petra はアノテーションを作成し、それを個人用と公開用の複数のシステムに送信して保存します。コピーを整合させたいので、彼女は正準的な IRI として UUID を設定し、サービス側でそれに対応する HTTP IRI を割り当てられるようにします。後続のシステムが公開コピーを収集する際、発見した正準 UUID を保持し、元の HTTP IRI を via に移し、自身が管理する IRI に置き換えます。

モデル

用語 型 説明
canonical 関係 Annotation、Body、またはTarget と、その識別性を追跡するために使用されるべき IRI との関係（そのリソースがどこで入手可能であっても同じ）。このプロパティが設定されている場合、システムはそれを変更または削除してはなりません。システムは、事前の合意なしに正準 IRI を割り当てるべきではありません。なぜならそのアノテーションは既に別の場所で正準 IRI を持っている可能性があるためです。
各リソースにつき正準的なcanonical IRIが正確に1つ存在することがあり得ます。
via 関係 Annotation、Body、またはTarget と、それを利用可能にしているシステムがそのリソースを取得した場所の IRI との関係。
各リソースについてviaに0個以上の IRI が提供されることがあります。

例

Example 17: その他の 識別子
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno17",
  "type": "Annotation",
  "canonical": "urn:uuid:dbfb1861-0ecf-41ad-be94-a584e5c4f1df",
  "via": "http://other.example.org/anno1",
  "body": {
    "id": "http://example.net/review1",
    "rights": "http://creativecommons.org/licenses/by/4.0/"
  },
  "target": "http://example.com/product1"
}

4. 特定リソース

上述の手法のみでも、フラグメント付きIRIを使用してリソースの一部を参照するアノテーションを作成できますが、それだけでは不十分な状況が多く存在します。例えば、画像の単純な円形領域や斜め線などはフラグメントでは扱えません。HTMLページ内の任意のテキスト範囲を選択するという注釈の最も単純な概念も、フラグメントではサポートされていません。さらに、分割用途以外にも、リソースの特定状態や表現を取得したり、特定のスタイルを適用したり、アノテーションが利用する際にリソースへ固有の役割を割り当てたり、特定の文脈でのみアノテーションを適用したい場合など、クライアント側で対応が必要となるケースもあります。

Web Annotation Data Modelでは、これらのアノテーション固有の要件を記述するために新しいタイプのリソース「SpecificResource」を導入します。SpecificResourceは、必要に応じてAnnotationとBodyまたはTargetの間に入り、そのAnnotation内での利用方法に関する追加情報を保持します。詳細説明は通常別エンティティとしてSpecificResourceから参照され、異なる要件を満たすため様々なタイプが使用できます。例えば、アノテーションのターゲットが画像上の円形領域であれば、SpecificResourceは円形領域自体となり、セレクターによって記述され、かつ元のImageリソースとも関連付けられます。

SpecificResourceや指定子（Specifier）は、それ自体がIRIを持つ外部ウェブリソースとなる場合（例：セレクター構成の事例）もありますが、アノテーション処理に必要な情報取得のための不要なネットワーク通信を避けるため、これらをアノテーション表現内に含めることが推奨されます。

この文書で定義される追加の具体性のタイプは以下のとおりです。

  • 目的: 元リソースを注釈内に含める意図を記述
  • セレクター: 注釈において対象となる元リソースのセグメントを記述
  • 状態: 注釈における元リソースの表現を記述
  • スタイル: 注釈において元リソースをどのようなスタイルで提示すべきかを記述
  • レンダリング: 注釈作成時にクライアントがリソースをレンダリングしたシステムを記述
  • スコープ: 注釈における元リソースの適用範囲を記述

モデル

用語 型 説明
id プロパティ 特定リソースの識別子。
Specific Resource はちょうど1つのIRIを持つ場合があります。
type 関係 特定リソースのクラス。
Specific ResourceはSpecificResourceクラスを持つべきです。
SpecificResource クラス 特定リソース用のクラス。
SpecificResourceクラスは、他リソースのより具体的な領域や状態としての役割が明確となるよう特定リソースに関連付けられるべきです。
source 関係 特定リソースと、それがより具体的な表現となる元リソースとの関係。
Specific Resourceにはsource関係が正確に1つ存在しなければなりません。sourceリソースは詳細に記述してもよいし、単にIRIであってもかまいません。

同じSpecific Resource／指定子クラスはTargetにもBodyにも利用されます。本節の例はどちらか一方のみですが、モデル自体は両方に共通します。

4.1 外部ウェブリソースの目的

テキスト本文だけでなく、外部ウェブリソースも注釈内に含める動機（Motivation）を与えることができます。これはSpecific Resourceパターンを利用して行われ、Selectorがセグメントを、Stateが表現を記述するのと同じように、注釈文脈内でのリソースの利用方法をpurposeで指定します。

利用例: Qitaraは、都市名の曖昧さを避けるために単なる文字列ではなく都市の識別IRIで写真にタグ付けしたいと考えます。クライアントは検索によって都市の有名なIRIを利用し、その目的割り当て管理のためにSpecific Resourceを作成します。

モデル

用語 型 説明
purpose 関係 ウェブリソースをアノテーションに含める理由。
SpecificResourceにはpurposeを使い0個以上のMotivationを関連付けることができます。

  "id": "http://example.org/anno18",
  "type": "Annotation",
  "body": {
    "type": "SpecificResource",
    "purpose": "tagging",
    "source": "http://example.org/city1"
  },

  }
}

4.2 セレクター

多くのアノテーションでは、リソース全体ではなくその一部をターゲットにしています。そのリソースの一部を「注目セグメント」と呼びます。セレクターはソースリソースからそのセグメントをどのように求めるかを記述します。セレクターの種類はリソースタイプによって異なり、メディアタイプごとにセグメント記述方法が異なります。同じセグメントを異なる手法で指定する複数のセレクターを与えることで、後で発見される可能性を高めたり、消費側のユーザーエージェントが少なくとも1つのセレクターで利用できるようにできます。

利用例: Ramonaはウェブページの選択テキストとデータセットの一部を関連付けたいと考えます。彼女はクライアントで両者を選択し、それぞれBodyとTargetにセレクターを持つSpecificResourceを持つアノテーションを作成します。

モデル

用語 型 説明
selector 関係 Specific Resourceとセレクターの関係。
Specific Resourceには0個以上のselector関係が関連付けられます。複数セレクターは同じ内容を選ぶべきですが、精度が異なる場合もあります。消費側のユーザーエージェントは異なるセグメントが記述されている場合いずれか一つを選ばなければなりません。

例

例 19: セレクター 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno19",
  "type": "Annotation",
  "body": {
    "source": "http://example.org/page1",
    "selector": "http://example.org/paraselector1"
  },
  "target": {
    "source": "http://example.com/dataset1",
    "selector": "http://example.org/dataselector1"
  }
}

4.2.1 フラグメント・セレクター

セグメント選択手法として最もよく知られているのは、表現のメディアタイプにより定義されるIRIのフラグメント部を利用する方法なので、これをセレクター経由で記述手法として許可するのは有用です。これにより既存および将来のフラグメント仕様をSpecific Resourceで統一的に利用できます。どのフラグメント種別が使われているか明確にするため、セレクターはその仕様を参照してもかまいません。

利用例: Sallyは画像の説明にビデオの一部を関連付けたいと考えます。彼女はビデオの時間範囲を選択し、その部分がターゲットを説明している旨をクリックします。クライアントはFragmentSelectorおよびdescribingMotivationを持つSpecificResourceを用いてアノテーションを作成します。

モデル

用語 型 説明
type 関係 セレクターのクラス。
FragmentSelectorは1つだけtypeがあり、その値はFragmentSelectorでなければなりません。
FragmentSelector クラス IRIのフラグメント部を用いてセグメントを記述するリソース。
value プロパティ セグメントを記述するIRIのフラグメント部内容。
FragmentSelector はvalueプロパティをちょうど1つ持たなければなりません。
conformsTo 関係 FragmentSelectorとvalueプロパティ内のIRIフラグメント構文を規定する仕様との関係。
Fragment Selector は仕様へのconformsToリンクを1つ持つべきで、複数指定不可。

FragmentSelectorを直接フラグメント付きIRIを使うのではなく、SpecificResource記述との互換性ある方法として一貫して使うことが推奨されます。消費側アプリケーションは両方の手法に対応すべきです。

以下のIRIはフラグメントの意味論を定義する仕様の例であり、conformsTo関係として利用できます。他のIRIも利用してよいです。

名称 フラグメント仕様 説明
HTML http://tools.ietf.org/rfc/rfc3236 [rfc3236] 例: namedSection
PDF http://tools.ietf.org/rfc/rfc3778 [rfc3778] 例: page=10&viewrect=50,50,640,480
プレーンテキスト http://tools.ietf.org/rfc/rfc5147 [rfc5147] 例: char=0,10
XML http://tools.ietf.org/rfc/rfc3023 [rfc3023] 例: xpointer(/a/b/c)
RDF/XML http://tools.ietf.org/rfc/rfc3870 [rfc3870] 例: namedResource
CSV http://tools.ietf.org/rfc/rfc7111 [rfc7111] 例: row=5-7
メディア http://www.w3.org/TR/media-frags/ [media-frags] 例: xywh=50,50,640,480
SVG http://www.w3.org/TR/SVG/ [SVG11] 例: svgView(viewBox(50,50,640,480))
EPUB3 http://www.idpf.org/epub/linking/cfi/epub-cfi.html [cfi] 例: epubcfi(/6/4[chap01ref]!/4[body01]/10[para05]/3:10)

フラグメントを使うIRIはsource・#・valueを連結して再構成することができます。下記例の場合、最終的なIRIはhttp://example.org/video1#t=30,60になります。

  "id": "http://example.org/anno20",
  "type": "Annotation",
  "body": {
    "source": "http://example.org/video1",
    "purpose": "describing",
    "selector": {
      "type": "FragmentSelector",

  },
  "target": "http://example.org/image1"
}

4.2.2 CSSセレクター

HTMLドキュメントオブジェクトモデルの要素を選択する最も一般的な方法の1つは、CSSセレクター [CSS3-selectors] を使うことです。CSSセレクターは、ウェブページ内の要素への経路を記述するための多様で広くサポートされた手段を提供し、ウェブ注釈の基本的なユースケースの多くをカバーします。CSSセレクターがドキュメントオブジェクトモデルに適合しない表現に適用された場合の結果は定義されていません。

CSSは注釈内のリソースのスタイリングにも利用できますが、このクラスは特にCSSセレクターの仕組みを再利用し、DOMに適合するリソースのセグメントを選択するためのものです。

利用例: Teynikaは、ウェブページ中でメモを書きたい段落を選択します。クライアントはその要素を明確に特定できるCSSパスを計算し、注釈に追加します。

モデル

用語 型 説明
type 関係 セレクターのクラス。
CssSelectorは必ず1つのtypeを持ち、その値はCssSelectorでなければなりません。
CssSelector クラス CSSセレクターリソースの型。
CSSセレクターにはこのクラスが必ず関連付けられなければなりません。
value プロパティ セグメントへのCSS選択パス。
CSSセレクターには必ずちょうど1つのvalueが関連付けられます。
注記
実装者は、相互運用性を最大化するため、スタイリングや変換ではなく、要素や内容の選択に直接貢献するCSSの一般的な機能のみを使うことが推奨されます。

例

例 21: CSSセレクター
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno21",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/page1.html",
    "selector": {
      "type": "CssSelector",
      "value": "#elemid > .elemclass + p"
    }
  }
}

4.2.3 XPathセレクター

XMLやHTML等のDOM（ドキュメントオブジェクトモデル）をサポートするリソース内で要素や内容を選択するもう一つの一般的手法は、XPath選択 [DOM-Level-3-XPath] を使うことです。XPathは構造を通じた経路を記述する際の柔軟性が非常に高いです。XPathセレクターがDOMに適合しない表現に適用された場合の結果は定義されていません。

注記
実装者はHTML5仕様によってパーサーがDOM内に「省略可能なタグ」を補完した要素を追加する点に注意すべきです。XPathは文書内の要素構造ではなくDOMに補完された要素も含めて構築することが推奨されます。

利用例: UlrikaはHTMLページのテーブル内のspan要素を選択し、その内容についてメモを書きます。この要素を明示的に参照するため、クライアントは正確にそれを特定するXPathを作成しターゲットに設定します。

モデル

用語 型 説明
type 関係 セレクターのクラス。
XPathセレクターは必ず1つのtypeを持ち、その値はXPathSelectorでなければなりません。
XPathSelector クラス XPathセレクターリソースの型。
XPathセレクターにはこのクラスが必ず関連付けられなければなりません。
value プロパティ 選択されたセグメントのXPath。
XPathセレクターには必ずちょうど1つのvalueが関連付けられます。
注記
相互運用性を最大化するため、実装者は要素や内容を選択するのに直接寄与するXPathの一般的な機能のみを使うことが推奨されます。

例

例 22: XPathセレクター
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno22",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/page1.html",
    "selector": {
      "type": "XPathSelector",
      "value": "/html/body/p[2]/table/tr[2]/td[3]/span"
    }
  }
}

4.2.4 テキスト引用セレクター

このセレクターは、テキスト範囲をコピーし、それと直前（プレフィックス）、直後（サフィックス）のテキストも含めることで、同じ文字列が複数回現れる場合でも特定する方式です。

たとえば文書が再び "abcdefghijklmnopqrstuvwxyz" であれば、"abcd" をprefix、"efg" を一致部分、"hijk" をsuffixとすれば "efg" を選択できます。

利用例: Valeriaはウェブページ内のタイプミス（'anotation'）を選び、正しい綴り（'annotation'）にすべきとコメントしました。

モデル

用語 型 説明
type 関係 セレクターのクラス。
Text Quote Selectorは必ずちょうど1つのtypeを持ち、その値はTextQuoteSelectorでなければなりません。
TextQuoteSelector クラス 引用（本体と前後抜粋）によってテキストセグメントを記述するセレクターのクラス。
TextQuoteSelectorにはこのクラスが必ず関連づけられなければなりません。
exact プロパティ 選択されるテキスト（正規化後）のコピー。
各TextQuoteSelectorはexactプロパティを必ずちょうど1つ持ちます。
prefix プロパティ 選択テキストの直前に現れる文字列の抜粋。
各TextQuoteSelectorはprefixプロパティを一つだけ持つべきで、複数は持てません。
suffix プロパティ 選択テキストの直後に現れる文字列の抜粋。
各TextQuoteSelectorはsuffixプロパティを一つだけ持つべきで、複数は持てません。

テキストの選択はユニコードのコードポイント（「文字位置」）で行う必要があります。コードユニット等ではいけません。セレクションはグラフェムクラスター内の途中から始まったり終わったりしないようにするべきです。選択は、特に双方向テキストの場合、視覚順序ではなく論理順序に基づく必要があります。ウェブ上のテキスト文字モデルの詳細については [charmod] を参照してください。

テキストはAnnotationに記録する前に正規化されなければなりません。したがってHTML/XMLタグは除去され、文字実体は実際の文字に置換されます。これは注釈対象ドキュメントの内容状態ではなく、Annotationドキュメント内での記録方法にのみ影響します。

prefix、exact、suffixを処理した結果、同じテキスト列が複数マッチした場合、そのすべてを一致として扱うべきです。

注記
コンテンツに著作権や使用権利が主張されている場合、このテキスト選択方法は潜在的に危険です。ユーザーが文書全体を選択して注釈し、それがコピーされ共有されることは望ましくありません。静的テキストかつアクセス・流通制限がある場合、Text Position Selectorの方が適しています。

例

例 23: テキスト引用セレクター
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno23",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/page1",
    "selector": {
      "type": "TextQuoteSelector",
      "exact": "anotation",
      "prefix": "this is an ",
      "suffix": " that has some"
    }
  }
}

4.2.5 テキスト位置セレクター

このセレクターはテキスト範囲の選択開始・終了位置をストリーム内で記録します。位置0は最初の文字の直前、位置1は2文字目の直前という具合です。したがって範囲には開始文字は含まれますが終了文字は含まれません。

例えば文書が "abcdefghijklmnopqrstuvwxyz" の場合、開始4、終了7 なら選択部分は "efg" です。

利用例: Wendyは内容の抜粋やコピーが許可されていない電子書籍のレビューを書きます。クライアントは本体内の開始と終了位置を用いて選択部分を記述します。

モデル

用語 型 説明
type 関係 セレクターのクラス。
Text Position Selectorは必ずちょうど1つのtypeを持ち、その値はTextPositionSelectorでなければなりません。
TextPositionSelector クラス 開始・終了位置に基づいてテキスト範囲を表現するセレクターのクラス。
TextPositionSelectorにはこのクラスが必ず関連付けられていなければなりません。
start プロパティ テキストセグメントの開始位置。全文の最初の文字が位置0、その文字はセグメントに含まれます。
各TextPositionSelectorはstartプロパティを必ずちょうど1つ持ち、その値は非負整数です。
end プロパティ テキストセグメントの終了位置。その文字はセグメントには含まれません。
各TextPositionSelectorはendプロパティを必ずちょうど1つ持ち、その値は非負整数です。

テキストは、文字数カウントの前にText Quote Selectorと同様の方法で正規化されなければなりません。

注記
このセレクターではText Quote Selectorと異なりソース文書からテキストをAnnotationグラフへコピーする必要はありませんが、リソースの変更に対して非常に脆弱です。どんな編集や動的挿入コンテンツでも選択範囲が変化してしまう可能性があるため、Stateを併用して正しい表現を指定するのが推奨されます。

例

例 24: テキスト位置セレクター
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno24",
  "type": "Annotation",
  "body": "http://example.org/review1",
  "target": {
    "source": "http://example.org/ebook1",
    "selector": {
      "type": "TextPositionSelector",
      "start": 412,
      "end": 795
    }
  }
}

4.2.7 SVGセレクター

SvgSelectorは、Scalable Vector Graphics [SVG11] 標準を使用して領域を定義します。これによりユーザーは、円や多角形など非矩形領域をSVGで記述してコンテンツ内から選択できるようになります。SVGはアノテーション内部に埋め込むことも、外部ウェブリソースとして参照することもできます。

SvgSelectorはSVGを使ってリソースの領域を選択します。SVG表現自体の内部セグメントも、FragmentSelectorやSvgSelectorなどのセレクターで選択できます。

利用例: Yadiraはオンラインの古地図に古道を示す斜め領域でタグ付けしたいと考え、クライアントは画像内容に相対するSVGポリゴンを作成します。

モデル

注記
実装者は、相互運用性を最大化するため、領域記述に直接関係するSVGの一般的な機能のみを使用し、スタイリングやトランスフォームではなく、Javascriptやアニメーション、テキスト、その他形状指向でない情報・スタイル情報をSVG要素内に含めることは非推奨です。クライアントはそのような情報が含まれている場合は無視すべきです。

4.2.8 範囲セレクター

ユーザーの選択が広範または表現中の内部境界を跨ぐ場合、正しい内容を堅牢に記述する単一のセレクターを構築するのは難しくなります。Range Selectorは他のセレクターを使って選択範囲の開始点と終了点を識別できます。この方法では最も適切な選択手法で正確に2つのポイントを特定し、それらを結びつけて選択範囲を形成します。選択は開始セレクターの始まりから終了セレクターの始まり直前までのすべてで構成されます。

利用例: Zaraはウェブページ中のテーブルで隣り合う2つのセルについてコメントしたいと考えます。2つのセルを選択し、クライアントは最初のセルと2番目の直後のセルへXPathを作成します。それぞれをstart、endとするRange Selectorを生成します。

モデル

用語 型 説明
type 関係 セレクターのクラス。
Range Selectorは必ずちょうど1つのtypeを持ち、その値はRangeSelectorでなければなりません。
RangeSelector クラス Range Selectorリソースの型。
Range Selectorはこのクラスが必ず関連付けられていなければなりません。
startSelector 関係 範囲の開始（含む地点）を記述するセレクター。
Range SelectorにはstartSelectorが必ずちょうど1つ関連付けられます。
endSelector 関係 範囲の終了（含まない地点）を記述するセレクター。
Range SelectorにはendSelectorが必ずちょうど1つ関連付けられ、startSelectorとendSelectorは同じクラスであるべきです。

例

例 28: 範囲セレクター
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno28",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/page1.html",
    "selector": {
      "type": "RangeSelector",
      "startSelector": {
        "type": "XPathSelector",
        "value": "//table[1]/tr[1]/td[2]"

      "endSelector": {
        "type": "XPathSelector",
        "value": "//table[1]/tr[1]/td[4]"
      }
    }
  }
}

4.2.9 選択の精緻化

リソース全体をセグメント選択するのではなく、セグメントをさらに細かく選択することで、より簡単かつ信頼性・精度の高い指定ができる場合があります。特にパッケージ形式のような他のリソースを含むリソースでは、構成要素が固有識別子を持たない際に選択機構を分解することもできます。これは、セレクター同士を鎖状につなぎ、それぞれが前の結果を精緻化する形で実現します。

利用例: Alexandraは段落とその中の短いフレーズを選びコメントします。クライアントはフレーズをTextQuoteSelectorで、段落を特定するFragmentSelectorを精緻化する形で記録します。

モデル

用語 型 説明
refinedBy 関係 より広いセレクターと、その結果に適用すべきより具体的セレクターとの関係。
1つのセレクターが1つ以上のrefinedByを持つことができます。複数ある場合はいずれも同じ選択範囲になるとみなされます。

例

例 29: 選択の精緻化
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno29",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/page1",
    "selector": {
      "type": "FragmentSelector",
      "value": "para5",
      "refinedBy": {
        "type": "TextQuoteSelector",
        "exact": "Selected Text",
        "prefix": "text before the ",
        "suffix": " and text after it"
      }
    }
  }
}

4.3 状態

状態（State）は、特定のアノテーションで適用されるリソースの意図された状態を記述し、そのリソースの正しい表現を取得するために必要な情報を提供します。ウェブリソースは時間とともに変化するため、状態は、意図した過去バージョンの復元方法を記述するためにも利用できます。またウェブリソースは複数のフォーマットを持つため、特定のフォーマットの取得方法を状態で記述することも可能です。同じ表現を説明する複数の状態を与えることで、消費側ユーザーエージェントが目的の表現を取得できる可能性を高めることができます。

利用例: Britneyは頻繁に内容が変わるウェブページについてコメントを作成します。彼女のクライアントは、注釈の元ターゲットを他のクライアントもできるだけ復元できるようにするための情報を記録します。

モデル

用語 型 説明
state 関係 SpecificResourceとStateとの関係。
各SpecificResourceに対してstate関係が0個以上可能です。複数の状態は同じ表現を説明すべきですが、精度が異なる場合もあり得ます。消費側ユーザーエージェントは異なる表現が記述されている場合は必ず1つ選ぶ必要があります。

状態（States）は、SelectorやStyle情報を処理する前に必ず処理されます。

例

例 30: 状態
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno30",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/page1",
    "state": {
      "id": "http://example.org/state1"
    }
  }
}

4.3.1 時間状態

Time Stateリソースは、そのリソースが注釈に対して適切であるとされる時刻、典型的には注釈作成時の時刻や現在バージョンの永続コピーへのリンクなどを記録します。リソースのタイムスタンプは、RFC 7089 [rfc7089]で記載されるMementoプロトコルにより解決可能です。

利用例: Carlaはニュースサイトのトップページの現時点での状態についてメモし、そのページが頻繁に変わることを指摘します。クライアントは注釈対象ページのバージョンを記述するため現在時刻を含む状態（State）を追加します。

モデル

用語 型 説明
type 関係 Stateのクラス。
TimeStateはちょうど1つのtypeを持ち、値はTimeStateでなければなりません。
TimeState クラス ソースリソースが注釈に対して時間的に適切な表現であることを記述。
Stateにはこのクラスが必ず関連付けられていなければなりません。
sourceDate プロパティ 注釈においてソースリソースを解釈すべきタイムスタンプ。
TimeState毎にsourceDateプロパティが0個以上であり得ます。複数ある場合は、いずれもソースを解釈可能な代替時刻を示します。値は必ずxsd:dateTime形式で、 必ず "Z"でUTCタイムゾーンを指定します。sourceDateがあればsourceDateStartやsourceDateEndは指定不可です。
sourceDateStart プロパティ 注釈においてソースリソースを解釈すべき時間区間の開始時刻。
TimeState毎にsourceDateStartプロパティがちょうど1つあり得ます。値は必ずxsd:dateTime形式で、 必ず "Z"でUTCタイムゾーンを指定します。sourceDateStartが指定されればsourceDateEndも必須です。
sourceDateEnd プロパティ 注釈においてソースリソースを解釈すべき時間区間の終了時刻。
TimeState毎にsourceDateEndプロパティがちょうど1つあり得ます。値は必ずxsd:dateTime形式で、 必ず "Z"でUTCタイムゾーンを指定します。sourceDateEndが指定されればsourceDateStartも必須です。
cached 関係 注釈に適切なソースリソースの表現コピーへのリンク。
TimeState毎にcached関係が0個以上あり得ます。複数ある場合は、いずれも表現の代替コピーを示します。

例

例 31: 時間状態 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno31",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/page1",
    "state": {
      "type": "TimeState",
      "cached": "http://archive.example.org/copy1",
      "sourceDate": "2015-07-20T13:30:00Z"
    }
  }
}

4.3.2 リクエストヘッダー状態

1つのIRIから多様な表現が返るリソースが多く、Specific Resourceがそれらのうちの1つにしか該当しない場合もあるため、正しい表現を取得するために必要なHTTPリクエストヘッダーを記録できることが重要です。HttpRequestStateリソースは、その表現を取得するときに再送信すべきヘッダーの写しを保持します。

利用例: DevinaはHTML・PDF・プレーンテキストなど様々な形で提供されるウェブリソースからPDF表現を取得し、その説明を書きます。彼女は自分の説明がPDF表現のみについてである旨をクライアントに伝え、ターゲット表現の取得方法を記述するStateを追加します。

モデル

用語 型 説明
type 関係 Stateのクラス。
Request Header Stateはちょうど1つのtypeを持ち、値はHttpRequestStateでなければなりません。
HttpRequestState クラス HTTPリクエストヘッダーに基づき注釈に適したソースリソース表現を取得する記述。
Stateにはこのクラスが必ず関連付けられていなければなりません。
value プロパティ HTTPリクエストで送信する全ヘッダーを1つのまとまった文字列として記載。
HttpRequestStateはvalueプロパティを必ずちょうど1つ持たなければなりません。
注記
オリジナルのアノテータのクライアントによってサーバから取得された表現は、必ずしもリクエストヘッダーのみで完全特定できない場合があります。たとえば、クライアントのIPアドレスによって、その国の言語で表現が決まる場合などです。サーバが Content-Location ヘッダーを返した際は、クライアントはリクエストしたIRIでなく、ヘッダーに示されたIRIをAnnotationの target に使うことがあります。

例

例 32: HTTPリクエスト状態
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno32",
  "type": "Annotation",
  "body": "http://example.org/description1",
  "target": {
    "source": "http://example.org/resource1",
    "state": {
      "type": "HttpRequestState",
      "value": "Accept: application/pdf"
    }
  }
}

4.3.3 状態の精緻化

選択精緻化と同様に、リソースの適切な状態を単独のStateリソースとしてではなく、階層的に細分化した操作単位Stateとして指定するとより簡単で信頼性や精度が増す場合があります。これは特に、内部変換を示すStateと外部リクエストを記述するStateの組み合わせを表現する際に適しています。こうした分解は、Stateをセレクターと同じようにチェーン接続することで実現されます。

さらに、Stateによって特定の表現が得られる場合、その表現セグメントを記述するのに特定セレクターが適切なこともあり、Stateがそのようなセレクターで精緻化できるようにもなっています。

利用例: Erinは時間経過で様々なバージョン・フォーマットが存在し得る旅行用電子書籍について、特定バージョンとフォーマットについてコメントします。クライアントは時間を記録するTimeStateと、フォーマットを記録するHttpRequestState、さらに該当フォーマットに適したFragmentSelectorを順に追加します。

モデル

用語 型 説明
refinedBy 関係 より広いStateと、より狭いStateまたはその結果に適用すべきSelectorとの関係。
各StateはrefinedByで1つ以上のStateまたはSelectorにより精緻化されます。複数の場合はどれも等価な結果とみなします。

例

例 33: 状態の精緻化
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno33",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/ebook1",
    "state": {
      "type": "TimeState",
      "sourceDate": "2016-02-01T12:05:23Z",
      "refinedBy": {
        "type": "HttpRequestState",
        "value": "Accept: application/pdf",
        "refinedBy": {
          "type": "FragmentSelector",
          "value": "page=10",
          "conformsTo": "http://tools.ietf.org/rfc/rfc3778"
        }
      }
    }
  }
}

4.4 スタイル

特定のアノテーションやその本文の解釈が、実装間で一貫した描画スタイルに依存している場合があります。画像やビデオなどバイナリコンテンツのアノテーションでは、ターゲットの背景色がアノテーションクライアントから取得できない場合や、デフォルトの色分けが見づらい場合（例：夜空画像の上に黒い長方形でターゲット領域を描画する等）があります。レンダリング情報はCSSスタイルシートおよびそこに定義されたクラス参照で記録します。

利用例: Felicityは文書の2つの段落をハイライトし、それぞれ赤色・黄色でハイライトするようクライアントで選択します。その後、彼女は黄色部分が赤部分に矛盾するとコメントします。クライアントは彼女がターゲットに赤と黄の色分けを選択したことを記録します。

モデル

用語 型 説明
type 関係 スタイルのクラス。
CSSスタイルシートはtypeを持つ場合があり、その値はCssStylesheetでなければなりません。
CssStylesheet クラス CSSを用いてアノテーションに関与するリソースのスタイルを記述するリソース。
このクラスはスタイルシートリソースに関連付けてもよいです。
stylesheet 関係 アノテーションとスタイルとの関係。
各アノテーションについてstylesheetは0または1つあり得ます。
styleClass プロパティ CSS記述で用いられるクラス名で、Specific Resourceに適用されるべきです。
Specific ResourceにstyleClassプロパティが0個以上あり得ます。

CSSスタイルシートはアノテーション自体に関連し、そのコンテンツがアノテーションを構成するリソースに関する描画ヒントを提供します。独自の参照可能なIRIを持っても、アノテーション内に埋め込んでも可です。これは、各リソースごとに単一行のスタイルシートを個別付与するのを避け、ある実装におけるスタイル全体を1つのIRIで参照できるようにするためです。

配信システムは必ずしもスタイルシートが処理されると仮定してはいけません。あくまでもヒントであり要求ではありません。

Specific Resourceの描画時、消費側アプリケーションはstyleClassプロパティがあるか確認すべきです。あれば、該当CSSドキュメントのセレクタを探してcss-valueブロックを適用するよう努めるべきです。Specific ResourceにstyleClass値があっても、アノテーションに関連付けられたstylesheetに対応クラス記述がなければ、そのstyleClassは無視すべきです。

例

例 34: CSSスタイル 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno34",
  "type": "Annotation",
  "stylesheet": "http://example.org/style1",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.org/document1",
    "styleClass": "red"
  }
}
例 35: CSSスタイル（埋め込み）
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno35",
  "type": "Annotation",
  "stylesheet": {
    "type": "CssStylesheet",
    "value": ".red { color: red }"
  },
  "body": "http://example.org/body1",
  "target": {
    "source": "http://example.org/target1",
    "styleClass": "red"
  }
}

4.5 レンダリングソフトウェア

アノテーション作成時、ターゲットリソースの処理または描画に用いられたソフトウェアを記録しておくことは有用です。この情報は後続のシステムが環境を再現し、アノテーションをターゲット表現の適切な部分と正確に結びつけやすくする助けになります。このライフサイクル情報は、同じターゲットへのアノテーション間で変化しやすいため、ターゲットリソース自体でなくSpecific Resourceに関連付けられます。

利用例: Gabrielleはブラウザ上のクライアントで学術論文のPDFをHTMLとしてレンダリングしています。彼女のブラウザは特定ライブラリを使ってPDFをHTML化します。彼女は自分の見ていたHTML表示上の段落に注釈し、クライアントはレンダリングに用いられたライブラリの情報・コメント・ターゲットPDFをアノテーションに記録します。

モデル

用語 型 説明
renderedVia 関係 アノテーション内でターゲットを表すSpecific Resourceと、アノテーション作成時にターゲットの描画に使われたソフトウェアやその他システムの関係。
各Specific Resourceに対してrenderedViaは0個以上あり得ます。
注記
レンダリングシステムには、schema:softwareVersion、アクセシビリティ機能、ラベル、実際のコードへの参照など他のプロパティも関連付けられます。これらの拡張は本仕様の範囲外ですが、詳細は annotation-vocab の拡張セクションを参照してください。

例

例 36: レンダリングソフトウェア
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno36",
  "type": "Annotation",
  "body": "http://example.org/comment1",
  "target": {
    "source": "http://example.edu/article.pdf",
    "selector": "http://example.org/selectors/html-selector1",
    "renderedVia": {
      "id": "http://example.com/pdf-to-html-library",
      "type": "Software",
      "schema:softwareVersion": "2.5"
    }
  }
}

4.6 リソースのスコープ

アノテーション作成時、アノテータが閲覧・利用していたリソースを文脈として含めることが重要になる場合があります。これは、そのページの文脈内でのみ画像のアノテーションが有効であると主張するものではなく、その時そのページを見ていたことを記録したに過ぎません。

利用例: Heatherはあるウェブページ内の画像について、それが本来の組織のロゴではないとコメントします。クライアントは画像が表示されているページ情報も含めますが、注釈はあくまで画像リソース自体に関連付けます。

モデル

用語 型 説明
scope 関係 Specific Resourceと、このアノテーションにおけるその範囲や文脈を提供するリソースとの関係。
各Specific Resourceに対してscopeは0個以上あり得ます。

例

例 37: スコープ 
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/anno37",
  "type": "Annotation",
  "body": "http://example.org/note1",
  "target": {
    "source": "http://example.org/image1",
    "scope": "http://example.org/page1"
  }
}

5. コレクション

アノテーションをまとめてリストとして集約し、「アノテーションコレクション」とすることがよく有用です。このリストは必ず順序付けられており、含まれているアノテーションを参照したり、コレクション自体に関する情報を保持するための手段となります。

コレクションモデルは2つの部分に分かれています。すなわち、リストの識別子や記述を管理する「アノテーションコレクション」と、コレクション内のアノテーションを一覧とする「アノテーションページ」です。

利用例: Ingeborgは出版社で働いており、作者によるスチームパンク小説のコメンタリーをセットの注釈として販売用に変換しました。会社は小説をすでに購入した顧客向けのアドオンおよび新規販売用バンドルとしてこれらを用意したいと考えています。

5.1 アノテーションコレクション

アノテーションコレクションは非常に大きくなる可能性があるため、モデルではコレクション本体と、その構成要素であるページの並びを区別します。コレクションは自身の情報（作成日時や説明情報など、発見や理解の手助けとなる情報）および少なくとも1つ目のアノテーションページへの参照を保持します。最初のページの最初のアノテーションから始め、ページを巡って最後のページの最後のアノテーションまでを追えば、全アノテーションが発見できます。

アノテーションは同時に複数のコレクションに属することができ、コレクションは含まれるアノテーションの作成者等とは別の主体により作成・管理されることがあります。

モデル

用語 型 説明
@context プロパティ JSONをアノテーションコレクションとして解釈するためのコンテキスト。
コレクションは1つ以上の@context値を必ず持ち、そのうちhttp://www.w3.org/ns/anno.jsonldが必ず含まれていなければなりません。
id プロパティ コレクションの識別子。
コレクションは必ずちょうど1つ、識別用のIRIを持ちます。
type プロパティ コレクションの種類。
コレクションは1つ以上の型をもち、その中にAnnotationCollectionクラスが必ず含まれていなければなりません。
AnnotationCollection クラス アノテーションの順序付きコレクションのクラス。
このクラスはtypeを用いてコレクションに必ず関連付ける必要があります。
label プロパティ コレクションの人間可読なラベル（名称）。
コレクションは1つ以上のlabelを持ち、その値は必ず文字列でなくてはなりません。
total プロパティ コレクション内に含まれるアノテーションの総数。
コレクションは1つだけtotalを持ち、もし存在する場合は必ず xsd:nonNegativeInteger でなければなりません。
first 関係 コレクション内に含まれるアノテーションが載っている最初のページ。
アノテーション数が0より大きいコレクションは必ずちょうど1つのfirstページを持ちます。最初のページはコレクション表現内に埋め込んでも、IRIとして与えてもかまいません。
last 関係 コレクション内に含まれるアノテーションの最後のページ。
アノテーション数が0より大きいコレクションはlastページへのIRI参照を持つべきです。

使用目的・知的財産権・プロベナンスその他有用な機能を記述するため、コレクションには他のプロパティを追加可能です。可能な限り本仕様で記載されたものを使うべきですが、適切な他ボキャブラリも使ってよいです。

例

例 38: アノテーションコレクション
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/collection1",
  "type": "AnnotationCollection",
  "label": "Steampunk Annotations",
  "creator": "http://example.com/publisher",
  "total": 42023,
  "first": "http://example.org/page1",
  "last": "http://example.org/page42"
}

5.2 アノテーションページ

アノテーションページはアノテーションコレクションの一部であり、コレクションに含まれる1つまたは複数のアノテーションを順序付きリストとして持ちます。各コレクションは複数ページを持て、ページ間のnextやprevリンクをたどることで移動できます。

モデル

用語 型 説明
@context プロパティ JSONをアノテーションコレクションページとして解釈するためのコンテキスト。
ページがコレクション内に埋め込まれていない場合は、1つ以上の@context値を必ず持ち、そのうちhttp://www.w3.org/ns/anno.jsonldが必ず含まれていなければなりません。埋め込まれている場合は付与すべきでありません。
id プロパティ ページの識別子。
ページは必ずちょうど1つ、識別用のIRIを持ちます。
type プロパティ ページの型。
ページは1つ以上の型を持ち、中にAnnotationPageクラスが必ず含まれていなければなりません。
AnnotationPage クラス アノテーションページのクラス。
このクラスはtypeを用いてページに必ず関連付ける必要があります。
partOf 関係 ページと、それが属するアノテーションコレクションとの関係。
各ページはpartOf関係を1つだけ持つべきで、値はコレクションのIRIまたは少なくともidを含むコレクションのプロパティを一部またはすべて持つオブジェクトです。
items 関係 ページに収められたアノテーションのリスト。
各ページには1つ以上のアノテーション配列が必ず items に格納されます。
next 関係 コレクションを構成するページ列での次ページの参照。
現在のページがコレクションの最後でないときは、続くページのIRIが必ず参照されます。
prev 関係 コレクションを構成するページ列での前ページの参照。
現在のページがコレクションの最初でないときは、直前ページのIRI参照があるべきです。
startIndex プロパティ itemsリストの最初のアノテーションがコレクション内で何番目かを示す相対位置。最初のページの最初の項目は0番とみなされます。
各ページはstartIndexを1つだけ持ち、1つより多く持ってはなりません。値は必ず xsd:nonNegativeIntegerでなければなりません。

例

例 39: アノテーションページ
{
  "@context": "http://www.w3.org/ns/anno.jsonld",
  "id": "http://example.org/page1",
  "type": "AnnotationPage",
  "partOf": {
    "id": "http://example.org/collection1",
    "label": "Steampunk Annotations",
    "total": 42023
  },
  "next": "http://example.org/page2",
  "startIndex": 0,
  "items": [
    {
      "id": "http://example.org/anno1",
      "type": "Annotation",
      "body": "http://example.net/comment1",
      "target": "http://example.com/book/chapter1"
    },
    {
      "id": "http://example.org/anno2",
      "type": "Annotation",
      "body": "http://example.net/comment2",
      "target": "http://example.com/book/chapter2"
    }
  ]
}

D. 本文およびターゲットの集合

この節は参考です。

複数のターゲットに注釈を付けることは可能ですが、その注釈の意味は各本文が各ターゲットに独立して適用されることになります。これは、全てのターゲットが注釈の正確な理解に必要な場合など、注釈者の意図と異なる場合があります。こうした要件を注釈者が表現できるように、Choiceに似たリソース、例えばComposite（順不同）やList（順序あり）が利用できます。

このパターンの技術的な実装は、Choiceと実質的に同一のため難しくはありませんが、クライアントが人間ユーザーの操作区別を認識できるUIの実装は非常に困難であることが分かっています。そのため、本付録で将来的な検討事項として言及します。

利用例: Karinは一連のウェブページをまとめて自分の研究仮説の証拠としてコメントします。クライアントは、そのウェブページ集合に固有の順序がないためCompositeを生成します。

利用例: Lanaは本の中のページ群を重要であるとタグ付けします。本のページには順序があり、クライアントはその順を維持するためListを生成します。

利用例: Melanieは複数の画像にポートレートであるという分類注釈を付与します。この分類は各画像に独立に適用されるため、クライアントはIndependentsリソースでそれらをグループ化します。

提案モデル

用語 型 説明
id プロパティ セットを識別するIRI。
セットリソースはちょうど1つの識別IRIを持つ場合があります。
type 関係 リソースの型。
セットは下記から1つのtypeクラスを必須で持つ必要があります。

F. Candidate Recommendation 終了基準

この節は参考です。

この仕様がProposed Recommendationに進むには、以下の各機能を少なくとも2つの独立した実装で備えている必要があります。各機能は異なる製品群で実装されてもよく、単一製品がすべての機能をサポートする必要はありません。

機能一覧

終了基準評価の観点から、次が「機能」とみなされます：

  • Annotationクラスとその必須プロパティ
  • 注釈に関連するAgentクラスと必須プロパティ
  • アノテーション本文として利用されるリソースに関連するAgentクラスと必須プロパティ
  • 埋め込みTextualBodyクラスと必須プロパティ
  • アノテーション本文として利用される外部ウェブリソース
  • アノテーション本文として利用されるChoiceリソース
  • アノテーション本文として利用されるSpecificResourceクラスと必須プロパティ
  • アノテーション対象として利用される外部ウェブリソース
  • アノテーション対象として利用されるSpecificResourceクラスと必須プロパティ
  • AnnotationCollectionクラスと必須プロパティ
  • AnnotationPageクラスと必須プロパティ

与えられた機能の有無で動作が変化しないソフトウェアは、CRフェーズ終了目的上、その機能を実装しているとはみなされません。
