RFC 9931

HTTP/1.1 における楽観的なプロトコル移行のセキュリティ上の考慮事項

このページは IETF RFC 9931（B. Schwartz、2026 年 3 月）の非公式な日本語の抜粋訳で、IETF の承認を受けておらず、全文訳ではありません。第 4.1 節の第 3 段落と図 1 の具体的な攻撃例を省略し、明示した編者の非操作的な要約に置き換えています。他のプロトコル要件と防御規定は原文に沿って翻訳しています。原文の著作権、ライセンス、免責事項、著者表示を保持しています。公式英語版を基準とし、省略箇所は公式第 4.1 節で確認してください。

概要

HTTP/1.1 では、クライアントは既存の接続で新しいプロトコルへの切り替えを要求できます。この文書は、その要求が確認される前にクライアントが送るデータに関するセキュリティ上の考慮事項を説明し、関連する問題を防ぐため RFC 9112 と RFC 9298 に新たな要件を追加します。¶

1. 概要

この文書は、同じ接続で HTTP/1.1 から別のプロトコルへ切り替える際のセキュリティ上の考慮事項を説明し、次を提供します。¶

  • 関連する標準の確認。¶

  • 移行の確認前にクライアントがデータを送る場合に生じ得るセキュリティリスクの検討。¶

  • 既存のアップグレードトークンのセキュリティ評価。¶

  • 実装および今後の標準文書への指針。¶

[HTTP/1.1] と [CONNECT-UDP]への更新は、新たな規範的要件を含め、それぞれ第 8 節と第 6.3節に記載されています。¶

2. 要件を表す用語

この文書のキーワード "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", "OPTIONAL" は、ここに示すようにすべて大文字で記載された場合に限り、BCP 14 [RFC2119] [RFC8174] に従って解 釈します。¶

3. 背景

HTTP/1.1 [HTTP/1.1] 以降では、一つの接続を多数のリクエストに使えます。HTTP/2 [HTTP/2] と HTTP/3 [HTTP/3]では、各リクエストをストリーム ID で明示的に区別するため、多重化できます。一方 HTTP/1.1 のリクエストは厳密に順次処理され、前のリクエストの終了によって次のリクエストを暗黙に区別します。¶

HTTP/1.1 は、接続の残りの部分で使用するプロトコルをクライアントが変更できる唯一の HTTP バージョンでもあります。この移行を要求する仕組みは二つあります。一つは Upgrade ヘッダーフィールド（[HTTP]、 第 7.8 節）です。リクエストに含めると、その接続で HTTP/1.1 以外のプロトコルを使いたいことを示します。サーバーが変更を受け入れると、101（Switching Protocols、プロトコル切り替え）ステータスコードを返します（[HTTP]、 第 15.2.2 節）。¶

もう一つは HTTP CONNECT メソッドです（第 9.3.6 節 、[HTTP]）。指定されたホストとポートへ TCP 接続を確立したいことを示します。受け入れた場合、サーバーは 2xx（Successful、成功）応答を返し、要求の受理と TCP 接続の確立を示します。それ以降、この TCP 接続は HTTP/1.1 接続ではなく TCP トンネルとして動作します。¶

どちらの仕組みでもサーバーは要求を拒否できます。例えば 第 7.8 節 （[HTTP] ）には次の記述があります。¶

その接続で現在のプロトコルを使い続けたいサーバーは、受信した Upgrade ヘッダーフィールドを無視してもかまいません（ MAY ）。¶

また 第 9.3.6 節 （[HTTP] ）には次の記述があります。¶

サーバーは、空または無効なポート番号を対象とする CONNECT リクエストを拒否しなければなりません（ MUST ）。通常は 400（Bad Request、不正なリクエスト）で応答します。¶

アップグレードの拒否は一般的であり、次のようなさまざまな理由があります。¶

  • サーバーがクライアントの示したどのアップグレードトークン（提案された新しいプロトコル）もサポートしていないため、HTTP/1.1 を使い続けます。¶

  • このリソースへのこのリクエストでは、提案されたプロトコルへ移行しても HTTP/1.1 より改善しないと分かっているため、サーバーは HTTP/1.1 で応答します。¶

  • サーバーがプロトコルをアップグレードする前にクライアント認証を要求するため、401（Authentication Required、認証が必要）を返し、Authorization 応答ヘッダーフィールドでチャレンジを提示します（[HTTP]、 第 11.6.2 節）。¶

  • リソースが移動したため、サーバーは 3xx（Redirection、リダイレクト）を返します（[HTTP]、 第 3.4 節）。¶

同様に、サーバーは次のような場合に HTTP CONNECT リクエストを拒否することがよくあります。¶

  • サーバーが HTTP CONNECT をサポートしていません。¶

  • サーバーポリシーで指定された宛先が許可されていません。¶

  • 宛先を解決できない、到達できない、または接続を受け入れません。¶

  • プロキシが処理の継続前にクライアント認証を要求します。¶

要求を拒否した後、サーバーはその接続で受信するバイトを引き続き HTTP/1.1 として解釈します。¶

第 7.8 節 （[HTTP] ）には、次の記述もあります。¶

クライアントは、リクエストメッセージを完全に送信するまで、接続上でアップグレード後のプロトコルを使い始めることはできません（メッセージの途中で送信するプロトコルを変更することはできません）。¶

つまり、リクエストメッセージの送信完了は、新しいプロトコルを使い始めるための 必要 条件です。ただしサーバーが拒否する可能性があるため、 十分 条件ではないことを明確にする必要があります。¶

クライアントは、要求したプロトコル移行をサーバーが受け入れる可能性が高いと予測する場合があります。例えば、あるアップグレードトークンの要求が最近成功していれば、同じトークンを使う後続の要求も成功すると期待できます。その予測が正しければ、応答を待たずに新しいプロトコルの最初のバイトを直ちに「楽観的に」送ることで、遅延を減らせることがよくあります。この文書は、その「楽観的」動作のセキュリティへの影響を検討します。¶

4. 考えられるセキュリティ上の問題

HTTP/1.1 接続に二つの当事者（クライアントとサーバー）しか関わらない場合、プロトコル移行は新たなセキュリティ問題を生みません。双方はもともと、相手がいつでも任意のデータを送ることに備える必要があるためです。しかし要求や応答に第三者のデータが含まれる場合、HTTP 接続には三者以上が関わることがあります。例えばブラウザー（第一者）がオリジン（第二者）へ送る要求のパス、ヘッダー、内容を、別オリジンのウェブサイト（第三者）が制御する場合です。WebSocket [WEBSOCKET]など移行後のプロトコルも、第三者が選んだデータの伝送によく使われます。¶

第三者のデータ源を信頼できない場合、そのデータは「攻撃者の制御下」にある可能性があります。そのようなデータと楽観的なプロトコル移行の組み合わせは、二つの重大なセキュリティ問題を生じさせます。¶

4.1. リクエストスマグリング

リクエストスマグリング攻撃（[HTTP/1.1]、 第 11.2 節）では、攻撃者が制御するデータが追加の HTTP リクエストとしてサーバーに解釈されるよう選ばれます。これにより攻撃者は、クライアント自身の要求発行ルールを回避しながら、クライアントを装って要求できます。両者の間を流れるデータの解釈が異なる場合、リクエストスマグリングが起こり得ます。¶

サーバーが移行要求を受け入れれば後続のバイトを新しいプロトコルとして解釈し、拒否すれば HTTP/1.1 として解釈します。しかしクライアントは、応答のステータスコードを受け取るまで、どちらの解釈になるか分かりません。新しいプロトコルを楽観的に使うと、その中の攻撃者が制御するデータを、サーバーがクライアントの追加 HTTP リクエストとして解釈する危険が生じます。¶

【編者による要約。RFC 原文の翻訳ではありません】原文の具体的な攻撃例は省略します。信頼できないデータが接続単位の認証の信頼境界を越える危険を扱う箇所です。原文の認証（[TLS]、 第 4.4.2 節）と要求の意味論（[HTTP]、 第 9.3.3 節）への参照は背景理解のため残しますが、メッセージ、ペイロード、操作手順は掲載しません。¶

4.2. パーサーの脆弱性の悪用

関連する別の種類の攻撃は、プロトコルの解釈の不一致を利用してサーバーの要求解析処理の脆弱性を悪用します。これは HTTP クライアントをサーバーが信頼していても、移行後のデータ源は信頼していない場合に当てはまります。HTTP 要求データの一部または全部を攻撃者が制御しないという前提でソフトウェアが開発されていると、楽観的送信がその前提を崩し、HTTP 要求パーサーの脆弱性を露呈させる可能性があります。¶

5. 運用上の問題

サーバーが移行要求を拒否しても、その接続は引き続き HTTP/1.1 に使えます。拒否に応じて接続を閉じる一般的な要件はなく、同じサーバーへの追加要求が見込まれる場合、接続を維持すると性能面で有利です。そのため、通常は移行の拒否を理由に接続を閉じるのは適切ではありません。¶

6. 既存のアップグレードトークンを使う HTTP Upgrade への影響

この節では、執筆時点で使われていると考えられる登録済みアップグレードトークン [IANA-UPGR] の一部について、この文書の考慮事項の影響を説明します。¶

6.1. "TLS"

「TLS」系のアップグレードトークンは [RFC2817]で定義され、サーバーが拒否する可能性も適切に指摘されています。クライアントがこれを無視して TLS データを楽観的に送っても、有効な HTTP/1.1 にはなりません。TLS 接続の最初のオクテットは 22（ContentType.handshake）でなければならず、これは HTTP/1.1 のメソッドに許される文字ではないためです（ [TLS] の 第 5.1 節 と [HTTP/1.1] の 第 3 節を参照）。準拠する HTTP/1.1 サーバーはこれを解析エラーとし、以後の要求を処理せずに接続を閉じます。¶

6.2. "WebSocket"/"websocket"

第 4.1 節 （[WEBSOCKET] ）には次の記述があります。¶

クライアントは開始ハンドシェイクを送信した後、追加のデータを送る前にサーバーの応答を待たなければなりません（ MUST ）。¶

したがって WebSocket では、HTTP Upgrade の楽観的な使用はすでに禁止されています。また、クライアントからサーバーへ送るフレームに高エントロピーのマスキングを要求します（第 5.1 節 、[WEBSOCKET]）。¶

6.3. "connect-udp"

第 5 節 （[CONNECT-UDP] ）には次の記述があります。¶

クライアントは UDP プロキシ要求への応答を受け取る前に、HTTP データグラムで UDP パケットを楽観的に送り始めてもかまいません（ MAY ）。¶

しかし HTTP/1.1 では、この「プロキシ要求」は HTTP Upgrade リクエストです。攻撃者が制御できる UDP 宛先アドレスが無効な場合など、拒否されやすい状況があります。また「connect-udp」のストリームには、クライアント機器上の別のアプリケーションから来た UDP パケットなど、信頼できないデータが含まれ得ます。そのためリクエストスマグリングが可能になります。これを避けるため、本文は上の記述を次のように置き換え、HTTP/1.1 での楽観的送信を除外します。¶

クライアントは、使用する HTTP バージョンが HTTP/2 以降である場合に限り、UDP プロキシ要求への応答前に HTTP データグラムで UDP パケットを楽観的に送り始めてもかまいません（ MAY ）。リクエストスマグリングの危険があるため、HTTP/1.x で UDP パケットを楽観的に送ってはなりません（ MUST NOT ）。¶

6.4. "connect-ip"

「connect-ip」アップグレードトークンは [CONNECT-IP]で定義されています。 第 11 節 （[CONNECT-IP] ）は HTTP/1.1 でクライアントがパケットを楽観的に送ることを禁止し、この問題を回避しています。¶

7. 今後のアップグレードトークンへの指針

ここで説明したセキュリティ上の問題を軽減または解消する設計例がすでにいくつかあり、今後の仕様にも適用できる可能性があります。¶

  • HTTP Upgrade の楽観的な使用を禁止する（第 4.1 節 、[WEBSOCKET] 、および 第 11 節 、[CONNECT-IP]）。¶

  • HTTP/1.1 の処理を意図的に終了させる固定プリアンブルを埋め込む（第 3.4 節 、[HTTP/2]）。¶

  • クライアントからサーバーへのデータに高エントロピーのマスキングを適用する（第 5.1 節 、[WEBSOCKET]）。¶

今後のアップグレードトークン仕様は、ここで述べたセキュリティ問題を考慮し、実装での回避方法を明確に示すべきです。¶

7.1. リクエストメソッドの選択

「TLS」など一部のアップグレードトークンは、通常の任意の HTTP メソッドで使えるよう定義されています。移行後のプロトコルは HTTP の意味論を維持し、その HTTP リクエストへの応答を伝送します。¶

第 6 節 で挙げた他のトークンは HTTP の意味論を維持しないため、メソッドは関係しません。これらはいずれも内容を持たない GET リクエストに対してのみ規定されています。¶

今後のアップグレードトークン仕様では、HTTP メソッドが他の点で関係せず、要求にメッセージ内容を載せる必要もなければ、内容を持たない GET リクエストに使用を限定するべきです。他のトークンとの一貫性が高まり、サーバー実装が簡単になります。¶

8. HTTP CONNECT の要件

この文書は、本節の残りの記述を含めるよう [HTTP/1.1] を更新します。本節の要件は HTTP/1.1 にのみ適用されます。¶

信頼できない TCP クライアントの代理として CONNECT リクエストを送るプロキシクライアントは、次の一方または両方を実施しなければなりません（ MUST ）。¶

  1. 2xx（Successful、成功）応答を待ってから TCP ペイロードデータを転送する。¶

  2. 「Connection: close」リクエストヘッダーを送る。¶

この二つの動作の少なくとも一方を実装しないプロキシクライアントは、単純なリクエストスマグリング攻撃に対して脆弱です（[HTTP/1.1]、 第 11.2 節）。¶

執筆時点で、一部のプロキシクライアントには上記の脆弱性があると考えられます。緩和策として、プロキシサーバーは CONNECT リクエストを拒否するとき、以後の要求をその接続で処理せず、基盤となる接続を閉じなければなりません（ MUST ）。要求に「close」接続オプションが含まれるかどうかに関係なく適用されます。¶

この緩和策は、正しく実装されたクライアントでも接続確立を遅くすることが多く、特に 407（Proxy Authentication Required、プロキシ認証が必要）を返す場合に影響します。この攻撃に対して脆弱でない HTTP/2 または HTTP/3 を使うことで、性能低下を避けられます。¶

性能の最適化として、クライアントが信頼できない TCP ペイロードを転送する前に 2xx（Successful、成功）応答を待つと分かっている場合（上記の項目 1 に準拠する場合）、プロキシサーバーはこの緩和策を無効にしてもかまいません（ MAY ）。要求の User-Agent ヘッダーフィールドと、準拠に関するユーザーエージェントベンダーの文書を使って、準拠するクライアントを識別できます。¶
