    HTTP ヘッダーフィールドのパラメーターにおける
                               文字エンコーディングと言語の指定

概要

   既定では、Hypertext Transfer Protocol（HTTP）メッセージの
   ヘッダーフィールド値に US-ASCII 符号化文字集合に含まれない文字を
   容易に含めることはできない。RFC 2231 は、
   Multipurpose Internet Mail Extensions（MIME）のヘッダー
   フィールド値内のパラメーターで使用する符号化方式を定義している。
   この文書は、HTTP ヘッダーフィールドに適した符号化方式を規定する。
   これは RFC 2231 の符号化方式の簡略化されたプロファイルと互換性がある。

   この文書は RFC 5987 を廃止する。

1.  はじめに

   US-ASCII 符号化文字集合（[RFC0020]）に含まれない文字を
   HTTP ヘッダーフィールド（[RFC7230]）で使用するのは容易ではない：

   o  HTTP 仕様は、フィールド値での非 US-ASCII 文字の使用を推奨せず、
      これらを拡張 Backus-Naur Form（ABNF）の "obs-text" 生成規則に
      分類している（[RFC7230]、第 3.2 節）。

   o  また、フィールド値の既定の文字符号化方式については規定していない。
      したがって、非 US-ASCII 文字を使用するには、
      個々のフィールド定義で規定するか、
      何らかの帯域外情報を用いる必要がある。

   o  最後に、一部の API は、HTTP メッセージから得られた
      オクテット列を文字列に対応付けるために、
      既定の文字符号化方式を仮定している。例えば XMLHttpRequest
      API（[XMLHttpRequest]）はインターフェイス定義言語の型
      "ByteString" を使用しており、実質的に ISO-8859-1
      文字符号化方式（[ISO-8859-1]）が使用されることになる。



Reschke                      Standards Track                    [Page 2]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   一方、RFC 2231 は MIME ヘッダーフィールド内の
   パラメーターの符号化方式を定義している（[RFC2231]）。MIME は
   HTTP メッセージとは異なり、非バイナリーの転送路で送る必要がある。
   この文書は、HTTP ヘッダーフィールドに適した符号化方式を規定する。
   これは、次の仕様の符号化方式の簡略化されたプロファイルと互換性がある：
   RFC 2231。この方式は、一般的な「パラメーター」
   （"name=value"）構文を使用する任意の HTTP ヘッダーフィールドに適用できる。

   この文書は [RFC5987] を廃止し、その状態を「歴史的」に変更する。
   変更点は付録 Aにまとめている。

      注：この文書の以降の部分では、RFC 2231 の参照は、
      採用した機能の選択理由を説明することのみを目的としている。
      したがって、これらの参照は純粋に参考情報である。

      注：この符号化方式は、HTTP 経由で送られるメッセージのペイロードには適用しない。
      例えば、メディア型 "multipart/form-data" を使用する場合のペイロード
      （[RFC7578]）が該当する。

2.  表記規則

   この文書のキーワード "MUST"、"MUST NOT"、"REQUIRED"、"SHALL"、"SHALL NOT"、
   "SHOULD"、"SHOULD NOT"、"RECOMMENDED"、"NOT RECOMMENDED"、"MAY"、
   および "OPTIONAL" は、次の仕様に記載された意味で解釈する：
   [RFC2119]。

   この仕様は [RFC5234] で定義された ABNF 記法を使用する。
   参照によって取り込むコア規則は、
   [RFC5234] の付録 B.1 に定義された ALPHA（英字）、DIGIT（十進数の 0-9）、HEXDIG
   （十六進数の 0-9/A-F/a-f）、および LWSP（線形空白）である。

   この仕様は [RFC6365] で定義された用語、すなわち
   「文字符号化方式」（以下では「文字エンコーディング」と略す）、
   "charset"、および「符号化文字集合」を使用する。

   これは RFC 2231 とは異なることに注意する。同 RFC は「文字符号化方式」を
   意味する用語として「文字集合」を使用している。

3.   RFC 2231 との比較および符号化方式の定義

   RFC 2231 は MIME の拡張をいくつか定義している。以下の各節では、
   それらを HTTP ヘッダーフィールドに適用するかどうか、および適用方法を説明する。

   要約すると：

   o  パラメーター継続は不要である（第 3.1 節）。





Reschke                      Standards Track                    [Page 3]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   o  文字エンコーディングと言語情報は有用なので、
      単純なサブセットを規定する（第 3.2 節）。また、

   o  符号化語における言語指定は不要である
      （第 3.3 節）。

3.1.  パラメーター継続

   [RFC2231] の第 3 節 は、MIME ヘッダーに適用される
   長さの制限に対処する仕組みを定義している。これらの制限は
   HTTP には適用されない（[RFC7231]、付録 A.6）。

   したがって、パラメーター継続は、この仕様が定義する
   符号化方式には含まれない。

3.2.  パラメーター値の文字エンコーディングと言語情報

   [RFC2231] の第 4 節 は、パラメーター値に言語情報を埋め込む方法と、
   非 ASCII 文字を符号化する方法を規定している。
   これは MIME および HTTP のヘッダーフィールドの
   パラメーターにおける制限に対処するものである。

   しかし、RFC 2231 は実装必須の文字エンコーディングを規定していないため、
   送信者が使用するエンコーディングを決めるのは難しい。
   したがって、この仕様を実装する受信者は、
   "UTF-8" 文字エンコーディング [RFC3629] をサポートしなければならない（MUST）。

   さらに、RFC 2231 は文字エンコーディング情報の省略を認めている。
   この仕様で定義する符号化方式では、
   省略を認めない。

3.2.1.  定義

   通常、拡張パラメーター値の存在は、
   末尾がアスタリスクのパラメーター名で示される。ただし、
   これは単なる慣例であり、拡張パラメーター値は、
   この拡張を使うヘッダーフィールドの定義において
   明示的に規定する必要がある（第 4 節参照）。

   拡張パラメーター値の ABNF を以下に示す：











Reschke                      Standards Track                    [Page 4]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


     ext-value     = charset  "'" [ language ] "'" value-chars
                   ; like RFC 2231's <extended-initial-value>
                   ; (see [RFC2231], Section 7)

     charset       = "UTF-8" / mime-charset

     mime-charset  = 1*mime-charsetc
     mime-charsetc = ALPHA / DIGIT
                   / "!" / "#" / "$" / "%" / "&"
                   / "+" / "-" / "^" / "_" / "`"
                   / "{" / "}" / "~"
                   ; as <mime-charset> in Section 2.3 of [RFC2978]
                   ; except that the single quote is not included
                   ; SHOULD be registered in the IANA charset registry

     language      = <Language-Tag, see [RFC5646], Section 2.1>

     value-chars   = *( pct-encoded / attr-char )

     pct-encoded   = "%" HEXDIG HEXDIG
                   ; see [RFC3986], Section 2.1

     attr-char     = ALPHA / DIGIT
                   / "!" / "#" / "$" / "&" / "+" / "-" / "."
                   / "^" / "_" / "`" / "|" / "~"
                   ; token except ( "*" / "'" / "%" )

   拡張パラメーターの値部分（ext-value）は、
   次の三つの部分からなるトークンである：

   1.  必須（REQUIRED）の文字エンコーディング名（charset）、

   2.  任意（OPTIONAL）の言語情報（language）、および

   3.  実際の値を表す文字列（value-chars）。
       各部分は単一引用符で区切られる。

   文字エンコーディング名と言語タグはいずれも、
   US-ASCII 符号化文字集合に制限され、大文字と小文字を区別せずに照合する
   （[RFC2978] の第 2.3 節および[RFC5646] の
   第 2.1.1 節参照）。

   値部分では、attr-char に含まれない文字を、
   指定した文字エンコーディングでオクテット列に符号化する。
   次に、そのオクテット列を、次の規定に従ってパーセント符号化する：
   [RFC3986] の第 2.1 節。





Reschke                      Standards Track                    [Page 5]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   生成者は "UTF-8"（[RFC3629]）文字エンコーディングを使用しなければならない（MUST）。
   拡張文字エンコーディング（mime-charset）は、
   将来の使用のために予約されている。

      注：受信者は、符号化エラーを堅牢に処理できるようにすることが望ましい。
      例えば、不正な形式や不完全なパーセントエスケープ列、
      または復号できないオクテット列がある。
      この仕様は特定の動作を義務付けない。
      例えば、次の方策はいずれも許容される：

      *  パラメーターを無視する。

      *  復号できないオクテット列を除去する。または、

      *  復号できないオクテット列を代替文字で置き換える。
         例えば Unicode 文字 U+FFFD
         （REPLACEMENT CHARACTER）である。

3.2.2.  歴史的な注記

   RFC 7230 の token 生成規則（[RFC7230]、第 3.2.6 節）は、
   RFC 2231 で使用する生成規則（[RFC2045] の
   第 5.1 節から導入）と異なり、波括弧（"{" および "}"）を除外している。
   したがって、attr-char 生成規則からも
   この二つの文字を除外する。

   ここで定義する <mime-charset> の ABNF は、
   [RFC2978] の第 2.3 節と異なり、単一引用符を
   認めない（RFC 正誤情報 ID 1912 [Err1912] も参照）。実際、
   この文書の執筆時点では、その文字を使った
   文字エンコーディング名は登録されていない。

   RFC 2231 との後方互換性のため、この仕様が定義する符号化方式は、
   一般的なパラメーター構文とは異なり、
   quoted-string 記法を認めない。汎用の
   パーサー部品を使用する実装は、quoted-string
   記法の使用を検出できず、この形式が無効であっても
   受け入れることがある。

   [RFC5987] は ISO-8859-1（[ISO-8859-1]）のサポートも要求していた。
   既存のコードとの互換性のため、受信者には
   このエンコーディングもサポートすることを奨励する。

3.2.3.  例

   "token" を使う非拡張の記法：

     foo: bar; title=Economy



Reschke                      Standards Track                    [Page 6]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   "quoted-string" を使う非拡張の記法：

     foo: bar; title="US-$ rates"

   Unicode 文字 U+00A3（"£"、POUND SIGN）を使用する
   拡張記法：

     foo: bar; title*=utf-8'en'%C2%A3%20rates

   注：Unicode のポンド記号 U+00A3 は、
   UTF-8 文字エンコーディングでオクテット列 C2 A3 に符号化され、
   次にパーセント符号化される。空白文字は attr-char に含まれないため、
   %20 として符号化されることにも注意する。

   Unicode 文字 U+00A3（"£"、POUND SIGN）
   および U+20AC（"€"、EURO SIGN）を使う拡張記法：

     foo: bar; title*=UTF-8''%c2%a3%20and%20%e2%82%ac%20rates

   注：Unicode のポンド記号 U+00A3 は、
   UTF-8 文字エンコーディングでオクテット列 C2 A3 に符号化され、
   次にパーセント符号化される。同様に、Unicode のユーロ記号 U+20AC は、
   オクテット列 E2 82 AC に符号化され、次にパーセント
   符号化される。HEXDIG は大文字と小文字の両方を認めるため、
   受信者は両方を理解しなければならない。また、言語
   情報は任意であるが、文字エンコーディングは任意ではない。

3.3.  符号化語における言語指定

   [RFC2231] の第 5 節 は [RFC2047] の符号化方式を拡張し、
   符号化語での言語指定もサポートする。現在は廃止された HTTP/1.1 仕様の RFC 2616 は、
   RFC 2047 を参照していた
   （[RFC2616]、第 2.2 節）。しかし、どのヘッダー
   フィールドに適用するかは不明確だった。そのため、HTTP/1.1 仕様の現在の改訂版では、
   次の仕様で定義された符号化形式の使用を非推奨とした：RFC
   2047（[RFC7230] の第 3.2.4 節参照）。

   したがって、この仕様はこの機能を含めない。

4.  HTTP ヘッダーフィールド定義での使用指針

   拡張を使用する HTTP ヘッダーフィールドの仕様は、
   第 3.2 節で定義する拡張を使うことを明確に述べることが望ましい。
   簡単な方法は、この仕様を規範的に参照し、
   個々のヘッダーフィールドのパラメーターの ABNF に
   ext-value 生成規則を含めることである。





Reschke                      Standards Track                    [Page 7]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   例えば：

     foo         = token ";" LWSP title-param
     title-param = "title" LWSP "=" LWSP value
                 / "title*" LWSP "=" LWSP ext-value
     ext-value   = <see RFC 8187, Section 3.2>

      注：次の節で定義されたパラメーター値の継続機能、
      すなわち [RFC2231] の第 3 節の機能では、同じ名前の拡張パラメーターを
      複数指定することはできない。継続の処理が
      曖昧になるためである。したがって、
      この拡張を使用する仕様には、この場合を禁止することを勧める。
      これにより RFC 2231 との互換性が保たれる。

      注：この仕様は、末尾がアスタリスクの
      パラメーター名に新しい解釈を自動的に割り当てるものではない。
      前述のとおり、ここで定義する構文を採用するかどうかは、
      非拡張パラメーターの仕様が決める。
      とはいえ、既存の一部の実装では、
      パラメーター名の末尾がアスタリスクの場合に
      この記法へ自動的に切り替えることが知られている。そのため、
      末尾がアスタリスクのパラメーター名を別の用途に使うと、
      相互運用性の問題が生じる可能性が高い。

4.1.  この拡張を使用する場合

   [RFC2277] の第 4.2 節 は、人間が読めるテキストを含む
   プロトコル要素が言語情報を保持できることを要求している。したがって、
   パラメーター値がテキストであり、その言語が分かっている場合には、
   常に ext-value 生成規則を使うことが望ましい。

   また、パラメーター値に US-ASCII 符号化文字集合に
   含まれない文字を保持する必要がある場合にも、
   この拡張を使うことが望ましい（[RFC0020]）。
   Unicode 文字集合のサブセットに限定した新しい
   パラメーターを定義することは許容できない点に注意する。

4.2.  エラー処理

   ヘッダーフィールドの仕様は、同じ名前のパラメーターを
   複数認めるかどうか、およびその処理方法を定義する必要がある。
   この仕様は、拡張構文を使うパラメーターを
   優先することを提案する。これにより、生成者は、
   拡張構文をまだ理解しない受信者の動作を損なわずに、
   両方の形式を使用できる。






Reschke                      Standards Track                    [Page 8]

RFC 8187            Charset/Language Encoding in HTTP     September 2017


   例：

     foo: bar; title="EURO exchange rates";
               title*=utf-8''%e2%82%ac%20exchange%20rates

   この場合、送信者は旧来の受信者向けに ASCII 版のタイトルを提供し、
   この仕様を理解する受信者向けに国際化された版も含める。
   後者の受信者は当然、古い構文よりも
   新しい構文を優先することが望ましい。

5.  セキュリティ上の考慮事項

   この文書で説明した形式は非 ASCII 文字を転送できるため、
   文字の「なりすまし」が可能になる。
   その場合、表示された値が実際とは異なるものに見える。

   また、UTF-8 の復号に関係する
   既知の攻撃シナリオがある。

   両方の話題の詳細は、[RFC3629] の第 10 節を参照。

   さらに、この文書で規定する拡張は、
   一つのパラメーターについて複数の言語版を転送できる。
   同じパラメーターの異なる言語版が同等でない場合、
   このような使用によってなりすまし攻撃が可能になることがある。
   この攻撃が実際に有効かどうかは、
   規定されたパラメーターによって決まる。

6.  IANA に関する考慮事項

   この文書は IANA による措置を必要としない。

付録 A.  次の仕様からの変更： RFC 5987

   この節では、[RFC5987] からの変更を要約する：

   o  文書の題名を「HTTP ヘッダーフィールドのパラメーターにおける
      文字エンコーディングと言語の指定」に変更した。

   o  フィールド値の非 ASCII 文字に関する問題をよりよく説明するため、
      はじめにの節を書き直した。

   o  "ISO-8859-1" エンコーディングをサポートする要件を削除した。

   o  この文書は、汎用の「パラメーター」の ABNF を
      再定義しようとはしなくなった（HTTP には本当に汎用的な
      パラメーター定義がないことが判明した。例えば、
      空白の処理には微妙な違いがある）。

   o  現在の実装のエラー処理の欠陥に関する注記は、
      もはや正確ではないため削除した。

付録 B.  実装報告

   この文書で定義する符号化方式は、現在、四つの
   異なる HTTP ヘッダーフィールドで使用されている：

   o  "Authentication-Control"（[RFC8053] で定義）、

   o  "Authorization"（HTTP ダイジェスト認証で使用され、
      [RFC7616] で定義）、

   o  "Content-Disposition"（[RFC6266] で定義）、および

   o  "Link"（[RFC5988] で定義）。

   この符号化方式は、1997 年の
   [RFC2231] が定義した方式のプロファイル／明確化であるため、
   [RFC5987] の公開時には、多くのユーザーエージェントが "Content-Disposition" での使用を既にサポートしていた。

   [RFC5987] の公開以降、さらに三つの一般的なデスクトップのユーザー
   エージェントがこの符号化方式をサポートした。詳細は
   <http://purl.org/NET/http/content-disposition-tests#encoding-
   2231-char> を参照。現時点では、主要なデスクトップの
   ユーザーエージェントはすべて、現在の版でサポートしている。
