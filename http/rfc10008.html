HTTP QUERY メソッド

概要

本仕様は、HTTP の QUERY メソッドを定義する。QUERY は、リクエスト 対象に対し、同封されたコンテンツを安全かつ冪等な方法で処理し、その後、 処理結果を応答として返すことを要求する。これは POST リクエストに似ているが、QUERY リクエストは、 部分的な状態変更を懸念することなく、自動的に繰り返したり再開したりできる。

1. はじめに

本仕様は、安全かつ冪等なリクエストを行う手段として HTTP QUERY リクエストメソッドを 定義する（第9.2節、[HTTP]を参照）。このリクエストには、 対象リソースがリクエストをどのように処理するかを記述する表現が同封される。

一般的なクエリのパターンは次のとおりである:

GET /feed?q=foo&limit=10&sort=-published HTTP/1.1
Host: example.org

しかし、伝達するデータが大量で、リクエストの URI に符号化できない場合、この パターンには問題が生じる:

  • リクエストは、相互に調整されていない多数のシステムを通過し得るため、 サイズ制限は事前にはわからないことが多い（ただし、第4.1節、[HTTP]では、送信者と 受信者に対し、少なくとも 8000 オクテットをサポートすることを推奨している点に注意）。
  • ある種のデータを対象 URI で表現することは、そのデータを有効な URI に符号化する オーバーヘッドのため、非効率である。
  • リクエスト URI は、リクエストコンテンツよりもログに記録されやすく、 ブックマークに現れることもある。
  • クエリをリクエスト URI に直接符号化すると、クエリ入力のあらゆる組み合わせを 事実上、別個のリソースとして扱うことになる。

GET の使用に代わる方法として、多くの実装は HTTP POST メソッドを使用して、 以下の例に示すようにクエリを実行する。この場合、クエリ 操作への入力は、リクエスト URI のクエリ成分を使用する代わりに、 リクエストコンテンツとして渡される。

クエリを要求するための HTTP POST の典型的な使用例は、次のとおりである:

POST /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded

q=foo&limit=10&sort=-published

しかし、この方法では、リクエストの送信先である リソースとサーバーについての具体的な知識がなければ、安全かつ冪等なクエリが 実行されていることは、容易には明らかにならない。

QUERY メソッドは、GET と POST の使用の間にある隔たりを埋める解決策を提供する。 上記の例は、次のように表現される:

QUERY /feed HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded

q=foo&limit=10&sort=-published

POST と同様に、クエリ操作への入力は、リクエスト URI の一部ではなく、 リクエストのコンテンツとして渡される。しかし、POST とは異なり、このメソッドは明示的に安全かつ 冪等であり、キャッシュ処理や自動再試行などの機能を動作させることができる。

重要なリソースはすべて URI によって識別されるべきであるという設計原則を踏まえ、 本仕様は、サーバーがクエリ自体にも、 特定のクエリ結果にも URI を割り当て、後で GET リクエストに使用できるようにする方法を記述する。

要約すると、次のとおりである:

表1: 関連するメソッドの性質の要約
GET QUERY POST
安全 はい はい そうでない可能性がある
冪等 はい はい そうでない可能性がある
クエリ自体の URI あり（定義による） 任意（Location 応答フィールド） なし
クエリ結果の URI 任意（Content-Location 応答 フィールド） 任意（Content-Location 応答 フィールド） 任意（Content-Location 応答 フィールド）
キャッシュ可能 はい はい はい。ただし、将来の GET または HEAD リクエストに対してのみ
コンテンツ（ボディ） 「定義された意味論なし」 想定される（意味論は対象 リソースに依存） 想定される（意味論は対象 リソースに依存）

1.1. 用語

本文書は、次に定義される用語を使用する: 第3節、[HTTP]。

さらに、URI のクエリ成分に含まれるパラメーターを指す用語として、URI クエリパラメーターを 使用する（第4.2.2節、 [HTTP]）。また、クエリ コンテンツは、リクエストコンテンツ（第6.4節、[HTTP]）のうち、QUERY リクエストのものを指す。

1.2. 表記規則

キーワード "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", および "OPTIONAL" は、本文書では、次に記述されるとおりに解釈される: BCP 14 [RFC2119] [RFC8174]。 ただし、ここに示すように、すべて大文字で現れる場合に限る。

2. QUERY メソッド

QUERY メソッドは、サーバー側のクエリを開始するために使用される。GET メソッドは、 対象 URI によって識別されるリソースの表現を要求する（第7.1節、[HTTP]で定義される）のに対し、QUERY メソッドは、 対象リソースに対し、その対象リソースの範囲内でクエリ操作を実行するよう 要求するために使用される。

リクエストのコンテンツとそのメディアタイプが、クエリを定義する。オリジンサーバーは、 対象リソースに基づいて操作の範囲を決定する。

サーバーは 必ず リクエストを失敗させなければならない。Content-Type リクエストフィールド（[HTTP]、第8.3節）が 欠落しているか、リクエストコンテンツと整合しない場合が、これに該当する。

すべての HTTP メソッドと同様に、対象 URI のクエリ部分は、クエリ対象のリソースの 識別に関与する。それがクエリ結果に直接影響するかどうか、およびどのように影響するかは、 リソースに固有であり、本仕様の範囲外である。

QUERY リクエストは、対象リソースに関して安全である（[HTTP]、第9.2.1節）。 すなわち、クライアントは、対象リソースの状態が変更されることを 要求も期待もしない。これは、サーバーが追加の HTTP リソースを作成し、 それを通じて追加情報を取得できるようにすることを妨げない（2.3節および2.4節を参照）。

さらに、QUERY リクエストは冪等である（[HTTP]、第9.2.2節）。 たとえば接続障害の後など、必要に応じて再試行したり繰り返したりできる。

第15.3節、 [HTTP]に従い、2xx（成功） 応答コードは、リクエストが正常に受信され、理解され、受け入れられたことを示す。

特に、200 (OK) 応答は、クエリが正常に処理され、 その処理結果が応答コンテンツとして同封されていることを示す。

2.1. メディアタイプとコンテンツネゴシエーション

QUERY リクエストの意味論は、リクエストコンテンツと、それに関連付けられた メタデータ（メディアタイプなど）の両方に依存する（[HTTP]、第8.3.1節）。 一般に、コンテンツとメタデータが整合しないリクエストに問題がある場合、必ず 4xx（クライアントエラー）応答によって拒否しなければならない（[HTTP]、第15.5節）。

以下の一覧は、さまざまな失敗の事例を記述し、具体的なステータスコードを推奨する:

  • リクエストにメディアタイプ情報が欠けている場合、定義上、そのリクエストは不正であり、 400（クライアントエラー）などの 4xx ステータスコードで失敗させる必要がある。
  • メディアタイプが指定されているが、リソースでサポートされていない場合、415 (Unsupported Media Type) が適切である。これには特に、 メディアタイプ自体は既知であるものの、対象リソースへの QUERY に固有の 意味論が存在しない場合が含まれる。いずれの場合も、Accept-Query 応答フィールド（第3節）を 使用して、サポートされるメディアタイプをクライアントに通知できる。
  • メディアタイプが指定されているが、実際のリクエストコンテンツと整合しない場合、 400 (Bad Request) を返すことができる。すなわち、サーバーはリクエストコンテンツからメディア タイプを推測し、欠落した値や「誤った」値を上書きすることは許されない （すなわち、「コンテンツスニッフィング」）。
  • メディアタイプが指定され、理解されており、コンテンツも実際にそのタイプと整合するが、 クエリの実際の内容が原因でクエリを処理できない場合、 ステータス 422 (Unprocessable Content) を使用できる。例としては、 存在しないテーブルを指定する、構文上は正しい SQL クエリが挙げられる。
  • クライアントが Accept フィールドを使用して特定の応答メディアタイプを要求し（[HTTP]、第 12.5.1節）、それがリソースでサポートされていない場合、ステータスコード 406 (Not Acceptable) が適切である。

2.2. 等価なリソース

ある QUERY リクエストの等価なリソースは、GET リクエストに応答し、 その QUERY リクエストとその対象を表し、メッセージの コンテンツとメタデータの両方を考慮するリソースである（第6節、[HTTP]）。特に、これには、 表現メタデータ（第8節、[HTTP]）、たとえば コンテンツのメディアタイプが含まれる。

言い換えると、等価なリソースは、QUERY を実装するリソースから、 リクエストコンテンツを組み込むことによって導出される。

等価なリソースという用語は、選択された表現など、 HTTP の他の側面の動作を定義するための手段として使用される。サーバーは、 これらのリソースに URI を割り当てることができるが、その必要はない（第1.1節、[URI]を参照）。割り当てた 場合、これらのリソースには GET リクエストでアクセスできるようになる。

2.3. Content-Location 応答フィールド

成功応答（2xx、第15.3節、 [HTTP]）には、 操作の結果に対応するリソースの識別子を含む Content-Location ヘッダーフィールドを 含めることができる。詳細は、第8.7節、[HTTP]を参照。これは、 クライアントが示された URI に対して GET リクエストを送信することで、 直前に実行されたクエリ操作の結果を取得できる、というサーバーの主張を表す。 示されたリソースは、一時的なものである可能性がある。

付録 A.4.1を 例として参照。

2.4. Location 応答フィールド

サーバーは、QUERY リクエストの等価なリソース（第2.2節）に URI を割り当てることができる。割り当てた 場合、そのリソースの URI を、2xx 応答の Location ヘッダーフィールドに 含めることができる（第10.2.2節、 [HTTP]を参照）。これは、 クライアントが示された URI に GET リクエストを送信することで、クエリコンテンツを再送信せずに、 直前に実行されたクエリ操作を繰り返せる、という主張を表す。このリソースの URI は、 一時的なものである可能性がある。将来のリクエストが失敗した場合、クライアントは、元の QUERY リクエスト対象と、以前に送信したコンテンツを使用して再試行できる。

付録 A.4.2を例として参照。

2.5. リダイレクト

場合によっては、サーバーは、ユーザーエージェントを別の URI にリダイレクトすることで、 QUERY リクエストに間接的に応答することを選択することがある（第15.4節、 [HTTP]を参照）。

ステータスコード 301 (Moved Permanently、[HTTP]、第 15.4.2節）、または 308 (Permanent Redirect、[HTTP]、第 15.4.9節）の応答は、対象リソースが、Location 応答フィールドによって参照される別の URI に恒久的に移動したことを示す（[HTTP]、第 10.2.2節）。同様に、ステータスコード 302 (Found、[HTTP]、第 15.4.3節）、または 307 (Temporary Redirect、[HTTP]、第 15.4.8節）の応答は、対象リソースが一時的に移動したことを示す。これら4つの 場合のいずれにおいても、サーバーは、ユーザーエージェントが同様の QUERY リクエストを Location によって参照される新しい対象 URI に送信することで、元の QUERY リクエストを 達成できることを示唆している。

301 または 302 応答の後で POST を GET リクエストとしてリダイレクトする例外は、 QUERY リクエストには適用されないことに注意。

ステータスコード 303 (See Other、第15.4.4節、 [HTTP]）の QUERY への応答は、 元のクエリが、Location 応答フィールドによって参照される URI に対する通常の取得リクエストで 達成できることを示す（[HTTP]、第 10.2.2節）。HTTP では、これは、新しい対象 URI に GET リクエストを送信することを意味する。 この例は、付録 A.4.3に示されている。

2.6. 条件付きリクエスト

選択された表現（第3.2節、[HTTP]）は、QUERY リクエストの場合、 その QUERY リクエストの等価なリソース（第2.2節）に対する GET リクエストの 場合と同じである。

条件付き QUERY は、選択された表現（すなわち、コンテンツネゴシエーション後のクエリ結果）を、 条件付きヘッダーフィールドに記述された状況においてのみ、 応答で返すことを要求する。これは、第13節、[HTTP]で定義されるとおりである。

付録 A.5を 例として参照。

2.7. キャッシュ処理

QUERY メソッドへの応答はキャッシュ可能であり、キャッシュはこれを使用 してもよい。 その用途は、次に従って後続の QUERY リクエストを満たすことである: 第4節、[HTTP-CACHING]。

QUERY リクエストのキャッシュキー（第2節、[HTTP-CACHING]）には、必ず リクエストコンテンツ（第6節、[HTTP-CACHING]）と関連する メタデータ（第8節、 [HTTP]）を組み込まなければならない。

キャッシュ効率を改善するため、キャッシュは事前に除去 してもよい。 その対象は、リクエストコンテンツと関連するメタデータにおける、意味上重要でない差異である。たとえば、 次のような方法による:

  • コンテンツ符号化を除去する（第8.4節、 [HTTP]）。
  • リクエストの Content-Type フィールドにあるメディアサブタイプの接尾辞が示す、 形式上の慣例に関する知識に基づいて正規化する（たとえば "+json"。第 4.2.8節、[RFC6838]を参照）。
  • リクエストの Content-Type フィールドによって示される、 コンテンツ自体の意味論に関する知識に基づいて正規化する。

このような変換は、キャッシュキーを生成する目的でのみ実行され、 リクエスト自体を変更するものではないことに注意。

クライアントは、"no-transform" キャッシュ指令を使用して（第 5.2.1.6節、[HTTP-CACHING]）、このような変換が 行われないことを望む旨を示すことができる（ただし、この指令は助言にすぎない点に注意）。

QUERY メソッドへの応答のキャッシュ処理は、本質的に GET への応答のキャッシュ処理より複雑である。 キャッシュキーを決定するために、リクエストのコンテンツを完全に読み取る必要が あるためである。QUERY 応答が、Location 応答フィールド（第2.4節）を提供して、 等価なリソース（第2.2節）の URI を示す場合、クライアントは後続のリクエストを GET に切り替えることで、処理を簡素化できる。

2.8. 範囲 リクエスト

QUERY の範囲リクエストの意味論は、GET のものと同じであり、 第14節、[HTTP]で定義されるとおりである。ただし、バイト範囲リクエスト （執筆時点で定義されている唯一の範囲単位）は、 QUERY リクエストの結果に対しては、ほとんど有用ではない。

クエリ形式は、結果集合を制限したり、ページ単位で取得したりする独自の方法を定義することが多い。 たとえば、SQL の "FETCH FIRST ... ROWS ONLY" がある。HTTP 範囲リクエストの代わりに、 これらの組み込み機能が使用されることが想定される。

3. Accept-Query ヘッダーフィールド

"Accept-Query" 応答ヘッダーフィールドは、リソースが QUERY メソッドのサポートを直接通知し、 同時に、使用できる具体的なクエリ形式のメディアタイプを識別するために 使用できる。

Accept-Query は、メディア範囲のリスト（第12.5.1節、 [HTTP]）を、構造化フィールドの 構文 [STRUCTURED-FIELDS]で含む。メディア 範囲は、Token または String から成る List 型の構造化ヘッダーフィールドによって表され、 パラメーターを除いたメディア範囲の値を含む。

メディアタイプのパラメーターがある場合、それらは String 型または Token 型の構造化フィールドパラメーターに 対応付けられる。Token と String の選択に意味上の違いはない。すなわち、 受信者は 変換してもよい（Token から String へ）が、しては ならない のは、受信した型に基づいて異なる処理をすることである。

メディアタイプは、Token に完全には対応しない。たとえば、先頭に数字を使用できる。 このような場合には、String 形式を使用する必要がある。

サポートされるワイルドカードの使用法は、任意のタイプに一致する "*/*" と、 指定されたタイプの任意のサブタイプに一致する "xxxx/*" のみである。

フィールド値に列挙されるタイプの順序に意味はない。

Accept-Query フィールドの値は、同じパスを共有するサーバー上のすべての URI に適用される。 言い換えると、クエリ成分は無視される。同じリソースへのリクエストが 異なる Accept-Query 値を返す場合、最後に受信した新鮮な値（第4.2節、 [HTTP-CACHING]による）が使用される。

たとえば:

Accept-Query: "application/jsonpath", application/sql;charset="UTF-8"

このフィールドの構文は、"Accept" などの他のフィールドの構文と似ているように見えるが （第12.5.1節、 [HTTP]）、これは構造化フィールドであり、 したがって 必ず 次に指定されたとおりに処理しなければならない: 第4節、[STRUCTURED-FIELDS]。

4. セキュリティ上の考慮事項

QUERY メソッドには、すべての HTTP メソッドと同じ一般的なセキュリティ上の考慮事項が 適用される。これらは、[HTTP]に記述されている。

これは、URI（たとえば、クエリ成分）にリクエスト情報を渡すことの 代替として使用できる。URI はリクエストコンテンツよりも、仲介者によってログに記録されたり、 その他の処理を受けたりしやすいため、場合によってはこちらが望ましい。また、 クエリに機密情報が含まれる場合には、URI がログに記録される可能性が、 GET より QUERY を使用する動機となることもある。

サーバーが QUERY リクエストの結果を表す一時的なリソースを作成し（たとえば、 Location または Content-Location フィールドで使用するため）、そのリソースに URI を割り当て、 リクエストにログへ記録できない機密情報が含まれる場合、その URI は 選ぶべきである。その際、元のリクエストコンテンツの機密部分を一切含まないように する。

QUERY コンテンツを誤って正規化するキャッシュや、リソースがコンテンツを処理する方法と 大きく異なる方法で正規化するキャッシュは、 正規化によって誤った一致が生じると、不正確な応答を返す可能性がある。

オリジン間リソース共有 (CORS) を実装するユーザーエージェントからの QUERY リクエストには、 「プリフライト」リクエストが必要となる。QUERY は、CORS セーフリストに登録された メソッドの集合に属していないためである（[FETCH]を参照）。

付録 A. 例

以下の例は、説明のみを目的とする。実際にこれほど短いクエリを送信する必要がある場合、 GET を使用する方がよい可能性が高い。

ほとんどの例で使用するメディアタイプは、"application/x-www-form-urlencoded" である（ブラウザーの ユーザークライアントからの POST リクエストで使用されるもので、"application/x-www-form-urlencoded" 、[URL]で定義される）。Content-Length フィールドは、 簡潔にするため省略している。

A.1. 単純なクエリ

以下は、直接応答を伴う単純なクエリである:

QUERY /contacts HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
Accept: application/json

select=surname,givenname,email&limit=10&match=%22email=*@example.*%22

応答:

HTTP/1.1 200 OK
Content-Type: application/json

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

A.2. QUERY サポートの検出

QUERY のサポートを検出する単純な方法は、OPTIONS（第9.3.7節、 [HTTP]）メソッドによって提供される: 

OPTIONS /contacts HTTP/1.1
Host: example.org

応答:

HTTP/1.1 200 OK
Allow: GET, QUERY, OPTIONS, HEAD

Allow 応答フィールド（第10.2.1節、 [HTTP]）は、指定されたリソースで サポートされるメソッドの集合を示す。

OPTIONS の使用に代わる方法もある。たとえば、サーバーのサポートに関する事前知識なしに、 QUERY リクエストを試みることができる。その場合、サーバーはリクエストを 処理するか、あるいは 405 (Method Not Allowed、第15.5.6節、 [HTTP]）などの 4xx ステータスで、 Allow 応答フィールドを含めて応答することがある。

A.3. QUERY 形式の検出

QUERY でサポートされるメディアタイプは、Accept-Query 応答フィールドを通じて検出できる（第3節）: 

HEAD /contacts HTTP/1.1
Host: example.org

応答:

HTTP/1.1 200 OK
Content-Type: application/xhtml
Accept-Query: application/x-www-form-urlencoded, application/sql

どのリクエストメソッドへの応答に Accept-Query が含まれるかは、 アクセス先のリソースによって異なる。

Accept-Query を確認する代わりに、QUERY リクエストを行い、その後、 415 応答 (Unsupported Media Type、第 15.5.16節、[HTTP]）などの 4xx ステータスの場合に、 Accept 応答フィールドを調べる方法もある（第12.5.1節、 [HTTP]）: 

HTTP/1.1 415 Unsupported Media Type
Content-Type: application/xhtml
Accept: application/x-www-form-urlencoded, application/sql

A.4. Content-Location, Location、および 間接応答

次の各節で説明したように、2.3節および2.4節にある、成功応答の Content-Location および Location 応答 フィールド（2xx、第15.3節、 [HTTP]）は、 GET リクエストに応答する代替リソースを識別する方法を提供する。それは、受信したリクエストの 結果を取得するため、または将来、同じ操作を実行するリクエストを行うためのものである。 付録 A.1の例に戻ると: 

QUERY /contacts HTTP/1.1
Host: example.org
Content-Type: application/x-www-form-urlencoded
Accept: application/json

select=surname,givenname,email&limit=10&match=%22email=*@example.*%22

応答:

HTTP/1.1 200 OK
Content-Type: application/json
Content-Location: /contacts/stored-results/17
Location: /contacts/stored-queries/42
Last-Modified: Sat, 25 Aug 2012 23:34:45 GMT
Date: Sun, 17 Nov 2024, 16:10:24 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

A.4.1. Content-Location の使用

上で受信した Content-Location 応答フィールドは、そのフィールドが現れた QUERY 応答の結果を保持するリソースを識別する:

GET /contacts/stored-results/17 HTTP/1.1
Host: example.org
Accept: application/json

応答:

HTTP/1.1 200 OK
Last-Modified: Sat, 25 Aug 2012 23:34:45 GMT
Date: Sun, 17 Nov 2024, 16:10:25 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Jones",
    "givenname": "Sally",
    "email": "sally.jones@example.com" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

サーバーがこのリソースを無期限に実装し続ける保証はないことに 注意。したがって、エラー応答の後、クライアントは、 新しい代替の場所を取得するために、元の QUERY リクエストを再実行する必要がある。

A.4.2. Location の使用

Location 応答フィールドは、GET に対して、 元の QUERY リクエストと同じ処理およびパラメーターによる現在の結果を返すリソースを識別する。 

GET /contacts/stored-queries/42 HTTP/1.1
Host: example.org
Accept: application/json

この例では、2024-11-17T16:12:01Z に1つのエントリーが削除された （Last-Modified フィールドで示されるとおり）。したがって、応答には2つのエントリーのみが含まれる:

HTTP/1.1 200 OK
Content-Type: application/json
Last-Modified: Sun, 17 November 2024, 16:12:01 GMT
ETag: "42-1"
Date: Sun, 17 Nov 2024, 16:13:17 GMT

[
  { "surname": "Smith",
    "givenname": "John",
    "email": "smith@example.org" },
  { "surname": "Dubois",
    "givenname": "Camille",
    "email": "camille.dubois@example.net" }
]

サーバーが引き続きそのリソースを公開しており、 クエリ結果に変更がないと仮定すると、次を含む後続の条件付き GET リクエスト:

If-None-Match: "42-1"

は、304 (Not Modified) 応答を生じさせる（第 15.4.5節、[HTTP]）。

A.4.3. 間接応答

サーバーは、「間接」応答（第2.5節）を、ステータスコード 303 (See Other、第 15.4.4節、[HTTP]）を使用して送信できる。

次の冒頭にあるリクエストが与えられた場合: 付録 A.4、 サーバーは次のように応答することがある:

HTTP/1.1 303 See Other
Content-Type: text/plain
Date: Sun, 17 Nov 2024, 16:13:17 GMT
Location: /contacts/stored-queries/42

"/contacts/stored-queries/42" にある保存済みクエリを参照。

これは、クエリの結果を返さない点を除けば、 直接応答に Location を含めることに似ている。これにより、サーバーは、 代替リソースの生成または再利用だけを行うことができる。このリソースは、その後、付録 A.4.2に示すように使用できる。

A.5. 条件付きリクエスト

QUERY を実装し、リクエストメディアタイプとして "application/sql" と "application/xslt+xml" [XSLT]をサポートする リソースを考える。このリソースは、"text/csv" として応答を生成できる。クエリ対象のデータセットは、 RFC 文書の情報を含み、クエリは10年単位でグループ化された情報を返す:

Host: example.org
Date: Sun, 7 Sep 2025, 00:00:00 GMT
Content-Type: application/xslt+xml
Accept: text/csv

...XSLT を使用したクエリコンテンツ...

応答:

その後、クライアントはクエリを繰り返すが、 結果が変更された場合にのみ返すよう指定する:

QUERY /rfc-index.xml HTTP/1.1

A.6. その他のクエリ形式

以下の例は、JSON 形式の [RFC8259] RFC 正誤情報データベースへのリクエストを示す。

以下のリクエストは、拡張可能スタイルシート言語変換 (XSLT) を使用して、 年ごと、および定義された正誤情報の種別ごとに集計した正誤情報を抽出する。

QUERY /errata.json HTTP/1.1
Host: example.org
Content-Type: application/xslt+xml
Accept: application/xml, text/csv

<transform xmlns="http://www.w3.org/1999/XSL/Transform"
  xmlns:j="http://www.w3.org/2005/xpath-functions"
  version="3.0">

  <output method="text"/>

  <param name="input"/>

  <variable name="json"
    select="json-to-xml(unparsed-text($input))"/>

  <variable name="sc">errata_status_code</variable>
  <variable name="sd">submit_date</variable>

  <template match="/">
    <text>year, total, rejected, verified, hdu, reported</text>
    <text>&#10;</text>
    <variable name="en" select="$json//j:map"/>
    <for-each-group select="$en"
      group-by="substring-before(j:string[@key=$sd],'-')">
      <sort select="current-grouping-key()"/>
      <variable name="year" select="current-grouping-key()"/>
      <variable name="errata" select=
        "$en[$year=substring-before(j:string[@key=$sd],'-')]">
      <value-of select="concat(
        $year,
        ', ',
        count($errata),

付録 B. メソッド名 'QUERY' の選定

「ハイパーテキスト転送プロトコル (HTTP) メソッドレジストリー」（<http://www.iana.org/assignments/http-methods>）には、 「安全」かつ「冪等」という性質を持つ他の3つのメソッドが、すでに含まれている: "PROPFIND" [RFC4918], "REPORT" [RFC3253], および "SEARCH" [RFC5323]。

これらのいずれかを再利用し、 本仕様が新しいメソッド "QUERY" として定義する内容に合うよう更新することも可能であった。実際、本仕様の初期 段階では "SEARCH" を使用していた。

最終的にメソッド名 "QUERY" が選ばれた理由は、次のとおりである:

  • 他の候補は、リクエストコンテンツに汎用的なメディアタイプ（"application/xml"）を使用する。 リクエストの意味論は、リクエストコンテンツのみに依存する。
  • さらに、それらはいずれも WebDAV の活動に由来し、これについては多くの人が複雑な 感情を抱いている。
  • "QUERY" は、URI のクエリ成分との関係を適切に捉えている。
