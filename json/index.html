     JavaScript Object Notation (JSON) データ交換形式

概要

   JavaScript Object Notation (JSON) は、軽量でテキストベースの、
   言語に依存しないデータ交換形式である。これは
   ECMAScript プログラミング言語標準から派生したものである。JSON は、構造化
   データを可搬的に表現するための少数の書式規則を定義する。

   この文書は、他の JSON 仕様との不整合を解消し、
   仕様上の誤りを修正し、経験に基づく
   相互運用性の指針を提供する。

1.  はじめに

   JavaScript Object Notation (JSON) は、構造化データを
   シリアライズするためのテキスト形式である。これは、ECMAScript プログラミング
   言語標準 第3版 [ECMA-262] で定義されている JavaScript のオブジェクト
   リテラルから派生したものである。

   JSON は、4つのプリミティブ型（文字列、数値、ブール値、
   null）と2つの構造化型（オブジェクトと配列）を表現できる。

   文字列は、0個以上の Unicode 文字 [UNICODE] の並びである。
   この引用は特定のリリースではなく、Unicode の最新バージョンを
   参照していることに注意されたい。Unicode 仕様の将来の
   変更が JSON の構文に影響することは想定されていない。

   オブジェクトは、0個以上の名前と値の
   ペアからなる順序のないコレクションであり、名前は文字列、値は文字列、数値、
   ブール値、null、オブジェクト、または配列である。

   配列は、0個以上の値からなる順序付きの並びである。

1.3.  この改訂について

   RFC 4627 の公開以降の年月で、JSON は非常に
   広く使用されるようになった。この経験により、仕様では
   許可されているものの、相互運用性の問題を引き起こす特定のパターンが明らかになった。

   また、RFC 4627 に関して少数の正誤情報が報告されている
   （RFC Errata ID 607 [Err607] および 3607 [Err3607] を参照）。また、
   RFC 7159 に関しても（RFC Errata ID 3915 [Err3915]、4264 [Err4264]、4336
   [Err4336]、および 4388 [Err4388] を参照）報告されている。

   この文書の目的は、正誤情報を反映し、他の JSON 仕様との
   不整合を解消し、相互運用性の問題につながる可能性のある
   慣行を強調することである。

2.  JSON 文法

   JSON テキストはトークンの並びである。トークンの集合には、6つの
   構造文字、文字列、数値、および3つのリテラル名が含まれる。

   JSON テキストはシリアライズされた値である。以前の一部の
   JSON 仕様では、JSON テキストをオブジェクトまたは
   配列に限定していたことに注意されたい。JSON テキストが必要とされる箇所で
   オブジェクトまたは配列のみを生成する実装は、すべての
   実装がそれらを適合する JSON テキストとして受け入れるという意味で相互運用可能である。

      JSON-text = ws value ws

   次の6つが構造文字である。

      begin-array     = ws %x5B ws  ; [ 左角括弧

      begin-object    = ws %x7B ws  ; { 左波括弧

      end-array       = ws %x5D ws  ; ] 右角括弧

      end-object      = ws %x7D ws  ; } 右波括弧

      name-separator  = ws %x3A ws  ; : コロン

      value-separator = ws %x2C ws  ; , コンマ

   重要でない空白は、6つの構造文字のいずれの前後にも

      ws = *(
              %x20 /              ; スペース
              %x09 /              ; 水平タブ

3.  値

   JSON 値は、オブジェクト、配列、数値、文字列、または
   次の3つのリテラル名のいずれかでなければならない。

      false
      null
      true

   リテラル名は小文字でなければならない。他のリテラル名は
   許可されない。

      value = false / null / true / object / array / number / string

      false = %x66.61.6c.73.65   ; false

      null  = %x6e.75.6c.6c      ; null

      true  = %x74.72.75.65      ; true

4.  オブジェクト

   オブジェクト構造は、0個以上の名前と値のペア
   （またはメンバー）を囲む一対の波括弧で表される。名前は
   文字列である。各名前の後には1つのコロンが置かれ、名前と
   値を分離する。1つのコンマが値とそれに続く
   名前を分離する。オブジェクト内の名前は一意であるべきである。

      object = begin-object [ member *( value-separator member ) ]
               end-object

      member = string name-separator value

   すべての名前が一意であるオブジェクトは、そのオブジェクトを受け取る
   すべてのソフトウェア実装が名前と値の対応について一致するという意味で
   相互運用可能である。オブジェクト内の名前が
   一意でない場合、そのようなオブジェクトを受け取るソフトウェアの動作は
   予測できない。多くの実装は最後の名前と値のペアのみを
   報告する。他の実装はエラーを報告するか、オブジェクトの解析に失敗する。

   また、一部の実装は重複を含むすべての名前と値のペアを
   報告する。

   JSON 解析ライブラリは、オブジェクトメンバーの順序を

   これらの相違の影響を受けないという意味で
   相互運用可能である。

5.  配列

   配列構造は、0個以上の値
   （または要素）を囲む角括弧で表される。要素はコンマで区切られる。

   array = begin-array [ value *( value-separator value ) ] end-array

   配列内の値が同じ
   型である必要はない。

6.  数値

   数値の表現は、多くの
   プログラミング言語で使用されているものと似ている。数値は
   10進数字を用いた基数10で表される。整数部分を含み、
   任意のマイナス記号を前置でき、その後に
   小数部および／または指数部を続けることができる。先頭のゼロは
   許可されない。

   小数部は、小数点の後に1個以上の数字が続く。

   指数部は大文字または小文字の E で始まり、
   その後にプラスまたはマイナス記号を続けることができる。E と任意の
   符号の後には1個以上の数字が続く。

   以下の文法で表現できない数値
   （Infinity や NaN など）は許可されない。

      number = [ minus ] int [ frac ] [ exp ]

      decimal-point = %x2E       ; .

      digit1-9 = %x31-39         ; 1-9

      e = %x65 / %x45            ; e E

      exp = e [ minus / plus ] 1*DIGIT

      frac = decimal-point 1*DIGIT

      int = zero / ( digit1-9 *DIGIT )

      minus = %x2D               ; -

      plus = %x2B                ; +

      zero = %x30                ; 0

   本仕様は、実装が受け入れる数値の範囲
   および精度に制限を設けることを許可する。IEEE 754 binary64
   （倍精度）数値 [IEEE754] を実装するソフトウェアは一般に
   利用可能で広く使用されているため、これが提供する以上の
   精度または範囲を期待しない実装は、実装が期待される精度内で
   JSON 数値を近似するという意味で、良好な相互運用性を
   実現できる。1E400
   や 3.141592653589793238462643383279 のような JSON 数値は、
   それを生成したソフトウェアが、受信側ソフトウェアに対して
   一般に利用可能なものより大きな数値の規模および精度を
   扱う能力を期待していることを示唆するため、潜在的な相互運用性の問題を示す可能性がある。

   このようなソフトウェアが使用される場合、整数であり、
   [-(2**53)+1, (2**53)-1] の範囲にある数値は、実装間で
   その数値が完全に一致するという意味で
   相互運用可能であることに注意されたい。

7.  文字列

   文字列の表現は、C 系
   プログラミング言語で使用される慣例と似ている。文字列は
   引用符で始まり、引用符で終わる。エスケープしなければならない
   文字、すなわち引用符、逆斜線、および制御文字（U+0000
   から U+001F）を除き、すべての Unicode 文字を
   引用符の内側に配置できる。

   任意の文字をエスケープできる。文字が基本
   多言語面（U+0000 から U+FFFF）にある場合、その文字は
   6文字の並びとして表現できる。すなわち、逆斜線、その後に
   小文字の u、その後にその文字のコードポイントを
   符号化する4桁の16進数字が続く。16進数字の A から
   F は大文字でも小文字でもよい。したがって、たとえば、
   逆斜線1文字だけを含む文字列は
   "\u005C" と表現できる。

   あるいは、よく使われる一部の文字には2文字の
   エスケープ表現がある。したがって、たとえば、
   逆斜線1文字だけを含む文字列は、
   より簡潔に "\\" と表現できる。

   基本多言語面にない拡張文字を
   エスケープするには、その文字を12文字の並びとして表現し、

      string = quotation-mark *char quotation-mark

      quotation-mark = %x22      ; "

8.  文字列と文字に関する問題

8.1.  文字エンコーディング

   閉じたエコシステムの一部ではないシステム間で交換される
   JSON テキストは、UTF-8 [RFC3629] を使用して符号化されなければならない。

   以前の JSON 仕様では、JSON テキストを送信する際に
   UTF-8 の使用を要求していなかった。しかし、JSON
   ベースのソフトウェア実装の圧倒的大多数は UTF-8 エンコーディングを
   使用することを選択しており、それが相互運用性を実現する
   唯一のエンコーディングとなっている。

   実装は、ネットワーク経由で送信される JSON テキストの
   先頭にバイトオーダーマーク（U+FEFF）を追加してはならない。相互運用性のため、
   JSON テキストを解析する実装は、バイトオーダーマークの存在を
   エラーとして扱う代わりに無視してもよい。

8.2.  Unicode 文字

   JSON テキストで表現されるすべての文字列が、完全に
   Unicode 文字 [UNICODE] から構成されている場合（どのようにエスケープされていても）、その JSON
   テキストは、それを解析するすべてのソフトウェア実装が
   オブジェクトおよび配列内の名前と文字列値の内容について
   一致するという意味で相互運用可能である。

   しかし、本仕様の ABNF は、メンバー名および
   文字列値に Unicode 文字を符号化できないビット列を含むことを
   許可している。たとえば、"\uDEAD"（単独で対応する相手のない UTF-16
   サロゲート）である。このような事例は、たとえばライブラリが
   UTF-16 文字列を切り詰める際に、その切り詰めが
   サロゲートペアを分割していないか確認しなかった場合に確認されている。そのような値を含む
   JSON テキストを受け取るソフトウェアの動作は予測できない。たとえば、
   実装によって文字列値の長さに異なる値を返したり、
   致命的な実行時例外が発生したりする可能性がある。

8.3.  文字列の比較

   ソフトウェア実装は通常、オブジェクトメンバーの名前が
   等しいかどうかを検査する必要がある。テキスト表現を
   Unicode コード単位の並びに変換し、その後、
   コード単位ごとに数値的に比較する実装は、
   2つの文字列が等しいか等しくないかについてすべての場合に
   実装間で一致するという意味で相互運用可能である。たとえば、
   エスケープされた文字を変換せずに文字列を比較する
   実装は、"a\\b" と "a\u005Cb" が等しくないと
   誤って判断する可能性がある。

9.  パーサー

   JSON パーサーは JSON テキストを別の表現に変換する。
   JSON パーサーは JSON 文法に適合するすべてのテキストを受け入れなければならない。
   JSON パーサーは、JSON ではない形式や拡張を受け入れてもよい。

   実装は、受け入れるテキストのサイズに制限を
   設けてもよい。実装は、ネストの最大深度に
   制限を設けてもよい。実装は、数値の範囲および精度に
   制限を設けてもよい。実装は、文字列の長さおよび
   文字内容に制限を設けてもよい。

   JSON 文法に厳密に適合しなければならない。

12.  セキュリティに関する考慮事項

   一般に、スクリプト言語にはセキュリティ上の問題がある。JSON は
   JavaScript のサブセットだが、代入と呼び出しは除外している。

   JSON の構文は JavaScript から借用されているため、
   その言語の "eval()" 関数を使用して大部分の JSON テキストを解析することができる
   （ただしすべてではない。U+2028 LINE SEPARATOR や U+2029
   PARAGRAPH SEPARATOR などの特定の文字は JSON では正当だが
   JavaScript では正当ではない）。テキストにはデータ宣言とともに
   実行可能コードが含まれる可能性があるため、これは一般に
   許容できないセキュリティリスクとなる。同じ
   考慮事項は、JSON テキストがその言語の構文に適合する
   他のプログラミング言語で eval() に類似した関数を使用する場合にも
   当てはまる。

付録 A.  RFC 7159 からの変更点

   この節では、この文書と
   RFC 7159 の本文との変更点を一覧にする。

   o  第1.2節は、ECMA-262 から JSON
      仕様が削除されたことを反映し、ECMA-404 を規範的
      参考文献とし、「規範的」の特定の意味を説明するために更新された。

   o  第1.3節は、RFC 4627 ではなく
      RFC 7159 に対して提出された正誤情報を反映するために更新された。

   o  第8.1節は、ネットワーク経由で
      送信する際に UTF-8 の使用を要求するよう変更された。

   o  第12節は、ECMAScript の "eval()" 関数を使用することから
      生じるセキュリティリスクの記述をより正確にするために
      更新された。

   o  第14.1節は、ECMA-404 を規範的
      参考文献として含めるよう更新された。

   o  第14.2節は、ECMA-404 を削除し、ECMA-262 の
      バージョンを更新し、正誤情報の一覧を更新するために変更された。
