この仕様は、Webアプリケーションがサンプリングプロファイラーを制御して、 クライアントのJavaScript実行時間を測定できるAPIを記述する。

はじめに

複雑なWebアプリケーションは現在、クライアントにおけるJSの 実行時間の内訳を十分に把握できない。効率的に スタックサンプルを収集できなければ、アプリケーションはコードに 不正確で、大幅な速度低下を招く可能性のあるプロファイリングフックを組み込んで 実行せざるを得ない。サンプリングプロファイラーを操作するAPIを提供することで、 アプリケーションは集計と分析のための豊富な実行データを 最小限のオーバーヘッドで収集できる。

例

次の例は、負荷の高い処理をプロファイリングし、JS実行サンプルを 10msごとに収集する方法を示す。トレースをサーバーへ送信して分析することで、外れ値をデバッグし、JS実行の 特性を集計して調べることができる。

        const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10000 });
        const start = performance.now();
        for (let i = 0; i < 1000000; i++) {
             doWork();
        }
        const duration = performance.now() - start;
        const trace = await profiler.stop();
        const traceJson = JSON.stringify({
          duration,
          trace,
        });
        sendTrace(traceJson);

もう一つの一般的な実際の利用例は、ページ読み込み全体にわたるJSのプロファイリングである。この例ではonload イベントをプロファイリングし、パフォーマンスタイミングデータをトレースとともに送信する。

        const profiler = new Profiler({ sampleInterval: 10, maxBufferSize: 10000 });

        window.addEventListener('load', async () => {
          const trace = await profiler.stop();
          const traceJson = JSON.stringify({
            timing: performance.timing,
            trace,
          });
          sendTrace(traceJson);
        });

        // ページの残りのJS初期化ロジック

定義

サンプルは、ある時点における 瞬間的な実行状態の記述子である。各サンプルには スタックが関連付けられる。

スタックはフレームのリストであり、 最も外側のフレームから最も内側のフレームへ順に並んでいなければならない。

フレームは、スタックのコンテキスト内にある要素で、 現在の実行状態に関する情報を含む。

プロファイリングセッション

プロファイリングセッションは、サンプルを生成する抽象的な主体である。各セッションは次を持つ：

  1. 状態。{started, paused, stopped}のいずれかである。
  2. サンプリング間隔。セッションがサンプルを取得する周期として定義される。

    UAがこの頻度でサンプルを取得することは要求されない。ただし、 より高品質なトレースを生成するため、この頻度でサンプルを取得するよう サンプリングを優先することが推奨される。

  3. プロファイリング対象のエージェント。
  4. プロファイリング対象のレルム。
  5. サンプルのタイムスタンプを測定する際の基準となる時間起点 。
  6. サンプルバッファーサイズ上限。
  7. 取得したサンプルを格納するProfilerTrace。

同じページ上で複数のプロファイリングセッションに対応するべきである。

状態

started状態では、UAは可能な限り、 サンプルを取得するアルゴリズムを[= 並列 に =]実行して、サンプリング間隔が経過するたびにサンプルを取得するべきである。 paused状態とstopped状態では、UAはサンプルを取得するべきではない。

プロファイリングセッションは、started状態で開始しなければならない。

UAは、セッションをstartedからpausedへ、またpausedから startedへ移行させてもよい。

ユーザーエージェントは、閲覧コンテキストがフォアグラウンドにない場合、 プロファイリングセッションのサンプリングを一時停止することが推奨される。

stopped状態のセッションは、started状態またはpaused状態へ移行してはならない。

処理モデル

プロファイリングセッションが与えられたとき、サンプルを取得するには、次の手順を実行する：

  1. ProfilerTrace.samplesの長さが、サンプルバッファーサイズ 上限（プロファイリングセッションに関連付けられたもの）以上の場合、新しいイベントを発火する。その型は samplebufferfullで、対象は関連付けられたProfilerとし、状態をstoppedへ移行し、 戻る。
  2. sampleを、新しいProfilerSampleとする。
  3. sampleのProfilerSample.timestampプロパティを、現在の高分解能時刻に設定する。その時刻の基準は、 プロファイリングセッションの時間起点とする。
  4. stackを、実行コンテキスト スタック（プロファイリングセッションのエージェントに関連付けられたもの）とする。
  5. sampleのProfilerSample.stackIdプロパティを、スタック IDを取得するアルゴリズムをstackに対して実行した結果に設定する。
  6. markerを、プロファイリングセッションに 関連付けられた環境設定オブジェクトが与えられた下で、マーカーを取得するアルゴリズムを実行した結果とする。
  7. markerがnullでない場合、sampleのProfilerSample.markerプロパティを markerに設定する。
  8. sampleを、セッションの ProfilerTraceに関連付けられたProfilerTrace.samplesに追加する。

環境 設定オブジェクトsettingsが与えられたとき、マーカーを取得するには、次の手順を実行する：

  1. candidateMarkerを、トップレベルの処理を最もよく表すProfilerMarker値とする。 その処理はサンプルの取得時に、ユーザーエージェントがプロファイリングセッションのエージェントで実行していたものとし、 該当する値がなければnullとする。
  2. candidateMarkerがnullの場合、nullを返す。
  3. candidateMarkerが表す処理が、[= 同一オリジン =]でない特定の文書のために実行された場合、その比較対象となるオリジンは settingsのものとし、nullを返す。
  4. candidateMarkerと settingsが与えられた下で、マーカーをフィルタリングするを実行した結果を返す。

ユーザーエージェントの内部動作からProfilerMarker値への対応付けは、意図的に 実装定義としている。エンジンのアーキテクチャが異なるためである。規範的でない指針として、ユーザーエージェントには、 作成者スクリプトの実行中はscriptを、ガベージコレクション中はgcを、 算出スタイルの再計算中はstyleを、ボックスの幾何情報の計算中はlayoutを （すなわちリフロー中に）、文書内容のラスタライズ中または合成中はpaintを報告することが期待される。 otherマーカーは、上記のいずれの分類にも当てはまらないユーザーエージェントの処理に 使用される。どの分類も該当しない場合（例えば、エージェントがアイドル状態の場合）、マーカーを取得する アルゴリズムはnullを返し、結果として得られる ProfilerSampleのProfilerSample.marker属性は存在しないままとなる。

同一オリジン検査は、マーカーが、プロファイラーと[= 同一オリジン =]である文書のために実行された処理のみを表すことを保証する。これは、このAPIがクロスオリジンの動作を明らかにしてはならないという要件と整合する。処理のうち、 単一の文書に帰属しないもの—例えば、エンジン全体のガベージコレクション—は、 その検査による制約を受けない。その代わり、そのような処理はプロファイラーがクロスオリジン分離されている場合にのみ公開される。 これはマーカーをフィルタリングするによって強制される。

ProfilerMarkermarkerと環境設定オブジェクトsettingsが与えられたとき、マーカーをフィルタリングするには、 次の手順を実行する：

  1. settingsのクロスオリジン分離 能力がtrueの場合、markerを返す。
  2. markerが"style"または"layout"の場合、markerを返す。
  3. nullを返す。

マーカーをフィルタリングするアルゴリズムは、クロスオリジン分離されていない コンテキストでは、styleマーカーとlayoutマーカーのみがProfilerSampleに現れるという観測可能な動作を生む。 script、gc、paint、otherの各マーカーは抑制される。 この動作の根拠は、マーカーの条件付き公開を参照。ユーザー エージェントは、オプトインの仕組み（例えば、オリジントライアルトークンや文書ポリシー）を提供してもよい。その仕組みは、 特定の環境設定オブジェクトについて、マーカーをフィルタリングするが返す集合を拡大する。そのようなオプトインは、 オリジンをまたいでマーカーを公開してはならない。

stackに束縛された実行コンテキストスタックが与えられたとき、スタックIDを取得するには、次の 手順を実行する：

  1. stackが空の場合、undefinedを返す。
  2. headをstackの最上位要素とし、tailを、 stackから最上位要素を取り除いた残りとする。
  3. parentIdを、tailに対してスタックIDを取得するを再帰的に呼び出した結果とする。
  4. frameIdを、headに対してフレームIDを取得するを呼び出した結果とする。
  5. frameIdがundefinedの場合、parentIdを返す。
  6. profilerStackを、新しいProfilerStackとし、そのProfilerStack.frameIdは frameIdと等しく、ProfilerStack.parentIdはparentIdと等しいものとする。
  7. profilerStackと ProfilerTrace.stacksに対して要素IDを取得するを実行した結果を返す。

実行 コンテキストがcontextに束縛されて与えられたとき、フレームIDを取得するには、次の手順を実行する：

  1. contextに関連付けられた[= レルム =]が、 プロファイリングセッションに関連付けられたレルムと一致しない場合、undefinedを返す。
  2. instanceを、関数 インスタンス（contextに関連付けられたもの）と等しいものとする。
  3. scriptOrModuleを、 contextに関連付けられたScriptOrModuleと等しいものとする。
  4. |attributedScriptOrModule : ScriptOrModule|を、次の アルゴリズムを実行した結果と等しいものとする：
    1. |scriptOrModule|がnullでない場合、|scriptOrModule|を返す。
    2. |instance|が組み込み関数オブジェクトの場合、ScriptOrModuleのうち、 |instance|を呼び出した関数を含むものを返す。

      上記のロジックの目的は、アクセスできないスクリプトから呼び出された組み込み関数が トレースに公開されないことを保証することであり、その呼び出し元のScriptOrModuleを 帰属先として使用する。

      「[...] |instance|を呼び出した関数を含むScriptOrModule」 は、より厳密に定義するべきである。スタック上の最も上にある実行コンテキストで、 ScriptOrModuleを定義するものを利用してこれを提供できるが、理想的ではない-- 組み込み関数を実行コンテキストスタックへ追加する別の仕組みが（理論上は） 存在する可能性があり、その場合、この帰属付けは無効になる。

    3. それ以外の場合、nullを返す。
  5. |attributedScriptOrModule|がnullの場合、undefinedを返す。
  6. |attributedScript : Script|を、 |attributedScriptOrModule|.[[\HostDefined]]から取得した[= スクリプト =]とする。
  7. |attributedScript|が[= クラシックスクリプト =]であり、そのエラーの 抑制を表す真偽値がtrueと等しい場合、undefinedを返す。

    この検査は、クロスオリジンのスクリプトに由来するスタックフレームを含めないことを保証する。そのスクリプトは、 CORSクロスオリジン応答で提供されたものである。この用途をより適切に反映するよう、エラーの抑制の名前を 変更することを検討してもよい。

  8. frameを、新しいProfilerFrameとする。
  9. frameのProfilerFrame.nameを、関数インスタンス名のうち、 |instance|に関連付けられたものに設定する。
  10. |scriptOrModule|がnullでない場合：
    1. scriptを、スクリプトのうち、 scriptOrModule.[[\HostDefined]]から取得したものとする。
    2. resourceStringを、基底URL（scriptのもの）と等しいものとする。
    3. ProfilerFrame.resourceIdを、要素IDを取得するを resourceStringとProfilerTrace.resourcesに対して実行した結果に設定する。
    4. frameのProfilerFrame.lineを、行の1を基点とするインデックスに設定する。その行は、 |script|内でinstanceが定義されている行とする。
    5. frameのProfilerFrame.columnを、列の1を基点とするインデックスに設定する。その列は、 |script|内でinstanceが定義されている列とする。
  11. frameと ProfilerTrace.framesに対して要素IDを取得するを実行した結果を返す。

list内のitemの要素IDを取得するには、次の手順を実行する：

  1. list内に、各構成要素がitemと等しい要素が存在する場合、そのインデックスを返す。
  2. それ以外の場合、itemをlistの末尾に追加し、そのインデックスを返す。

Profilerインターフェイス

      [Exposed=(Window, Worker)]
      interface Profiler : EventTarget {
        readonly attribute DOMHighResTimeStamp sampleInterval;
        readonly attribute boolean stopped;

        constructor(ProfilerInitOptions options);
        Promise<ProfilerTrace> stop();
      };

各Profilerには、正確に一つのプロファイリングセッションが関連付けられていなければならない。

sampleInterval属性は、関連付けられた プロファイリングセッションのサンプリング間隔を、DOMHighResTimeStampとして表した値を反映しなければならない。

stopped属性は、プロファイリングセッションの状態が stoppedである場合に限り、trueでなければならない。

new Profiler(options)

new Profiler(options)は、型が ProfilerInitOptionsであるオブジェクトoptionsが与えられた下で、次の手順を実行する：
  1. optionsの{{ProfilerInitOptions/sampleInterval}}が0未満の場合、 RangeErrorを投げる。
  2. |globalObject|を、現在のグローバルオブジェクトとする。
  3. |globalObject|がWindowまたはWorkerGlobalScopeである場合：
    1. ポリシー値を 取得する。対象は|globalObject|の"js-profiling-mode"とし、 |profilingMode|をその結果とする。
    2. |profilingMode|が"eager"でも"lazy"でもない場合：
      1. ポリシー値を 取得する。対象は|globalObject|の"js-profiling"とし、 |jsProfilingEnabled|をその結果とする。
      2. |jsProfilingEnabled|がfalseの場合、"NotAllowedError" DOMExceptionを投げる。
  4. それ以外の場合、"NotAllowedError" DOMExceptionを投げる。
  5. 次のような新しいプロファイリングセッションを作成する：
    1. 関連付けられたサンプリング間隔は、ProfilerInitOptions.sampleInterval またはUAが対応する、その次に小さい間隔に設定される。
    2. 関連付けられた時間起点は、|globalObject|の時間起点と等しい。
    3. 関連付けられたサンプルバッファーサイズ上限は、{{ProfilerInitOptions/maxBufferSize}}に設定される。
    4. 関連付けられた[= エージェント =]は、周囲のエージェントに設定される。
    5. 関連付けられた[= レルム =]は、現在のレルム レコードに設定される。
    6. 関連付けられたProfilerTraceは、 «[{{ProfilerTrace/resources}} → «», {{ProfilerTrace/frames}} → «», {{ProfilerTrace/stacks}} → «», {{ProfilerTrace/samples}} → «»]»に設定される。
  6. 新しく作成したプロファイリングセッションに関連付けられた、新しいProfilerを返す。

stop()メソッド

プロファイラーを停止し、トレースを返す。このメソッドは、次の手順を実行しなければならない：

  1. 関連付けられた[= プロファイリングセッション =]の状態がstoppedの場合、[= 次の値で 拒否されたプロミス =]を返す。その値は"InvalidStateError" DOMExceptionとする。
  2. [= プロファイリングセッション =]の状態をstoppedに設定する。
  3. |p:Promise|を、[= 新しいプロミス =]とする。
  4. 次の手順を[= 並列に =]実行する：
    1. [= プロファイリングセッション =]を停止するために、[= 実装定義 =]の処理を実行する。
    2. |p|を、プロファイラーの[= プロファイリングセッション =]に関連付けられた{{ProfilerTrace}}で解決する。
  5. |p|を返す。

stop()の呼び出し後に取得されたサンプルは、プロファイリング セッションに含めるべきではない。

ProfilerTrace辞書

      typedef DOMString ProfilerResource;

      dictionary ProfilerTrace {
        required sequence<ProfilerResource> resources;
        required sequence<ProfilerFrame> frames;
        required sequence<ProfilerStack> stacks;
        required sequence<ProfilerSample> samples;
      };

resources属性は、ProfilerResourceリストのうち、サンプルを 取得するアルゴリズムによって設定されたものを返さなければならない。

frames属性は、サンプルを取得する アルゴリズムによって設定されたProfilerFrameリストを返さなければならない。

stacks属性は、サンプルを取得する アルゴリズムによって設定されたProfilerStackリストを返さなければならない。

samples属性は、サンプルを取得する アルゴリズムによって設定されたProfilerSampleリストを返さなければならない。

V8トレース イベント形式 およびGecko プロファイル形式に着想を得た、 この表現は、容易かつ効率的にシリアライズできるよう設計されている。

ProfilerSample辞書

        enum ProfilerMarker { "script", "gc", "style", "layout", "paint", "other" };

        dictionary ProfilerSample {
          required DOMHighResTimeStamp timestamp;
          unsigned long long stackId;
          ProfilerMarker? marker;
        };

timestampは、初期化された値を返さなければならない。

stackIdは、初期化された値を返さなければならない。

markerは、サンプルを取得するアルゴリズムによって初期化された値を返すか、 マーカーが設定されなかった場合は存在しないものでなければならない。公開可能なマーカー値の集合は、 マーカーをフィルタリングするアルゴリズムによって制御される。

クロスオリジン分離されたコンテキストでは、マーカーをフィルタリングするアルゴリズムは、 ProfilerMarker列挙のすべての値を返す。分離されていないコンテキストでは、styleと layoutのみを返すため、それ以外のマーカーは抑制される（marker属性は、 対応するProfilerSampleに存在しない）。

ProfilerStack辞書

        dictionary ProfilerStack {
          unsigned long long parentId;
          required unsigned long long frameId;
        };

parentIdは、初期化された値を返さなければならない。

frameIdは、初期化された値を返さなければならない。

ProfilerFrame辞書

        dictionary ProfilerFrame {
          required DOMString name;
          unsigned long long resourceId;
          unsigned long long line;
          unsigned long long column;
        };

nameは、初期化された値を返さなければならない。

resourceIdは、初期化された値を返さなければならない。

lineは、初期化された値を返さなければならない。

columnは、初期化された値を返さなければならない。

ProfilerInitOptions辞書

      dictionary ProfilerInitOptions {
        required DOMHighResTimeStamp sampleInterval;
        required unsigned long maxBufferSize;
      };

ProfilerInitOptionsは、次のフィールドに対応しなければならない：

  • sampleIntervalは、アプリケーションが希望するサンプリング間隔である。この値は、 0以上でなければならない。
  • maxBufferSizeは、希望するサンプルバッファーサイズ上限をサンプル数で表したものである。

文書ポリシー

この仕様は、設定 ポイントを文書 ポリシー内に定義し、プロファイリング機能と初期化動作を制御する。

js-profiling-mode

この仕様は、設定 ポイントを定義し、その名前はjs-profiling-modeとする。その型 はenumで、許可される値は"eager"と"lazy"である。既定 値は空文字列である。

設定されると、このポリシーはスクリプトによるJS自己プロファイリングAPIの使用を許可する。

eager

js-profiling-modeが"eager"に設定されると、 ページ読み込み中のプロファイリングが想定されることをUAに通知する。

UAはこのヒントを使用して、プロファイリング基盤を早期に初期化し、必要な メタデータを格納して、文書読み込み中のできるだけ早い段階でプロファイリングコンポーネントを準備できる。ただし、 これにより、プロファイリングが実際に使用されていなくても、無視できないパフォーマンスオーバーヘッドが発生する可能性がある。この オーバーヘッドは、First Contentful Paint（FCP）やLargest Contentful Paint（LCP）などの指標に悪影響を及ぼす可能性がある。

lazy

js-profiling-modeが"lazy"に設定されると、 プロファイリングが条件付きで使用されることをUAに通知する。

UAはこのヒントを使用して、プロファイリング関連の初期化オーバーヘッドを、最初の Profilerがインスタンス化されるまで延期し、重要なレンダリング期間中に プロファイリングが実際に使用されていない場合のパフォーマンスコストを回避できる。ただし、ユーザー操作の 処理中に初期化が発生すると、Interaction to Next Paint（INP）に悪影響を及ぼす可能性がある。このモードは、特に、 サンプリングの判断に基づいてプロファイリングを条件付きで有効にする文書に適している。

js-profiling（非推奨）

この仕様は、設定 ポイントも定義し、その名前はjs-profilingとする。その型 はbooleanで、既定 値はfalseである。

有効にされると、このポリシーはスクリプトによるJS自己プロファイリングAPIの使用を許可し、UAに プロファイリング基盤の早期初期化を実行するよう通知する（意味的には js-profiling-mode=eagerと等価である）。

js-profiling真偽値設定ポイントは非推奨であり、代わりに js-profiling-modeを使用する。両方が指定された場合、js-profiling-modeが優先され、 js-profilingは無視しなければならない。実装は、後方互換性のためにjs-profilingに対応するべきであるが、 将来、その対応を削除してもよい。

プライバシーとセキュリティ

以下の節では、このAPIにおけるプライバシーとセキュリティに関する設計上の選択を詳述し、 さまざまな種類の攻撃に対する保護策を示す。

クロスオリジンスクリプトの内容

このAPIは、クロスオリジンスクリプトの内容を公開しないよう、次の要件を課す。 サンプルを取得するアルゴリズムによって含められるすべての関数は、CORS同一オリジンで提供されるスクリプト内で定義されていなければならず、これはエラーの抑制プロパティによって保証される。 ブラウザーの組み込み機能（performance.now()など）も、 [= CORS同一オリジン =]のスクリプトから呼び出された場合にのみ含めなければならない。

その結果、このAPIは、クロスオリジンスクリプトの内容や実行特性について、 手動で計測処理を組み込むことで既に得られる情報を超える、新たな知見を公開しない。UAは、 非常に短いサンプリング間隔の値（例えば、 1ミリ秒未満）に対応する場合、この性質が成り立つことを検証することが奨励される。

クロスオリジンの実行

クロスオリジンの実行コンテキストは、 サンプルを取得するアルゴリズム内のレルム検査により、このAPIから観測できないようにするべきである。クロスオリジンのiframesやその他の実行コンテキストで、 プロファイラーとエージェントを共有するものについては、したがって、この APIを通じてその実行を観測できない。

タイミング攻撃

高分解能のタイミング情報の新たな情報源を導入し得るAPIでは、 タイミング攻撃が引き続き懸念となる。トレース内で収集されるタイムスタンプは、[[?HR-Time]]の 現在の高分解能時刻と同じ情報源から取得し、新たなサイドチャネル攻撃の経路を公開しないようにするべきである。

[[?HR-Time]]のクロックの 分解能に関する議論を参照。

マーカーの条件付き公開

既定では、マーカーをフィルタリングするアルゴリズムは、script、gc、 paint、otherの各マーカーを、プロファイラーの環境設定オブジェクトにおいて、そのクロスオリジン分離 能力がtrueに設定されている場合にのみ公開する。これらのマーカーは、確実には 単一のオリジンに帰属させられないエンジンの処理を反映する可能性がある—例えば、ガベージコレクションやその他のコンテキスト間のエンジン動作は、 コンテキスト間の処理を関連付ける可能性があり、描画では他のフレームの内容が合成される場合がある。そのような処理の タイミングを分離せずに公開すると、クロスオリジンのサイドチャネルにつながる可能性がある。そのようなサイドチャネルは、 クロスオリジン 分離が軽減するよう設計されているものであるため、分離を公開の条件としている。ユーザーエージェントは、公開される 集合を明示的なオプトイン（上記のマーカーをフィルタリングするの注記で説明したもの）によって拡大してもよいが、そのようなオプトインは、 オリジンをまたいでマーカーを公開してはならない。

styleマーカーとlayoutマーカーは、クロスオリジン分離なしで公開される。 これらが明らかにするタイミングは、既に同一オリジンから観測可能であるためである。文書は、既存のAPIを使用して、自身のスタイルとレイアウトについて既に同期的に 更新を反映し、その所要時間を測定できる—例えば、 getBoundingClientRect()はレイアウトを強制し、getComputedStyle()はスタイルの更新を反映する （必要な場合はレイアウトも反映する）。この性質を保つため、マーカーを取得するアルゴリズムは、 プロファイラーと同一オリジンの文書のために実行された処理についてのみマーカーを報告する。処理のうち、 同一オリジンの文書に帰属させられないものは、これらのマーカーを通じて報告されない。その結果、これらは、 同一オリジンの文書が既に自身で取得できるものを超えるタイミング情報を公開しない。
