要約

本ドキュメントは、HTTPおよびDOMを通じて送信されるシグナルを定義します。このシグナルは、個人がウェブサイトやサービスに対して、自身の個人情報を第三者に販売または共有しないよう要求するものです。本標準は、そのような要求に法的拘束力を与える既存および今後の法的枠組みと連携することを目的としています。

1. はじめに

このセクションは非規範的です。

今日のウェブサイト構築では、多くの場合、利用者がやり取りすることを選択した事業者以外の 事業者によって提供されるサービスに依存することになります。これは、 Web技術の複雑化と、異なるサービス間での分業の結果です。 このアーキテクチャはより優れたWeb体験のために利用できますが、 プライバシー（[privacy-principles]）を侵害するために悪用されることもあります。データは、 限定された運用目的でサービス プロバイダーと共有できますが、多くのユーザーが好ましくないと考える方法で、 行動ターゲティングのために共有または使用されることもあります。

この懸念に対処するため、世界各地の法域で いくつかの異なる法的枠組みが提案または制定されています。一部のモデルは追跡についてユーザーの同意に依存します。その他の データ最小化の原則に基づくモデルでは、特定のデータ共有または データ処理を全面的に禁止します。

一部の法律や提案では、ユーザーに対して、自らのプライバシーが 保護されるよう要求する権利を付与しています。これには、自らのデータが、やり取りすることを意図した 事業者以外に販売または共有されないよう求める「オプト アウト」要求が含まれます。しかし、訪問するすべてのサイトごとに自らの 権利を手動で表明するよう人々に要求することは非現実的であり、 人々に「プライバシー労働」を 課すことになります （[privacy-principles]）。

この仕様は、この最後の種類の法律を対象として設計されており、 HTTPヘッダー またはDOMを通じて、すべてのウェブサイト運営者に対して普遍的に、データの販売を防止するために適用される権利、 データの第三者との共有、およびクロスコンテキスト・ターゲット 広告へのデータ利用を防止する権利を本人が主張するための方法を提供することで、ユーザーの選択を大規模に扱うことの難しさに対処します。このシグナルにより、ユーザーは、これらの グローバル オプトアウト に基づく法律の一部に存在する特定の規定を利用できます。たとえば、個人情報の販売または共有の販売を停止するための California Consumer Privacy Actにおける「オプトアウト選好 シグナル」に関する規定 [CCPA-REGULATIONS]、またはColorado州 およびその他の州の法律にある「ユニバーサル・オプトアウト メカニズム」に関する類似の規定を利用して、ユーザーが自らの情報の販売または 組織横断型ターゲット広告への利用をオプトアウトできるようにします。

ただし、Global Privacy Controlは、共有およびクロスコンテキスト・ターゲット広告から オプトアウトする選好をユーザーが表明できるように設計されていますが、このコントロールは、考えられるあらゆる プライバシー権を行使することを意図したものではなく、広告や広告ターゲティングをオプトアウトするすべての権利を行使することさえ意図していません。たとえば、GPCは 削除権を行使するようには設計されていません。また、GPCは、同一のコンテキスト内でのデータ収集や広告ターゲティングに対処するようにも設計されていません。 詳細については、 法的および実装上の考慮事項 ガイドを参照してください。

この仕様は、オプトアウト型の 規制、またはより広範なクロスコンテキスト追跡を支持するものとして解釈されるべきではなく、 同意またはデータ最小化に基づく他のモデルを否定するものとして解釈されるべきでもありません。代わりに、この仕様は、特定の法域で ユーザーに付与された積極的な権利を行使できるようにするために設計されています。

2. 定義

販売または共有を拒否するインタラクションとは、 ウェブサイトとのインタラクションであり、その中で 本人が、自らがやり取りすることを意図する相手以外のいかなる当事者にも自らのデータを販売または共有しないこと、 または自らのデータをクロスコンテキスト広告ターゲティングに使用しないことを要求するものです。 W3Cのプライバシー 原則の用語では、本人は少なくとも、 データ管理者が1つだけ存在すること、 およびそのデータが別の コンテキストで広告ターゲティングに使用されないことを要求しています。その コンテキストが 同じ事業者によって所有されている場合でも同様です。

販売または共有を拒否する選好とは、 本人が 自らのデータを「販売または共有しない」よう 要求することです。たとえば、ユーザーエージェントでGlobal Privacy Control 設定を有効にすることや、そのような設定を既定とするツールを使用することによります（場合によっては、 この設定がそのツールのユーザーの最も一般的な期待に一致するためです）。 設定されている場合、この選好は、本人が 販売または共有を拒否するインタラクションでWebを閲覧することを期待していることを示します。

3. 販売または 共有を 拒否する選好の表明

3.1 表明形式

Global Privacy Controlの選好は、すべてのHTTPリクエスト（HTTPヘッダーの形式） およびすべてのウェブサイト（Web APIプロパティの形式）について伝達されるべきです。

設定されている場合、この選好は、単一の値1、または コンテキストに応じて同等の trueとして表明されます。

規制上、法律上、またはその他の要件がない場合、ウェブサイトは、 表明されたGlobal Privacy Controlの選好を、特に本人のプライバシーへの期待、 コンテキスト、 および文化的事情に照らして、当該本人に最も適切と考える方法で解釈できます。同様に、ウェブサイトは、 このプロトコルの範囲外にあるその他の選好情報、 たとえばサイト固有の本人の選好や 第三者の 登録サービスを利用して、このプロトコルを通じて明示的な選好が 表明されていない場合の動作を決定または調整することもできます。

ユーザーエージェントは、本人の選好を可能な限り正確に伝達することが期待されます。ユーザー エージェントは、Global Privacy Control値に関してユーザーエージェントが本人の 選好であると最も適切に判断したものを表すようSHOULD努めるべきです。

3.2 選好のキャッシュ

本人のデータを「販売または共有しない」という要求の伝達に一貫性を確保するため、 選好は、各 トップレベル ナビゲーションでMUSTキャッシュされなければなりません。これは、トップレベルナビゲーション中またはその後に選好が変更された場合、 次のナビゲーションまでその変更が反映されないことを意味します。

トップレベル 閲覧コンテキストは、gpcAtNavigationというbooleanを持ちます。 初期値はfalseです。

gpcAtNavigationの値は、 選好を、 トップレベル 閲覧コンテキストのアクティブ 文書の読み込みが 開始された時点での本人の状態としてMUST反映しなければなりません。 本人の選好が有効であった場合は trueになり、 本人の選好が無効であったか、設定されていなかった場合はfalseになります。

選好が、 トップレベル 閲覧コンテキストにキャッシュされた一部の gpcAtNavigationと整合しないように変更された場合、ユーザーエージェントは、 不整合なタブについてユーザーに通知し、 それらを再読み込みして、キャッシュされたgpcAtNavigationを現在の選好を反映するよう更新する選択肢を提供するようSHOULDすべきです。

3.3 HTTPリクエストの Sec-GPC ヘッダーフィールド

Sec-GPC ヘッダーフィールドは、HTTP リクエスト （任意のリクエストメソッド）において、本人が選好する一般的かつ普遍的な販売または共有を拒否するインタラクションを表明するための仕組みです。 場合によっては、その本人との特定の取り決めにより、ウェブサイトが一般的に適用される選好を無視することが認められる場合があります（以下の§ 5.3および 法的および実装上の 考慮事項ガイドを参照してください）。

このフィールドの構文（[ABNF]）は次のとおりです。 

Sec-GPC-field-name  = "Sec-GPC"
Sec-GPC-field-value = "1"

トップレベル 閲覧コンテキストの gpcAtNavigationがfalseの場合、ユーザーエージェントは Sec-GPC ヘッダーフィールドを生成してはMUST NOTなりません。

トップレベル 閲覧コンテキストの gpcAtNavigationがtrueの場合、ユーザーエージェントは、 フィールド値が数値文字「1」と正確に一致する Sec-GPC ヘッダーフィールドを生成するMUST必要があります。

ユーザーエージェントは、特定のHTTP リクエスト内で複数の Sec-GPC を生成してはMUST NOTならず、 HTTPトレーラーで Sec-GPC フィールドを使用してもMUST NOTなりません。

Sec-GPC ヘッダーを含むHTTPリクエストを処理するサーバーは、 フィールド値が文字「1」と正確に一致しない限り、そのヘッダーを無視し、 そのヘッダーが指定されていなかったかのようにリクエストを処理するMUST必要があります。複数の Sec-GPC ヘッダーがあり、そのうち少なくとも1つのフィールド値が正確に「1」である場合、サーバーは リクエストを、 フィールド値が 「1」である Sec-GPC ヘッダーが1つだけ存在するかのように扱うMUST必要があります。それ以外の場合は、ヘッダーが存在しないものとして扱います。

HTTP中継者は、「1」に設定された Sec-GPC ヘッダーを削除してはMUST NOTなりませんが、 その他の値を含む Sec-GPC ヘッダーは削除してもMAYかまいません。さらに、特定のHTTP リクエストを発信したそのその本人が販売または共有を拒否する選好を持っていると考える理由があるHTTP中継者は、 「1」に設定された Sec-GPC ヘッダーを挿入してもMAYかまいません。

例 1: GPCリクエストの例 
GET /something/here HTTP/1.1
Host: example.com
Sec-GPC: 1

3.3.1 Sec-GPCフィールド値の拡張性

Sec-GPC は、意図的に拡張メカニズムなしで定義されています。 以前の類似ヘッダーの経験から、特に まだ拡張が存在しない場合、その存在を検査する際に値を解析するのではなく文字列の 等価性に依存する傾向があることが分かっています。このような検査は当然ながら、 拡張内容が存在すると失敗し、その結果、この仕組み自体が意味を失います。この標準に 拡張が必要であることが判明した場合、それらは別の ヘッダーを通じて実装する必要があり、やがてこのヘッダーに取って代わる可能性があります。

3.4 選好を 検出する JavaScriptプロパティ

globalPrivacyControl プロパティにより、 クライアント側 スクリプトは、 トップレベル 閲覧コンテキストのアクティブ 文書を読み込んだときに、 どの Sec-GPC ヘッダーフィールド値が送信されたかを判定できます。 

WebIDLinterface mixin GlobalPrivacyControl {
  readonly attribute boolean globalPrivacyControl;
};
Navigator includes GlobalPrivacyControl;
WorkerNavigator includes GlobalPrivacyControl;

Sec-GPCヘッダーフィールドが送信されない場合、値はfalseです。 それ以外の場合、値はtrueです。

globalPrivacyControl の値は、 トップレベル 閲覧コンテキストのgpcAtNavigationであるMUST必要があります。

globalPrivacyControl プロパティは、 通常のコンテキストとワーカーコンテキストの両方で navigatorオブジェクトから利用できるため、 navigator.globalPrivacyControlから読み取ることで確認できます。

例 2: スクリプトでGPCを確認する 
if (!navigator.globalPrivacyControl) {
  // すばらしい、この人のデータを販売できる！
}

4. GPCサポートリソース

オリジンは、少なくともそうすることが要求される場合に、 GPCリクエストに従うことを表すため、.well-known URLにリソースを生成してもMAYかまいません。GPCサポートリソースの目的は、 オリジンから提供されるページにおいてGlobal Privacy Controlを認識し、 サポートしていることをオリジンが伝えることです。 サポートリソースは、そのリソースにアクセスするユーザーエージェントからのGPC リクエストにオリジンが従うかどうかを伝えることを意図していません。 既定では、オリジンのサポート状況は不明です。

GPCサポートリソースは、オリジンサーバーのURLに対して相対的な well-known識別子/.well-known/gpc.jsonを持ちます[RFC8615]。

GPCサポートリソースを対象とする有効なGETリクエストを受信したオリジンサーバーは、 オリジンから提供されるページがどのようにGPCを尊重するかについて機械可読な表現を含む正常なレスポンス、 またはそのような表現へと導く一連のリダイレクト （別のオリジンにあるサーバーが提供してもMAYかまいません） のいずれかで応答します。

4.1 GPCサポート表現

オリジンサーバーは、 application/jsonメディアタイプ[RFC8259]を使用した有効な 表現としてGPCサポートリソースを返すMUST必要があります。それ以外の場合、 オリジンのサポート状況は 不明です。

GPCサポート表現は JSONオブジェクトであるMUST必要があります。それ以外の場合、 オリジンのサポート状況は不明です。このJSONオブジェクトに含まれる、以下の一覧にないメンバーは、 この仕様では意味を持たず、無視するMUST必要があります。メンバーには次が含まれます。

  • gpcメンバー。gpcメンバーの値は、 少なくとも法的に義務付けられている範囲でサーバーがGPCリクエストに従う意図があることを示す true、または従わないことを示すfalseの いずれかであるMUST必要があります。それ以外の値では、オリジンのサポート状況は不明です。
  • lastUpdateメンバー。lastUpdate メンバーの値は、RFC3339のfull-date（YYYY-MM-DD）または date-time （YYYY-MM-DDTHH:mm:ss.sssZ）[RFC3339]であるMUST必要があります。これは、 サポート表明が行われた 時刻を示し、その後GPC標準の意味が変更されたとしても、法的目的でのリソースの解釈に 影響しないようにします。 メンバーが有効なRFC3339形式でない場合、最終更新日時は 不明です。

例 3: example.orgはGPCに従う 
GET /.well-known/gpc.json HTTP/1.1
Host: example.org
User-Agent: whatever


Content-Type: application/json

{
  "gpc": true,
  "lastUpdate": "2025-04-15"
}

5. 法的効果

このセクションは非規範的です。

GPCシグナルは、ユーザーが自らのデータの特定の 共有または処理を停止する法的権利を利用できるように設計されています。そのため、GPCシグナルの送信および受信は、 シグナルを送信する個人の所在地、 適用法の範囲、ならびにシグナルの受信者と 個人との間の個別の合意などの要因に応じて、法的効果を持つ場合があります。ただし、GPCは必ずしも あらゆる法域におけるすべての新たなプライバシー権を行使することを意図しているわけではありません。法的効果の詳細については、 法的および 実装上の考慮事項ガイドを参照してください。

たとえば、個人によるGPCシグナルの使用は、該当する場合、 次の権利を行使する個人の意思を伝えることを意図します。

特定の法域においてGPCシグナルを適用する最善の方法を理解しようとする 規制当局および実装者には、W3Cのプライバシー 原則で詳述されているグローバルオプトアウトメカニズムの意味を参照することを推奨します。 その詳細は、Web上のユーザーエージェントに課される期待にあまり馴染みのない 人々には理解しにくい場合があるためです。

5.1 米国のプライバシー法

GPCは当初、米国における新しいオプトアウト型プライバシー法を利用するために作成されました。 2018年のCalifornia Consumer Privacy Act制定を皮切りに、米国の複数の州が、 消費者に、自らのデータの販売または共有、あるいは 組織横断型ターゲット広告へのデータ利用をオプトアウトする法的権利を付与するプライバシー法を可決しています。これらの州法の多くは、 GPCのようなユニバーサル・オプトアウト・メカニズムを通じてそれらの権利を行使することを 明示的に規定しています。少なくとも4つの州が、法的なオプトアウト権を行使する有効な手段としてGPCを具体的に認めています。 少数の州では、ユニバーサル・オプトアウト要求をどのように尊重すべきかについての詳細を規制当局が 拡充できる規則制定手続を設けています。他の州では、 GPCシグナルをめぐる法的義務の範囲を明確化するため、非公式な指針や執行措置に 依存する場合があります。

5.2 その他の法域 および プライバシー権

GPCは、他の法域における権利を示すためにも使用できる可能性があります。たとえば、 GDPRは、第7条および第21条に基づき、データ主体に個人情報の共有を制限する権利を 与える可能性があります。世界中の他の多くの国も、 多くの場合GDPRをモデルとして積極的なプライバシー法を採用しています。それらの国の規制当局は、 GPCによって、受信者に何らかの対応を要求する法的権利が行使されると判断する可能性があります。

Virginia州やUtah州など、米国のその他の州のプライバシー法では、 データ販売および組織横断型ターゲット広告に関する新たなオプトアウト 権を消費者に付与していますが、グローバル・オプトアウト・シグナルの法的 効果については言及していません。これらの法律を執行する規制当局は、 GPCのようなシグナルを有効化することが、それらの法域におけるオプトアウト権を 法的に行使するのに十分であると判断する可能性があります。

ただし、GPCは必ずしも、あらゆる 法域におけるすべての新たなプライバシー権を行使することを意図しているわけではありません。たとえば、GPCは、 ユーザーが訪問するすべてのウェブサイトに対してデータ削除権を一律に行使することを意図していません。GPCはまた、 ファーストパーティによる、 同一のコンテキスト内での個人情報の利用 （たとえば、その同じ コンテキストにおける以前の活動に基づき、 パブリッシャーが自らのウェブサイト上のユーザーに広告をターゲティングすること）を制限することも意図していません。

既存の同意フレームワークの複雑さを考慮すると、GPCシグナルを受け入れるパブリッシャーは、 その法域においてGPCシグナルをどのように扱うか、また、 シグナルと本人がすでにパブリッシャーに直接行ったその他の特定のプライバシー選択との 競合をどのように処理するかを開示するべきです。これには、 サービス プロバイダー／処理者への共有、 法律に基づく共有、または 個人の指示に基づく共有など、第三者との共有が 許可される場合も含まれます。

5.3 ユーザーインターフェイスの文言

この文書では、GPCを有効化する前にユーザーへ提示しなければならない 情報を規定していません。ユーザーエージェントがプライバシー機能を推奨したりプライバシー設定を提供したりする場合、 ユーザーに開示された内容に基づいて、GPCを送信することが適切かどうかを判断できます。 ユーザーエージェントは、Global Privacy Control値についてユーザーエージェントが 本人の 選好であると最も適切に判断したものを表すようSHOULD努めるべきです。調査では、ほとんどの人が 自らのデータの販売または共有を望んでいないことが示されていますが、一部の法域では「オプトアウト」型の法的枠組みが制定されており、 消費者は、データ 共有またはターゲット広告へのデータ利用を制限する選好を表明するために積極的な行動を取る必要があります。 GPCは、ユーザーがこれらの法律を容易に 利用できるよう設計されています。

GPCのようなユニバーサル・オプトアウトをプラットフォームが有効にできるようになるまでの前提条件は、 法域によって異なります。米国の多くの州では、ユーザーエージェントがユニバーサル・オプトアウト・シグナルを 「デフォルト」で送信してはならないとされていますが、少なくとも1つの州では、 プライバシー重視のユーザーエージェントを選択することがユーザーの意思を示す十分な指標であるとされています。

法域によっては、企業が普遍的に適用されるオプトアウト・シグナルを 上書きまたは無視できる場合についても異なる規則が存在する可能性があります。 たとえば、そのための同意をユーザーから得ている場合です。

グローバル・オプトアウトをめぐる法的環境も変化しています。現在では複数の州が、 グローバル・オプトアウトを尊重する要件を含む法律を可決していますが、それらの州の規定の一部は 大きく異なります。また、California州が2018年に可決された元のCCPAを すでに改正したように、各州は法的要件を改訂する可能性があります。

米国に加えて、その他の法域でもユニバーサル・プライバシー・シグナルを認める可能性があり、 そのようなシグナルが法的拘束力を持つとみなされる前に、独自の要件を課す場合があります。

最新の法的要件の詳細については、 法的および実装上の 考慮事項ガイドを確認してください。このガイドでは、グローバル・オプトアウトをめぐる最新の法的 指針について、 より新しい情報が提供されます。

ユーザーエージェントは、必要な場合、人々が利用したい権利が 有効に拘束力を持つことを確実にするため、適切なすべての通知を人々に提示することが期待されます。

6. プライバシーに関する考慮事項

ユーザーの選好を公開すること（HTTPヘッダーフィールドまたはnavigator オブジェクト内で） は、ブラウザーまたはデバイスのフィンガープリンティングに利用できる情報を増加させる可能性がある形で、 ユーザーを2つのグループに分ける可能性があります。この追加情報は、 シグナルが他のシグナルと完全に相関しているか、設定変更できない状態で有効になっていない限り 利用可能です。したがって、実装によっては、GPCシグナルには プライバシー上のコストが伴う可能性がありますが、それはシグナル送信によるプライバシー上の利益によって 正当化されることが意図されています。

7. セキュリティに関する考慮事項

この仕様の機能による既知のセキュリティ上の影響はありません。

8. 自動化

ユーザーエージェントの自動化およびアプリケーションテストを目的として、この文書では、 次の拡張コマンドを定義します。[WebDriver]

8.1 Global Privacy Controlを設定する

HTTPメソッド URIテンプレート
POST /session/{session id}/privacy

Global Privacy Controlを設定する拡張コマンドは、現在のセッションに対する 販売または共有を拒否する選好を変更し、 更新された設定を 返します。

リモートエンドの 手順は、 session、URL variables、 parametersが与えられた場合、次のとおりです。

  1. gpcを、parametersのプロパティgpcとします。

  2. gpcがundefinedであるかbooleanでない場合、エラーコードinvalid argumentのエラーを返します。

  3. このsessionについてユーザーの選好を記録し、 gpcがtrueの場合、ブラウザーが 販売または共有を拒否するインタラクションを 実行し、 gpcがfalseの場合、 販売または共有を拒否するインタラクションを実行しないようにします。

  4. resultを、プロパティ「gpc」がgpcに設定されたJSON Object とします。

  5. データ resultを伴う成功を 返します。

8.2 Global Privacy Controlを取得する

HTTPメソッド URIテンプレート
GET /session/{session id}/privacy

Global Privacy Controlを取得する拡張コマンドは、現在のセッションに対する 販売または共有を拒否する選好を返します。

リモートエンドの 手順は、 session、URL variables、 parametersが与えられた場合、次のとおりです。

  1. このsessionについてのユーザーの選好により、 ブラウザーが 販売または共有を拒否するインタラクションを実行する場合、 gpcをtrueとします。

  2. それ以外の場合、gpcをfalseとします。

  3. resultを、プロパティ「gpc」がgpcに設定されたJSON Object とします。

  4. データ resultを伴う成功を 返します。

9. 適合性

非規範的と明示されているセクションに加えて、この仕様に含まれるすべてのオーサリングガイドライン、図、例、および注記は 非規範的です。この仕様のそれ以外のすべては規範的です。

この文書のキーワードMAY、MUST、MUST NOT、および SHOULDは、 ここに示すようにすべて 大文字で記述されている場合に限り、 BCP 14 [RFC2119] [RFC8174] に記載されているとおりに解釈されます。

A. 実装上の考慮事項

GPCシグナルは、特定のサイトに対して行われるすべてのHTTPリクエストに 付加されることを考慮する価値があります。Web上でページをレンダリングするには、多くの場合、そのようなリクエストを数十回行う必要があります。そのため、 GPCとのインタラクションのたびに、コストの高い監査証跡を伴う本格的なオプトアウト手続を GPCシグナルによって開始することは非現実的となり得ます。これは、 可能な限り効率的に実行する必要があるコンテンツ配信ネットワーク（CDN）から提供されるリソースを含め、 大量の処理を発生させるためです。

GPCをサポートすることを意図する規制では、このような実装上の 困難を考慮することが推奨されます。これらに対処する方法の1つは、サイト上に保持される 販売または共有を拒否するインタラクションの 選好を要求する目的で人々に提供されるユーザーインターフェイス上の操作手段と、 ユーザーエージェントによって状態が保持される 販売または共有を拒否するインタラクションのシグナルの提供とを 区別することです。後者の場合、そのインタラクションは、 本人が以前にそのような販売または共有を拒否する インタラクションの選好を要求しており、 その選好がすでに有効な状態でインタラクションしているかのように処理できます。
