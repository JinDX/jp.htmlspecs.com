RFC 9101

OAuth 2.0 認可フレームワーク：JWT で保護された認可リクエスト (JAR)

概要

RFC 6749 で説明されている OAuth 2.0 の認可リクエストでは、 クエリパラメーターによるシリアライズが使用されます。これは、認可リクエストの パラメーターがリクエストの URI にエンコードされ、Web ブラウザーなどのユーザー エージェントを介して送信されることを意味します。実装は容易ですが、これは a) ユーザーエージェントを介した通信は完全性が 保護されないため、パラメーターが改ざんされる可能性がある、b) 通信元が 認証されない、c) ユーザーエージェントを 介した通信が監視される可能性がある、ということを意味します。これらの弱点により、 このプロトコルに対するいくつかの攻撃が現在までに提示されています。¶

本文書では、代わりにリクエストパラメーターを JSON Web Token (JWT) で送信する機能を導入します。これにより、リクエストを JSON Web Signature (JWS) で署名し、JSON Web Encryption (JWE) で暗号化できるため、 認可リクエストの完全性、送信元認証、および機密性の 特性が実現されます。リクエストは 値によって、または参照によって送信できます。¶

1. はじめに

OAuth 2.0 [RFC6749] の認可リクエストでは クエリパラメーターによる シリアライズが使用され、通常は Web ブラウザーなどのユーザーエージェントを介して送信されます。¶

たとえば、パラメーター response_type、client_id、state、および redirect_uri はリクエストの URI にエンコードされます:¶ 

    GET /authorize?response_type=code&client_id=s6BhdRkqt3&state=xyz
    &redirect_uri=https%3A%2F%2Fclient%2Eexample%2Ecom%2Fcb HTTP/1.1
    Host: server.example.com
¶

実装は容易ですが、URI でのエンコードでは アプリケーション層のセキュリティを使用して 機密性および完全性保護を提供することはできません。 TLS はクライアントとユーザーエージェント間、およびユーザーエージェントと 認可サーバー間の通信セキュリティを提供するために使用されますが、TLS セッションはユーザーエージェントで終了します。 さらに、TLS セッションは一部のミドルボックス （ロードバランサーなど）で途中終了する場合があります。¶

その結果、[RFC6749] の認可リクエストには 次のような欠点があります:¶

(a)
ユーザーエージェントを介した通信は 完全性が保護されないため、パラメーターが改ざんされる可能性がある （完全性保護の失敗）;¶
(b)
通信元が認証されない （送信元認証の失敗）;¶
(c)
ユーザーエージェントを介した通信が監視される可能性がある （封じ込め／機密性の失敗）。¶

これらの固有の弱点により、リダイレクト URI の書き換えなど、 このプロトコルに対するいくつかの攻撃が特定されています。¶

アプリケーション層のセキュリティを使用することで、これらの問題が軽減されます。¶

アプリケーション層のセキュリティを使用すると、信頼できる第三者が リクエストを準備できるため、クライアントアプリケーションは事前に 合意された以上の権限を要求できなくなります。¶

さらに、リクエストを参照で渡すことにより、通信上のオーバーヘッドを削減できます。¶

JWT [RFC7519] エンコードが選択された理由は次のとおりです:¶

(1)
OAuth のレスポンス形式として使用されている JSON と 密接な関係があること¶
(2)
テキスト形式であるため開発者にとって扱いやすいこと¶
(3)
XML と比較して比較的コンパクトであること¶
(4)
関連する署名および暗号化方式とともに、 Proposed Standard として開発されていること [RFC7515] [RFC7516]¶
(5)
XML Signature および Encryption と比較して JWS と JWE が比較的扱いやすいこと。¶

パラメーター request および request_uri は、 OAuth 2.0 [RFC6749] フロー用の追加の認可リクエストパラメーターとして導入されます。 request パラメーターは、 JWT Claims Set に JSON エンコードされた OAuth 2.0 認可リクエストパラメーターを保持する JSON Web Token (JWT) [RFC7519] です。 RFC 7519 とは異なり、Claims Set の要素は エンコードされた OAuth リクエストパラメーター [IANA.OAuth.Parameters] であり、 IANA が管理する JSON Web Token Claim [IANA.JWT.Claims] のうち、ごく一部、特に iss および aud のみが追加されることに注意してください。request パラメーター内の JWT は、JWS を使用して完全性が 保護され、送信元が認証されます。¶

JWT [RFC7519] は 参照によって認可エンドポイントに渡すことができ、 その場合は request の代わりに パラメーター request_uri が使用されます。¶

クエリパラメーターの代わりに JWT [RFC7519] をリクエストエンコードとして使用すると、 いくつかの利点があります:¶

(a)
完全性保護。 リクエストに署名することで、リクエストの完全性を確認できます。¶
(b)
送信元認証。 リクエストに署名することで、署名者を認証できます。¶
(c)
機密性保護。 リクエストを暗号化することで、TLS 接続が どこかの時点（ユーザーエージェントおよびその手前を含む）で終了する場合でも、 エンドツーエンドの機密性を提供できます。¶
(d)
収集の最小化。リクエストに信頼できる 第三者が署名し、認可リクエストが特定の ポリシーに準拠していることを証明できます。たとえば、リクエストを 信頼できる第三者が事前に審査し、要求されるすべての個人データが エンドユーザーが依頼した処理を実行するために 厳密に必要であることを確認できます。その後、その信頼できる第三者が リクエストに署名します。認可サーバーは署名を検証し、 準拠状態をエンドユーザーに表示します。これによりユーザーは、 認可時にリクエストの正当性について一定の保証を得られます。場合によっては、 このような状況では認可ダイアログを省略することが 望ましい場合もあります。¶

参照によるリクエストが有用な場合には、たとえば次のようなものがあります:¶

  1. 送信されるリクエストのサイズを削減することが望ましい場合。 アプリケーション層のセキュリティを使用すると、特に公開鍵暗号方式を使用する場合に リクエストのサイズが増加します。¶
  2. クライアントがアプリケーションレベルの 暗号処理を行いたくない場合。認可サーバーは、 クライアントとの直接通信を介して認可リクエストを受け付けるエンドポイントを 提供することができ、それによってクライアントが認証され、チャネルが TLS で 保護されます。¶

この機能は OpenID Connect [OpenID.Core] で使用されています。¶

2. 用語

本仕様では、 OAuth 2.0 フレームワーク [RFC6749]、 JSON Web Signature [RFC7515]、および JSON Web Encryption [RFC7516] で定義されているものに加え、次の用語および 定義が適用されます。¶

2.1. リクエストオブジェクト

リクエストオブジェクトとは、JWT Claims Set に JSON エンコードされた OAuth 2.0 認可リクエスト パラメーターを保持する JSON Web Token (JWT) [RFC7519] です。¶

2.2. リクエストオブジェクト URI

リクエストオブジェクト URI は、OAuth 2.0 認可リクエストを構成する パラメーターの集合を参照する絶対 URI です。URI が参照する リソースの内容は リクエスト オブジェクト (第2.1節) です。ただし、 URI が同じ認可サーバーからクライアントに 提供された場合は、内容は認可サーバーの裁量による 実装の詳細です。内容をリクエストオブジェクトとするのは、 request_uri の提供者と利用者が別の エンティティである場合の相互運用性を確保するためです。たとえば、クライアントが HTTPS を介してアクセス可能にしたクライアントのバックエンドサービス上に保存された リクエストオブジェクトを参照する URI を提供する場合などです。後者の、 認可サーバーが URI の提供者と利用者を兼ねる場合、たとえば リクエストオブジェクトと引き換えに URI を提供する エンドポイントを提供する場合には、この相互運用性上の懸念は当てはまりません。¶

4. リクエストオブジェクト

リクエストオブジェクト (第2.1節) は、 OAuth 2.0 認可リクエストの認可リクエストパラメーターを 提供するために使用されます。これは、OAuth 2.0 [RFC6749] の 認可リクエストを処理するために使用されるすべてのパラメーター（拡張 パラメーターを含む）を、この文書で定義される request および request_uri パラメーターを除いて、MUST 含まなければなりません。 パラメーターはオブジェクトの JWT Claim として表現されます。 パラメーター名および文字列値は JSON 文字列として MUST 含めなければなりません。 リクエストオブジェクトはドメインをまたいで処理され、閉じたエコシステムの 外部で扱われる可能性があるため、第8.1節 of [RFC8259] に従い、 これらの JSON 文字列は UTF-8 [RFC3629] を使用して MUST エンコードしなければなりません。 数値は JSON 数値として MUST 含めなければなりません。 リクエストオブジェクトは任意の拡張パラメーターを MAY 含めることができます。 この JSON [RFC8259] オブジェクトは、 JWT [RFC7519] で定義されている JWT Claims Set を構成します。 JWT Claims Set はその後、署名されるか、署名されて暗号化されます。¶

署名には、JSON Web Signature (JWS) [RFC7515] が 使用されます。その結果、JWS 署名された JWT [RFC7519] になります。署名されている場合、 認可リクエストオブジェクトは、Claim iss（発行者）および aud（対象者）を、 JWT [RFC7519] 仕様で定義されたものと同じ意味を持つメンバーとして SHOULD 含むべきです。aud の値は、 RFC 8414 [RFC8414] で定義される認可サーバー (AS) の issuer の値であるべきです。¶

暗号化には、JWE [RFC7516] が使用されます。 署名と暗号化の両方を適用する場合、 JWT は、第11.2節 of [RFC7519] に記載されているとおり、 最初に署名し、その後暗号化 MUST しなければなりません。 その結果は、 [RFC7519] で定義されている Nested JWT になります。¶

クライアントは、リクエストオブジェクトの署名および暗号化に使用する アルゴリズムを決定します。選択されるアルゴリズムは、 クライアントと認可サーバーの両方でサポートされている必要があります。クライアントは、 動的クライアント登録メタデータ [RFC7591] で、 サポートするアルゴリズムを認可サーバーに通知できます。 具体的には、メタデータ値 request_object_signing_alg、 request_object_encryption_alg、および request_object_encryption_enc です。同様に、 認可サーバーは認可サーバーメタデータ [RFC8414] で、サポートするアルゴリズムを クライアントに通知できます。具体的には、メタデータ値 request_object_signing_alg_values_supported、 request_object_encryption_alg_values_supported、および request_object_encryption_enc_values_supported です。¶

リクエストオブジェクトは、第5.1節で 説明されているように値で MAY 送信でき、 または 第5.2節で説明されているように参照で送信できます。 request および request_uri パラメーターは リクエストオブジェクトに MUST NOT 含めてはなりません。¶

リクエストオブジェクト (第2.1節) のメディア タイプ [RFC2046] は application/oauth-authz-req+jwt です。既存の一部の デプロイメントでは、代わりに application/jwt タイプを使用している場合があることに注意してください。¶

5. 認可リクエスト

クライアントは、 application/x-www-form-urlencoded 形式を使用して 認可エンドポイント URI のクエリコンポーネントに 次のパラメーターを追加することにより、認可リクエスト URI を構築します:¶

request
request_uri が指定されていない限り REQUIRED です。 第4節 of [RFC6749] (OAuth 2.0) に記載された 認可リクエストパラメーターを保持する リクエストオブジェクト (第2.1節)。 このパラメーターが認可リクエストに存在する場合、 request_uri は存在しては MUST NOT なりません。¶
request_uri
request が指定されていない限り REQUIRED です。RFC 3986 [RFC3986] で定義されている絶対 URI であり、 第4節 of [RFC6749] (OAuth 2.0) に記載された認可リクエスト パラメーターを参照する リクエストオブジェクト URI (第 2.2節) です。 このパラメーターが認可リクエストに存在する場合、 request は存在しては MUST NOT なりません。¶
client_id
REQUIRED。OAuth 2.0 [RFC6749] の client_id です。この値は、 request または request_uri の リクエストオブジェクト (第2.1節) の client_id と一致しなければ MUST なりません。¶

6. JWT ベースのリクエストの検証

6.1. JWE で暗号化されたリクエスト オブジェクト

リクエストオブジェクトが暗号化されている場合、 認可サーバーは JSON Web Encryption [RFC7516] 仕様に従って JWT を復号しなければ MUST なりません。¶

結果は署名されたリクエストオブジェクトです。¶

復号に失敗した場合、認可サーバーは 認可リクエストへの応答として、invalid_request_object エラーを クライアントに返さなければ MUST なりません。¶

6.2. JWS で署名されたリクエスト オブジェクト

認可サーバーは、JWS 署名された [RFC7515] リクエスト オブジェクトの署名を検証しなければ MUST なりません。 kid ヘッダーパラメーターが存在する場合、識別された鍵を 使用しなければ MUST ならず、その鍵はクライアントに関連付けられた 鍵で MUST なければなりません。署名は、 クライアントに関連付けられた鍵と、alg ヘッダーパラメーターで 指定されたアルゴリズムを使用して検証しなければ MUST なりません。 アルゴリズム検証は、[RFC8725] の 第3.1節 および 第3.2節 で 規定されているとおり実行しなければ MUST なりません。¶

鍵がクライアントに関連付けられていない場合、または署名の 検証に失敗した場合、認可サーバーは認可リクエストへの応答として invalid_request_object エラーをクライアントに返さなければ MUST なりません。¶

6.3. リクエストパラメーターの 組み立てと検証

認可サーバーは、リクエストオブジェクト値から 認可リクエストパラメーターの集合を抽出しなければ MUST なりません。 同じパラメーターがクエリパラメーターとして提供されている場合でも、 認可サーバーはリクエストオブジェクト内の パラメーターのみを使用しなければ MUST なりません。 client_id リクエストパラメーターと リクエストオブジェクトの client_id Claim 内のクライアント ID 値は 同一でなければ MUST なりません。 その後、認可サーバーは、 OAuth 2.0 [RFC6749] で規定されているとおり、リクエストを検証します。¶

クライアント ID の確認またはリクエストの検証に失敗した場合、 認可サーバーは、第 5.2節 of [RFC6749] (OAuth 2.0) で規定されているとおり、 認可リクエストへの応答としてクライアントにエラーを返さなければ MUST なりません。¶

7. 認可サーバーのレスポンス

認可サーバーのレスポンスは、 第4節 of [RFC6749] (OAuth 2.0) と同様に作成され、クライアントへ送信されます。¶

さらに、本文書では次の追加エラー値を使用します:¶

invalid_request_uri
認可リクエスト内の request_uri が エラーを返すか、無効なデータを含んでいます。¶
invalid_request_object
request パラメーターに 無効なリクエストオブジェクトが含まれています。¶
request_not_supported
認可サーバーは request パラメーターの使用をサポートしていません。¶
request_uri_not_supported
認可サーバーは request_uri パラメーターの使用をサポートしていません。¶

8. TLS 要件

リクエストオブジェクト URI 方式をサポートするクライアント実装は、 「Transport Layer Security (TLS) および Datagram Transport Layer Security (DTLS) の 安全な使用に関する推奨事項」 [RFC7525] に従って、TLS をサポートしなければ MUST なりません。¶

情報漏えいおよび改ざんから保護するため、 機密性と完全性を保護する暗号スイートを備えた TLS を使用して、 機密性保護を適用しなければ MUST なりません。¶

HTTP クライアントは、中間者攻撃を回避するため、 DNS-ID [RFC6125] を使用して TLS サーバー証明書も検証しなければ MUST なりません。 [RFC6125] で定義されている規則および指針が、 次の考慮事項とともにここにも適用されます:¶

  • DNS-ID 識別子タイプ（すなわち、subjectAltName 拡張内の dNSName ID）のサポートは REQUIRED です。サーバー証明書を 発行する認証局は DNS-ID 識別子タイプをサポートしなければ MUST ならず、DNS-ID 識別子タイプはサーバー証明書に 存在しなければ MUST なりません。¶
  • サーバー証明書内の DNS 名には ワイルドカード文字 * を MAY 含めることができます。¶
  • クライアントは CN-ID 識別子を使用しては MUST NOT なりません。 Common Name フィールド（CN フィールド）はサーバー証明書の subject name に存在する場合がありますが、[RFC7525] に記載された規則の範囲内で 認証に使用しては MUST NOT なりません。¶
  • 第6.5節 of [RFC6125] で説明されている SRV-ID および URI-ID は、 比較に使用しては MUST NOT なりません。¶

OAuth 2.0 で説明されているすべてのセキュリティ上の 考慮事項 [RFC6819] に加えて、 [RFC7515]、[RFC7516]、 [RFC7518]、および [RFC8725] のセキュリティ上の 考慮事項も考慮する必要があります。また、[BASIN] など、OAuth のようなプロトコルの セキュリティ特性に関して有用な洞察を提供する学術論文もいくつかあります。¶

上記を考慮し、本文書では次の セキュリティ上の考慮事項を考慮することを推奨します。¶

10.1. アルゴリズムの選択

認可リクエストオブジェクトを request パラメーターを介して送信する場合、これは その時点で適切と考えられるアルゴリズムを使用して、 JWS [RFC7515] で署名するか、 JWS [RFC7515] で署名した後、 JWE [RFC7516] で暗号化するかのいずれかでなければ MUST なりません。¶

10.2. リクエスト送信元の 認証

認可リクエストの送信元は常に検証しなければ MUST なりません。これにはいくつかの方法があります:¶

(a)
リクエストオブジェクトの JWS 署名を検証する。¶
(b)
JWE が対称暗号を使用している場合、 JWE 暗号化用の対称鍵が正しいことを検証する。ただし、 公開鍵暗号を使用する場合は、誰でも公開鍵に対して 暗号化できるため、暗号化によって送信元認証は 提供されないことに注意してください。¶
(c)
リクエストオブジェクト URI の TLS サーバー ID を検証する。 この場合、認可サーバーは、クライアントがリクエストオブジェクト URI を 使用しており、TLS 証明書によってクライアントだけが カバーされていることを帯域外で認識していなければ MUST なりません。 一般に、これは信頼できる方法ではありません。¶
(d)
認可サーバーが、 リクエストオブジェクトと引き換えにリクエストオブジェクト URI を返す サービスを実装する場合、認可サーバーは リクエストオブジェクトを受け付けるためクライアント認証を実行し、 クライアント識別子を提供するリクエストオブジェクト URI に バインドしなければ MUST なりません。 また、(a) に従って署名を検証しなければ MUST なりません。 リクエストオブジェクト URI はリプレイ可能であるため、その有効期間は 短くし、できれば一度限りの使用にしなければ MUST なりません。 リクエストオブジェクト URI のエントロピーは十分に大きくなければ MUST なりません。 適切な有効期間の短さおよび リクエストオブジェクト URI のエントロピーは、 保護されるリソースの価値に基づく リスク計算によって決まります。一般的な指針として、 本仕様の執筆時点では、有効期間は1分未満とし、 リクエストオブジェクト URI には 128 ビット以上の暗号学的乱数値を 含めることが推奨されます。¶
(e)
信頼できる第三者サービスがリクエストオブジェクトと引き換えに リクエストオブジェクト URI を返す場合、(a) に従って署名を 検証しなければ MUST なりません。さらに、認可サーバーは 第三者サービスから信頼されていなければ MUST ならず、 クライアントもそのサービスから信頼されていることを帯域外で 認識していなければ MUST なりません。¶

10.3. 明示的なエンドポイント

本仕様では必須としていませんが、 [BASIN] などの研究では、 開始者の意図が曖昧にならないように、 意図する対話エンドポイントとシーケンス内の メッセージ位置を改ざん検知可能な方法で 明示することが良い実践であると指摘されています。本仕様では、 [RFC6749]、[RFC6750]、および [RFC8414] で定義された次のエンドポイントに対して、 この実践を使用することが RECOMMENDED されます:¶

(a)
保護対象リソース (protected_resources)¶
(b)
認可エンドポイント (authorization_endpoint)¶
(c)
リダイレクト URI (redirect_uri)¶
(d)
トークンエンドポイント (token_endpoint)¶

さらに、動的ディスカバリーを使用する場合、この実践は ディスカバリー関連のエンドポイントにも適用されます。¶

[RFC6749] では、 リダイレクト URI は認可リクエストに含まれますが、その他は 含まれません。その結果、同じことが認可 リクエストオブジェクトにも当てはまります。¶

10.4. request_uri に関連する リスク

request_uri の導入により、 いくつかの攻撃の可能性が生じます。 URI に関連するリスクの詳細については、 第7節 of [RFC3986] のセキュリティに関する考慮事項を 参照してください。¶

10.4.1. 認可サーバーに対する DDoS 攻撃

悪意のある複数のクライアントは、 request_uri に極端に大きな内容を返す、または 応答が極端に遅い URI を指定することで、 認可サーバーに DoS 攻撃を仕掛けることができます。 このような攻撃を受けると、サーバーはリソースを使い果たし、 障害を起こし始める可能性があります。¶

同様に、悪意のあるクライアントは、 request_uri を使用する認可リクエスト URI 自体を 指す request_uri 値を指定し、 再帰的なルックアップを引き起こすことができます。¶

このような攻撃が成功するのを防ぐため、サーバーは a) request_uri パラメーターの値が 予期しない場所を指していないことを確認し、 b) レスポンスのメディアタイプが application/oauth-authz-req+jwt であることを確認し、 c) request_uri の内容を取得する際の タイムアウトを実装し、 d) request_uri に対して 再帰的な GET を実行しないようにするべきです。¶

10.4.2. リクエスト URI の 書き換え

request_uri の値は署名されていません。 そのため、man-in-the-browser 攻撃者によって改ざんされる可能性があります。 これにより、いくつかの攻撃の可能性が生じます。たとえば、 a) 攻撃者が書き換えられた URI の参照先となる別のファイルを 作成し、追加のスコープを要求できるようにすることや、 b) request_uri の値を被害者サイトに 設定することで、被害者サイトに DoS 攻撃を仕掛けることが 可能です。¶

このような攻撃が成功するのを防ぐため、サーバーは a) request_uri パラメーターの値が 予期しない場所を指していないことを確認し、 b) レスポンスのメディアタイプが application/oauth-authz-req+jwt であることを確認し、 c) request_uri の内容を取得する際の タイムアウトを実装するべきです。¶

10.5. ダウングレード攻撃

クライアントとサーバーが使用するプロトコルが OAuth JWT-Secured Authorization Request (JAR) の使用に固定されていない限り、 攻撃者は RFC 6749 リクエストを使用して、 本仕様によって提供されるすべての保護を回避できます。¶

この種の攻撃を防ぐため、本仕様では require_signed_request_object という同じ名前を持つ 新しいクライアントメタデータ値とサーバーメタデータ値を定義します。 どちらの値もブール値です。¶

クライアントメタデータとしての値が true の場合、 サーバーは本仕様に準拠しないそのクライアントからの 認可リクエストを拒否しなければ MUST なりません。 また、このサーバーメタデータ値が true の場合に リクエストオブジェクトが none の alg 値を 使用している場合も、リクエストを拒否しなければ MUST なりません。省略した場合、デフォルト値は false です。¶

サーバーメタデータとしての値が true の場合、 サーバーは本仕様に準拠しない任意のクライアントからの 認可リクエストを拒否しなければ MUST なりません。 また、リクエストオブジェクトが none の alg 値を 使用している場合も、リクエストを拒否しなければ MUST なりません。省略した場合、 デフォルト値は false です。¶

require_signed_request_object メタデータ値が 存在しない場合でも、クライアントとサーバーが相互にサポートする 署名アルゴリズムがあることを条件として、クライアントは署名された リクエストオブジェクトを MAY 使用できることに注意してください。 署名アルゴリズムメタデータの使用については、 第4節で説明されています。¶

10.6. TLS セキュリティに関する 考慮事項

現在のセキュリティ上の 考慮事項は、「Transport Layer Security (TLS) および Datagram Transport Layer Security (DTLS) の安全な使用に関する推奨事項」 [RFC7525] に記載されています。これは、 OAuth 2.0 [RFC6749] の TLS バージョンに関する推奨事項に 優先します。¶

10.7. パラメーターの不一致

OAuth パラメーター値が通常の OAuth パラメーターと リクエストオブジェクト Claim という2つの異なる場所で送信されるため、 実装は、不一致のパラメーター値を利用して 意図しない結果を得ようとする攻撃を防がなければなりません。 これが、2つのクライアント ID 値が一致しなければ MUST ならない理由、 リクエストオブジェクト内のパラメーター値だけを使用する理由、 および request と request_uri のいずれも リクエストオブジェクト内に出現できない理由です。¶

10.8. JWT 間の混同

第2.8節 of [RFC8725] で説明されているように、 攻撃者は、ある目的のために発行された JWT を、その JWT が意図されていない コンテキストで使用しようとする場合があります。 これらの攻撃について説明されている緩和策は、リクエストオブジェクトにも適用できます。¶

攻撃者がリクエストオブジェクトを別用途に転用しようとする方法の1つは、 第2.2節 of [RFC7523] で説明されているように、 クライアント認証 JWT として使用しようとすることです。 これを防ぐ簡単な方法は、リクエストオブジェクト内の sub 値としてクライアント ID を決して使用しないことです。¶

JWT 間の混同を防ぐ別の方法は、 第3.11節 of [RFC8725] で説明されている 明示的な型付けを使用することです。 値 oauth-authz-req+jwt を持つ typ ヘッダーパラメーターを含めることで、 リクエストオブジェクトを明示的に型付けできます （これは 第9.4.1節で登録されています）。 ただし、既存の認可サーバーで明示的に型付けされたリクエストオブジェクトを 必須にすると、既存のクライアントはすでに型付けされていないリクエストオブジェクトを 一般的に使用しているため、ほとんどの既存デプロイメントが破損することに 注意してください。特に OpenID Connect [OpenID.Core] ではその傾向があります。 しかし、既存デプロイメントとの互換性を考慮する必要がない 新しい OAuth デプロイメントプロファイルでは、明示的な型付けを 必須にすることは良い考えです。¶

最後に、JWT 間の混同を防ぐさらに別の方法は、 リクエストオブジェクトの署名に使用する鍵を、 他の目的に使用される鍵と識別可能な形で明確に区別する 鍵管理方式を使用することです。そうすれば、攻撃者が リクエストオブジェクトを別のコンテキストで転用しようとした場合、 鍵の不一致が発生し、攻撃を阻止できます。¶

11. プライバシーに関する考慮事項

クライアントが個人データを含む保護対象リソースへの アクセスを許可される場合、クライアントと 認可サーバーの両方がプライバシー原則を 遵守する必要があります。 「インターネットプロトコルに関するプライバシー上の考慮事項」 [RFC6973] は、 プロトコルの設計および実装の改善について 優れた指針を提供しています。 そこに列挙されている規定に従うべきです。¶

ほとんどの規定は、 「OAuth 2.0 認可フレームワーク」 [RFC6749] および「OAuth 2.0 認可フレームワーク：Bearer Token の使用」 [RFC6750] に適用されるものであり、本仕様に固有のものではありません。 以下では、本仕様に固有の規定のみを 記載します。¶

11.1. 収集の制限

クライアントが個人データを含む保護対象リソースへのアクセスを 許可される場合、クライアントは個人データの収集を、 適用される法令の範囲内で、指定された目的に 厳密に必要なものに制限するべきです。¶

要求された個人データが厳密に必要かどうかを ユーザーが判断するのは、多くの場合困難です。信頼できる第三者サービスは、 クライアントのリクエストを調査し、それをクライアントが提案する 処理と比較し、リクエストを認証することで ユーザーを支援できます。認証後、クライアントは認可リクエストを行う際、 信頼できる第三者サービスに認可リクエストを送信して リクエストオブジェクト URI を取得できます。この処理には2つのステップがあります:¶

(1)
（認証プロセス）信頼できる第三者サービスは クライアントのビジネスプロセスを調査し、必要な Claim を 決定します。これが認証プロセスです。クライアントが 認証されると、信頼できる第三者サービスに対して認証し、 リクエストオブジェクトをプッシュして request_uri を取得するための クライアント資格情報が発行されます。¶
(2)
（変換プロセス）クライアントは取得したクライアント資格情報を使用して、 リクエストオブジェクトを信頼できる第三者サービスにプッシュし、 request_uri を取得します。信頼できる第三者サービスは、 前のステップに従って、リクエストオブジェクトがクライアントに 認められている Claim と一致していることも検証します。¶

認可リクエスト内でこのようなリクエストオブジェクト URI を受信すると、 認可サーバーはまず、リクエストオブジェクト URI の authority 部分が 信頼できる第三者サービスに対して正当なものであることを検証します。 次に、認可サーバーはリクエストオブジェクト URI に HTTP GET リクエストを 発行します。接続すると、認可サーバーは、 TLS 証明書で表されるサーバー ID がリクエストオブジェクト URI に対して 正当であることを検証しなければ MUST なりません。その後、 認可サーバーは、クライアントを表す client_id を含む リクエストオブジェクトを取得できます。¶

同意画面はクライアントを示さなければ MUST ならず、 また、収集制限の原則への準拠について、リクエストが信頼できる 第三者サービスによって審査済みであることを示すべきです SHOULD。¶

11.2. 開示の制限

11.2.1. リクエストの開示

本仕様では拡張パラメーターを使用できます。 これらには機密性の高い可能性がある情報が含まれる場合があります。 URI クエリパラメーターはさまざまな方法で、 特にリファラーおよびブラウザー履歴を通じて漏えいする可能性があるため、 認可リクエストに機密性の高い可能性があるパラメーターが 含まれる場合、クライアントは JWE [RFC7516] を使用して リクエストオブジェクトを暗号化するべきです。¶

リクエストオブジェクト URI 方式を使用している場合、 リクエストオブジェクトに個人を特定できる情報または機密情報が 含まれている場合、リクエストオブジェクト自体が JWE [RFC7516] を使用して暗号化されていない限り、 request_uri は一度だけ使用し、 有効期間を短くするべきであり、適用されるセキュリティポリシーに対して 十分なエントロピーを持たなければ MUST なりません。 適切な有効期間の短さおよびリクエストオブジェクト URI のエントロピーは、 保護されるリソースの価値に基づく リスク計算によって決まります。一般的な指針として、 本仕様の執筆時点では、有効期間は1分未満とし、 リクエストオブジェクト URI には 128 ビット以上の暗号学的乱数値を含めることが推奨されます。¶

11.2.2. リクエストオブジェクト URI を使用した追跡

保護対象リソースに個人を特定できる情報が 含まれていない場合でも、ユーザーごとに永続的かつ固定された リクエストオブジェクト URI を使用すると、 リクエストオブジェクト URI を通じてユーザーを特定できる場合があります。 第三者はブラウザー履歴などを介してそれを観察し、 それを使用してユーザーの活動を関連付け始める可能性があります。 ある意味では、これもデータ開示であり、 回避するべきです。¶

したがって、ユーザーごとの永続的なリクエストオブジェクト URI は避けるべきです。 一度限りのリクエストオブジェクト URI は代替手段の1つです。¶
