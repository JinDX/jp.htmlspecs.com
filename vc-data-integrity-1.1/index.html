1. はじめに

このセクションは非規範的です。

この仕様では、暗号技術、特にデジタル署名 および関連する数学的証明を使用して、検証可能なクレデンシャルや 同様の種類の制約されたデジタル 文書の真正性と完全性を確保するための仕組みについて説明します。暗号学的証明は、 分散システムの実装者にとって有用な機能を実現します。たとえば、証明は 次の目的で使用できます。

  • 作成者を第三者が検証できるため、信頼を損なうことなく共有できる 言明を作成します。たとえば、 検証可能なクレデンシャル [VC-DATA-MODEL-2.0]、検証可能な プレゼンテーション、 またはソーシャルメディアの投稿の一部として使用できます。
  • 特定の識別子によって識別されるエンティティとして認証します。たとえば、 分散型識別子 (DID) [DID] によって識別される主体として認証します。
  • 認可ケイパビリティ [ZCAP] などの 仕組みを介して、リモート実行環境におけるアクションの認可を委任します。
  • 合意を別の当事者が検証できる契約に同意します。
  • さらに、暗号学的デジタル署名に基づく多くの証明は 完全性保護の利点を提供し、文書やデータの 改ざんを検知可能にします。

1.1 完全開示

このセクションは非規範的です。

検証可能なクレデンシャル・データモデル v2.0によると、検証可能なクレデンシャル は、同じ発行者によって行われた、1つまたは 複数のクレーム の集合です。特定の保有者は、 多数の発行者から検証可能な クレデンシャルを取得できます。検証者に提示する際、保有者は 既存の検証可能なクレデンシャルから1つだけ、またはその一部を 選択して、検証可能なプレゼンテーションを構成できます。特定の検証可能な プレゼンテーションで検証者に提示するクレデンシャルの 部分集合を最小限にすることで、プライバシーが向上します。

最も単純なデプロイメントでは、検証可能なプレゼンテーションを介して 検証可能なクレデンシャル全体のみを共有できます。言い換えると、特定の 検証可能なクレデンシャルから単一のクレームを共有するには、その検証可能なクレデンシャル全体を 検証可能なプレゼンテーションの一部にする必要があります。 このアプローチを完全開示と呼びます。

1.1.1 完全開示の仕組み

このセクションは非規範的です。

Data Integrity の動作は概念的には単純です。 暗号学的証明を作成するには、次の手順を実行します。1) 変換、 2) ハッシュ化、3) 証明生成。

変換は、入力データを受け取り、ハッシュ化プロセス用に準備する変換 アルゴリズムによって記述されるプロセスです。 可能な変換の一例として、会議に出席した人々の名前の記録を取得し、 各人の姓に基づいて一覧をアルファベット順に並べ替え、 並べ替えた順に1行に1名ずつ紙に名前を書き直すことが挙げられます。 変換の例には、 正規化 および バイナリからテキストへの符号化があります。

ハッシュ化は、ハッシュアルゴリズムによって記述されるプロセスで、 暗号学的ハッシュ関数を使用して、変換されたデータの識別子を計算します。このプロセスは概念的には、 電話帳の仕組みに似ています。電話帳では、人の名前（入力データ）を取得し、 その名前をその人の電話番号（ハッシュ）に対応付けます。 暗号学的ハッシュ関数の例には、 SHA-3 および BLAKE-3があります。

証明生成は、 証明直列化アルゴリズムによって記述されるプロセスであり、 入力データの完全性を変更から保護する、または所望の一定の信頼しきい値を 証明する値を計算します。このプロセスは概念的には、 手紙が入った封筒に封蝋を使用して送信者への信頼を確立し、 輸送中に手紙が改ざんされていないことを示す方法に似ています。 証明直列化関数の例には、一般に、 デジタル署名、 プルーフ・オブ・ステーク、および 知識証明があります。

暗号学的証明を検証するには、次の手順を実行します。 1) 変換、2) ハッシュ化、3) 証明検証。

検証中、変換およびハッシュ化の手順は、 概念的には上記で説明したものと同じです。

証明検証は、 入力データを信頼できるかどうかを確認するために暗号学的証明検証関数を適用する 証明検証アルゴリズムによって記述されるプロセスです。使用可能な証明 検証関数には、一般に、 デジタル署名、 プルーフ・オブ・ステーク、および 知識証明があります。

この仕様では、暗号ソフトウェアのアーキテクトおよび 実装者が、これらのプロセスを暗号スイートと呼ばれるものにまとめ、 転送中および保存時のアプリケーションデータの完全性を保護する目的で、 アプリケーション開発者に提供する方法を詳しく説明します。

1.2 選択的開示

このセクションは非規範的です。

完全開示は、主体と保有者の双方の プライバシーに明白かつ重大な影響を及ぼします。 保有者のプライバシーをさらに高めるために、発行者は選択的開示をサポートする検証可能な クレデンシャルを作成できます。これは、発行者が、 保有者が元のクレデンシャルのクレームの一部だけを選択的に開示できる 検証可能なクレデンシャル を作成し、検証者に提示される 派生クレデンシャルを生成できるようにする暗号技術です。 これは、派生 クレデンシャル内のデータの完全性と真正性について、発行者から検証者への保証を伴って実現されます。

選択的開示は通常、クレーム レベルで適用されることに注意してください。保有者は、発行されたクレームの意味を変更しつつ、 派生クレデンシャルの検証可能性を維持することはできません。 保有者ができるのは、一連の選択的開示 制約を介して、どのクレームを 派生クレデンシャルに含めるかを制限することだけです。ただし、状況によっては、 ゼロ知識証明 (ZKP) と組み合わせたコミットメント付き開示などの より高度な技術により、保有者は 発行者に基づく真正性およびデータ完全性の保証を維持しながら、 「クレーム全体」より少ない情報を開示できます。 さらに、発行者は任意で、元のクレデンシャルの特定のクレームを 必須開示 制約を介して開示する必要があることを指定できます。通常、どのクレームを理解し 検証したいかを示すのは検証者の責任ですが、この制約が存在する可能性にかかわらず、 必要なものは常に要求することが期待されます。

1.2.1 選択的開示の 仕組み

このセクションは非規範的です。

セクション1.1.1 完全開示の仕組みでは、暗号学的証明を 作成および 検証する基本的なプロセスについて説明しています。選択的開示では、 2つではなく3つのプロセスがあります。1) 発行者が基本証明を作成し、2) 保有者が基本証明から派生証明を作成し、3) 検証者が 派生証明を検証します。 この追加の手順が必要な理由は、 派生証明を作成する方法は、特定の方法で作成された 基本証明と組み合わせて使用すると、はるかに効率的だからです。保有者は、 提示時に基本証明を決して開示しないことが期待されます。基本証明内の情報の一部は、 たとえばプライバシーを保護する派生証明を作成するためなど、 保有者のみが使用することを意図している可能性があるためです。

図 3では、発行者は必須開示制約を定義して、 クレームを必須 クレーム（すなわち、他の制約に関係なく派生クレデンシャルに 含まれなければならないクレーム）と、派生クレデンシャルに含める必要がない 非必須クレームに分離できます。 必須開示制約を課すことは任意です。

変換およびハッシュ化の手順は、 必須クレームと非必須クレームが 別々に変換およびハッシュ化される点を除き、完全開示の場合と同様です。 これらの手順の詳細は、基盤となる暗号アルゴリズムによって異なります。

  • 単純なアプローチ（SIC、すなわち「個別クレームへの署名」と呼ばれます）では、 一時的な暗号鍵ペアを生成します。 この鍵ペアのスコープは特定の証明に限定され、 その秘密鍵は基本証明が生成されると破棄されます。 この一時的な鍵ペアを使用して、必須クレームのブロック、および 非必須クレームを1つずつ署名します。次に署名される 基本証明のデータ構造には、一時的な鍵ペアの公開鍵とともに、 これらの署名値が含まれます。
  • SICには、基本証明用に非常に大きなデータ構造が生成される可能性があるという 欠点があります。これは、量子耐性を持つ一部の署名方式のように 署名サイズが大きい場合に発生し、一部のアプリケーションでは 許容できないほど大きくなる可能性があります。 この場合には、代替アプローチ（SHoC、すなわち「クレームのソルト付きハッシュ」と呼ばれます）を 使用できます。各クレームに対してソルト値 （すなわち、ランダムなノンス）を作成し、ソルト+クレームのペアに ハッシュ関数を適用します。 次に署名される基本証明のデータ構造には、 各ソルト+クレームにつき1つのハッシュの一覧と、 対応するソルト値が含まれます。SHoCアプローチには、 実装がより複雑になること、署名されたクレームの総数に関する情報が漏洩する可能性があること、 また、開示されないクレームについてもすべてのハッシュを証明に含める必要があり、 そのサイズが増加すること（ただし、署名サイズではなくハッシュサイズに基づく）という欠点があります。

技術的な詳細、およびSICとSHoC （さらに、非常に特定の署名方式に適合した第3のアプローチ、すなわち [VC-DI-BBS]）の比較については、 4.3.1 はじめにおよび表 1を参照してください。

1.3 設計目標と根拠

このセクションは非規範的です。

単純性
この技術は、暗号技術に関する高度な訓練を必要とせず、 アプリケーション開発者が容易に使用できるように設計されています。 次の関係者の優先順位に最適化されています。暗号 スイート実装者よりアプリケーション開発者を、暗号スイート設計者より暗号スイート 実装者を、暗号アルゴリズム仕様の作成者より暗号スイート設計者を優先します。 このソリューションは、効果のない保護メカニズムが選択されるのを防ぐため、 妥当なデフォルトに重点を置いています。詳細については、セクション 5.2 アプリケーション開発者の保護および 5.1 暗号スイートのバージョン管理を参照してください。
合成可能性
歴史的なデジタル署名メカニズムの多くは、データ変換、構文、 デジタル署名、直列化を単一の仕様にまとめたモノリシックな 設計を採用しており、ユースケースが制限されていました。この 仕様では各コンポーネントを階層化することで、一般化された選択的開示や 直列化方式に依存しない署名など、より広範なユースケースを 実現できます。さらなる根拠については、セクション5.6 変換、セクション5.8 データの不透明性、および 5.1 暗号スイートのバージョン管理を参照してください。
耐障害性
技術の進歩によってデジタル証明メカニズムが予告なく危殆化する可能性があるため、 暗号 スイートが 複数の保護層を提供し、迅速にアップグレードできることが重要です。この 仕様は、アルゴリズムのアジリティと暗号学的な階層化の両方を提供しながら、 デジタル証明の形式を開発者が容易に理解し、 使用できるものに保ちます。詳細については、セクション5.4 アジリティと階層化を参照してください。
段階的な拡張性
新しい暗号学的保護メカニズムの作成とデプロイは、 実験から実装、標準化へと段階的に拡張が進むことを認識した、 熟慮を伴う反復的かつ慎重なプロセスとなるよう設計されています。 この仕様は、暗号技術におけるイノベーションの速度を高める必要性と、 安定した本番環境向け暗号スイートの必要性とのバランスを取ることを目指しています。 新しい種類の暗号学的証明を確立するための手順については、セクション3. 暗号スイートを参照してください。
直列化の柔軟性
暗号学的証明は、異なるが等価な多くの方法で直列化でき、 多くの場合、元の文書構文に密接に結び付けられてきました。この 仕様では、元の文書構文に 結び付けられない暗号学的証明を作成できるため、暗号学的証明を 再生成することなく、JSON や CBOR などのさまざまな 直列化構文にわたって単一のデジタル署名を使用するといった、より高度なユースケースが可能になります。 このようなアプローチの利点の説明については、セクション5.6 変換を参照してください。

2. データモデル

このセクションでは、 データ完全性証明および関連するリソースの完全性を表現するために使用される データモデルを規定します。

この仕様のすべてのデータモデルのプロパティと型は URL に対応付けられます。 これらの URL が定義されている語彙は、セキュリティ語彙です。 保護された文書でこの対応付けを行うために使用される明示的な メカニズムは、@context プロパティです。

この対応付けメカニズムは、JSON-LD 1.1によって定義されています。JSON-LD ライブラリを使用せずに 文書を相互運用可能な形で処理できるようにするため、文書作成者は、 ドメイン専門家が 1) @context プロパティに関連付けられるすべての値について想定される順序を 指定し、2) 各 @context ファイルの暗号学的 ハッシュを公開し、3) 各 @context ファイルの内容が 意図されたユースケースに適切であると判断していることを確認することが推奨されます。

JSON-LD ライブラリを利用しないプロセッサによって文書が処理され、JSON-LD 環境で使用されるものと 同じ意味論を使用する必要がある場合、実装者は 1) @context プロパティの 想定される順序と値を強制し、2) 各 @context ファイルが 各 @context ファイルについて既知の暗号学的ハッシュと一致することを確認することが推奨されます。

公開された暗号学的ハッシュを持つ静的でバージョン管理された @context ファイルを JSON Schema と併用することは、上記で説明した メカニズムを実装するための許容されるアプローチの1つであり、JSON-LD ライブラリを利用しないプロセッサが使用される場合に、 適切な用語の識別、型付け、 および順序を確保します。 詳細については、検証可能なクレデンシャル・データモデル v2.0の 型固有の処理に関するセクションを参照してください。

2.1 証明

データ完全性証明は、証明メカニズム、 その証明を検証するために必要なパラメータ、および証明値自体についての情報を提供します。 この情報はすべて、 セキュリティ 語彙などの Linked Data 語彙を使用して提供されます。

オブジェクト上でデータ完全性証明を表現する場合、 proof プロパティを使用しなければなりません。 検証可能なクレデンシャル内の proof プロパティは、名前付きグラフです。存在する場合、 その値は単一のオブジェクト、または順序のないオブジェクト集合のいずれかでなければならず、 以下のプロパティを使用して表現されます。

id
証明の任意の識別子であり、URN としての UUID （urn:uuid:6a1676b8-b51f-11ed-937b-d76685a20ff5）などの URL [URL] でなければなりません。 このプロパティの使用方法については、セクション2.1.2 証明 チェーンでさらに説明します。
type
証明の具体的な型は、URL に対応付けられる文字列として指定しなければなりません [URL]。証明型の例には、 DataIntegrityProof および Ed25519Signature2020 があります。証明型は、証明を 保護および検証するために必要なその他のフィールドを決定します。
proofPurpose
証明が作成された理由は、URL に対応付けられる文字列として 指定しなければなりません [URL]。証明目的は、証明が 意図された目的以外の目的に適用されることで 誤用されるのを防ぐための安全策として機能します。たとえば、この値がない場合、 証明の作成者が、ログイン処理中（authentication）に、通常は検証可能な クレデンシャルを作成するために使用される暗号学的素材（assertionMethod）を 使用するよう欺かれ、その結果、単に Web サイトへログインするという 意図した操作ではなく、作成するつもりのなかった検証可能な クレデンシャルが作成される可能性があります。
verificationMethod
検証方法とは、証明を検証するために必要な手段と情報です。 含まれる場合、その値は [URL] に対応付けられる文字列でなければなりません。 verificationMethod を含めることは任意ですが、含まれない場合、 cryptosuite などのその他のプロパティが、証明を検証するために必要な 情報を取得するメカニズムを提供する場合があります。verificationMethod が データ完全性証明で表現される場合、 その値はデータの実際の場所を指すことに注意してください。つまり、verificationMethod は URL を介して、 証明の検証に使用できる公開鍵の場所を参照します。この 公開鍵データは、検証方法の完全な説明を含む制御された識別子 文書に保存されます。
cryptosuite
証明の検証に使用できる暗号スイートの識別子です。詳細については、 3. 暗号スイートを参照してください。証明の type が DataIntegrityProof の場合、cryptosuite を指定しなければなりません。 それ以外の場合、cryptosuite を 指定してもよいです。指定する場合、その値は文字列でなければなりません。
created
証明が作成された日時は任意であり、含まれる場合は、 [XMLSCHEMA11-2] dateTimeStamp 文字列として指定しなければなりません。値の末尾の Z で示される協定 世界時 (UTC)、または UTC に対するタイム ゾーンオフセットのいずれかです。適合するプロセッサは、 オフセットなしで誤って直列化された 時刻値を処理することを選択してもよいです。オフセットなしで誤って 直列化された時刻値は UTC として解釈されます。
expires
expires プロパティは任意であり、存在する場合、 証明がいつ期限切れになるかを指定します。存在する場合、[XMLSCHEMA11-2] dateTimeStamp 文字列でなければなりません。 値の末尾の Z で示される協定世界時 (UTC)、 または UTC に対するタイムゾーンオフセットのいずれかです。適合するプロセッサは、 オフセットなしで誤って直列化された時刻値を処理することを 選択してもよいです。オフセットなしで誤って直列化された時刻値は UTC として解釈されます。
domain
domain プロパティは任意です。これは、証明が 使用されることを意図する1つ以上のセキュリティドメインを伝えます。指定する場合、関連付けられる値は、 文字列、または順序のない文字列の集合のいずれかでなければなりません。 検証者は、その証明が、検証者が動作しているセキュリティドメインで 使用されることを意図していたことを確認するために、その値を使用すべきです。 domain パラメータの指定は、検証者が証明の作成者に既知の セキュリティドメイン内で動作しているチャレンジレスポンスプロトコルで有用です。 ドメイン値の例には、domain.example（DNS ドメイン）、https://domain.example:8443 （Web オリジン）、mycorp-intranet（独自のテキスト文字列）、および b31d37d4-dd59-47d3-9dd8-c973da43b63a（UUID）があります。
challenge
domain が指定されている場合に証明へ含めるべき文字列値です。 この値は、特定のドメインおよび時間枠に対して1回使用されます。この 値はリプレイ攻撃を軽減するために使用されます。challenge 値の例には、 1235abcd6789、79d34551-ae81-44ae-823b-6dadbab9ebd4、および ruby があります。
proofValue
指定された verificationMethod を使用して デジタル証明を検証するために必要な、base 符号化されたバイナリデータを表現する 文字列値です。この値は、 制御された識別子 v1.0仕様のセクション 2.4 Multibaseで説明されている ヘッダーおよび符号化を使用してバイナリデータを表現しなければなりません。 この値の内容は特定の cryptosuite によって決定され、その cryptosuite の 証明追加アルゴリズムによって生成された証明値に設定されます。 cryptosuite によって異なる符号化方式が指定された代替プロパティを、このプロパティの 代わりに使用して、デジタル証明の検証に必要なデータを符号化してもよいです。
previousProof
previousProof プロパティは任意です。存在する場合、 文字列値または順序のない文字列値のリストでなければなりません。各値は別の データ完全性証明を識別し、現在の 証明が検証済みと見なされるには、それらすべても検証に成功しなければなりません。このプロパティはセクション 2.1.2 証明チェーンで使用されます。
nonce
証明の作成者によって提供される任意の文字列値です。この フィールドの用途の1つは、決定論的に生成される署名によって生じるリンク可能性を 低減することでプライバシーを向上させることです。

}

2.1.3 証明グラフ

文書内のデータを保護する場合、保護されるデータを明確に区分することが重要です。 これは、保護メカニズムに関連付けられたデータを含むグラフを除き、 文書内で表現されるすべてのグラフです。その除外されるグラフは、 証明グラフと呼ばれます。この分離を行うことで、 処理アルゴリズムは、保護された文書を決定論的に 保護および検証できます。

文書へデータ完全性証明が追加される前の 入力文書に含まれる情報は、1つ以上の グラフで表現されます。異なるデータ完全性証明からの情報が 誤って混在しないようにするため、証明グラフの概念を使用して、 各データ完全性証明をカプセル化します。文書の proof プロパティに関連付けられた各値は個別のグラフを識別し、これは 名前付きグラフと呼ばれることもあります。 型はProofGraphであり、単一のデータ完全性証明を含みます。

これらのグラフを使用することは JSON-LD 処理を実行する際に具体的な効果を持ちます。これは、 あるグラフで表現された文を別のグラフの文から適切に分離するためです。 JSON、YAML、CBOR など他のメディア型だけに 処理を限定する実装者は、ある文書のデータを別の文書のデータと マージする場合、たとえば id 値の文字列が両方の文書で同じ場合に、 この点を考慮する必要があります。似た プロパティを持つように見えるオブジェクトでも、それらのオブジェクトが id プロパティを持たず、 かつ URL などのグローバル識別子型を使用していない場合は、 そのような2つのオブジェクトが同じエンティティに関する情報を表現しているかどうかを 判断できないため、マージしないことが重要です。

2.2 証明目的

目的を記述する証明は、それが他の 目的に誤用されるのを防ぐのに役立ちます。証明目的によって、検証者は 証明作成者の意図を知ることができるため、メッセージが誤って 別の目的に悪用されるのを防げます。たとえば、単に 表明を行う目的で署名されたメッセージ（広く共有することを意図している可能性がある）が、 サービスへの認証や何らかのアクションの実行（何かを行うための ケイパビリティを呼び出すなど）のためのメッセージとして悪用される場合があります。

証明目的は、 JSON Web Key (JWK) の key_ops 制限、 Web Cryptography API の KeyUsage 制限、および Internet X.509 公開鍵基盤 証明書および証明書失効リスト (CRL) プロファイルとは異なるメカニズムであることに 注意することが重要です。証明目的は、 証明が作成された理由と、その意図された使用ドメインを表現する一方で、 前述のその他のメカニズムは、秘密鍵で何を行えるかを制限することを 意図しています。証明目的は証明とともに「移動」しますが、鍵の制限は そうではありません。

以下は、一般的に使用される証明目的値の一覧です。

authentication
特定の証明が認証プロトコルの目的にのみ 使用されることを示します。
assertionMethod
証明が表明の作成にのみ使用できることを示します。たとえば、 検証可能な クレデンシャルへの署名です。
keyAgreement
証明が、一般的な暗号化 ライブラリで使用される楕円曲線 Diffie Hellman 鍵共有などの 鍵共有プロトコルに使用されることを示します。
capabilityDelegation
証明がケイパビリティの委任にのみ使用できることを示します。詳細については、 認可ケイパビリティ [ZCAP] 仕様を参照してください。
capabilityInvocation
証明がケイパビリティの呼び出しにのみ使用できることを示します。詳細については、 認可ケイパビリティ [ZCAP] 仕様を参照してください。

2.3 リソースの完全性

外部リソースへのリンクが 適合する保護された文書に含まれている場合、 識別されるリソースが証明の作成後に 変更されたかどうかを知ることが望ましいです。これは、 外部リソースをリモートから取得する場合だけでなく、 検証者が リソースのローカルキャッシュされたコピーを持っている場合にも適用されます。

適合する保護された文書によって参照されるリソースが、 文書が保護されてから変更されていないことを確認できるようにするため、 実装者は id プロパティを含む任意のオブジェクトに digestMultibase という名前のプロパティを含めてもよいです。 存在する場合、digestMultibase 値は、単一の 文字列値、またはリスト形式の文字列値でなければならず、それぞれが Multibase で符号化された Multihash 値です。

JSON-LD コンテキストの作成者は、他のリソースを参照する文書で使用される コンテキストに digestMultibase を追加し、 関連付けられた暗号学的ダイジェストを含めることが期待されます。たとえば、 検証可能なクレデンシャル・データモデル v2.0 の基本 コンテキスト（https://www.w3.org/ns/credentials/v2）には、 digestMultibase プロパティが含まれています。

リソース完全性によって保護されたオブジェクトの例を以下に示します。

例 8: オブジェクトに関連付けられた 完全性保護された画像 
{
  ...
  "image": {
    "id": "https://university.example.org/images/58473",
    "digestMultibase": "zQmdfTbBqBPQ7VNxZEYEj14VmRuZBkqFbiwReogJgS1zR1n"
  },
  ...
}

実装者は、自身のユースケースに適切なハッシュアルゴリズムを 選択していることを確認するため、 FIPS 180-4 セキュアハッシュ標準や 商用国家安全保障アルゴリズムスイート 2.0などの適切な情報源を 参照することが強く推奨されます。

2.4.1 コンテキストの検証

処理を行うアプリケーションが、処理対象となる入力文書の 型、ひいては意味論を明示的に承認していることを確認する必要があります。 JSON-LD コンテキスト値を既知の正しい値と照合しないと、それらが伝える意味論の 差異によってセキュリティ脆弱性につながる可能性があります。 アプリケーションは、適合する保護された文書内のコンテキストを検証するため、 セクション4.1.6 コンテキスト検証のアルゴリズム、または 同等の保護を実現するアルゴリズムを使用しなければなりません。 コンテキスト検証は、セクション4.1.4 証明の 検証またはセクション 4.1.5 証明セットとチェーンの検証の 該当するアルゴリズムを実行した後に実行しなければなりません。

セクション4.1.6 コンテキスト検証で説明されるアルゴリズムは、 コンテキスト値を確認する1つの方法と、未知のコンテキスト値を安全に処理する任意の方法の1つを 提供しますが、実装者は、同じ保護を提供する代替アプローチ、または 異なる手順の順序を使用してもよいです。

たとえば、JSON-LD 処理を一切行わない場合、この確認を行う代わりに、 アプリケーションは、その種類の文書の意味論を適切に理解するために 帯域外で提供される信頼できる文書のガイダンスに従うことができます。

別のアプローチとして、承認されたコンテキストファイルのローカルコピーのみを使用するように、 JSON-LD Context ローダー（文書ローダーと呼ばれることもある）を使用するよう アプリケーションを構成できます。これにより、コンテキストファイルも その暗号学的ハッシュも決して変更されないことが保証され、実質的に セクション4.1.6 コンテキスト検証のアルゴリズムと同じ結果になります。

さらに別の代替アプローチとして、同じく実質的にセクション 4.1.6 コンテキスト検証のアルゴリズムと同等ですが、 アプリケーションが、すべてのコンテキストファイルを ローカルに保存せずに、よく知られたコンテキスト URL と関連付けられた承認済み暗号学的ハッシュの 一覧を保持する方法があります。これにより、アプリケーションの セキュリティ要件を損なうことなく、これらのコンテキストをネットワークから安全に読み込めます。

さらに別の有効なアプローチとして、送信側アプリケーションが、 検証可能なプレゼンテーションを 要求するようなプロトコルを介して、受信側アプリケーションが要求する内容に文書を正確に 圧縮し、 元の文書を保護するときに使用された送信者固有の追加 コンテキスト値を省略できます。暗号 スイートの検証アルゴリズムが検証成功の結果を提供する限り、 このような変換は有効であり、省略されたコンテキストによって以前は圧縮されていた用語が 完全な URL になります。つまり、受信者にとって未知の送信者提供コンテキスト （たとえば `https://ontology.example/v1）に基づいて以前は foo に 圧縮されていた用語は、代わりに https://ontology.example#foo のような URL に 「展開」され、未知のコンテキストが省略され、受信側アプリケーションによって JSON-LD 圧縮アルゴリズムが適用されると、同じ URL に「圧縮」されます。

2.4.2 コンテキスト注入

@context プロパティは、この仕様内の用語が処理される際に 実装が同じ意味論を使用していることを確保するために使用されます。たとえば、 type のようなプロパティが処理され、 DataIntegrityProof のようなその値が使用される場合に重要となることがあります。

アプリケーションが文書を保護するとき、文書に @context プロパティが 提供されていない場合、または文書内で使用される Data Integrity 用語が @context プロパティ内の既存の値によって対応付けられていない場合、実装は https://w3id.org/security/data-integrity/v2 の値を持つ @context プロパティ、 または少なくとも同じ宣言を持つ1つ以上のコンテキスト （検証可能なクレデンシャル・データモデル v2.0 の コンテキスト（https://www.w3.org/ns/credentials/v2）など）を 注入または追加すべきです。

JSON-LD 処理を使用する意図のない実装は、文書の最上位に @context 宣言を含めないことを選択してもよいです。 ただし、@context 宣言を含めない場合、この仕様または対応する cryptosuite に関連する 拡張（新しいプロパティの追加など）を行ってはなりません。

2.4.3 データを損失なく保護する

HTML プロセッサは、回復可能なエラーが 検出された場合でも処理を継続するように設計されています。JSON-LD プロセッサも同様に動作します。 この設計思想は、開発者が JSON-LD 言語のうち有用だと考える部分だけを使用でき、開発者にとって重要でない可能性のあるものについて プロセッサがエラーをスローしないようにすることを意図していました。 この思想は、とりわけ、未定義の用語などに遭遇した場合に、 JSON-LD プロセッサがエラーをスローせず、 代わりに開発者へ警告するよう設計されることにつながりました。

文書を正規化するときなど、JSON-LD から RDF データセットへ変換する場合 [RDF-CANON]、未定義の用語や相対 URL は暗黙のうちに削除される場合があります。 値が削除されると、それらはデジタル証明によって保護されません。これにより 期待の不一致が生じ、JSON-LD プロセッサの動作を知らない 開発者が、特定のデータが保護されていると思っていたにもかかわらず、 エラーがスローされなかったのに実際には保護されていなかったことに驚く可能性があります。 この仕様では、JSON-LD 変換を実行する際に 回復可能なデータ損失が発生した場合、開発者のセキュリティ上の期待との 不一致を避けるため、エラーにすることを要求します。

RDF データセット 正規化 [RDF-CANON] などの JSON-LD 処理を使用する実装は、 入力文書内で未定義の用語が検出された場合など、 JSON-LD プロセッサによってデータが削除されたとき、エラーをスローしなければならず、 そのエラーは DATA_LOSS_DETECTION_ERROR であるべきです。

同様に、適合する保護された 文書は、あるセキュリティドメインから別の セキュリティドメインへ転送される可能性があるため、 適合するプロセッサは、 適合する保護された文書を処理するとき、 文書に特定のベース URL があると仮定できません。 RDF に逆直列化する場合、実装は ベース URL が null に設定されていることを確保しなければなりません。

2.4.4 データ型

このセクションでは、この仕様で使用されるデータ型を定義します。

2.4.4.1 cryptosuiteString データ型

この仕様では、暗号スイート識別子を列挙可能な 文字列として符号化します。これは、圧縮アルゴリズムなど、 このような文字列を効率的に符号化する必要がある処理で有用です。 RDF [RDF-CONCEPTS] など、 文字列値の データ型をサポートする環境では、暗号識別子の 内容は、データ型が https://w3id.org/security#cryptosuiteString に設定されたリテラル値を使用して示されます。

cryptosuiteString データ型は次のように定義されます。

このデータ型を示す URL
https://w3id.org/security#cryptosuiteString
字句空間
すべての Data Integrity cryptosuite 仕様の 集合によって定義された、American Standard Code for Information Interchange [ASCII] 文字列を使用して表現される、すべての cryptosuite 文字列の和集合。
値空間
セクション3.1 DataIntegrityProofで定義される、cryptosuite プロパティを使用して表現されるすべての cryptosuite 型の和集合。
字句から値への対応付け
字句空間の任意の要素は、それを内部表現へ解析した結果に対応付けられ、 その内部表現は、他のすべての可能な cryptosuite 型から その cryptosuite 型を一意に識別します。
正規対応付け
値空間の任意の要素は、字句空間内の対応する文字列へ 対応付けられます。

2.5 Linked Data との関係

Linked Data という用語は、URL などの標準を使用して 物事やそのプロパティを識別し、Web 上の情報を 公開、共有、接続するために推奨されるベストプラクティスを説明するために使用されます。 情報が Linked Data として提示されると、関連する他の情報を容易に発見でき、 新しい情報を容易にリンクできます。Linked Data は 分散型の方法で拡張可能であり、大規模統合への障壁を大幅に低減します。

さまざまなアプリケーションで Linked Data の利用が増えるにつれて、 Linked Data 文書の真正性と完全性を検証できる必要性が 生じています。この仕様は、拡張性や合成可能性などの Linked Data の機能を損なうことなく、数学的証明を使用して データ文書に認証および完全性保護を追加します。

注記: Linked Data の使用は任意の機能です

この仕様は Linked Data にデジタル署名するためのメカニズムを提供しますが、 この仕様が提供する一部の利点を得るために Linked Data を使用する必要はありません。

2.6 検証可能な クレデンシャルとの関係

この仕様を実装する暗号スイートは、 検証可能なクレデンシャル および検証可能な プレゼンテーションを保護するために使用できます。これらのユースケースに 対応する実装者は、この種の文書を処理する際に 追加の確認が適切な場合があることに注意してください。

一部のユースケースでは、証明で使用される 検証 方法が、 検証可能なクレデンシャルのissuer、 または 検証可能なプレゼンテーションの holderに、 妥当性確認の過程で 関連付けられていることを確認することが重要です。そのような関連付けを確認する方法の1つは、 証明の検証方法の controller プロパティの値が、 issuer または holderをそれぞれ識別するために 使用される URL 値と一致し、 検証方法が証明目的を考慮して許容可能な検証関係の下で 表現されていることを確認することです。この特定の関連付けは、 issuer または holderがそれぞれ、 証明の検証に使用される検証方法の コントローラであることを示します。

文書作成者および実装者は、 created およびexpires プロパティを使用して表現される 証明の有効期間と、 validFrom および validUntil プロパティを使用して表現される クレデンシャルの有効期間との 違いを理解することが推奨されます。 これらのプロパティが同じ有効期間を表現する場合もありますが、 そうでない場合もあります。 証明を検証するときは、対象となる時刻 （現在時刻またはその他の任意の時刻である可能性がある）が 証明の有効期間内（すなわち、 created と expires の間）にあることを確認することが重要です。 検証可能なクレデンシャルを 妥当性確認する場合は、 対象となる時刻が クレデンシャルの有効期間内 （すなわち、 validFrom と validUntil の間）に あることを確認することが重要です。 証明の有効期間、または クレデンシャルの有効期間の いずれかの妥当性確認に失敗すると、拒否すべきデータを 受け入れてしまう可能性があることに注意してください。

最後に、実装者は、 検証可能なクレデンシャルに 関連付けられた失効情報と、検証 方法の 失効 および有効期限時刻との間に 違いがあることも理解するよう強く推奨されます。 検証 方法の 失効および 有効期限時刻は、 それぞれ revocation および expires プロパティを使用して表現されます。これらは秘密鍵の 侵害や有効期限切れなどのイベントに関連し、コントローラの セキュリティ慣行や、いつ侵害された可能性があるかといった詳細を明らかにする可能性のある 時刻情報を提供することがあります。検証可能なクレデンシャルの 失効情報は credentialStatus プロパティを使用して表現され、 個人が検証可能なクレデンシャルによって 付与された権限を失うなどのイベントに関連し、 時刻情報を提供しないため、プライバシーが向上します。

3. 暗号スイート

データ完全性証明は、開発者が容易に使用できるように設計されているため、 証明を生成するために覚えておく必要がある情報量を最小限に抑えることを 目指しています。多くの場合、証明の作成を開始するために開発者に要求されるのは、 暗号スイート名（ eddsa-rdfc-2022 など）だけです。これらの暗号スイートは、安全な暗号プリミティブの組み合わせが 使用されることを確保するために必要な暗号技術の訓練を受けた人々によって 作成およびレビューされることがよくあります。このセクションでは、 暗号スイート仕様を作成するための要件を規定します。

すべてのデータ完全性暗号スイート仕様に対する要件は 次のとおりです。

  • 仕様は、人間が読める文書として URL で公開されなければなりません。
  • 仕様は、暗号スイートの type と、そのスイートで使用できるすべての パラメータを特定しなければなりません。
  • 仕様は、入力データを保護対象のデータへ変更するために使用される 変換アルゴリズム（存在する場合）、 パラメータ、およびその他の必要な詳細を記述しなければなりません。
  • 仕様は、保護対象のデータに対して暗号学的ハッシュ化を実行するために使用される ハッシュ アルゴリズムの パラメータ、およびその他の必要な詳細を記述しなければなりません。
  • 仕様は、データの暗号学的保護を実行するために使用される 証明直列化アルゴリズム、 パラメータ、およびその他の必要な詳細を記述しなければなりません。
  • 仕様は、データの暗号学的 検証を実行するために使用される証明検証アルゴリズム、 パラメータ、およびその他の必要な詳細を記述しなければなりません。
  • 仕様は、オプションの集合（マップ options）を受け取り、 暗号スイート インスタンス（構造体 cryptosuite）を返す、データ完全性暗号スイートのインスタンス化 アルゴリズムを定義しなければなりません。このアルゴリズムは、 検証可能なクレデンシャル拡張 文書に記載されるべきです。データ完全性暗号スイート インスタンスの構造体には、 次の項目があります。
    createProof
    入力文書（マップ inputDocument）および証明オプション（マップ options）を入力として受け取り、 データ完全性証明（マップ）またはエラーを生成するアルゴリズム。
    verifyProof
    保護されたデータ文書（マップ securedDocument）を入力として受け取り、暗号スイート検証 結果またはエラーを生成するアルゴリズム。暗号スイート検証結果は、 次の項目を含む 構造体です。
    verified
    検証に成功した場合は true、それ以外の場合は false となるブール値。
    verifiedDocument
    verified が true の場合は、 検証済みの証明が削除された保護されたデータ 文書を表すマップ、 それ以外の場合は null。
    この構造体には、デバッグ情報など、開発者にとって 有用なその他の実装固有情報を含めてもよいです。エラーが生成された場合、 検証処理は完了できなかったことを意味します。ネットワークエラーなどのエラーは、 将来の検証試行も失敗することを意味するものではありません。
  • 仕様は、アルゴリズムで発生する可能性がある既知のリソース枯渇攻撃を詳述し、 各攻撃に対するテスト可能な軽減策を提供しなければなりません。
  • 仕様は、暗号スイート固有のセキュリティ上の考慮事項を詳述する セキュリティに関する考慮事項のセクションを含まなければなりません。
  • 仕様は、暗号スイート固有のプライバシーに関する考慮事項を詳述する プライバシーに関する考慮事項のセクションを含まなければなりません。
  • 暗号スイートに関連付けられた JSON-LD コンテキストは、@protected キーワードを使用して、 その用語を安全でない再定義から保護しなければなりません。

暗号スイート インスタンスは、暗号スイートのインスタンス化アルゴリズムを使用してインスタンス化され、 実装固有の方法でアルゴリズムから利用可能になります。 実装は、既知の暗号スイートのインスタンス化 アルゴリズムを発見するために、検証可能な クレデンシャル拡張文書を使用してもよいです。

3.1 DataIntegrityProof

多くの暗号スイートは、 データ完全性証明を表現する際に同じ基本パターンに従います。このセクションでは、 その一般的な設計パターン、すなわち DataIntegrityProof と呼ばれる暗号スイート型を規定します。 これは、設計プリミティブとソースコードを再利用することで、暗号スイートの 記述と実装の負担を軽減します。

この設計パターンを利用する暗号スイートを規定する場合、 proof 値は次の形式を取ります。

type
type プロパティは、文字列 DataIntegrityProof を含まなければなりません。
cryptosuite
cryptosuite プロパティの値は、 暗号スイートを識別する文字列でなければなりません。 処理環境が文字列 サブタイプをサポートする場合、cryptosuite 値のサブタイプは https://w3id.org/security#cryptosuiteString サブタイプでなければなりません。
proofValue
proofValue プロパティは、セクション 2.1 証明で規定されているとおり使用されなければなりません。

暗号スイートの設計者は、セクション 2.1 証明で定義されている必須の proof 値プロパティを 使用しなければならず、自身の暗号スイート固有のその他のプロパティを 定義してもよいです。

注記: 従来の暗号スイートの設計 パターン

2012年から2020年までの Data Integrity 暗号スイートで見られた設計パターンの1つは、 type プロパティを使用して暗号スイートの特定の型を確立することでした。 Ed25519Signature2020 暗号スイートは、そのような仕様の1つでした。この 方法は暗号スイートの実装に大きな負担をもたらし、新しい 暗号スイートごとに新しい JSON-LD コンテキストの指定が必要となり、 開発者体験が最適とは言えないものになりました。この設計 パターンの合理化された版が2020年に登場し、開発者はすべての最新の暗号スイートをサポートするために、 単一の JSON-LD コンテキストを含めるだけで済むようになりました。これにより、 EdDSA 暗号スイート [DI-EDDSA] や ECDSA 暗号スイート [DI-ECDSA] などのより新しい暗号スイートが、 このセクションで説明する合理化されたパターンに基づいて構築されることが促進されました。

開発者体験を向上させるため、新しい Data Integrity 暗号スイート仕様を作成する作成者は、type を DataIntegrityProof に設定し、 cryptosuite プロパティに cryptosuite の識別子を格納し、 cryptosuite 固有の暗号 データを proofValue 内にカプセル化する（すなわち、アプリケーション層データとして直接公開しない） 最新のパターンを使用するべきです。このパターンに従うことが 知られている暗号スイート仕様の一覧は、 検証可能なクレデンシャル拡張の保護メカニズムのセクション で提供されています。

4. アルゴリズム

4.1 文書アルゴリズム

以下で定義するアルゴリズムは、JSON オブジェクトとして表現された文書を操作します。この 仕様は、JSON オブジェクトをマップとして表現する際に、 JSON-LD 1.1 処理アルゴリズムおよび API仕様に従います。 保護されていないデータ文書とは、証明値を含まないマップです。 入力文書とは、現在の証明がまだ追加されていないマップですが、以前の処理によって追加された証明値を 含んでもよいです。保護されたデータ 文書とは、 1つ以上の証明値を含むマップです。

実装者は、開発者による誤り、過剰なリソース 消費、特定の保護が存在する新たに発見された攻撃モデル、およびその他の改善を 軽減するため、以下のアルゴリズムに加えて合理的なデフォルトと安全策を 実装してもよいです。以下に示すアルゴリズムは、 相互運用可能な実装の最低要件であり、開発者には、より安全で 効率的なエコシステムに貢献できる追加措置を含めることが強く推奨されます。

4.1.1 処理モデル

適合するプロセッサおよびその アプリケーション固有ソフトウェアが使用する処理モデルを、このセクションで説明します。 ソフトウェアが情報を改ざん検知可能にする場合、次の手順を実行します。

  1. ソフトウェアは、JSON または JSON-LD 文書などの文書へ情報をまとめます。
  2. 文書が JSON-LD 文書の場合、ソフトウェアは1つ以上の JSON-LD コンテキストを選択し、@context プロパティを使用して表現します。
  3. ソフトウェアは、許容可能な暗号鍵素材を使用して、 完全開示、選択的開示、またはリンク不能な 開示を提供するものなど、ユースケースの要件を満たす1つ以上の暗号スイートを選択します。
  4. ソフトウェアは、1つ以上の証明を追加するために、 セクション4.1.2 証明の 追加 またはセクション4.1.3 証明セット／チェーンの追加で提供される 該当するアルゴリズムを使用します。

この仕様で説明されるメカニズムを使用して送信された情報を ソフトウェアが使用する必要がある場合、次の手順を実行します。

  1. ソフトウェアは、受信データを、セクション4.1.4 証明の検証またはセクション 4.1.5 証明セットとチェーンの検証で提供される 該当するアルゴリズムが理解できる文書へ変換します。
  2. ソフトウェアは JSON Schema または同等のメカニズムを使用して、 受信文書がアプリケーションによって使用される想定されたスキーマに従っていることを検証します。
  3. ソフトウェアは、受信文書の 完全性を検証するために、セクション4.1.4 証明の検証 またはセクション4.1.5 証明セットとチェーンの検証で提供される該当するアルゴリズムを使用します。
  4. 文書が JSON-LD 文書の場合、ソフトウェアは、文書で使用されるすべての JSON-LD コンテキスト値を 検証するために、セクション4.1.6 コンテキスト検証で提供されるアルゴリズム、 または同等の保護を提供するアルゴリズムを使用します。

4.1.2 証明の追加

次のアルゴリズムは、デジタル証明を入力文書へ追加し、その後、出力文書の真正性 および完全性を検証するために使用する方法を規定します。必要な入力は、 入力文書（マップ inputDocument）、暗号スイートインスタンス（構造体 cryptosuite）、および オプションの集合（マップ options）です。出力は保護されたデータ文書 （マップ）またはエラーです。 このアルゴリズムが文字列を符号化する場合は常に、 UTF-8 符号化を使用しなければなりません。

  1. proof を、inputDocument および options をパラメータとして渡して、 cryptosuite.createProof で指定されたcreateProof アルゴリズムを呼び出した結果とします。アルゴリズムがエラーを生成した場合、 エラーを伝播しなければならず、エラー型を伝えるべきです。
  2. proof.type、 proof.verificationMethod、および proof.proofPurpose の1つ以上の値が設定されていない場合、 エラーを発生させなければならず、 PROOF_GENERATION_ERROR のエラー型を 伝えるべきです。
  3. options に null でない domain 項目がある場合、それは proof.domain と等しくなければならず、 そうでなければエラーを発生させなければならず、 PROOF_GENERATION_ERROR のエラー型を 伝えるべきです。
  4. options に null でない challenge 項目がある場合、それは proof.challenge と等しくなければならず、 そうでなければエラーを発生させ なければならず、 PROOF_GENERATION_ERROR のエラー型を 伝えるべきです。
  5. securedDataDocument を inputDocument のコピーとします。
  6. securedDataDocument.proof を proof の値に設定します。
  7. securedDataDocument を保護されたデータ文書として返します。

4.1.3 証明セット／チェーンの追加

次のアルゴリズムは、証明または証明 セット／チェーンのいずれかを含む保護された文書から開始して、証明セットまたは証明チェーンへ 証明を段階的に追加する方法を規定します。必要な入力は、保護されたデータ文書（マップ securedDocument）、暗号スイート（暗号スイート インスタンス suite）、およびオプションの集合（マップ options）です。出力は新しい 保護されたデータ文書（マップ）です。このアルゴリズムが文字列を 符号化する場合は常に、 UTF-8 符号化を使用しなければなりません。

  1. proof を securedDocument.proof に設定します。 allProofs を空のリストとします。proof がリストの場合、 proof のすべての要素を allProofs にコピーします。proof がオブジェクトの場合、そのオブジェクトのコピーを allProofs に追加します。
  2. inputDocument を、proof 属性を削除した securedDocument のコピーとします。output を inputDocument のコピーとします。
  3. matchingProofs を空のリストとします。
  4. options に文字列である previousProof 項目がある場合、 previousProof と一致する id 属性を持つ allProofs の要素を matchingProofs に追加します。 previousProof と等しい id を持つ証明が allProofs に存在しない場合、エラーを発生させなければならず、 PROOF_GENERATION_ERROR のエラー型を 伝えるべきです。
  5. options に配列である previousProof 項目がある場合、 その配列の要素と一致する id 属性を持つ allProofs の各要素を追加します。 previousProof リストのいずれかの要素に、 allProofs のどの要素の id 属性とも一致しない id 属性がある場合、エラーを 発生させなければならず、 PROOF_GENERATION_ERROR のエラー型を 伝えるべきです。
  6. inputDocument.proof を matchingProofs に設定します。
    注記: この手順は文書および既存の証明を保護します

    この手順では、名前付き グラフへの参照を追加するとともに、証明 グラフに含まれるすべてのクレームのコピーも追加します。この手順は、 現在の証明を適用する前に、一致する証明を文書へ結び付けるため、 重要です。文書の proof 値は、このアルゴリズムの後の 手順で更新されます。

  7. inputDocument、suite、および options を渡して、 セクション4.1.2 証明の 追加のアルゴリズムの手順1から6を実行します。 例外が発生しなかった場合、生成された proof 値を allProofs に追加し、 それ以外の場合は例外を発生させます。
  8. output.proof を allProofs の値に設定します。
  9. output を新しい保護されたデータ文書として返します。

4.1.4 証明の検証

次のアルゴリズムは、デジタル 証明を検証することで、保護されたデータ文書の真正性と完全性を確認する方法を規定します。 このアルゴリズムは次を入力として受け取ります。

mediaType
[MIMESNIFF] で定義されるメディア型
documentBytes
メディア型が mediaType であるバイト列
cryptosuite
暗号スイートインスタンス
expectedProofPurpose
任意の文字列。 検証者が期待する理由で証明作成者によって proof が生成されたことを 確認するために使用します。一般的な値については、2.2 証明 目的を参照してください
domain
任意の文字列の 集合。 証明作成者が証明を特定のセキュリティドメインへ固定するために使用し、 検証者が証明が異なるセキュリティドメイン間で 使用されていないことを確認するために使用します
challenge
任意の文字列のchallenge。攻撃者が以前に作成された証明を リプレイしていないことを検証者が確認するために使用します

このアルゴリズムは、次の項目を持つ 構造体である 検証結果を返します。

verified
true または false
verifiedDocument
verified が false の場合は Null、 それ以外の場合は入力文書
mediaType
verified が false の場合は Null、 それ以外の場合はメディア型であり、 パラメータを含んでもよいです
warnings
ProblemDetailsのリスト。 デフォルトは空のリスト
errors
ProblemDetailsのリスト。 デフォルトは空のリスト

手順で「エラーを発生させなければならない」と記述されている場合、それは、 verified 値が false で、空でないerrors リストを持つ検証結果を返さなければならないことを意味します。

  1. securedDocument を、documentBytes に対して JSON バイト列を Infra 値へ解析するを実行した結果とします。
  2. securedDocument がマップでないか、または securedDocument.proof が マップでない場合、 エラーを発生させなければならず、 PARSING_ERROR のエラー型を伝えるべきです。
  3. proof を securedDocument.proof とします。
  4. proof.type、 proof.verificationMethod、および proof.proofPurpose の1つ以上が 存在しない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を 伝えるべきです。
  5. expectedProofPurpose が与えられており、それが proof.proofPurpose と一致しない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を 伝えるべきです。
  6. domain が与えられており、 proof.domain と同じ文字列を含まない場合 （単一の文字列は、その 文字列だけを含む 集合として扱う）、 エラーを発生させなければならず、 INVALID_DOMAIN_ERROR のエラー型を 伝えるべきです。
  7. challenge が与えられており、それが proof.challenge と一致しない場合、 エラーを発生させなければならず、 INVALID_CHALLENGE_ERROR のエラー型を 伝えるべきです。
  8. cryptosuiteVerificationResult を、 securedDocument を入力として渡して cryptosuite.verifyProof アルゴリズムを 実行した結果とします。
  9. 次の項目を持つ検証結果を返します。
    verified
    cryptosuiteVerificationResult.verified
    verifiedDocument
    cryptosuiteVerificationResult.verifiedDocument
    mediaType
    mediaType

4.1.5 証明セットと チェーンの検証

証明セットまたは証明チェーンでは、 保護されたデータ文書に、 証明のリスト（allProofs）を含む proof 属性があります。次の アルゴリズムは、allProofs 内のすべての証明を検証することによって、 保護されたデータ文書の真正性と完全性を確認する1つの方法を提供します。 特に、allProofs に含まれる証明の 部分集合だけを検証したい場合には、他のアプローチも可能です。証明の部分集合だけを 検証する別のアプローチを採用する場合、その部分集合内で previousProof を持つ証明は、 それが参照する証明も検証済みと見なされる場合に限り、 検証済みと見なせることに注意することが重要です。

必要な入力は保護されたデータ文書 （securedDocument）です。allProofs の各証明に対応する 検証結果のリストが 生成され、単一の統合された検証結果が出力として返されます。 実装は、統合された検証結果とともに、 その他の検証結果および／または その他のメタデータを返してもよいです。

  1. allProofs を securedDocument.proof に設定します。
  2. verificationResults を空のリストに設定します。
  3. allProofs 内の各 proof について、次の手順を実行します。
    1. matchingProofs を空のリストとします。
    2. proof が previousProof 属性を含み、その 属性の値が文字列である場合、 previousProof の値と一致する id 属性値を持つ allProofs の要素を matchingProofs に追加します。 previousProof の値と等しい id 値を持つ証明が allProofs に存在しない場合、エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー 型を伝えるべきです。 previousProof 属性がリストの場合、その リストの要素の値と一致する id 属性値を持つ allProofs の各要素を追加します。 previousProof リストのいずれかの要素に、 allProofs のどの要素の id 属性値とも一致しない id 属性値がある場合、エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を 伝えるべきです。
    3. inputDocument を、証明値を 削除した securedDocument のコピーとし、その後 inputDocument.proof を matchingProofs に設定します。
      注記: 文書および以前の証明の保護

      この手順がどの文書プロパティおよび以前の証明を保護するかについては、 セクション4.1.3 証明セット／チェーンの追加の 手順6の注記を参照してください。

    4. inputDocument に対して、セクション4.1.4 証明の検証のアルゴリズムの手順4から8を実行します。 例外が発生しなかった場合、 cryptosuiteVerificationResult を verificationResults に追加します。
  4. successfulVerificationResults を空のリストに設定します。
  5. combinedVerificationResult を空の構造体とします。 combinedVerificationResult.status を true に、combinedVerificationResult.document を null に、 combinedVerificationResult.mediaType を null に設定します。
  6. verificationResults 内の各 cryptosuiteVerificationResult について、 次を実行します。
    1. cryptosuiteVerificationResult.verified が false の場合、 combinedVerificationResult.verified を false に設定します。
    2. それ以外の場合、combinedVerificationResult.document を cryptosuiteVerificationResult.verifiedDocument に、 combinedVerificationResult.mediaType を cryptosuiteVerificationResult.mediaType に設定し、 cryptosuiteVerificationResult を successfulVerificationResults に追加します。
  7. combinedVerificationResult.status が false の場合、 combinedVerificationResult.document を null に、 combinedVerificationResult.mediaType を null に設定します。
  8. combinedVerificationResult、successfulVerificationResults を返します。

4.1.6 コンテキスト検証

次のアルゴリズムは、アプリケーションが文書内の入力に固有の ビジネスルールを実行する前に、その文書に関連付けられたコンテキストを理解していることを 確保するために使用できる1つのメカニズムを提供します。このアルゴリズムに関連する さらなる根拠については、セクション2.4.1 コンテキストの検証を参照してください。 このアルゴリズムは、文書（マップ inputDocument）、 既知の JSON-LD コンテキストの集合（リスト knownContext）、および未知のコンテキストが検出された場合に 再圧縮するかどうかを示すブール値（ブール値 recompact）を入力として受け取ります。

このアルゴリズムは、次の項目を持つ 構造体である コンテキスト検証結果を返します。

validated
true または false
validatedDocument
validated が false の場合は Null、 それ以外の場合は入力文書
warnings
ProblemDetailsのリスト。 デフォルトは空のリスト
errors
ProblemDetailsのリスト。 デフォルトは空のリスト

コンテキスト検証アルゴリズムは次のとおりです。

  1. result.validated を false に、 result.warnings を空のリストに、 result.errors を空のリストに、compactionContext を空の リストに設定し、 inputDocument を result.validatedDocument へ複製します。
  2. contextValue を、 result.validatedDocument の @context プロパティの値とします。 これは未定義である可能性があります。
  3. contextValue が knownContext と深い等価でない場合、 result.validatedDocument 内のいずれかの部分木が @context プロパティを含む場合、または contextValue 内のいずれかの URI を参照解決した JSON-LD コンテキストファイルが 既知の正しい値または暗号学的ハッシュと一致しない場合、該当する操作を実行します。
    1. recompact が true の場合、 result.validatedDocument を、 inputDocument と knownContext を入力として JSON-LD 圧縮アルゴリズムを実行した結果に設定します。 圧縮に失敗した場合、少なくとも1つのエラーを result.errors に追加します。
    2. recompact が true でない場合、 少なくとも1つのエラーを result.errors に追加します。
  4. result.errors が空の場合、 result.validated を true に設定します。 それ以外の場合、result.validated を false に設定し、 result から document プロパティを削除します。
  5. result の値を返します。

実装は、実装または特定のユースケースに固有の 追加の検証規則を強制する追加の警告またはエラーを含めてもよいです。

  • detail 値は、エラーについてより長い、人間が読める文字列を提供するべきです。

4.2.2 証明の作成

  1. proof を証明オプション options の複製とします。
  2. proofConfig を、 options、cypherSuiteName、canonScheme、および hashName をパラメータとして渡して、 セクション4.2.4.2 証明構成のアルゴリズムを 実行した結果とします。
  3. transformedData を、unsecuredDocument、 options、cypherSuiteName、canonScheme、および hashName をパラメータとして渡して、セクション 4.2.4.3 変換のアルゴリズムを実行した結果とします。
  4. hashData を、transformedData、 proofConfig、および hashName を パラメータとして渡して、セクション 4.2.4.1 ハッシュ化のアルゴリズムを実行した結果とします。
  5. proofBytes を、hashData、options、および sigFunc をパラメータとして渡して、セクション 4.2.4.4 証明の直列化のアルゴリズムを 実行した結果とします。
  6. proofEncoding が base64 の場合、 proof.proofValue を proofBytes の base64-url 符号化された Multibase 符号化とし、それ以外で proofEncoding が base58 の場合、 proof.proofValue を proofBytes の base58-btc 符号化された Multibase 値とします。
  7. proof をデータ完全性証明として返します。

4.2.4 共通関数

4.2.4.1 ハッシュ化

次のアルゴリズムは、変換済みデータ文書と 証明構成を暗号学的にハッシュ化し、それぞれの 暗号スイートの証明直列化および証明検証アルゴリズムへの入力として 提供できる暗号学的ハッシュデータを生成する方法を規定します。

このアルゴリズムに必要な入力は、変換済みデータ文書 （transformedDocument）、正規証明構成 （canonicalProofConfig）、およびハッシュ名（hashName）です。 一連のバイトとして表現される単一の ハッシュデータ値が出力として生成されます。

  1. hashName が SHA-256 の場合、 transformedDocumentHash を、それぞれの transformedDocument に SHA-256（256ビット出力の SHA-2） 暗号学的ハッシュアルゴリズム [RFC6234] を適用した結果とします。 対応する transformedDocumentHash のサイズは正確に32バイトになります。
  2. hashName が SHA-384 の場合、 transformedDocumentHash を、それぞれの transformedDocument に SHA-384（384ビット出力の SHA-2） 暗号学的ハッシュアルゴリズム [RFC6234] を適用した結果とします。 対応する transformedDocumentHash のサイズは正確に48バイトになります。
  3. hashName が SHA-512 の場合、 transformedDocumentHash を、それぞれの transformedDocument に SHA-512（512ビット出力の SHA-2） 暗号学的ハッシュアルゴリズム [RFC6234] を適用した結果とします。 対応する transformedDocumentHash のサイズは正確に64バイトになります。
  4. hashName が SHA-256 の場合、 proofConfigHash を canonicalProofConfig に SHA-256（256ビット出力の SHA-2） 暗号学的ハッシュアルゴリズム [RFC6234] を適用した結果とします。対応する proofConfigHash のサイズは正確に32バイトになります。
  5. hashName が SHA-384 の場合、 proofConfigHash を canonicalProofConfig に SHA-384（384ビット出力の SHA-2） 暗号学的ハッシュアルゴリズム [RFC6234] を適用した結果とします。対応する proofConfigHash のサイズは正確に48バイトになります。
  6. hashName が SHA-512 の場合、 proofConfigHash を canonicalProofConfig に SHA-512（512ビット出力の SHA-2） 暗号学的ハッシュアルゴリズム [RFC6234] を適用した結果とします。対応する proofConfigHash のサイズは正確に64バイトになります。
  7. hashData を、proofConfigHash（最初の ハッシュ）と transformedDocumentHash（2番目のハッシュ）を連結した結果とします。
  8. hashData をハッシュデータとして返します。
4.2.4.2 証明構成

次のアルゴリズムは、証明ハッシュ化アルゴリズムへの 入力として使用される証明オプションの集合から、 証明構成を生成する方法を規定します。

このアルゴリズムに必要な入力は、証明オプション （options）、暗号スイート識別子（cryptosuite）、 正規化スキーム（canonScheme）、およびハッシュ名 （hashName）です。 証明オプションは、 暗号スイートの型識別子（type）を含まなければならず、 暗号スイート識別子（cryptosuite）を含まなければなりません。 証明構成オブジェクトが出力として生成されます。

  1. proofConfig を options オブジェクトの複製とします。
  2. proofConfig.type が DataIntegrityProof に設定されていない場合、 proofConfig.cryptosuite が暗号スイートに設定されていない場合、 またはその両方の場合、INVALID_PROOF_CONFIGURATION エラーを 発生させなければなりません。
  3. proofConfig.created が、有効な [XMLSCHEMA11-2] 日時ではない値に設定されている場合、INVALID_PROOF_DATETIME エラーを 発生させなければなりません。
  4. proofConfig.|@context| を unsecuredDocument.|@context| に設定します。
  5. canonScheme が rdfc の場合、 canonicalProofConfig を、 ハッシュパラメータを hashName に設定して proofConfig に Universal RDF Dataset Canonicalization Algorithm [RDF-CANON] を適用した結果とします。
  6. canonScheme が jcs の場合、 canonicalProofConfig を、 proofConfig に JSON Canonicalization Scheme [RFC8785] を適用した結果とします。
  7. canonicalProofConfig を返します。
4.2.4.3 変換

次のアルゴリズムは、保護されていない入力文書を、 セクション4.2.4.1 ハッシュ化の ハッシュ化アルゴリズムへの入力として提供できる変換済み文書へ 変換する方法を規定します。

このアルゴリズムに必要な入力は、 保護されていないデータ文書（unsecuredDocument）、 変換オプション（options）、暗号スイート識別子（cryptosuite）、 正規化スキーム（canonScheme）、およびハッシュ名 （hashName）です。 変換オプションは、 暗号スイートの型識別子（type）および暗号スイート 識別子（cryptosuite）を含まなければなりません。 変換済みデータ文書が出力として生成されます。 このアルゴリズムが文字列を符号化する場合は常に、UTF-8 符号化を使用しなければなりません。

  1. options.type が文字列 DataIntegrityProof に設定されていない場合、 options.cryptosuite が暗号スイート 値に設定されていない場合、またはその両方の場合、 PROOF_TRANSFORMATION_ERROR を 発生させなければなりません。
  2. canonScheme が rdfc の場合、 canonicalDocument を、 ハッシュパラメータを hashName に設定して unsecuredDocument に Universal RDF Dataset Canonicalization Algorithm [RDF-CANON] を適用した結果とします。
  3. canonScheme が jcs の場合、 canonicalDocument を、 unsecuredDocument に JSON Canonicalization Scheme [RFC8785] を適用した結果とします。
  4. output を canonicalDocument の値に設定します。
  5. canonicalDocument を変換済みデータ文書として返します。
4.2.4.4 証明の直列化

次のアルゴリズムは、暗号学的ハッシュデータの集合から デジタル署名を直列化する方法を規定します。この アルゴリズムは、Data Integrity 仕様 [VC-DATA-INTEGRITY] の セクション4: アルゴリズムで定義されているアルゴリズムと 併用するように設計されています。必要な入力は、 暗号学的ハッシュデータ（hashData）、証明オプション（options）、 および署名関数（sigFunc）です。 証明オプションは、 暗号スイートの 型識別子（type）を含まなければならず、 暗号スイート識別子（cryptosuite）を含んでもよいです。 一連のバイトとして表現される単一のデジタル証明値が 出力として生成されます。

  1. privateKeyBytes を、 options.verificationMethod 値によって識別される 検証方法に関連付けられた秘密鍵バイト （または秘密鍵バイトを使用可能にする署名インターフェース）を取得した結果とします。
  2. proofBytes を、privateKeyBytes によって指定される 秘密鍵を使用して署名するデータとして hashData を指定し、 sigFunc を適用した結果とします。 proofBytes は、暗号スイートで示される長さになります。
  3. proofBytes をデジタル証明として返します。
4.2.4.5 証明の検証

次のアルゴリズムは、暗号学的ハッシュデータの集合から デジタル署名を検証する方法を規定します。この アルゴリズムは、Data Integrity [VC-DATA-INTEGRITY] 仕様のセクション4: アルゴリズム で定義されているアルゴリズムと併用するように設計されています。 必要な入力は、暗号学的ハッシュデータ（hashData）、 デジタル署名（proofBytes）、証明オプション（options）、 および検証関数（verifyFunc）です。 ブール値として表現される検証結果が 出力として生成されます。

  1. publicKeyBytes を、 Data Integrity 仕様 [VC-DATA-INTEGRITY] の セクション 4: 検証方法の取得で説明されているとおり、 options.verificationMethod 値に関連付けられた 公開鍵バイトを取得した結果とします。
  2. verificationResult を、 publicKeyBytes によって指定される公開鍵を使用し、 proofBytes に対して検証するデータとして hashData を指定して、 verifyFunc を適用した結果とします。
  3. verificationResult を検証結果として返します。

4.3 選択的開示 アルゴリズム

4.3.1 はじめに

このセクションは非規範的です。

暗号学的選択的開示をサポートするクレデンシャルでは、3つの高水準アルゴリズムが 使用されます。最初に、発行者は基本 証明の追加アルゴリズムを使用して、選択的 開示をサポートする署名付きクレデンシャルを作成します。次に、保有者は派生証明の追加アルゴリズムを 使用して、発行者が署名したクレデンシャルの選択的に開示された版を 派生証明とともに作成します。最後に、検証者は派生 証明の検証アルゴリズムを使用して、受信した選択的に開示されたクレデンシャルと 派生証明を、発行者の検証 情報に対して検証します。

この仕様では、主として検証可能なクレデンシャル内のクレーム のレベルで動作する、選択的開示の3つの異なる実装アプローチを認めています。 すなわち、保有者はクレデンシャル内の個々のクレームを選択的に 開示するか、しないかを選択できます。この3つのアプローチは、 使用される基礎的な暗号署名アルゴリズムの効率を 考慮しています。標準化されている（予定の）暗号署名 アルゴリズムのうち、BBS だけが選択的開示をネイティブにサポートします。すなわち、 順序付けられたクレーム一覧に対して基本 署名を生成し、そのクレーム一覧の部分集合に対する「派生署名」の作成を 容易にします。その他の 暗号署名アルゴリズムでは、通常2つのアプローチが使用されます。 (1) 各クレームに個別の署名を提供する、または (2) すべてのクレームの 「ソルト付きハッシュ」の一覧に署名する、という方法です。前者をSIC（個別 クレームへの署名）、後者をSHoC（クレームのソルト付きハッシュ）と呼びます。 署名アルゴリズムが自然に複数のクレームをサポートする場合は、 MCS（複数クレームサポート）と呼びます。

すべてのアプローチは、証明関連のメタデータを保護し、 派生証明から非開示情報が漏洩するのを最小限に抑えるために、 同様のメカニズムを使用します。これらの目的のため、すべてのアプローチで 基本証明と派生証明におおよそ同程度のオーバーヘッドが発生します。 同様に、すべてのアプローチでは、証明に含まれる個々のデータ項目に 同じ符号化である CBOR を使用し、生のオクテットを文字列へ最終的に符号化する際には base64-url を使用します。したがって、この情報は概要の表 1には示していません。

SICアプローチでは、変換手順の後に個々のクレームへ署名します。 したがって、 基本証明のサイズは、クレーム数に選択した署名アルゴリズムが生成する 署名サイズを掛けた値に比例します。そのため、このアプローチは 小さい署名を生成する署名アルゴリズムに適しています。同様に、 派生証明のサイズは、開示されるクレーム数に署名サイズを掛けた値に 比例します。つまり、開示するクレームが少ないほど証明は小さくなります。 これは、他の2つのアプローチにはない優れた特性です。

SHoCアプローチに従う場合、各クレームに対して ソルト値（ランダムなノンス）を作成します。そのソルト値をクレームと連結し、 暗号学的に衝突耐性のあるハッシュ関数をソルト+クレームのペアの一覧に 適用して、各クレームにつき1つのハッシュ一覧を生成します。新たにペアになったソルトと ハッシュの一覧を組み合わせ、選択した署名アルゴリズムで署名します。必要な 署名は1つだけなので、このアプローチは署名サイズが 大きい署名アルゴリズムに適しています。このアプローチの欠点は、ソルトとハッシュの完全な一覧を 保有者と検証者の双方へ伝える必要があることです。開示された クレームを検証するには、検証者はまずソルトとハッシュを組み合わせた一覧への署名を 検証する必要があります。次に、その一覧内のクレームのインデックスを 知る必要があり、その後、一覧から適切なソルト値を使用して、受信したクレームと ソルトを連結した値のハッシュが、表内の ハッシュと一致することを検証します。

MCS 署名アルゴリズムの1つである BBS では、生成される基本証明は 80バイトと非常に短い一方、派生証明は非開示クレーム1つにつき32バイトずつ増加します。

4.3.2 基本証明の作成

次のアルゴリズムは、保護されていないデータ文書が 与えられた場合に、データ完全性証明を作成する方法を規定します。 必要な入力は、保護されていないデータ文書（マップ unsecuredDocument）と、 証明オプションの集合（マップ options）です。出力として、データ完全性証明（マップ）、 またはエラーが生成されます。

  1. proof を証明オプション options の複製とします。
  2. proofConfig を、 options をパラメータとして渡して、セクション 4.2.4.2 証明構成のアルゴリズムを 実行した結果とします。
  3. transformedData を、unsecuredDocument、 proofConfig、および options をパラメータとして渡して、 4.4.1 TransformSD のアルゴリズムを実行した結果とします。
  4. hashData を、transformedData と proofConfig をパラメータとして渡して、 4.4.2 HashSD のアルゴリズムを実行した結果とします。
  5. SHoC アプローチでは、4.6.1 SaltedHashSD のアルゴリズムを実行した結果である saltedHash データを hashData に追加します。
  6. proofBytes を、アプローチ固有の SerializeBase アルゴリズムを実行した結果とします。たとえば、SIC アプローチでは 4.5.1 SerializeBase-SIC を使用し、 SHoC アプローチでは4.6.2 SerializeBase-SHoC を使用します。すべての場合で、 hashData と options をパラメータとして渡します。
  7. proof.proofValue を、proofBytes の base64-url-encoded Multibase 値とします。
  8. proof をデータ完全性証明として返します。

4.3.3 派生証明の追加

次のアルゴリズムは、選択的開示の派生証明を作成します。これは、 選択的開示の「基本証明」によって保護された検証可能な クレデンシャルの保有者によって呼び出されます。派生証明は 検証者へ 提供されます。 アルゴリズムの入力には、JSON-LD 文書（document）、 選択的開示の基本証明（proof）、文を選択的に開示するために使用する JSON ポインタの配列（selectivePointers）、および文書ローダーなどの 任意のカスタム JSON-LD API オプションが含まれます。オブジェクトとして表現される単一の 選択的に開示された文書値が出力として生成されます。

  1. proofData オブジェクトを、アプローチ固有の ParseBase サブアルゴリズムから返された結果とします。たとえば、SIC アプローチでは 4.5.2 ParseBase-SIC を使用し、SHoC アプローチでは4.6.3 ParseBase-SHoC を使用します。 少なくとも、proofData オブジェクトには hmacKey と mandatoryPointers フィールドが含まれます。
  2. disclosureData を、4.4.3 CreateDisclosureData のアルゴリズムを、 document、proofData、 selectivePointers、および文書 ローダーなどの任意のカスタム JSON-LD API オプションを渡して呼び出したときに返されるオブジェクトで初期化します。 disclosureData オブジェクトには次のフィールドが含まれます。 revealDocument、mandatoryIndexes、selectiveIndexes、 verifierLabelMap mandatory、および nonMandatory。
  3. newProof を proof の浅いコピーで初期化します。
  4. newProof 内の proofValue を、アプローチ固有の SerializeDerived アルゴリズムを呼び出した結果で置き換えます。たとえば、SIC アプローチでは 4.5.3 SerializeDerived-SIC を使用し、SHoC アプローチでは 4.6.4 SerializeDerived-SHoC を使用します。 すべての場合で、 proofData と disclosureData をパラメータとして渡します。
  5. revealDocument 内の "proof" プロパティの値を newProof に設定します。
  6. revealDocument を選択的に開示された文書として返します。

4.3.4 派生証明の検証

次のアルゴリズムは、選択的開示の 派生証明の検証を試みます。このアルゴリズムは、選択的 開示によって保護された検証可能な クレデンシャルの検証者によって呼び出されます。アルゴリズムの入力には、 JSON-LD 文書（document）、選択的開示の派生証明 （proof）、および文書ローダーなどの任意のカスタム JSON-LD API オプションが含まれます。 このアルゴリズムは検証結果を返します。

  1. unsecuredDocument を、proof 値を削除した document のコピーとします。
  2. proofData オブジェクトを、アプローチ固有の ParseDerived サブアルゴリズムから返された結果で初期化します。たとえば、SIC アプローチでは 4.5.4 ParseDerived-SIC を使用し、SHoC アプローチでは4.6.5 ParseDerived-SHoC を使用します。 少なくとも、proofData オブジェクトには labelMap と mandatoryIndexes フィールドが含まれます。
  3. verifyData オブジェクトを、セクション4.4.4 CreateVerifyData の アルゴリズムを、document、 proofData、および文書ローダーなどの任意のカスタム JSON-LD API オプションを渡して 呼び出したときに返される値で初期化します。 verifyData オブジェクトには次のフィールドが含まれます。proofHash、 mandatoryHash、および nonMandatory。
  4. verified を、アプローチ固有の VerifyDerived アルゴリズムを呼び出した結果で初期化します。たとえば、SIC アプローチでは 4.5.5 VerifyDerived-SIC を使用し、SHoC アプローチでは 4.6.6 VerifyDerived-SHoC を使用します。すべての場合で、 proofData と verifyData をパラメータとして渡します。
  5. 次の項目を持つ検証結果を返します。

4.4 選択的 開示共通サブアルゴリズム

4.4.1 TransformSD

次のアルゴリズムは、保護されていない入力文書を、 セクション4.4.2 HashSD のハッシュ化アルゴリズムへの 入力として提供できる変換済み文書へ変換する方法を規定し、アプローチによっては ソルト付きハッシュ化アルゴリズム4.6.1 SaltedHashSDへの入力として提供される場合もあります。

このアルゴリズムに必要な入力は、保護されていないデータ 文書 （unsecuredDocument）と変換オプション（options）です。 変換オプションは、暗号スイートの 型識別子（type）、暗号スイート識別子（cryptosuite）、 および検証方法（verificationMethod）を含まなければなりません。 変換オプションは、 必須 JSON ポインタの配列（mandatoryPointers）を含まなければならず、 JSON-LD 文書ローダーなどの追加 オプションを含んでもよいです。変換済みデータ 文書が出力として生成されます。このアルゴリズムが 文字列を符号化する場合は常に、UTF-8 符号化を使用しなければなりません。

  1. hmac を、ローカルで生成されエクスポート可能な HMAC 鍵を使用する HMAC API で初期化します。HMAC は署名アルゴリズムで使用されるものと同じ ハッシュアルゴリズムを使用し、これは関数に提供された verificationMethod を介して検出されます。たとえば、P-256 曲線では SHA-256 です。 [RFC2104] の推奨事項に従い、HMAC 鍵は ダイジェストサイズと同じ長さでなければなりません。SHA-256 の場合、 これは256ビット、すなわち32バイトです。
  2. cryptosuite が ecdsa-sd-2023 に設定されている場合、 labelMapFactoryFunction を、hmac を渡して セクション4.7.5 createHmacIdLabelMapFunction のアルゴリズムを呼び出した結果で 初期化します。それ以外の場合、 labelMapFactoryFunction を、hmac を渡して セクション4.7.4 createShuffledIdLabelMapFunction のアルゴリズムを呼び出した結果で 初期化します。
  3. groupDefinitions を、文字列 "mandatory" をキー、mandatoryPointers を値とするエントリを持つマップで初期化します。
  4. groups を、labelMapFactoryFunction、 groupDefinitions、document としての unsecuredDocument、 および任意のカスタム JSON-LD API オプションを渡して、セクション 4.7.19 canonicalizeAndGroup のアルゴリズムを呼び出した結果で 初期化します。注記: この手順は文書を、hmac に基づく 疑似ランダムな空白ノード識別子を持つ正規 N-Quads の配列へ変換し、 JSON ポインタに基づく選択に従って N-Quad 文字列をグループ化します。
  5. mandatory を、 groups.mandatory.matching マップ内の値で初期化します。
  6. nonMandatory を、 groups.mandatory.nonMatching マップ内の値で初期化します。
  7. hmacKey を、hmac から HMAC 鍵をエクスポートした結果で初期化します。
  8. mandatoryPointers を mandatoryPointers に、 mandatory を mandatory に、nonMandatory を nonMandatory に、 hmacKey を hmacKey に設定したオブジェクトを返します。

4.4.2 HashSD

次のアルゴリズムは、変換済みデータ文書と証明構成を 暗号学的にハッシュ化して、 4.5.1 SerializeBase-SIC や 4.6.2 SerializeBase-SHoC などのアプローチ固有アルゴリズムへの 入力として提供できる暗号学的ハッシュデータを生成する方法を規定します。

このアルゴリズムに必要な入力は、変換済みデータ文書 （transformedDocument）と正規証明構成 （canonicalProofConfig）です。オブジェクトとして表現される ハッシュデータ値が出力として生成されます。

  1. proofHash を、 canonicalProofConfig に RDF データセット正規化 アルゴリズム [RDF-CANON] を適用した後、その結果を 署名アルゴリズムで使用されるものと同じハッシュ、 たとえば P-256 曲線の場合は SHA-256 を使用して暗号学的に ハッシュ化した結果で初期化します。注記: この手順は並列に実行できます。 結果は戻り値の一部であるため、このアルゴリズムが終了する前に 完了していれば十分です。
  2. mandatoryHash を、transformedDocument.mandatory を渡して、 セクション 4.7.20 hashMandatoryNQuads のアルゴリズムを 呼び出した結果で初期化します。
  3. hashData を transformedDocument のディープコピーとして初期化し、 proofHash を proofHash として、mandatoryHash を mandatoryHash としてその オブジェクトに追加します。
  4. hashData をハッシュデータとして返します。

4.4.3 CreateDisclosureData

次のアルゴリズムは、派生証明の生成に使用するデータを作成します。 入力には、JSON-LD 文書（document）、解析済み基本証明データ （proofData）、文を選択的に開示するために使用する JSON ポインタの配列 （selectivePointers）、および文書ローダーなどの任意のカスタム JSON-LD API オプションが 含まれます。単一のオブジェクトである開示データが 出力として生成され、"revealDocument"、"mandatoryIndexes"、 "selectiveIndexes"、"verifierLabelMap"、"mandatory"、および "nonMandatory" フィールドを含みます。

  1. hmac を、proofData.hmacKey を使用する HMAC API で初期化します。 HMAC は署名アルゴリズムで使用されるものと同じハッシュ アルゴリズム、たとえば P-256 曲線の場合は SHA-256 を使用します。
  2. cryptosuite が ecdsa-sd-2023 に設定されている場合、 labelMapFactoryFunction を、hmac を渡して セクション4.7.5 createHmacIdLabelMapFunction のアルゴリズムを呼び出した結果で 初期化します。それ以外の場合、 labelMapFactoryFunction を、hmac を渡して セクション4.7.4 createShuffledIdLabelMapFunction のアルゴリズムを呼び出した結果で 初期化します。
  3. combinedPointers を、mandatoryPointers と selectivePointers を連結した結果で初期化します。
  4. groupDefinitions を次のエントリを持つマップで初期化します。文字列 "mandatory" をキー、proofData.mandatoryPointers を値とするエントリ、 文字列 "selective" をキー、selectivePointers を値とするエントリ、および 文字列 "combined" をキー、combinedPointers を値とするエントリ。
  5. groups と labelMap を、 document、labelMapFactoryFunction、groupDefinitions、 および任意のカスタム JSON-LD API オプションをパラメータとして渡して、 セクション4.7.19 canonicalizeAndGroup のアルゴリズムを 呼び出した結果の対応する値で初期化します。注記: この手順は文書を、 hmac に基づく疑似ランダムな空白ノード識別子を持つ 正規 N-Quad 文字列の配列へ変換し、JSON ポインタに基づく選択に従って N-Quad 文字列をグループ化します。
  6. 必須インデックスを計算します。relativeIndex をゼロで初期化します。
  7. mandatoryIndexes を空の配列で初期化します。
  8. groups.combined.matching のキーに含まれる各 absoluteIndex について、任意の必須 N-Quad の絶対インデックスを、 開示される結合出力に対する相対インデックスへ変換します。
    1. groups.mandatory.matching が absoluteIndex をキーとして持つ場合、 relativeIndex を mandatoryIndexes に追加します。
    2. relativeIndex を増加させます。
  9. 選択的インデックスを計算します。relativeIndex をゼロで初期化します。
  10. selectiveIndexes を空の配列で初期化します。
  11. groups.combined.matching のキーに含まれる各 absoluteIndex について、任意の選択的 N-Quad の絶対インデックスを、 開示される結合出力に対する相対インデックスへ変換します。
    1. groups.selective.matching が absoluteIndex をキーとして持つ場合、 relativeIndex を selectiveIndexes に追加します。
    2. relativeIndex を増加させます。
  12. revealDocument を、document と pointers としての combinedPointers を渡して、セクション 4.7.16 selectJsonLd のアルゴリズムを呼び出した結果で初期化します。
  13. 結合した |combinedGroup.deskolemizedNQuads| に対して RDF データセット正規化アルゴリズム [RDF-CANON] を実行し、 任意のカスタムオプションを渡して、正規 bnode 識別子マップ canonicalIdMap を取得します。 注記: このマップには、検証者が開示文書を正規化するときに生成する 正規空白ノード識別子が含まれます。
  14. verifierLabelMap を空のマップで初期化します。このマップは、 検証者が開示文書を正規化するときに生成する 正規空白ノード識別子を、基本証明で元々署名された空白ノード識別子へ 対応付けます。
  15. canonicalIdMap 内の各キー（inputLabel）と 値（verifierLabel）について、
    1. verifierLabelMap に、verifierLabel をキー、 labelMap で inputLabel をキーとして関連付けられた 値を値とするエントリを追加します。
  16. revealDocument、mandatoryIndexes、 selectiveIndexes、verifierLabelMap、 mandatory としての groups.mandatory.matching、 および nonMandatory としての groups.mandatory.nonMatching に一致するプロパティを持つ オブジェクトを返します。

4.4.4 CreateVerifyData

次のアルゴリズムは、派生証明で保護された、選択的に開示された検証可能な クレデンシャルの検証を実行するために必要な追加データを作成します。 入力には、JSON-LD 文書（document）、解析済み派生証明データ（proofData）、 および文書ローダーなどの任意のカスタム JSON-LD API オプションが含まれます。単一の 検証データオブジェクト値が出力として生成され、次の フィールドを含みます。"proofHash"、"mandatoryHash"、および "nonMandatory"。

  1. proofHash を、セクション 4.2.4.2 証明構成のアルゴリズムが返した canonicalProofConfig 値を暗号学的にハッシュ化した結果とします。 署名アルゴリズムで使用されるものと同じハッシュ、 たとえば P-256 曲線の場合は SHA-256 を使用します。
  2. labelMapFactoryFunction を、 proofData.verifierLabelMap をパラメータとして セクション4.7.3 createLabelMapFunction のアルゴリズムを 呼び出した結果で初期化します。
  3. nquads を、document、 labelMapFactoryFunction、および任意のカスタム JSON-LD API オプションを渡して、セクション 4.7.2 labelReplacementCanonicalizeJsonLd のアルゴリズムを 呼び出した結果で初期化します。注記: この手順は文書を、 labelMap に基づく疑似ランダムな空白ノード識別子を持つ 正規 N-Quads の配列へ変換します。
  4. mandatory を空の配列で初期化します。
  5. nonMandatory を空の配列で初期化します。
  6. nquads 内の各エントリ（index、nq）について、 N-Quads を必須と非必須のカテゴリへ分離します。
    1. mandatoryIndexes が index を含む場合、 nq を mandatory に追加します。
    2. それ以外の場合、nq を nonMandatory に追加します。
  7. mandatoryHash を、mandatory を渡して 4.7.20 hashMandatoryNQuads 関数を 呼び出した結果で初期化します。
  8. proofHash、nonMandatory、および mandatoryHash に一致するプロパティを持つオブジェクトを返します。

4.5 署名付き 個別クレーム (SIC) 固有サブアルゴリズム

4.5.1 SerializeBase-SIC

次のアルゴリズムは、署名付き個別クレーム (SIC) アプローチで 直列化された基本証明を作成する方法を規定します。 必要な入力は、 暗号学的ハッシュデータ（hashData）と 証明オプション（options）です。 証明オプションは、 暗号スイートの型識別子（type）を含まなければならず、 暗号スイート識別子（cryptosuite）を含んでもよいです。 一連のバイトとして表現される単一のデジタル証明値が 出力として生成されます。

  1. proofHash、mandatoryPointers、mandatoryHash、 nonMandatory、 および hmacKey を、hashData 内で それぞれのプロパティ名に関連付けられた値で初期化します。
  2. proofScopedKeyPair を、 crytosuite が使用する署名アルゴリズムに対応する、ローカルで生成された鍵ペアで 初期化します。 注記: この鍵ペアは特定の証明にスコープされており、他の用途には 使用されません。また、このアルゴリズムが終了すると秘密鍵は破棄されます。
  3. signatures を、nonMandatory 内の各 N-Quad 文字列の UTF-8 表現を順番にデジタル署名した結果を各要素に格納する配列で初期化します。 デジタル署名アルゴリズムは cryptosuite のものと同じで、 proofScopedKeyPair の秘密鍵を使用します。注記: この手順では、 選択的に開示できる各文（クレーム）に対して、ローカルで証明にスコープされた 鍵ペアを使用して個別の署名を生成し、それらをまとめて結び付けます。この鍵ペアは、 基本証明の検証方法に関連付けられた秘密鍵を使用して、その公開鍵に 署名することで証明へ結び付けられます。
  4. publicKeyProofScoped を、proofScopedKeyPair からエクスポートされた 公開鍵の multikey 表現で初期化します。
  5. toSign を、proofHash、 publicKeyProofScoped、および mandatoryHash をこの順序で連結した結果で初期化します。
  6. baseSignature を、基本証明の検証方法に関連付けられた 秘密鍵を使用して toSign をデジタル署名した結果で初期化します。
  7. cryptosuite が ecdsa-sd-2023 に設定されている場合、 バイト配列 proofBytes を、従来の ECDSA-SD 基本証明ヘッダーバイト 0xd9、0x5d、0x00 で始まるように初期化します。 それ以外の場合は、proofValue を一般 SIC ヘッダーバイト TBD で初期化します。
  8. components を、次の値を含む5要素の配列で初期化します。 baseSignature、publicKeyProofScoped、hmacKey、 signatures、および mandatoryPointers。
  9. [RFC8949] に従って components を CBOR 符号化します。このとき、いずれの components に対しても CBOR タグ付けを使用してはなりません。 生成された符号化値を proofBytes に追加します。
  10. proofBytes を返します。

4.5.2 ParseBase-SIC

次のアルゴリズムは、従来の ecdsa-sd-2023 選択的 開示基本証明値、または一般的な署名付き個別クレーム (SIC) アプローチの 選択的開示基本証明の構成要素を解析します。必要な入力は証明値 （proofValue）です。baseSignature、publicKeyProofScoped、 hmacKey、 signatures、および mandatoryPointers という名前を使用した 5つの要素を含む単一のオブジェクト解析済み基本証明が出力として生成されます。

  1. proofValue 文字列が u で始まらず、それが multibase-base64url-no-pad 符号化された値であることを示していない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  2. decodedProofValue を、 proofValue の先頭の u より後の部分文字列を base64url-no-pad 復号した結果で初期化します。
  3. decodedProofValue が ECDSA-SD 基本証明 ヘッダーバイト 0xd9、0x5d、0x00、 または一般 SIC ヘッダーバイト TBD で始まらない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  4. components を、3バイトの基本証明ヘッダーに続く バイトを CBOR 復号した結果である配列で初期化します。結果が 5要素の配列であることを確認します。
  5. 5つの要素をそれぞれ baseSignature、publicKeyProofScoped、hmacKey、 signatures、および mandatoryPointers という名前のプロパティに設定したオブジェクトを返します。

4.5.3 SerializeDerived-SIC

次のアルゴリズムは、派生証明値を直列化します。必要な入力は、 次のフィールドを含む dislosureData オブジェクトです。 基本署名（baseSignature）、公開鍵 （publicKey）、署名の配列（signatures）、ラベル マップ（labelMap）、および必須インデックスの配列 （mandatoryIndexes）。バイト文字列として直列化された単一の 派生証明値が出力として生成されます。

  1. compressedLabelMap を、 labelMap をパラメータとして渡して、セクション 4.7.6 compressLabelMap のアルゴリズムを 呼び出した結果で初期化します。
  2. cryptosuite が ecdsa-sd-2023 に設定されている場合、 バイト配列 proofValue を、ECDSA-SD 開示 証明ヘッダーバイト 0xd9、0x5d、0x01 で始まるように初期化します。 それ以外の場合は、バイト 配列 proofValue を、一般 SIC 派生証明ヘッダーバイト TBD で始まるように初期化します。
  3. components を、次の値を含む5要素の配列で初期化します。 baseSignature、publicKeyProofScoped、signatures、 compressedLabelMap、および mandatoryIndexes。
  4. [RFC8949] に従って components を CBOR 符号化します。このとき、いずれの components に対しても CBOR タグ付けを使用してはなりません。 生成された符号化値を proofValue に追加します。
  5. 制御された識別子 v1.0の Multibase セクションで説明されているように、 proofValue を base64url-no-pad 符号化した文字列として 派生証明を返します。つまり、 "u" で始まり、proofValue の base64url-no-pad 符号化値で終わる文字列を返します。

4.5.4 ParseDerived-SIC

次のアルゴリズムは、派生証明値の構成要素を解析します。 必要な入力は派生証明値（proofValue）です。 "baseSignature"、"publicKeyProofScoped"、"signatures"、 "labelMap"、および "mandatoryIndexes" という名前を使用した5つの要素の集合を 含む単一の派生証明値オブジェクトが出力として生成されます。

  1. proofValue 文字列が u で始まらず、それが multibase-base64url-no-pad 符号化された値であることを示していない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  2. decodedProofValue を、 proofValue の先頭の u より後の部分文字列を base64url-no-pad 復号した結果で初期化します。
  3. decodedProofValue が ECDSA-SD 開示証明 ヘッダーバイト 0xd9、0x5d、0x01、 または一般 SIC アプローチの派生 証明ヘッダーバイト TBD で始まらない場合、エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  4. components を、3バイトの派生証明ヘッダーに続くバイトを CBOR 復号した結果である配列で初期化します。結果が 5要素の配列でない場合、エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  5. components の既存の4番目の要素を compressedLabelMap とし、cryptosuite とともに渡して、 セクション4.7.7 decompressLabelMap のアルゴリズムを 呼び出した結果を使用して、components の4番目の要素を置き換えます。
  6. 5つの要素をそれぞれ "baseSignature"、"publicKey"、"signatures"、 "labelMap"、および "mandatoryIndexes" という名前のプロパティに設定したオブジェクトとして 派生証明値を返します。

4.5.5 VerifyDerived-SIC

次のアルゴリズムは、ecdsa-sd-2023 派生 証明、または一般 SIC アプローチの派生証明の検証を試みます。このアルゴリズムは、 ECDSA-SD または SIC アプローチによって保護された 検証可能な クレデンシャルの検証者によって呼び出されます。入力には JSON-LD 文書 （document）、派生証明データ（proofData）、検証データ （verifyData）、および文書ローダーなどの任意のカスタム JSON-LD API オプションが含まれます。 このアルゴリズムは検証結果を返します。

  1. unsecuredDocument を、proof 値を削除した document のコピーとします。
  2. publicKeyBytes を、 制御された 識別子 v1.0仕様の セクション: 検証方法の取得で説明されているとおり、 options.verificationMethod 値に関連付けられた 公開鍵バイトを取得した結果とします。
  3. baseSignature、publicKeyProofScoped、および signatures を proofData オブジェクト内でそれぞれのプロパティ名に 関連付けられた値で初期化し、 proofHash、mandatoryHash、および nonMandatory を verifyData オブジェクト内でそれぞれのプロパティ名に 関連付けられた値で初期化します。
  4. signatures の長さが nonMandatory の長さと一致しない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。 これは、署名数が非必須メッセージ数と一致しないことを示します。
  5. toVerify を、proofHash、 publicKeyProofScoped、および mandatoryHash をこの順序で連結した結果で初期化します。
  6. verified を true で初期化します。
  7. verificationCheck を、 cryptosuite に適した署名アルゴリズムの検証 アルゴリズムを適用した結果で初期化します。このとき、publicKeyBytes によって 指定される公開鍵を使用し、baseSignature に対して検証するデータとして toVerify を使用します。verificationCheck が false の場合、verified を false に設定します。
  8. signatures 内の各エントリ（index、signature）について、 選択的に開示された（非必須）各文のすべての署名を検証します。
    1. verificationCheck を、 cryptosuite の署名アルゴリズム用の検証 アルゴリズムを適用した結果で初期化します。このとき、 publicKeyProofScoped によって指定される公開鍵を使用し、 signature に対して検証するデータとして nonMandatory の index にある値の UTF-8 表現を使用します。
    2. verificationCheck が false の場合、 verified を false に設定します。
  9. 次の項目を持つ検証結果を返します。
    verified
    verified の値
    verifiedDocument
    verified が true の場合は unsecuredDocument、 それ以外の場合はNull

4.6 クレームのソルト付き ハッシュ (SHoC) 固有サブアルゴリズム

4.6.1 SaltedHashSD

次のアルゴリズムは、ソルト付きハッシュデータを作成する方法を規定します。

このアルゴリズムに必要な入力は、変換済みデータ文書 (transformedDocument) と cryptosuite です。オブジェクトとして表現される ソルト付きハッシュデータ値が出力として生成されます。

  1. salts を空の配列として初期化します。 transformedDocument 内の各 nonMandatory 項目について、 ハッシュ長の半分のバイト長を持つ暗号学的に安全な乱数を作成します。たとえば、 SHA-256 を使用するセキュリティカテゴリ1または2では、各ソルトの長さは16バイトになります。
  2. saltedHashes を空の配列として初期化します。 transformedDocument 内の各 nonMandatory 項目について、 各 salt と対応する nonMandatory 項目を連結したものに対して 適切なハッシュ（セキュリティカテゴリ1または2の署名アルゴリズムでは SHA-256）を計算します。 このハッシュ値を saltedHashes 配列に追加します。
  3. salts を salts として、saltedHashes を saltedHashes として saltedHashData オブジェクトに追加します。
  4. saltedHashData を返します。
編集者注

4.6.2 SerializeBase-SHoC

次のアルゴリズムは、SHoC アプローチの基本証明を直列化する方法を規定します。 Quantum-Safe-SD で保護された検証可能なクレデンシャルの 発行者によって呼び出されます。 基本証明は保有者のみに 提供され、保有者はそこから派生証明を生成し、 選択的に開示された詳細だけを証明内で検証者に公開する責任を負います。この アルゴリズムは、Data Integrity [VC-DATA-INTEGRITY] 仕様の セクション4: アルゴリズムで定義されるアルゴリズムと 併用するように設計されています。必要な入力は、 暗号学的ハッシュデータ (hashData) と 証明オプション (options) です。 証明オプションは、 暗号スイートの型識別子 (type) を含まなければならず、 暗号スイート識別子 (cryptosuite) を含んでもよいです。 一連のバイトとして表現される単一のデジタル証明値が 出力として生成されます。

  1. proofHash、mandatoryPointers、mandatoryHash、 salts、 saltedHashes、 および hmacKey を、hashData 内でそれぞれのプロパティ名に 関連付けられた値で初期化します。
  2. toSign を、proofHash、 mandatoryHash、salts、 および saltedHashes をこの順序で連結したもののハッシュで初期化します。 この連結順序には従わなければなりません。 暗号学的ハッシュアルゴリズムは、 cryptosuite の署名アルゴリズムに対して指定されているものです。
  3. signature を、基本証明の検証方法に関連付けられた 秘密鍵を使用して toSign をデジタル署名した結果で初期化します。
  4. バイト配列 proofValue を、SHoC アプローチの 基本証明ヘッダーバイト 0xd9、0x5d、0x10 で始まるように初期化します。
  5. components を、次の値を含む5要素の配列で初期化します。 signature、hmacKey、salts、saltedHashes、および mandatoryPointers。
  6. [RFC8949] に従って components を CBOR 符号化します。このとき、いずれの components に対しても CBOR タグ付けを使用してはなりません。 生成された符号化値を proofValue に追加します。
  7. proofValue を証明バイトとして返します。
編集者注

SHoC アプローチの基本証明ヘッダーバイト 0xd9、0x5d、0x10 は、 [VC-DI-ECDSA] または [VC-DI-BBS] のいずれの値とも 衝突しないように選択されています。これらは 現時点では暫定的なものです。

4.6.3 ParseBase-SHoC

次のアルゴリズムは、SHoC アプローチの選択的 開示基本証明値の構成要素を解析します。必要な入力は証明値 (proofValue) です。signature、hmacKey、salts、 saltedHashes、および mandatoryPointers という名前を使用した 5つの要素を含む単一のオブジェクト証明データが出力として生成されます。

  1. proofValue 文字列が u で始まらず、それが multibase-base64url-no-pad 符号化された値であることを示していない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  2. decodedProofValue を、 proofValue の先頭の u より後の部分文字列を base64url-no-pad 復号した結果で初期化します。
  3. decodedProofValue が SHoC アプローチの基本証明 ヘッダーバイト 0xd9、0x5d、0x10 で始まらない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  4. components を、3バイトの SHoC アプローチ基本証明ヘッダーに続く バイトを CBOR 復号した結果である配列で初期化します。 結果が5要素の配列であることを確認します。
  5. 5つの要素をそれぞれ signature、hmacKey、salts、saltedHashes、および mandatoryPointers という名前のプロパティに設定したオブジェクトを返します。

4.6.4 SerializeDerived-SHoC

次のアルゴリズムは、SHoC アプローチの派生証明値を直列化します。 必要な入力は、基本署名 (signature)、ソルトの配列 (salts)、ソルト付きハッシュの配列 (saltedHashes)、ラベルマップ (labelMap)、必須インデックスの配列 (mandatoryIndexes)、および 選択的インデックスの配列 (selectiveIndexes) です。UTF-8 文字列として直列化された 単一の派生証明値が出力として生成されます。

  1. compressedLabelMap を、labelMap をパラメータとして渡して、 4.7.6 compressLabelMap のアルゴリズムを呼び出した結果で初期化します。
  2. バイト配列 proofValue を、SHoC アプローチの 派生証明ヘッダーバイト 0xd9、0x5d、0x11 で始まるように初期化します。
  3. components を、次の値を含む6要素の配列で初期化します。 signature、salts、saltedHashes、compressedLabelMap、 mandatoryIndexes、 selectiveIndexes。
  4. [RFC8949] に従って components を CBOR 符号化します。このとき、いずれの components に対しても CBOR タグ付けを使用してはなりません。 生成された符号化値を proofValue に追加します。
  5. 制御された識別子 v1.0の Multibase セクションで説明されているように、 proofValue を base64url-no-pad 符号化した文字列として 派生証明を返します。つまり、 "u" で始まり、proofValue の base64url-no-pad 符号化値で終わる文字列を返します。
編集者注

SHoC アプローチの派生証明ヘッダーバイト 0xd9、0x5d、および 0x11 は、[VC-DI-ECDSA] および [VC-DI-BBS] で使用される値と 衝突しないように選択されたもので、暫定的なものです。

4.6.5 ParseDerived-SHoC

次のアルゴリズムは、SHoC アプローチの派生証明 値の構成要素を解析します。必要な入力は派生証明値 (proofValue) です。 "signature"、"salts"、 "saltedHashes"、"labelMap"、"mandatoryIndexes"、および "selectiveIndexes" という名前を使用した 6つの要素の集合を含む単一の証明データオブジェクトが出力として生成されます。

  1. proofValue 文字列が u で始まらず、それが multibase-base64url-no-pad 符号化された値であることを示していない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  2. decodedProofValue を、 proofValue の先頭の u より後の部分文字列を base64url-no-pad 復号した結果で初期化します。
  3. decodedProofValue が SHoC アプローチの派生証明 ヘッダーバイト 0xd9、0x5d、0x11 で始まらない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  4. components を、3バイトの SHoC アプローチ派生証明ヘッダーに続くバイトを CBOR 復号した結果である配列で初期化します。結果が次の6要素の配列でない場合 — 署名サイズに対応する長さのバイト配列、 それぞれがソルトサイズに適した長さを持つバイト配列の配列、 それぞれがハッシュサイズに対応する長さを持つバイト配列の配列、 整数からそれぞれ長さ32のバイト配列へのマップ、 整数の配列、および別の整数の配列 — エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。
  5. components の既存の4番目の要素を compressedLabelMap として渡して、 4.7.7 decompressLabelMap の アルゴリズムを呼び出した結果を使用して、components の4番目の要素を置き換えます。
  6. 6つの要素をそれぞれ "signature"、"salts"、"saltedHashes"、 "labelMap"、"mandatoryIndexes"、および "selectiveIndexes" という名前のプロパティに設定した オブジェクトとして証明データを返します。

4.6.6 VerifyDerived-SHoC

次のアルゴリズムは、SHoC アプローチの派生 証明の検証を試みます。このアルゴリズムは、SHoC アプローチによって保護された 検証可能な クレデンシャルの検証者によって呼び出されます。入力には JSON-LD 文書 (document)、派生証明データ (proofData)、検証データ (verifyData)、および文書ローダーなどの任意の カスタム JSON-LD API オプションが含まれます。このアルゴリズムは 検証結果を返します。

  1. unsecuredDocument を、proof 値を削除した document のコピーとします。
  2. signature、salts、saltedHashes、および selectiveIndexes を、 proofData パラメータ内でそれぞれのプロパティ名に関連付けられた値で初期化し、 proofHash、nonMandatory、および mandatoryHash を、 verifyData パラメータ内でそれぞれのプロパティ名に関連付けられた値で初期化します。
  3. salts の長さが saltedHashes の長さと一致しない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。 これは、ソルト数がソルト付きハッシュ数と一致しないことを示します。
  4. selectiveIndexes 配列の要素値は、0 から salts 配列の長さから1を引いた値までの範囲内でなければなりません。 そうでない場合、 エラーを発生させなければならず、 PROOF_VERIFICATION_ERROR のエラー型を伝えるべきです。 これは、選択的インデックスが範囲外であることを示します。
  5. toVerify を、proofHash、 mandatoryHash、salts、および saltedHashes の値を この順序でバイト連結したもので初期化します。このとき、配列値自体も 互いに連結します。
  6. verified を true で初期化します。
  7. verificationCheck を、 "cryptosuite" プロパティによって示される適切な署名アルゴリズムの 検証アルゴリズムを適用した結果で初期化します。 このとき、signature に対して検証するデータとして toVerify を使用します。 verificationCheck が false の場合、verified を false に設定します。
  8. nonMandatory 内の各エントリ (nq、index) について、 選択的に開示された（非必須）各文のソルト付き ハッシュを検証します。
    1. computedHash を、 salts[selectiveIndexes[index]] と nq を連結したもののハッシュとします。
    2. verificationCheck を、 computedHash と saltedHashes[selectedIndexes[index]] の値を比較した結果で初期化します。
    3. verificationCheck が false の場合、 verified を false に設定します。
  9. 次の項目を持つ検証結果を返します。
    verified
    verified の値
    verifiedDocument
    verified が true の場合は unsecuredDocument、 それ以外の場合はNull

4.7 選択的開示関数

次のセクションには、選択的開示を実行する 暗号スイート全体で使用される一連の関数が含まれています。

4.7.1 labelReplacementCanonicalizeNQuads

次のアルゴリズムは、N-Quad [N-QUADS] 文字列の配列を正規化し、 ラベルマップ生成関数 labelMapFactoryFunction を使用して、 正規化された結果内の空白ノード識別子を置き換えます。必要な入力は、 N-Quad 文字列の配列 (nquads) とラベルマップ生成関数 (labelMapFactoryFunction) です。任意のカスタムオプションも渡すことができます。 置き換えられた空白ノードラベルを持つ、N-Quad 文字列の配列としての canonicalNQuads の N-Quads 表現、および 古い空白ノード ID から新しい空白ノード ID へのマップ labelMap が出力として生成されます。

  1. 結合された nquads に対して RDF データセット正規化アルゴリズム [RDF-CANON] を実行し、 任意のカスタムオプションを渡して、正規 bnode 識別子 マップ canonicalIdMap を含む正規化済みデータセットを 出力として取得します。
  2. canonicalIdMap を labelMapFactoryFunction に渡して、 新しい bnode 識別子マップ labelMap を生成します。
  3. 正規化済みデータセットと labelMap を使用して、 N-Quad 文字列の配列 canonicalNQuads として正規 N-Quads 表現を生成します。
  4. labelMap と canonicalNQuads を含むオブジェクトを返します。

4.7.2 labelReplacementCanonicalizeJsonLd

次のアルゴリズムは JSON-LD 文書を正規化し、ラベルマップ生成 関数 labelMapFactoryFunction を使用して、正規化された結果内の 空白ノード識別子を置き換えます。必要な入力は JSON-LD 文書 (document) とラベルマップ生成関数 (labelMapFactoryFunction) です。追加のカスタムオプション（ 文書ローダーなど）も渡すことができます。 置き換えられた空白ノードラベルを持つ、N-Quad 文字列の配列としての canonicalNQuads の N-Quads 表現、および古い空白ノード ID から 新しい空白ノード ID へのマップ labelMap が出力として生成されます。

  1. 任意のカスタムオプション（文書ローダーなど）を渡して、 JSON-LD を RDF に逆直列化するアルゴリズムを使用し、JSON-LD 文書を RDF rdf に逆直列化します。
  2. rdf を N-Quad 文字列の配列 nquads に直列化します。
  3. nquads、 labelMapFactoryFunction、および任意のカスタムオプションを渡して、 セクション 4.7.1 labelReplacementCanonicalizeNQuads の アルゴリズムを呼び出した結果を返します。

4.7.3 createLabelMapFunction

次のアルゴリズムは、入力ラベルマップを使用して正規空白ノード識別子を 別の値に置き換えるラベルマップ生成関数を作成します。必要な入力は ラベルマップ labelMap です。関数 labelMapFactoryFunction が出力として生成されます。

  1. 1つの必須入力（正規ノード識別子マップ canonicalIdMap）を持ち、 空白ノード識別子マップ bnodeIdMap を出力として返す 関数 labelMapFactoryFunction を作成します。 関数の実装を次のように設定します。
    1. 新しい空の bnode 識別子マップ bnodeIdMap を生成します。
    2. canonicalIdMap 内の各マップエントリ entry について、
      1. entry の値から正規識別子を labelMap のキーとして使用し、 新しいラベル newLabel を取得します。
      2. entry のキーをキーとして、newLabel を値として使用し、 新しいエントリ newEntry を bnodeIdMap に追加します。
    3. bnodeIdMap を返します。
  2. labelMapFactoryFunction を返します。

4.7.4 createShuffledIdLabelMapFunction

次のアルゴリズムは、HMAC を使用して正規空白ノード識別子をシャッフルする ラベルマップ生成関数を作成します。必要な入力は、 （事前に秘密鍵で初期化された）HMAC HMAC です。関数 labelMapFactoryFunction が出力として生成されます。

  1. 1つの必須入力（正規ノード識別子マップ canonicalIdMap）を持ち、 空白ノード識別子マップ bnodeIdMap を出力として返す 関数 labelMapFactoryFunction を作成します。 関数の実装を次のように設定します。
    1. 新しい空の bnode 識別子マップ bnodeIdMap を生成します。
    2. canonicalIdMap 内の各マップエントリ entry について、
      1. entry の値から正規識別子に対して HMAC 演算を実行し、 HMAC ダイジェスト digest を取得します。
      2. 新しい文字列値 b64urlDigest を生成し、"u" に続けて digest 値の base64url-no-pad 符号化版を追加した値で初期化します。
      3. entry のキーをキー、b64urlDigest を値として使用し、 新しいエントリ newEntry を bnodeIdMap に追加します。
    3. bnodeIdMap から次のようにシャッフルされた対応付けを導出します。
      1. hmacIds を bnodeIdMap の値をソートした配列に設定し、 bnodeKeys を bnodeIdMap のキーの順序付き配列に設定します。
      2. bnodeKeys 内の各キーについて、そのキーの bnodeIdMap 値を、hmacIds 配列内の値の インデックス位置に "b" を前置したものに置き換えます。すなわち、 bnodeIdMap.set(bkey, 'b' + hmacIds.indexOf(bnodeIdMap.get(bkey)))。
    4. bnodeIdMap を返します。
  2. labelMapFactoryFunction を返します。
注記

上記アルゴリズムの手順1.2は、[DI-ECDSA] の セクション3.3.4 createHmacIdLabelMapFunction の手順1.2と同一であることに 注意してください。そのため、両方を実装する場合、開発者はコードを再利用するか 関数を呼び出せる可能性があります。

4.7.5 createHmacIdLabelMapFunction

次のアルゴリズムは、HMAC を使用して正規空白ノード識別子を、 その符号化された HMAC ダイジェストに置き換える ラベルマップ生成関数を作成します。必要な入力は、 （事前に秘密鍵で初期化された）HMAC HMAC です。関数 labelMapFactoryFunction が出力として生成されます。

  1. 1つの必須入力（正規ノード識別子マップ canonicalIdMap）を持ち、 空白ノード識別子マップ bnodeIdMap を出力として返す 関数 labelMapFactoryFunction を作成します。 関数の実装を次のように設定します。
    1. 新しい空の bnode 識別子マップ bnodeIdMap を生成します。
    2. canonicalIdMap 内の各マップエントリ entry について、
      1. entry の値から正規識別子に HMAC を適用し、 HMAC ダイジェスト digest を取得します。
      2. 新しい文字列値 b64urlDigest を生成し、"u" に続けて digest 値の base64url-no-pad 符号化版を追加した値で初期化します。
      3. entry のキーをキー、b64urlDigest を値として使用し、 新しいエントリ newEntry を bnodeIdMap に追加します。
    3. bnodeIdMap を返します。
  2. labelMapFactoryFunction を返します。
注記: その他の アルゴリズムも可能です

別のプリミティブを作成し、結果として得られる HMAC ダイジェストを代わりにソートし、 そのソート順に基づくプレフィックスと整数を使用して、 生成されるラベルマップ内でラベルを割り当てるラベルマップ生成 関数を返すこともできます。このプリミティブは、 非開示データの漏洩を最小限に抑えることよりリンク不能性を優先する BBS などの 選択的開示方式で有用な場合があります。

4.7.6 compressLabelMap

次のアルゴリズムはラベルマップを圧縮します。必要な入力は、 ラベルマップ (labelMap) と cryptosuite です。出力は 圧縮済みラベルマップです。

  1. map を空のマップで初期化します。
  2. labelMap 内の各エントリ (k、v) について、
    1. cryptosuite が ecdsa-sd-2023 に設定されている場合、 k 内の "c14n" プレフィックスに続く文字から解析された10進整数をキー、 v 内の "u" プレフィックスに続く文字を base64url-no-pad 復号した結果の バイト配列を値とするエントリを map に追加します。 それ以外の場合は、map に、k 内の "c14n" プレフィックスに続く文字から解析された10進 整数をキー、v 内の "b" プレフィックスに続く文字から解析された 10進整数を値とするエントリを追加します。
  3. map を圧縮済みラベルマップとして返します。

4.7.7 decompressLabelMap

次のアルゴリズムはラベルマップを展開します。必要な入力は、 圧縮済みラベルマップ (compressedLabelMap) と cryptosuite です。出力は 展開済みラベルマップです。

  1. map を空のマップで初期化します。
  2. compressedLabelMap 内の各エントリ (k、v) について、
    1. cryptosuite が ecdsa-sd-2023 に設定されている場合、 k にプレフィックス "c14n" を追加したものをキー、 v の base64url-no-pad 符号化値にプレフィックス "u" を追加したものを 値とするエントリを map に追加します。 それ以外の場合は、k にプレフィックス "c14n" を追加したものをキー、 v にプレフィックス "b" を追加したものを値とする エントリを map に追加します。
  3. map を展開済みラベルマップとして返します。

4.7.8 skolemizeNQuads

次のアルゴリズムは、N-Quad 文字列の配列内にあるすべての空白ノード識別子を カスタムスキーム URN に置き換えます。必要な入力は、N-Quad 文字列の配列 (inputNQuads) と URN スキーム (urnScheme) です。 N-Quad 文字列の配列 skolemizedNQuads が出力として生成されます。 この操作は、セクション4.7.9 deskolemizeNQuads のアルゴリズムを 使用することで可逆となることを意図しています。

  1. N-Quad 文字列の新しい配列 skolemizedNQuads を作成します。
  2. inputNQuads 内の各 N-Quad 文字列 s1 について、
    1. s1 のコピーであり、空白ノード識別子の各出現箇所を URN ("urn:")、入力カスタムスキーム (urnScheme)、 コロン (":")、および空白ノード識別子の値で置き換えた 新しい文字列 s2 を作成します。たとえば、次のような形式の 正規表現で目的の結果を得られます。 s1.replace(/(_:([^\s]+))/g, '<urn:custom-scheme:$2>')。
    2. s2 を skolemizedNQuads に追加します。
  3. skolemizedNQuads を返します。

4.7.9 deskolemizeNQuads

次のアルゴリズムは、N-Quad 文の配列内にあるすべてのカスタムスキーム URN を 空白ノード識別子に置き換えます。必要な入力は、N-Quad 文字列の配列 (inputNQuads) と URN スキーム (urnScheme) です。N-Quad 文字列の配列 deskolemizedNquads が出力として生成されます。この操作は、 セクション4.7.9 deskolemizeNQuads のアルゴリズムの使用を逆転させることを意図しています。

  1. N-Quad 文字列の新しい配列 deskolemizedNQuads を作成します。
  2. inputNQuads 内の各 N-Quad 文字列 s1 について、
    1. s1 のコピーであり、URN ("urn:")、入力 カスタムスキーム (urnScheme)、コロン (":")、 および空白ノード識別子の値の各出現箇所を、空白ノードプレフィックス ("_:") と 空白ノード識別子の値に置き換えた新しい文字列 s2 を作成します。 たとえば、次のような形式の正規表現で目的の結果を得られます。 s1.replace(/(<urn:custom-scheme:([^>]+)>)/g, '_:$2').。
    2. s2 を deskolemizedNQuads に追加します。
  3. deskolemizedNQuads を返します。

4.7.10 skolemizeExpandedJsonLd

次のアルゴリズムは、展開済み JSON-LD 文書内のすべての空白ノード識別子を カスタムスキーム URN に置き換えます。ラベルのない 空白ノードへのこのような URN の割り当ても含まれます。必要な入力は、展開済み JSON-LD 文書 (expanded)、カスタム URN スキーム (urnScheme)、UUID 文字列または同程度にランダムな別の文字列 (randomString)、および共有整数への参照 (count) です。 追加のカスタムオプション（文書ローダーなど）も渡すことができます。 スコーレム化された JSON-LD 文書の展開形式 (skolemizedExpandedDocument が出力として生成されます。この 操作で使用されるスコーレム化は、セクション 4.7.12 toDeskolemizedNQuads のアルゴリズムを 使用することで可逆となることを意図しています。

  1. skolemizedExpandedDocument を空の配列で初期化します。
  2. expanded 内の各 element について、
    1. element がオブジェクトでないか、キー @value を含む場合、element のコピーを skolemizedExpandedDocument に追加し、次の element に進みます。
    2. それ以外の場合、skolemizedNode をオブジェクトとして初期化し、 element 内の各 property と value について、
      1. value が配列の場合、 skolemizedNode 内の property の値を、 value を expanded として渡し、 その他のパラメータを同じままにして、このアルゴリズムを 再帰的に呼び出した結果に設定します。
      2. それ以外の場合、skolemizedNode 内の property の値を、 value だけを要素として持つ配列を expanded として渡し、 その他のパラメータを同じままにしてこのアルゴリズムを再帰的に呼び出した 配列結果の最初の要素に設定します。
    3. skolemizedNode に @id プロパティがない場合、 skolemizedNode 内の @id プロパティの値を、 "urn:"、urnScheme、"_"、randomString、"_"、 および count の値を連結したものに設定し、その後 count の値を増加させます。
    4. それ以外で、skolemizedNode 内の @id プロパティの値が "_:" で始まる場合、スコーレム化時に既存の空白ノード 識別子を保持するため、skolemizedNode 内の @id プロパティの値を "urn:"、urnScheme、および空白ノード識別子 （すなわち、@id プロパティの既存値から "_:" プレフィックスを除いたもの。 たとえば、@id プロパティの既存値が _:b0 の場合、 空白ノード識別子は b0）を連結したものに設定します。
    5. skolemizedNode を skolemizedExpandedDocument に追加します。
  3. skolemizedExpandedDocument を返します。

4.7.11 skolemizeCompactJsonLd

次のアルゴリズムは、圧縮済み JSON-LD 文書内のすべての空白ノード識別子を カスタムスキーム URN に置き換えます。必要な入力は、圧縮済み JSON-LD 文書 (document) と、デフォルト値が "custom-scheme:" の カスタム URN スキーム (urnScheme) です。document は、 文書の最上位で1つの @context プロパティのみを使用すると仮定されます。追加の カスタムオプション（文書ローダーなど）も渡すことができます。出力として、 スコーレム化された JSON-LD 文書の展開形式 (skolemizedExpandedDocument と、スコーレム化された JSON-LD 文書の圧縮形式 (skolemizedCompactDocument) の両方を生成します。 この操作で使用されるスコーレム化は、同じカスタム URN スキーム (urnScheme) を使用するセクション 4.7.12 toDeskolemizedNQuads のアルゴリズムを 使用することで可逆となることを意図しています。

  1. expanded を、document と任意のカスタム オプションを渡して JSON-LD 展開アルゴリズムを実行した結果で初期化します。
  2. skolemizedExpandedDocument を、 セクション4.7.10 skolemizeExpandedJsonLd のアルゴリズムの結果で初期化します。
  3. skolemizedCompactDocument を、skolemizedExpandedDocument と 任意のカスタムオプションを渡して JSON-LD 圧縮アルゴリズムを実行した結果で初期化します。
  4. skolemizedExpandedDocument と skolemizedCompactDocument の両方を持つオブジェクトを返します。

4.7.12 toDeskolemizedNQuads

次のアルゴリズムは、セクション4.7.11 skolemizeCompactJsonLd のアルゴリズムを使用して作成されたものなど、 スコーレム化された JSON-LD 文書を、デスコーレム化された N-Quads の配列へ変換します。 必要な入力は JSON-LD 文書 skolemizedDocument です。 追加のカスタムオプション（文書ローダーなど）も渡すことができます。 デスコーレム化された N-Quad 文字列の配列 (deskolemizedNQuads) が出力として生成されます。

  1. skolemizedDataset を、任意のカスタムオプション（文書ローダーなど）を渡して、 skolemizedDocument を JSON-LD から N-Quads 形式の RDF に変換する JSON-LD を RDF に逆直列化するアルゴリズムの結果で初期化します。
  2. skolemizedDataset を個々の N-Quads の配列 skolemizedNQuads に分割します。
  3. deskolemizedNQuads を、skolemizedNQuads と "custom-scheme:" をパラメータとして渡して、セクション 4.7.9 deskolemizeNQuads のアルゴリズムを実行した結果に設定します。 実装は、skolemizedDocument を生成する際に同じスキーム名が 使用されている限り、"custom-scheme:" とは異なる urnScheme を選択してもよいです。
  4. deskolemizedNQuads を返します。

4.7.13 jsonPointerToPaths

次のアルゴリズムは、JSON Pointer [RFC6901] を JSON ツリー内のパスの配列に変換します。必要な入力は JSON Pointer 文字列 (pointer) です。パスの配列 (paths) が出力として生成されます。

  1. paths を空の配列で初期化します。
  2. pointer を "/" 文字で分割し、最初の空の分割要素をスキップして、 splitPath を配列として初期化します。Javascript 表記では、この手順は次のコードと同等です。 pointer.split('/').slice(1)
  3. splitPath 内の各 path について、
    1. path に ~ が含まれない場合、整数として解析できるなら 整数に変換し、できない場合は文字列のままにして、 path を paths に追加します。
    2. それ以外の場合、path 内の JSON pointer エスケープシーケンスをすべて アンエスケープし、その結果を paths に追加します。
  4. paths を返します。

4.7.14 createInitialSelection

次のアルゴリズムは、JSON-LD オブジェクトに基づいて初期選択 （JSON-LD 文書の断片）を作成します。これは、セクション 4.7.16 selectJsonLd のアルゴリズム内で使用される ヘルパー関数です。必要な入力は JSON-LD オブジェクト (source) です。 JSON-LD 文書断片オブジェクト (selection) が出力として生成されます。

  1. selection を空のオブジェクトで初期化します。
  2. source に空白ノード識別子ではない id がある場合、 selection.id をその値に設定します。 注記: JSON Pointer のパス上にある空白ノードではないすべての識別子を 選択に含めなければなりません。これにはルート 文書識別子も含まれます。
  3. source.type が設定されている場合、 selection.type をその値に設定します。 注記: 選択には、任意の JSON Pointer のパス上にあるすべての type を 含めなければなりません。これにはルート文書の type も含まれます。
  4. selection を返します。

4.7.15 selectPaths

次のアルゴリズムは、解析済み JSON Pointer から解析されたパスを使用して、 圧縮済み JSON-LD 文書の一部を選択します。これは、セクション 4.7.16 selectJsonLd のアルゴリズム内で使用される ヘルパー関数です。必要な入力は、JSON Pointer から解析された パスの配列 (paths)、圧縮済み JSON-LD 文書 (document)、値を設定する選択文書 (selectionDocument)、および選択された配列を追跡するための配列の配列 (arrays) です。このアルゴリズムは 出力を生成しません。代わりに、paths を介して選択された 値を指定された selectionDocument に設定します。

  1. parentValue を document で初期化します。
  2. value を parentValue で初期化します。
  3. selectedParent を selectionDocument で初期化します。
  4. selectedValue を selectedParent で初期化します。
  5. paths 内の各 path について、
    1. selectedParent を selectedValue に設定します。
    2. parentValue を value に設定します。
    3. value を parentValue.path に設定します。 value が未定義になった場合、 エラーを発生させなければならず、 PROOF_GENERATION_ERROR のエラー型を伝えるべきです。 これは、JSON pointer が指定された document と一致しないことを示します。
    4. selectedValue を selectedParent.path に設定します。
    5. selectedValue が未定義になった場合、
      1. value が配列の場合、selectedValue を空の配列に設定し、 selectedValue を arrays に追加します。
      2. それ以外の場合、value を source として渡して、セクション 4.7.14 createInitialSelection の アルゴリズムに初期選択を渡し、その結果を selectedValue に設定します。
      3. selectedParent.path を selectedValue に設定します。
  6. 注記: ターゲット値までのパス走査が完了すると、選択された値が 計算されます。
  7. value がリテラルの場合、selectedValue を value に設定します。
  8. value が配列の場合、selectedValue を value のコピーに設定します。
  9. その他のすべての場合、selectedValue を、 selectedValue の浅いコピーと value のディープコピーをマージした オブジェクトに設定します。たとえば、{...selectedValue, …deepCopy(value)}。
  10. paths から最後の path、lastPath を取得します。
  11. selectedParent.lastPath を selectedValue に設定します。

4.7.16 selectJsonLd

次のアルゴリズムは、JSON Pointer の配列を使用して 圧縮済み JSON-LD 文書の一部を選択します。必要な入力は、JSON Pointer の配列 (pointers) と圧縮済み JSON-LD 文書 (document) です。 document は、@id と @type をそれぞれ id と type にエイリアスする JSON-LD コンテキストを使用し、 文書の最上位では1つの @context プロパティのみを使用すると仮定されます。 元の JSON-LD 文書の選択 (selectionDocument) を表す 新しい JSON-LD 文書が出力として生成されます。

  1. pointers が空の場合、null を返します。これは、元の文書から 何も選択されていないことを示します。
  2. arrays を空の配列で初期化します。この変数は、 すべての pointers が処理された後で、選択された疎配列を 密な配列にするために追跡する目的で使用されます。
  3. document を source として渡して、セクション 4.7.14 createInitialSelection のアルゴリズムに初期選択を渡し、 その結果で selectionDocument を初期化します。
  4. selectionDocument 内の @context プロパティの値を、 document 内の @context プロパティの値のコピーに設定します。
  5. pointers 内の各 pointer について、 ルートから pointer のターゲット値まで文書を走査しながら selectionDocument を構築します。
    1. セクション4.7.13 jsonPointerToPaths の アルゴリズムを使用して、pointer をパスの配列 paths に解析します。
    2. document、paths、selectionDocument、および arrays を渡して、セクション 4.7.15 selectPaths のアルゴリズムを使用します。
  6. arrays 内の各 array について、
    1. 定義済みの要素同士の間にある未定義要素を削除して、 array を密な配列にします。
  7. selectionDocument を返します。

4.7.17 relabelBlankNodes

次のアルゴリズムは、空白ノードラベルマップを使用して、 N-Quad 文字列の配列内の空白ノード識別子に再ラベル付けします。 必要な入力は N-Quad 文字列の配列 (nquads) と空白ノードラベルマップ (labelMap) です。再ラベル付けされた空白ノード 識別子を持つ N-Quad 文字列の配列 (relabeledNQuads) が出力として生成されます。

  1. N-Quad 文字列の新しい配列 relabeledNQuads を作成します。
  2. nquads 内の各 N-Quad 文字列 s1 について、
    1. s1 のコピーであり、その中の各空白ノード識別子を labelMap 内でその識別子をキーとして関連付けられた値に 置き換えた新しい文字列 s2 を作成します。
    2. s2 を relabeledNQuads に追加します。
  3. relabeledNQuads を返します。

4.7.18 selectCanonicalNQuads

次のアルゴリズムは、JSON Pointer の配列を使用して、スコーレム化された圧縮済み JSON-LD 文書の一部を選択し、指定されたラベルマップを使用して空白ノードラベルを 置き換えた結果の正規 N-Quads を出力します。必要な入力は JSON Pointer の配列 (pointers)、 スコーレム化された圧縮済み JSON-LD 文書 (skolemizedCompactDocument)、 および空白ノードラベルマップ (labelMap) です。追加のカスタムオプション （文書ローダーなど）も渡すことができます。document は、 @id と @type をそれぞれ id と type にエイリアスする JSON-LD コンテキストを使用し、 文書の最上位では1つの @context プロパティのみを使用すると 仮定されます。元の JSON-LD 文書の選択を表す新しい JSON-LD 文書 (selectionDocument)、デスコーレム化された N-Quad 文字列の配列 (deskolemizedNQuads)、および置換された空白ノードラベルを持つ 正規 N-Quads の配列 (nquads) を含むオブジェクトが出力として生成されます。

  1. pointers と、 document としての skolemizedCompactDocument を渡して、 セクション4.7.16 selectJsonLd のアルゴリズムを実行した結果で selectionDocument を初期化します。
  2. selectionDocument を skolemizedCompactDocument として、 および任意のカスタムオプションを渡して、セクション 4.7.12 toDeskolemizedNQuads のアルゴリズムを 実行した結果で deskolemizedNQuads を初期化します。
  3. labelMap と、 nquads としての deskolemizedNQuads を渡して、 セクション4.7.17 relabelBlankNodes のアルゴリズムを 実行した結果で nquads を初期化します。
  4. selectionDocument、 deskolemizedNQuads、および nquads を含むオブジェクトを返します。

4.7.19 canonicalizeAndGroup

次のアルゴリズムは、圧縮済み JSON-LD 文書のカスタム選択と一致する 正規 N-Quad 文字列を出力するために使用されます。これは、 圧縮済み JSON-LD 文書を正規化し（ラベルマップを使用して空白ノード識別子を置き換え）、 結果として得られる正規 N-Quad 文字列を、 各グループに関連付けられた選択に従ってグループ化することで実現します。 各グループは、割り当てられた名前と JSON pointer の配列を使用して定義されます。 JSON pointer は、スコーレム化された文書の一部を 選択するために使用され、その出力を正規 N-Quads に変換して グループの照合を実行できるようにします。

必要な入力は、圧縮済み JSON-LD 文書 (document)、 ラベルマップ生成関数 (labelMapFactoryFunction)、および 名前付きグループ定義のマップ (groupDefinitions) です。追加のカスタム オプション（文書ローダーなど）も渡すことができます。document は、 @id と @type をそれぞれ id と type にエイリアスする JSON-LD コンテキストを使用し、 文書の最上位では1つの @context プロパティのみを 使用すると仮定されます。作成されたグループ (groups)、スコーレム化された圧縮済み JSON-LD 文書 (skolemizedCompactDocument)、スコーレム化された展開済み JSON-LD 文書 (skolemizedExpandedDocument)、デスコーレム化された N-Quad 文字列 (deskolemizedNQuads)、空白ノードラベルマップ (labelMap)、および正規 N-Quad 文字列 nquads を含む オブジェクトが出力として生成されます。

  1. skolemizedExpandedDocument と skolemizedCompactDocument を、 document と任意のカスタムオプションを渡して、 セクション4.7.11 skolemizeCompactJsonLd のアルゴリズムを実行した結果の 対応する値で初期化します。
  2. skolemizedExpandedDocument と任意のカスタムオプションを渡して、 セクション4.7.12 toDeskolemizedNQuads のアルゴリズムを実行した結果で deskolemizedNQuads を初期化します。
  3. labelMapFactoryFunction、nquads としての deskolemizedNQuads、および任意のカスタムオプションを渡して、 セクション 4.7.1 labelReplacementCanonicalizeNQuads のアルゴリズムを 実行した結果の対応する値で、 nquads と labelMap を初期化します。
  4. selections を新しいマップで初期化します。
  5. groupDefinitions 内の各キー (name) と値 (pointers) の エントリについて、
    1. pointers、labelMap、 document としての skolemizedCompactDocument、 および任意のカスタムオプションを渡して、セクション 4.7.18 selectCanonicalNQuads のアルゴリズムを 実行した結果を値、name をキーとするエントリを追加します。
  6. groups を空のオブジェクトで初期化します。
  7. selections 内の各キー (name) と値 (selectionResult) のエントリについて、
    1. matching を空のマップで初期化します。
    2. nonMatching を空のマップで初期化します。
    3. selectedNQuads を、 selectionResult の nquads で初期化します。
    4. selectedDeskolemizedNQuads を、 selectionResult の deskolemizedNQuads で初期化します。
    5. nquads 内の各要素 (nq) とインデックス (index) について、
      1. index をキー、nq を値とする マップエントリ entry を作成します。
      2. selectedNQuads が nq を含む場合、 entry を matching に追加し、 それ以外の場合は entry を nonMatching に追加します。
    6. groups 内の name を、 matching、nonMatching、および deskolemizedNQuads としての selectedDeskolemizedNQuads を 含むオブジェクトに設定します。
  8. groups、 skolemizedExpandedDocument、skolemizedCompactDocument、 deskolemizedNQuads、labelMap、および nquads を含むオブジェクトを返します。

4.7.20 hashMandatoryNQuads

次のアルゴリズムは、提供されたハッシュ API を使用して、 開示必須の N-Quads の配列を暗号学的にハッシュ化します。必要な入力は、 開示必須の N-Quads の配列 (mandatory) とハッシュ関数 (hasher) です。暗号学的ハッシュ (mandatoryHash) が 出力として生成されます。

  1. bytes を、結合された mandatory N-Quads の UTF-8 表現で初期化します。
  2. mandatoryHash を、hasher を使用して bytes をハッシュ化した結果で初期化します。
  3. mandatoryHash を返します。

5. セキュリティに関する考慮事項

以下のセクションでは、この仕様を実装する開発者が安全な ソフトウェアを作成するために認識しておくべきセキュリティ上の考慮事項について説明します。

5.1 暗号スイートのバージョン管理

暗号技術は秘密を使用して情報を保護します。必要な 秘密を知っていれば、特定の情報へ計算上容易にアクセスできます。 同じ情報は、計算上困難な総当たりによる試行によって 秘密の推測に成功した場合にもアクセスできます。現代のすべての暗号技術では、 計算上困難なアプローチが時間の経過後も困難であり続ける必要がありますが、 科学や数学の進歩によって、常にそうであるとは限りません。つまり、 暗号技術には寿命があります。

この仕様では、現在使用されているどの暗号技術も時間の経過とともに 破られる可能性が非常に高いと想定することで、すべての暗号方式の陳腐化に 備えています。ソフトウェアシステムは、情報を継続して保護するために、 使用する暗号技術を時間の経過とともに変更できなければなりません。このような変更には、 必要な秘密のサイズを増やすことや、使用する暗号 プリミティブを変更することが含まれる場合があります。ただし、暗号パラメータの 組み合わせによっては、実際にはセキュリティを低下させる可能性があります。これらの前提を踏まえると、 システムは、安全な暗号パラメータの異なる組み合わせ、すなわち 暗号スイートを互いに区別できる必要があります。暗号スイートを識別または バージョン管理する場合、パラメータ、番号、日付など、 いくつかのアプローチを採用できます。

パラメトリックなバージョン管理では、暗号スイートで使用される 特定の暗号パラメータを指定します。たとえば、 RSASSA-PKCS1-v1_5-SHA1 のような識別子を使用できます。この方式の利点は、十分な訓練を受けた 暗号技術者であれば、識別子から使用されているすべてのパラメータを 判断できることです。この方式の欠点は、この種の識別子を使用する人々の 大半が十分な訓練を受けておらず、そのため、前述の識別子が もはや安全に使用できない暗号スイートであることを理解できないことです。 さらに、この知識不足によって、ソフトウェア 開発者が暗号スイート識別子の解析を一般化し、 暗号プリミティブのどのような組み合わせでも許容するようになり、 セキュリティが低下する可能性があります。理想的には、暗号スイートは 特定の許容可能な暗号パラメータのプロファイルとしてソフトウェアに実装されるべきです。

番号によるバージョン管理では、 1.0 や 2.1 のようなメジャーおよびマイナーバージョン番号を指定できます。 番号によるバージョン管理は特定の順序を示し、 高いバージョン番号ほど低いバージョン番号より高機能であることを示唆します。 このアプローチの利点は、専門性の低い 開発者には理解しにくい複雑なパラメータを取り除き、 アップグレードが適切かもしれないことを示す、より単純なモデルにできることです。 このアプローチの欠点は、ソフトウェアのバージョン番号が上がっても、 ソフトウェアが動作し続けるために必ずしもアップグレードする必要がないことが多いため、 アップグレードが必要なのか明確ではないことです。これにより、 特定のバージョンを使用していることが安全ではないにもかかわらず、 開発者が安全だと考えてしまう可能性があります。理想的には、 ソフトウェアで暗号スイートを使用する開発者に対し、 それらのスイートが引き続き安全であるか定期的なレビューが 必要であることを示す追加のシグナルが提供されるべきです。

日付に基づくバージョン管理では、特定の 暗号スイートについて具体的なリリース日を指定します。年などの日付を使用する利点は、 その日付が比較的古いか新しいかを開発者が すぐに判断できることです。古い日付を目にすると、 開発者がより新しい暗号スイートを探すきっかけになる可能性がありますが、 パラメトリックまたは番号ベースのバージョン管理方式では そうならない可能性があります。日付ベースのバージョンの欠点は、一部の暗号 スイートが5～10年間有効なままである可能性があり、開発者が より新しい暗号スイートを探しても、より新しいものが見つからない場合があることです。 これは不便ではありますが、より安全な エコシステムの振る舞いにつながる不便です。

5.2 アプリケーション 開発者の保護

現代の暗号アルゴリズムは、異なるユースケースのさまざまな要件を満たせるよう、 調整可能な多数のパラメータと オプションを提供しています。たとえば、組み込みシステムは処理能力とメモリが限られた環境にあり、 特定のアルゴリズムで最も強力なデジタル署名を生成するための リソースを持たない場合があります。金融取引システムのような他の環境では、 取引が行われている1日だけデータを保護すればよい場合がある一方、 他の環境では数十年にわたりデータを保護する必要がある場合があります。これらの ニーズを満たすため、暗号アルゴリズムの設計者は多くの場合、 暗号アルゴリズムを構成する複数の方法を提供します。

暗号ライブラリの実装者は、多くの場合、 暗号アルゴリズム設計者や仕様作成者が作成した仕様を受け取り、 そのライブラリを使用するアプリケーション開発者がすべてのオプションを利用できるように 実装します。これは、特定のアプリケーション開発者が 特定の暗号技術の導入でどの機能の組み合わせを必要とするか分からないためです。 その結果、すべてのオプションがアプリケーション開発者に公開されることがよくあります。

暗号ライブラリを使用するアプリケーション開発者は、多くの場合、 特定のアプリケーションに適切な暗号パラメータとオプションを 選択するために必要な暗号技術の専門知識と知識を持っていません。この 専門知識の不足により、特定のアプリケーションに対して不適切な暗号パラメータ やオプションを選択する可能性があります。

この仕様では、関係者の優先順位を、暗号ライブラリ実装者より アプリケーション開発者を、暗号仕様作成者より暗号ライブラリ実装者を、 暗号アルゴリズム設計者より暗号仕様作成者を保護するように設定しています。 これらの優先順位を踏まえ、次の推奨事項を示します。

  • 暗号アルゴリズム設計者には、暗号ライブラリ実装者が ソフトウェアライブラリについてより容易に監査可能なセキュリティ攻撃 対象領域を持てるよう、オプションとパラメータの 数を可能な限り少なくすることが推奨されます [RFC7696]。
  • 暗号仕様の作成者には、可能であれば、 暗号アジリティを確保しつつ、下流のソフトウェアライブラリの監査可能な セキュリティ攻撃対象領域を最小限に保つため、 オプションとパラメータの数をさらに可能な限り少なくすることが推奨されます。
  • 暗号ライブラリの実装者には、可能であれば、既知の 適切なオプションとパラメータの組み合わせをアプリケーション開発者へ提供することが推奨されます。 楕円曲線デジタル署名など、どのアルゴリズム クラスについても、これらのプリセットを使用する場合に パラメータやオプションを細かく調整できない、2つの事前設定されたデフォルト構成が 理想的です。専門家がライブラリの使用を細かく調整するためのライブラリオプションを提供できますが、 一般のアプリケーション開発者がこれらのオプションを使用することは推奨されません。
  • 暗号ライブラリの実装者は、非推奨または実験的な 暗号機能を提供できますが、ライブラリオプションなどを通じて 開発者が明示的に要求した場合にのみ提供し、 非推奨または実験的な暗号技術がアプリケーションで 有効になったことをライブラリが警告するようにすることが推奨されます。
  • アプリケーション開発者には、複数の事前設定された 暗号ライブラリ構成から選択し、暗号 オプションやパラメータを変更したり、実験的または非推奨の暗号技術を使用したりしないことが推奨されます。

上記の指針は、有用な暗号オプションと パラメータをアーキテクチャの下位層で提供しつつ、 各オプションの利点と欠点のバランスを十分に理解していない可能性がある アプリケーション開発者には、それらのオプションとパラメータを 公開しないようにすることを目的としています。

5.3 暗号スイートの 命名規則

セクション5.1 暗号スイートのバージョン管理では、特定の 暗号スイートがどの程度新しいかについて、比較的理解しやすい情報を 提供することの重要性を強調しました。一方、セクション 5.2 アプリケーション開発者の保護では、指定する オプション数を最小限にすることをさらに強調しました。実際、セクション3. 暗号スイートには、 アルゴリズム、変換、ハッシュ化、および直列化の詳細な指定を含む 暗号スイートの要件が一覧されています。したがって、暗号スイートの名前に これらすべての詳細を含める必要はありません。これは、セクション 5.1 暗号スイートのバージョン管理で述べた パラメトリックなバージョン管理が必要でも望ましくもないことを意味します。

暗号スイートの推奨される命名規則は、 署名アルゴリズム識別子から構成される文字列で、暗号スイートが互換性のない 実装オプションをサポートする場合は、ハイフンで区切って オプション識別子を続け、さらにハイフンと、そのスイートが提案された おおよその年を示す指定を続けるものです。

たとえば、[DI-EDDSA] は EdDSA デジタル署名に基づき、正規化アプローチに基づく 互換性のない2つのオプションをサポートし、おおよそ2022年に 提案されたため、2つの異なる暗号スイート名を持ちます。 eddsa-rdfc-2022 と eddsa-jcs-2022 です。

[DI-ECDSA] は ECDSA デジタル署名に基づき、[DI-EDDSA] と同じ 互換性のない2つの正規化アプローチをサポートし、さらに 楕円曲線とハッシュの2つの代替セットによって 2つの異なるセキュリティレベル（128ビットと192ビット）をサポートしますが、 暗号スイート名は2つだけです。 ecdsa-rdfc-2019 と ecdsa-jcs-2019 です。セキュリティレベルと対応する 曲線およびハッシュは、検証で使用される公開鍵の multi-key 形式から 決定されます。

5.4 アジリティと階層化

暗号アジリティとは、 頻繁に接続される情報セキュリティシステムを、 複数の暗号プリミティブおよび／またはアルゴリズムを切り替えられるように設計する 慣行です。暗号アジリティの主な 目的は、システムのインフラストラクチャに破壊的な変更を加えることなく、 システムが新しい暗号プリミティブやアルゴリズムへ迅速に適応できるようにすることです。 したがって、SHA-1 アルゴリズムなどの特定の暗号プリミティブが もはや安全に使用できないと判断された場合、単純な設定ファイルの変更によって より新しいプリミティブを使用するようシステムを再構成できます。

暗号アジリティは、情報セキュリティシステム内のクライアントとサーバーが 定期的に接触している場合に最も効果的です。ただし、 特定の暗号アルゴリズムによって保護されるメッセージが、検証可能な クレデンシャルのように長期間存続する場合、および／または クライアント（保有者）がサーバー（発行者）へ容易に 再接続できない可能性がある場合、暗号アジリティは 望ましい保護を提供できません。

暗号階層化とは、 まれにしか接続されない情報セキュリティシステムを、 複数のプリミティブおよび／またはアルゴリズムを同時に使用するように設計する 慣行です。暗号階層化の 主な目的は、1つ以上の暗号アルゴリズムまたはプリミティブが 破綻しても、ペイロードに対する暗号学的保護を失うことなく システムが存続できるようにすることです。たとえば、1つの 情報に対して RSA、ECDSA、Falcon アルゴリズムを並列に使用してデジタル署名すれば、 これら3つのデジタル署名アルゴリズムのうち2つが破綻しても 存続できるメカニズムを提供できます。768ビット鍵を使用する RSA デジタル署名など、 特定の暗号学的保護が侵害された場合でも、 システムは侵害されていない暗号学的保護を引き続き利用して 情報を保護できます。1年以上保護する必要がある可能性のある すべての署名済みコンテンツについて、開発者はこの機能を活用することが強く推奨されます。

この仕様は、両方の形態のアジリティを提供します。 あるアルゴリズムから別のアルゴリズムへ容易に切り替えられる 暗号アジリティを提供します。また、 通常は並列に複数の暗号アルゴリズムを同時に使用できる 暗号階層化も提供します。これにより、情報を保護するために使用される いずれのアルゴリズムも、他のアルゴリズムに依存したり必要としたりすることなく使用でき、 それでもデジタル証明形式を 開発者にとって使いやすいものに保てます。

5.5 より安全な抽象化

証明には proofValue が含まれ、 その中に暗号学的証明に関連する多数の パラメータを埋め込むことができます。たとえば、 Data Integrity ECDSA 暗号スイート v1.0 仕様の選択的開示アルゴリズムでは、 選択的に開示可能な各 項目につき1つずつ、複数の暗号署名を proofValue に含めます。これは、 アプリケーション開発者にとって技術をより簡単かつ安全に使用できるようにするためです。

この仕様は、アプリケーション層ではほとんど必要とされない 情報を単一の値で抽象化するよう仕様作成者に強く推奨します。 画像を表現する data: URL が多くの画像レンダリングパラメータを単一の値にカプセル化するのと同様に、 proofValue プロパティ（およびその他の類似プロパティ）は、 アプリケーション開発者にとって有用でない情報を抽象化し、 アプリケーションにとって重要なフィールドを識別しやすくします。 このように情報を抽象化すると、開発者が扱いやすいデータ構造になり、 たとえば、重要なプロパティを追加または削除するプログラミングエラーによる 偶発的な破損の影響を受けにくくなり、 暗号層への悪影響を軽減できます。

この仕様におけるデータ完全性の設計は、一般に 暗号層でのみ有用な情報を単一のプロパティへ抽象化し、 アプリケーション開発者の負担を軽減するとともに、システムのセキュリティを向上させます。

5.6 変換

暗号学的保護処理中に、保護対象のデータを変換することが 有益な場合があります。このような「インライン」変換により、 特定の種類の暗号学的保護を、それが格納されるデータ形式に依存しないものにできます。 たとえば、一部の Data Integrity 暗号スイートでは、 初期表現を正規形式 [N-QUADS] に変換する RDF データセット正規化 [RDF-CANON] を使用し、その後、それを直列化、 ハッシュ化し、デジタル署名します。保護された データを表現するどの構文でもこの正規形式へ変換できる限り、 デジタル署名を検証できます。これにより、情報に対する同じデジタル署名を、 各構文について暗号学的証明を作成し直すことなく、 JSON、CBOR、YAML、およびその他の互換性のある構文で表現できます。

同じデジタル署名をさまざまな構文で表現できることは、 システムが多くの場合、それぞれ固有のネイティブデータ形式で 動作するため有益です。たとえば、一部のシステムは JSON データを使用して記述され、 他のシステムは CBOR データを使用して記述されています。変換がない場合、 内部で CBOR としてデータを処理するシステムは、 デジタル署名されたデータ 構造を JSON として保存する必要があります（またはその逆）。これはデータの二重保存につながり、 データベースに保存された未署名の表現が署名済みの表現から誤ってずれた場合、 セキュリティ攻撃対象領域が増加する可能性があります。変換を使用することで、 デジタル証明をネイティブデータ形式に保持でき、 時間の経過による検出困難なデータベースのずれを防ぐのに役立ちます。

この仕様は、「インライン」データ変換を利用することで、 署名済み情報の複製を必要としないように設計されています。 アプリケーション開発者には、アプリケーションのネイティブデータ形式で 暗号学的に保護されたデータを扱い、 暗号学的証明を保護対象データから分離して保存しないことが強く推奨されます。 また、アプリケーションストレージへの書き込み時および 読み出し時に、暗号学的に保護されたデータが改ざんされていないことを 定期的に確認することも強く推奨されます。

RDF データセット正規化 [RDF-CANON] などの一部の変換には、 攻撃者が過剰な処理サイクルを消費させるために使用できる入力データセットに対する 軽減策があります。この種の攻撃は データセット汚染と呼ばれ、 現代のすべての RDF データセット正規化器は、このような不正な 入力を検出して処理を停止することが要求されています。RDF データセット正規化の テストスイートには、このような汚染されたデータセットが含まれており、 すべての適合実装にこのような軽減策が存在することを確認します。一般的に、 変換を使用する暗号スイート 仕様はこの種の攻撃を軽減することが要求され、実装者には、 使用するソフトウェアライブラリがこれらの軽減策を 強制していることを確認するよう強く推奨されます。これらの攻撃は、 接続を意図的に遅くしてサーバー上の接続を枯渇させる HTTP クライアントなど、 あらゆるリソース枯渇攻撃と同じ一般的な カテゴリに属します。 実装者には、防御的なセキュリティ戦略を実装する際に この種の攻撃を考慮することが推奨されます。

5.7 保護される情報

任意のデータ完全性証明によって保護される データは、変換済みデータです。変換済みデータは、 特定の暗号スイートによって指定される変換アルゴリズムによって 生成されます。この保護メカニズムは、入力データに対していかなる種類の 変換も行わない、 より従来型のデジタル署名メカニズムの一部とは異なります。変換の利点については、セクション 5.6 変換で詳しく説明します。

たとえば、 ecdsa-jcs-2019 や eddsa-jcs-2022 などの 暗号スイートは、 JSON 正規化スキーム (JCS) を使用してデータを正規化された JSON へ変換し、 その後、暗号学的にハッシュ化してデジタル署名します。この アプローチの利点の1つは、空白、タブ、改行など、 署名対象情報の意味に影響を与えない書式文字を追加または削除しても、 デジタル署名が無効にならないことです。より従来型のデジタル署名 メカニズムには、この機能はありません。

ecdsa-rdfc-2019 や eddsa-rdfc-2022 などの その他の暗号スイートは、 RDF データセット 正規化を使用して、データを正規化された N-Quads [N-QUADS] へ変換し、その後、暗号学的にハッシュ化して デジタル署名します。このアプローチの利点の1つは、 署名を無効にすることなく、暗号署名を JSON、YAML、CBOR など さまざまな異なる構文へ移植できることです。より従来型の暗号署名 メカニズムには、この機能はありません。

実装者および開発者には、データ完全性証明を含む情報について、 その証明が検証され、 返されるすべてのデータが正常に保護されていることを確認したソフトウェアライブラリから 検証済みデータが戻り値として提供されない限り、 信頼しないことが強く推奨されます。

5.8 データの不透明性

アプリケーションデータを検査できるかどうかは、システム効率と 開発者の生産性に影響します。base 符号化されたバイナリデータなど、 暗号学的に保護されたアプリケーションデータをデータベースなどの アプリケーションサブシステムが容易に処理できない場合、 暗号学的に保護された情報を扱う労力が増えます。たとえば、 データベースにネイティブに保存およびインデックス付けできる暗号学的に保護されたペイロードは、 次のような、より単純なシステムにつながります。

  • 保護された情報を変更することなく、既存の業界標準データベース機能を 利用する利点を得られる、
  • 一方のデータコピーがメッセージとデジタル署名を保持し、 もう一方のコピーがメッセージだけを保存およびインデックス付けして システムの動作を駆動するという、データを複製する複雑さを回避できる、
  • 複数の入れ子になった base 符号化ペイロードを持つ、入れ子の デジタル署名済みデータを直列化および逆直列化するなど、 保護された情報を構造的に変更する必要がある独自ソリューションの複雑さを回避できる。

同様に、複数の上流ネットワークシステムで処理可能な 暗号学的に保護されたペイロードは、セキュリティアーキテクチャを適切に 階層化する能力を高めます。たとえば、上流システムが受信ペイロードを 繰り返し復号する必要がない場合、上流サブシステムを攻撃へ能動的に 対抗するよう特化させることで、システムが処理負荷を 分散する能力が高まります。実質的な操作を行う前には必ずデジタル署名を 確認する必要がありますが、透明なペイロードに対して、 識別子に基づくレート制限、署名の有効期限 確認、nonce/challenge の確認など、その他の上流チェックを実行して、 明らかに不正なリクエストを拒否できます。

さらに、開発者がシステム内のデータを容易に確認できない場合、 システムの正しさを容易に監査またはデバッグする能力が損なわれます。たとえば、 アプリケーション開発者に base 符号化されたアプリケーションデータを コピー＆ペーストさせる必要があると、開発が難しくなり、 すべてのメッセージを手動操作の base 復号ツールへ通す必要があるため、明らかなバグを見落とす可能性が高まります。

ただし、データを不透明にすることが正しい設計判断となる場合もあります。 他のアプリケーションサブシステムで処理する必要のないデータや、 アプリケーション開発者が変更またはアクセスする必要のないデータは、 不透明な形式へ直列化できます。例としては、デジタル 署名値、暗号鍵パラメータ、および暗号ライブラリのみが アクセスすればよく、アプリケーション開発者が変更する必要のないその他のデータフィールドがあります。 また、保存時暗号化を実行するデータベースのように、 基盤となるサブシステムが不透明なデータの 内部的な複雑さをアプリケーション開発者へ公開しない場合、 データの不透明性が適切な例もあります。このような場合、 アプリケーション開発者は透明なアプリケーションデータ形式を使用して 開発を続ける一方、データベースがアプリケーションデータを長期ストレージへ 暗号化して保存し、そこから復号する複雑さを管理します。

この仕様は、アプリケーションデータをネイティブ形式のまま 不透明にせず、デジタル署名などのその他の暗号 データは不透明なバイナリ符号化形式のまま保持するアーキテクチャを提供することを目指しています。 暗号スイートの実装者には、スイートを設計する際にデータの 不透明性を適切に使用することを検討し、アプリケーションデータを不透明にする場合と アプリケーション層で暗号データへアクセスできるようにする場合の 設計上のトレードオフを比較検討することが強く推奨されます。

5.9 検証方法のバインディング

実装者は、検証方法の定義から 制御された識別子 文書へたどり、その制御された識別子 文書にも 検証方法への参照が 含まれていることを確認することで、検証方法が特定の コントローラへバインドされていることを確認します。この処理は、 検証方法を取得するアルゴリズムで説明されています。

5.10 検証 関係の妥当性確認

実装が証明を検証する場合、証明の生成に使用された 検証方法が 制御された識別子 文書に記載されていることだけでなく、 検証対象の証明を生成するために使用されることを意図したものであったことも 検証することが不可欠です。この処理は 「検証関係の妥当性確認」と呼ばれます。

検証関係を妥当性確認する処理は、 制御された識別子 v1.0 仕様のセクション 3.3 検証方法の取得で概説されています。

この処理は、秘密 暗号鍵などの暗号素材が、アプリケーションによって意図しない目的に誤用されないようにするために使用されます。 暗号素材の誤用の例として、検証可能なクレデンシャルを 発行するために使用することを意図した秘密暗号 鍵が、代わりに Web サイトへのログイン（すなわち認証）に使用される場合があります。 検証関係を確認しないことは危険です。なぜなら、一部の 暗号素材の制限および保護プロファイルは、その意図された用途によって 決定される可能性があるためです。たとえば、一部のアプリケーションは 暗号素材を1つの目的だけに使用すると信頼されている場合があり、 また一部の暗号素材は、ラップトップ上の暗号化されていないファイルとしてではなく、 データセンター内のハードウェアセキュリティモジュールへ保存するなど、 より強く保護されている場合があります。

5.11 証明目的の妥当性確認

実装が証明を検証する場合、 証明目的が意図された用途と 一致することを検証することが不可欠です。

この処理は、証明がアプリケーションによって 意図しない目的に誤用されないようにするために使用されます。このような誤用は証明作成者にとって危険です。 誤用の例として、検証可能なクレデンシャル内の 表明を保護する目的であると記述された証明が、 代わりに Web サイトへログインするための認証に使用される場合があります。この場合、 証明作成者は、無制限の数の他者へ配布されることを想定した 任意の数の検証可能なクレデンシャルへ 証明を付与していました。Web サイトがそのような証明を、本来の目的ではなく 認証として誤って受け入れた場合、 これらの当事者の誰でも証明作成者として Web サイトへログインできてしまいます。

5.12 正規化方法の セキュリティ

正規化などの変換をどのように実行するかは、 システムのセキュリティ特性に影響を与える可能性があります。最適な 正規化メカニズムの選択はユースケースによって異なります。多くの場合、 望ましいセキュリティ要件を満たす最も単純なメカニズムが 最良の選択です。このセクションでは、この仕様で参照される 2つの主要な正規化メカニズム、すなわち JSON 正規化スキーム [RFC8785] と RDF データセット正規化 [RDF-CANON] のどちらを選択するかについて、 実装者を支援する簡単な指針を提供することを試みます。

アプリケーションが JSON のみを使用し、どのような RDF 意味論にも依存しない場合、JSON 正規化スキーム [RFC8785] を使用する暗号 スイートを採用することは魅力的なアプローチです。

アプリケーションが JSON-LD を使用し、文書の意味論を 保護する必要がある場合、RDF データセット正規化 [RDF-CANON] を使用する暗号スイートを 採用することは魅力的なアプローチです。

実装者には、変換を一切行わず、 証明をデータへ埋め込む代わりに暗号エンベロープでデータを包むことで 保護するその他のメカニズムも利用可能であることが推奨されます。たとえば、 JWT [RFC7519] や CWT [RFC8392] があります。 これらのアプローチには、一部のユースケースで単純性という 利点がありますが、この仕様で詳述するアプローチが提供する 一部の利点を失うという代償があります。

5.13 正規化方法の 正しさ

この仕様で使用されるアルゴリズム処理の1つは正規化であり、 これは変換の一種です。正規化とは、 意味論的に等価なさまざまな方法で表現される可能性のある情報を 入力として受け取り、すべての出力を「正規形式」と呼ばれる 単一の方法で表現する処理です。

正規化を利用する結果のデータ完全性証明の セキュリティは、アルゴリズムの正しさに大きく依存します。たとえば、 正規化アルゴリズムが異なる意味を持つ2つの入力を 同じ出力へ変換すると、作成者の意図が検証者に対して 誤って表現される可能性があります。これは攻撃者によって 攻撃経路として使用される可能性があります。

さらに、入力内の意味論的に重要な情報が出力に存在しない場合、 攻撃者は証明検証を失敗させることなく、そのような情報を メッセージへ挿入できる可能性があります。これは、メッセージへ暗号学的に署名する際によく使用される 別の変換である暗号学的ハッシュ化と似ています。 攻撃者が異なる入力から同じ暗号学的 ハッシュを生成できる場合、その暗号学的ハッシュアルゴリズムは 安全とは見なされません。

実装者には、入力をハッシュ化 処理へ渡すための変換に使用する すべての正規化アルゴリズムが適切に精査されていることを確認するよう強く推奨されます。 適切な精査には、少なくとも、アルゴリズムの正しさについて査読済みの 数学的証明との関連付けが含まれます。また、複数の実装と、 標準化団体の場で専門家による精査が行われることが望ましいです。 実装者には、情報の正規化について正式な 訓練を受けているか、またはアルゴリズムの正しさについて査読済みの数学的証明を 作成できる当該分野の専門家へアクセスできない限り、 新しいメカニズムを考案または使用しないことが強く推奨されます。

5.14 ネットワークリクエスト

この仕様は、適合する保護された文書上の証明を検証する際に、 ネットワークリクエストが一切必要とならないよう設計されています。 ただし、JSON-LD コンテキストと検証 方法には、ネットワーク接続経由で取得される可能性のある URL が 含まれる場合があることに読者は注意してください。この懸念は、 検証中または検証後にネットワークから読み込まれる可能性のあるすべての URL に当てはまります。

可能な限り、実装者には、このような情報を永続的または積極的に キャッシュし、そのような URL をネットワーク経由で取得する必要がある 実装の攻撃対象領域を減らすことが強く推奨されます。たとえば、 JSON-LD コンテキストのキャッシュ技法についてはセクション 2.4 コンテキストと語彙で説明されており、 did:key [DID-KEY] など一部の検証 方法は、 ネットワークからまったく取得する必要がありません。

特定の HTTP URL ベースの検証方法のインスタンスに初めて 遭遇した場合など、キャッシュされた情報を使用できない場合、 ネットワークからリソースを取得する可能性のある処理中に サービス拒否攻撃を軽減するため、防御的な措置を講じるよう実装者に注意が促されます。

5.15 その他のセキュリティに関する考慮事項

この仕様で説明される文書を保護する技術は 本質的に汎用化されているため、その使用によるセキュリティへの影響は 読者にはすぐに明らかでない可能性があります。完全なソフトウェアシステムで 考慮する必要がある可能性のあるセキュリティ上の 懸念を理解するため、実装者には、この技術が 検証可能なクレデンシャル エコシステム [VC-DATA-MODEL-2.0] でどのように使用されるかを 読むことが強く推奨されます。詳細については、 検証可能なクレデンシャルのセキュリティに関する考慮事項のセクションを参照してください。

6. プライバシーに関する考慮事項

以下のセクションでは、この仕様を実装する開発者が プライバシーを向上させるソフトウェアを作成するために認識しておくべき プライバシーに関する考慮事項について説明します。

6.1 リンク不能性

デジタル署名されたペイロードに、複数の 検証者から見えるデータが含まれている場合、それは相関の起点となります。このようなデータの 例として、ショッピングのロイヤルティカード番号があります。相関可能なデータは、 検証者による追跡目的に使用される可能性があり、プライバシーに対する期待に反する場合があります。 一部のデータが追跡に使用できるという事実は、すぐには明らかでない場合があります。 このような相関可能なデータの例には、静的な デジタル署名や画像の暗号学的ハッシュなどがありますが、これらに限定されません。

相関可能な追跡データを一切持たず、かつ特定のやり取りにおいて ペイロードが信頼できることについて一定水準の保証を提供する デジタル署名付きペイロードを作成することが可能です。この特性は リンク不能性と呼ばれます。これは、デジタル署名されたペイロードで 相関可能なデータを使用しないことを確保しつつ、一定水準の 信頼を提供するものであり、その十分性は各検証者が判断する必要があります。

すべてのユースケースがリンク不能性を必要とする、あるいは 許容するわけではないことを理解することが重要です。危険物を輸送および保管する 組織と個人を関連付ける場合など、規制上または安全上の理由から リンク可能性と相関が必要となるユースケースがあります。リンク不能性は、 特定のやり取りでプライバシーが期待される場合に有用です。

一定水準のリンク不能性を提供できるメカニズムは少なくとも2つあります。 第1の方法は、メッセージで使用されるデータ値が、将来のメッセージで 決して繰り返されないようにすることです。第2の方法は、繰り返されるデータ 値が十分な群衆プライバシーを提供し、そのやり取りで一定水準のプライバシーを期待する エンティティを相関することが事実上不可能になるようにすることです。

リンク不能性を実現するためには、さまざまな方法を使用できます。これらの方法には、 メッセージを、相関目的に使用できる情報を一切含まない 使い捨てのベアラートークンにすること、十分な水準の群衆プライバシーを確保する 属性を使用すること、および、提示されるメッセージへの信頼を損なうことなく メッセージを提示するエンティティが新しい署名を再生成できる 暗号スイートを使用することが含まれます。

6.2 選択的開示

選択的開示とは、以前に署名されたメッセージ （すなわち、その作成者によって署名されたメッセージ）の受信者が、 それらの部分の検証可能性を損なうことなく、メッセージの一部だけを開示できるようにする 技法です。たとえば、レンタカーを借りる目的でデジタル運転免許証を 選択的に開示することが考えられます。この場合、免許証から 発行機関、免許証番号、生年月日、および認可された自動車区分だけを 開示することができます。この場合、免許証番号は相関可能な 情報ですが、運転者の氏名全体と住所が共有されないため、 一定程度のプライバシーは維持されることに注意してください。

すべてのソフトウェアや暗号スイートが選択的開示を提供できるわけではありません。 メッセージの作成者が、その受信者によって選択的に開示できるようにしたい場合、 その特定のメッセージで選択的開示を有効にし、 両者が対応する暗号スイートを使用する必要があります。作成者は、 メッセージの特定の部分を必須開示にすることもできます。メッセージの内容の一部を 選択的に開示したい受信者は、この技法を実行できる ソフトウェアを使用する必要があります。選択的開示をサポートする暗号スイートの例として bbs-2023 があります。

リンク不能性を維持しない形で情報を選択的に開示することも可能です。 たとえば、規制要件により相関可能でなければならない 荷物識別子やロット番号を含む、出荷に関連する検査 結果を開示したい場合があります。 ただし、検査結果全体の開示は必要ではなく、 合格／不合格の状態だけを選択的に開示すれば十分と判断される場合があります。 プライバシーを維持しながら情報を開示する方法の詳細については、セクション 6.1 リンク不能性を参照してください。

6.3 以前の証明

2.1.2 証明 チェーンで定義される previousProof 機能を使用する場合、 実装は、1つ以上の以前の証明を保護されたペイロードに含めるため、 それらを対象としてデジタル署名する必要があります。これにより必然的に、 以前の証明を追加した各エンティティに関連する情報が公開されます。

少なくとも、以前の証明の検証方法、たとえば 公開鍵は、証明チェーン内で次の証明を作成する者から見えます。これは、 以前の証明の作成者が証明チェーンに含まれることを意図していなかった場合には プライバシー上の懸念となる可能性がありますが、あらゆる種類の文書へ 否認防止可能なデジタル署名を追加する場合には避けられない結果です。

グループ署名など、 より高度な暗号メカニズムを使用して メッセージの署名者の身元を隠すことが可能であり、 Data Integrity 暗号スイートによって このプライバシー上の懸念を軽減することも可能です。

6.4 ネットワーク リクエストによるフィンガープリンティング

証明の検証中または検証後にネットワークから読み込まれる可能性のある すべての URL には、フィンガープリンティングに関する懸念があります。この 仕様は、適合する保護された文書上の証明を検証する際に ネットワークリクエストを必要としないよう設計されています。 ただし、JSON-LD コンテキストおよび 検証 方法には、ネットワーク接続経由で取得される可能性のあるリソース URL が 含まれる場合があり、フィンガープリンティングに関する懸念につながることに注意してください。

たとえば、適合する保護された文書の作成者は、 JSON-LD コンテキストおよび 検証 方法について、文書ごとに一意の URL を作成する可能性があります。このような文書を検証する際、 検証者がその情報をネットワークから取得すると、 適合する保護された文書への関心を 文書の作成者へ明らかにすることになり、文書作成者ではないエンティティにとって プライバシーに対する期待との不一致につながる可能性があります。

実装者には、URL のキャッシュおよびネットワークから URL を取得する際の 防御的な実装について、セクション5.14 ネットワーク リクエストの指針に従うことが強く推奨されます。 リクエストを行うクライアントを明らかにせずにネットワークからリソースを取得する Oblivious HTTP などの技法を使用することが推奨されます。さらに、 適合する保護された文書の作成者が、 プライバシーに対する期待に反する可能性のある方法でフィンガープリンティング URL を使用しているかどうかを 判断するために、ヒューリスティックを使用することもできます。 このようなヒューリスティックを使用して、フィンガープリンティング URL の疑いがあるものを含む 文書を処理する可能性のあるエンティティに警告を表示できます。

6.5 正規化方法の プライバシー

変換、すなわち正規化をどのように実行するかは、 システムのプライバシー特性に影響を与える可能性があります。最適な 正規化メカニズムの選択はユースケースによって異なります。 このセクションでは、プライバシーの観点から、この仕様で参照される 2つの主要な正規化メカニズム、すなわち JSON 正規化スキーム [RFC8785] と RDF データセット正規化 [RDF-CANON] のどちらを選ぶかについて、 実装者を支援する簡単な指針を提供することを試みます。

アプリケーションが、保護された文書内の情報について選択的開示を 実行する必要がなく、JSON-LD も利用しない場合、JSON 正規化スキーム [RFC8785] は魅力的なアプローチです。

アプリケーションが JSON-LD を使用し、保護された文書内の情報について 選択的開示を必要とする可能性がある場合、RDF データセット正規化 [RDF-CANON] を使用する暗号スイートを 採用することは魅力的なアプローチです。

実装者には、変換を一切行わず、 証明をデータに埋め込む代わりに暗号エンベロープでデータを包むことで保護する、 その他の選択的開示メカニズムも利用可能であることが推奨されます。たとえば、 SD-JWT [SD-JWT] があります。このアプローチには、 一部のユースケースで単純性という利点がありますが、 この仕様で詳述するアプローチによって提供される一部の利点を 失うという代償があります。

6.6 その他のプライバシーに関する考慮事項

この仕様で説明される文書を保護する技術は 本質的に汎用化されているため、その使用によるプライバシーへの影響は 読者にはすぐに明らかでない可能性があります。完全なソフトウェアシステムで 考慮する必要がある可能性のあるプライバシー上の 懸念を理解するため、実装者には、この技術が 検証可能なクレデンシャル エコシステム [VC-DATA-MODEL-2.0] でどのように使用されるかを 読むことが強く推奨されます。詳細については、 検証可能なクレデンシャルのプライバシーに関する考慮事項のセクションを参照してください。

7. アクセシビリティに関する考慮事項

以下のセクションでは、この仕様を実装する開発者が、 認知、運動、視覚に関して異なるニーズを持つ人々にも ソフトウェアを利用できるようにするため、考慮することが強く推奨される アクセシビリティに関する考慮事項について説明します。一般的に、この仕様はシステムソフトウェアによって使用され、 アクセシビリティに関する考慮事項の対象となる情報を個人へ 直接公開することはありません。ただし、この仕様によって表現される情報に 個人が間接的に触れる可能性がある場合があるため、 そのような状況に向けて以下の指針を提供します。

7.1 時刻値の提示

この仕様では、暗号学的証明の有効期間に関連する 日付と時刻を表現できます。証明が処理され、 許容される時間範囲外であると検出された場合、この情報が個人に間接的に 公開される可能性があります。これらの日付と時刻を個人へ公開する場合、 実装者には、表示ソフトウェアで 日付と時刻を表現する際の文化的規範とロケール を考慮することが強く推奨されます。これらの 考慮事項に加えて、情報を受け取る個人の認知的負担を 軽減する方法で時刻値を提示することが、推奨されるベストプラクティスです。

たとえば、特定のデジタル署名された情報の集合について 有効期限を伝える場合、実装者には、正確さを 優先する表現よりも理解しやすい言葉を使用して 有効期限を提示することが強く推奨されます。有効期限を「このチケットは 3日前に期限切れになりました。」と提示する方が、「このチケットは2023年7月 25日午後3時43分に期限切れになりました。」のような表現より好まれます。前者は、 後者より理解しやすい相対時刻を提供します。後者では、 個人が頭の中で計算する必要があり、そのような 計算を行えることを前提としているためです。

A. 証明セット と証明チェーンの理解

このセクションは非規範的です。

セクション2.1.1 証明セットおよび2.1.2 証明チェーンでは、 複数の証明を保護されたデータ文書で 表現する方法について説明しています。つまり、 保護されたデータ文書に単一の 証明を 含める代わりに、 例 6および 例 7に示すように、複数の証明をリストで表現できます。 このリストの要素は、 証明セットのメンバーであり、任意で証明チェーンのメンバーでもあります。この セクションの目的は、これら各機能の意図された用途と、特に それぞれの異なるセキュリティ特性を説明することです。これらの異なるセキュリティ 特性により、セクション 4.1.3 証明セット／チェーンの追加での処理に違いが生じます。

このセクションでは、重要なセキュリティ特性を 観察できるように、証明を含む保護されたデータ文書を 省略した形で表現します。

CEO、CFO、およびエンジニアリング担当 VP の3人の署名者がいるシナリオを考えます。 各署名者は文書へ署名するための公開鍵と秘密鍵のペアを持つ必要があります。 これらの署名者それぞれの秘密鍵／公開鍵を、 secretCEO/publicCEO、secretCFO/publicCFO、および secretVPE/publicVPE と表記します。

各署名者が特に依存関係を考慮せずに inputDocument へ署名する証明セットを構築する場合、 証明を記号的に次のように構築します。

例 9: 証明がどのように作成されるかの記号表現 
{
  "type": "DataIntegrityProof",
  "cryptosuite": "eddsa-jcs-2022",
  "created": "2023-03-05T19:23:24Z",
  "proofPurpose": "assertionMethod",
  "verificationMethod": publicCEO,
  "proofValue": signature(secretCEO, inputDocument)
}

ここで publicCEO は、CEO の公開鍵へ解決される参照の プレースホルダーとして使用され、signature(secretKey, inputDocument) は、特定の秘密鍵を使用して特定の文書に対し、 特定のデータ完全性暗号スイートによってデジタル署名を計算することを表します。 type、cryptosuite、created、および proofPurpose 属性は、この説明には関係しないため省略します。特に、 以下では、エンジニアリング担当 VP、CFO、および CEO によって署名された文書上の 証明セットに含まれるすべての証明を示します。

例 10: 証明セットの記号表現 
{
  // 保護されたデータ文書の残りは表示しない（上記）
  "proof": [{
    "verificationMethod": publicVPE,
    "proofValue": signature(secretVPE, inputDocument)
  }, {
    "verificationMethod": publicCFO,
    "proofValue": signature(secretCFO, inputDocument)
  }, {
    "verificationMethod": publicCEO,
    "proofValue": signature(secretCEO, inputDocument)
  }]
}

証明セットを含む保護されたデータ文書を受信した 保有者または その他の仲介者は、別のエンティティへ渡す前に セット内の任意の proof 値を削除できますが、それでも保護された データ文書は検証に成功します。これは意図された動作である場合も、そうでない場合もあります。 大切な従業員へ誕生日カードを送る署名者の場合、 証明セットの使用はおそらく問題ありません。 会社の階層に沿って承認が上がっていくビジネスプロセスをモデル化しようとしている場合、 これは理想的ではありません。仲介者が証明セットから署名を削除しても、 なお検証に成功するためです。たとえば、以下の例では、 CFO と CEO がエンジニアリング担当 VP の同意なしに何かを 承認したように見えます。

例 11: 証明セットからの署名の削除 
{
  // 保護されたデータ文書の残りは表示しない（上記）
  "proof": [{
    "verificationMethod": publicCFO,
    "proofValue": signature(secretCFO, inputDocument)
  }, {
    "verificationMethod": publicCEO,
    "proofValue": signature(secretCEO, inputDocument)
  }]
}

証明セット内の証明間に依存関係を導入することもできます。 そのためには、別の証明から参照できるよう、各証明の id プロパティを設定します。 言い換えると、依存する証明は、 previousProof プロパティを使用して他の 依存元となる証明から参照されます。このような 依存関係チェーンは任意の深さを持つことができます。このような証明チェーンの意図は、 ビジネスプロセスにおける承認チェーンや、公証人によるアナログ署名の立会いをモデル化することです。

以下の例では、まずエンジニアリング担当 VP が文書を承認して署名し、 その署名とレビューに基づいて CFO が文書を承認して署名し、 最後に、先行する2つの署名とレビューに基づいて CEO が文書を承認して署名する場合に、 証明チェーンをどのように構築できるかを示します。 他の者がエンジニアリング担当 VP の署名を参照するため、 証明に id を追加する必要があります。まず、エンジニアリング担当 VP が 入力文書へ署名します。

例 12: `id` プロパティを設定した最初の証明を含む証明チェーン 
{
  // 保護されたデータ文書の残りは表示しない（上記）
  "proof": {
    "id": "urn:proof-1",
    "verificationMethod": publicVPE,
    "proofValue": signature(secretVPE, inputDocument)
  }
}

次に、CFO は文書を受け取り、エンジニアリング担当 VP が署名したことを検証し、 レビューとエンジニアリング担当 VP の署名に基づいて署名します。 このため、受信した文書内の証明への 依存関係を示すことで証明チェーンを設定する必要があります。 これは、第2の証明の previousProof プロパティを urn:proof-1 の値に設定することで行います。これにより、第2の証明が第1の証明に 「結び付けられ」、その後署名されます。次の例は、第1の証明への依存関係が どのように作成されるかを示しています。

例 13: 2つの証明を含む証明チェーン 
{
  // 保護されたデータ文書の残りは表示しない（上記）
  "proof": [{
    "id": "urn:proof-1",
    "verificationMethod": publicVPE,
    "proofValue": signature(secretVPE, inputDocument)
  }, {
    "id": "urn:proof-2",
    "verificationMethod": publicCFO,
    "previousProof": "urn:proof-1",
    "proofValue": signature(secretCFO, inputDocumentWithProof1)
  }]
}

ここで CEO が、上記の証明チェーンを持つ受信済みの保護された データ文書を検証すると、 CFO がエンジニアリング担当 VP の署名に基づいて署名したことを確認します。 まず、値が urn:proof-1 である id プロパティを持つ証明を、 エンジニアリング担当 VP の公開鍵に対して確認します。この証明は 元の文書を対象としていることに注意してください。

次に CEO は、値が urn:proof-2 である id プロパティを持つ証明を CFO の公開鍵に対して確認します。 ただし、エンジニアリング担当 VP がすでに 署名した証明を含む文書に CFO が署名したことを確認するため、 文書と urn:proof-1 の組み合わせを対象としてこの証明を検証します。 検証に成功すると CEO が署名し、urn:proof-1 と urn:proof-2 を含む 文書を対象とする証明を生成します。最終的な 証明チェーンは次のようになります。

例 14: 3つの証明を含む証明チェーン 
{
  // 保護されたデータ文書の残りは表示しない（上記）
  "proof": [{
    "id": "urn:proof-1",
    "verificationMethod": publicVPE,
    "proofValue": signature(secretVPE, inputDocument)
  }, {
    "id": "urn:proof-2",
    "verificationMethod": publicCFO,
    "previousProof": "urn:proof-1",
    "proofValue": signature(secretCFO, inputDocumentWithProof1)
  }, {
    "id": "urn:proof-3",
    "verificationMethod": publicCEO,
    "previousProof": "urn:proof-2",
    "proofValue": signature(secretCEO, inputDocumentWithProof2)
  }]
}

この保護されたデータ文書の受信者は、その後、 チェーン内の各証明を確認しながら、同様の 方法で妥当性確認します。
