概要

この文書はSHACLプロファイリングを定義する。

SHACL、すなわちShapes Constraint Languageは、RDFグラフの構造を記述するための言語である。 SHACLは、検証、推論、ドメインのモデリング、他のエージェントに知らせるための オントロジーの生成、ユーザーインターフェイスの構築、コード生成、データ統合など、 さまざまな目的に使用できる。

SHACLプロファイリングは、SHACLのプロファイルとSHACLによるプロファイリングを記述できるようにする、SHACL Shapes Constraint Languageの要素を定義します。この文書の範囲は、SHACLシェイプを含むグラフを含め、RDFグラフのプロファイリングに限定されます。

この仕様はData Shapes作業部会が公開しています。

1.1 SHACLプロファイリングとは何か?

定義上、SHACLはRDFデータを制約するため、シェイプグラフに従って妥当であるデータは、データグラフのプロファイルになります。シェイプグラフがデータグラフのすべての要素を検証する場合、得られる妥当なデータはデータグラフの「Null」プロファイル、すなわち元のデータグラフと同一のものになります。

The Profiles Vocabularyでは、プロファイルを次のように定義しています。

他の標準の使用を制約、拡張、組合せ、またはその使用に関する指針や説明を提供する標準

シェイプグラフを「標準」と見なすと、シェイプグラフに従って妥当であるデータが検証対象のデータグラフのプロファイルになるだけでなく、シェイプグラフ自体もデータグラフで使用するデータモデルのプロファイルになります。

この文書では、最適なプロファイリングのためにSHACL情報をパッケージ化する方法を説明し、各SHACL仕様のために作成したRDFデータのパッケージ化を例として示します。

2. SHACLのパッケージ化

SHACLのパッケージ化とは、SHACL要素をシェイプグラフおよび結果グラフ内で提示することです。

2.1 動機

SHACL要素のパッケージ化に関する指針によって解決される、四つのユースケースが明確化されています。

  1. SHACL要素のグループを識別する
  2. あるグループが依存するすべてのSHACL要素を見つける
  3. あるグループが依存するすべてのSHACL要素のグループを見つける
  4. 検証結果をコンテキストとともに保存する
Issue 623: あるグループが依存するSHACL要素のすべてのグループを見つける ProfilingUCR

Profileが依存するすべてのProfileを見つける。

2.2 推奨事項の要約

上記のユースケースに対する指針を、次の推奨事項で示します。これらは、W3CのRDF Schema 1.1、OWL 2 Web Ontology Language Document Overview (Second Edition)、およびPROV-O: The PROV Ontologyの各仕様における、十分に確立された実践に基づきます。

  1. sh:ShapesGraphのインスタンスは、SHOULDとして、検証に使用するSHACL要素のインスタンスをグループ化するために使用することが望まれます
  2. 検証に使用するSHACL要素のインスタンスは、SHOULDとして、それを定義するsh:ShapesGraphのインスタンスをrdfs:isDefinedBy述語で示すことが望まれます
  3. sh:ShapesGraphのインスタンスが、SHACL要素を検証に使用するものの定義していない場合、SHOULDとして、そのSHACL要素をrdfs:member述語でメンバーとして示すことが望まれます
  4. sh:ShapesGraphのインスタンスを、SHACL要素のうち検証に使用するもののグループ化に用いる場合、SHOULDとして、他のSHACL要素のグループへの依存を示すことが望まれます。それらのグループはsh:ShapesGraphのインスタンスで識別し、依存はowl:imports述語で示します
  5. 結果グラフの要素の結果を永続化するとき、検証報告のコンテキストは、SHOULDとして、SHACLプロファイリング語彙の要素を使って与えることが望まれます

以下のサブセクションでは、これらの推奨事項をそれぞれ詳述する。

2.3 SHACL 要素のグループの識別

sh:ShapesGraphのインスタンスは、SHOULDとして、検証に使用するSHACL要素のインスタンスをグループ化するために使用することが望まれます。

SHACL要素は、他の多くのRDF定義データと同様に、 OWL 2 Web Ontology Language RDF-Based Semantics (Second Edition)の owl:Ontologyクラスのインスタンス内でグループ化されることが多かった。

例えば、Open Geospatial Consortiumの空間RDFデータ用標準GeoSPARQL 1.1は、SHACL検証器を提供しています。そのTurtleファイルには、27個のsh:NodeShapeのインスタンスと、同程度の数のsh:PropertyShapeのインスタンスが含まれます。また、このファイルにはowl:Ontologyのインスタンスもあり、更新日や使用許諾など、検証用リソースのメタデータを提示します。

この推奨事項はその実践に代わるものであり、sh:ShapesGraphを使うことを推奨します。これはSHACL 1.2 Coreで、SHACL要素をグループ化するために特別に定義されたクラスです。

NodeShapeとクラス定義など、SHACLとOWLの要素が混在する場合には、owl:OntologyをSHOULDとして引き続き使用することが望まれます。

2.4 要素定義の 表示

検証に使用するSHACL要素のインスタンスは、SHOULDとして、それを定義するsh:ShapesGraphのインスタンスをrdfs:isDefinedBy述語で示すことが望まれます.

SHACL要素を、owl:Ontologyのインスタンスで識別したグループにまとめる際は、要素とオントロジーのインスタンスを単にRDFファイルに含めるのが一般的でした。これはデータ交換には適していますが、交換したファイルをRDFデータベースに格納すると、コンテナーのインスタンスと、その中で定義されたSHACL要素の関連が失われることがあります。名前付きグラフに読み込む場合、その名前付きグラフがオントロジーとSHACL要素をまとめることで関連を保持できるかもしれませんが、これは非意味的な関連、すなわちグラフ内で直接見える関連ではありません。

この推奨事項では、SHACL要素の作成者は、SHOULDとして、そのSHACL要素が定義されるグループを示すことが望まれます。そのようなRDFの表明の例を次に示します。

ex:sg-M a sh:ShapesGraph ; . ex:shape-1 a sh:NodeShape ; rdfs:isDefinedBy ex:sg-M ; .
[ { "@id": "http://example.com/ns#ont-M", "@type": [ "http://www.w3.org/ns/shacl#ShapesGraph" ] }, { "@id": "http://example.com/ns#shape-1", "@type": [ "http://www.w3.org/ns/shacl#NodeShape" ], "http://www.w3.org/2000/01/rdf-schema#isDefinedBy": [ { "@id": "http://example.com/ns#ont-M" } ] } ]

2.6 グループ依存関係の表示

sh:ShapesGraphのインスタンスを、SHACL要素のうち検証に使用するもののグループ化に用いる場合、SHOULDとして、他のSHACL要素のグループへの依存を示すことが望まれます。それらのグループはsh:ShapesGraphのインスタンスで識別し、依存はowl:imports述語で示します.

SHACLの検証ツールでは、SHACL要素をRDFデータを含むファイルなどのコレクションから別のコレクションへ、owl:imports指示によってインポートすることが確立した実践です。pySHACL [PYSH]など、多くのSHACL検証エンジンがこれを行います。この表明によって検証エンジンの特定の動作を期待しない場合でも、コレクションやグループから別のものへの依存を示すためにこの実践を推奨します。SHACLデータの管理にも有益な情報になると考えられます。

owl:importsの例は、以下の例のとおりである。

# 'Shapes Graph N' imports 'Shapes Graph M' ex:sg-M a sh:ShapesGraph ; . ex:sg-N a sh:ShapesGraph ; owl:imports ex:sg-M ; .

# 'Shapes Graph N' imports 'Version 4.2 of Shapes Graph M' ex:sg-M a sh:ShapesGraph ; owl:versionIRI ex:sg-M-4.2 ; . ex:sg-N a sh:ShapesGraph ; owl:imports ex:sg-M-4.2 ; .

2.7 コンテキストを伴う検証結果の永続化

結果グラフの要素の結果を永続化するとき、検証報告のコンテキストは、SHOULDとして、SHACLプロファイリング語彙の要素を使って与えることが望まれます.

結果グラフを将来も理解できる形で永続化するには、検証報告にコンテキストを関連付ける必要があるかもしれません。把握することが重要と考えられるコンテキストは、検証への入力であるデータグラフとシェイプグラフ、検証の時期、および検証を実行したシステムの詳細です。

このようなイベント、すなわち検証の詳細は、PROV-O: The PROV Ontologyが特徴付ける標準的な事項です。PROV-Oは、コンテキストを保持するための一般的なモデルである来歴を提供します。以下のSHACLプロファイリング語彙では、PROV-Oの基本要素を特殊化します。この語彙はSHACL 1.2 Coreの語彙の部分集合です。

PROV-Oの一般的な来歴モデルは、出発点の図である図1に示すとおり、prov:Activityのインスタンスを時間的イベントとして捉えます。これらは、消費（prov:used）と生成（prov:generated）の対象となる物（prov:Entityのインスタンス）を扱い、人、組織、またはシステムとの実行上の関連（prov:wasAssociatedWith）を持ちます。後者はprov:Agentのインスタンスです。

SHACL検証のイベント、すなわち処理は、prov:Activityの特殊化であるsh:ValidationActivityとして表します。プロセッサーオブジェクトは、prov:Agentの特殊化であるsh:ValidationAgentとして表します。

SHACL 1.2 Coreの検証の節は、処理に必要な入力をデータグラフ（sh:DataGraph）とシェイプグラフ（sh:ShapesGraph）として規定しています。プロセッサーの実装は、推論などに使う追加リソースにも対応する場合があります。また、処理はsh:ValidationReportのインスタンスを生成すると定義されています。これらはすべてprov:Entityの特殊化です。

sh:ValidationActivityは、入力として少なくともデータグラフとシェイプグラフを持つ必要があり、その役割は大きく異なります。そのため、これらを示すためにprov:usedを特殊化した二つの形式、sh:usedDataGraphとsh:usedShapesGRaphを用意しています。

4. SHACLによる プロファイリング

この節では、SHACLでRDFリソースのプロファイルを作成する方法を説明します。

The Profiles Vocabularyの一般的な プロファイリング用語および要素を、5. SHACLプロファイリング語彙で定義される、より特殊化されたSHACLプロファイリング要素とともに用いる。

4.1 はじめに

このセクションは非規範である。

2017年の公開以来、SHACLは、W3Cオントロジーなどの開世界のRDFモデルを基礎として、アプリケーションが使う閉世界のRDFデータモデルを作成するために広く使われてきました。

典型的な例として、Indigenous Data Networkはプロファイルをschema.orgに対して定義しています。これは、この汎用RDF語彙を先住民データの目録作成に用いるために制約するものです。IDNは、目録に記載されたオブジェクトのメタデータがそのプロファイルに適合するかをテストするSHACL検証器を提供しています。

汎用的または制約の緩いモデルを制約するだけでなく、規則に従ってデータを検証するリソースを提供していない仕様に対しても、シェイプグラフを定義できます。シェイプグラフが元のモデルに追加規則を課さず、仕様のすべての規則の実装も試みる場合、それはそのモデルのNullプロファイルになります。

仕様のプロファイリングに加え、RDFデータセットからのデータ抽出に使う場合、SHACLはそのデータセットのデータプロファイルを作成します。

以下の節では、仕様のプロファイリングとデータのプロファイリングについて説明し、指針を示します。

4.2 仕様のプロファイリング

4.2.2 推論

The Profiles Vocabularyには一つの推論公理があり、プロファイルに適合するデータは、そのプロファイルの元となる標準にも適合すると理解できます。

dcterms:conformsTo owl:propertyChainAxiom ( dcterms:conformsTo prof:isProfileOf ) ; .

この規則は、ある標準のプロファイルであるシェイプグラフに従って妥当と宣言されたデータを、その標準に適合すると理解できるようにするために提示しています。この規則は、4.2.4 Nullプロファイルの作成の節に従い、SHACLでNullプロファイルを作成する際に重要です。

4.2.3 プロファイル階層

SHACLで定義したプロファイルと、そのプロファイルの元となる標準の両方にデータが適合するかをテストする必要がある場合、その標準もSHACLで定義されているか、SHACLで作成した検証の役割のリソースを提供していれば、プロファイルと標準またはその検証器を組み合わせたシェイプグラフを作成できます。

これは、複数の標準をプロファイリングしたり、他のプロファイルのプロファイルを作成したりするような複雑な状況で重要になると考えられます。標準とプロファイルから自動的にシェイプグラフを組み立てる方が、手動で組み立てるよりはるかに望ましい場合があるためです。

4.2.4 Nullプロファイルの作成

SHACLが作られる前は、閉世界のRDFデータモデルや、RDFモデルの検証器を表す標準化された方法がありませんでした。SHACLが存在する現在は、標準のNullプロファイルを作成することで、OWL 2 Web Ontology Language Document Overview (Second Edition)などのモデル化システムで作成した標準に、検証の仕組みを後付けできます。

The Profiles Vocabularyおよび4.1 はじめにに従うと、標準のNullプロファイルとは、元の標準に追加規則を課さず、その標準のすべての規則の実装も試みるものです。

標準のNullプロファイルはSHACL以外のモデル化システムや規則システムでも作成できますが、ここではSHACLの使用だけに焦点を当てます。

Issue 1420: Nullプロファイルの節のレビューを完了する Profiling
 

SHACLを使って標準のNullプロファイルを作成する主な目的は、SHACL検証によってその標準への適合をテストできるようにすることです。OWLモデルやモデルの自然言語文書だけといったモデル標準を持ちながら、SHACL検証器のようなデータ検証の仕組みを提供していないRDFデータモデルが数多くあるため、この目的が生じます。その例として、Data Catalog Vocabulary (DCAT) - Version 3、Schema.org、The RDF Data Cube Vocabulary、および多くのW3C標準があります。

注記

null profileとして機能するRDFデータ向けの非SHACL validatorの例として、 W3CのConstraints of the PROV Data Modelがある。 これは、PROV-O: The PROV Ontologyに従って定式化された来歴データに適用される制約の一覧を提供する。 Constraints of the PROV Data Modelは、PROV-O: The PROV Ontologyおよび 概念的なPROV-DM: The PROV Data Modelで 明示または暗示されたものを超える制約を実装しない。ただし、時間的エンティティの順序付けなど、 モデルが明示的にモデル化していないが適切な使用には必要なものに対するテストを含んでいる。 これらの制約の実装は、SPARQLクエリを実行してRDFデータ検証を可能にするPythonスクリプトとして 作成されている。

標準のNullプロファイルを作成する普遍的で厳密な方法論は示せません。このタスクの性質上、標準の規則が不正確に定義されている場合があり、その規則を厳密なSHACLで特徴付ける方法も、その不正確な定義と同様に変わるためです。

他の標準のNullプロファイルの例は、B. Nullプロファイルの例を参照してください。

5.7 規則: conforms to shapes graph

「conforms to shapes graph」規則は、データグラフがシェイプグラフに適合することを示せる推論規則です。その条件は、検証報告（Validation Report）が存在し、その検証にデータグラフとシェイプグラフを使用し、その報告のsh:conformsプロパティがtrueを示すことです。

この推論規則は、sh:conformsプロパティ値の検査を伴うため、OWLプロパティ連鎖公理では表現できません。そこで、SPARQL 1.2 Query Languageの規則とSPARQL 1.2 RLの規則の両方で示します。

CONSTRUCT { ?dg sh:conformsToShapesGraph ?sg } WHERE { ?va sh:usedDataGraph ?dg ; sh:usedShapesGraph ?sg ; prov:generated ?vr ; . ?vr sh:conforms true . }
RULE { ?dg sh:conformsToShapesGraph ?sg } WHERE { ?va sh:usedDataGraph ?dg ; sh:usedShapesGraph ?sg ; prov:generated ?vr ; . ?vr sh:conforms true . }

5.8 規則: conforms to standard

「conforms to standard」規則は、データグラフが標準に適合することを示せる推論規則です。その条件は、データグラフが、シェイプグラフに適合し、そのグラフが当該標準のプロファイルであることです。この推論により、標準のプロファイルや標準自体へのデータの適合性を静的に主張できます。これは、その適合性を知る必要がある一方で継続的には検証できないデータに有用です。

この推論規則は、SPARQL 1.2 Query Languageの規則と、SPARQL 1.2 RLの規則の両方で示します。

A.2.3 再帰的制約を禁止するプロファイル

このプロファイルは、SHACLシェイプを定義する際の構造的検証規則を定め、再帰的制約の記述を明示的に禁止します。SHACLコア仕様は構造的な再帰を認めていますが、異なる実装が再帰的定義を異なる方法で評価する可能性を認めています。この違いは、プロセッサーが循環するデータグラフに遭遇した際、非決定的な動作や無限の検証ループにつながることがよくあります。適合するすべてのプロセッサーで予測可能かつ一貫した検証結果を得られるように、このプロファイルは、自己参照シェイプ、相互依存するシェイプ、再帰的な木構造など、禁止するシェイプ記述パターンを定義します。

再帰的制約の定義

SHACLシェイプグラフSGが非再帰的制約プロファイルに適合するのは、その必要十分条件として、以下で定義するシェイプ参照グラフが非循環である場合です。

R(SG)を、次の条件を満たす有向グラフとします。

  • 各ノードはSG内のシェイプです。すなわち、sh:Shape、sh:NodeShape、sh:PropertyShapeのいずれかであるRDFノード、または以下の定義に従いシェイプを表す位置で使われるRDFノードです。
  • R(SG)に有向辺s → tが存在するのは、SG内でシェイプsがシェイプtを、SHACLプロパティを通じて参照する場合です。そのプロパティ値は、シェイプを直接識別するか、シェイプへの参照を含むRDFリストを識別します。

シェイプグラフがこのプロファイルに適合するかを判定するため、実装はMUSTとして、シェイプ参照グラフの構築と循環の検査において、以下の各プロパティとリスト構成をシェイプ参照関係として扱わなければなりません。

  • sh:node
  • sh:property（参照されたプロパティシェイプへの辺）
  • sh:qualifiedValueShape
  • リストのメンバー：sh:and、sh:or、sh:xoneの各リストに含まれるもの
  • sh:not
  • sh:memberShape
  • sh:reifierShape
  • sh:someValue

シェイプグラフは、s → ⋯ → sという循環を一つでも含むと、このプロファイルに違反します。これには次のものが含まれます。

  • 直接的な自己参照（シェイプが自分自身を参照する）、および
  • 間接的な自己参照（シェイプが別のシェイプを参照し、その参照をたどると元のシェイプに戻る）
  • 自己参照的な否定（自分自身を否定するシェイプ）

C. セキュリティとプライバシーに関する 考慮事項

このセクションは非規範である。

ほとんどのRDFベース技術と同様に、SHACLプロセッサーは、さまざまなソースから 組み立てられたグラフを操作する場合がある。一部のアプリケーションは、オープンな 「linked data」（「LD」）アーキテクチャを持ち、組織の信頼ネットワークの外部にあるソースから RDFトリプルを動的に組み立てる場合がある。 RDFでは誰でも任意のリソースについて文を追加できるため、トリプルがshape定義または データグラフ内のノードの当初意図された意味を変更し、その結果、 誤解を招く結果につながる可能性がある。 これ（および以下）のシナリオに対する保護は、信頼され検証されたRDFソースのみを使用し、 owl:importsおよびsh:shapesGraphを介してグラフが動的に追加される可能性を 排除することで実現可能である。

他の標準のプロファイルを作成するとき、作成者は、自分の制約がその標準の規則に違反しないことを確認する必要があります。違反する制約があり、偶然または意図的に、標準の規則ではなくプロファイルの規則だけを使ってデータの妥当性を検査すると、データを誤って妥当と判定する可能性があります。これは、意図しないデータの公開や使用につながり、セキュリティ問題を引き起こす可能性があります。
