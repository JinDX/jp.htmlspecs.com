概要

この文書は、RDF 向けの Datalog 形式のルール言語である SPARQL-RL を定義します。

SPARQL-RL は、入力 RDF グラフに対して宣言的な ルールの集合を評価することにより、新しい RDF データを生成します。ルールは SPARQL に似たテキスト構文で記述されます。

1. 序論

この文書では SPARQL-RL を紹介します。これは、宣言的なルールを通じて 既存の RDF データから新しい RDF トリプルを導出するための仕組みです。 この文書では、ルールベース推論の構文と意味論を定義します。

SPARQL-RL の実装は、infer および query の 一方または両方の操作を提供します。 infer 操作は、指定された ベースグラフにルールを適用し、ベースグラフには現れない、 ルール評価によって導出された RDF トリプルを含む推論グラフを生成します。 推論グラフとベースグラフを結合するかどうかは任意であり、 ユーザーに委ねられます。 query 操作は、指定されたゴールパターンが、 ルールを使用してベースグラフから導出できるかどうか、およびどのように導出できるかを 判定します。

SPARQL-RL では、空白ノードを含む新しい RDF 項を作成でき、 それらをルールのヘッド内のトリプルテンプレートで使用できます。

SPARQL-RL は失敗による否定もサポートしており、ルールを 評価する順序によって異なる推論グラフが生じる可能性があります。 これを避けるため、ルールは層別化という手法を使用して評価されます。 これはルール間に順序を確立し、 常に同じ推論グラフが生成されることを保証します。

文脈が明確な場合、SPARQL-RL は SRL と呼ぶことができます。

3. SPARQL-RL の概要

この節は非規範的です。

SPARQL-RL は、ベースグラフとルールセットを与えると、新しいトリプルを推論します。 評価の出力は、ベースグラフには現れない導出された トリプルを含む推論グラフです。

各ルールには、ボディと呼ばれるパターンと、 ヘッドと呼ばれる結果テンプレートがあります。 ルールは、ボディが結合されたベースグラフおよび その時点までの実行によって推論されたトリプルに一致するように、 ボディ内の変数の値を見つけることで実行されます。 次に、これらの値を使用してルールヘッド内のトリプルテンプレートを インスタンス化し、新しい推論トリプルを生成します。

それ以上トリプルが推論されなくなるまでルールが実行され、 新しい推論トリプルが利用可能になるにつれて、ルールは複数回 実行されることがあります。

SPARQL-RL の実行は、新しい空白ノードを含む 新しい RDF 項を作成する場合や、パターンが存在しないことを テストする場合に、ルールの実行順序によって異なる結果が 生じないように定義されています。言い換えると、ルールの実行順序に 関係なく同じ推論グラフが生成されます。

SPARQL-RL には、SPARQL 1.2 クエリ言語から着想を得た、 人間に扱いやすい構文があります。 ルールセットの評価には SPARQL と類似した要素が含まれますが、 ルールの実行順序に関係なく同じ推論グラフが生成されることを 保証するため、細部には相違があります。

この節の例では、ソフトウェアコンポーネントと その依存関係について説明します。フロントエンドがアプリケーションサーバーを呼び出し、 アプリケーションサーバーは既知の脆弱性を持つ データベースにクエリを行います。

3.1 トリプルパターン

トリプルパターンはトリプルデータと照合され、 変数に値を与えます。パターンには 3つの要素があり、それぞれはRDF用語、変数、 または変数を含むトリプル用語のパターンです。

この最初の例では、基本グラフと規則集合に次のデータがあります。

例 1: 基本的な例 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
:frontend :dependsOn :app .
:app      :dependsOn :db .

上記の規則をデータに適用すると、次のように結論付けられます。 :frontendは:appに依存し、:appは :dbに依存します。依存関係の種類は問いません。

次に、依存する規則を追加することで、:exposedTo関係を導出できます。 その依存先は、他の規則によって生成される:dependsOnトリプルです （後述の4.3 規則の 依存関係も参照）。

例 2: 推論されたトリプルへの依存 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
:app      :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

3.2 再帰

前節の:exposedTo規則が到達するのは直接の 依存先のみです。:frontendは:dbに直接依存しないため、 :frontendについて:exposedToトリプルは推論されません。 任意の長さの依存関係の連鎖に沿って曝露を伝播させるため、 その規則を2つの規則に置き換えます。コンポーネントは、自身が持つ 脆弱性にさらされ、また、コンポーネントは、 その直接の依存先がさらされているあらゆる脆弱性にさらされます。

例 3: 規則の再帰 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :hasVulnerability ?v }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :exposedTo ?v }
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

前の例と比較すると、ここでは次のものが追加されます。 :db :exposedTo :vuln1 — データベースは自身の 脆弱性にさらされます — および:frontend :exposedTo :vuln1です。 曝露は、依存関係の連鎖を通じて:frontendに到達します。 その連鎖の長さは問いません。

この最後の規則は再帰的な規則です。規則の本体が 規則の頭部に依存しています。

3.3 フィルタリング

規則の本体で式を使用することで、変数の値を制限できます。 この制限は、本体の照合時に適用されます。 たとえば、各脆弱性の深刻度が与えられた場合、 深刻な脆弱性にさらされているコンポーネントに 状態を付与できます。

例 4: フィルタリング 
:app1 :exposedTo :vuln1 .
:app2 :exposedTo :vuln2 .
:vuln1 :severity 9.1 .
:vuln2 :severity 4.3 .
RULE { ?x :status :criticallyExposed }
WHERE {
    ?x :exposedTo ?v .
    ?v :severity ?s .
    FILTER(?s >= 9.0)
}
:app1 :status :criticallyExposed .

FILTERは式を評価し、現在の 変数束縛の集合を、式の評価結果が真であれば保持し、 式の評価結果が偽であれば、現在の変数束縛の集合を破棄します。 これは、次のものと同じです。 SPARQLのFILTER演算 また、SPARQL-RLはSPARQLと同じ関数および演算子を多数提供します。

3.4 否定

否定は、一致してはならないパターンを指定するために使用されます。 これは「失敗による否定」と呼ばれます。

否定要素を評価するため、規則集合の評価アルゴリズムは、 否定要素内のパターンに一致するトリプルを生成し得るすべての規則が 完了していることを保証します。これは、 階層化と呼ばれ、否定が、 データ由来であるか他の規則由来であるかを問わず、関連するすべての可能なトリプルに 基づくことを保証します。否定を含む規則は、 これらのトリプルを生成する規則に依存するといいます （後述の4.3 規則の 依存関係を参照）。

例 5: 失敗による否定 
:app rdf:type :Component ;
    :status :criticallyExposed .

:logger rdf:type :Component .
RULE { ?x :status :safeToDeploy }
WHERE {
    ?x rdf:type :Component .
    NOT { ?x :status :criticallyExposed }
}
:logger :status :safeToDeploy .

3.5 代入とRDF 用語の作成

代入により、規則は式の結果を変数に代入できます。 これは規則の本体で行われます。これを使用すると、新しいRDF用語を データに基づいて作成できます。

例 6: 代入 
RULE { ?v :riskScore ?r }
WHERE {
    ?v :severity ?s .
    ?v :exploitLikelihood ?p .
    SET ( ?r := ?s * ?p )
}

規則の頭部では空白ノードを使用でき、それぞれが新しい空白ノードを生成します。 この生成は、規則の評価がトリプルを生成するたびに行われます。

例 7: 規則の頭部における空白ノード 
RULE { [] rdf:type :Notification ; :concerns ?x }
WHERE { ?x :status :criticallyExposed }

代入を含む規則、空白ノードを作成する規則で、 その作成が規則の頭部の評価によるもの、およびテンプレートを持つ規則で、 そのテンプレートにトリプル用語が含まれ、その用語が変数を含むものは、 単一実行規則です。 このような規則は、依存するデータを生成し得るすべての規則の後に実行され、 自身が生成するデータに依存するすべての規則より前に実行されます。

この条件は、このような規則が自身へと循環し、 無制限の数のRDF用語を作成することがないよう保証します。

注

定数のRDF用語が規則の頭部にあっても、 その規則が 単一実行規則になるわけではありません。その用語が 基本グラフに現れない場合でも同様です。規則は評価されるたびに同じ用語を 提供するため、追加できる用語の数には上限があります。

代入内の式の評価でエラーが発生した場合、 現在の解写像は、次の代入によって棄却されます。

3.6 グループ化と集約

GROUP BYと集約関数を提供します。 これには少なくとも、 COUNT、COUNT DISTINCT、MIN、MAX、および SUMが含まれます。

集約要素を持つ規則は、単一実行規則です。 このような規則は、自身が依存するデータを生成し得るすべての規則の 後に、自身が生成するデータに依存するすべての規則より前に実行されます。 集約要素は、完全なコレクションを消費します。その対象は、 解列であり、先行する規則要素のものです。 これらは規則の本体内にあり、次のものに基づいてグループにまとめられます。 グループキー。その後、評価します

出力は、解列であり、各[solution mapping=]は、 グループキーと集約代入を含みます。

3.7 規則集合のインポート

SPARQL-RLの規則集合は、他の規則集合を組み込むことができます。 そのためには、それらのURLを、その規則集合の規則集合のインポートに含めます。 これにより、規則集合間で共有されるライブラリとして規則を構成できます。

規則集合のIMPORTS文は、その規則集合内のいずれの規則が 評価されるよりも前に処理されます。インポートのステップでは、インポートされた規則集合に 独自のインポートがある場合、それらも再帰的に処理されます。 規則集合の処理中にIMPORTS文をたどると、 循環するインポートに遭遇することがあります。規則集合は一度だけインポートされます。 インポート文のグラフに循環があっても、無限ループにはなりません。

規則集合のインポートのサポートは、SPARQL-RL 処理系にとって任意です。 詳細については、4.5 処理対象の インポートを参照してください。

3.8 データブロック

データブロックは、規則集合の評価にRDFトリプルを直接提供します。 データブロック内のトリプルは推論グラフに追加され、 規則の本体での照合に利用できます。

たとえば、規則集合には、既知の事実を直接表明して 含めることができます。データから導出する必要はありません。

例 8: 規則集合にデータを含める 
DATA {
    # バージョン2.0.0以前には既知の脆弱性があり
    # 深刻な脆弱性にさらされていると想定されます。
    :appV2 rdf:type :Component ;
           :version "2.0.0" ;
           :status :criticallyExposed .
}
注

データブロックは、本体が空の規則と同等です。 そのトリプルは、いずれの規則も 評価されることなく、推論グラフの一部となります。

3.9 基本データの照合

規則集合の評価中には、 元の基本グラフのみを対象としてパターン照合を行い、 推論されたトリプルを対象としないことが必要な場合があります。

この例として、既定値の設定があります。 規則は、基本グラフにすでに値が含まれているかを検査しなければならず、含まれていない場合、 その規則は既定値を計算できます。

例 9: NOTによる基本データ 
:A :distanceMiles 5 .
:A :distanceKilometers 8 .
:B :distanceMiles 10 .
RULE  { ?x :distanceKilometers ?kilometers }
WHERE {
    ?x :distanceMiles ?miles .
    NOT DATA { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?miles *  1.60934))
}
:B :distanceKilometers 16 .

NOT DATAを使用すると、規則の本体の他の部分では推論されたトリプルを照合できます。 また、すべての規則の本体の照合を、基本グラフに対して行うこともできます。 これにはWHERE DATAを使用します。 このような規則は、基本グラフからの照合のみに依存します。

WHERE DATA {
    ?x :distanceMiles ?miles .
    NOT { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?miles *  1.60934))
}
注

この節での照合対象は、基本グラフです。 次によって追加されるトリプルは含まれません。 規則集合の評価 その追加元は、規則集合のDATAブロックです （3.8 データブロック）。

3.10 規則集合の評価

規則は、規則集合にまとめられます。 規則集合とデータグラフ（基本グラフ）が評価への入力です。 出力は、推論グラフと呼ばれるグラフであり、 評価プロセスによって生成されるトリプルの集合で、 次の基本グラフに現れないものです。

評価中に、ある規則に基づいて推論されたトリプルは、 他の規則での照合に利用できます。 規則集合の評価は、 それ以上のトリプルを推論できなくなるまで進行します。 その入力は、規則集合と基本グラフです。

評価は、次のステップから始まります。 規則集合の準備 これらは、規則自体が評価される前に行われます。

  1. サポートされている場合、入力規則集合のインポートを解決し、 インポートされたすべての規則集合のすべての規則を含む 規則集合を形成します。 いずれかのインポートを処理系が受け入れられない場合、 処理系はエラーを通知します（4.5 インポートの処理）。
  2. 各規則が整形式の規則であることを確認します。
  3. 依存関係グラフを計算します。
  4. 階層化が計算されます （4.4 階層化）。 これにより、否定要素と単一実行規則は、一貫性があり、 予測可能な結果を生成します。階層化には、次のものの検査が含まれます。 依存関係、 すなわち規則間の関係です （4.3.1 依存関係 グラフ）。

規則集合の準備が完了すると、評価は次のように進行します。 階層化から各層を順に取り出し、 その層の規則を完了するまで評価し、 その後、次の層に進みます。 規則の実行によってトリプルが推論されると、それらは直ちに、 他の規則が実行される際に利用可能になります。

4.3 ルールの依存関係

規則R1は、2番目の規則の出力が 最初の規則の本体の評価に影響する場合、規則R2に依存します。すなわち、R2の頭部は トリプルテンプレートを持ち、それは、次のものに一致するトリプルを生成できます。 トリプルパターンで、R1の本体内にあり、 トリプルパターン要素として、または否定要素内、 もしくは集約パターン内にあるものです。

依存関係には2種類あります。 閉じた依存関係と開いた 依存関係です。 閉じた依存関係は、規則R2が、 規則R1の実行前に、可能な出力をすべて生成済みであることを保証します。 規則の依存関係が閉じていない場合、それは開いた依存関係です。 これは、最初の規則R1の実行を許可します。 その一方で、規則R2は、さらにトリプルを生成するために再実行される可能性があり、 それによって、R2からの新しいトリプルを用いてR1が再評価されることがあります。

フラグ.evaldataがfalseに設定された規則は、 基本グラフを使用して照合を行い、その規則には依存関係がありません。

この最初の例では、最初の規則は開いた依存関係を持ちます。 その依存先は2番目の規則です。

例 11: 開いた依存関係 
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }

この2番目の例では、最初の規則は閉じた依存関係を持ちます。 その依存先は2番目の規則です。トリプルパターン?x :status :criticallyExposedは、 最初の規則の否定要素内に現れ、 2番目の規則の頭部にあるトリプルテンプレートに一致します。 最初の規則は、2番目の規則が 可能な出力をすべて生成するまで評価できません。

例 12: 閉じた依存関係 
RULE { ?x :status :safeToDeploy }
WHERE { ?x rdf:type :Component . NOT { ?x :status :criticallyExposed } }

RULE { ?x :status :criticallyExposed } WHERE { ?x :exposedTo ?v }

トリプルパターンの依存関係

トリプルパターンは、 依存するといいます。その依存先が トリプルテンプレートであるのは、 そのトリプルパターンが、 一致できる場合です。 その一致先は、当該トリプルテンプレートです。

  • トリプルパターンで、否定要素内に現れ、その要素が R1のものであり、当該否定要素のフラグ .evaldataがtrueであるものが、 トリプルテンプレートに一致し、そのテンプレートが規則の頭部、すなわちR2の頭部にある場合。

4.3.1 依存関係グラフ

ルール間の依存関係は、依存関係グラフと呼ばれる有向グラフとして表されます。 グラフの頂点はルールセットのルールであり、辺には、 依存関係が開いた依存関係か閉じた依存関係かに応じて、 open または closed のラベルが付けられます。

依存関係グラフ

推移的ルール依存関係
ルール R1 からルール R2 への経路が 依存関係グラフ内に存在する場合、 ルール R1 はルール R2 に 推移的依存関係を持ちます。
再帰的ルール依存関係

R を含む循環経路が 依存関係グラフ内に存在する場合、 ルール R は再帰的依存関係を持ちます。

注記

依存関係グラフはベースグラフの影響を受けません。

4.3.2 依存関係グラフのアルゴリズム

次のアルゴリズムは、ルールセットから依存関係 グラフを構築する方法の一例を示します。 適合性は、依存関係グラフの定義を満たす依存関係グラフを生成することに依存し、 この手順を使用することには依存しません。 

define mergeLabel(oldLabel, newLabel):
    # 閉じた依存関係は開いた依存関係に優先します。
    if oldLabel == "open" and newLabel == "open":
        the result is "open"
    else:
        the result is "closed"
    endif
enddefine

# 出力 -- 規則を頂点とし、ラベル付きの辺を持つ依存関係グラフ。
define buildDependencyGraph(ruleSet):
    # edgeLabelMapは(R1, R2)を"open"または"closed"に対応付けます
    let edgeLabelMap be a map from pair (rule, rule) to label

    foreach rule R1 in ruleSet.rules:
        let bodyDependencies = {}

        if R1.evaldata then:
            # 規則内の各トリプルパターンTPを、"open"または"closed"を必要とするものとして分類します
            # その分類は、否定要素内または集約
            # パターン内にあるかどうかによります。
            foreach rule element RBE in R1.body:
                if RBE is a triple pattern element of triple pattern TP:
                    let item be a pair (TP, "open")
                    add item to bodyDependencies
                else if RBE is a filter element:
                    # 何もしません
                else if RBE is a negation element:
                    if RBE.evaldata then:
                        foreach triple pattern TP in RBE.inner:
                            let item be a pair (TP, "closed")
                            add item to bodyDependencies
                        endfor
                    endif
                else if RBE is an assignment element:
                    # 何もしません
                else if RBE is an aggregation element:
                    foreach triple pattern TP in RBE.pattern:
                        let item be a pair (TP, "closed")
                        add item to bodyDependencies
                    endfor
                endif
            endfor
        endif

        foreach pair (triple pattern TP, depLabel) in bodyDependencies:
            if R1 is a run-once rule:
              set depLabel to "closed"
            endif
            # このトリプルパターン要素または否定要素の依存関係を見つけます。
            foreach rule R2 in ruleSet.rules:
                foreach triple template TT in R2.head:
                    if triple pattern TP matches triple template TT:
                        let key = (R1, R2)
                        if edgeLabelMap contains key:
                            let oldLabel = edgeLabelMap.get(key)
                            let merged = mergeLabel(oldLabel, depLabel)
                            edgeLabelMap.set(key, merged)
                        else:
                            edgeLabelMap.set(key, depLabel)
                        endif
                    endif
                endfor
            endfor
        endfor
    endfor

    let DP = { }
    foreach entry ((R1, R2), label) in edgeLabelMap:
        add an edge (R1 -> R2) labeled with label to DP
    endfor

    the result is DP
enddefine

4.4 層別化

階層化は、規則集合を 順序付きの階層化の層の列に分割するプロセスです（層は 「strata」、単数形では「stratum」とも呼ばれます）。低い層の規則は、 高い層の規則より前に評価されます。

階層化は、依存関係に制約を課します。その対象は規則間の依存関係であり、 否定要素、集約要素、 および単一実行規則が依存する対象を、 先行する（低い）層を使用して計算された結果、および 基本グラフのみに限定することを保証します。 これにより、単一で明確に定義された有限の 結果が、規則集合の評価から得られることが保証されます。その評価対象は、与えられた基本グラフです。

注

階層化プロセスは、評価に関する他の 決定にも使用できます。この文書は、一貫した評価に 必要な条件を説明し、階層化を形成するための 可能な方法の1つを示します。実装は、互換性のある動作を得るために、 ここで説明する条件を満たす必要がありますが、 提示されたとおりにアルゴリズムを実装する必要はありません。

階層化レイヤー

階層化レイヤー SL は、対をなす 互いに素な集合であり、その要素は ルールです（SL.once, SL.general）。 SL.once は、そのレイヤーの一度だけ実行される ルールのみからなります。 これらのルールは、それぞれ評価されます。 その回数は、階層化レイヤーの評価開始時に、ちょうど一度です。 SL.general は、そのレイヤーの残りのルールの集合であり、 新しいトリプルが推論されなくなるまで繰り返し評価されます。

階層化

階層化は、ルール集合に対する、階層化レイヤーの列です。 ルール集合内の各ルールは、いずれか 1 つの集合にちょうど一度現れます。 その集合は、いずれか 1 つの階層化レイヤーに属します。

階層化レイヤーには、それらが属する階層化内で番号が付けられます。 番号はゼロから始まります。層番号は、ルールに対して、その番号を表します。 これは、階層化レイヤーのうち、そのルールを含むものの番号です。 より小さい層番号を持つルールは、 下位の層にあります。 より大きい層番号を持つルールは、 上位の層にあります。

ルール R1 からルール R2 へのすべての辺について、 依存グラフが属するルール集合では、次の条件が成り立ちます。

  • 辺に closed というラベルが付いている場合、層 番号について、 R1 の値は、層 番号の R2 の値より厳密に大きくなります。
  • 辺に open というラベルが付いている場合、層 番号について、 R1 の値は、層 番号の R2 の値以上になります。
注

ルール集合には、複数の階層化が存在する場合があります。 実装は、任意の階層化を、そのルール集合について使用できます。

4.4.1 層別化条件

層別化は、次の条件が 満たされる場合にのみ定義されます。ルールセットがこの条件を満たさない場合、 この仕様では、そのようなルールセットの評価結果を定義しません。

層別化条件
層別化条件では、 ルールセットの依存関係グラフに、 閉じた依存関係を含む 再帰的依存関係が 存在しないことが要求されます。
注記

層別化条件は、 層別化が存在するための条件そのものです。 ルールセットの層別化を形成できるための必要十分条件は、 そのルールセットの依存関係グラフ内のいかなる循環経路も 閉じた依存関係を含まないことです。

4.4.2 層別化アルゴリズム

次のアルゴリズムは、ルールセットのみに基づく 層別化の一例を示します。 

define stratification(ruleSet):

    let DP = Dependency graph for the rule set.
    let stratumMap be a map from rule to integer

    # 依存関係グラフは層別化条件を満たす必要があります。
    # 無制限の層別化のチェックは、
    # 層別化条件違反に対する保護です。
    let limit = num rules + 1
    let maxStratum = 0

    # stratumMap を初期化します
    foreach rule in ruleSet.rules:
        stratumMap.set(rule, 0)
    endfor

    boolean changed = true
    while changed:
        changed = false
        foreach edge E in DP:
            # pRule から qRule へのラベル付き辺
            let pRule = source of edge
            let qRule = destination of the edge
            let label = edge label

            if label == "open":
                if stratumMap.get(pRule) < stratumMap.get(qRule):
                    stratumMap.set(pRule, stratumMap.get(qRule))
                    changed = true
                endif
            endif
            if label == "closed":
                if stratumMap.get(pRule) <= stratumMap.get(qRule):
                    let xStratum = 1 + stratumMap.get(qRule)
                    if xStratum > limit:
                        # 層別化要件違反
                        error "Stratification error"
                    endif
                    stratumMap.set(pRule, xStratum)
                    maxStratum = max(maxStratum, xStratum)
                    changed = true
                endif
            endif
        endfor
    endwhile

    # 結果マップを初期化します。
    let stratumRules be a map from integer to rules.
    foreach i = 0 to maxStratum
        stratumRules.set(i, {})
    endfor

    # stratumMap 内で同じレベル番号を持つルールを集めます
    foreach rule R in map stratumMap:
        let stratumNum = stratumMap.get(R)
        add R to stratumRules.get(stratumNum)
    endfor

    # 各レベルを once と general に分割します
    let stratumLevels be a sequence of pairs of sets of rules.
    for i = 0 to maxStratum:
        let rules = stratumRules.get(i)
        let once = { R in rules | R is a run-once rule }
        let general = rules \ once
        stratumLevels.set(i, pair(once, general))
    endfor

    the result is stratumLevels
enddefine
注記

層別化条件の帰結として、 一度だけ実行されるルールが評価されると、 そのルールの結果を決定するために使用されたデータは、 その後の評価中に変化しません。

完全なルールセットに対して依存関係分析と 層別化を段階的に適用し、その後評価まで追跡する例は、 6.6 実例 に示されています。

4.5 インポートの処理

Web から文書を読み込むことには、セキュリティ上の影響がある。 ルールセットのインポートへの対応は、SPARQL-RL プロセッサーでは任意である。 さらに、実装は 任意で部分的なサポートを提供してもよく、 例えば、特定のルールセットのインポートのみをサポートし、他はサポートしないことや、 検証済みのコピーからのみインポートすることなどがある。

インポートの処理には、次の条件が適用される。

  • ルールセットのインポートをサポートしない実装は 必ず、 ルールセットに IMPORTS 文が含まれる場合、それを拒否し、 エラーを通知しなければならない。
  • 部分的なサポートを提供する実装は、 必ず、サポート対象外のインポートに遭遇した場合、 エラーを通知しなければならない。
  • 実装は 必ず、インポート対象の 文書を解決できない場合、 またはその文書が構文的に妥当でない場合に、エラーを通知しなければならない。
  • プロセッサーは 必ず、無限ループを防ぐため、ルールセットを一度だけインポートしなければならない （IMPORTS 文を処理する際）。

解決済みルールセットは、別のルールセットのインポートを基に、 そこに記載されたすべてのルールセットを再帰的に読み込むことにより、 その元となる ルールセットから生成される。

5. SPARQL-RL と SPARQL の関係

この節は非規範的です。

SRL と SPARQL は密接な関係にあります。SRL は互換性を持つように設計されており、 その対象は SPARQL で、SRL の多くの構成要素は、 SPARQL のパターンマッチングから取り入れられたか、着想を得たものです。ただし、いくつかの違いがあります。

SRL では、RULE 変数は使用前に常に束縛されます。使用箇所が FILTER または SET の式である場合も、トリプルテンプレートである場合も同様です。 これらが属するのは ルールヘッドです。SPARQL の CONSTRUCT クエリと INSERT 更新は、 変数が CONSTRUCT または INSERT テンプレートに現れても WHERE 節で値を与えられていない場合、部分的な結果を生成します。

  • 整形式性条件は、次のことを保証します。 変数は、少なくとも 1 つのトリプルパターン要素に現れるか、 または代入変数として現れます。 これは、フィルター要素または代入 要素で使用される前であり、 これらはルール本体内にあります。
  • SRL の SET 形式と SPARQL の BIND 形式は、 エラー処理の動作が異なります。SET で発生したエラーは、 現在の解を除外しますが、BIND は 現在の解の変数を設定せずに、その解を引き渡します。 SET(?var := expr) は、次のものと同等です。 SPARQL で BIND(expr AS ?var) の後に FILTER(BOUND(?var)) を続けたものです。
  • ルール本体の WHERE 節の構文には、 UNION または OPTIONAL 構文は含まれません。 これらの SPARQL 要素は、未束縛の変数を生じさせる可能性があります。 UNION または OPTIONAL の効果は、 整形式のルールを使用して実現できます。

その他の違いには、次のものがあります。

  • NOT の構文は、内部の本体をトリプル パターンとフィルターに制限し、入れ子のパターンを許可しません。 NOT は、ルール本体内の記述された位置でフィルターとして 実行され、SPARQL の FILTER NOT EXISTS とは異なります。
  • プロパティパス構文は、/ と ^ を使用するパスのみを対象とします。 これらはトリプルパターンに展開できます。 任意長の演算子 * と + は許可されません。 任意長のパスは、SPARQL-RL において、 より一般的な手法として再帰を使用して表現できます。
  • 一部の関数は SRL の構文に含まれません。 COALESCE と BOUND はありません。ハッシュ関数もありません。 RAND もありません。これは、呼び出されるたびに結果が 異なるためです。
    注
    NOW() は許可されており、同じ時点を返すように 定義されています。この時点は、ルール集合の評価全体を通じて変わりません。
  • BNODE を使用すると、呼び出しごとに異なる空白ノードが生成されます。 ルール集合の評価の結果として生成される推論グラフは、 グラフ同型になります。

  • UUID と STRUUID は、一意な識別子を生成するために使用できます。 ルールは、これらの生成された識別子を検査せず、 トリプルの生成にのみ使用するべきです。

    再現性をテストするために、専用の生成器を使用できます。 これは、NOW の結果をテストする場合と同様です。

6. ルールセットの評価

この節では、与えられたデータに対してルールセットを評価した結果を定義する。 実装はこのアルゴリズムを使用する必要はない。 実装は同じ結果を生成する任意のアルゴリズムを使用できる。 

入力: ベースグラフと呼ばれるグラフ G、およびルールセット RS。
出力: 推論されたトリプルからなる RDF グラフ GI

推論されたトリプルには、 ベースグラフに存在するトリプルは含まれない。

6.1 評価の定義

解写像
解写像 μ は、部分 関数 μ : V → Tです。 ここで、V はすべての変数の集合であり、 T はすべてのRDF 用語の集合です。 μ の定義域は、 dom(μ)で表され、 μ が定義されている V の部分集合です。 解という用語は、解写像を意味することが明らかな場合に使用できます。 μ0 は、 dom(μ0)が空集合となる解写像を表すものとします。
置換関数

置換関数、または単に置換は、 次の関数です。 subst(μ, トリプルパターン) この関数は、トリプルパターンを返します。 ここで、トリプルパターンに出現する各変数 var のうち、 dom(μ) に含まれるものは、RDF 用語に置き換えられます。これは、 解写像が var に対して与えるものです。 結果のトリプルパターンに変数がない場合、それは RDF トリプルです。

関数 subst(μ, トリプルテンプレート) も同様に定義されます。各変数の出現箇所について、 トリプルテンプレート内の変数は、RDF 用語に置き換えられます。これは、 解写像が var に対して与えるものです。

テンプレートインスタンス関数
テンプレートインスタンス関数は、次の関数です。 replaceBlankNodes(list of トリプルテンプレート) この関数は、 トリプルテンプレートのリストを返し、各空白ノードは、 引数内で新しい空白ノードに置き換えられます。 同じ空白ノードの複数の出現箇所は、 同じ新しい空白ノードに置き換えられます。
評価 グラフ
評価グラフは、RDF グラフであり、基底グラフ と、ルール集合の評価中に生成されたすべてのトリプルを組み合わせたものです。
グラフマッチ
グラフマッチは、トリプルパターンを トリプルに写像する方法を見つけます。対象は、RDF グラフ内のトリプルです。

G をRDF グラフ、TP をトリプルパターンとします。 関数 graphMatch(G, TP) は、可能なすべての 解の集合を返します。これらの解は、 トリプルパターンに適用すると、 グラフ G 内にあるトリプルを生成します。

G をRDF グラフ、TP をトリプルパターン、 V を TP に出現する変数の集合とします。 

graphMatch(G, TP) = { μ | dom(μ) = V and subst(μ, TP) is a triple in G }
解の互換性
2 つの解 S1 と S2 は、変数に対する値が一致する場合に互換です。対象は、 共通する変数です。

S1 と S2 を解とします。 

compatible(μ1, μ2) = true
                      if forall v in dom(μ1) intersection dom(μ2)
                          μ1(v) = μ2(v)
compatible(μ1, μ2) = false otherwise
解列
解列は、解の多重集合です。 この列には順序が定義されていません。 これは順序のないリストに相当し、重複を含むことができます。
解のマージ
2 つの解が互換である場合、2 つの解のマージは、 各解の変数をRDF 用語に写像する解です。 この RDF 用語は、いずれか一方の解に由来します。
μ1、μ2 を解写像、S1 と S2 を解列とします。 
merge(μ1, μ2) = μ such that
                    μ(v) = μ1(v) if v in dom(μ1)
                    μ(v) = μ2(v) otherwise
merge(S1, S2) = { μ |
                    μ1 in S1, μ2 in S2
                    and compatible(μ1, μ2)
                    μ = merge(μ1, μ2) }
注

merge(μ1, μ2)の定義域は、 domain(μ1) ∪ domain(μ2)です。

2 つの解に共通する変数がない場合、それらは互換であり、 2 つの解のマージは、 μ1 と μ2 の和集合です。

実効ブール値
関数 EBV(x) は、実効ブール値を返します。 対象は、RDF 用語です。

ルールは、解 列をルール本体から計算し、 次に各解写像を、その解列から使用して、 トリプルを生成することで評価されます。これにはルールヘッドを使用します。

ルール本体内では、トリプルパターン内の空白ノードは変数のように振る舞います。 これは、 SPARQL のグラフパターンマッチングと互換性があります。

空白ノードを変数として扱う
空白ノードは、トリプル パターン内で変数として扱われます。これは、 ルール本体内の各空白ノードを、 そのルールで使用されていない変数に置き換えることで行います。 これには、トリプル用語内の空白ノードの置換も含まれます。 同じ変数が、各出現箇所に使用されます。 これは同じ空白ノードの出現箇所であり、異なる変数が、 異なる空白ノードごとに使用されます。 
# ルール本体を評価する
# この関数は解の列を返す

define evalRuleElements(B, SEQ, G, GD):
    where
        B is a sequence of rule elements
        SEQ is a solution sequence
        G and GD are RDF graphs

    foreach rule element rElt in B:

        if rElt is a triple pattern element TP:
            X = graphMatch(G, TP)
            SEQ1 = {}
            foreach μ1 in X:
                foreach μ2 in SEQ:
                    if compatible(μ1, μ2):
                      μ3 = merge(μ1, μ2)
                      add μ3 to SEQ1
                    endif
                endfor
            endfor
        endif

        if rElt is a filter element F:
            SEQ1 = {}
            foreach solution μ in SEQ:
                let x = evalFunction(F.expr, μ)
                if x is not an error and EBV(x) is true:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is a negation element N:
            SEQ1 = {}
            foreach solution μ in SEQ:
                S = sequence{ μ }
                if N.evaldata:
                    NEG = evalRuleElements(N.inner, S, G, GD)
                else:
                    NEG = evalRuleElements(N.inner, S, GD, GD)
                endif
                if NEG is empty:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is an assignment element A:
            SEQ1 = {}
            foreach solution μ in SEQ:
                let x = evalFunction(A.expr, μ)
                if x is not an error:
                    # 写像 A.var -> x を解 μ に追加する
                    let μ2 be a solution mapping μ ∪ { (A.var, x) }
                    add μ2 to SEQ1
                else:
                    # エラー: 解 μ を破棄する
                endif
            endfor
        endif

        ## COUNT(*) はどうするか？
        if rElt is an aggregation element AGG:
            let SEQX = evalRuleElements(AGG.pattern, SEQ, G, GD)
            let KGRP = empty map of solution mappings to solution sequences
            # 解写像をグループに割り当てる。
            foreach solution μx in SEQX:
                let μk be μx restricted to AGG.grouping
                if KGRP[μk] is defined:
                    Add μx to the solution sequence KGRP[μk]
                else:
                    KGRP[μk] = solution sequence of one element μx
                endif
            endfor
            # 各グループについて、集約関数を計算し、
            # グループキーと
            # 集約代入の結果を含む解写像を作成する。
            let SEQ1 be an empty solution sequence
            foreach key K of map KGRP:
                let X be solution sequence of KGRP[K]
                let Z be an empty solution mapping
                foreach aggregation function F in AGG.assignments:
                    let V = calculate F.function(X)
                    add solution mapping (F.var, V) to Z
                endfor
                Z = merge(Z, K)
                add Z to SEQ1
            endfor
        endif
        SEQ = SEQ1
    endfor

    return SEQ
enddefine

define evalRule(R, G, GD):
    where
        R is a well-formed rule
        G and GD are RDF graphs
    let B be R.body
        treating blank nodes as variables.

    # どの変数も写像しない 1 つの解からなる解列。
    let SEQ0: Solution sequence = { μ0 }

    if R.evaldata:
        let SEQ = evalRuleElements(B, SEQ0, G, GD)
    else:
        let SEQ = evalRuleElements(B, SEQ0, GD, GD)
    endif

    # ルールヘッドを評価する
    let OUT = empty set
    foreach μ in SEQ:
        let S = {}
        # 各空白ノードを新しい空白ノードに置き換えたルールヘッド
        let HT = replaceBlankNodes(R.head)
        foreach triple template TT in HT
            let triple = subst(μ, TT)
            Add triple to S
        endfor
        OUT = OUT ∪ S
    endfor
    return OUT
enddefine

6.5 ルールセットの評価

ルールセットの評価は、そのルールセットの各 層を実行することとして定義される。 層化において、各層は 完全に実行され、 次の 層に進む前に、順番に処理される。 層は、まず その層の各 一度だけ実行されるルールを評価し、続いて 一般ルールを新しいトリプルが生成されなくなるまで繰り返し 評価することによって評価される。 

let G0 be the input base graph
let RS be the rule set

Apply stratification to RS

            let Y = { t ∈ X | t ∉ GE }

                finished = false
                GI = GI ∪ Y
                GE = GE ∪ Y

6.6.1 依存関係の 決定

各ルールボディ内の各トリプルパターンを、 すべてのルールヘッド内のトリプルテンプレートと比較して、 どのルールがどのルールに依存するかを決定します （4.3 ルールの 依存関係）。

  • R1 のボディは単一のトリプルパターン ?x :hasVulnerability ?v です。述語 :hasVulnerability を持つ トリプルを生成できるトリプルテンプレートを持つルールヘッドはないため、 このパターンはデータにのみ一致できます。 R1 には依存関係がありません。
  • R2 のボディには 2 つのトリプルパターンがあります。 ?x :dependsOn ?y はどのルールヘッドにも一致できないため、 データにのみ一致します。?y :exposedTo ?v は R1 のヘッドテンプレート ?x :exposedTo ?v と一致し、 R2 自身のヘッドにも一致します。 どちらもトリプルパターン要素であり、 （否定要素内には現れず、 R2 は 一度だけ実行されるルールでもないため）、 R2 は R1 に対して開いた依存関係を持ち、 自身に対しても開いた依存関係を持ちます。 R2 の自身に対する依存関係により、R2 は再帰的ルールになります。
  • R3 のボディでは、パターン ?x :exposedTo ?v が R1 と R2 のヘッドに一致するため、 R3 はそれぞれに対して開いた依存関係を持ちます。 パターン ?v :severity ?s はどのルールヘッドにも一致しません。
  • R4 のボディでは、パターン ?x rdf:type :Component は どのルールヘッドにも一致しません。述語 rdf:type を持つ唯一のヘッドテンプレートは R5 にあり、そのオブジェクト :Notification は :Component とは異なる RDF 項なので、生成された トリプルが一致することはありません。 パターン ?x :status :criticallyExposed は、 否定要素 NOT { ?x :status :criticallyExposed } 内に現れ、 R3 のヘッドテンプレートと一致します。このパターンは 否定要素内に現れるため、R4 は R3 に対して 閉じた依存関係を持ちます。
  • R5 のボディでは、パターン ?x :status :criticallyExposed が R3 のヘッドに一致します。R5 のヘッドには 空白ノードが含まれているため、R3 への依存関係は、 パターンが通常のトリプルパターン要素であっても、 閉じた依存関係です。 どのルールボディ内のパターンも R5 のヘッドテンプレートには一致しないため、 R5 に依存するルールはありません。

したがって、依存関係グラフには 5 つの頂点と 6 つの 辺があります。

  • R2 → R1 (open)
  • R2 → R2 (open)
  • R3 → R1 (open)
  • R3 → R2 (open)
  • R4 → R3 (closed)
  • R5 → R3 (closed)

R4 と R5 は R1 または R2 に直接依存していませんが、それぞれ R3 を介して両方に 推移的依存関係を持ちます。

グラフ内の唯一の循環は自己辺 R2 → R2 であり、 これは開いた依存関係です。閉じた依存関係を含む循環はないため、 層別化条件は 満たされ、 ルールセットには明確に定義された結果があります。

6.6.2 層別化の 計算

層別化アルゴリズムに従い、 すべてのルールは層 0 から開始します。その後、変化がなくなるまで 辺を繰り返し調べます。

  • 開いた辺では、始点のルールが 終点と同じ層か、それより高い層にある必要があります。 4 つの開いた辺はいずれも、すべてのルールが層 0 にある状態ですでに この条件を満たしているため、変更は生じません。
  • 閉じた辺では、始点のルールが 終点より厳密に高い層にある必要があります。これは、終点が 先に完了まで実行されなければならないためです。辺 R4 → R3 (closed) では、R4 と R3 がどちらも層 0 にあるため、 R4 は層 1 に移動します。同様に、辺 R5 → R3 (closed) により R5 も層 1 に移動します。

さらに辺を一巡しても変更は生じないため、層は確定します。 次に各層を一度だけ実行されるルールと一般ルールに分割します。 R5 はヘッドに空白 ノードを持つため、一度だけ実行されるルールです。 ルールセット内の他のルールはいずれも一度だけ実行されるルールではありません。 層別化は次のとおりです。

  • 層 0: 一般ルール R1、R2、R3。一度だけ実行されるルールはなし
  • 層 1: 一度だけ実行される R5。一般ルール R4

この順序付けは、より高い層にあるルールの意図を反映しています。 コンポーネントを安全にデプロイできるかどうか、および どのコンポーネントに通知が必要かは、 すべての :status :criticallyExposed トリプルが導出された後でのみ決定できます。 そして、それらを導出するルール R3 は、 それに入力を与えるルール R1 および R2 とともに その下の層で完了します。

6.6.3 各層の評価

評価は、 6.5 ルールセットの 評価のアルゴリズムに従います。 評価グラフ GE はベースグラフとして開始し、 推論グラフ GI は空で開始します。各層は順番に完了まで評価されます。 層内のルールはパスごとに評価され、 新しいトリプルを生成しないパスになるまでパスを繰り返します。 このアルゴリズムでは、パス内で層のルールを評価する順序は 規定されていません。この追跡では R1、R2、R3 の順序を使用します。 異なる順序では、同じ推論が異なる数のパスに分散する可能性がありますが、 層 0 は完了まで実行されるため、最終的には同じグラフが生成されます。

このルールセットには DATA ブロックがないため、評価中のすべての時点で GE は G0 と GI の和集合です。したがって、この追跡では GI のみを追跡し、評価の進行に伴う状態を示すとともに、 各新しいトリプルに、それを生成したルールを示します。

層 0、第 1 パス。

  • R1: ボディは :db :hasVulnerability :vuln1 に一致し、 ?x = :db および ?v = :vuln1 を束縛します。 ヘッドは :db :exposedTo :vuln1 を生成します。 このトリプルは GE にないため、GE と GI に追加されます。
  • R2: ボディは ?x :dependsOn ?y と ?y :exposedTo ?v を結合します。GE には現在 :db :exposedTo :vuln1 が含まれているため、結合によって 1 つのソリューション、 ?x = :app、?y = :db、?v = :vuln1 （:app :dependsOn :db から）が得られます。 ヘッドは :app :exposedTo :vuln1 を生成し、これは新しいため 追加されます。:frontend のソリューションはまだありません。 この R2 の評価が開始された時点では、 :app :exposedTo :vuln1 が GE に存在しなかったためです。
  • R3: ?x :exposedTo ?v は現在 :db と :app に一致します。 :vuln1 :severity 9.1 と結合し、 FILTER(?s >= 9.0) を適用すると、両方のソリューションが保持されます。 ヘッドは :db :status :criticallyExposed と :app :status :criticallyExposed を生成し、どちらも新しいものです。

7. SPARQL-RL 文法

SPARQL-RL 文書 は、RDF 文字列であり、UTF-8 [RFC3629] で符号化され、 RuleSet 生成規則から始まり、次で定義されている追加の制約に適合します。 7.6 文法。 Unicode スカラー値のみが、 U+0000 から U+D7FF の範囲 および U+E000 から U+10FFFF の範囲で 許可されます。これにより、 サロゲートコードポイントの、 U+D800 から U+DFFF の範囲が除外されます。

B. インポートのアルゴリズム例

この節は非規範的である。

次のアルゴリズムは、参照されるすべての文書を再帰的に 訪問することで IMPORTS 文を解決する方法の一例を示す。

2つのルールセットの ルールセットのマージは、RS1 と RS2 について、 次のように定義されるルールセット MR を生成する。 

let RS be a rule set
let V = {}
if RS has a location:
    V = { location of RS }
endif

define ruleSetMerge(rule set RS1, rule set RS2):
    let MR be a rule set
    MR.rules = RS1.rules ∪ RS2.rules
    MR.data = rdf_merge(RS1.data, RS2.data)
    MR.imports = {}
    the result is MR
enddefine

define imports(rule set RS):
    let RS2 be a rule set formed from RS.rules and RS.data
    foreach URL x in RS.imports:
        if x ∉ V:
            V = V ∪ { x }
            read rule set RS3 from URL x
            RS2 = ruleSetMerge(RS2, imports(RS3))
        endif
    endfor
    the result is RS2
enddefine

result is imports(RS)

D. セキュリティに関する考慮事項

この節は非規範的である。

SPARQL-RL 文書には、他の SPARQL-RL 文書を参照し、その内容を現在の 文書にインポートする IMPORTS 文が含まれる場合がある。 インポートされた文書自体に IMPORTS 文が含まれている場合、 それらの文書もインポートされる。

ルールセットのモジュール化には有用であるが、IMPORTS 文の使用は セキュリティリスクをもたらす可能性がある。 リスクには、悪意によるものか偶発的なものかを問わず、ルールセットが 評価中に過剰な計算を引き起こすことや、 HTTP リクエストが傍受され、古いコピーを含む 別の文書が返されることなどが含まれるが、これらに限定されない。

SPARQL-RL ルールセットを RDF グラフに適用すると、 大量の計算処理やメモリー使用が発生する可能性があり、これが悪用されて サービス拒否を引き起こすおそれがある。 アプリケーションは、SPARQL-RL ルールセットの適用によって発生する 計算量とメモリー使用量を制限するよう注意するべきである。

SPARQL-RL 構文は UTF-8 [RFC3629] で符号化され、 文字列データ内で エスケープされていない制御文字の使用を許容する。 この仕様はその内容をエンドユーザーに直接公開しないが、 ユーザーエージェントを通じて表示される場合があり、そのような文字によって 表示されるテキストが誤解を招くものになる可能性がある。

SPARQL-RL は、任意のアプリケーションデータの処理と作成に使用できる。 セキュリティに関する考慮事項は、使用分野によって異なる。 テキストに適用できるセキュリティツールやプロトコル （例えば、PGP 暗号化、チェックサム検証、パスワード保護された圧縮）は、 SPARQL-RL 文書にも使用できる。 SPARQL-RL ルールセットの評価結果に含まれる情報の機密性に応じて、 セキュリティおよびプライバシーのプロトコルを適用しなければならない。

SPARQL-RL のセキュリティに関する考慮事項には、 RDF データや、 RDF Turtleなどの形式に関するものも含まれる。

E. プライバシーに関する考慮事項

この節は非規範的である。

SPARQL-RL 文書には、追加のアプリケーションデータが含まれる場合があり、 その中には個人を特定できる情報（PII）や、 その他の機密性が高いと見なされる情報が含まれる可能性がある。 このような情報を含むルールセットを公開する著者には、 そのような情報を公開する必要性や用途、 および、そのデータが利用され、場合によっては開示されると 想定される地域に適用される規制（例えば、 GDPR、 CCPA、 その他）を慎重に検討することが推奨される。 特に、そのデータへのアクセスに認可措置が必要かどうかを検討するべきである。
