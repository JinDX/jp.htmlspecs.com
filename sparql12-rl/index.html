概要

この文書は、RDF 向けの Datalog 形式のルール言語である SPARQL-RL を定義します。

SPARQL-RL は、入力 RDF グラフに対して宣言的な ルールの集合を評価することにより、新しい RDF データを生成します。ルールは SPARQL に似たテキスト構文で記述されます。

この仕様は、 W3C Data Shapes ワーキンググループによって公開されています。

1. 序論

この文書では SPARQL-RL を紹介します。これは、宣言的なルールを通じて 既存の RDF データから新しい RDF トリプルを導出するための仕組みです。 この文書では、ルールベース推論の構文と意味論を定義します。

SPARQL-RL の実装は、infer および query の 一方または両方の操作を提供します。 infer 操作は、指定された ベースグラフにルールを適用し、ベースグラフには現れない、 ルール評価によって導出された RDF トリプルを含む推論グラフを生成します。 推論グラフとベースグラフを結合するかどうかは任意であり、 ユーザーに委ねられます。 query 操作は、指定されたゴールパターンが、 ルールを使用してベースグラフから導出できるかどうか、およびどのように導出できるかを 判定します。

SPARQL-RL では、空白ノードを含む新しい RDF 項を作成でき、 それらをルールのヘッド内のトリプルテンプレートで使用できます。

SPARQL-RL は失敗による否定もサポートしており、ルールを 評価する順序によって異なる推論グラフが生じる可能性があります。 これを避けるため、ルールは層別化という手法を使用して評価されます。 これはルール間に順序を確立し、 常に同じ推論グラフが生成されることを保証します。

文脈が明確な場合、SPARQL-RL は SRL と呼ぶことができます。

3. SPARQL-RL の概要

この節は非規範的です。

SPARQL-RL は、ベースグラフとルールセットを与えると、新しいトリプルを推論します。 評価の出力は、ベースグラフには現れない導出された トリプルを含む推論グラフです。

各ルールには、ボディと呼ばれるパターンと、 ヘッドと呼ばれる結果テンプレートがあります。 ルールは、ボディが結合されたベースグラフおよび その時点までの実行によって推論されたトリプルに一致するように、 ボディ内の変数の値を見つけることで実行されます。 次に、これらの値を使用してルールヘッド内のトリプルテンプレートを インスタンス化し、新しい推論トリプルを生成します。

それ以上トリプルが推論されなくなるまでルールが実行され、 新しい推論トリプルが利用可能になるにつれて、ルールは複数回 実行されることがあります。

SPARQL-RL の実行は、新しい空白ノードを含む 新しい RDF 項を作成する場合や、パターンが存在しないことを テストする場合に、ルールの実行順序によって異なる結果が 生じないように定義されています。言い換えると、ルールの実行順序に 関係なく同じ推論グラフが生成されます。

SPARQL-RL には、SPARQL 1.2 クエリ言語から着想を得た、 人間に扱いやすい構文があります。 ルールセットの評価には SPARQL と類似した要素が含まれますが、 ルールの実行順序に関係なく同じ推論グラフが生成されることを 保証するため、細部には相違があります。

この節の例では、ソフトウェアコンポーネントと その依存関係について説明します。フロントエンドがアプリケーションサーバーを呼び出し、 アプリケーションサーバーは既知の脆弱性を持つ データベースにクエリを行います。

3.1 トリプルパターン

トリプルパターンはトリプルデータと照合され、 変数に値を与えます。このパターンには 3 つの要素があり、それぞれ RDF 項、変数、 または変数を含むトリプル項のパターンです。

この最初の例では、ベースグラフとルールセットに次のデータがあります。

例 1: 基本的な例 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
:frontend :dependsOn :app .
:app      :dependsOn :db .

上記のルールをデータに適用すると、 :frontend は :app に依存し、:app は :db に依存すると結論付けられます。これは依存関係の種類に関係ありません。

次に、他のルールによって生成された :dependsOn トリプルに 依存するルールを追加することで、:exposedTo 関係を導出できます （以下の4.3 ルールの 依存関係も参照してください）。

例 2: 推論されたトリプルへの依存 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
:app      :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

3.2 再帰

前節の :exposedTo ルールが到達するのは直接の 依存関係だけです。:frontend は :db に直接依存していないため、 :frontend について :exposedTo トリプルは推論されません。 任意の長さの依存関係チェーンに沿って露出を伝播させるため、 そのルールを 2 つのルールに置き換えます。コンポーネントは自身が持つ 脆弱性にさらされ、さらにコンポーネントは、その直接の依存先がさらされている あらゆる脆弱性にさらされます。

例 3: ルールの再帰 
:frontend :callsService :app .
:app      :queriesDatabase :db .
:db       :hasVulnerability :vuln1 .
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }
RULE { ?x :dependsOn ?y } WHERE { ?x :queriesDatabase ?y }
RULE { ?x :exposedTo ?v } WHERE { ?x :hasVulnerability ?v }
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :exposedTo ?v }
:db       :exposedTo :vuln1 .
:app      :exposedTo :vuln1 .
:frontend :exposedTo :vuln1 .
:frontend :dependsOn :app .
:app      :dependsOn :db .

前の例と比較すると、ここでは :db :exposedTo :vuln1 — データベースは自身の 脆弱性にさらされています — と :frontend :exposedTo :vuln1 が追加されます。 露出は、チェーンがどれほど長くても、依存関係の チェーンを通じて :frontend に到達します。

この最後のルールは再帰的なルールです。ルールのボディが そのルールのヘッドに依存しています。

3.3 フィルタリング

ルールのボディ内で式を使用して、ボディの照合時に 変数の値を制限できます。 たとえば、各脆弱性の重大度が与えられている場合、 深刻な脆弱性にさらされているコンポーネントに ステータスを付与できます。

例 4: フィルタリング 
:app1 :exposedTo :vuln1 .
:app2 :exposedTo :vuln2 .
:vuln1 :severity 9.1 .
:vuln2 :severity 4.3 .
RULE { ?x :status :criticallyExposed }
WHERE {
    ?x :exposedTo ?v .
    ?v :severity ?s .
    FILTER(?s >= 9.0)
}
:app1 :status :criticallyExposed .

FILTER は式を評価し、式が true と評価された場合は現在の 変数バインディングの集合を保持し、式が false と評価された場合は 現在の変数バインディングの集合を破棄します。 これは SPARQL の FILTER 操作 と同じであり、SPARQL-RL は SPARQL と同じ関数および演算子の多くを提供します。

3.4 否定

否定は、一致してはならないパターンを指定するために使用されます。 これは「失敗による否定」と呼ばれます。

否定要素を評価するため、ルールセット評価アルゴリズムは、 否定要素内のパターンに一致するトリプルを生成し得るすべてのルールが 完了していることを保証します。これは 層別化と呼ばれ、否定が データ由来か他のルール由来かにかかわらず、関連する可能性のある すべてのトリプルに基づくことを保証します。否定を含むルールは、 これらのトリプルを生成するルールに依存するといいます （以下の4.3 ルールの 依存関係を参照してください）。

例 5: 失敗による否定 
:app rdf:type :Component ;
    :status :criticallyExposed .

:logger rdf:type :Component .
RULE { ?x :status :safeToDeploy }
WHERE {
    ?x rdf:type :Component .
    NOT { ?x :status :criticallyExposed }
}
:logger :status :safeToDeploy .

3.5 代入と RDF 項の作成

代入により、式の結果をルールのボディ内の変数に 代入できます。これは、データに基づいて新しい RDF 項を作成するために 使用できます。

例 6: 代入 
RULE { ?v :riskScore ?r }
WHERE {
    ?v :severity ?s .
    ?v :exploitLikelihood ?p .
    SET ( ?r := ?s * ?p )
}

空白ノードはルールヘッド内で使用でき、ルール評価によってトリプルが生成される たびに、それぞれ新しい空白ノードが生成されます。

例 7: ルールヘッド内の空白ノード 
RULE { [] rdf:type :Notification ; :concerns ?x }
WHERE { ?x :status :criticallyExposed }

代入を含むルール、空白ノードを作成するルール、 ルールヘッドの評価によるもの、およびテンプレートを持つルールで、 トリプル項を含み、そこに変数が含まれるものは、 一度だけ実行されるルールです。 このようなルールは、それらが依存するデータを生成し得るすべてのルールの後に実行され、 それらが生成するデータに依存するあらゆるルールの前に実行されます。

この条件により、このようなルールが自身に循環して戻り、 無制限の数の RDF 項を作成することを防ぎます。

注記

ルールヘッド内の定数RDF 項は、その項が ベースグラフに現れない場合であっても、ルールを 一度だけ実行されるルールにはしません。ルールは評価されるたびに同じ項を追加するため、 追加できる項の数は有限です。

代入内の式を評価してエラーが発生した場合、 現在のソリューションマッピングは代入によって拒否されます。

3.6 ルールセットのインポート

SPARQL-RL のルールセットは、他のルールセットの URL を そのルールセットのルールセットインポートに含めることで、 他のルールセットを組み込むことができます。 これにより、ルールをルールセット間で共有されるライブラリとして構成できます。

ルールセットの IMPORTS 文は、ルールセット内のいずれかのルールが 評価される前に処理されます。インポート手順中、インポートされたルールセットが 独自のインポートを持つ場合、それらも再帰的に処理されます。 ルールセットの処理中に IMPORTS 文をたどると、 循環インポートに遭遇することがあります。ルールセットがインポートされるのは一度だけであり、 インポート文グラフ内の循環によって無限ループが生じることはありません。

ルールセットのインポートのサポートは、SPARQL-RL プロセッサでは任意です。 詳細については、4.5 インポートの 処理を参照してください。

3.7 データブロック

データブロックを使用すると、RDF トリプルをルールセット評価に直接簡潔に提供できます。 データブロック内のトリプルは推論グラフに追加され、 ルールのボディ内での照合に使用できます。

たとえば、ルールセットには、データから導出する代わりに、 既知の事実を直接表明して含めることができます。

例 8: ルールセットにデータを含める 
DATA {
    # バージョン 2.0.0 以前には既知の脆弱性があり
    # 深刻にさらされていると見なされます。
    :appV2 rdf:type :Component ;
           :version "2.0.0" ;
           :status :criticallyExposed .
}
注記

データブロックは、空のボディを持つルールと等価です。 そのトリプルは、いかなるルールも評価されることなく 推論グラフの一部となります。

3.8 ルールセットの評価

ルールはルールセットに編成されます。 ルールセットとデータグラフ（ベースグラフ）が評価への入力です。 出力は推論グラフと呼ばれるグラフで、 評価プロセスによって生成された、ベースグラフには現れないトリプルの集合です。

評価中、あるルールに基づいて推論されたトリプルは、 他のルールでの照合に利用できます。 ルールセット評価は、推論グラフが ルールセットとベースグラフの入力から 得られるすべての可能なトリプルを含むまで続行されます。

評価は、ルールそのものが評価される前に ルールセットを準備する 手順から始まります。

  1. サポートされている場合、入力ルールセットのインポートを解決し、 インポートされたすべてのルールセットのすべてのルールを含む ルールセットを形成します。 いずれかのインポートがプロセッサに受け入れられない場合、 プロセッサはエラーを通知します（4.5 インポートの処理）。
  2. 各ルールが整形式のルールであることを確認します。
  3. 依存関係グラフを計算します。
  4. 層別化を計算し （4.4 層別化）、 否定要素と一度だけ実行されるルールが、一貫性のある 予測可能な結果を生成するようにします。層別化では、ルール間の 依存関係 （4.3.1 依存関係 グラフ）を調べます。

ルールセットの準備が完了すると、評価は 層別化の各層を順番に取得し、 その層内のルールを完了するまで評価してから、 次の層へ進むことで行われます。

3.9 ベースデータの照合

ルールセット評価中には、 推論されたトリプルではなく、元のベースグラフだけを パターン照合する必要がある場合があります。

この例の一つが、デフォルト値の設定です。 ルールは、ベースグラフにすでに値が含まれているかどうかをテストし、含まれていない場合は、 デフォルト値を計算できます。

例 9: NOT を使用したベースデータ 
:A :distanceMiles 5 .
:A :distanceKilometers 8 .
:B :distanceMiles 10 .
RULE  { ?x :distanceKilometers ?kilometers }
WHERE {
    ?x :distanceMiles ?miles .
    NOT DATA { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?miles *  1.60934))
}
:B :distanceKilometers 16 .

NOT DATA を使用すると、ルールボディの他の部分は推論されたトリプルに照合できます。 また、WHERE DATA を使用することで、すべてのルールボディの照合をベースグラフに対して行うこともできます。 そのようなルールは、ベースグラフからの照合だけに依存します。

例 10: WHERE を使用したベースデータ 
RULE  { ?x :distanceKilometers ?kilometers }
WHERE DATA {
    ?x :distanceMiles ?originalMiles .
    NOT { ?x :distanceKilometers ?km }
    SET ( ?kilometers := xsd:integer(?originalMiles *  1.60934))
}
注記

この節の照合はベースグラフに対して行われます。 これには、 ルールセットの DATA ブロックから ルールセット評価によって追加されたトリプルは含まれません （3.7 データブロック）。

4. SPARQL-RL 抽象構文

SPARQL-RL 抽象構文は、SPARQL-RL の論理構造です。 これは SPARQL-RL の実行アルゴリズムを定義するために使用されます。

4.1 抽象構文の 要素

変数
変数は、トリプルパターン内の可能なRDF 項を表します。 変数は式でも使用されます。
式
式とは、RDF 項、変数、 または関数もしくは関数形式の引数への適用であり、 各引数自体も式です。 式はソリューションマッピングに関して評価され、 結果としてRDF 項を与えるか、評価が エラーになります。 式は SPARQL 式と互換性があります。
データブロック
データブロックはトリプルの集合です。 これらのトリプルは追加の事実として推論グラフに追加され、 推論プロセスに含まれます。
トリプルパターン
トリプルパターンは 3-タプルであり、各要素は 変数、RDF 項、または トリプル項の、変数を含むパターンです。 タプルの第 2 要素は、IRIまたは 変数でなければなりません。 トリプルパターンはボディ内のルールに現れ、 RDF トリプルの照合に使用されます。
トリプルテンプレート

トリプルテンプレートは 3-タプルであり、各要素は 変数、RDF 項、または トリプル項の、変数を含むテンプレートです。 タプルの第 2 要素は、IRI または変数でなければなりません。 トリプルテンプレートはヘッド内のルールに現れ、 RDF トリプルの生成に使用されます。

注記

トリプル項のパターンまたはテンプレートで、 変数が一つも現れないものは、トリプル項であり、したがって RDF 項でもあります。

フィルター要素
フィルター要素は、式であり、 ルール要素として現れます。 これは、パターン照合における変数の値を 制限するために使用されます。
トリプルパターン要素
トリプルパターン要素は、トリプルパターンであり、 ルール要素として現れます。
否定要素
否定要素は、ルール要素です。 これは、トリプルパターン要素と フィルター要素のシーケンスから構成される 否定要素のボディを持ちます。 否定要素には、フラグ .evaldataがあり、 否定要素のボディの照合にどのグラフを使用するかを 示します。
代入 要素
代入要素は、 ルール要素であり、 変数（代入変数と呼ばれる）と、 式（代入式と呼ばれる）からなる ペアです。
ルール要素
ルール要素は、 トリプルパターン要素、 フィルター要素、 否定要素、または 代入要素のいずれかです。
ルールヘッド
ルールヘッドは、トリプル テンプレートのシーケンスです。
ルールボディ
ルールボディは、ルール要素のシーケンスです。 つまり、シーケンスの各要素は、 トリプルパターン要素、 フィルター要素、 否定要素、 または代入要素のいずれかです。
ルールセットのインポート
ルールセットのインポート（単に「インポート」と呼ばれることもあります）は、 評価中に含められる他のルールセットに対する IMPORTS 文の URL の集合です。
ルール
ルールは、ルールヘッド（単に 「ヘッド」と呼ばれることもあります）、 ルールボディ（単に「ボディ」と呼ばれることもあります）、 およびボディ内のトリプルパターンの照合にどのグラフを使用するかを示す フラグ .evaldataを含みます。 ルールには、その識別を補助するために URI または空白ノードを指定できます。
一度だけ実行されるルール

一度だけ実行されるルールとは、ルールセットの評価における 特定の時点で正確に一度だけ実行されるルールです。 ルールは、次のいずれかが成立する場合、 一度だけ実行される ルールです。

  • ルールボディに代入要素がある。
  • ルールヘッドのトリプルテンプレートに空白ノードがある。
  • ルールヘッドのトリプルテンプレートに、 トリプル項のテンプレートがあり、その中に変数が現れる。
一般ルール
一般ルールは、一度だけ実行されるルールではないルールです。 一般ルールは、ルールセット評価中に複数回実行されることがあります。
ルールセット
ルールセットは、0 個以上のルールの集合、 0 個以上のデータブロックの集合、 および 0 個以上のルールセットのインポートの集合です。 解決済み ルールセットとは、インポートを持たないルールセットです。 解決済みルールセットは、別のルールセットに インポートプロセスを適用することで作成されます。
ベースグラフ
ベースグラフは、評価プロセスへの入力として与えられるRDF グラフです。
推論 グラフ
推論グラフは、 ルールセット評価によって生成されるRDF グラフです。 これは、ルールセットをベースグラフに適用することで推論された、 ベースグラフには存在しないすべての推論トリプルを 含みます。
ルールセット 評価
ルールセット評価は、ルールセットを ベースグラフに適用して推論 グラフを生成するプロセスです。 ルール 評価とは、ルールを一度評価するプロセスです。 ルールを評価すると、トリプルがベースグラフ内にあるか、ルールセット評価中にすでに推論されているか、 または新しく推論されたトリプルであるかにかかわらず、 ルールボディの評価によって ルールヘッドが与えるすべてのトリプルが生成されます。 ルールセット評価中、ルールは複数回 評価されることがあります。

SPARQL-RL は、infer と query という 2 つの操作を提供します。

Infer
Infer は、ルールセットを指定された ベースグラフに適用し、推論されたトリプルを含む推論グラフを生成する操作です。 完全なルールセット評価を適用します。
Query

Query は、指定されたパターンがベースグラフからルールセットを使用して導出できるかどうかを判定し、 各ソリューションマッピングが 変数に RDF 項を与えるソリューションシーケンスを返す操作です。

Query は、infer 操作を実行し、 続いてゴールパターンを、結合された ベースグラフと推論 グラフに照合する効果を持ちます。

query 操作は、すべてのルールを評価しない場合があります。代わりに、 クエリのゴールに答えるために必要なルールだけを評価することがあります。

SPARQL-RL プロセッサ
SPARQL-RL プロセッサは、 SPARQL-RL 仕様を実装し、ルールセットを評価でき、 infer と query の一方または両方の操作を提供するシステムです。

トリプルパターンまたはトリプル テンプレートでは、 タプルの位置 1 は非形式的に主語、 位置 2 は非形式的に述語、 位置 3 は非形式的に目的語と呼ばれます。

注記

ルール要素のシーケンス内の要素には、1 から始まるラベルが付けられます。

4.2 整形式条件

整形式性は、 ルールセットの抽象構文に対する条件の集合です。これらの条件を合わせることで、 ルールのヘッド内の変数に、そのルールのボディ内で定義された値があること、 フィルター要素 または代入式内の各変数が 評価時点で値を持つこと、 およびルール内の各代入が、ルールボディのそれ以前で使用されていない 新しい変数を導入することを保証します。

初期変数集合が与えられたルール要素のシーケンスについて、 整形式性を定義します。

elti を、ルール要素のシーケンスの i 番目の要素とします。

varsi を、 elti によって定義される変数の集合として、次のように定めます。

  • elti がトリプルパターン要素である場合、
    • varsi は、そのトリプルパターン 要素に現れる変数の集合です。
  • elti が代入要素である場合、
    • varsi は、代入変数の集合です。
  • それ以外の場合、
    • varsi は空集合です。

V0 を、シーケンスの初期変数とします。

Vi を、V0 と、 j が 1 から i までのすべての varsj の 和集合とします。

Vall を VN の値とします。 ここで N はシーケンスの長さです。

整形式 シーケンスとは、変数の集合 V0 が与えられた ルール要素のシーケンスであり、 1 から N までの各 i について 次の条件を満たすものです。

  • elti がフィルター 要素である場合、
    • フィルター要素で言及されるすべての変数が Vi-1 の要素である。
  • elti が代入要素である場合、
    • 代入式で言及されるすべての変数が Vi-1 の要素である。
    • 代入変数が Vi-1 の要素ではない。
  • elti が否定要素である場合、
    • 否定要素の ボディ内のルール要素のシーケンスが、 整形式 シーケンスであり、 V0 を ルール要素の Vi-1 の値に設定する。

ルールが整形式の ルールであるのは、 ルールボディのルール要素のシーケンスが、 V0 を空集合として開始する 整形式シーケンスであり、 かつルールヘッドのトリプルテンプレート内の各変数が Vall の要素である場合です。

ルールセットが整形式のルールセットであるための必要十分条件は、 そのルールセットのすべてのルールが整形式のルールであることです。

4.3 ルールの依存関係

2 番目のルールの出力が 1 番目のルールのボディの評価に影響する場合、 ルール R1 はルール R2 に依存します。すなわち、R2 のヘッドに、 R1 のボディ内のトリプルパターンと一致するトリプルを生成できる トリプルテンプレートがあり、 そのトリプルパターンがトリプルパターン要素として、または否定要素内に存在する場合です。

依存関係には 2 種類あります。 閉じた依存関係と開いた 依存関係です。 閉じた依存関係は、ルール R1 が実行される前に、 ルール R2 が可能なすべての出力を生成済みであることを保証します。 ルールの依存関係が閉じていない場合、それは開いた依存関係であり、 1 番目のルール R1 を実行できる一方で、 ルール R2 はさらにトリプルを生成するために再度実行される可能性があり、 その新しいトリプルによって R1 が再評価される場合があります。

フラグ .evaldata が false に設定されたルールは、 ベースグラフを使用して照合を行い、そのルールには依存関係がありません。

この最初の例では、1 番目のルールは 2 番目のルールに対して 開いた依存関係を持ちます。

例 11: 開いた依存関係 
RULE { ?x :exposedTo ?v } WHERE { ?x :dependsOn ?y . ?y :hasVulnerability ?v }
RULE { ?x :dependsOn ?y } WHERE { ?x :callsService ?y }

この 2 番目の例では、1 番目のルールは 2 番目のルールに対して 閉じた依存関係を持ちます。トリプルパターン ?x :status :criticallyExposed は 1 番目のルールの否定要素内に現れ、 2 番目のルールのヘッド内のトリプルテンプレートと一致します。 1 番目のルールは、2 番目のルールが可能なすべての出力を 生成し終えるまで評価できません。

例 12: 閉じた依存関係 
RULE { ?x :status :safeToDeploy }
WHERE { ?x rdf:type :Component . NOT { ?x :status :criticallyExposed } }

RULE { ?x :status :criticallyExposed } WHERE { ?x :exposedTo ?v }
トリプルパターンの照合

トリプルパターンがトリプルテンプレートと一致するのは、 そのトリプルテンプレートが、そのトリプルパターンに一致するトリプルを生成できる場合です。

トリプルパターンの依存関係

トリプルパターンが トリプルテンプレートに 依存するのは、 そのトリプルパターンが そのトリプルテンプレートと 一致できる場合です。

ルールの依存関係

R1.evaldata が true であり、R1 のボディ内の いずれかのトリプル パターンが、 トリプルパターン要素としてであれ、 neg.evaldata が true である 否定要素 neg 内であれ、 R2 のヘッド内のトリプルテンプレートに 依存する場合、ルール R1 は ルール R2 に依存 します。

閉じた依存関係

ルール R1 のルール R2 に対する ルールの依存関係が 閉じた依存関係であるのは、 次の条件のいずれかが成立する場合です。

  • R1 の否定要素内に現れるトリプルパターンで、 その否定要素のフラグ .evaldata が true であるものが、 R2 のルールヘッド内のトリプルテンプレートと一致する。
  • ルール R1 がルール R2 に依存し、 かつ R1 が一度だけ実行されるルールである。
開いた依存関係

ルール R1 のルール R2 に対する ルールの依存関係が、 閉じた依存関係ではない場合、その依存関係は 開いた依存関係です。

トリプルテンプレートが RDF トリプル T1 を 生成できるのは、 トリプルテンプレートの変数に対する値が存在し、 テンプレート内の変数を値で置換することでトリプル T2 が得られ、 T2 が T1 と等しい場合です。

同様に、トリプルパターンがトリプル T1 と 一致するのは、 トリプルパターンの変数に対する値が存在し、 パターン内の変数をその値で置換することでトリプル T2 が得られ、 T2 が T1 と等しい場合です。

トリプル テンプレート またはトリプルパターン内で変数が複数回使用される場合、 置換には同じ RDF 項が使用されます。

トリプルパターン内の変数を RDF 項で置換することには、 トリプル項内の変数を置換することも含まれます。

4.3.1 依存関係グラフ

ルール間の依存関係は、依存関係グラフと呼ばれる有向グラフとして表されます。 グラフの頂点はルールセットのルールであり、辺には、 依存関係が開いた依存関係か閉じた依存関係かに応じて、 open または closed のラベルが付けられます。

依存関係グラフ
ルールセットの 依存関係グラフは、 各頂点がルールセット内のルールであり、 R1 が R2 に依存する場合にルール R1 から ルール R2 への辺が存在する有向グラフです。 その辺には、依存関係が 開いた依存関係か閉じた依存関係かに応じて、 open または closed のラベルが付けられます。
推移的ルール依存関係
ルール R1 からルール R2 への経路が 依存関係グラフ内に存在する場合、 ルール R1 はルール R2 に 推移的依存関係を持ちます。
再帰的ルール依存関係

R を含む循環経路が 依存関係グラフ内に存在する場合、 ルール R は再帰的依存関係を持ちます。

注記

依存関係グラフはベースグラフの影響を受けません。

4.3.2 依存関係グラフのアルゴリズム

次のアルゴリズムは、ルールセットから依存関係 グラフを構築する方法の一例を示します。 適合性は、依存関係グラフの定義を満たす依存関係グラフを生成することに依存し、 この手順を使用することには依存しません。 

define mergeLabel(oldLabel, newLabel):
    # 閉じた依存関係は開いた依存関係より優先されます。
    if oldLabel == "open" and newLabel == "open":
        the result is "open"
    else:
        the result is "closed"
    endif
enddefine

# 出力 -- ルールの頂点とラベル付き辺を持つ依存関係グラフ。
define buildDependencyGraph(ruleSet):
    # edgeLabelMap は (R1, R2) を "open" または "closed" に対応付けます
    let edgeLabelMap be a map from pair (rule, rule) to label

    foreach rule R1 in ruleSet.rules:
        let bodyDependencies = {}

        if R1.evaldata then:
            # ルール内の各トリプルパターン TP を、"open" または "closed" が必要なものとして分類します
            # これは、そのパターンが否定要素内にあるかどうかによって決まります。
            foreach rule element RBE in R1.body:
                if RBE is a negation element:
                    if RBE.evaldata then:
                        foreach triple pattern TP in RBE.inner:
                            let item be a pair (TP, "closed")
                            add item to bodyDependencies
                        endfor
                    endif
                else if RBE is a triple pattern element of triple pattern TP:
                    let item be a pair (TP, "open")
                    add item to bodyDependencies
                else if RBE is a filter element:
                    # 何もしません
                else if RBE is an assignment element:
                    # 何もしません
                endif
            endfor
        endif

        foreach pair (triple pattern TP, depLabel) in bodyDependencies:
            if R1 is a run-once rule:
              set depLabel to "closed"
            endif
            # このトリプルパターン要素または否定要素の依存関係を見つけます。
            foreach rule R2 in ruleSet.rules:
                foreach triple template TT in R2.head:
                    if triple pattern TP matches triple template TT:
                        let key = (R1, R2)
                        if edgeLabelMap contains key:
                            let oldLabel = edgeLabelMap.get(key)
                            let merged = mergeLabel(oldLabel, depLabel)
                            edgeLabelMap.set(key, merged)
                        else:
                            edgeLabelMap.set(key, depLabel)
                        endif
                    endif
                endfor
            endfor
        endfor
    endfor

    let DP = { }
    foreach entry ((R1, R2), label) in edgeLabelMap:
        add an edge (R1 -> R2) labeled with label to DP
    endfor

    the result is DP
enddefine

4.4 層別化

層別化は、ルールセットを 順序付けられた層別化レイヤーのシーケンス （「strata」、単数形は「stratum」とも呼ばれます）に分割するプロセスです。 より低い層のルールは、 より高い層のルールより前に評価されます。

層別化は、否定要素と一度だけ実行されるルールが、 それ以前の（より低い）層と ベースグラフを使用して計算された結果だけに依存することを保証するため、 ルール間の依存関係に制約を課します。 これにより、指定されたベースグラフに対するルールセットの評価から、 一意で明確に定義された有限の結果が得られることが保証されます。

注記

層別化プロセスは、その他の評価上の決定にも使用できます。 この文書では、一貫した評価に必要な条件を説明し、 層別化を形成する方法の一例を示します。 実装は互換性のある動作を得るためにここで説明する条件を満たす必要がありますが、 提示されたアルゴリズムをそのまま実装する必要はありません。

層別化レイヤー

層別化レイヤー SL は、 互いに素なルール集合のペア （SL.once、SL.general）です。 SL.once は、そのレイヤーの一度だけ実行される ルールだけからなります。 これらのルールはそれぞれ、層別化レイヤーの評価開始時に 正確に一度だけ評価されます。 SL.general はレイヤー内の残りのルールの集合であり、 新しいトリプルが推論されなくなるまで繰り返し評価されます。

層別化

ルールセットの 層別化は、 層別化レイヤーのシーケンスです。 ルールセット内の各ルールは、 層別化レイヤーのいずれか一つの集合に、正確に一度だけ現れます。

層別化の層別化レイヤーには、 0 から番号が付けられます。ルールの 層番号は、そのルールを含む 層別化レイヤーの番号です。 より小さい層番号を持つルールは、 より低い層にあり、 より大きい層番号を持つルールは、 より高い層にあります。

ルールセットの 依存関係グラフにおける、 ルール R1 からルール R2 への各辺について、

  • 辺に closed のラベルが付けられている場合、 R1 の層 番号は、 R2 の層 番号より厳密に大きい。
  • 辺に open のラベルが付けられている場合、 R1 の層 番号は、 R2 の層 番号以上である。
注記

ルールセットには、複数の層別化が存在する場合があります。 実装は、そのルールセットの任意の層別化を使用できます。

4.4.1 層別化条件

層別化は、次の条件が 満たされる場合にのみ定義されます。ルールセットがこの条件を満たさない場合、 この仕様では、そのようなルールセットの評価結果を定義しません。

層別化条件
層別化条件では、 ルールセットの依存関係グラフに、 閉じた依存関係を含む 再帰的依存関係が 存在しないことが要求されます。
注記

層別化条件は、 層別化が存在するための条件そのものです。 ルールセットの層別化を形成できるための必要十分条件は、 そのルールセットの依存関係グラフ内のいかなる循環経路も 閉じた依存関係を含まないことです。

4.4.2 層別化アルゴリズム

次のアルゴリズムは、ルールセットのみに基づく 層別化の一例を示します。 

define stratification(ruleSet):

    let DP = Dependency graph for the rule set.
    let stratumMap be a map from rule to integer

    # 依存関係グラフは層別化条件を満たす必要があります。
    # 無制限の層別化のチェックは、
    # 層別化条件違反に対する保護です。
    let limit = num rules + 1
    let maxStratum = 0

    # stratumMap を初期化します
    foreach rule in ruleSet.rules:
        stratumMap.set(rule, 0)
    endfor

    boolean changed = true
    while changed:
        changed = false
        foreach edge E in DP:
            # pRule から qRule へのラベル付き辺
            let pRule = source of edge
            let qRule = destination of the edge
            let label = edge label

            if label == "open":
                if stratumMap.get(pRule) < stratumMap.get(qRule):
                    stratumMap.set(pRule, stratumMap.get(qRule))
                    changed = true
                endif
            endif
            if label == "closed":
                if stratumMap.get(pRule) <= stratumMap.get(qRule):
                    let xStratum = 1 + stratumMap.get(qRule)
                    if xStratum > limit:
                        # 層別化要件違反
                        error "Stratification error"
                    endif
                    stratumMap.set(pRule, xStratum)
                    maxStratum = max(maxStratum, xStratum)
                    changed = true
                endif
            endif
        endfor
    endwhile

    # 結果マップを初期化します。
    let stratumRules be a map from integer to rules.
    foreach i = 0 to maxStratum
        stratumRules.set(i, {})
    endfor

    # stratumMap 内で同じレベル番号を持つルールを集めます
    foreach rule R in map stratumMap:
        let stratumNum = stratumMap.get(R)
        add R to stratumRules.get(stratumNum)
    endfor

    # 各レベルを once と general に分割します
    let stratumLevels be a sequence of pairs of sets of rules.
    for i = 0 to maxStratum:
        let rules = stratumRules.get(i)
        let once = { R in rules | R is a run-once rule }
        let general = rules \ once
        stratumLevels.set(i, pair(once, general))
    endfor

    the result is stratumLevels
enddefine
注記

層別化条件の帰結として、 一度だけ実行されるルールが評価されると、 そのルールの結果を決定するために使用されたデータは、 その後の評価中に変化しません。

完全なルールセットに対して依存関係分析と 層別化を段階的に適用し、その後評価まで追跡する例は、 6.6 実例 に示されています。

4.5 インポートの処理

Web から文書を読み込むことにはセキュリティ上の影響があります。 ルールセットのインポートのサポートは、SPARQL-RL プロセッサでは任意です。 さらに、実装は、特定のルールセットのインポートをサポートし、 その他をサポートしないなど、部分的なサポートをMAY提供できます。 また、検証済みのコピーからのインポートをサポートすることもできます。

インポート処理には、次の条件が適用されます。

  • ルールセットのインポートをサポートしない実装は、IMPORTS 文を含む ルールセットをMUST拒否し、 エラーを通知しなければなりません。
  • 部分的なサポートを提供する実装は、 サポートしていないインポートに遭遇した場合、エラーを MUST通知しなければなりません。
  • 実装は、インポート文書を解決できない場合、 またはその文書が構文的に有効でない場合、エラーをMUST通知しなければなりません。
  • プロセッサは、IMPORTS 文を処理する際の無限ループを避けるため、 ルールセットを一度だけMUSTインポートしなければなりません。

解決済みルールセットは、 別のルールセットのインポートで言及されている すべてのルールセットを再帰的に読み込むことで、その別のルールセットから生成されます。

アルゴリズムの例は、 A. インポート アルゴリズムの例に示されています。

5. SPARQL-RL と SPARQL の関係

この節は非規範的です。

SRL と SPARQL には密接な関係があります。SRL は SPARQL と互換性を持つよう設計されており、 SRL の構成要素の多くは SPARQL のパターン照合から取り入れられたか、 それに着想を得ています。ただし、いくつかの相違点があります。

SRL では、RULE の変数は、FILTER または SET の 式で使用される場合でも、トリプルテンプレート で使用される場合でも、使用前に常に束縛されます。 ルールヘッド。SPARQL の CONSTRUCT クエリおよび INSERT 更新は、 CONSTRUCT または INSERT テンプレートに変数が現れるものの、 WHERE 句で値が与えられていない場合、部分的な結果を生成します。

  • 整形式条件は、 変数が少なくとも 1 つのトリプルパターン要素に現れるか、 または代入変数として現れた後で、 フィルター要素または代入 要素で使用されることを保証します。 ルールボディ内で。
  • SRL の SET 形式と SPARQL の BIND 形式では、 エラー処理の動作が異なります。SET でエラーが発生すると、 現在のソリューションは除外されますが、BIND は 現在のソリューションに変数を設定せず、そのソリューションをそのまま渡します。 SET(?var := expr) は、 SPARQL の BIND(expr AS ?var) に続けて FILTER(BOUND(?var)) を実行することと同じです。
  • ルールボディの WHERE 句の構文には、 UNION または OPTIONAL の構文は含まれません。 これらの SPARQL 要素は未束縛変数を生じさせる可能性があります。 UNION または OPTIONAL の効果は、 整形式のルールを使用して実現できます。

その他の相違点には、次のものがあります。

  • NOT の構文では、内部ボディをトリプル パターンとフィルターに限定し、ネストされたパターンは許可しません。 NOT は、SPARQL の FILTER NOT EXISTS とは異なり、 ルールボディ内で記述された位置においてフィルターとして実行されます。
  • プロパティパス構文は、/ と ^ を使用するパスのみを対象とします。 これらはトリプルパターンに展開できます。 任意長演算子 * および + は許可されません。 任意長のパスは、より一般的な方法として再帰を使用して SPARQL-RL で表現できます。
  • 一部の関数は SRL 構文に含まれていません。 COALESCE や BOUND はありません。ハッシュ関数もありません。 呼び出すたびに異なる結果になるため、RAND も ありません。
    注記
    NOW() は使用可能であり、ルールセット評価全体を通して 同じ時点を返すよう定義されています。
  • BNODE を使用すると、呼び出すたびに異なる空白ノードが生成されます。 ルールセット評価の結果は、 グラフ同型な推論グラフを生成します。

  • UUID および STRUUID は、一意な識別子を生成するために使用できます。 ルールは、生成されたこれらの識別子を検査せず、 トリプルを生成するためにのみ使用するべきです。

    NOW の結果をテストする場合と同様に、 再現性をテストするために専用のジェネレーターを使用できます。

6. ルールセットの評価

この節では、指定されたデータに対してルールセットを評価した結果を定義します。 実装方法としてこのアルゴリズムを使用することを規定するものではありません。 実装は、同じ結果を生成する任意のアルゴリズムを使用できます。 

Inputs: graph G, called the base graph, and a rule set RS.
Output: an RDF graph GI of inferred triples

推論されたトリプルには、 ベースグラフのトリプル集合に存在するトリプルは含まれません。

6.1 評価の定義

ソリューションマッピング
ソリューションマッピング μ は、部分 関数 μ : V → T です。 ここで V はすべての変数の集合、 T はすべてのRDF 項の集合です。 μ の定義域は dom(μ) と表され、これは μ が定義されている V の部分集合です。 ソリューションという用語は、 ソリューションマッピングを意味することが明らかな場合に使用できます。 dom(μ0) が空集合となる ソリューションマッピングを μ0 と表します。
置換関数

置換関数、または単に置換は、 関数 subst(μ, triple pattern) であり、トリプルパターンを返します。 そのトリプルパターン内に現れる変数 var のうち、 dom(μ) に含まれるものは、 var に対して ソリューションマッピングが与える RDF 項で置き換えられます。 結果のトリプルパターンに変数がなければ、それは RDF トリプルです。

関数 subst(μ, triple template) も同様に定義されます。トリプルテンプレート内に現れる各変数は、 var に対して ソリューションマッピングが与える RDF 項で置き換えられます。

テンプレートインスタンス関数
テンプレートインスタンス関数は、 replaceBlankNodes(list of triple templates) という関数であり、 引数内の各空白ノードを新しい空白ノードで置換した トリプルテンプレートのリストを返します。 同じ空白ノードが複数回現れる場合は、 同じ新しい空白ノードで置き換えられます。
評価 グラフ
評価グラフは、RDF グラフであり、 ベースグラフと、 ルールセットの評価中に生成されたすべてのトリプルを結合したものです。
グラフ照合
グラフ照合は、トリプルパターンを RDF グラフ内のトリプルに対応付ける方法を見つけます。

G をRDF グラフ、TP をトリプルパターンとします。 関数 graphMatch(G, TP) は、 トリプルパターンに適用したときにグラフ G 内にある トリプルを生成する、可能なすべての ソリューションの集合を返します。

G をRDF グラフ、TP をトリプルパターン、 V を TP に現れる変数の集合とします。 

graphMatch(G, TP) = { μ | dom(μ) = V and subst(μ, TP) is a triple in G }
ソリューションの互換性
2 つのソリューション S1 と S2 は、共通する変数について一致する場合、 互換です。

S1 と S2 をソリューションとします。 

compatible(μ1, μ2) = true
                       if forall v in dom(μ1) intersection dom(μ2)
                           μ1(v) = μ2(v)
 compatible(μ1, μ2) = false otherwise
ソリューション シーケンス
ソリューションシーケンスは、ソリューションの多重集合です。 シーケンスの順序は定義されていません。 これは順序なしリストと等価であり、重複を含むことができます。
ソリューションのマージ
2 つのソリューションが互換である場合、2 つのソリューションのマージは、 各ソリューションの変数を、いずれかのソリューションからの RDF 項に対応付けるソリューションです。
μ1、μ2 を ソリューションマッピング、S1 と S2 をソリューションシーケンスとします。 
merge(μ1, μ2) = μ such that
                    μ(v) = μ1(v) if v in dom(μ1)
                    μ(v) = μ2(v) otherwise
merge(S1, S2) = { μ |
                    μ1 in S1, μ2 in S2
                    and compatible(μ1, μ2)
                    μ = merge(μ1, μ2) }
注記

merge(μ1, μ2) の定義域は domain(μ1) ∪ domain(μ2) です。

2 つのソリューションに共通の変数がない場合、それらは互換であり、 2 つのソリューションのマージは μ1 と μ2 の和集合です。

実効ブール値
関数 EBV(x) は、 RDF 項の実効ブール値を返します。

6.2 評価の準備

ルールセットの評価には、インポートされたすべてのルールセットを収集し、 4.5 インポートの 処理で説明されているように、単一の結合されたルールセットを構築することが含まれます。

次に、結合されたルールセットを 以下の手順で評価用に準備します。

  1. 各ルールが整形式のルールであることを、 4.2 整形式 条件で説明されているように確認します。
  2. 依存関係グラフを、 4.3.2 依存関係グラフのアルゴリズムで説明されているように計算します。
  3. 結合されたルールセットの層別化を、 4.4 層別化で説明されているように計算します。 4.4.2 層別化アルゴリズムでは、 層別化を計算する方法の一例を示します。

6.3 式の評価

式は、フィルター要素で使用される場合でも、 代入要素で使用される場合でも、 ソリューションマッピングに関して評価されます。 ソリューションマッピングは、式内の各変数に RDF 項の値を提供します。 4.2 整形式条件の要件により、 式内のすべての変数が ソリューションマッピングに現れることが保証されます。 

define evalFunction(F, μ):
    # F は式です。RDF 項、変数、または op(expr1, ..., exprN)
    # ここで op は関数または関数形式です。
    # μ はソリューションマッピングです
    if F is an RDF term:
        return F
    if F is a variable:
        # 整形式性により、F ∈ dom(μ) です。
        return μ(F)
    # F は F = op(expr1, ..., exprN) の形式です
    if op is a functional form (e.g., IF, logical-or):
        # op に固有の方法で評価されます。op は一部の引数だけを評価する場合があります。
        # たとえば、IF(c, t, f) は c を評価し、その後 t または f のどちらか一方だけを評価します。
        return the value defined for op over expr1, ..., exprN under μ
    # op は通常の関数です。最初にすべての引数を評価します。
    return op(evalFunction(expr1, μ), ..., evalFunction(exprN, μ))
enddefine

6.4 ルールの評価

ルールは、ルールボディからソリューション シーケンスを計算し、 そのソリューションシーケンスの各ソリューションマッピングを使用して、 ルールヘッドによりトリプルを生成することで評価されます。

トリプルパターン内の空白ノードは、変数のように振る舞います。 これは SPARQL グラフパターン照合と互換性があります。 

# ルールボディを評価します
# この関数はソリューションのシーケンスを返します

define evalRuleElements(B, SEQ, G, GD):
    where
        B is a sequence of rule elements
        SEQ is a solution sequence
        G and GD are RDF graphs

    foreach rule element rElt in B:

        if rElt is a triple pattern element TP:
            X = graphMatch(G, TP)
            SEQ1 = {}
            foreach μ1 in X:
                foreach μ2 in SEQ:
                    if compatible(μ1, μ2):
                      μ3 = merge(μ1, μ2)
                      add μ3 to SEQ1
                    endif
                endfor
            endfor
        endif

        if rElt is a filter element F:
            SEQ1 = {}
            foreach solution μ in SEQ:
                let x = evalFunction(F.expr, μ)
                if EBV(x) is true:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is a negation element N:
            SEQ1 = {}
            foreach solution μ in SEQ:
                S = sequence{ μ }
                if N.evaldata:
                    NEG = evalRuleElements(N.inner, S, G, GD)
                else:
                    NEG = evalRuleElements(N.inner, S, GD, GD)
                endif
                if NEG is empty:
                    add μ to SEQ1
                endif
            endfor
        endif

        if rElt is an assignment A:
            SEQ1 = {}
            foreach solution μ in SEQ:
                let x = evalFunction(A.expr, μ)
                if x is not an error:
                    # マッピング A.var -> x をソリューション μ に追加します
                    let μ2 be a solution mapping μ ∪ { (A.var, x) }
                    add μ2 to SEQ1
                else:
                    # エラー: ソリューション μ を破棄します
                endif
            endfor
        endif

        SEQ = SEQ1
    endfor

    return SEQ
enddefine

define evalRule(R, G, GD):
    where
        R is a well-formed rule
        G and GD are RDF graphs
    let B be R.body
        where each blank node in a triple pattern in R.body
        is replaced by a variable which is not used in the rule.
        The same variable is used for each occurrence of the
        same blank node, and a different variable is used for
        each different blank node.

    # どの変数にも対応付けを行わない 1 つのソリューションからなるソリューションシーケンス。
    let SEQ0: Solution sequence = { μ0 }

    if R.evaldata:
        let SEQ = evalRuleElements(B, SEQ0, G, GD)
    else:
        let SEQ = evalRuleElements(B, SEQ0, GD, GD)
    endif

    # ルールヘッドを評価します
    let OUT = empty set
    foreach μ in SEQ:
        let S = {}
        # 各空白ノードを新しい空白ノードで置き換えたルールヘッド
        let HT = replaceBlankNodes(R.head)
        foreach triple template TT in HT
            let triple = subst(μ, TT)
            Add triple to S
        endfor
        OUT = OUT ∪ S
    endfor
    return OUT
enddefine
注記

OUT には、ベースグラフにも存在するトリプルが含まれる場合があります。

6.5 ルールセットの評価

ルールセットの評価は、 そのルールセットの層別化の各層を実行することとして定義され、 各層は、次の層に進む前に、 順番に完全に実行されます。 層は、まずその層の 一度だけ実行されるルールをそれぞれ評価し、 その後、その層の一般ルールを、新しいトリプルが 生成されなくなるまで繰り返し評価することで評価されます。 

let G0 be the input base graph
let RS be the rule set
let D be the graph of all DATA triples in RS

Apply stratification to RS

let LS be the sequence of layers after stratification

# 推論グラフ
let GI = { t ∈ D | t ∉ G0 }

# 評価グラフとデータブロック
let GE = G0 ∪ D

foreach stratum ST in LS:
    foreach rule R in ST.once:
        let X = evalRule(R, GE, G0)
        let Y = { t ∈ X | t ∉ GE }
        GI = GI ∪ Y
        GE = GE ∪ Y
    endfor

    let finished = false
    while ! finished:
        finished = true
        foreach rule R in ST.general:
            let X = evalRule(R, GE, G0)
            let Y = { t ∈ X | t ∉ GE }
            if Y is not empty:
                finished = false
                GI = GI ∪ Y
                GE = GE ∪ Y
            endif
        endfor
    endwhile
endfor
the result is GI

この節では、完全なルールセットの評価を段階的に説明します。ルールの依存関係を決定し （4.3 ルールの 依存関係）、 層別化を計算し （4.4 層別化）、 各層を順に評価して 推論グラフを生成します （6.5 ルールセットの 評価）。

6.6.1 依存関係の 決定

各ルールボディ内の各トリプルパターンを、 すべてのルールヘッド内のトリプルテンプレートと比較して、 どのルールがどのルールに依存するかを決定します （4.3 ルールの 依存関係）。

  • R1 のボディは単一のトリプルパターン ?x :hasVulnerability ?v です。述語 :hasVulnerability を持つ トリプルを生成できるトリプルテンプレートを持つルールヘッドはないため、 このパターンはデータにのみ一致できます。 R1 には依存関係がありません。
  • R2 のボディには 2 つのトリプルパターンがあります。 ?x :dependsOn ?y はどのルールヘッドにも一致できないため、 データにのみ一致します。?y :exposedTo ?v は R1 のヘッドテンプレート ?x :exposedTo ?v と一致し、 R2 自身のヘッドにも一致します。 どちらもトリプルパターン要素であり、 （否定要素内には現れず、 R2 は 一度だけ実行されるルールでもないため）、 R2 は R1 に対して開いた依存関係を持ち、 自身に対しても開いた依存関係を持ちます。 R2 の自身に対する依存関係により、R2 は再帰的ルールになります。
  • R3 のボディでは、パターン ?x :exposedTo ?v が R1 と R2 のヘッドに一致するため、 R3 はそれぞれに対して開いた依存関係を持ちます。 パターン ?v :severity ?s はどのルールヘッドにも一致しません。
  • R4 のボディでは、パターン ?x rdf:type :Component は どのルールヘッドにも一致しません。述語 rdf:type を持つ唯一のヘッドテンプレートは R5 にあり、そのオブジェクト :Notification は :Component とは異なる RDF 項なので、生成された トリプルが一致することはありません。 パターン ?x :status :criticallyExposed は、 否定要素 NOT { ?x :status :criticallyExposed } 内に現れ、 R3 のヘッドテンプレートと一致します。このパターンは 否定要素内に現れるため、R4 は R3 に対して 閉じた依存関係を持ちます。
  • R5 のボディでは、パターン ?x :status :criticallyExposed が R3 のヘッドに一致します。R5 のヘッドには 空白ノードが含まれているため、R3 への依存関係は、 パターンが通常のトリプルパターン要素であっても、 閉じた依存関係です。 どのルールボディ内のパターンも R5 のヘッドテンプレートには一致しないため、 R5 に依存するルールはありません。

したがって、依存関係グラフには 5 つの頂点と 6 つの 辺があります。

  • R2 → R1 (open)
  • R2 → R2 (open)
  • R3 → R1 (open)
  • R3 → R2 (open)
  • R4 → R3 (closed)
  • R5 → R3 (closed)

R4 と R5 は R1 または R2 に直接依存していませんが、それぞれ R3 を介して両方に 推移的依存関係を持ちます。

グラフ内の唯一の循環は自己辺 R2 → R2 であり、 これは開いた依存関係です。閉じた依存関係を含む循環はないため、 層別化条件は 満たされ、 ルールセットには明確に定義された結果があります。

6.6.2 層別化の 計算

層別化アルゴリズムに従い、 すべてのルールは層 0 から開始します。その後、変化がなくなるまで 辺を繰り返し調べます。

  • 開いた辺では、始点のルールが 終点と同じ層か、それより高い層にある必要があります。 4 つの開いた辺はいずれも、すべてのルールが層 0 にある状態ですでに この条件を満たしているため、変更は生じません。
  • 閉じた辺では、始点のルールが 終点より厳密に高い層にある必要があります。これは、終点が 先に完了まで実行されなければならないためです。辺 R4 → R3 (closed) では、R4 と R3 がどちらも層 0 にあるため、 R4 は層 1 に移動します。同様に、辺 R5 → R3 (closed) により R5 も層 1 に移動します。

さらに辺を一巡しても変更は生じないため、層は確定します。 次に各層を一度だけ実行されるルールと一般ルールに分割します。 R5 はヘッドに空白 ノードを持つため、一度だけ実行されるルールです。 ルールセット内の他のルールはいずれも一度だけ実行されるルールではありません。 層別化は次のとおりです。

  • 層 0: 一般ルール R1、R2、R3。一度だけ実行されるルールはなし
  • 層 1: 一度だけ実行される R5。一般ルール R4

この順序付けは、より高い層にあるルールの意図を反映しています。 コンポーネントを安全にデプロイできるかどうか、および どのコンポーネントに通知が必要かは、 すべての :status :criticallyExposed トリプルが導出された後でのみ決定できます。 そして、それらを導出するルール R3 は、 それに入力を与えるルール R1 および R2 とともに その下の層で完了します。

A. インポートアルゴリズムの例

この節は非規範的です。

次のアルゴリズムは、参照されるすべての文書を再帰的に訪問することで IMPORTS 文を解決する 方法の一例を示します。

2 つのルールセット RS1 と RS2 のルールセットのマージは、 次のように定義されるルールセット MR を生成します。 

let RS be a rule set

let V = {}

if RS has a location:

    V = { location of RS }

endif



define ruleSetMerge(rule set RS1, rule set RS2):

    let MR be a rule set

    MR.rules = RS1.rules ∪ RS2.rules

    MR.data = rdf_merge(RS1.data, RS2.data)

    MR.imports = {}

    the result is MR

enddefine



define imports(rule set RS):

    let RS2 be a rule set formed from RS.rules and RS.data

    foreach URL x in RS.imports:

        if x ∉ V:

            V = V ∪ { x }

            read rule set RS3 from URL x

            RS2 = ruleSetMerge(RS2, imports(RS3))

        endif

    endfor

    the result is RS2

enddefine



result is imports(RS)

ここで rdf_merge は、 RDF マージ 操作です。

C. セキュリティに関する考慮事項

この節は非規範的です。

SPARQL-RL 文書には、他の SPARQL-RL 文書を参照し、その内容を現在の 文書にインポートする IMPORTS 文を含めることができます。 インポートされた文書自体に独自の IMPORTS 文が含まれている場合、 それらの文書もインポートされます。

ルールセットをモジュール化するのに有用ですが、IMPORTS 文の使用は セキュリティリスクをもたらす可能性があります。 リスクには、悪意によるか偶発的かを問わず、評価中にルールセットが 過剰な計算を引き起こすことや、 HTTP リクエストが傍受され、古いコピーを含む 別の文書が返されることなどがありますが、これらに限定されません。

SPARQL-RL ルールセットを RDF グラフに適用すると、 大量の計算とメモリー使用量が必要になる可能性があり、これが悪用されて サービス拒否を引き起こす可能性があります。 アプリケーションは、SPARQL-RL ルールセットを適用することで生じ得る計算量と メモリー使用量を制限するよう注意するべきです。

SPARQL-RL 構文は UTF-8 [RFC3629] で符号化され、 文字列データで エスケープされていない制御文字の使用を許可します。 この仕様ではこの内容をエンドユーザーに直接公開しませんが、 ユーザーエージェントを介して提示される可能性があり、そのような文字によって提示されたテキストが 誤解を招くものになる可能性があります。

SPARQL-RL は任意のアプリケーションデータを処理および作成するために使用できます。 セキュリティに関する考慮事項は使用分野によって異なります。 テキストに適用できるセキュリティツールおよびプロトコル （たとえば、PGP 暗号化、チェックサム検証、パスワードで保護された圧縮） は、SPARQL-RL 文書にも使用できます。 セキュリティ/プライバシープロトコルは、SPARQL-RL ルールセット評価の結果に含まれる 情報の機密性を反映するよう適用しなければなりません。

SPARQL-RL のセキュリティに関する考慮事項には、 RDF データおよび 次のような形式のセキュリティに関する考慮事項も含まれます。 RDF Turtle。

D. プライバシーに関する考慮事項

この節は非規範的です。

SPARQL-RL 文書には、追加のアプリケーションデータを含めることができ、 そこには個人を特定できる情報（PII）の表現 または機密性があるとみなされ得るその他の情報が含まれる場合があります。 このような情報を含むルールセットを公開する作成者は、 そのような情報を公開する必要性と用途、および データが利用され、場合によっては開示されることが想定される地域で適用される規制 （たとえば、 GDPR、 CCPA、 その他）を慎重に検討し、 特に、データへのアクセスに認可措置が必要かどうかを考慮することが推奨されます。
