1.  はじめに

   この仕様は、JSON Web Signature (JWS) [JWS]、JSON Web
   Encryption (JWE) [JWE]、および JSON Web Key (JWK) [JWK] 仕様で
   使用される暗号アルゴリズムと識別子を登録する。
   また、これらの識別子のための複数の IANA レジストリを定義する。これらの
   仕様はすべて JSON ベースの [RFC7159] データ構造を利用する。この
   仕様は、これらのアルゴリズムと鍵タイプに固有の意味論および操作についても
   説明する。

   アルゴリズムと識別子を JWS、JWE、JWK 仕様ではなくここで登録することは、
   必須、推奨、任意、非推奨とされるアルゴリズムの集合が
   時間の経過とともに変更されても、これらの仕様を変更せずに
   維持できるようにすることを意図している。これにより、この文書を変更せずに
   JWS、JWE、JWK 仕様を変更することもできる。

   この仕様で定義される名前が短いのは、結果として得られる表現を
   コンパクトにすることが主要な目標だからである。

3.  デジタル署名および MAC のための暗号アルゴリズム

   JWS は、JWS Protected Header と JWS Payload の内容にデジタル署名するか、
   または MAC を作成するために暗号アルゴリズムを使用する。

3.1.  JWS の "alg" (アルゴリズム) ヘッダーパラメーター値

   次の表は、この仕様で JWS 用として定義する "alg" (アルゴリズム)
   ヘッダーパラメーター値の集合であり、それぞれについて
   後続のセクションでより詳細に説明する。

   +--------------+-------------------------------+--------------------+
   | "alg" パラメーター | デジタル署名または MAC          | 実装要件             |
   | 値           | アルゴリズム                    |                    |
   +--------------+-------------------------------+--------------------+
   | HS256        | SHA-256 を使用する HMAC         | 必須               |
   | HS384        | SHA-384 を使用する HMAC         | 任意               |
   | HS512        | SHA-512 を使用する HMAC         | 任意               |
   | RS256        | SHA-256 を使用する              | 推奨               |
   |              | RSASSA-PKCS1-v1_5              |                    |
   | RS384        | SHA-384 を使用する              | 任意               |
   |              | RSASSA-PKCS1-v1_5              |                    |
   | RS512        | SHA-512 を使用する              | 任意               |
   |              | RSASSA-PKCS1-v1_5              |                    |
   | ES256        | P-256 と SHA-256 を使用する ECDSA | 推奨+              |
   | ES384        | P-384 と SHA-384 を使用する ECDSA | 任意               |
   | ES512        | P-521 と SHA-512 を使用する ECDSA | 任意               |
   | PS256        | SHA-256 および                  | 任意               |
   |              | SHA-256 を使用する MGF1 による RSASSA-PSS |             |
   | PS384        | SHA-384 および                  | 任意               |
   |              | SHA-384 を使用する MGF1 による RSASSA-PSS |             |
   | PS512        | SHA-512 および                  | 任意               |
   |              | SHA-512 を使用する MGF1 による RSASSA-PSS |             |
   | none         | デジタル署名または MAC を       | 任意               |
   |              | 実行しない                      |                    |

   実装要件列での "+" の使用は、
   将来の仕様バージョンで要件の強度が引き上げられる可能性が高いことを

   署名および MAC の "alg" (アルゴリズム) 値と、他の標準や
   ソフトウェアパッケージで使用される同等の識別子との相互参照表については、
   付録 A.1 を参照すること。

3.2.  SHA-2 関数を使用する HMAC

   ハッシュベースのメッセージ認証コード (HMAC) により、
   秘密値と暗号学的ハッシュ関数を使用して MAC を生成できる。
   これは、MAC を生成した者が
   MAC 鍵を所持していたことを示すために使用できる。HMAC の実装および
   検証アルゴリズムは RFC 2104 [RFC2104] で規定されている。

   このアルゴリズムでは、ハッシュ出力と同じサイズ
   (たとえば "HS256" の場合は 256 ビット) 以上の鍵を使用しなければならない。
   (この要件は NIST SP 800-117 [NIST.800-107] の
   セクション 5.3.4 (HMAC
   鍵のセキュリティ効果) に基づく。同文書では、実効セキュリティ強度は
   鍵のセキュリティ強度と内部ハッシュ値のサイズの 2 倍の
   小さい方であると述べている。)

   HMAC SHA-256 MAC は、RFC 2104 に従って生成され、SHA-256 を
   ハッシュアルゴリズム "H" として、JWS Signing Input を "text" 値として、
   共有鍵を使用する。HMAC 出力値が JWS
   Signature となる。

   次の "alg" (アルゴリズム) ヘッダーパラメーター値は、
   JWS Signature が対応するアルゴリズムを使用して計算された
   HMAC 値であることを示すために使用される。

                +-------------------+--------------------+
                | "alg" パラメーター値 | MAC アルゴリズム    |
                +-------------------+--------------------+
                | HS256             | SHA-256 を使用する HMAC |
                | HS384             | SHA-384 を使用する HMAC |
                | HS512             | SHA-512 を使用する HMAC |
                +-------------------+--------------------+

   JWS の HMAC SHA-256 MAC は、RFC 2104 に従って HMAC
   値を計算することで検証される。SHA-256 をハッシュアルゴリズム "H" として、
   受信した JWS Signing Input を "text" 値として、共有鍵を使用する。
   その後、計算された HMAC 値を、受信したエンコード済み JWS Signature 値を
   base64url デコードした結果と比較する。タイミング攻撃を防ぐため、
   計算された HMAC 値と JWS Signature 値との比較は
   定数時間で実行しなければならない。
   代わりに、計算された HMAC 値を base64url エンコードし、
   受信したエンコード済み JWS Signature 値と比較することもできる
   (これも定数時間で行う)。この比較は、エンコードされていない値を
   比較する場合と同じ結果を生成するためである。いずれの場合も、値が一致すれば、
   HMAC は検証されたことになる。

3.4.  ECDSA によるデジタル署名

   楕円曲線デジタル署名アルゴリズム (ECDSA) [DSS] は、
   RSA 暗号と同等のセキュリティを、より短い鍵サイズで、
   多くの操作においてより高速な処理速度で提供できる
   楕円曲線暗号の使用を可能にする。これは、
   同等の強度を持つ RSA デジタル署名と比べて、ECDSA デジタル署名の
   長さが大幅に短くなることを意味する。

   この仕様では、P-256 曲線と SHA-256 暗号学的ハッシュ関数を使用する ECDSA、
   P-384 曲線と SHA-384 ハッシュ関数を使用する ECDSA、
   および P-521 曲線と SHA-512 ハッシュ関数を使用する ECDSA を定義する。
   P-256、P-384、P-521 曲線は
   [DSS] で定義されている。

   ECDSA P-256 SHA-256 デジタル署名は、次のように生成する。

   1.  目的の秘密鍵を使用して、ECDSA
       P-256 SHA-256 により JWS Signing Input のデジタル署名を生成する。出力は
       ペア (R, S) となり、R と S は 256 ビットの符号なし整数である。

   2.  R と S をビッグエンディアン順のオクテットシーケンスに変換し、
       各配列の長さを 32 オクテットとする。値に含まれる先頭のゼロ
       オクテットを省略するために、オクテットシーケンス表現を
       短縮してはならない。

   3.  2 つのオクテットシーケンスを R、次に S の順で連結する。
       (多くの ECDSA 実装では、この連結を
       出力として直接生成することに注意。)

   4.  結果として得られる 64 オクテットのシーケンスが JWS Signature 値となる。

   次の "alg" (アルゴリズム) ヘッダーパラメーター値は、
   JWS Signature が対応するアルゴリズムを使用して計算された
   デジタル署名値であることを示すために使用される。

           | ES256             | P-256 と SHA-256 を使用する ECDSA |
           | ES384             | P-384 と SHA-384 を使用する ECDSA |
           | ES512             | P-521 と SHA-512 を使用する ECDSA |

3.6.  アルゴリズム "none" の使用

   完全性保護を提供しない JWS を作成してもよい。
   このような JWS は Unsecured JWS と呼ばれる。Unsecured JWS は
   "alg" 値 "none" を使用し、他の JWS と同じ形式であるが、
   JWS Signature 値として空のオクテットシーケンスを使用しなければならない。
   受信者は、JWS Signature 値が空の
   オクテットシーケンスであることを検証しなければならない。

   Unsecured JWS をサポートする実装は、
   特定のオブジェクトが完全性保護されていなくても許容可能であることを
   アプリケーションが指定しない限り、そのようなオブジェクトを有効として
   受け入れてはならない。実装は既定で Unsecured JWS を
   受け入れてはならない。ダウングレード攻撃を軽減するため、
   アプリケーションは Unsecured JWS の受け入れをグローバルレベルで
   通知してはならず、オブジェクトごとに受け入れを
   通知すべきである。このアルゴリズムの使用に関連するセキュリティ上の
   考慮事項については、セクション 8.5 を参照すること。

   共有秘密 Z から合意済み鍵を導出する。

   鍵導出は、[NIST.800-56A] の
   セクション 5.8.1 で定義されている Concat KDF を使用して実行し、
   Digest Method は SHA-256 とする。

   Z

      表現したものに設定する。

      これは、目的の出力鍵のビット数に設定する。
      "ECDH-ES" の場合、これは "enc" アルゴリズムが使用する鍵の長さである。

      それぞれ 128、192、256 である。

      0 個以上のオクテットからなる可変長文字列、Datalen は

      ヘッダーパラメーター値の ASCII 表現のオクテットに設定する。
      Key Agreement with Key Wrapping の場合、Data は
      "alg" (アルゴリズム) ヘッダーパラメーター値の ASCII 表現の
      オクテットに設定する。

5.2.2.1.  AES_CBC_HMAC_SHA2 暗号化

   認証付き暗号化アルゴリズムは、4 つのオクテット文字列、
   秘密鍵 K、平文 P、Additional Authenticated Data
   A、および Initialization Vector IV を入力として受け取る。
   認証付き暗号文値 E と Authentication Tag 値 T を出力する。
   平文内のデータは暗号化および認証され、
   Additional Authenticated Data は認証されるが暗号化されない。

   暗号化処理は次のとおりである。または、これと同等の一連の
   手順を使用する。

   1.  補助鍵 MAC_KEY および ENC_KEY を、
       入力鍵 K から次のように生成する。これら 2 つの鍵はそれぞれ
       オクテット文字列である。

          MAC_KEY は K の先頭 MAC_KEY_LEN オクテットから、
          順序どおりに構成する。
          ENC_KEY は K の末尾 ENC_KEY_LEN オクテットから、
          順序どおりに構成する。

       入力鍵 K のオクテット数は、
       MAC_KEY_LEN と ENC_KEY_LEN の合計でなければならない。
       これらのパラメーターの値は、セクション
       5.2.3 から 5.2.5 の Authenticated Encryption アルゴリズムによって指定される。
       入力鍵 K では MAC 鍵が暗号化鍵より前にあることに注意。
       これは識別子 "AES_CBC_HMAC_SHA2" における
       アルゴリズム名の順序とは逆である。

   2.  使用する IV は、暗号で使用するためにランダムまたは
       擬似ランダムに生成された 128 ビット値である。

   3.  ENC_KEY を鍵、IV を Initialization Vector として、
       PKCS #7 パディングを使用して平文を CBC 暗号化する。
       この手順から得られる暗号文出力を E と表記する。

   4.  オクテット文字列 AL は、Additional Authenticated Data A の
       ビット数を 64 ビット符号なし
       ビッグエンディアン整数として表したものに等しい。

   5.  次のデータに順番どおり HMAC
       [RFC2104] を適用して、メッセージ Authentication Tag T を計算する。

          Additional Authenticated Data A、
          Initialization Vector IV、
          前の手順で計算した暗号文 E、および
          上で定義したオクテット文字列 AL。

       文字列 MAC_KEY を MAC 鍵として使用する。この手順で
       計算された MAC の出力を M と表記する。M の先頭 T_LEN オクテットを
       T として使用する。

   6.  暗号文 E と Authentication Tag T を、
       認証付き暗号化の出力として返す。

   暗号化処理は次のように示すことができる。ここで K、P、A、
   IV、E はそれぞれ鍵、平文、Additional Authenticated Data、
   Initialization Vector、暗号文を表す。

      MAC_KEY = K の先頭 MAC_KEY_LEN オクテット,
      ENC_KEY = K の末尾 ENC_KEY_LEN オクテット,
      E = CBC-PKCS7-ENC(ENC_KEY, P),
      M = MAC(MAC_KEY, A || IV || E || AL),
      T = M の先頭 T_LEN オクテット。

5.2.2.2.  AES_CBC_HMAC_SHA2 復号

   認証付き復号操作には、上で定義した K、A、IV、E、
   T の 5 つの入力がある。出力は 1 つだけであり、
   平文値 P または入力が真正でないことを示す
   特別なシンボル FAIL のいずれかである。認証付き復号アルゴリズムは
   次のとおりである。または、これと同等の一連の手順を使用する。

   1.  補助鍵 MAC_KEY および ENC_KEY を、
       セクション 5.2.2.1 の手順 1 と同様に入力鍵 K から生成する。

   2.  セクション 5.2.2.1 の手順 5 と同じ入力を使用して
       HMAC を計算し、A と E の完全性と真正性を確認する。
       前の手順の値 T を、
       HMAC 出力の先頭 MAC_KEY 長ビットと比較する。
       これらの値が同一であれば、A と E は有効とみなし、
       処理を継続する。それ以外の場合、MAC 検証に使用した
       すべてのデータを破棄し、認証付き
       復号操作は失敗したことを示す結果を返して、
       操作を停止する。(ただし、タイミング攻撃を防ぐためのセキュリティ上の
       考慮事項については [JWE] のセクション 11.5 を参照。)

   3.  値 E を復号し、PKCS #7 パディングを検証して
       除去する。値 IV を Initialization Vector として使用する。
       値 ENC_KEY を復号鍵として使用する。

   4.  平文値を返す。

   現時点で暗号学的に信頼できるとみなされているか、

   アルゴリズム名:
      要求する名前 (例: "HS256")。この名前は大文字と小文字を区別する
      ASCII 文字列である。指定専門家が例外を許可する説得力のある理由が
      あると判断しない限り、大文字と小文字を区別しない比較で
      他の登録済みの名前と一致してはならない。

   アルゴリズムの説明:
      アルゴリズムの簡単な説明 (例: "SHA-256 を使用する HMAC")。

   アルゴリズムの使用箇所:
      アルゴリズムの使用箇所。アルゴリズムを JWS または
      JWE で使用する場合、これは "alg" または "enc" の
      1 つ以上の値でなければならない。アルゴリズム識別子を
      JWK の "alg" メンバー値として使用するが、JWS または
      JWE では使用しない場合は、値 "JWK" を使用する。
      これは、たとえば認証なし暗号化アルゴリズムの場合に該当し得る。
      指定専門家の承認を得て、他の値を使用してもよい。

   JOSE 実装要件:
      JWS および JWE のアルゴリズム実装要件であり、
      必須、推奨、任意、非推奨、禁止のいずれかの語でなければならない。
      必要に応じて、その語の後に "+" または
      "-" を付けることができる。"+" の使用は、
      将来の仕様バージョンで要件の強度が
      引き上げられる可能性が高いことを示す。
      "-" の使用は、将来の仕様バージョンで要件の強度が
      引き下げられる可能性が高いことを示す。
      認証なし暗号化アルゴリズム、または JWS や JWE
      アルゴリズムとして直接使用することが不適切なその他のアルゴリズムとして
      登録される識別子は、"禁止" として登録しなければならない。

   変更管理者:
      標準化過程 RFC の場合は "IESG" を記載する。それ以外の場合は、
      責任を負う当事者の名前を記載する。その他の詳細
      (例: 郵便住所、電子メールアドレス、ホームページ URI) を
      含めてもよい。

8.1.  暗号アジリティ

   実装者は、暗号アルゴリズムが時間の経過とともに
   弱くなることを認識すべきである。新しい暗号解析技法が開発され、
   計算性能が向上するにつれて、特定の暗号アルゴリズムを破るために
   必要な作業量は減少する。そのため、実装者および配備環境は、
   サポートおよび使用するアルゴリズムの集合が
   時間の経過とともに変化することに備えなければならない。
   したがって、暗号アルゴリズムの実装はモジュール式とし、
   新しいアルゴリズムを容易に追加できるようにすべきである。

8.2.  鍵の有効期間

   多くのアルゴリズムには、鍵の有効期間や、
   鍵を使用できる回数に関連するセキュリティ上の考慮事項がある。
   これらのセキュリティ上の考慮事項は、JOSE データ構造で
   それらのアルゴリズムを使用する場合にも引き続き適用される。
   鍵の有効期間に関する具体的なガイダンスについては、NIST SP 800-57
   [NIST.800-57] を参照すること。

8.3.  RSAES-PKCS1-v1_5 のセキュリティに関する考慮事項

   RFC 3447 のセクション 8 [RFC3447] では、
   新しいアプリケーションに RSASSA-PKCS1-v1_5 を採用せず、
   代わりに RSASSA-PSS へ移行することを明示的に求めているが、
   RSASSA-PKCS1-v1_5 は広く実装されているため、
   相互運用性上の理由からこの仕様には含まれている。

   RSAES-PKCS1-v1_5 で使用する鍵は、
   RFC 3447 のセクション 7.2 の制約に従わなければならない。
   また、"Twenty Years of Attacks on the
   RSA Cryptosystem" [Boneh99] の セクション 3 で説明されているような、
   公開鍵指数値が小さい鍵を使用してはならない。

8.4.  AES GCM のセキュリティに関する考慮事項

   AES GCM で使用する鍵は、[NIST.800-38D] のセクション 8.3 の
   制約に従わなければならない。そこでは、
   「指定された鍵について、すべての IV 長および認証付き暗号化関数の
   すべてのインスタンスを含め、認証付き暗号化関数の総呼び出し回数は
   2^32 を超えてはならない」とされている。この規則に従い、
   AES GCM は同じ鍵値で 2^32 回を超えて使用してはならない。

   IV 値は、同じ AES
   GCM 鍵で複数回使用してはならない。これを防ぐ方法の 1 つは、
   鍵とともにカウンターを保存し、使用するたびに
   インクリメントすることである。このカウンターは、
   上記の 2^32 の制限を超えることを防ぐためにも使用できる。

   このセキュリティ上の考慮事項は、複合 AES-CBC
   HMAC SHA-2 または AES Key Wrap アルゴリズムには適用されない。

8.5.  セキュリティ保護されていない JWS に関する考慮事項

   セキュリティ保護されていない JWS ("alg" 値 "none" を使用する JWS) は、
   完全性保護を提供しない。したがって、ペイロードが
   デジタル署名または MAC 値以外の手段によって保護されている場合、
   または保護する必要がない場合にのみ使用しなければならない。

   セキュリティ保護されていない JWS を既定で受け入れることを防ぐ方法の例として、
   仮想的な JWS ソフトウェアライブラリの "verify" メソッドに、
   "none" が許容可能な "alg" 値であることを示す
   Boolean 型の "acceptUnsecured" パラメーターを持たせる方法がある。
   別の例として、"verify" メソッドが、
   アプリケーションに許容されるアルゴリズムのリストを
   パラメーターとして受け取り、そのリストに "none" が含まれていなければ
   セキュリティ保護されていない JWS 値を拒否する方法もある。

   次の例は、セキュリティ保護されていない JWS を
   グローバルレベルで受け入れない理由を示す。
   あるアプリケーションが、(1) HTTP と (2) クライアント
   認証付き HTTPS の 2 つのチャネルで JWS を受け入れるとする。
   HTTP 経由で受信したオブジェクトには JWS Signature を要求するが、
   HTTPS 経由ではセキュリティ保護されていない JWS を受け入れる。
   アプリケーションが "none" を許容するとグローバルに指定した場合、
   攻撃者は HTTP 経由でセキュリティ保護されていない JWS を提供し、
   そのオブジェクトを正常に検証させることができる。
   代わりに、アプリケーションは HTTPS 経由で受信する各オブジェクトについて
   "none" の受け入れを指定する必要がある
   (例: 上記の最初の仮想的な JWS ソフトウェアライブラリで
   "acceptUnsecured" を "true" に設定する) が、
   HTTP 経由で受信する各オブジェクトについては指定してはならない。

8.6.  サービス拒否攻撃

   署名を検証する受信エージェントおよびメッセージを暗号化する送信エージェントは、
   この仕様で義務付けられているより大きな鍵を使用して
   署名の検証やメッセージの暗号化を行う際の暗号処理の使用量に
   注意する必要がある。攻撃者は、たとえばこの仕様で義務付けられたものより
   大きな鍵など、過大な暗号処理を引き起こす鍵を使用する
   コンテンツを提供する可能性がある。実装は、受け入れる
   鍵サイズに上限を設定し、それを強制すべきである。NIST SP 800-57
   [NIST.800-57] の セクション 5.6.1
   (同等のアルゴリズム強度) には、適用可能な

8.8.  パスワードに関する考慮事項

   パスワードは多くの攻撃に対して脆弱である。
   これらの制約の一部を軽減するため、この文書では、
   ユーザーが提供したパスワードから暗号鍵を導出するために
   RFC
   2898 [RFC2898] の原則を適用する。

   ただし、パスワードの強度は依然として大きな影響を及ぼす。
   高エントロピーのパスワードは辞書攻撃に対する耐性が高い。
   [NIST.800-63-2] にはパスワードエントロピーを推定するためのガイドラインがあり、
   アプリケーションとユーザーがより強いパスワードを生成する際に役立つ。

   理想的なパスワードは、導出鍵の長さと同じ
   (またはそれ以上) の長さを持つものである。ただし、特定の
   アルゴリズム固有サイズより大きなパスワードは最初にハッシュされるため、
   攻撃者の実効的な探索空間はハッシュアルゴリズムの長さまで縮小される。
   "PBES2-HS256+A128KW" に使用するパスワードは
   16 オクテット以上 128 オクテット以下とし、
   "PBES2-HS512+A256KW" に使用するパスワードは
   32 オクテット以上 128 オクテット以下とすることを推奨する。

   それでも、パスワードベース暗号化をどこでどのように
   使用するかには注意が必要である。反復回数が少なすぎる場合、
   これらのアルゴリズムは依然として辞書ベースの攻撃を受ける可能性がある。
   ファイルシステムに保存された保護対象データのように、
   攻撃者が保護の突破を無制限に試行できるデータを
   これらのアルゴリズムで保護する場合は、特に問題となる。

付録 C.  ECDH-ES 鍵合意計算の例

   この例では、セクション 4.6 で説明した方法で CEK を導出するため、
   ECDH-ES 鍵合意と Concat KDF を使用する。この例では、
   ECDH-ES Direct Key Agreement モード ("alg" 値 "ECDH-ES") を使用して、
   128 ビット鍵を使用する AES GCM ("enc"
   値 "A128GCM") の合意済み鍵を生成する。

   この例では、生成者 Alice が消費者
   Bob にコンテンツを暗号化している。生成者 (Alice) は、鍵
   合意計算のために一時鍵を生成する。この例の
   鍵合意計算で使用する Alice の一時鍵
   (JWK 形式、秘密部分を含む) は次のとおりである。

     {"kty":"EC",
      "crv":"P-256",
      "x":"gI0GAILBdu7T53akrFmMyGcsF3n5dO7MmwNBHKW5SV0",
      "y":"SLW_xSffzlPWrHEVI30DHM_4egVwt3NQqeUD7nMFpps",
      "d":"0_NxaRPUMQoAJt50Gz8YiTr8gRTwyEaCumd-MToTmIo"
    }

   (JWK 形式、秘密部分を含む) は次のとおりである。

     {"kty":"EC",
      "crv":"P-256",
      "x":"weNJy2HscCSM6AEDTDg04biOvhFhyyWvOHQfeF_PxMQ",
      "y":"e8lnCO-AlStT-NJVX-crhB7QRYhiix03illJOVAOyck",
      "d":"VEmDZpDXXK8p8N0Cndsxs924q6nS1RXFASRl6BfUqdw"

   "apu" (agreement PartyUInfo) ヘッダーパラメーター値は
