概要

この文書は、ウェブアプリケーションが要求できるようにする API を規定します 画面ウェイクロック。適切な条件下で、かつ許可されている場合、 画面ウェイクロックは、システムがデバイスの 画面をオフにすることを防ぎます。

1. はじめに

この節は非規範的である。

現代のオペレーティングシステムは、積極的な電力管理を実装することで バッテリーの駆動時間を延ばしている。つまり、ユーザーの操作が 途絶えると、ホストデバイスはほどなく画面の明るさを下げ、 画面を消灯し、さらには CPU を深い省電力状態に移行させることで、 電力消費を可能な限り抑えることがある。

これはバッテリーの駆動時間を延ばすには優れているものの、場合によっては、 バーコードの読み取り、電子書籍の閲覧、レシピの確認、 聴衆に向けたプレゼンテーションなどのユースケースを妨げることがある。 ウェイクロック：ユースケースも参照。

ウェイクロックは一般に何らかの動作を防止するが、UA （および基盤となる OS）は、バッテリーの状態 （外部電源への接続、放電中、残量不足）に応じてその有効時間を制限したり、 省電力モードが有効な場合にはウェイクロックを禁止したりすることがある。

2. ウェイクロック

この仕様は、次の ウェイクロック 種別を定義する：

  1. 画面ウェイクロックは、画面が 消灯するのを防ぐ。可視状態の文書だけが画面ウェイクロックを 取得できる。

API では、ウェイクロック種別は、 WakeLockType 列挙型の値で表される。

注記

他の仕様が異なるウェイクロック種別を定義することもある。

3. ポリシーによる制御

Screen Wake Lock API は、ポリシー制御される機能を、 文字列 "screen-wake-lock" で識別されるものとして定義する。その 既定の許可リストは 'self' である。

注記

この 既定の許可リストの 'self' は、 同一オリジンの入れ子になったフレームでのウェイクロックの使用を許可するが、 サードパーティのコンテンツによる使用は防止する。

サードパーティによる使用は、フレームコンテナー要素に allow="screen-wake-lock" 属性を追加することで選択的に有効化できる：

例: リモートコンテンツで画面ウェイクロックを有効化する 
<iframe src="https://third-party.com" allow="screen-wake-lock"/></iframe>

あるいは、HTTP レスポンスヘッダーで権限ポリシーを指定することで、 Screen Wake Lock API を完全に無効化できる：

例: Permissions Policy ヘッダー 
Permissions-Policy: screen-wake-lock=()

詳細については、権限ポリシーを 参照。

4. 権限とユーザーへの確認

[PERMISSIONS] API は、ウェブサイトがユーザーに権限を要求し、 どの権限を持っているかを照会するための統一的な方法を提供する。

ユーザー エージェントは、ウェイクロックを拒否することができる。 対象は、 特定の ウェイクロック種別と特定の Documentであり、その理由は、 プラットフォームの設定やユーザーの選好など、 実装固有の任意の理由でよい。

次のことが 推奨される：ユーザーエージェントは、邪魔にならない何らかの通知で、 ウェイクロックが有効であることをユーザーに知らせるとともに、 継続中の動作を ブロックするための手段、または 単に通知を 閉じるための手段をユーザーに提供する。

4.1 "screen-wake-lock" 強力な機能

"screen-wake-lock" 強力な機能は、 この仕様で定義する機能を有効にする。

4.2 権限アルゴリズム

"screen-wake-lock" 強力な機能は、権限取り消し アルゴリズムを定義する。画面 ウェイクロック権限取り消しアルゴリズムを呼び出すには、次の手順を実行する：

  1. document を、現在のグローバルオブジェクトに 関連付けられた Document とする。
  2. lockList を、 document.[[ActiveLocks]]["screen"] とする。
  3. それぞれについて、lock を lockList の各項目として：
    1. ウェイクロックを解放する手順を、document、lock、および "screen" を用いて実行する。

5. 概念

タスクソースのうち、この仕様で言及する タスクに 用いるものは、画面ウェイクロックタスクソースである。

プラットフォーム ウェイクロックという用語は、ユーザーエージェントが 状態の照会、およびウェイクロックの取得と解放のために やり取りするプラットフォームのインターフェースを指す。

プラットフォームウェイクロックは、基盤となるプラットフォーム （例えば、ネイティブのウェイクロックフレームワーク）によって、またはハードウェアを 直接制御できる場合はユーザーエージェントによって定義できる。

8. WakeLock インターフェース

WakeLock インターフェースを使うと、文書は 画面ウェイクロックを取得できる。 

WebIDL[SecureContext, Exposed=(Window)]
interface WakeLock {
  Promise<WakeLockSentinel> request(optional WakeLockType type = "screen");
};

8.1 request() メソッド

request(type) メソッドの手順は次のとおりである：

  1. document を、this の 関連するグローバルオブジェクトに 関連付けられた Document とする。
  2. もし document が 完全にアクティブでなければ、次の値で拒否されるプロミスを返す："NotAllowedError" DOMException。
  3. もし document が 使用を許可されていない ポリシー制御される機能の名前が "screen-wake-lock" であれば、次の値で拒否されるプロミスを返す："NotAllowedError" DOMException。
  4. もし ユーザーエージェントが ウェイクロックを拒否する対象の種別がこの type であり、対象の文書が document であれば、次の値で拒否されるプロミスを返す： "NotAllowedError" DOMException。
  5. もし document の 可視性状態が "hidden" であれば、次の値で拒否されるプロミスを返す："NotAllowedError" DOMException。
  6. promise を、新しい プロミスとする。
  7. 次の手順を 並列に実行する：
    1. state を、使用する 権限を要求する対象を "screen-wake-lock" とした結果とする。
    2. もし state が "denied" であれば：
      1. グローバルタスクをキューに入れる。使用するのは 画面ウェイク ロックタスク ソースであり、document の 関連するグローバルオブジェクトを与え、 promise を "NotAllowedError" DOMException で拒否する。
      2. これらの手順を中止する。
    3. グローバルタスクをキューに入れる。使用するのは 画面ウェイクロックタスク ソースであり、document の 関連するグローバルオブジェクトを与え、 次の手順を実行する：
      1. もし document が 完全にアクティブでなければ：
        1. promise を "NotAllowedError" DOMException で拒否する。
        2. これらの手順を中止する。
      2. もし document の 可視性状態が "hidden" であれば：
        1. promise を "NotAllowedError" DOMException で拒否する。
        2. これらの手順を中止する。
      3. もし document.[[ActiveLocks]]["screen"] が 空であるならば、 次の手順を 並列に 実行する：
        1. ウェイクロックを 取得する手順を、 "screen" を用いて呼び出す。
          注記
          ウェイクロックを取得する アルゴリズムは、 最終的にオペレーティングシステムからロックを 取得できない場合があるが、ユーザーの フィンガープリンティングを避けるため、 ロックの取得に成功した場合とは区別できない （例えば、取得の失敗はバッテリー残量不足を示す場合がある）。
      4. lock を、新しい WakeLockSentinel オブジェクトとし、その type 属性の設定値を type とする。
      5. 追加する対象を lock とし、追加先を document.[[ActiveLocks]]["screen"] とする。
      6. promise を lock で解決する。
  8. promise を返す。

9. WakeLockSentinel インターフェース 

WebIDL[SecureContext, Exposed=(Window)]
interface WakeLockSentinel : EventTarget {
  readonly attribute boolean released;
  readonly attribute WakeLockType type;
  Promise<undefined> release();
  attribute EventHandler onrelease;
};

WakeLockSentinel オブジェクトは、プラットフォームウェイク ロックへのハンドルを提供し、手動で解放されるか、 基盤となる プラットフォームウェイクロックが解放されるまで保持する。その 存在により、プラットフォームウェイクロックは、指定された ウェイクロック 種別について有効に保たれる。また、すべての WakeLockSentinel インスタンスのうち、 指定された ウェイクロック種別のものを解放すると、基盤となる プラットフォームウェイク ロックが解放される。

注記
ウェイクロックの自動解放、文書が完全にアクティブでなくなった 場合の処理、および 文書が可視状態でなくなった 場合の処理を参照。 これらには、指定されたウェイクロックが解放される場合について記載されている。 解放を行うのは、 ユーザー エージェントである。

9.1 内部スロット

WakeLockSentinel インスタンスは、 次の 内部 スロットを持つものとして作成される：

内部スロット 初期値 説明（非規範的）
[[Released]] false 指定された WakeLockSentinel が解放されたかどうか。

9.2 released 属性

released のゲッターの手順は、 this.[[Released]] を返すことである。

注記
WakeLockSentinel が 一度解放されると、 released は true になり、その値は以後 変化しない。

9.3 type 属性

type のゲッターの手順は、this の ウェイクロック種別を返すことである。

9.4 release() メソッド

release() メソッドの手順は 次のとおりである：

  1. もし this の [[Released]] が false であれば、 ウェイクロックを解放する手順を実行する。その際、lock の設定値を this とし、type の設定値を 次の値とする： this の type 属性の値。
  2. 次の値で解決されるプロミスを返す： undefined。

9.5 onrelease 属性

onrelease 属性は、イベントハンドラー IDL 属性であり、"onrelease" イベント ハンドラーに対応する。その イベントハンドラーのイベント種別は "release" である。

これは、指定された WakeLockSentinel オブジェクトのハンドルが解放されたことをスクリプトに通知するために使われる。その原因は、 release() メソッドの 呼び出し、または ウェイクロックを解放した ユーザーエージェントによるものである。

注記
WakeLockSentinel オブジェクトのハンドルが解放されても、 必ずしも プラットフォームウェイクロックのうち、指定された ウェイク ロック種別のものが解放されたことを意味しない。それは プラットフォームウェイク ロックの [[ActiveLocks]] 内部 スロットによる。ウェイクロックを 解放する手順を参照。
注記
例 2には、 onrelease イベントハンドラーの使用例がある。

9.6 ガベージコレクション

WakeLockSentinel オブジェクトに 1つ以上のイベントリスナーが、 "release" に対して登録されており、かつ WakeLockSentinel オブジェクトがまだ 解放されていない間は、次の強参照の存在が 必須である： 参照元は Window オブジェクトであり、そこから WakeLockSentinel オブジェクトのコンストラクターが 呼び出されたものとする。参照先は、 WakeLockSentinel オブジェクト自身である。

WakeLockSentinel オブジェクトによって、 画面ウェイクロックタスクソースにキューに入れられたタスクがある間は、必須である、次の強参照が存在することが。 参照元は Window オブジェクトであり、その WakeLockSentinel オブジェクトの コンストラクターがそこから呼び出されたものとする。参照先は、その WakeLockSentinel オブジェクトである。

11. ウェイクロックの管理

この節は、各 ウェイクロック種別に等しく、 独立して適用される。ただし、特定の ウェイクロック種別が明示的に 言及されている場合を除く。

ユーザー エージェントが ウェイクロックを 取得するには、基盤となるオペレーティングシステムにロックの適用を 要求する。基盤となるオペレーティングシステムへの要求に 戻り値があっても、それは確認されない。言い換えると、ユーザーエージェントには、 必須である、ウェイクロックの取得を助言的なものとしてのみ扱うことが。

逆に、ユーザーエージェントが ウェイクロックを解放するには、 基盤となるオペレーティングシステムにウェイクロックの適用を終了するよう 要求する。ロックが解放されたとみなされるのは、オペレーティングシステムへの 要求が成功した場合だけである。

ウェイクロックが 適用可能であるのは、 オペレーティングシステムの状態がロックの適用を許す場合である （例えば、バッテリーに十分な残量がある場合）。

画面ウェイクロックについて、次のことは 禁止される：適用可能であることが、 ユーザーが手動で画面を消灯した後から、再び点灯するまで 続くこと。

注記
ウェイクロックが適用可能かどうかは一時的な条件である。例えば、 バッテリー残量が少なくても、その後充電されることがある。そのため、 可視性の要件と同様に、これはウェイクロックの自動管理の一部であり、 ウェイクロックを許可するか拒否するかを決定する処理の 一部ではない。

11.1 ウェイクロックの自動解放

ユーザーエージェントは、いつでも ウェイクロックを解放することができる。例えば、 次の場合である：

  • 無限ループや、設定された時間制限（ある場合）を超過するタスクなど、 異常な動作を検出した場合。
  • バッテリー残量が少なく、放電中と判断される場合。
  • ユーザーが何らかのデバイス省電力モードを有効にした場合。
  • ユーザーの在席状態に基づいて画面を暗くするか消灯するよう、 オペレーティングシステムが設定されている場合。

11.2 文書が完全にアクティブでなくなった場合の処理

Document document が、それまでの 完全にアクティブな状態を失った場合、ユーザーエージェントは次の 手順を実行しなければならない：

  1. それぞれについて、lock を document.[[ActiveLocks]]["screen"] の各項目として：
    1. ウェイクロックを解放する手順を、document、lock、および "screen" を用いて実行する。

  1. もし state が "hidden" でなければ、これらの手順を中止する。

11.4 ウェイクロック取得アルゴリズム

ウェイクロックを 取得するには、指定された type に対して、 次の手順を実行する：

  1. もし種別 type のウェイクロックが 適用可能でなければ、 これらの手順を中止する。
  2. 基盤となるオペレーティングシステムに、ウェイクロックを 取得するよう、種別 type を指定して要求する。

11.5 ウェイクロック解放アルゴリズム

ウェイクロックを 解放するには、指定された document、 lock、および type に対して、次の 手順を実行する：

  1. もし document.[[ActiveLocks]][type] が lock を含んでいなければ、これらの手順を中止する。
  2. lock を、 document.[[ActiveLocks]][type] から取り除く。
  3. もし document.[[ActiveLocks]][type] が 空であるならば、次の手順を 並列に実行する：
    1. 基盤となるオペレーティングシステムに、ウェイクロックを 解放するよう、種別 type を指定して要求し、success を、操作が成功した場合は true、 そうでなければ false とする。
    2. もし success が true であり、かつ type が "screen" であれば、 次を実行する：
      1. 期限が切れると画面が実際に消灯する、 プラットフォーム固有の非アクティブタイマーをリセットする。
      注記
      非アクティブタイマーをリセットすると、ウェイクロックの解放直後に 画面が消灯するのを防げる。
  4. lock の [[Released]] を true に設定する。
  5. イベントを発火する。名前を "release"、対象を lock とする。

12. セキュリティ上の考慮事項

画面ウェイクロックにより、デバイスのさまざまな構成要素、特に ディスプレイが、通常より高い電力消費で動作することが ある。これにより、デバイスの自動ロックが妨げられたり、 バッテリーの消耗が速まったりするなど、望ましくない影響が生じることがある。 バッテリーの消耗が速まることは、モバイルデバイスでは特に問題となる。 固定電源をすぐに利用できないことが多いためである。 予期しないときにバッテリーが完全に切れると、 ユーザーは通話の発信や着信、およびネットワークサービスを 利用できなくなることがあり、これには緊急通報サービスも含まれる。

実装が画面ウェイクロックの要求を無視することは 許容される。例えば、 バッテリー残量が少ない場合や、ユーザーがデバイスを 省電力モードにしている場合である。

13. プライバシー上の考慮事項

次のことが 推奨される：ユーザーエージェントは、画面ウェイクロックが 有効であることをユーザーが知るための UI や表示を提供する。 そのような UI は、特定のウェブアプリケーションが デバイスの電力消費に悪影響を及ぼしているかどうかをエンドユーザーが判断し、 希望に応じて対処する助けとなり得る。

14. 例

この節は非規範的である。

例 1: 画面ウェイクロックを取得して解放する 
function tryKeepScreenAlive(minutes) {
  navigator.wakeLock.request("screen").then(lock => {
    setTimeout(() => lock.release(), minutes * 60 * 1000);
  });
}

tryKeepScreenAlive(10);

この例では、ユーザーがチェックボックスをクリックすることで 画面ウェイクロックを要求できる一方、ウェイクロックの状態が変わった場合は、 チェックボックスのチェック状態を更新する：

例 2 
const checkbox = document.createElement("input");
checkbox.setAttribute("type", "checkbox");
document.body.appendChild(checkbox);

const sentinel = await navigator.wakeLock.request("screen");
checkbox.checked = !sentinel.released;
sentinel.onrelease = () => checkbox.checked = !sentinel.released;

この例では、2つの異なるウェイクロック要求を作成し、 それぞれ独立して解放する：

例 3 
let lock1 = await navigator.wakeLock.request("screen");
let lock2 = await navigator.wakeLock.request("screen");

lock1.release();
lock2.release();
